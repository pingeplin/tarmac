# 2607.0004 Option+Arrow Word-Jump in Terminal Cards

**Date:** 2026-07-02
**Status:** implemented
**Author:** EP Lin

## Context

`termKeyBinding.ts` (`desktop/src/kit/termKeyBinding.ts`) is the pure decider
behind Tarmac's Ghostty-parity terminal editing shortcuts
([2606.0007](2606.0007_ghostty_macos_key_editing_terminal_cards.md), issue
#21): `App.tsx`'s capture-phase `window` keydown listener calls
`bytes(input)` for every keystroke while a live terminal is focused, and if
it returns a byte array, injects those bytes via `termInput()` and swallows
the event (`preventDefault`/`stopPropagation`) before it ever reaches
xterm.js. If it returns `null`, the key falls through to xterm.js's own
`attachCustomKeyEventHandler`/default keydown handling in `TerminalCard.tsx`.

`bytes()` today recognizes five rows: ⌘⌫, ⌘←, ⌘→, ⌥↑, ⌥↓. The existing test
suite (`termKeyBinding.test.ts`, scenario S11) explicitly asserts that
⌥←/⌥→ **defer** to xterm.js — "keys that must stay xterm.js's" — on the
assumption that xterm.js's `macOptionIsMeta: true` option (set in
`desktop/src/cards/TerminalCard.tsx:122`) already produces correct word-jump sequences for
Option+Arrow. That assumption was carried over from the pre-Tauri
Swift/SwiftTerm app (`ed3c92a`, "Replace the Swift/AppKit UI with a Tauri 2 +
React + xterm.js cockpit"), where the underlying native key handling differed.

## Motivation

Issue [#61](https://github.com/pingeplin/tarmac/issues/61): in the current
Tauri/WKWebView/xterm.js stack, ⌥←/⌥→ does not word-jump. Tracing xterm.js's
non-kitty keyboard path (`evaluateKeyboardEvent`, the code the terminal
actually uses since a plain shell never enables the kitty keyboard protocol)
shows the arrow-key switch cases (keyCode 37–40) build their CSI modifier
byte purely from raw DOM modifier bits and never consult `macOptionIsMeta` —
so Option+Left produces `ESC[1;3D` (modifier code 3, plain "Alt"), not a
Meta-flavored sequence. Whatever bytes actually survive to the PTY in
practice (the issue's repro shows only the bare final letter, e.g. `D`,
landing in the shell buffer — a WKWebView/xterm.js interaction this spec
does not need to fully diagnose to fix), the practical fact is: **macOS's
default zsh (`bindkey -e`, no user dotfiles — verified via `zsh -f -c
'bindkey -e; bindkey'` on a clean invocation) does not bind `\e[1;3D` /
`\e[1;3C` to word motion at all.** It binds only the Meta-letter forms
`\eb` → `backward-word` and `\ef` → `forward-word` — the same convention
real GNU readline binds by default, and the same bytes Terminal.app/iTerm2
send for Option+Left/Right out of the box. So even a byte-perfect
`ESC[1;3D` would silently no-op in the repo's target shell, not word-jump.
This is what the existing ⌥↑/⌥↓ row already works around (it explicitly
injects `ESC[1;3A`/`ESC[1;3B` rather than trusting xterm.js) — ⌥←/⌥→ needs
the same explicit treatment, with the byte convention that's actually bound.

## Proposed Solution

### Overview

Extend `termKeyBinding.ts`'s `bytes()` switch. The `ArrowLeft`/`ArrowRight`
cases **already exist** — they emit Ctrl-A/Ctrl-E for ⌘←/⌘→ under the
`metaOnly` gate. Add an `altOnly` branch to each of those two existing cases
so that ⌥←/⌥→ emit the Meta-letter escape sequences readline/zle bind to
word motion by default (`ESC b` / `ESC f`), leaving the existing `metaOnly`
→ Ctrl-A/Ctrl-E result untouched. This mirrors exactly how ⌘⌫/⌘←/⌘→/⌥↑/⌥↓
are already handled. No change to `App.tsx`'s wiring, `TerminalCard.tsx`, or
the kitty/composing gates is needed — the existing dispatch already routes
every keystroke through this decider first, and the `altOnly`/`composing`/
`kittyActive` gating machinery already applies uniformly to whatever rows
the switch recognizes.

### Key Components

- **`bytes()` in `desktop/src/kit/termKeyBinding.ts`** — the `ArrowLeft` and
  `ArrowRight` cases already exist and currently return `metaOnly ? [0x01] :
  null` / `metaOnly ? [0x05] : null` (⌘←/⌘→ → Ctrl-A/Ctrl-E). Extend each
  with an `altOnly` branch so they become `return metaOnly ? [0x01] : altOnly
  ? [0x1b, 0x62] : null;` and `return metaOnly ? [0x05] : altOnly ? [0x1b,
  0x66] : null;` (⌥← → `ESC b`, ⌥→ → `ESC f`). Do **not** add a second `case
  "ArrowLeft"`/`case "ArrowRight"`: a duplicate label leaves the new branch
  unreachable, so ⌥←/⌥→ would keep returning `null` and S15/S16 would stay
  red.
- **`termKeyBinding.test.ts`** — S11 currently asserts ⌥←/⌥→ defer
  (`toBeNull()`); this scenario's premise is what issue #61 falsifies, so it
  must be corrected to assert the new byte sequences instead, not merely
  deleted. Ctrl+Left/Right (Mission Control) staying deferred is unaffected
  and stays part of the no-regression coverage.

### Data Flow

1. User presses ⌥+ArrowLeft (or Right) while a terminal card is focused and
   the terminal switcher is closed.
2. `App.tsx`'s capture-phase `window` keydown handler (unchanged) reads
   `focusedLiveTermId()` and `focusedTermKittyActive()`, builds a
   `TermKeyInput`, and calls `bytes()`.
3. `bytes()` now recognizes `ArrowLeft`/`ArrowRight` with `alt` as the sole
   intent modifier and returns `[0x1b, 0x62]` / `[0x1b, 0x66]`.
4. `App.tsx` calls `termInput(termId, String.fromCharCode(...binding))`,
   `preventDefault()`s, `stopPropagation()`s — xterm.js never sees the event.
5. The PTY/shell receives `ESC b` or `ESC f`, which zsh's (and bash
   readline's) default emacs keymap binds to `backward-word`/`forward-word`.

### Interface Contract

`bytes()`'s existing signature and gating semantics (`composing`/
`kittyActive` unconditional `null`, exact-modifier matching, `code`-keyed
switch) are unchanged — this is a data-only extension of the two existing
`ArrowLeft`/`ArrowRight` cases (an `altOnly` branch added to each; the
`metaOnly` → Ctrl-A/Ctrl-E branch untouched):

```
bytes({ code: "ArrowLeft",  alt: true, meta: false, ctrl: false, shift: false, composing: false, kittyActive: false }) → [0x1b, 0x62]  // ESC b
bytes({ code: "ArrowRight", alt: true, meta: false, ctrl: false, shift: false, composing: false, kittyActive: false }) → [0x1b, 0x66]  // ESC f
```

## Alternatives Considered

- **`ESC[1;3D` / `ESC[1;3C` (same CSI-with-modifier-3 convention as the
  existing ⌥↑/⌥↓ rows)** — more internally consistent with the Up/Down
  rows, and it would eliminate the corruption symptom (a well-formed,
  correctly-escaped CSI sequence that a shell doesn't recognize is silently
  swallowed by zsh/readline, not echoed as text). Rejected as the primary
  fix because it does not satisfy the issue's actual expected behavior —
  verified that vanilla macOS zsh does not bind this form to word motion,
  so the cursor still wouldn't move. `ESC b`/`ESC f` is both corruption-free
  and functional.
- **Fix inside `TerminalCard.tsx` / xterm.js's `macOptionIsMeta` handling
  directly** (e.g. a custom `attachCustomKeyEventHandler` interception) —
  would duplicate the focused-terminal/kitty-gating logic `App.tsx` +
  `termKeyBinding.ts` already own, and diverge from the established pattern
  every other Ghostty-parity shortcut in this file follows. Rejected in
  favor of extending the existing single decision point.

## Acceptance Scenarios

Building on `termKeyBinding.test.ts`'s existing S1–S14 (2606.0007);
new/changed scenarios below.

### Happy Path
- **S15:** Given `code: "ArrowLeft", alt: true` (all other modifiers false, not composing, kitty inactive), when decided, then bytes == `[0x1b, 0x62]` (`ESC b`).
- **S16:** Given `code: "ArrowRight", alt: true` (all other modifiers false, not composing, kitty inactive), when decided, then bytes == `[0x1b, 0x66]` (`ESC f`).

### Edge Cases
- **S17:** Given the ⌥← and ⌥→ rows (S15/S16) re-decided with `shift` additionally held (⇧⌥←, ⇧⌥→), when decided, then result is `null` — exact-modifier gating applies to the new rows exactly as it does to ⌥↑/⌥↓ (mirrors existing S8).
- **S18:** Given the ⌥← and ⌥→ rows, when re-decided with `composing: true`, then result is `null`; when re-decided with `kittyActive: true`, then result is `null` (mirrors existing S9/S10 — the shared gates apply to the new rows too, proven by a paired on/off assertion).

### Error Scenarios
- **S19 (was S11):** Given `ArrowLeft`/`ArrowRight` with **ctrl** as the sole intent modifier (⌃←/⌃→, claimed by macOS Mission Control), when decided, then result is `null` — this half of the old S11 is unaffected by the fix and must keep passing. (The other half of old S11 — ⌥←/⌥→ deferring — is superseded by S15/S16 and must be removed or corrected, not left asserting the old, now-wrong, behavior.)

### No-Regression (shared cases)
- **S2/S3 (unchanged, must stay green):** The `ArrowLeft`/`ArrowRight` cases the fix extends are the same ones that already serve ⌘←/⌘→ under the `metaOnly` gate. Existing S2 (`code: "ArrowLeft", meta: true` → `[0x01]`, Ctrl-A) and S3 (`code: "ArrowRight", meta: true` → `[0x05]`, Ctrl-E) must continue to pass — the fix adds an `altOnly` branch to these cases, it does not replace their `metaOnly` branch. A regression here is the primary risk of extending (rather than duplicating) the two cases.

## Trade-offs and Limitations

- `ESC b`/`ESC f` assumes an emacs-mode-bound shell (zsh's and bash
  readline's default). A shell in vi line-editing mode (`bindkey -v` /
  `set -o vi`) would interpret a bare `ESC` as "exit insert mode" and `f`
  as vi's find-character motion, not forward-word — a pre-existing class of
  limitation this fix doesn't newly introduce (the existing ⌘⌫/⌘←/⌘→/⌥↑/⌥↓
  rows carry the same emacs-mode assumption via raw Ctrl-A/Ctrl-E bytes).
- Up/Down are unaffected by this spec; only Left/Right are added.
