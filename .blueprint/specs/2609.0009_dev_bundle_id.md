# 2609.0009 Per-worktree window title for `make run`

**Date:** 2026-09-07 (re-scoped same day after the identifier spike)
**Status:** final
**Author:** EP Lin
**Issue:** [#102](https://github.com/pingeplin/tarmac/issues/102) `chore(dev): give each dev app its own bundle identifier via tauri dev --config`

> House-numbered `2609.0009`, assigned at the issue gate. The file name still reads
> `dev_bundle_id` for continuity with the issue; the **contract is the window title**, not the
> bundle identifier — see *Why the bundle identifier is not delivered*.

## Context

Several dev apps routinely run at once — one per worktree — alongside the installed
`/Applications/Tarmac.app`. During the #89 QA run (2026-09-05) automation targeting "Tarmac"
resolved to the wrong one: the installed app's window was moved to another display and received
stray keystrokes.

`make run` already pins per-worktree `TARMAC_SOCKET` and `TARMAC_STATE` under `$(ROOT)/.dev/`,
where `ROOT := $(abspath $(dir $(lastword $(MAKEFILE_LIST))))` (`Makefile:1`). What is missing is
any **on-screen** tell of which worktree a given dev window belongs to.
`desktop/src-tauri/tauri.conf.json:15` configures the title `tarmac`, but that is only the
*launch* title: `desktop/src/App.tsx` runs a `useEffect` that calls
`getCurrentWindow().setTitle(" ▞ <board name> ")` on mount and on every board switch, so the
steady-state title of a running dev app is the active board's name — identical across worktrees
that opened the same board.

## Why the bundle identifier is not delivered

The original version of this spec proposed `tauri dev --config '{"identifier":…}'`. A spike on
2026-09-07 (recorded as a comment on
[#102](https://github.com/pingeplin/tarmac/issues/102)) established that route is infeasible:

- `tauri-codegen 2.6.3` (`src/context.rs:302-333`) embeds only `CFBundleName` and the two version
  keys into the dev binary's `__TEXT,__info_plist`. It never writes `CFBundleIdentifier`, so
  `tauri dev --config '{"identifier":…}'` changes nothing observable.
- The dev app's bundle id is **already NULL on `main`** — `lsappinfo info -only bundleid <pid>`
  returns `[ NULL ]` and `LSDisplayName` is `tarmac-app`, the executable filename. Launch Services
  ignores an embedded plist entirely for a non-bundled executable, so even a
  `src-tauri/Info.plist` sidecar (which *is* merged into the binary) leaves the bundle id NULL.
- That sidecar is additionally picked up unconditionally by `tauri build`
  (`tauri-cli/src/interface/rust.rs:1650-1663`) and merged last by the bundler
  (`tauri-bundler/.../macos/app.rs:354-360`), so it would silently override the release
  `com.tarmac.desktop`. Not adopted.

Two consequences worth recording. First, a per-worktree bundle id would need a real `.app`
wrapper bundle built at `make run` time — a separate spike, out of scope here. Second, the #89
incident was **not** a bundle-id collision: the dev app has no bundle id at all, so bundle-id
targeting can only ever resolve to the installed app. Automation that must pick a specific Tarmac
should match on `lsappinfo`'s `executable path` (already worktree-unique) or on the window title
this change introduces — never on bundle id.

## Motivation

Deliver the other half of the issue's checklist, "distinguishable window titles". A titled window
is the tell a human reads at a glance and the handle AppleScript/computer-use can match on, and
unlike the identifier it is fully under our control.

## Proposed Solution

### Overview

`make run` exports one extra environment variable. Vite bakes it into the frontend bundle at build
time, and `App.tsx` appends it to the title it already sets.

```
VITE_TARMAC_DEV_LABEL=$(notdir $(ROOT))   # e.g. 102-dev-bundle-id
suffix                                     # " · 102-dev-bundle-id"
window title                               # " ▞ board-0 · 102-dev-bundle-id "
```

A *suffix* rather than a whole title because `App.tsx` owns the window title and rewrites it on
mount and on every board switch — a Rust `set_title` at setup is overwritten within the first
render (observed: ` ▞ board-0`). The `VITE_` prefix is load-bearing: it is what makes Vite expose
the value on `import.meta.env`, so no IPC round-trip or React state is needed.

`make bundle` and `make release` set no such variable, so a bundled or installed Tarmac gets the
empty suffix and its title is byte-identical to `main`'s ` ▞ <board name> `.

### Key components

- **`Makefile`, `run` recipe** — add `VITE_TARMAC_DEV_LABEL="$(notdir $(ROOT))" \` to the existing
  env prefix, alongside `TARMAC_SOCKET`/`TARMAC_STATE`/`TARMAC_DAEMON`/`PATH`. The recipe stays one
  backslash-continued shell command. No `--config` flag anywhere.

- **`Makefile`, the comment block above `run`** — extend the existing "TARMAC_SOCKET/TARMAC_STATE
  pin a stable per-worktree dev path" sentence to record that `VITE_TARMAC_DEV_LABEL` titles the
  window per worktree for the same reason, why the `VITE_` prefix matters, and that
  `bundle`/`release` set it nowhere so a shipped Tarmac's title is unchanged. **This is the one
  place the rationale lives** — not `docs/architecture.md` (a sibling branch is editing that file
  and this change must stay disjoint from it), and not duplicated across the source files.

- **`desktop/src/kit/devTitle.ts`** — a **pure function**
  `devTitleSuffix(label: string | undefined): string`: trims the label and returns
  `" · <trimmed>"`, or `""` when the label is absent, empty or whitespace-only. The **trimmed**
  value is what appears in the title, so `"  wt  "` and `"wt"` produce the identical `" · wt"`.
  All the decidable behaviour lives here, in `kit/`, which is where this repo puts logic it
  intends to unit-test.

- **`desktop/src/kit/devTitle.test.ts`** — Vitest cases for S1 and S2.

- **`desktop/src/vite-env.d.ts`** — declare `readonly VITE_TARMAC_DEV_LABEL?: string` on
  `ImportMetaEnv` so the read is typed rather than `any`. Optional, because the shipped build has
  no such variable.

- **`desktop/src/App.tsx`** — one module-level constant,
  `const devSuffix = devTitleSuffix(import.meta.env.VITE_TARMAC_DEV_LABEL)`, interpolated into the
  existing title effect: `` setTitle(` ▞ ${name}${devSuffix} `) ``. The effect's dependency array
  is unchanged — the constant is fixed for the lifetime of the bundle.

- **Nothing else.** No Rust, no Tauri command, no IPC, no `tauri.conf.json` change, no daemon, no
  wire protocol, no script.

### Interface Contract

- **No Rust, wire-protocol, daemon, or IPC change.** `core/` and `desktop/src-tauri/` are
  untouched: no `Msg` variant, no Tauri command, no persisted state key. `tauri.conf.json` is
  untouched, so `identifier` stays `com.tarmac.desktop`, `productName` stays `Tarmac`, and the
  window's configured `title`, `width`, `height`, `minWidth`, `minHeight` and `theme` are
  unchanged.
- **The one behavioural contract added** is: with `VITE_TARMAC_DEV_LABEL=<label>` non-blank after
  trimming in the environment of the Vite build, the window title is
  ` ▞ <board name> · <trimmed label> `; with the variable unset, empty or whitespace-only, the
  title is the unchanged ` ▞ <board name> `. It holds **after frontend mount and across board
  switches** — it is not a launch-instant-only claim.
- **Breaking change for callers: none.** No existing code reads `VITE_TARMAC_DEV_LABEL`; the name
  is new. The only edit to existing behaviour is the interpolation added to `App.tsx`'s title
  template, which is a no-op when the suffix is `""` — the shipped-app case, whose emitted title
  is byte-identical to `main`'s.

## Alternatives Considered

### `--config '{"identifier":…}'` (the original proposal)

Infeasible — see *Why the bundle identifier is not delivered*. Rejected on spike evidence.

### Patching `app.windows[0].title` via `--config`

`tauri-build` merges config with RFC 7396 JSON Merge Patch, in which **an array replaces the
target array wholesale**. Patching `{"app":{"windows":[{"title":"…"}]}}` would drop `width`,
`height`, `minWidth`, `minHeight` and `theme` from `tauri.conf.json` and launch a
differently-sized, light-themed window. Rejected.

### A Rust-only `set_title` in the `.setup` hook

Proven a no-op: `App.tsx`'s title effect overwrites it on first render. A build carrying exactly
that wiring reported ` ▞ board-0`, not the intended title. Rejected on runtime evidence — this is
what forced the label into the frontend.

### Passing the label over IPC (a `#[tauri::command]` + `invoke` + React state)

Implemented and working, then rejected as unnecessary machinery: it spent a Rust helper, a Tauri
command, an `invoke` wrapper, React state and an effect on a value that is fixed at build time.
`VITE_`-prefixed env is the idiomatic Vite route and reduces the change to one module-level
constant, with the pure function unit-tested in `kit/` where the repo already tests such logic.

### A generated per-worktree `.app` wrapper bundle

The only route to a real per-worktree bundle id, and it would also fix the title. It means
generating a bundle directory at `make run` time — a new build artifact, a new gitignore entry, a
stale-bundle failure mode, and `LSEnvironment` plumbing. Out of scope; file separately if
bundle-id targeting is ever actually needed.

## Testability

The label→suffix derivation is a pure function in `kit/` and **is** unit-tested by
`cd desktop && npm test` (already part of `make test`), which also typechecks the `App.tsx` and
`vite-env.d.ts` edits. The wiring around it — Vite's build-time substitution and the React effect
that applies the title — needs a running app and is covered by the runtime scenario S5, not by an
automated test; that matches the repo's standing position that the Tauri/React shell is verified
by QA rather than unit tests.

`make docs-check` scans only `docs/`, `README.md` and `CLAUDE.md`; for this change it is a
formality, not evidence. It is still in the DoD because it must not go red.

## Acceptance Scenarios

- **S1 [G] — the pure function derives the suffix, trimming its input.** Given `devTitleSuffix`,
  when it is called with `"102-dev-bundle-id"`, then it returns `" · 102-dev-bundle-id"`; and when
  called with a padded label, it agrees with the unpadded call — the surrounding whitespace never
  reaches the title. Automated, `desktop/src/kit/devTitle.test.ts`.

- **S2 [G] — an absent or blank label yields no suffix.** Given `devTitleSuffix`, when it is called
  with `undefined`, `""` or a whitespace-only string, then it returns `""`, so the title is the
  unchanged ` ▞ <board name> `. Automated, same file. (This is the case that protects
  `make bundle`/`make release` and the installed app: no variable, no suffix.)

- **S3 [G] — `make run` exports the label.** Given the changed Makefile, when the recipe is
  expanded without running it, then the printed command sets the variable to this worktree's
  directory name and passes **no** `--config`:

  ```sh
  make -n run | grep -q 'VITE_TARMAC_DEV_LABEL="102-dev-bundle-id"'
  make -n run | grep -c -- '--config'      # must report 0
  ```

  (As in S4: `grep -c` exits **1** when the count is `0`. That non-zero status *is* the pass —
  don't run this under `set -e` and read it as a failure.)

  Derivation from `ROOT` is proven without a second checkout by overriding it:
  `make -n ROOT=/tmp/fake-wt run | grep -q 'VITE_TARMAC_DEV_LABEL="fake-wt"'` (`ROOT :=` is a
  simple assignment, so a command-line variable wins).

- **S4 [G] — release paths are unaffected.** Given the change, when the release paths are
  inspected, then none of them carries the variable: `make -n bundle` prints no
  `VITE_TARMAC_DEV_LABEL`, `grep -c VITE_TARMAC_DEV_LABEL scripts/bundle.sh scripts/release.sh`
  reports `0` for both (`grep` exits `1` when it finds nothing — that non-zero status *is* the
  pass here; don't run it under `set -e` and read it as a failure), and
  `git diff origin/main -- desktop/src-tauri/tauri.conf.json` is empty.

- **S5 [G] — the running dev app is titled, durably.** Given this worktree, with
  `ROOT=/Users/eplin/workspace/tarmac-worktrees/102-dev-bundle-id` as an absolute path (do not
  rely on `$PWD`), when `make run` is launched in the background and the board has rendered, then
  the main window's title ends in ` · 102-dev-bundle-id` — e.g. ` ▞ board-0 · 102-dev-bundle-id `.

  Take the reading **after** the board renders, not at first paint: `App.tsx`'s title effect is
  precisely the thing under test.

  **Find the pid by executable path, never by name or by an absolute-path `pgrep`.** Cargo execs
  the app as the *relative* path `target/debug/tarmac-app` with cwd `desktop/src-tauri`, so
  `pgrep -f "$ROOT/desktop/src-tauri/target/debug/"` matches **nothing**, and a bare
  `ps | grep 'target/debug/tarmac-app'` is **ambiguous** — every worktree's dev app shows that
  same relative argv, which is precisely the collision this spec exists for. Confirm any candidate
  pid against the absolute executable path before trusting it:

  ```sh
  lsof -p <pid> -Fn | grep -m1 tarmac-app     # must be under $ROOT
  ```

  Then read the title:

  ```sh
  osascript -e 'tell application "System Events" to get name of every window of (first process whose unix id is <pid>)'
  ```

  **System Events needs an Accessibility grant and may be refused** (`-1743` / "not allowed
  assistive access"). If it is, report the error **verbatim** and record the title as
  *unverified* — do **not** widen the diff, grant permissions, or substitute a screenshot-based
  claim.

  **Failure mode / time bound.** The first `make run` after the change rebuilds the frontend; a
  changed `VITE_*` var does not invalidate the Rust crate, so no cargo recompile is expected.
  Allow up to 10 minutes for the app process to appear. If none has by then, S5 fails — capture the
  backgrounded `make run` output rather than retrying blind.

  **Cleanup, in this order:**
  1. `make kill-daemon` (socket-scoped). **Never `pkill tarmacd`** — that kills the user's
     installed Tarmac.
  2. `kill` this worktree's app pid and its `npm run tauri dev` / `node .../tauri dev` pids,
     identified by the worktree path in their argv. Do not kill by process name.
  3. `lsof -ti :1420 | xargs -r kill` — killing the shell can orphan Vite, and a leftover
     listener on 1420 blocks the next `make run`.

- **S6 [G] — the diff stays minimal.** Given the change, when the diff is reviewed, then
  `git diff --name-only origin/main` returns exactly: `Makefile`, `desktop/src/App.tsx`,
  `desktop/src/vite-env.d.ts`, `desktop/src/kit/devTitle.ts`, `desktop/src/kit/devTitle.test.ts`
  and this spec. In particular `desktop/src-tauri/`, `tauri.conf.json`, `scripts/`, `docs/` and
  `core/` are absent.

## Trade-offs and Limitations

- **The label is baked in at build time.** Changing `VITE_TARMAC_DEV_LABEL` requires restarting
  `make run` (a Vite rebuild), not merely reloading. Acceptable: the label is derived from the
  worktree, which does not change under a running app.
- **Label charset is not sanitized.** Any string lands in the title verbatim. A title is free-form
  text, so unlike a bundle identifier there is nothing to break — a pathological directory name
  produces an ugly title, not a failure.
- **The frontend owns the whole title.** Anything that later sets the title from Rust will be
  overwritten, exactly as the rejected setup-hook draft was. A future window-title feature must go
  through `App.tsx`'s effect.
- **The title format is a judgement call.** ` ▞ <board> · <label> ` keeps the board name first
  because that is what the existing effect optimises for; a reviewer may prefer the label leading.
  Changing it is a one-line edit plus the S1 assertion.
- **No per-worktree bundle identifier.** The dev app still reports a NULL bundle id, exactly as it
  does on `main` today. This change does not regress that; it routes around it. Automation must
  target the executable path or the window title.
- **`make bundle` output is untested here beyond the static checks** — S4 asserts the absence of
  the variable, not a rebuilt `.app`'s title. Since the suffix is `""` without it, the emitted
  title is byte-identical to `main`'s.
