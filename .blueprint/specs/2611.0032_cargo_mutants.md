# 2611.0032 Mutation testing for the Rust workspace

**Date:** 2026-11-22
**Status:** accepted
**Author:** EP Lin
**Issue:** #486

## Context

The rule "a test that would pass before your change is not a test of your change" is held today by a reviewer who reads the diff and asks, for each line, "if this were wrong, would a test fail?" (the referee's thought-mutation). For Rust a tool can run that experiment: `cargo-mutants` changes one expression at a time, runs the tests, and names each change that no test saw.

Facts measured before this spec (cargo-mutants 27.1.0, this tree):

- The workspace has 1,354 mutants: `tarmacd` about 717, `tarmac-cli` 532, `tarmac-protocol` 104.
- The tool reads its config from `<workspace root>/.cargo/mutants.toml`. The workspace root is `core/`, so the file is `core/.cargo/mutants.toml`; a file at the repository root is not read (measured: an `exclude_re = ["."]` there removed nothing).
- A diff for `--in-diff` must name paths relative to `core/`. A diff from the repository root names `core/crates/…`, matches no file, and the tool exits 0 with nothing tested (from the tool's source; proven in *Recorded runs* before this change is merged).
- The tool's exit codes: 0 every tested mutant was caught, 2 a mutant was missed, 3 a test run timed out (it wins over 2), 4 the unmutated tests fail, 5 and 6 the diff does not fit the tree or is not a diff, 1 and 70 a usage or internal error. A mutant that does not compile ("unviable") changes no exit code.
- One place in the three crates sends a signal: `TermHandle::kill` in `core/crates/tarmacd/src/term.rs` (`make arch-check` holds that). Its two mutants only narrow what is signalled, but the guarantee "no mutant widens a signal" is true only while that stays so.
- Every path that `tarmacd` and `tarmac-cli` write comes from `HOME`, `CLAUDE_CONFIG_DIR`, a `TARMAC_*` variable, or the current directory. A terminal that the daemon starts runs a shell, which reads its start-up files from `HOME` (or `ZDOTDIR`).

## Motivation

A pilot on `tarmac-protocol` left 19 of 104 mutants alive; on 12 mutants of `tarmacd`, one. The reviewer's thought experiment is slow and misses these. The owner's rule for this repository is that a check a tool can decide is not left to judgment, and that a surviving mutant in a pull request fails CI from the first day.

## Proposed Solution

### Overview

One script, `scripts/check/mutants.mjs`, runs `cargo mutants` on the Rust lines a branch changed and words the result with the reporter of the other checks. `make mutants` calls it; a CI job calls `make mutants`; a weekly workflow calls it over the whole workspace with `--report`: it words the survivors and fails only when it could not run.

The script, not the caller, makes the run safe: it starts the tool with a small, fixed environment and a `HOME` that is a new empty directory, so a mutated path, and a shell that a mutated daemon starts, cannot reach the real home.

### Key Components

- **`scripts/check/mutants.mjs`** — the check. Arguments: `--base <ref>` (default `origin/main`), `--all` (the whole workspace, no diff; a `--base` beside it is accepted and not read, because `make mutants` always passes one), `--shard <k>/<n>` (passed to the tool, `k` from 0; with `--all` only), `--report` (a survivor is worded as always, to stderr and to the file `$GITHUB_STEP_SUMMARY` names when that is set, but the exit code is 0; "cannot run" stays 2), `--jobs <n>` (a positive integer, default 2).
- **`core/.cargo/mutants.toml`** — the one exclusion, `TermHandle::kill`, with its reason in a comment.
- **`make mutants`** — `node scripts/check/mutants.mjs --base $(BASE)`; `ALL=1`, `SHARD=k/n` and `JOBS=n` map to the arguments. Not part of `make test`.
- **`.github/workflows/mutants.yml`** — job `mutants (rust, in diff)` on every pull request; job `mutants (rust, all)` on a weekly schedule and on `workflow_dispatch`, as 8 shards (`0/8` … `7/8`) with `REPORT=1`. A red weekly shard means the run did not work, not that a mutant survived. Its survivors are filed as issues by hand, the first time after this change is merged.
- **`.gitignore`** — `/core/mutants.out*/`.
- **Docs** — `CLAUDE.md` (*Build, run, test*), `docs/workflow.md`, `CONTRIBUTING.md`.

### Data Flow (a diff run)

1. Find the repository root and `core/`. Find the merge base of `--base` and `HEAD`. An unknown ref is "cannot run".
2. Take `git diff --relative --src-prefix=a/ --dst-prefix=b/ --no-ext-diff --no-textconv --no-color <merge base> -- '*.rs'` with `core/` as the current directory. The prefixes are forced because the tool reads only `b/` or none: a user's `diff.mnemonicPrefix` or `diff.noprefix` would give a diff that matches no file, and a run that tests nothing and passes. It compares the merge base with the working tree, so it holds uncommitted changes to tracked files too: the tool mutates the tree as it is. A new `.rs` file under `core/` that git does not track and does not ignore is added to the diff as a whole new file (`git diff --no-index -- /dev/null <file>`, also from `core/`), so a file that is not yet committed is mutated like the rest. Nothing is written to the index.
3. An empty diff: print one line on stderr (`mutants: no Rust change against <base>`) and exit 0. The tool is not needed and not started.
4. Check the tool: `cargo mutants --version` must print the version this script pins (`27.1.0`). Missing or another version is "cannot run", with the install command.
5. Make a temporary directory. In it: `home/` (empty) and the diff file.
6. Start `cargo mutants --workspace --no-shuffle --jobs <n> --in-diff <file> --output <core>` in `core/`, with the environment of *The environment of a run*. The tool's own progress goes to the terminal unchanged.
7. Read the result (*Exit codes*) from the tool's exit code and from `core/mutants.out/missed.txt` and `timeout.txt` (one mutant per line, a documented format); for exit 0, the number of tested mutants from the tool's result files (S35 names them).
8. Remove the temporary directory, in every outcome.

### The environment of a run

An allow-list, not a block-list: a variable that is not named here does not reach the tool or the tests.

| Variable | Value |
|---|---|
| `HOME` | the new empty directory |
| `CARGO_HOME` | the caller's value, else `<real home>/.cargo` |
| `RUSTUP_HOME` | the caller's value, else `<real home>/.rustup` |
| `PATH`, `TMPDIR`, `LANG`, `LC_ALL`, `TERM`, `USER`, `LOGNAME`, `SHELL` | the caller's value, when set |
| `CARGO_TERM_COLOR`, `NO_COLOR`, `CI`, `GITHUB_ACTIONS`, `RUNNER_OS`, `RUNNER_TEMP` | the caller's value, when set |
| `RUSTUP_TOOLCHAIN` | not passed: `rust-toolchain.toml` decides |

So `CLAUDE_CONFIG_DIR`, `ZDOTDIR` and every `TARMAC_*` variable are absent. `GITHUB_ACTION` is not passed either, so the tool writes no annotations of its own: the report below is the one message.

### Exit codes

| Tool | This check | Message |
|---|---|---|
| 0 | 0 | one line on stderr: how many mutants were tested (also when that is 0) |
| 2 | 1 | the `mutants` failure: each missed mutant |
| 3 | 1 | the `mutants` failure: each mutant whose tests timed out, and each missed one |
| 2 with `missed.txt` absent or empty, or 3 with `timeout.txt` absent or empty | 2 | cannot run: the result cannot be read |
| 4 | 2 | cannot run: the tests fail with no mutation |
| 5, 6 | 2 | cannot run: the diff does not fit the tree |
| other, or the tool cannot be started, or its version is not the pinned one | 2 | cannot run |

### Interface Contract

A failure (exit 1), on stderr, through `failure()` of `report.mjs`:

```
✗ mutants: 2 changes to the code that no test saw
  at   crates/tarmac-cli/src/wait.rs:43:9: replace wait::helper -> Option<Child> with None
       crates/tarmacd/src/proc.rs:185:41: replace * with + in proc_facts
  why  each line is a change the tool made to the code; the tests still passed, so no test holds that behaviour
  fix  add a test that fails with that change (see the change: core/mutants.out/diff/), or list the mutant in core/.cargo/mutants.toml with the reason it cannot be seen
  then make mutants
```

Each `at` line is a line of `missed.txt` or `timeout.txt` as the tool wrote it. The count in the summary is the number of `at` lines, missed and timed out together; for one it reads `1 change to the code that no test saw`.

A timed-out mutant is in the same `at` list with the suffix ` (the tests did not end)`, and `why` gets a second line: `a time-out is not a catch: add a test that fails fast, or exclude the mutant with its reason`.

"Cannot run" (exit 2) uses `cannotRunFor("mutants", "make mutants")`. For a missing or wrong tool the `fix` is `cargo install cargo-mutants --version 27.1.0 --locked`.

`core/.cargo/mutants.toml`:

```toml
# The one place that sends a signal. Its mutants signal less, not more, but a
# mutant here runs with a real pid: it is never tried. arch-check keeps
# libc::kill in this file.
exclude_re = ["TermHandle::kill\\b"]
```

The workflow installs the tool with `taiki-e/install-action` and `tool: cargo-mutants@27.1.0`. The version in the workflow and the one in the script are the same text; a test holds that.

## Alternatives Considered

### Call `cargo mutants` from the Makefile and from CI directly

Two definitions of the environment and of the diff, and the repository-root diff (which tests nothing and exits 0) is one typo away in either. One script holds both.

### `#[mutants::skip]` on `TermHandle::kill`

It needs the `mutants` crate as a normal dependency of the daemon. The config file needs nothing in the product.

### Run every test of the workspace for each mutant (`test_workspace = true`)

A mutant in `tarmac-protocol` would then also be tried against the daemon's and the CLI's suites, and fewer would survive. It makes each mutant cost the whole 80 s suite. The default (the mutated package's own tests) is kept: a crate's tests hold that crate's behaviour. One line in the config reverses it.

### A block-list for the environment (unset `TARMAC_*`, `CLAUDE_*`)

A new variable that moves a path would pass until someone adds it. The allow-list fails the other way: a variable a test needs is missing, the baseline fails, and the check says so.

### In `pre-push`

A branch with 100 mutants takes about half an hour. It stays a command a person or an agent runs before a review, and CI is the gate.

## Security Considerations

A mutant is the product with one wrong expression, run on a developer's machine. The limits:

- It cannot signal a process it does not own: the one signal site is excluded, and `arch-check` fails when a second one appears outside `term.rs`.
- It cannot write under the real home through any path the code derives: `HOME` is a new directory, and the variables that override a path are absent.
- A shell it starts reads no start-up file of the user: `HOME` is empty and `ZDOTDIR` is absent.
- Not limited: a mutant can still write where the code names an absolute path with no variable, and can use the network as the tests do. No such path exists in the three crates today (checked by search for *Recorded runs*).

## Acceptance Scenarios

The tests of the script (`scripts/check/mutants.test.mjs`) put a stand-in `cargo` first on `PATH`: a small script that answers `mutants --version`, records its arguments and environment to a file, writes a `mutants.out` it is told to write, and exits with a code it is told to use. They make a git repository with a `core/` directory in the temp directory. No scenario below except those marked *recorded run* needs the real tool.

### Happy Path

- **S1:** Given a branch whose diff against the base holds no `.rs` file under `core/`, when the check runs, then it exits 0, prints `no Rust change` on stderr (stdout is empty), and the stand-in was not started (also with no `cargo` on `PATH` at all).
- **S2:** Given a changed `.rs` file and a tool run that exits 0 after it tested 3 mutants, when the check runs, then it exits 0, stderr holds no failure and one line with the number 3, and stdout is empty.
- **S3:** Given a tool run that exits 2 with two lines in `missed.txt`, when the check runs, then it exits 1 and the report has both lines, unchanged, under `at`, the summary `2 changes to the code that no test saw`, and the `why`, `fix` and `then` of the contract.
- **S4:** Given a changed file `core/crates/x/src/a.rs`, one committed change and one uncommitted change, when the check runs, then the diff file the tool was given names `crates/x/src/a.rs` (no `core/` before it) and holds both changes.
- **S5:** Given `--all`, when the check runs, then the tool is started with no `--in-diff`; with `--shard 3/8` it gets `--shard 3/8`; and it is started even when the diff is empty.
- **S6:** Given `--jobs 4`, the tool gets `--jobs 4`; given none, `--jobs 2`.

### The environment

- **S7:** Given a caller environment with `HOME`, `TARMAC_SOCKET`, `TARMAC_STATE`, `TARMAC_TERM_ID`, `TARMAC_CONFIG_DIR`, `CLAUDE_CONFIG_DIR`, `ZDOTDIR`, `GITHUB_ACTION` and a variable of no known name set, when the tool is started, then its environment holds none of them except `HOME`; `HOME` is an existing empty directory that is not the caller's `HOME`; `PATH` is the caller's. Given also `RUSTUP_TOOLCHAIN` and `GITHUB_ACTIONS` set, then `RUSTUP_TOOLCHAIN` is absent and `GITHUB_ACTIONS` has the caller's value.
- **S8:** Given no `CARGO_HOME` and no `RUSTUP_HOME` in the caller's environment, then the tool gets `<caller's HOME>/.cargo` and `<caller's HOME>/.rustup`; given both set, it gets those values.
- **S9:** Given any outcome (exit 0, 1 or 2), when the check ends, then the temporary directory with the stand-in home and the diff file is gone.

### Edge Cases

- **S10:** Given a tool run that exits 3 with one line in `timeout.txt` and one in `missed.txt`, then the check exits 1, the summary is `2 changes to the code that no test saw`, the timed-out mutant has the suffix ` (the tests did not end)`, the missed one is listed too, and `why` has the time-out line.
- **S11:** Given a diff that changes only a `.rs` file outside `core/`, or only non-Rust files inside it, then S1 holds (exit 0, tool not started).
- **S12:** Given a tool run that exits 2 but `missed.txt` is absent or empty, then the check exits 2 ("cannot run": the result cannot be read), not 0 and not 1.
- **S13:** Given a `HEAD` that is the base itself (nothing changed) and a clean tree, then S1 holds.

### Error Scenarios

- **S14:** Given a changed `.rs` file and no `cargo mutants` (the stand-in answers `no such command`), then the check exits 2 and the `fix` is the install command with the pinned version.
- **S15:** Given a tool of another version, then the check exits 2, names both versions, and the tool is not started on the tree.
- **S16:** Given a tool run that exits 4, then the check exits 2 and says the tests fail with no mutation; given 5 or 6, exit 2 and it says the diff does not fit the tree; given 70, exit 2.
- **S17:** Given a `--base` that names no commit, then the check exits 2 and names the ref. Given a directory that is in no git repository, exit 2.
- **S18:** Given an unknown argument, or `--shard` without `--all`, then the check exits 2 with the usage.

### The tree

- **S19:** `core/.cargo/mutants.toml` is the text of the contract; `.gitignore` holds `/core/mutants.out*/`. A test reads both.
- **S20:** `.github/workflows/mutants.yml`: the version after `cargo-mutants@` equals the script's pinned version; the pull-request job has no `paths:` or `paths-ignore:` filter (it must report for every pull request, also one with no Rust change) and checks out with `fetch-depth: 0`; both jobs call `make mutants`; the whole-workspace job runs on `schedule` and `workflow_dispatch` only, with `ALL=1`, `REPORT=1` and the 8 shards `SHARD=0/8` … `SHARD=7/8`. A test reads the file as text.
- **S21:** `make mutants` runs the script with `--base $(BASE)`; `ALL=1` adds `--all`, `SHARD=3/8` adds `--shard 3/8`, `JOBS=4` adds `--jobs 4`, `REPORT=1` adds `--report` (a test runs `make -n`).
- **S22:** `CLAUDE.md` describes `make mutants` under *Build, run, test*, `docs/workflow.md` says when to run it, and `CONTRIBUTING.md` names the CI job. `make docs-check` passes.

### Recorded runs (the real tool, written into this spec before the merge)

- **S23:** With the real tool and the config, `cargo mutants --list --workspace` in `core/` (a `--list` reads the source and runs nothing, so it may be run directly) has no line with `TermHandle::kill`, and two lines fewer than without the config.
- **S24:** In a throwaway clone, a branch that adds a function with a branch no test reaches: `make mutants` exits 1 and names that mutant. A branch that adds the same function with a test that holds it: exit 0. The same first branch with a diff taken from the repository root (the mistake this script prevents) is shown to test nothing.
- **S25:** Around the first real run that includes `tarmac-cli` and `tarmacd` mutants: the newest modification time under the user's Claude Code config directory and the user's Tarmac support directory is the same before and after (or the record lists each newer file with the program that wrote it, and that program is not the run), and no `tarmacd` process started by the run is left. (What a mutant wrote into the stand-in home is not shown: the script removes that directory, S9.)
- **S26:** The time of that run, and of the baseline, is written down. From it the record gives the expected time of one weekly shard (the whole workspace divided by 8) and says whether it is under 6 hours, the time limit of a job on a GitHub-hosted runner.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

- **Behavioral over structural** — assert the exit code, the report text, and what the stand-in tool was given; not internals.
- **Every test can fail** — S7 must fail when one variable leaks; S4 when the diff is taken from the repository root.
- **Deterministic, isolated, readable** — each test makes its own repository and its own stand-in directory.

Safety while building this: the real tool is run only through the script, never bare, once the script exists; `cargo mutants --list` is the exception (it builds and runs nothing). Nothing under `core/target` is executed by hand. No `make setup`, `lefthook install` or `git config` write in the maintainer's clone.

## Definition of Done

- [ ] Test suite is green (`make test`, `make lint`, `make fmt-check`, `make arch-check`, `make dco-check`).
- [ ] Every scenario S1…S22, S27…S32, S36…S38 and S42…S48 maps to at least one test; S23…S26, S33…S35 and S39…S41 are written into *Recorded runs*.
- [ ] No covered-but-vacuous scenario: each test fails under the smallest break of its behaviour.
- [ ] No implementation-quality blockers.

## Trade-offs and Limitations

- **Rust only.** Swift has no such gate (its own spike follows); JavaScript check scripts have none.
- **A mutant is tried against its own package's tests.** Behaviour of `tarmac-protocol` that only the daemon's suites hold counts as not held.
- **Slow.** About 18 s for a mutant of `tarmacd` at `--jobs 2`; a pull request with 100 mutants takes about half an hour in one job. The pull-request job is one job until a real pull request shows the need for shards.
- **An unstable test fails the job.** When the unmutated tests fail once (#469), the check is "cannot run" and the job is red; the remedy is to run it again. The check does not retry by itself: a retry would hide a baseline that is truly broken half the time.
- **A change with no mutant passes.** A diff of Rust lines in which the tool finds nothing to change (only deletions, comments, a file no crate includes) ends with `0 changes to the code tried` and exit 0.
- **An equivalent mutant needs a line in the config.** A change that no test can see (it alters nothing observable) fails the job until it is listed with its reason.
- **The weekly run only reports (`--report`).** It will have survivors from the first day (19 of 104 in the pilot of one crate). They are filed as issues, not fixed here.
- **Not covered:** a mutant in code under `#[cfg(test)]` or in `tests/` (the tool makes none); code behind `#[cfg(not(debug_assertions))]` (the tests build debug); a mutant that does not compile; the version of the tool on a developer's machine other than by refusing a wrong one.
- **A signal leaves a directory.** When the check is ended by a signal, the temporary directory with the stand-in home stays in the temp directory, and a signal sent to the node process alone leaves the tool running. Ctrl-C in a terminal reaches both.
- **The job blocks a merge only once it is in the `Protect main` ruleset.**

## Recorded runs (2026-11-22)

- **The tests under the allow-list.** Before the script was written: `cargo test --locked` in `core/` with exactly the environment of the table (an empty stand-in home). 936 passed, 0 failed; the stand-in home was still empty afterwards, and no daemon was left.
- **S23.** `cargo mutants --list --workspace` in `core/`: 1,354 lines with `--no-config`, 1,352 with the config. The two that go are `replace TermHandle::kill with ()` and `delete - in TermHandle::kill`; no other line differs.
- **S34.** `--list --workspace --shard k/8` for k = 0 … 7: 1,352 lines in all, no line twice, and the sorted whole equals the sorted list without a shard.
- **S24, the gate.** In a throwaway clone, a branch that adds `pub fn planted(n: u8) -> u8 { if n > 3 { n + 1 } else { n } }` to `tarmac-protocol` with no test: `make mutants` failed after 22 s with `✗ mutants: 7 changes to the code that no test saw` and the seven mutants of that function. With one test (`[0, 3, 4, 9]` gives `[0, 3, 5, 10]`): `7 mutants tested in 23s: 7 caught`, exit 0. The same branch's diff taken from the repository root (`git diff origin/main`, paths under `core/`): the tool says `No mutants to filter`; taken as the script takes it: 7 mutants.
