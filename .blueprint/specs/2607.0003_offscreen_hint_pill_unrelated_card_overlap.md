# 2607.0003 Offscreen-hint pill overlaps an unrelated on-screen card

**Date:** 2026-07-02
**Status:** implemented (algorithm revised post-review — see Trade-offs)
**Author:** EP Lin
**Issue:** [#64](https://github.com/pingeplin/tarmac/issues/64) — fix(board): offscreen-hint pill overlaps an unrelated on-screen card

## Context

This is a follow-up to [#58](https://github.com/pingeplin/tarmac/issues/58) ("offscreen-hint pill overlaps cards near the viewport edge"), which was **closed as won't-do**. #58's own prototype fix (threading each hint's own `cardRectView` and nudging the pill clear of *its own* card's visible sliver — drafted as spec `2607.0002_offscreen_hint_pill_edge_overlap.md` on a since-abandoned branch) never landed on `main`: the maintainer's closing comment on #58 concluded that a pill overlapping the *same* card it points to "isn't actually confusing enough to be worth the added complexity — that scenario is acceptable as-is," and explicitly separated out the actually-worth-fixing case: *"a pill can land on top of an unrelated, fully on-screen card that happens to extend to the viewport edge (e.g. a maximized/large card), since pill placement only avoids the card it's pointing at, not other cards."* That is #64, tracked here. `main`'s `desktop/src/kit/offscreenHints.ts` today is unchanged from before #58 — no `cardRectView`, no own-card nudge — so this spec builds directly on the original algorithm, not on #58's rejected approach.

**`stackPills()`** (`desktop/src/kit/offscreenHints.ts:76-124`) lays out offscreen-hint pills in four steps:

1. Project each hint to an edge via `hintPlacement()` (`boardWayfinding.ts`) — hints whose world center is inside the viewport are dropped entirely (`isOffscreen()` checks only the card's *center*, so a maximized/edge-spanning card whose center is on-screen never becomes a hint itself, and is therefore never considered by anything downstream *unless it's explicitly fed in as an obstacle*, which today nothing does).
2. Group projected hints by edge (`left`/`right`/`top`/`bottom`); sort each group by the along-edge coordinate (`p.along`: `y` for left/right, `x` for top/bottom).
3. Walk the sorted group keeping one running scalar `lastEnd` — the far edge, along-axis, of the previously placed pill in this group. For each pill: clamp its natural position into `[minBound+edgeMargin, maxBound-len-edgeMargin]`; if that's closer to the origin than `lastEnd+stackGap`, push it forward to `lastEnd+stackGap`; update `lastEnd` (`:100-101`, `:106-107`).
4. Round and emit `{left, top}`.

This is a 1-D forward-only nudge against a single running boundary, scoped only to the pill's own edge group. It never consults **any** card's rect — only sibling pills' rects, implicitly via `lastEnd` — so a large on-screen card that happens to abut the same edge band is completely invisible to the algorithm. That is the root cause of #64: a card whose *center* is on-screen (so `isOffscreen` never gives it a hint of its own) can still physically extend to a viewport edge — e.g. resized/maximized via the full-edge/corner resize feature (`.blueprint/specs/2606.0008_full_edge_and_corner_card_resize.md`) — and sit exactly where an unrelated, genuinely-offscreen card's pill lands.

`App.tsx`'s `offscreen` `useMemo` (`:1601-1629`, deps `[activeCards, viewport]`) is the one production call site. `activeCards` is every card on the active board (`activeBoard()?.cards ?? []`, `:1599`) — not just the signalling ones that get hints — each carrying `c.frame: WorldFrame` and `c.z`. `engineRef.current` (`BoardEngine`) exposes `viewportWorldRect`, `viewportSize`, and `worldToLocal(wx, wy)` — a pure linear map (uniform zoom scale + translate, no rotation). This is exactly the data needed to express "every currently visible card" as obstacles in view space.

## Motivation

The pill is `pointer-events: none` (click-through), so this is not a functional blocker, but a wayfinding label rendering on top of an unrelated card undercuts the polish the offscreen-hint system exists to provide, and is strictly worse than the #58 case the maintainer accepted (that one at least points at the card it overlaps; this one doesn't). The fix must generalize "avoid a rect" to *every* currently-visible card, not add a second card-identity-aware special case — the maintainer's #58 closure was explicit that own-card avoidance isn't worth bespoke complexity, and #64 asks for uniform, not targeted, obstacle avoidance. Concretely: **the own-card case is intentionally not special-cased.** All visible cards — including, if it happens to still be resolvable as an obstacle, the pill's own target card — are treated as one undifferentiated obstacle set. The chosen data shape enforces this structurally: obstacles are passed as plain `Rect[]` with no `cardId`, so `stackPills` has no way to even ask "is this my own card" — the uniformity isn't a policy `stackPills` chooses to follow, it's a fact about the types it's given.

## Proposed Solution

### Overview

Thread every currently-visible card's view-space rect into `stackPills` as a new `obstacles: Rect[]` input, and replace the single-scalar `lastEnd` nudge with a per-edge interval-based resolver that treats sibling-pill spacing and obstacle avoidance as one unified mechanism: both become "blocked intervals" on the edge's along-axis, merged and resolved with a single forward-scan-with-backward-fallback. The existing sibling-pill `stackGap` floor is re-expressed as one more interval (`{lo: -Infinity, hi: lastEnd + stackGap}`) so the new resolver is a strict generalization — with zero obstacles it produces byte-identical output to today's algorithm (verified below and by the unmodified existing test suite). `isOffscreen`/`hintPlacement` in `boardWayfinding.ts` are untouched — the center-only "toward the card" offscreen test is not part of this fix.

### Algorithm

> **Revised during implementation review** (see Trade-offs, "Window-bounded gap
> search, not forward-scan-with-backward-fallback"). The version below is what
> actually shipped; an earlier forward/backward-fallback draft was found by
> adversarial stress-testing to let a pill land tens to hundreds of pixels
> outside `[posLo, posHi]` under obstacle-plus-sibling saturation —
> `.offscreen-hints` clips at the viewport edge, so that pill would simply not
> render, which is a worse failure than the overlap being fixed. The final
> version instead searches for the free gap closest to the pill's desired
> position within the *legal window* `[max(posLo, siblingFloor), posHi]`, and
> only exceeds that window in the one case where it has no valid answer at all
> (see below).

Replace the current per-edge loop body (`offscreenHints.ts:92-121`) with:

```ts
interface Interval { lo: number; hi: number }

function mergeIntervals(intervals: Interval[]): Interval[] {
  const sorted = [...intervals].sort((a, b) => a.lo - b.lo);
  const out: Interval[] = [];
  for (const iv of sorted) {
    const last = out[out.length - 1];
    if (last && iv.lo <= last.hi) last.hi = Math.max(last.hi, iv.hi);
    else out.push({ ...iv });
  }
  return out;
}

/** Find a position for a `len`-long pill that never overlaps the previous
 * sibling on this edge (`siblingFloor`) and, best-effort, avoids `obstacles`
 * too — while always staying inside `[posLo, posHi]`, since an unclamped pill
 * would be clipped invisible by `.offscreen-hints`'s `overflow: hidden`.
 *
 * The one exception is pure over-saturation: so many same-edge pills that
 * `siblingFloor` alone has already pushed past `posHi`. That has no valid
 * in-bounds answer; push forward past whatever's in the way and let it
 * overflow, exactly like the pre-fix scalar nudge (unbounded stacking there
 * is pre-existing, accepted behavior — see S6).
 *
 * Otherwise, search `[max(posLo, siblingFloor), posHi]` for the free gap (the
 * window minus the obstacle intervals inside it) closest to `desired`; ties
 * favor the later/forward gap. If obstacles saturate the entire window, fall
 * back to the window-clamped `desired` (residual obstacle overlap, but
 * in-bounds and never overlapping the sibling). A pill is always returned,
 * never suppressed. */
function resolveAlongPos(
  desired: number,
  len: number,
  obstacles: Interval[],
  siblingFloor: number,
  posLo: number,
  posHi: number,
): number {
  const lo = Math.max(posLo, siblingFloor);
  if (lo > posHi) {
    let pos = Math.max(desired, siblingFloor);
    for (const o of mergeIntervals(obstacles)) {
      if (pos < o.hi && pos + len > o.lo) pos = o.hi;
    }
    return pos;
  }

  const windowed = mergeIntervals(obstacles)
    .map((o) => ({ lo: Math.max(o.lo, lo), hi: Math.min(o.hi, posHi) }))
    .filter((o) => o.hi > o.lo);
  const clampedDesired = clamp(desired, lo, posHi);
  if (!windowed.some((o) => clampedDesired < o.hi && clampedDesired + len > o.lo)) return clampedDesired;

  const gaps: Interval[] = [];
  let cursor = lo;
  for (const o of windowed) {
    if (o.lo > cursor) gaps.push({ lo: cursor, hi: o.lo });
    cursor = Math.max(cursor, o.hi);
  }
  if (posHi > cursor) gaps.push({ lo: cursor, hi: posHi });

  let best: number | null = null;
  let bestDist = Infinity;
  for (const g of gaps) {
    if (g.hi - g.lo < len) continue;
    const candidate = clamp(clampedDesired, g.lo, g.hi - len);
    const dist = Math.abs(candidate - clampedDesired);
    if (dist <= bestDist) {
      bestDist = dist;
      best = candidate;
    }
  }
  return best ?? clampedDesired;
}
```

Note this version takes `obstacles` (raw, unmerged) and `siblingFloor` (a
number) separately rather than one pre-merged `blocked` list — the sibling
floor defines the *legal window*, not just one more interval to dodge, which
is what makes the in-bounds guarantee provable (see Trade-offs).

```ts
for (const edge of edges) {
  const group = projected.filter((x) => x.p.edge === edge);
  group.sort((a, b) => a.p.along - b.p.along);
  let lastEnd = -Infinity; // far edge, along-axis, of the previously placed pill
  for (const { h, p, size } of group) {
    const vertical = edge === "left" || edge === "right";
    const len = vertical ? size.h : size.w;
    const posLo = (vertical ? minY : minX) + edgeMargin;
    const posHi = (vertical ? maxY : maxX) - len - edgeMargin;
    const crossPos =
      edge === "left" ? minX + edgeMargin
      : edge === "right" ? maxX - size.w - edgeMargin
      : edge === "top" ? minY + edgeMargin
      : maxY - size.h - edgeMargin;
    const bandRect: Rect = vertical
      ? { x: crossPos, y: minY, w: size.w, h: maxY - minY }
      : { x: minX, y: crossPos, w: maxX - minX, h: size.h };
    const obstacleIntervals: Interval[] = obstacles
      .filter((o) => rectsIntersect(bandRect, o))
      .map((o) =>
        vertical
          ? { lo: o.y - stackGap, hi: o.y + o.h + stackGap }
          : { lo: o.x - stackGap, hi: o.x + o.w + stackGap },
      );
    const blocked = mergeIntervals([{ lo: -Infinity, hi: lastEnd + stackGap }, ...obstacleIntervals]);
    const desired = clamp(p.along - len / 2, posLo, posHi);
    const pos = resolveAlongPos(desired, len, blocked, posLo, posHi);
    lastEnd = pos + len;
    out.push({
      cardId: h.cardId,
      signal: h.signal,
      label: h.label,
      edge,
      arrow: arrow(edge),
      left: Math.round(vertical ? crossPos : pos),
      top: Math.round(vertical ? pos : crossPos),
    });
  }
}
```

Worked-through cases:

- **Zero obstacles (degenerate case, must match today exactly).** `windowed` is `[]`, so the "does `clampedDesired` collide with anything" check is vacuously false and `resolveAlongPos` returns `clampedDesired = clamp(desired, max(posLo, siblingFloor), posHi)` directly, without ever reaching the gap search. Since `desired` is already `clamp(p.along - len/2, posLo, posHi)` at the call site, this reduces to `max(desired, siblingFloor)` when `siblingFloor <= posHi` — the identical result as today's `if (y < lastEnd + stackGap) y = lastEnd + stackGap;`. When `siblingFloor > posHi` (too many same-edge pills already), the `lo > posHi` branch returns `Math.max(desired, siblingFloor)` unclamped — again identical to today's unbounded stacking. Byte-identical output; verified both by hand-trace and by a dedicated 30-pill, zero-obstacle stress comparison against a faithful port of the pre-fix scalar algorithm (see Trade-offs).
- **One obstacle, no sibling pills.** `siblingFloor = -Infinity`, so `lo = posLo`. If `desired` falls inside the padded, window-clipped obstacle interval, the gap search finds the free gap on whichever side of the obstacle is closer to `desired` (clamped into that gap) — never past `posHi`, never before `posLo`.
- **Two obstacles with a gap between them.** Both survive the `rectsIntersect(bandRect, o)` band filter, are merged (if they touch) and clipped to the window. The gap list is exactly the window's complement against these merged, clipped intervals — including the gap *between* two disjoint obstacles. The closest gap to `clampedDesired` wins (ties favor the higher/forward gap), so a pill whose desired position sits between two obstacles lands there, not past the second one.
- **Overlapping/adjacent obstacles.** `mergeIntervals` coalesces any obstacle-derived intervals that touch or overlap after padding into one wider interval before the gap search runs — never a false gap the pill could still overlap.
- **Obstacle band saturates the entire legal window.** No gap in `gaps` is `>= len`, so `best` stays `null` and the function falls back to `clampedDesired` — in-bounds (`[lo, posHi] ⊆ [posLo, posHi]`) and never before `siblingFloor`, but may still overlap an obstacle — accepted as best-effort (see Trade-offs). The pill is always pushed to `out`; nothing in this algorithm can drop a pill.
- **Composing with sibling `stackGap`.** `siblingFloor` defines the lower edge of the search window itself (`lo = max(posLo, siblingFloor)`), not one more interval competing with obstacles for a forward push — so the sibling constraint is structurally impossible to violate by the gap search (every candidate is drawn from `[lo, ...]`), and there is no two-pass order-dependence between "avoid the obstacle" and "avoid the sibling."
- **The pill's own target card as an obstacle.** `obstacles: Rect[]` carries no `cardId` — there is no field in the type for `stackPills` to compare against `h.cardId` even if someone wanted to. If `App.tsx`'s unfiltered `activeCards.map(...)` happens to include the hinted card's own (partially visible) rect, it is nudged around exactly like any other obstacle — an emergent, not targeted, side effect (see Trade-offs; this is not a reopening of #58, which is about added *complexity*, and none is added here for that purpose).

## Acceptance Scenarios

- **S1 — single unrelated obstacle avoided.** *Given* one hint whose naive (pre-fix) `stackPills` placement would land on top of an obstacle rect that is not the pointed-to card, *when* `stackPills` runs with that rect in `opts.obstacles`, *then* the emitted pill's `{left, top, w, h}` does not `rectsIntersect` the obstacle rect (asserted via `placement.ts`'s `rectsIntersect`, mirroring production logic rather than re-deriving it by hand).
- **S2 — nearest gap between two obstacles, not overshoot.** *Given* two obstacles on the same edge band with a free gap between them, positioned so the pill's natural (unnudged) position falls inside the *first* obstacle, *when* `stackPills` runs, *then* the pill lands in the gap between the two obstacles — not pushed past the second one.
- **S3 — obstacles carry no card identity; uniform treatment is structural, not policy.** *Given* `StackOpts.obstacles: Rect[]` has no `cardId` field, *when* `App.tsx`'s `offscreen` `useMemo` is read, *then* it builds `obstacles` from `activeCards.map(...)` unconditionally — no filter excludes the signal-bearing card's own rect, non-signalling cards, or any other subset. *And*, at the `stackPills` level, feeding an obstacle rect that coincides with where the hinted card's own sliver would be still produces a nudge away from it (there is no code path capable of special-casing it either way). Verified by reading `App.tsx` (no DOM test harness, per repo convention) plus a `stackPills` unit test asserting the nudge fires regardless of which card the obstacle rect "represents."
- **S4 — saturated band never suppresses the pill.** *Given* an obstacle (or merged set of obstacles) whose padded interval spans the entire nudge-able band within `[posLo, posHi]`, *when* `stackPills` runs, *then* a pill is still returned for that hint (`stackPills` output length unchanged), clamped into the viewport; residual overlap in this pathological case is accepted, not engineered around.
- **S5 — composes with sibling `stackGap`.** *Given* two hints on the same edge where the second hint's natural position collides with both an obstacle and the first (already-placed) pill, *when* `stackPills` runs, *then* the returned pills satisfy **both** invariants simultaneously: the second pill's rect does not `rectsIntersect` the obstacle, and the second pill's `top`/`left` is `>= ` the first's `+ size + stackGap` (the existing invariant from "nudges a second overlapping right-edge pill down by >= stackGap").

## Trade-offs and Limitations

- **Best-effort, not a hard guarantee.** When an obstacle (or merged set) saturates the entire nudge-able band (S4), the resolver's clamp fallback can still leave partial overlap. No suppression fallback is introduced — consistent with #58's closure, which treated hint suppression as new, unwanted design surface.
- **Window-bounded gap search, not forward-scan-with-backward-fallback.** An earlier draft of this algorithm (see the Algorithm section's revision note) tried "push forward past every blocked interval; if that overflows `posHi`, scan backward instead; if *that* fails, clamp." It looked correct and passed the initial adversarial review, but a follow-up randomized stress test (thousands of trials varying pill count, obstacle count/size/position) found two independent failure modes: (1) the backward-fallback's final `clamp` was only reachable along one code path, so the *other* fallback path could return a raw, unclamped position tens to hundreds of pixels past `posHi` — invisible, since `.offscreen-hints` clips at the viewport edge; (2) once one same-edge pill was pushed to such an out-of-bounds position, its inflated `lastEnd` poisoned every later sibling's `siblingFloor` in the same edge group, cascading the invisibility. The shipped version instead computes the *legal window* (`[max(posLo, siblingFloor), posHi]`) up front and searches for the closest free gap strictly inside it, so every non-degenerate return value is provably in-bounds by construction — no fallback chain to have a gap in. This is *not* purely a robustness polish: it changes which position gets picked when the true nearest-gap gap is behind the pill's natural position (the old draft's forward-only bias would have missed it entirely, not just mis-clamped it).
- **Realistic loads verified exhaustively; extreme same-edge saturation can still push a pill off-screen, matching pre-existing behavior.** Randomized stress-testing (5000 trials at up to 6 simultaneous hints and 3 simultaneous obstacles per trial — well above what a real board session is likely to show at once) found zero pill-vs-pill overlaps, zero out-of-window placements, and exact byte-identical output to the pre-fix algorithm whenever `obstacles` is empty. Pushing far past realistic load (up to 15 hints and 7 obstacles on one edge simultaneously) can still trigger the accepted `lo > posHi` branch (documented above) and produce an off-screen, invisible pill — but this is the *same* pre-existing degenerate case the original algorithm already has for "too many same-edge signalling cards to fit" (confirmed: it reproduces identically with `obstacles: []`, i.e. it is not obstacle-specific); obstacles simply make the shared edge band feel more crowded sooner, so the threshold for hitting it is lower than before. Not fixed here — doing so would mean relaxing the hard "never overlap a sibling" invariant, a bigger design change than this issue asks for.
- **A pre-existing, unrelated cross-edge corner-overlap was found and is explicitly out of scope.** While stress-testing, two pills on *different* edges (e.g. one on `left`, one on `bottom`) were found to visually overlap near a shared viewport corner when both land close to that corner — `stackPills` only ever nudges within one edge's group, so it has no way to see a pill on an adjacent edge. Reproduced with `obstacles: []`, confirming it predates both #58 and #64 and is unrelated to obstacle avoidance. Requires clustering several simultaneous signalling cards at one corner to trigger — out of scope for this fix; worth its own issue if it turns out to matter in practice.
- **Obstacle padding reuses `stackGap`.** Rather than a distinct, possibly smaller "obstacle clearance" constant, the same 8px used between sibling pills is used between a pill and any obstacle. A pill visually abutting a card edge vs. a sibling pill may reasonably want a different gap, but the issue's framing ("respecting the existing `edgeMargin`/`stackGap` bounds") points at reuse, and introducing a second gap constant is unjustified complexity for a cosmetic difference.
- **No obstacle pre-filtering by viewport intersection.** `App.tsx` passes every `activeCards` rect converted to view space, including cards nowhere near the viewport. This is correctness-neutral (a fully offscreen card's converted rect can't intersect any edge band a pill could occupy) and cheap at this app's card-count scale; it is a possible micro-optimization, not a requirement.
- **Emergent, not targeted, interaction with #58.** Because `obstacles` is unfiltered and carries no `cardId`, a hint's own still-visible sliver — the #58 scenario — can end up being avoided too, purely as a side effect of uniform treatment. This does not reopen #58: no `cardId`-aware logic was added to make that happen, and #58's objection was specifically to added *complexity* for that one case, not to it coincidentally being fixed by something else.
- **No DOM test harness for `App.tsx`/`BoardEngine`.** Per repo convention, only pure `kit/` logic is unit-tested; the `obstacles` threading (S8) is verified by reading the source and by manual visual QA via `make run`, not an automated render test.
- **Nudge accuracy is bounded by `measurePill`'s existing text-metrics approximation** (`App.tsx:136`, ~6.3px/char), a pre-existing heuristic this fix does not change.
