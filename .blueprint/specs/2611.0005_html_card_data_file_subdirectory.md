## Gate

Written 2026-11-12 from the code at `29a03e4`. The approach is the design's and is not open here. The user's decisions that bind this spec:

- 14, 15: a card reads no file outside its own directory tree; there is no setting; a read inside needs no consent.
- 16: a directory under the HTML file's directory is inside the tree. Phase 1 refused it; this phase opens it.
- 13: an HTML card is not a network boundary. No hardening against a script's ways to the network is proposed.
- One data file for each card (phase 1). No recursive watch.

Where this spec finds a risk that does not change the product's direction, the author decides, as in phase 1. Each such choice is in "Choices made in this spec".

## Context

What the code does today (`29a03e4`), each point checked by an investigation and a second reading on 2026-11-12:

- **App.** `CardDataPath.dataFile(html:name:)` judges the name in the text, as bytes. A result under the HTML file's directory is refused with `in a subdirectory: not read yet`. At each read `CardDataRead.read` resolves both files and asks `CardDataPath.isBeside`, which compares the bytes before the last slash of each.
- **Daemon.** `docs::record_data` refuses a `data` that is not beside the doc (`beside`: same parent, on the text). `Registry::watched_paths` gives each data file to the look, so a look reads a data file wherever it is. A look runs only on a wake (`docs::watch_loop`); there is no look on a timer.
- **The watch.** A directory is watched without recursion (`watch.rs`). `notify` 9.0.0-rc.8 drops an FSEvents event for a path deeper than a direct child of a watched directory. Measured, 5 runs of each: with `beside` relaxed and no new watch, an append to `sub/stats.json`, a replace of it by rename, and the creation of a missing file in `sub/` gave no `file_event` in 2 s; each was reported after the next change of a doc in the parent directory.
- **Counts.** `Daemon::acquire_watch` and `release_watch` count the registered docs of a directory; the first count watches and the last release unwatches. `close_doc` and `delete_board` release the doc's own parent only.
- **A directory that is not there.** `acquire_watch` fails (`NotWatched::Refused`) and nothing tries the watch again: the thread's retry set holds only the directories of a volume that did not answer. Its one caller, `open_doc`, gives the count back. If a caller left the count standing, a second `acquire_watch` on that directory would return `Ok(false)` with nothing watched.
- **The watcher thread wakes a look after each watch or unwatch it tries**, also one that failed (`watch.rs`, `Thread::reconcile`). A look that asks for the watch of a missing directory would so cause the next look, about ten a second with a warning line each.
- **Two texts, one watch.** The daemon's counts and the thread's set are keyed by the path's text; `notify` keys its watches by the resolved path. A doc's directory is resolved (`handle_open`). A data file's directory comes from the app as text and one of its components can be a link (`sub -> .`). Two texts then share one `notify` entry, and the unwatch of one removes the watch of the other with no sign. Read from the code; not run.
- **A watched directory that is removed and made again** is still watched (the stream is by path). Measured once on `notify` alone.
- **When the app names the file.** `doc_data` is sent on the first stamped `ready` of each load (the same name again at each reload of the HTML file, never "none" first), and once for each card that reads a file after a reconnect. Nothing is sent at a card's close or a board switch.
- **A registration outlives its app.** The daemon keeps each doc's `data` when the app goes away. A new app process whose card now names no file sends nothing (P1-S25), so the old registration stays until `doc_close`, `board_delete` or a daemon restart. Today that costs one stat for each look. With this phase it would also hold a watch.

## Motivation

A producer must put its data file beside the HTML file, among the other files of that directory. The design puts a subdirectory inside the tree a card may read; phase 1 left it out only because the change of such a file wakes no look.

## Proposed Solution

### Overview

The path rule takes a file under the HTML file's directory, at any depth. The daemon counts the directory of each data file as it counts the directory of a doc, so that a change there wakes a look. No wire message is added or changed: `doc_data` takes a wider set of paths.

### Key Components

- **`CardDataPath` (kit).** `dataFile` gives `.file` for a result under the HTML file's directory. `inSubdirectory` is removed. `isBeside` becomes a check that the resolved file is under the resolved HTML file's directory, by whole components, as bytes.
- **`CardDataRead` (kit).** Uses the new check. The texts do not change (`leads outside this card's directory`).
- **`docs.rs`, `boards.rs`, `state.rs` (daemon).** The directory check, and the count of a data file's directory with every place that drops a registration.
- **Docs.** `docs/protocol.md` (`doc_data`), `docs/architecture.md` (HTML cards, the watcher), `tarmac-cli/src/GUIDE.md` (how to write a card that takes data), and the design's status lines.

### Interface Contract

**The name (`<meta name="tarmac-data">`).** A relative name is taken from the directory of the HTML file. The result must be a file in that directory or in a directory under it, at any depth. `.` and empty components are dropped and `..` takes off the component before it, on the text, as bytes. A result anywhere else is refused with `outside this card's directory`; a name that names no file with `names no file` (phase 1's rules, unchanged).

**The read.** At each read both files are resolved. The resolved data file must be under the directory of the resolved HTML file: each component of that directory equals, as bytes, the component of the file at the same place, and the file has at least one more component. Otherwise the read is refused with `leads outside this card's directory` and no file is opened. A resolved path is taken as it is given: one that has an empty, `.` or `..` component is not under any directory (it is not worked out again; phase 1's `testS30AResolvedPathIsNotNormalisedAgain` keeps its answer). A resolve of either file that fails is refused as in phase 1.

**`doc_data` at the daemon.** `data` is taken when it is absolute, it has no `.`, `..` or empty component (`//`), it does not end in `/`, it has a file name, and it is under the doc's directory by whole components. Any other `data` is refused whole: nothing is recorded, nothing is counted, and the registration that stood before stays, with its count. The same for an unknown board or an unknown doc (phase 1). The stat of the file follows a link, as in phase 1 (choice 11): only a stamp reaches the app.

**The watch of a data file's directory.** This replaces phase 1's "No directory is watched or counted for a data file", and the "watches nothing" of phase 1 choice 6.

- A registration whose data file's text is in the doc's own directory counts nothing (that directory is counted for the doc).
- For any other registration the daemon resolves the data file's directory (links followed, off the runtime's threads and inside the gate's limit, as a doc's file is read). The resolved directory is the one counted and watched, so one directory on disk has one count whatever text led to it.
- The resolve is made when the count is taken. The count is given back for that same directory, never for a new resolve: a link in the path that is changed later moves no count (Trade-offs).
- When the resolved directory is the doc's own directory, nothing is counted for the registration (the doc counts it). When it is neither the doc's directory nor under it, by whole components, nothing is counted or watched for the registration. In both cases the registration stands, and each look stats the file as in phase 1. The app's read refuses a file outside the tree.
- The registration counts its resolved directory once, for as long as it stands. The same name sent again counts nothing more.
- The count is given back when the registration is replaced by another name or by none, when the doc is closed, when its board is deleted, and when the app goes (below). A registration that counted nothing gives nothing back.
- When the count makes a new watch, the daemon looks at the docs before its handling of that `doc_data` ends, as `open_doc` does, so that a change the restarted stream lost is reported.
- **A directory that cannot be resolved or watched** (it is not there, it is not a directory, or the watch is refused): the registration stands and the answer is as in phase 1 (a `file_event` when the file is there). The daemon tries the watch again at each wake that the file system gave, and at each `doc_data` that names the file again. When the try makes the watch, the daemon looks. A wake that the watcher thread gives after its own work is not a wake that the file system gave: it brings one look and no try. So while nothing changes on disk, the daemon makes no further look and no further try. A registration that is replaced, cleared or dropped before a try succeeds is not tried again.
- **A volume that does not answer.** When the resolve of the directory, or the watch, is held past the gate's limit, the directory is one that cannot be resolved or watched: the handling of the `doc_data` ends, the registration stands, nothing is watched. The gate's word that a held call came back counts as a wake of the file system for the try (it is what makes the retry of a doc's directory today).

**When the app goes.** The app's place is the one app connection the daemon pushes to; a new app connection takes it from the old one. The daemon drops every data registration of every board (the boards in the background too), with its count: when the connection that holds the app's place ends, and when another connection takes that place. The end of a connection that no longer holds the place drops nothing: a `doc_data` of the connection that now holds the place is never dropped by the end of an older one. The app names each file again after it connects (P1-S48), and a card that is built later names its file at its first `ready`.

## Acceptance Scenarios

Each "no `file_event` comes" check first forces a look where one can run (phase 1's rule): it changes a doc in a watched directory and waits for that doc's `file_event`. Where the scenario says "with no other change", no such look is forced before the wait, and the check for the data path's event is positive. S30a is the one exception, and says why. Before the write of a "with no other change" check, the test waits out each look that its own earlier steps woke (an open, a `mkdir`, a removal, a `doc_data` that watched or unwatched): it waits a `quiet` window, as phase 1's tests settle. Else that look stats the file and reports the write, and the check passes on a tree that does not watch the directory.

**Where the daemon tests live.** Each daemon scenario names its harness. Two exist, and each sees different things:

- **[it]** `core/crates/tarmacd/tests/doc_data_integration.rs`: a daemon process with the real FSEvents watch. It sees the wire and `state.json` only. It is the only harness where a write on disk wakes a look, so every "with no other change" and "one write brings exactly one `file_event`" check is here. It cannot see which directories are watched. `write_doc` returns the canonical path: a path through a link must be made as text (as `Card::beside` does), or the test names the resolved path and tests nothing.
- **[st]** `core/crates/tarmacd/src/state/tests/`: the `Daemon` in the test's process, with a stand-in source. "Watched" is `watched(daemon, dir)`, which asks `Watcher::watched`; that call is `#[cfg(test)]` and is reachable only from here. `held_source`, `WatchFails` and `RefusesDir` record or refuse the source's watch and unwatch calls (`SourceCalls::of`). `stuck_fs` counts the gate's calls (`StuckFs::calls`). No write on disk wakes a look: a look is forced with `look_at`, or "a wake is given as the file system's", which is `daemon.wake` today (the source's wake; if the change gives the file system's wake its own way in, the test gives it there). "Given S9" in an [st] scenario is the same set-up in that harness: `<dir>/sub/stats.json` exists and a `doc_data` for it was handled. "The app sends `doc_data`" is the daemon's own handling of it (`docs::record_data` today). "A connection takes the app's place" is `install_app`, which returns the generation; "it ends" is `remove_app` with that generation (`connect_app` drops the generation, so a test of S26 and S26a calls `install_app` itself). The docs' directory must be canonical (`canon_tmp`): the `open_doc` helper does not resolve, and a resolved directory under `/private/var` is not under `/var`, so a check that a directory is not watched would pass for the wrong reason.

### Path rule (Kit)

- **S1:** Given the HTML file `/a/b/dash.html`, the names `sub/stats.json`, `./sub/stats.json`, `sub//stats.json`, `sub/x/../stats.json` and `/a/b/sub/stats.json` each give the file `/a/b/sub/stats.json`; `sub/deep/stats.json` gives `/a/b/sub/deep/stats.json`. (Changes P1-S16.)
- **S2:** The names `../stats.json`, `/etc/passwd`, `sub/../../x.json`, `/a/bc/x.json` and `../bc/x.json` are refused as outside the card's directory, with the normalised path. (`/a/bc` has the directory's name as the start of its own.)
- **S3:** The names `sub/..`, `sub/../`, `sub/` and `sub/./` are refused as naming no file.
- **S3a:** Given the HTML file `/dash.html` (a card at the root), the name `s/x.json` gives the file `/s/x.json`. (Changes phase 1's `testACardAtTheRootTakesAFileBesideIt`, which refused it as a subdirectory.)
- **S4:** Paths are judged as bytes. With the HTML file in a directory whose name is written with a precomposed letter, an absolute name that writes that directory with the letter and a combining mark, followed by `sub/x.json`, is refused as outside. `sub/` followed by a combining mark and `x.json` gives a file in `sub` whose name starts with the mark. `../` followed by a combining mark is refused as outside. (Replaces the subdirectory case of P1-S18a.)

### The read (Kit)

- **S5:** The under-check, on resolved paths: `/a/b/x.json`, `/a/b/sub/deep/x.json` and `/a/b/sub/` followed by a combining mark and `x.json` are under the directory of `/a/b/dash.html`; `/a/bc/x.json`, `/a/x.json`, `/x.json`, `/a/b` and `/a/b/l/../x.json` are not; a file under the directory written with a precomposed letter is not under the one written with a combining mark.
- **S6:** Given the read function with a stand-in `resolve` and `read`: when `resolve` leads `/a/b/link/x.json` to `/elsewhere/x.json`, then `read` is not called and the result is the refusal `leads outside this card's directory`; when it leads it to `/a/b/other/x.json`, or the name `/a/b/stats.json` to `/a/b/sub/stats.json`, then `read` is called with that resolved path; when `resolve` leads the HTML file to `/real/dash.html` and the data file to `/real/sub/x.json`, then `read` is called with that path. (Changes P1-S30: its tests take `/a/b/sub/stats.json` and `/a/b/sub/` followed by a combining mark and `x.json` as outside.)
- **S7:** Given a card at load *N*, when a `ready` with `load: N` and `data: "sub/stats.json"` is handled, then the effects register `/…/sub/stats.json` and the console gains no line. (Changes the subdirectory step of P1-S24.)

### Daemon: the directory check (Rust)

- **S8 [it]:** Given a doc `<dir>/dash.html` on the active board, a `doc_data` whose `data` is one of: `<dir>/sub/../x.json`, `<dir>/../x.json`, `<dir>/sub/../../<other>/x.json`, `<dir>/./x.json`, `<dir>/sub/./x.json`, `<dir>//sub/x.json`, `<dir>/sub/x.json/`, `<dir>x/x.json` (a sibling whose name starts with the directory's), `<dir>` itself, the parent's `x.json`, a relative `sub/x.json`: then no `file_event` for the file it would lead to comes at once, nor after that file is rewritten and a look is forced. (Widens P1-S41 and replaces its subdirectory case.)
- **S8a [st]:** Given S8's `data` values, each sent for a doc whose directory is watched, then the source is asked for no watch after the doc's own, and no directory other than the doc's is watched.
- **S8b [st]:** Given S9 and an existing `<dir>/two/x.json`, when a `doc_data` for the same doc names a `data` that S8 refuses, or a `doc_data` names `<dir>/two/x.json` for a doc that is not open on that board or for an unknown board, then `<dir>/sub` is still watched, `<dir>/two` is not, and a later `doc_data` with no `data` for the doc leaves `<dir>/sub` not watched.

### Daemon: the watch (Rust)

- **S9 [it]:** Given `<dir>/sub/stats.json` exists, when the app sends `doc_data` for it, then a `file_event` for it comes.
- **S10 [it]:** Given S9, when the file is changed with one write and nothing else changes, then exactly one `file_event` for it comes (one, then none within the `quiet` window). (Red on a tree where only the directory check is opened.)
- **S11 [it]:** Given S9, when the file is replaced by a rename of a file written in `sub`, with no other change, then at least one `file_event` for it comes, and the last one before the `quiet` window carries the new file's mtime.
- **S12 [it]:** Given a `doc_data` for `<dir>/sub/new.json`, where `sub` exists and the file does not, then no `file_event` for it comes after a forced look; when the file is made, with no other change, one comes.
- **S13 [it]:** Given a `doc_data` for `<dir>/sub/stats.json` where `sub` does not exist, when `sub` is made, and the file is written after the look that the `mkdir` wakes has passed, with no other change, then a `file_event` for it comes. (A write inside that look's window would be reported with no watch of `sub`.)
- **S14 [st]:** Given the doc's open has been flushed (`flushed`: the look its watch woke has passed), and a `doc_data` for `<dir>/sub/stats.json` where `sub` does not exist, and its handling has ended: the source is asked for no watch of `<dir>/sub`, and the gate's call counts (`StuckFs::calls` of every kind, the resolve of the directory included) do not change over a wait of `4 * BURST`. The same where `<dir>/sub` is a regular file.
- **S14a [st]:** Given the doc's open has been flushed, and a `doc_data` for `<dir>/sub/stats.json` where `sub` exists and the source refuses its watch (`WatchFails`): the source is asked for the watch of `<dir>/sub` once. After the look that the failed watch wakes, the gate's stamp count does not change over a wait of `4 * BURST`, and the source is asked for no further watch. When a wake is then given as the file system's, the source is asked for the watch once more, and once only.
- **S14b [st]:** Given S14 (`sub` does not exist), when `sub` is made and a wake is given as the file system's, then `<dir>/sub` is watched; when the app then sends no `data`, it is not. And given S14 again, when the app sends no `data` first, and then `sub` is made and a wake is given, then `<dir>/sub` is not watched and the source is asked for no watch of it.
- **S14c [st]:** Given a doc open and the stand-in file system (`StuckFs`) holding every call on `<dir>/sub`, when `doc_data` names `<dir>/sub/stats.json`, then its handling ends within the gate's limit, the registration stands (a forced look asks the gate for the file) and `<dir>/sub` is not watched; when the held calls are let go and the gate says they came back, then `<dir>/sub` is watched.
- **S15 [it]:** Given `<dir>/a/b/stats.json` exists and is registered, when it is changed with one write and nothing else changes, then exactly one `file_event` for it comes.
- **S16 [it]:** Given S9, when `sub` is removed with its file and made again, and the file is written after the looks that those changes wake have passed, with no other change, then a `file_event` for it comes.

### Daemon: the count (Rust)

- **S21 [st]:** Given S9 and a second doc open in `<dir>`, when the HTML doc is closed, then `<dir>/sub` is not watched and `<dir>` is.

- **S23 [st]:** Given S9 and a doc `<dir>/sub/notes.md` open on the board, when the app sends no `data`, then `<dir>/sub` is watched; when `notes.md` is then closed, it is not.
- **S24 [st]:** Given a `doc_data` for `<dir>/stats.json` (beside the doc) and no other doc in `<dir>`, when the HTML doc is closed, then `<dir>` is not watched. And given the same registration sent, replaced by none, and the doc still open, then `<dir>` is watched.
- **S25 [st]:** Given a doc on a board in the background, when `doc_data` names `<dir>/sub/stats.json`, then `<dir>/sub` is watched and no `file_event` comes after a forced look of the active board.
- **S25a [it]:** Given a doc on a board in the background and an existing `<dir>/sub/stats.json`, when `doc_data` names it, then no `file_event` for it comes at once nor after a forced look of the active board; when that board is made active, a `file_event` for the file comes after the `restore`. (P1-S44 with the file in `sub`.)
- **S26 [st]:** Given S9 on the active board and a registration of an existing `<dir>/bg/x.json` by a doc of a board in the background, both by the connection that holds the app's place, and both `<dir>/sub` and `<dir>/bg` seen watched, when that connection ends, then neither `<dir>/sub` nor `<dir>/bg` is watched; when a new connection takes the place and sends the `doc_data` for `<dir>/sub/stats.json` again, then `<dir>/sub` is watched and a `file_event` for the file comes to it.
- **S26a [st]:** Given S9 by connection A (generation *a*). When connection B takes the app's place (`install_app`), then `<dir>/sub` is not watched before B sends anything. When B then sends `doc_data` for the file, and `remove_app(a)` runs after it, then `<dir>/sub` is watched, and a rewrite of the file with a forced look brings exactly one more `file_event`, to B. The same when `remove_app(a)` runs between B's `install_app` and B's `doc_data`. (`conn::handshake` sends `hello_ok`, then `app_session` calls `install_app`; A's task can end after B's first frames are handled. Only this harness can put the two in a set order.)
- **S26b [it]:** Given S9, and a second HTML doc in `<dir>` that registered `<dir>/beside.json`, when the app's connection ends and a new app connects and sends no `doc_data`, then a rewrite of `<dir>/sub/stats.json` and of `<dir>/beside.json` brings no `file_event` for either after a forced look. (Red on today's tree for `beside.json`, since a registration used to stay: read from the code, not run.)
- **S27 [st]:** Given a `Silent` source, another doc open in its own watched directory and changed after its last look, when a `doc_data` for `<dir>/sub/stats.json` makes the new watch of `<dir>/sub`, then that doc's `file_event` is in the app's queue when the daemon's handling of the `doc_data` ends, with no wait (the wake of the watcher thread brings its look `BURST` later). The harness of `an_open_reports_a_change_that_no_wake_told_of` in `state/tests/looks.rs`.
- **S28:** Given S9 on the active board, when the daemon saves its state, then `state.json` has no trace of the data path or of `<dir>/sub` ([it], as P1-S46); and a daemon started from that state file asks the source for no watch of `<dir>/sub`, and does not watch it, until a `doc_data` names the file ([st], with `state_with_docs` and `held_source`).

### Live (dev channel, hand-run with evidence kept under `.dev/`)

- **L1:** A card that names `data/stats.json` shows the file's content. The file is rewritten 100 times, slower than the look: the document's load counter stays at 1 and the last content shown is the last written. Nothing else in the card's directory changes during the run.
- **L2:** A card names `link/x.json`, where `link` is a symlink in the card's directory to a directory outside it: nothing of that file reaches the document and the console names the path and `leads outside this card's directory`. A `../x.json` name is refused as outside. (Replaces the subdirectory case of P1's L4: that name is now read.)
- **L3:** A card names `late/stats.json` and `late` does not exist. `mkdir late` and a write of the file follow: the document gets the content, with no rewrite of the HTML file.
- **L4:** Twenty cards on one board, each with a data file in its own subdirectory. The app is ended and started again: each card shows its data. The time from the app's start to the last card's data is recorded, and a terminal on the board takes typed input during it.
- **L5:** A file whose name is not valid UTF-8 is **not** made on disk in any run (the installed daemon; memory rule). Bytes are tested in unit tests only.

## Choices made in this spec

None changes the product's direction.

1. **Any depth.** The design says "a directory under it". One level only would be a second rule with no gain.
2. **The under-check is by whole components**, not a prefix of bytes: `/a/bc` is not under `/a/b` (S2, S5).
3. **The daemon refuses a path with `.` or `..`** and does not work one out (S8). `Path::starts_with` takes `/a/b/../../etc/x.json` as under `/a/b` (measured). The app always sends a normalised path, so only another sender is refused.
4. **The daemon resolves the directory it watches** (S29–S31), and watches none that is outside the doc's directory. Without it a link in the tree gives two texts for one watch, and the unwatch of one ends the other. The stat of the file still follows a link (phase 1, choice 11): only the stamp reaches the app, and the app's read refuses the file (S6, L2).
5. **The file swapped between the resolve and the read** (design, *For the specs*, phase 3; phase 1 choices 12 and 23): stays as it is. Both files are resolved at each read. A check of the open descriptor's own path is not added: the window needs a local process that can write in the card's tree at the right moment, and that process can read the file itself. A card's script cannot write a file.
6. **A directory that is not there is tried again at a file-system wake** (S13). The design did not say. A directory made one level at a time with pauses, more than one level below a watched directory, can be missed until the next wake or the next load of the HTML file (Trade-offs). Watching the deepest directory that exists, and moving the watch down, would close that at the cost of a second mechanism; not taken.
7. **No bound on the number of watches** beyond what the design gives: one data file for a card, so at most one more directory for each HTML doc. L4 records what twenty cost.
8. **The registrations are dropped when the app goes** (S26, S26a). There is one app place; a new connection takes it from the old. It changes phase 1's daemon (a registration used to stay), and no phase 1 scenario asks that it stay: the app names its files again when it connects. Without it a registration of an earlier app process would hold a watch that nothing gives back.
9. **A board in the background counts its watch** (S25), as a doc of such a board counts its directory.
10. **`in a subdirectory: not read yet` is removed** with its constant. No card can depend on a refusal text.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

Project rules that bind the work (`CLAUDE.md`, `docs/coding-style.md`):

- **TDD, red first.** Each new test is seen to fail on the unmodified tree, for its behaviour and not for a compile error, before the change that makes it pass. Keep the red record under the worktree's `.dev/`. S10 has a second red: on a tree where only the directory check is opened.
- **S29's red** rests on "two texts, one watch", which was read from the code and not run. Record S29 red on a tree that counts the text of the data file's directory, before the resolve is added. If it is not red there, stop and report: the reason for choice 4 is then not shown.
- **One `Notify` carries every wake today** (`Daemon::wake`). The try needs the file system's wake told apart from the watcher thread's own; that change inside the daemon is accepted.
- **Every changed assertion of a phase 1 test is reported**, with the old and the new text. Known: P1-S16, P1-S18a, P1-S24, P1-S30 (`CardDataReadTests`: `/a/b/sub/stats.json` and `/a/b/sub/` with a combining mark, both taken as outside), P1-S41, and `testACardAtTheRootTakesAFileBesideIt` (S3a).
- **Decisions live in `TarmacKit`**; do not widen visibility for a test.
- **The count is paired.** Every place that drops or replaces a doc's `data` gives the count back: `set_data`, `close_doc`, `delete_board`, the drop when the app goes. `Registry::close_doc` returns only a bool today, so the data path is lost before `Daemon::close_doc` can release it. A failed `acquire_watch` leaves its count standing, and a second call then answers `Ok(false)` with nothing watched. The count is given back for the directory it was taken for, not for a new resolve (S31b).
- **The watcher thread wakes a look after its own work**, also after a watch that failed. A try of the watch from inside each look would loop (S14, S14a). A watch that fails because the path is not there restarted no stream.
- **One `Notify` carries every wake today** (`Daemon::wake`): the source's, the watcher thread's after its own work, and the gate's when a late call returns. The retry rule needs the file system's wake told apart from the thread's (S14a). If it gets its own way in, the [st] tests give their "wake as the file system's" there.
- **The directory resolve is a call of the gate.** `PathFs::resolve` refuses a path that is not a regular file. If the resolve of a directory is a new kind of call, `StuckFs` counts it too, so that S14 can see a try.
- **The drop when the app goes is made in the `Daemon` steps that take and leave the app's place** (`install_app`, `remove_app`), not only in `conn::app_session`, so that [st] can put it in a set order (S26a).
- **`Path::components` drops `.` and empty components** (and a trailing `/`), so a check written on it takes `<dir>/./x.json` and `<dir>//sub/x.json` (S8). Judge the bytes of `data` as given. (Rust's documented behaviour; not run here.)
- **Where the count can be taken.** `set_data` runs inside the look's `apply`, under the `boards` lock, where `acquire_watch` cannot wait. Take the count before the look, as `open_doc` does, and give it back when the registration was refused or was the same as before.
- **The drop at the app's end** must not undo a `doc_data` of the connection that took the place (S26a): `hello_ok` is sent before `install_app`, and the old connection's task ends after it.
- **`a_doc_data_that_is_refused_records_nothing`** expects `sub/below.json` refused today; its `sub/../through.json` case stays refused.
- **Daemon locks** are never held across `.await`; nothing is pushed from inside `Daemon::look`.
- **Wire:** no change. `docs/protocol.md` changes in its text only; no vector changes.
- Do not `cargo fmt`. Match the code around the change. No comment that restates the code.
- Never run a daemon by hand, and never kill one by name; daemons run only inside the test harness, or through `make run` with its pinned sockets.
- Never make a file or directory whose name is not valid UTF-8, and mount no disk image. Byte cases are unit tests over strings and byte arrays.
- `make test` must pass. The docs named in Key Components are part of the change.

Write tests to these principles (the same ones `/verify` scores against):

- **Behavioral over structural** — assert observable output and effects, not internals; the suite must survive refactoring.
- **Every test can fail** — no copy-pasted expected values, no asserting a constant, no tautologies.
- **Deterministic, isolated, readable** — inject clocks, no cross-test state, setup inline.

## Security Considerations

- **What a card can now read.** One file at a time, in the directory of its own HTML file or in any directory under it, when its content is strict JSON. The tree is wider than in phase 1: a card opened at the root of a repository can name any JSON file of that repository. This is the design's decision 16, and the user's act of consent is still `tarmac open` on the HTML file. An HTML card is not a network boundary, so what a card reads it may also send away.
- **A link that leads out of the tree** is refused at the read, on the resolved paths of both files, at each read (S6, L2). The window between the resolve and the read is choice 5.
- **The daemon checks the path by itself** (S8), and watches no directory outside the doc's own, also through a link (S30). The stat of a named file follows a link; only a stamp reaches the app (choice 4).
- **A card's script cannot grow the watch set without bound**: only the first `ready` of a load names a file, one file for a card, and a new name gives back the count of the one before (S18).

## Trade-offs and Limitations

- **Each registered subdirectory is a watch**, and each new watch or unwatch restarts the daemon's one FSEvents stream (#253). The daemon looks after it, as it does for a doc.
- **A reconnect of the app makes each such watch again**, one restart for each directory (L4).
- **A missing directory more than one level down, made a level at a time**, can be seen late (choice 6).
- **A link in the data path that is pointed elsewhere after the registration** moves no watch: the count stays on the directory the link led to when it was taken (S31b), and the same name sent again counts nothing more, so a reload of the HTML file does not move it either. A change in the new directory is seen at the next look that something else wakes. The watch moves when the registration is replaced or cleared, or when the app connects again (the registrations are dropped and named again). The read is not touched: it resolves both files at each read.
- All of phase 1's limits stand: one data file for a card, the whole file read at each change, no state for a board in the background.

- **A `doc_data` of a connection that lost the app's place**, still in handling when the new one took it, can be recorded after the drop and stay until the app next goes. It needs two apps at once. Accepted.
