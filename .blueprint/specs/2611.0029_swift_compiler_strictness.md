# 2611.0029 Swift compiler strictness

**Date:** 2026-11-22
**Status:** accepted (spec-evaluator review and advisor scoping, 2026-11-22)
**Author:** EP Lin
**Issue:** #475

## Context

`make lint` runs clippy for Rust and the swift-format rules for Swift (specs 2611.0027, 2611.0028). The Swift compiler's own diagnostics are not checked:

- A clean build of the package prints 3 warnings, all in `TarmacTerm` (#478). Nobody sees them: an incremental build prints a warning only for a file it compiles again.
- `TarmacKit` must import no AppKit. SwiftPM enforces the target graph, and nothing enforces it file by file: a file can use a member of a module that another file of the same target imported.

Measured on `main` at `86a5320`, with Swift 6.4:

| Probe | Result |
| --- | --- |
| `swift build -Xswiftc -warnings-as-errors` | works from the command line, but stops at the first failing file of a module: 1 of the 3 warnings is listed |
| `-print-diagnostic-groups` | the 3 warnings have no group, so no setting can downgrade only them |
| a clean build into its own build path | lists all 3, every time; about 24 seconds |
| `MemberImportVisibility` | 2 files fail: `TarmacKit/FontSizeRule.swift` uses `trimmingCharacters(in:)` with no `import Foundation`, and `TarmacApp/FontFollowing.swift` uses a `TarmacKit` case with no `import TarmacKit` |
| `ExistentialAny` | 6 places must write `any P` |

The Swift compiler is not pinned. The CI image has 6.3.3 and a current Xcode has 6.4.

## Motivation

A compiler warning that nobody reads is a rule left to chance. And "TarmacKit imports no AppKit" is the layering rule that the whole test strategy depends on; a file-level check makes it something the compiler holds.

## Proposed Solution

### Overview

Two parts with different owners:

1. **What compiles** goes in `app/Package.swift`: the upcoming features `MemberImportVisibility` and `ExistentialAny` on the three product targets. Every build honours them, and the required `app (swift test)` job proves that both compilers accept the tree.
2. **Warnings** go in `make lint`, not in `Package.swift`. Warnings as errors in the manifest would let an Xcode update, which can add a warning, stop `make run`, `make bundle` and the required test job. In `make lint`, a new warning fails the lint job and nothing else.

### Key Components

- **`app/Package.swift`** — `swiftSettings: [.enableUpcomingFeature("MemberImportVisibility"), .enableUpcomingFeature("ExistentialAny")]` on `TarmacKit`, `TarmacTerm` and `TarmacApp`.
- **The 8 source changes** that those features need: two imports, six `any`.
- **`scripts/check/lint.mjs`** — a third lint, named `swiftc`: a build of the package into an empty build path, so that every warning is printed, then the warnings compared with a list of known ones.
- **`scripts/check/swiftc-known-warnings.json`** — the known warnings: for each, the file, the message, the issue that holds it, and a reason. Three entries today, all for #478.
- **`make lint ONLY=swiftc`**, and a `lint (swiftc)` job in `.github/workflows/lint.yml` on `macos-26`. `make lint` with no `ONLY` runs it too.

### The known-warnings list

The list file is a JSON array of entries; an empty list is `[]`. A warning matches an entry when the repo-relative file and the message text are equal. The line number is not part of the match, so an edit above the warning does not break it.

- A warning with no entry is a finding, named `swiftc-warning`.
- An entry that no warning matched is a finding too, named `known-warning-is-gone`: the list must shrink when the code is fixed. (This is what a Rust `#[expect]` does by itself.)
- An entry needs `file`, `message`, `issue` and `reason`, each a non-empty string. A list file that is missing, is not valid JSON, is not an array, or has an entry that lacks one of the four, cannot run the check (exit 2).
- If the build prints the same file, line, column and message more than once, it counts as one warning.
- In the report, the `at` lines are one list in byte order, as `report.mjs` sorts every list.
- The build needs `app/Vendor/`. A `make lint` run that includes `swiftc` (no `ONLY`, or `ONLY=swiftc`) stages it first (`make ghostty-vt`), so the lint can run in a fresh worktree and in CI. `ONLY=rust` and `ONLY=swift` do not stage it.
- The build directory is a new directory under the system temporary directory (`os.tmpdir()`, so `TMPDIR` moves it).

### Interface Contract

```
make lint ONLY=swiftc
node scripts/check/lint.mjs swiftc
        # exit 0: every warning of a clean build is a known one, and every known one was seen
        # exit 1: at least one finding
        # exit 2: the package does not build, swift is not on the PATH, or the list is missing or malformed
```

```
✗ lint: 2 findings from swiftc
  at   app/Sources/TarmacKit/Cull.swift:12:9 swiftc-warning
       scripts/check/swiftc-known-warnings.json:3 known-warning-is-gone
  fix  correct each warning above; remove a known warning from scripts/check/swiftc-known-warnings.json when its code is fixed
  then make lint ONLY=swiftc
```

The compiler's own lines for each finding go to stderr before the block. For `known-warning-is-gone`, the place is the list file and the entry's position in it (1 for the first).

When the package does not build:

```
✗ lint: cannot run swiftc
  why  app/Sources/TarmacKit/Cull.swift:12:9 error: cannot find 'x' in scope
  fix  make the package build: cd app && swift build
  then make lint ONLY=swiftc
```

## Alternatives Considered

### Warnings as errors in `Package.swift`

One line, and every build enforces it. Not chosen: the compiler is not pinned, so a toolchain update could stop the release build and the required test job on a warning in code nobody touched.

### `-warnings-as-errors` on the lint's command line

It needs no list. Not chosen: it reports the first failing file of a module only, and the three warnings that exist today have no diagnostic group to exempt.

### Fix the three warnings first

Then no list is needed. Not chosen here: the fix changes unsafe code on the terminal's path; #478 holds it.

## Acceptance Scenarios

S1–S7 and S15–S18 are `node --test` tests against a small SwiftPM package in a temporary git repository (`app/Package.swift`, one target), with a known-warnings list the test writes. S8–S13 and S19 are recorded commands on the real tree.

### Happy Path

- **S1:** Given a package that builds with no warning and an empty list, when `node scripts/check/lint.mjs swiftc` runs, then it exits 0 and writes nothing.
- **S2:** Given a package with one warning (an unused variable) and an empty list, when the script runs, then it exits 1, stderr holds the compiler's line, and the report is `✗ lint: 1 finding from swiftc` with the `at` line `<path>:<line>:<column> swiftc-warning`, where `<path>` is relative to the repository root (`app/Sources/...`), not absolute.
- **S3:** Given the package of S2 and a list with an entry for that file and message, when the script runs, then it exits 0.
- **S4:** Given the package of S2 with the entry of S3, and a blank line added above the warning, when the script runs, then it still exits 0.
- **S8:** Given the real tree at the head of this change, when `make lint ONLY=swiftc` runs, then it exits 0, with three entries in the list.
- **S9:** Given the real tree, when `swift test` runs in `app/`, then 2,677 tests pass.

### Edge Cases

- **S5:** Given a package with no warning and a list with one entry, when the script runs, then it exits 1 and the `at` line is `scripts/check/swiftc-known-warnings.json:1 known-warning-is-gone`.
- **S6:** Given two runs of the script one after the other on the package of S2, when the second one runs, then it reports the same finding as the first (a warning is not lost to an incremental build).
- **S10:** Given the real tree, when the three entries are removed from the list, then `make lint ONLY=swiftc` names three `swiftc-warning` findings, one in each of the three `TarmacTerm` files.

### Error Scenarios

- **S7:** Given a package that does not compile, when the script runs, then it exits 2 with `✗ lint: cannot run swiftc` and a `why` line that holds the place and the compiler's error. Given a list that is not valid JSON, or an entry with no `reason`, it exits 2 and the `why` line names the list file.

### Added scenarios

- **S15:** Given a PATH with no `swift` on it, when the script runs, then it exits 2 with `✗ lint: cannot run swiftc` and a `why` line that says `swift` is not on the PATH.
- **S16:** Given, one at a time, a list file that is missing, a list that is a JSON object (not an array), an entry that lacks `file`, `message` or `issue`, and an entry whose `reason` is `""`, when the script runs, then each run exits 2 and the `why` line names the list file.
- **S17:** Given the package of S2 and a list with one entry for that warning and one entry that matches nothing, when the script runs, then it exits 1 with exactly one finding: `scripts/check/swiftc-known-warnings.json:2 known-warning-is-gone`.
- **S18:** Given `TMPDIR` set to an empty directory, and the package of S2 with no `app/.build` directory, when the script runs (exit 1) and when it runs on the package of S7 (exit 2), then after each run the `TMPDIR` directory is empty again and the repository has no new path (`git status --porcelain --ignored` is unchanged; `app/.build` does not exist).
- **S19:** Given the real tree with one entry removed from the list (a knockout that is reverted), when `make lint` runs with no `ONLY`, then it exits 1 and the report names one `swiftc-warning` finding.

### The features hold (on the real tree; each one is a knockout that is reverted)

- **S11:** A new file in `app/Sources/TarmacKit` that uses a Foundation member (`"x".trimmingCharacters(in: .whitespaces)`) and imports nothing does not build: the error names the missing import of `Foundation`.
- **S12:** Given a `TarmacKit` file that imports AppKit (itself a violation of the layering rule), a second `TarmacKit` file that uses an AppKit member with no import of its own does not build. (This is the "through another file" case.)
- **S13:** A protocol used as a type with no `any` in `TarmacKit` is reported by the compiler. If the compiler reports it as an error, `swift build` fails. If it reports it as a warning, `make lint ONLY=swiftc` exits 1 with a `swiftc-warning` finding at that place. The record names which of the two the compiler did.

### Documents

- **S14:** `docs/coding-style.md` §4 says that a file imports what it uses and that the compiler holds it, and `CLAUDE.md` describes `make lint ONLY=swiftc`, the known-warnings list and why warnings as errors are not in `Package.swift`. `make docs-check` passes.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

- Write the tests of the script first. The existing tests of `scripts/check/` must still pass.
- The eight source changes must change no run-time result: two imports and six `any` keywords.
- The lint builds into its own empty directory and removes it afterwards. It must not touch `app/.build`, which `make run` and `make test` use.
- Never run `tarmacd`, `tarmac`, `TarmacApp`, `tarmac-smoke`, `tarmac-term-demo` or `make run`.

## Definition of Done

- [ ] `make test` and `make lint` are green.
- [ ] Every scenario maps to a test or to a recorded command with its observed values.
- [ ] No covered-but-vacuous scenarios; tests meet the Desiderata bar; no implementation-quality blockers.
- [ ] The PR's own CI run is green on the image's Swift 6.3.3: `app (swift test)` (the features compile) and `lint (swiftc)` (the same three warnings, no other). If the image's compiler reports another set of warnings, stop: that is a compiler difference to record, not a tree to change.

## Trade-offs and Limitations

- The lint builds the package from nothing, about 24 seconds, so `make lint` with no `ONLY` takes that much longer.
- The list matches on the message text. A compiler that words a warning differently makes the entry stale and the warning new; the commit that changes the toolchain corrects the list.
- CI and a current Xcode have different compilers. One list must fit both. If they disagree, the list needs a compiler field; that is decided when it happens.
- `ExistentialAny` and `MemberImportVisibility` are on for the three product targets, not for the test targets or the two demo executables.

## Decisions

1. **One entry, one warning.** Entries are used up one for one. Two warnings with the same file and message need two entries, so a fix to one of them leaves an entry that no warning matched.
2. **A missing list file** cannot run the check (exit 2). An empty list is the file `[]`.
3. **What is built:** `swift build --build-tests`, so a warning in a test target counts.
4. **`ExistentialAny` on Swift 6.4** makes a missing `any` a warning ("this will be an error in a future Swift language mode"), not an error. So S13's result is a `swiftc-warning` finding from `make lint ONLY=swiftc`. What 6.3.3 does is read from the CI run of this change.
5. **Staging `app/Vendor/`.** Accepted as the review wrote it: `make lint` stages it unless `ONLY` names `rust` or `swift`.
6. **A repository with no `app/Package.swift`** has nothing for this lint: it is clean, and the list is not read.
