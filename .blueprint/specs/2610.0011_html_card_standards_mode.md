## Context

An HTML card is `<iframe sandbox="allow-scripts">` at `tarmac-card://doc/<path>`, inside a host page (`app/Sources/TarmacApp/HTMLCardView.swift:5-11`, `Resources/Web/card-host.html`). `CardProtocol.respond` (`app/Sources/TarmacKit/CardProtocol.swift:91-105`) answers `<script>{shim}</script>\n` and then the file bytes, with the CSP header. Its doc comment says "no content sniffing, so a `<!DOCTYPE>` or a BOM changes nothing."

The script start tag is the first token the HTML parser sees. The parser puts the document in quirks mode, and makes `<html>` and `<head>` for the script. The author's doctype comes later and is ignored. So every card is in quirks mode, whatever the file says. The guide shows a card that starts with `<!doctype html>` (`GUIDE.md`, "A minimal card"), so authors expect standards mode.

Why now: PR #230 (2610.0010) gives pages `var(--tarmac-prose-size, 14px)`. In quirks mode a table cell does not inherit `font-size` from `body`. The pattern fails for tables only in Tarmac (Measured, table 3).

The shim must still run before any author script. Seven uses in the shim and the host were checked for a dependence on the mode (the table in "What the shim and the host do in both modes"). None needs a code change. Two comments become false, and one row of that table needed a correction (a quirks document can have no scrolling element for its whole life).

## Motivation

A card that starts with `<!doctype html>` renders as an author expects in every browser, and in Tarmac it does not. Tables ignore the font size of the page. `body` is as tall as the card. Images get no baseline gap. The user's Document size cannot reach table cells through `var(--tarmac-prose-size)`. An agent that tests its page in a browser and then opens it in Tarmac sees a different page. The fix is small and makes the mode the file's own.

## Proposed Solution

### Overview

`CardProtocol.respond` puts the shim's `<script>` at one byte offset of the file, not at offset 0. The offset is the end of the file's leading doctype. A file with no doctype keeps the script at the start (after a BOM, if there is one). The file's bytes are unchanged and in order. The doctype is not read, not moved and not judged: the browser's parser takes its mode from the same bytes it would see in a browser.

The offset comes from a new pure function. `respond` joins three slices.

### Key Components

- **`ShimPlacement`** (`app/Sources/TarmacKit/ShimPlacement.swift`, new). `offset(in:)` gives the byte offset for the shim. Pure, no Foundation beyond `Data`.
- **`CardProtocol.respond`** (`CardProtocol.swift`). Body is `file[..<o]` + `<script>{shim}</script>\n` + `file[o...]`. Headers, CSP, status and the 404 path do not change. The doc comment changes.
- **The shim** (`card_shim.js`). No behaviour change. Its header comment and the comment at the scroll report change.
- **The guide** (`core/crates/tarmac-cli/src/GUIDE.md`) and **`docs/architecture.md`**.
- **QA**: `qa/html-card-standards-mode.html` and `qa/html-card-standards-mode-shell.html` (new fixtures), `qa/html-card-standards-mode-qa.md` (new record).

### Data Flow

1. WebKit asks the scheme handler for the file. `CardSchemeHandler` fills the shim (fonts, per request) and hands it to `CardSchemeRouter.respond`, as in 2610.0010. Nothing here changes.
2. `CardProtocol.respond` reads the file's leading bytes through `ShimPlacement.offset(in:)` and builds the body.
3. WebKit parses: BOM, white space, comments, the doctype (these set the mode), then the shim's `<script>` (the parser makes `<html>` and `<head>` for it), then the rest of the file.
4. The shim runs before the first author script, as before. `started`, `ready`, `zoom`, `fonts`, `cull`, `scrollTo` and the scroll report work as before.

### Interface Contract

```swift
public enum ShimPlacement {
    /// The byte offset, from the first byte of `file`, at which the shim's
    /// script goes.
    public static func offset(in file: Data) -> Int
}
```

**The byte rule** (all matching is on bytes; no Unicode, no decoding). In five lines: skip a BOM; skip ASCII white space; skip `<!--` comments (closers `-->` and `--!>`) and `<?` comments (to the first `>`); then `<!doctype` (any case) ends at its first `>`, and the offset is one past it; anything else stops the scan, and the offset is the BOM length. In steps:

1. Let `p` be 0. If the file starts with `EF BB BF`, `p` is 3. `p` and every offset below count bytes from the first byte of the file.
2. Repeat at `p`, and apply the first line that matches:
   - if `p` is the end of the file, stop;
   - if the byte at `p` is an ASCII white space byte (`09`, `0A`, `0C`, `0D`, `20`), `p` moves past that one byte;
   - if the bytes at `p` are `<!--`, the comment ends after the first `-->` that starts at or after `p + 2`, or the first `--!>` that starts at or after `p + 4`, whichever starts first; `p` moves past the last byte of that closer (3 or 4 bytes); if neither exists, the result is the BOM length (rule 4);
   - if the bytes at `p` are `<?`, the comment ends after the first `>` at or after `p + 2`; `p` moves past it; if there is none, the result is the BOM length (rule 4);
   - otherwise stop.
3. If the bytes at `p` are `<!` and then `doctype` in any ASCII case (7 bytes), the offset is one past the first `>` at or after `p + 9`. If there is no such `>`, go to rule 4. The doctype's name, identifiers and quotes are not read: the tokenizer also ends a doctype at the first `>`, in quotes or not (Measured, table 1).
4. No doctype: the offset is the BOM length: 3 if the file starts with `EF BB BF`, else 0.

The result is always in `0 ... file.count`. The rule does not skip any other comment form (`<!x>`, `</ x>`, `<![CDATA[`, …) or a NUL byte: a file that starts with one gets rule 4 and stays in quirks mode, as today (Trade-offs).

The offset counts from `file.startIndex`, whatever the `Data`'s indices. A scan reads only the bytes up to the end of the doctype or the first byte that stops it. An unclosed comment, an unclosed `<?` or a doctype with no `>` makes the scan read to the end of the file once.

**The body of a 200 response:**

```
body = file[0 ..< o] + "<script>" + shim + "</script>\n" + file[o ...]      (o = ShimPlacement.offset)
```

Every file byte is in the body, in its order. Headers are exactly `Content-Type: text/html; charset=utf-8` and the CSP. A file that cannot be read gets the same 404 with no shim as today.

**The old rule "no content sniffing" is replaced by:** the response reads the start of the file up to the end of its doctype, and no more.

**Wire protocol:** no change. `tarmac-card://` is the app's own scheme. The daemon socket, `docs/protocol.md`, the conformance vectors and `tarmac-protocol` are not touched.

### What the shim and the host do in both modes

A file with no doctype stays in quirks mode, as in a browser. So the shim is correct in both modes, and both are tested (S12, S16, S23 to S26, S34).

### The shell, which is wiring

`HTMLCardView` changes only in a comment (`HTMLCardView.swift:8` says the handler "prepends the shim"). `CardSchemeHandler` does not change. The decision (the offset) is in `ShimPlacement`.

## Alternatives Considered

### (b) Always put `<!DOCTYPE html>` first

The simplest. It is wrong for a file a browser would put in quirks mode: 11 of 28 measured files differ from the browser (Measured, 1): no doctype, an HTML 4.01 Transitional doctype with no system id, `<!doctype>`, a broken doctype. An author who wrote a legacy page, or a page with no doctype, would see a standards page that the browser does not show. It also hides the author's own doctype. Not chosen.

### (c) A `WKUserScript` at document start

The file would be served as it is. It runs before the first author script in the sandboxed frame (measured), but there is no `document.head` then, so the default colour scheme of 2610.0007 is lost (count of metas 0 against 1), the two observers observe `null`, and the source of a user script is fixed when the web view is made, so the per-request font fill of 2610.0010 cannot be done. It also runs in every nested frame of the page. It would change three contracts to keep a rule ("bytes untouched") that the split already keeps in another form. Not chosen.

### Move the doctype, not split

`DOCTYPE` + shim + (file minus the doctype). It reorders the file's bytes, and leading comments end up after the doctype. Splitting at one offset keeps every byte in order. Not chosen.

### Skip every bogus comment of the HTML grammar

`<!x>`, `</ x>`, `</>`, `<![CDATA[x]]>`, `<!->`, `<!doctyp>` and the like end at the first `>`. A rule that skips them matched the browser on all 41 files of the author. It adds a clause for forms that no page in `qa/` and no guide example uses, and the failure of the lean rule is in the safe direction (quirks mode, as today). The user chose the lean rule (D1). Not chosen.

### Keep quirks mode, tell authors to write `table { font-size: inherit }`

It does not fix the issue, and every page in Tarmac would still differ from the browser. Not chosen.

### A per-card opt-out (a `<meta>`)

See Migration & Rollback.

## Migration & Rollback

### Migration Steps

1. The change is in the response of the scheme handler. A card document is served again when the app loads it, so a card shows the new mode the next time its document loads (app start, or a change of the file).
2. No state, no file format and no setting changes. Nothing is migrated.
3. Existing cards that start with a doctype change layout (Measured, 3). The list of fixtures that read differently is in Measured, 4. QA records: see "What happens to the QA records" in Trade-offs.
4. **Merge order (D3).** This work is built on the #225 branch (`538508e`) and is a stacked PR. PR #230 merges first; then this PR is retargeted at `main` (it needs no rebase if #230 is squash-merged with the same tree; if it is not, rebase it on `main` and run S22 again). It touches no line of #230's `CardProtocol.respond`, `CardFontVariables` or `HTMLCardSession`. The shared files are `card_shim.js` (header comment and one comment), `GUIDE.md` (a section next to "The user's fonts") and `docs/architecture.md` (the `doc` host bullet and the shim bullet, next to #230's edits).

### Rollback Plan

Revert the commit. Nothing persists. There is no per-card opt-out, on purpose: a file with no doctype is in quirks mode, as in a browser, so an author who needs quirks mode can leave the doctype out, or use a legacy doctype. A Tarmac-only `<meta>` would be markup that only Tarmac reads, and `ZoomMode` already avoids "markup injected into the page" that "makes the served document lie about its source". The cost of the opt-out would be a new rule to read, document and test for a case that has a one-line answer.

## Security Considerations

The CSP is unchanged and is still sent as a header; the shim is still one inline script in the same document. The scan reads file bytes only to find an offset. If the scan and the tokenizer disagreed, the shim's script could land in a comment or in a doctype and not run, or after content that the browser had parsed. The card would then have no shim, which is the state of a file that cannot reach the shim today (the host counts a frame that has loaded as started, `card-host.js`). The scan was compared with WebKit on 99 runs (41 files of the author and 58 of the verifier, Measured, 1). In none of them did the lean rule give standards mode where the browser gives quirks mode, and in all 58 files of the verifier the shim ran. The differences are all in the other direction (the script goes to the start of the file, runs, and the document is in quirks mode, as today). The `--!>` closer is what keeps `<!-- a --!> b -->` + doctype on the safe side. The shim cannot be moved into a context that gives a file more power.

### The offset (kit)

All in `ShimPlacementTests`. The vectors are literal bytes with their offset. In S1 to S4, D is `<!doctype html>` (15 bytes) and R is `<p>x</p>`; a vector is the prefix named, then D, then R (`prefix + D + R`). The offsets below were not counted by hand: they are the output of the rule run on every vector, in two scratch implementations (Python and Swift, `scratchpad/spec-214/lean/rule.py` and `cli.swift`), which agree on all 56 vectors of the scratch set: the 54 vectors of S1 to S6, and two files of the known differences (`<!x>` + D + R and `</x>` + D + R, offset 0) that are not test vectors (For the Implementing Agent).

- **S1 [red, `ShimPlacementTests`]:** Given the files `<!doctype html><p>x</p>`, `<!DOCTYPE HTML><p>x</p>`, `<!DocType html><p>x</p>` and `<!doctypehtml><p>x</p>`, when the offset is asked, then it is one past the first `>`: 15, 15, 15 and 14. The bytes at the offset are `<p>x</p>`. Given a file that is only `<!doctype html>` (15 bytes), then the offset is 15, the length of the file, and the rest is empty.
- **S2 [red, `ShimPlacementTests`]:** Given `prefix + D + R` with each prefix below, then the offset is as shown: a BOM `EF BB BF` 18; one white space byte `09`, `0A`, `0C`, `0D` or `20` 16 each; `<!-- n -->` 25; `<!-- a -->\n<!-- b -->\n` and two spaces 39; `<?xml version="1.0"?>\n` 37; `<?x>` 19 and `<?>` 18 (a `<?` ends at its first `>`, not at `?>`); a BOM, `\n<!-- c -->\n` 30; `<!-- <!doctype html> > -->\n` 42. - **S3 [red, `ShimPlacementTests`]:** Given `prefix + D + R` with a comment before the doctype, then the offset is: `<!-- x -->` 25; `<!-- x --!>` 26; the abrupt `<!-->` 20 and `<!--->` 21; `<!---->` 22; `<!----!>` 23; the nested openers `<!-- a <!--> ` 28, `<!-- a <!---> ` 29 and `<!-- a <!-- b --> ` 33 (each ends with a space). ## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

Implement however you work best. Only the result is checked. The repository's own rules still bind (`docs/coding-style.md`): red first and observed red; the smallest correct diff; no line-noise comments; do not run `cargo fmt`; verify with `make`, not the editor.

A guard is not the red of any change. Start from the **[red]** scenarios: S1 to S7, S9 to S11, S14, S15, S17, S19, S20, S35. Watch each fail on the unmodified tree for the reason you predicted. Introduce `ShimPlacement.offset(in:)` as a stub that returns `-1` first (never a valid offset), so that S1 to S7 fail on an assertion and not on a compile error. A stub that returns 0 is not enough: S5 and the "offset is 0" vectors of S3 pass against it. A test that slices the file at the offset (S1, S7) first asserts the integer with `XCTAssertEqual`, and slices only when the offset is in `0 ... file.count`: a `Data` slice at `-1` traps and stops the whole test process, which is not a red.

Points that are easy to get wrong:

- **Split the file; do not move or edit the doctype.** The body is three slices. If a test passes when the doctype is copied, or when `<!DOCTYPE html>` is added, it does not test the change (the exact bodies of S9, S10, S11 and S15 break both).
- **Never judge the doctype.** The mode comes from the browser. The code finds the end of the doctype and nothing else. Any test that asserts a mode is a QA test.
- **The first `>` ends a doctype, even inside quotes** (Measured, table 1; S4). Do not parse quotes.
- **The lean rule is the rule (D1).** Do not add `<!x>`, `</` or `<![CDATA[` handling, and do not skip NUL bytes. A vector for them would pin a divergence; they are in Trade-offs only.
- **Comment closers.** `-->` is searched from `p + 2`, because `<!-->` and `<!--->` end at once. `--!>` is searched from `p + 4`, because `<!---!>` does not end (S3). Both closers are needed: with `-->` alone, `<!-- a --!> b -->` + doctype puts the script after content the browser has parsed. Measured against WebKit: `<!-->`, `<!--->`, `<!---->`, `<!-- x --!>`, `<!----!>`, `<!-- a --!> b -->`, and the three nested forms. `<!---!>` swallows the file, so it has no `compatMode`.
- **An unterminated thing means no doctype, and the offset is the BOM length**, not "the end of the file" (S5, S6).
- **Do not touch the shim string.** The offset function has no knowledge of the marker or the fonts. `CardFontVariables.filling` runs before `respond`, as it does now (S14). `CardProtocol.respond` and `CardSchemeRouter.respond` keep their signatures.
- **`CardShimTests` cannot test the mode.** Do not add a stand-in `compatMode`. Leave the "no scrolling element" test and its assertions (S16). Rewrite the comment of the `started` test at `CardShimTests.swift:1394` (S20).
- **No code change in the shim.** If a scenario seems to need one, the scenario is wrong: the report is the same in both modes (Measured, 2). Change only the two comments, with the text given in "What the shim and the host do in both modes".
- **Rename the two flipped tests** (S9, S11). Their old names say the shim precedes the doctype and the BOM.
- **The guide is read on a machine with no checkout.** Name no repo path and no relative link (S17, S18).
- **An ACTIVE doc may not name a file with a path that does not exist** (`scripts/docs-check.mjs`, rule 3). In `docs/architecture.md`, say `ShimPlacement` without a path, or name `app/Sources/TarmacKit/ShimPlacement.swift` only after the file exists.
- **The QA files are real work.** Make the two fixtures from the text above, make the copies as "The QA witness" describes them (one change of bytes each), and add the record. A scenario with no observed value is not done. The fixture must keep `setInterval(follow, 100)`: without it S26 cannot pass (Measured, 8).
- **Never launch `dist/Tarmac.app`.** Never kill a daemon by name. All live QA is against `make run`; stop its daemon with `make kill-daemon`.

Test principles, the ones `/verify` scores against:

- **Behavioral over structural**: assert the bytes that are served, not the helper that made them.
- **Every test can fail**: no copy of the expected value from the code; write the vectors by hand.
- **Deterministic, isolated, readable**: no clock, no machine-dependent bound.

## Trade-offs and Limitations

- **Every existing card with a doctype changes layout.** The differences are in Measured, 3: table cells inherit the font size; `body` and `html` are as tall as their content; `height: 100%` on a child of `body` resolves to auto; an image in a block gets the line's descender gap; unitless lengths are ignored; `document.body.scrollTop` stops scrolling. This is the browser's behaviour for the same file. Of 29 `qa/` pages, 3 changed total by 5, 44 and 598 units; 26 did not. All 29 become `CSS1Compat`, the 3 that start with a comment too.
- **What happens to the QA records.** They are dated runs and are not edited, except for dated notes (S35). These records ran in quirks mode and stay as history: `qa/scroll-indicator-qa.md` S16 (`compat BackCompat`), `qa/magnify-card-qa.md` S5 (it expects `BackCompat`, and the two `clientWidth` values to disagree), `qa/native-wheel-qa.md` (the probe paints `compat`), `qa/cull-qa.md` (it says the shim is "before the file's first byte"). `qa/html-card-scheme/README.md` is not a dated run: it describes permanent QA files, and its sentence "with the shim before its first byte" is corrected (S20). `qa/magnify-card-qa.md` S5 gets a dated note: a file with a doctype now reads `CSS1Compat`; `magnify-probe.html` prints `scrolled=true` (it printed `false`) and `clientWidth=1176 bodyClientWidth=376` (it printed `392` and `1176`); the ICB probe is the criterion in both modes. The same record's S6 gets a dated note that `wrap-probe.html` labels the line `ICB 1176px` (it labelled `ICB 392px`) with the same break offsets. These records are run again: `qa/html-card-qa.md` (S18 with `sandbox-probe.html`), `qa/scroll-band-qa.md` (row 1), `qa/doc-card-raster-cost-qa.md` (the scaler probe), the S62 and S66 rows of `qa/theme-qa.md`, `qa/html-card-font-variables-qa.md` S30 to S40, and the rows named in S28. These are not run again: `qa/cull-qa.md`, `qa/doc-refresh-qa.md` and the wrap records. The verifier settled this: their totals are equal, and the readings that change are the two noted above.
- **A page that scrolls with `document.body.scrollTop` stops scrolling.** This is what a browser does. The guide says so (S17).
- **A card whose body scrolls itself now reports a scroll position.** Before, `document.scrollingElement` was `null` for the whole life of such a document, so the shim sent no `scrolled` message and the dev snapshot's `scroll` was `null`. After, a file with a doctype sends (0, v, v). There is no visible effect: the indicator needs an overflow. Only the snapshot's shape changes (S34).
- **`<head>` attributes are dropped, as today.** The shim's script makes `<head>` before the author's `<head>` tag, so `<head id="x" data-y="1">` loses its attributes (measured: `headId` `""`, `headData` `null`, in both today and (a); with no shim they are kept). `<html>` and `<body>` attributes are kept. Not a regression; not fixed here. The guide says it (S17).
- **A BOM that is not at the start of the file** is not touched.
- **A file that starts with a comment form other than `<!--` and `<?` stays in quirks mode** (D1). `<!x>`, `<!>`, `<!ELEMENT …>`, `<!->`, `</ x>`, `</>`, `<![CDATA[x]]>` and `<!doctyp>` before the doctype are skipped by a browser, which then gives standards mode (measured: CSS1Compat). The lean rule stops at them, gives offset 0, and the document is in quirks mode, as today. The direction is safe: the shim is first and runs, and the page is as it was.
- **Known divergence: NUL bytes before the doctype.** WebKit drops NUL bytes in the initial insertion mode and gives standards mode (CSS1Compat). The rule stops at a NUL byte (offset 0, quirks, as today). The HTML Standard agrees with the rule here (a NUL is not white space), so this is a difference of WebKit from the standard, in the safe direction. It is not handled. The verifier found it (cases with NUL before, after a BOM and after a comment).
- **A UTF-16 file does not run**, today or after: the response says UTF-8 and the shim is UTF-8 text. The rule gives 0 for it.
- **The scan is not a parser.** It follows the HTML tokenizer for comments, `<?` comments and the doctype. A file whose start the scan reads differently from WebKit gets the script in a place where it may not run. The files tried are in Measured, 1; the differences found are the quirks-direction ones above.
- **Limited quirks and standards look the same to `compatMode`.** The doctype is passed through unchanged, so the mode is the browser's, but the live scenarios do not show the limited-quirks layout rule (image gaps in table cells).
