# 2609.0008 Terminals keep their scrollback across a webview reload

**Date:** 2026-09-07
**Status:** draft
**Author:** EP Lin
**Issue:** [#41](https://github.com/pingeplin/tarmac/issues/41) `fix(terminal): scrollback lost after webview reload`
**Design doc:** none — the approach is settled by the code evidence below.

All citations checked against `main` @ `68be9cc` (the worktree base).

## Context

After the WKWebView default "Reload", every terminal card remounts with a fresh
xterm.js instance and no history. The Tauri backend process and its daemon socket
are untouched by the reload, so both stores of the bytes survive:

- the daemon's per-term 256 KiB ring (`core/crates/tarmacd/src/term.rs`, snapshot via
  `TermHandle::scrollback_snapshot`, used by `conn.rs:126-138 snapshot_scrollback`);
- the bridge's per-term buffer (`desktop/src-tauri/src/bridge.rs:43-47`).

Neither reaches the fresh xterm:

1. **The bridge buffer never holds history.** `dispatch` buffers a chunk only when
   **no channel is attached** (`bridge.rs:357-376`); once `attach_output` has run,
   bytes go straight to the channel and are never retained. So a buffer preserved
   across an unmount would carry only the bytes of the unmount→remount window —
   seconds of output, not the 256 KiB the acceptance bullet asks for. (The issue's
   part 1 also targets `TerminalCard`'s cleanup → `detachTermOutput`
   (`TerminalCard.tsx:325`) → `term_detach` (`commands.rs:32-34`) →
   `Bridge::forget_term` (`bridge.rs:165-168`), which wipes the buffer. On a hard
   reload that cleanup does not even run — see the Unmount table.)
2. **The daemon replays at most once per board per connection.** `AppConn.replayed`
   (`conn.rs:100-107`) gates `send_board` (`conn.rs:145-168`); a webview reload does
   not drop the socket, so no second replay is ever produced. `Bridge::replay`
   on `frontend_ready` re-emits status / board_list / restores only (`bridge.rs:115-127`).

**Therefore the issue's part 1 is neither sufficient nor necessary; the fix is part 2
alone — the daemon must be able to re-emit a term's ring on demand.**

## Motivation

A reload — accidental (right-click → Reload is one menu item away, and is how QA
reaches Inspect Element) or deliberate (dev HMR) — silently destroys every
terminal's visible history while the shells themselves keep running. The user sees
live-but-amnesiac terminals and has no way to recover the transcript. The data
exists in two places already; only the delivery path is missing.

## Proposed Solution

### Overview

Make the **daemon ring the single replay source, requested per terminal at attach
time**, and let the bridge — not React — decide what a card mount means. Two
additive wire messages carry the request and its reply; the bridge holds live bytes
until the reply lands so a fresh xterm receives history-then-live, exactly once.

### Key Components

- **`tarmac-protocol` (`core/crates/tarmac-protocol/src/lib.rs`)** — two additive
  variants above `#[serde(other)] Unknown`: `ScrollbackRequest { term_id }`
  (app → daemon) and `Scrollback { term_id, bytes }` (daemon → app, `serde_bytes`
  `bin`). Plus conformance vectors V12 and V13.
- **`tarmacd` (`core/crates/tarmacd/src/conn.rs`)** — a `dispatch_app_msg` arm for
  `ScrollbackRequest`: snapshot that one term's ring (reuse the existing
  `scrollback_snapshot` call shape — **not** `snapshot_scrollback`, which skips empty
  rings and would answer S5 with silence) and send **exactly one** `Scrollback` frame on
  `conn.tx`. `AppConn.replayed` is not read or written by this arm.
- **`Bridge` (`desktop/src-tauri/src/bridge.rs`)** — an `awaiting: Mutex<HashSet<String>>`
  (terms whose reply is outstanding); `attach_output` marks awaiting and sends the
  request; `dispatch` gains a `Msg::Scrollback` arm (binary — must not fall through
  to the JSON `other` arm) and buffers `Output` while awaiting; the connection loop
  clears `awaiting` on socket loss; `forget_term` also clears the term's `awaiting`
  entry, so an unmount mid-request leaves nothing behind.
- **`commands.rs`, `TerminalCard.tsx`, `App.tsx` — unchanged.** `term_detach` keeps
  calling `forget_term`, and the frontend never distinguishes a reload unmount from
  any other unmount. See the Unmount table for why this is now correct.

### Data Flow (a card mount)

1. `TerminalCard` mounts → `attachTermOutput` (`TerminalCard.tsx:223`).
2. `Bridge::attach_output`: insert the channel, mark the term awaiting, drain
   nothing, send `ScrollbackRequest { term_id }`.
3. Daemon: `dispatch_app_msg` snapshots the ring and sends one `Scrollback` frame.
4. Live `Output` arriving in between goes to `push_buffered` (the term is awaiting).
5. `Bridge` receives `Scrollback`: **discard that term's buffer**, write `bytes` to
   the channel, clear awaiting. Subsequent `Output` flows live.

Step 5's discard is safe whenever no pump push lands between the daemon's snapshot
and the reply being enqueued: everything already pushed is inside the snapshot, and
everything pushed after the reply arrives after it on the same FIFO socket. A push
inside that gap duplicates or drops exactly that one chunk — a pre-existing window,
see Trade-offs.

### Interface Contract

```rust
// app -> daemon: re-emit one term's scrollback ring. Unknown term_id is NOT an
// error — the daemon replies with empty bytes so the app never waits forever.
ScrollbackRequest { term_id: String },

// daemon -> app: the answer to exactly one ScrollbackRequest. Always sent, even
// when the ring is empty or the term is unknown. One frame per request.
Scrollback { term_id: String, #[serde(with = "serde_bytes")] bytes: Vec<u8> },
```

**Replay rule (the single-source guarantee).** A fresh xterm receives its history
from `Scrollback` and from nowhere else:

| Bridge event | Behavior |
|---|---|
| `attach_output(term)` | insert channel; mark `term` awaiting under a fresh generation; send `ScrollbackRequest` |
| `attach_output(term)` while `term` is already awaiting (a card unmounted and remounted inside the window) | the new attach's generation replaces the entry, so the earlier deadline is stale and its `expire` is a no-op — the remount keeps holding for its own reply. The first reply to arrive settles the term either way: every request for a term is answered with the same ring, so `Scrollback` carries no generation |
| `Output` for `term` | send iff a channel is attached **and** `term` is not awaiting; else `push_buffered` |
| `Scrollback` for a non-awaiting `term` | drop (guards a double attach / duplicate reply) |
| `Scrollback` for an awaiting `term` | discard the term's buffer, write `bytes` to the channel (drop if the channel is gone — the next attach re-requests), clear awaiting |
| no reply within `AWAIT_TIMEOUT` (2 s) | clear awaiting and **deliver** the term's buffer in order — the one case the buffer is drained. A same-version daemon built before this change decodes `scrollback_request` as `Unknown` and never replies; without the deadline every card would await forever and stay blank. A reply arriving after it is dropped by the non-awaiting row above |
| socket loss | clear all `awaiting` (a dead daemon must not leave cards blank forever) |
| `forget_term(term)` | drop the channel, the buffer, and the `awaiting` entry |

**Unmount table.** Every unmount path keeps its current behavior — `term_detach` →
`forget_term` (channel + buffer + `awaiting` dropped) — because under the Replay rule
the buffer is never a replay source: it holds bytes only between an attach and its
reply, a window in which the card is by definition mounted. Whatever a buffer held
before an attach is discarded at step 5 anyway.

| Path | Cleanup runs? | Bridge effect | Correct? |
|---|---|---|---|
| Webview reload | **no** (WKWebView Reload; Vite HMR *does* re-run cleanups → `forget_term`, which is equally fine — the remount re-requests either way) — the only unload hook is `beforeunload → flushPersist` (`App.tsx:1490,1493`); nothing unmounts the React root | stale channel entry survives, so bytes in the gap are dropped into it, never buffered; the remount's `attach_output` replaces it and re-requests the ring | yes |
| ⌘W card close | yes | `detach_output` at `term_close` (`commands.rs:80`), then `forget_term` at unmount | yes |
| Board delete | yes | `forget_term` per card; daemon kills the ptys (`conn.rs:409-410` → `term.rs:326-332`) | yes |
| Term exits on its own | for `remove`/`removeAndReplace` (`App.tsx handleExit`); a non-zero exit holds the card open | `forget_term` at unmount, or nothing while a dead card stays | yes — the daemon dropped the handle, so a later request replies empty either way |
| Board switch | **no** — hidden boards are `display:none` (`Board.tsx:143`), and offscreen culling toggles visibility only | none | yes |
| App quit | process exit | none | yes |

The outcome is identical whether or not a cleanup runs on any given path, so the
frontend needs no reload-vs-exit discrimination and the permanent-death path is
literally untouched (acceptance bullet 3).

## Alternatives Considered

### (a) Drop and re-establish the daemon socket on reload

A fresh connection resets `AppConn.replayed`, so `send_board` replays. Rejected on
four grounds: `Bridge::replay` re-emits `connected: true` on `frontend_ready`, so the
deliberate drop trips the "tarmacd connection lost" toast (`App.tsx:1145-1148`);
`frontend_ready` also fires on first launch, and the bridge cannot tell a reload from
a launch, so it would reconnect on every start; `connect()` runs the daemon-**spawn**
path on a miss (`bridge.rs:397-423`), churning generations against a healthy daemon;
and `send_board` replays the active board only, leaving hidden boards blank until
switched. (Note: it would *not* raise the "daemon restarted" toast — a reload resets
React state, so every restore is `isFirstVisit` and the reconcile branch at
`App.tsx:767-784` is never entered.)

### (b') `ScrollbackRequest` answered with ordinary `Msg::Output` chunks

The issue's sketch, and one variant/one vector cheaper. Rejected: a chunk stream has
no end marker, so the bridge cannot know when to stop holding live bytes. Without a
hold, live output produced during the remount is written to xterm **before** the
replayed history (reorder) and **again** inside it (duplicate). The single-frame
`Scrollback` reply is that marker; the second variant buys the exactly-once rule.

### (c) The issue's part 1 — buffer-preserving detach, in either form

Either route `term_detach` to `detach_output` and move `forget_term` to a bridge
`Msg::Exit` arm, or gate `forget_term` on the card's `dead` flag in React. Rejected as
dead weight: the preserved buffer is discarded at step 5 regardless, the cleanup does
not run on the WKWebView reload path at all, and the `dead`-flag variant additionally puts a
daemon-liveness decision in React (which learns of death asynchronously) where this
repo has no component tests. Both enlarge the diff around the permanent-death path
that bullet 3 asks us not to disturb.

## Acceptance Scenarios

### Happy path

- **S1** (automated, tarmacd integration): Given a live term that has echoed a marker
  string (send `Input`, `recv_until` an `Output` containing it), when the app sends
  `ScrollbackRequest { term_id }`, then a `Scrollback` frame for that term arrives
  whose `bytes` contain the marker, and no second `Scrollback` for that term arrives
  within a short window (`none_within`). (The harness is out-of-process — `common/mod.rs` spawns a real
  daemon — so assert over the wire, never over `scrollback_snapshot()`.)
- **S2** (automated, bridge unit): Given a term marked awaiting with buffered live
  bytes, when its `Scrollback` reply is applied, then the buffered bytes are
  discarded, the reply bytes are the only thing delivered, and the term is no
  longer awaiting.
- **S3** (QA): Given terminals with visible history on the board, when the user
  right-clicks the board and picks Reload, then each terminal card remounts showing
  its history (up to the 256 KiB cap) with no duplicated or out-of-order region.
- **S4** (QA): Given a reloaded terminal, when the user types, then the characters
  echo and the shell responds normally.

### Edge cases

- **S5** (automated, tarmacd integration): Given a `term_id` the daemon does not own
  — and, separately, a live but silent term (spawn with `cmd: ["sleep","30"]`; a
  default shell prints a prompt within milliseconds) — when it receives
  `ScrollbackRequest`, then in both cases it replies with `Scrollback` carrying empty
  `bytes` (never silence) and does not error. *(Hot path: `attachTermOutput`
  precedes `onSpawn` at `TerminalCard.tsx:223`, so ⌘T's request always reaches the
  daemon before its `SpawnTerm`.)*
- **S6** (automated, tarmacd integration): Given a connection that has been served a
  `ScrollbackRequest` for a term on a not-yet-visited board, when the app then
  switches to that board for the first time, then its restore is still followed by
  the one-time `Output` replay (and a switch away and back yields none) — the request
  neither consumes nor sets `AppConn.replayed`.
- **S7** (automated, bridge unit): Given a term that is awaiting, when `Output`
  arrives for it, then it is buffered rather than written to the attached channel;
  and given a term that is not awaiting with a channel attached, it is written
  through.
- **S8** (automated, bridge unit): Given a `Bridge` (constructible from an
  `UnboundedSender` alone — no `AppHandle`) whose term is awaiting with a non-empty
  buffer, when `forget_term` runs, then both the buffer and the `awaiting` entry are
  gone, so a subsequent `Scrollback` for that term is dropped (Replay-rule row 3).
- **S9** (automated, bridge unit): Given a term that is **not** awaiting, when a
  `Scrollback` for it is applied, then nothing is delivered and no buffer is
  discarded — and given an awaiting term whose channel is gone, the reply still
  clears `awaiting` and drops the bytes (the next attach re-requests).
- **S13** (automated, bridge unit): Given a term left awaiting when the socket drops,
  when the connection loss is handled, then the term is no longer awaiting, so a
  later `Output` for it is written through instead of buffered forever.
- **S10** (automated, protocol): Given the byte-pinned vectors V12
  (`scrollback_request`) and V13 (`scrollback`, `bin`-encoded bytes), when decoded,
  then they round-trip to the new variants, and V1–V11 are unchanged.

### Error / regression scenarios

- **S11** (QA): Given a terminal whose shell is running, when the user runs `exit`
  (status 0) in it, then the card is removed (or replaced, per `App.tsx handleExit`'s
  existing policy) exactly as on `main` — the permanent-death path is unchanged.
- **S12** (QA): Given a board with live terminals, when the daemon is restarted
  (`make kill-daemon`), then the "daemon restarted — terminals lost" toast appears
  exactly once and the terminals are marked dead.

## Trade-offs and Limitations

- **A request per card mount costs up to 256 KiB of IPC.** Mounts are rare (spawn,
  reload, first visit to a board) — board switches keep cards mounted — so this is
  bounded and local.
- **`send_board`'s connect-time replay becomes redundant work** (its bytes are
  buffered, then discarded by the first `Scrollback`). Left in place on purpose:
  `restore_integration.rs` pins it, and removing it is out of scope.
- **Pump window, inherited and slightly widened.** `Daemon::push` feeds the same
  `conn.tx` the reply uses (`state.rs:517-523`), and the pump rings-then-pushes as two
  steps (`term.rs:305-308`), so a chunk pushed between the snapshot and the reply is
  outside the snapshot yet arrives ahead of it — and the bridge **discards** its
  buffer at step 5, so that chunk is *dropped*. `send_board`'s connect-time replay
  has the same race on `main` (`conn.rs:154-156`) but a milder consequence: nothing
  discards there, so it can only reorder or duplicate. We trade a rare one-chunk
  loss for the exactly-once guarantee, and pay it on every card mount rather than
  once per board per connection. The mirror-image seam is the pump's own
  ring-append-then-enqueue (`term.rs:288-291`, and again at `:303-307`): a chunk
  already in the ring but not yet on `conn.tx` is both snapshotted and delivered
  live, duplicating exactly one chunk (never losing one). Both windows are
  sub-microsecond and accepted; closing either needs pump-side changes — out of
  scope for #41.
- **A reload can still take two restores, in one narrow window.** If the daemon's
  connect-time `restore` reaches the frontend in the IPC hop before its
  `frontend_ready` reaches the bridge, the re-requested restore is that board's
  second and takes the reconnect-revive path. Pre-existing on `main` — the cached
  replay had the same window — and unchanged here: issue #123's fix stops the
  *stale* restore, not the second one.
- **A dead-but-retained card is blank after a reload.** The ring dies with the
  `TermHandle` (`term.rs:326-332`), so a card held open by a non-zero exit answers
  its post-reload request with empty bytes and loses the transcript that explains
  the failure. Likewise a term that exits *during* the request round-trip shows
  nothing: the handle is gone before the snapshot is taken.
- **A term that exited before its card was ever mounted shows nothing.** Its
  pre-attach buffer is discarded at step 5 and the daemon has already dropped the
  handle (`term.rs:326-332`), so the reply is empty. On `main` those buffered bytes
  would have been drained on the first attach. Narrow (only a board never visited
  this session) and inherent to making the ring the single source.
- Context-menu suppression (also floated on #41) is **out of scope**; QA relies on
  the right-click menu.
