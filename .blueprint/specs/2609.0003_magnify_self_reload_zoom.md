# 2609.0003 Magnify root zoom survives a document self-reload

**Date:** 2026-09-05
**Status:** accepted
**Author:** EP Lin
**Issue:** [#99](https://github.com/pingeplin/tarmac/issues/99) `fix(cards): magnify card renders at 1/K after the document self-reloads`
**Design doc:** none — the shape is settled by [2608.0001](../../docs/designs/2608.0001_frozen_k_magnify_for_html_cards.md) (frozen-K) and by the precedent [2609.0002](../../docs/designs/2609.0002_offscreen_html_card_throttle.md) set for the cull post; this spec picks between two named fixes and states the trade-off.
**Corrects:** spec [2607.0006](2607.0006_magnify_zoom_mode_for_html_cards.md) S9 (the standing `pendingZoom` note), and the S17 *tell* in `desktop/qa/magnify-card-qa.md` (the received-zoom panel). 2607.0006's own S17 text names only the mode-in-force and the one-line-per-load count, both of which survive this fix, so it needs no correction.
**Must not regress:** [2609.0002](2609.0002_offscreen_html_card_throttle.md) S36 (`desktop/qa/cull-qa.md` S36 — the #99-shaped self-reload comes back paused)

## Context

Under frozen-K magnify (2608.0001) the host posts the sandboxed document exactly
one root zoom per load, `{tarmac:"zoom", z: MAGNIFY_K}`, and carries every
subsequent board zoom with a permanent `scale(--zoom / K)` on the outer box. The
box is sized `frame × K`. Both halves are required: if the root zoom never lands
while the box stays `frame × K`, the document lays out in a viewport `K×` too
wide and the compositor then shrinks it — the card renders at **1/K size with
broken scroll height**, which 2608.0001 §Capability names as "not a fallback, a
visibly broken card".

The host posts that zoom from exactly one place —
`desktop/src/cards/HtmlCard.tsx:163`, inside the `ready` handler, **after** the
`readyHandledRef` guard at `:142`. The ref is cleared only by the effect keyed on
`props.lastChangedMs` (`:119–124`). A document that reloads **itself** —
card JS calling `location.reload()`, or webview recovery — changes neither `src`
nor `lastChangedMs`, so:

1. the reloaded document's shim posts a genuine `ready`;
2. the host returns early at the guard and posts no zoom;
3. `document.documentElement.style.zoom` is never set on the new document;
4. `magnify` state stays `true`, so the box stays `frame × K` — sized for a root
   zoom that never landed.

Two facts about the current tree bound the fix:

- **#106 already put one post in front of that guard.** `postCull(culledRef.current)`
  at `:141` is pre-guard precisely so a #99-shaped self-reload comes back paused
  (2609.0002 §The gate, specified; verified as `cull-qa.md` S36). It is an
  idempotent *state*, which is why re-asserting it cannot weaken the guard.
- **The shim's `pendingZoom` retention branch is unreachable by the repro that
  was written for it.** `card_shim.js:257` declares it, `:302` retains, `:318`
  applies. The host posts zoom only *in reply to* `ready`, and `postReady` sets
  `ready = true` before it posts — so a zoom can never reach a shim that has not
  yet posted its own `ready`. What remains reachable today is one narrow shape:
  the host's reply to a **first** `ready` crossing a self-reload in flight, so it
  lands on the *next* document's unready shim. Nobody can force that by hand, and
  the settle-driven repro 2607.0006 S9 prescribes cannot reach it at all under
  frozen-K. Fix (b) makes the same race reachable on every generation rather than
  the first only — while also making the retained value redundant with the reply
  to that document's own `ready` (§The `pendingZoom` decision).
  2607.0006 S9 carries a standing note against deleting the branch on
  the strength of a not-verified; `desktop/qa/magnify-card-qa.md` S9 records the
  scenario as **NOT VERIFIED** for exactly this reason.

Every line citation above was re-checked against `136fc0c`.

## Motivation

The failure is silent and total: a card that self-reloads becomes unreadable and
stays unreadable for the rest of its life, with no console line and no chrome to
say what happened. Nothing in `make test` catches it, and the one QA scenario
pointed at this path (`magnify-card-qa.md` S9) is blocked on it. The bug also
leaves the shim's `pendingZoom` branch load-bearing for a race no test exercises
and no prescribed repro can reach — three lines the repo cannot currently
demonstrate, delete cheaply, or reason about. This fix does not remove them; it
makes them redundant and pins them with a test (§The `pendingZoom` decision).

`location.reload()` is not exotic for the documents Tarmac cards are: a dashboard
that re-fetches by reloading, a generated report that refreshes itself, and
WebKit's own recovery after a renderer crash all take this path.

## Proposed Solution

### Overview

**Fix (b) — split what the guard protects.** Keep `readyHandledRef`'s
once-per-load semantics for the two things that must not repeat (the
`zoom-mode declared=… effective=…` console line, and adopting the mode the meta
declares), and let the `{tarmac:"zoom", z: MAGNIFY_K}` post answer **every**
genuine `ready`, gated on the mode already **in force for this load**.

This mirrors the precedent #106 set one line earlier: under frozen-K the zoom
post is a fixed constant, so re-posting it is an idempotent state assertion that
cannot flip a mode, exactly as the cull post is. Fix (a) — clearing the ref on
every `ready` — is rejected below; it answers the same loads but re-opens the
forgery hole the ref exists to close.

**One invariant is load-bearing and is what separates this from the issue's
sketch of (b):** a repeat `ready` decides whether to post zoom from the mode
**in force**, never from that repeat's own `meta`. A blind pre-guard post would
let a forged `{tarmac:"ready", meta:"magnify"}` inject root zoom `K` into a
*reveal* card, which is a new regression rather than an accepted trade-off.

### Key Components

- **`desktop/src/kit/zoomMode.ts`** — gains `readyActions()`, the pure per-`ready`
  verdict: what this `ready` adopts, whether it logs the console line, and what
  (if anything) it posts to the document. The module's own docstring already
  claims to be where every zoom verdict lives so it stays unit-testable; the React
  shell has no unit tests, so a decision left in the handler is a decision that
  cannot be tested (`.claude/…/memory` note: *App layer isn't unit-tested*).
- **`desktop/src/cards/HtmlCard.tsx`** — the `ready` handler becomes glue: post
  cull (unchanged, still first), call `readyActions`, apply what it returns.
  `readyHandledRef: boolean` is replaced by a single per-load ref
  `loadModeRef: ZoomMode | null` (`null` = no genuine `ready` honored yet for this
  load), so "has a ready been honored" and "which mode is in force" cannot drift
  apart.
- **`desktop/src-tauri/src/card_shim.js`** — **no source change.** Its
  `pendingZoom` branch is kept (see below) and its existing comment already
  describes the case it catches — "a zoom aimed at a previous load that crosses a
  reload in flight". Note (b) makes that retention *redundant* rather than more
  valuable; the branch is kept on cost and coverage grounds, not correctness.
- **`desktop/src/card-shim.test.ts`** — the existing `vm` harness gains the
  retention-branch coverage the shipped shim has never had.

### Data Flow

For one `ready` message arriving from this card's iframe:

1. `postCull(culledRef.current)` — unchanged, **first, before anything else**
   (2609.0002; `cull-qa.md` S36).
2. `readyActions(loadModeRef.current, msg.meta)` returns
   `{ declared, adopt, logMode, zoomPost }`.
3. If `zoomPost` is non-null, `postMessage(zoomPost, "*")` to the iframe.
4. If `logMode`, push one `zoom-mode declared=${declared} effective=${declared}`
   console entry — verbatim the string `HtmlCard.tsx:154` builds today.
5. If `adopt` is non-null, write it to `loadModeRef.current` **and** derive the
   `magnify` state from it (`setMagnify(adopt === "magnify")`).
6. The effect keyed on `props.lastChangedMs` resets `loadModeRef.current` to
   `null` alongside `setMagnify(false)` — the `?v=` reload path, unchanged.

On the four `ready` shapes (three genuine loads plus a forgery):

| load shape | `loadModeRef` at `ready` | logs a line | posts zoom |
|---|---|---|---|
| first open | `null` (fresh mount) | yes, if meta present | yes, if magnify |
| `?v=` reload (file rewrite / #101 refresh) | `null` (effect reset it) | yes, if meta present | yes, if magnify |
| **self-reload (#99)** | `"magnify"` (never reset) | **no** | **yes — the fix** |
| forged repeat `ready` | mode in force | **no** | yes iff magnify is in force |

### Interface Contract

```ts
// desktop/src/kit/zoomMode.ts
export interface CardZoomPost { tarmac: "zoom"; z: number }

export interface ReadyActions {
  /** This ready's own `declaredZoomMode(meta)`. The only value the console line
   *  may report — and inert whenever `logMode` is false. */
  declared: ZoomMode;
  /** The mode to adopt for this load, or null to keep the one already in force. */
  adopt: ZoomMode | null;
  /** Emit the once-per-load `zoom-mode declared=… effective=…` line. */
  logMode: boolean;
  /** The payload to post to the document, or null to post nothing. */
  zoomPost: CardZoomPost | null;
}

/**
 * @param inForce the mode already adopted for THIS document load, or null when
 *                no genuine ready has been honored yet.
 * @param meta    this ready's `<meta name="tarmac-zoom">` content (null = absent).
 */
export function readyActions(inForce: ZoomMode | null, meta: string | null): ReadyActions;
```

Required semantics:

- `declared` is **always** `declaredZoomMode(meta)` — this `ready`'s own reading,
  on a first and a repeat alike. It is the only value the console line may report,
  and on a repeat it is inert because `logMode` is `false`. (Pinned so two
  implementations that both satisfy S1–S7 cannot disagree about it.)
- `inForce === null` (first honored `ready` of a load): `adopt = declared`,
  `logMode = meta !== null`, `zoomPost = declared === "magnify" ? {tarmac:"zoom", z: MAGNIFY_K} : null`.
- `inForce !== null` (a repeat `ready`): `adopt = null`, `logMode = false`, and
  `zoomPost` is decided by **`inForce`**, not by `declared` —
  `inForce === "magnify" ? {tarmac:"zoom", z: MAGNIFY_K} : null`.
- `logMode` keys on `meta !== null`, not on `declared` — an empty (`""`) or
  malformed `content` is a *present* tag, so it logs, exactly as
  `HtmlCard.tsx:150` does today. Only an absent tag (`meta === null`) is silent.
- `z` is always the constant `MAGNIFY_K` imported from `kit/cardZoom.ts`. Never
  the board zoom (that is the settle-time shape frozen-K removed); `readyActions`
  takes no board zoom argument, so it has none to reach for.

Unchanged and out of bounds for this fix: the wire protocol, the daemon, the CLI,
`parseCardMessage` (`zoom` is still not a host-inbound kind — 2607.0006 S16),
`cardSrcUrl` / the `?v=` reload path, `MAGNIFY_K`'s value, `cullPayload`, and
`card_shim.js`'s source bytes.

### The `pendingZoom` decision: keep the branch, on a narrower argument than it first looks

**Keep it — but not because fix (b) makes it matter more. (b) makes the retention
path execute more often and its retained value redundant.** Stating that plainly
is the difference between a justified three lines and a flattered one.

Trace the one race that reaches the branch:

1. document A (generation N) posts `ready`;
2. A calls `location.reload()` before the host's listener runs;
3. the host posts zoom at `iframeRef.current.contentWindow`;
4. document B (generation N+1) has committed and its prepended shim has installed
   its listener, but has not reached `DOMContentLoaded` — so `ready === false`
   and the value is retained;
5. B's `postReady()` applies it.

**Today the branch is load-bearing.** B applies the retained zoom at `postReady()`,
and B's own `ready` is then discarded by the guard — so that retained value is the
only root zoom B will ever get. Delete it today and B renders at 1/K.

**Under (b) it is redundant.** With the branch: B applies the retained zoom, then
B's own `ready` draws a reply and B applies `K` again — same value, one hop
earlier. Without it: the crossing zoom is dropped, B's own `ready` draws the
reply, B applies `K`. **The end state is identical**, and the "without" timing is
just the normal path's timing. (b) fixes this race the same way it fixes the plain
self-reload — by answering B's own `ready` — so the branch is insurance, not the
mechanism.

The decision therefore rests on cost and on coverage, not on correctness:

- **Deleting it is not free.** `card_shim.js` is `include_str!`-embedded, so
  removing three lines forces a Rust rebuild and re-opens the 2607.0006 shim
  surface — real cost, for a behavioral change of nothing.
- **It stops being untested dead weight.** S8 exercises the retention path
  deterministically against the shipped bytes, so the branch becomes pinned
  rather than merely tolerated — which is what 2607.0006 S9's standing note was
  actually asking for.
- **It is what keeps the shim correct against a host that does *not* reply to
  every `ready`** — precisely the host this repo shipped until this fix.

The honest resolution of 2607.0006 S9 is a **scripted fixture, not a manual run**:
the app-level race is timing-dependent and cannot be forced by hand, which is why
S9 has been NOT VERIFIED since it was written. The `vm` harness in
`desktop/src/card-shim.test.ts` drives the same order deterministically against
the shipped bytes — `loadShim()` → `send({tarmac:"zoom", z:3})` → `domReady()` —
so the branch moves from *never exercised* to *exercised on every `make test`*.
Accordingly:

- 2607.0006 S9's manual repro is **retired** and its standing note **resolved** by
  a `**Correction (#99):**` paragraph in the pattern that file already uses. That
  paragraph must say the branch is kept **because removing it costs a shim edit
  for no correctness gain and because S8 now pins it** — *not* that (b) made the
  race it guards more important. Under (b) the retained value is redundant with
  the reply to the same document's own `ready`.
- `magnify-card-qa.md` S9 stops being a NOT VERIFIED retention hunt and becomes
  the user-visible self-reload render check (S11 below), which is what a human
  can actually observe.

## Alternatives Considered

### (a) Clear the per-load ref on every genuine `ready`

The issue's first shape. It answers every load with the same one-line change, and
it restores the second `zoom-mode` console line on a self-reload (mild
observability win). **Rejected:** the ref exists to make a forged repeat `ready`
inert (2607.0006 S17). Clearing it on `ready` means a card can post
`{tarmac:"ready", meta:"reveal"}` at its parent and flip the mode actually in
force out from under the console line — the strip then disagrees with the render,
which is precisely what S17 forbids — and can spam the host's 500-entry console
buffer with one line per forgery. (b) gives up strictly less: a forged repeat
re-asserts a constant the document already has.

### (c) Reset the per-load state from the iframe element's `load` event

Superficially the strongest option: a `load` event on the host's `<iframe>` fires
for a genuine navigation and cannot be forged by `postMessage`. **Rejected on one
prong, which is enough, so no event-ordering claim has to be adjudicated.** If the
shim's `ready` message is delivered before the element's `load` event, the reset
in `load` lands *after* the handler ran — leaving the guard open at rest, so every
forged `ready` from then on is honored and S17 is lost outright. *(The other order
is deliberately **not** counted against (c): a forged `ready` arriving ahead of
the genuine one is honored on every fresh mount today, because the ref starts
`false`. That is the status quo, not a regression (c) would introduce.)* (c) also
adds a second per-load reset channel that can disagree with the `lastChangedMs`
one.

### (d) Delete `pendingZoom` and post zoom pre-emptively on every load

Removes the branch instead of justifying it, and replaces the reply-to-`ready`
handshake with a guess about when the document is listening. The handshake exists
because a post issued before the new document commits lands on the outgoing
`about:blank` window and is dropped (2609.0002 P1 measured this for the cull
post). Rejected.

## Security Considerations

The iframe is untrusted (`sandbox="allow-scripts"`, opaque origin) and can post
anything at its parent. Fix (b) widens exactly one thing: a card that spams forged
`{tarmac:"ready"}` messages now causes the host to post one
`{tarmac:"zoom", z: MAGNIFY_K}` back per forgery. The bound is the card's own
message rate, the payload is a constant, the target is the forging document
itself, and the effect is re-applying a root zoom it already has. Under fix (a)
the same spam would instead flip the mode in force and flood the host's console
buffer — so (b) is the narrower surface, not merely an acceptable one.

`parseCardMessage` is unchanged, so `zoom` remains rejected as an inbound host
message kind (2607.0006 S16), and the shim's `e.source !== window.parent` guard is
untouched (S15).

### Happy path

**S1–S3 are guard scenarios.** They characterize behavior that already ships and
that this fix must not disturb; they fail today only because `readyActions` does
not exist yet, not because the behavior is wrong. S4 is the only happy-path
scenario whose *behavior* is new.

- **S1** [K] **(guard)** Given no mode in force (`inForce = null`) and a `ready` whose meta is
  `"magnify"`, when `readyActions` runs, then it adopts `"magnify"`, logs the mode
  line, and returns the zoom payload `{tarmac:"zoom", z: MAGNIFY_K}`.
- **S2** [K] **(guard)** Given no mode in force and a `ready` with **no** meta (`null`), when
  `readyActions` runs, then it adopts `"magnify"` (the default) and returns the
  zoom payload, but **does not** log a mode line — a meta-less document has never
  logged one and must not start. The boundary that separates "absent" from
  "present but useless": a `meta` of `""` or `"banana"` also adopts `"magnify"`,
  but **does** log (`logMode` keys on `meta !== null`, not on the resolved mode),
  which is what `HtmlCard.tsx:150` does today and what the shim's
  `el.content || ""` can actually deliver.
- **S3** [K] **(guard)** Given no mode in force and a `ready` declaring `"reveal"`, when
  `readyActions` runs, then it adopts `"reveal"`, logs the mode line, and returns
  **no** zoom payload.
- **S4** [K] **The fix.** Given `"magnify"` already in force for this load (the
  self-reload shape: same `src`, same `lastChangedMs`, ref never reset) and a
  second genuine `ready` carrying the same meta, when `readyActions` runs, then it
  returns the zoom payload `{tarmac:"zoom", z: MAGNIFY_K}` while adopting nothing
  and logging nothing. **Run the same assertion with `meta = null`** — the
  meta-less repeat is the commoner real case (agent-written cards rarely declare
  the tag, and `cull-qa.md` S36's own `s36probe.html` carries no
  `<meta name="tarmac-zoom">`), and it is the one place a `logMode` derived from
  `declared` rather than from `inForce`-vs-`meta` would look correct by accident.
- **S5** [K] Given any of the above, when the returned payload is non-null, then
  it equals `{tarmac:"zoom", z: MAGNIFY_K}` with `MAGNIFY_K` **imported from
  `kit/cardZoom.ts` by the test**, so any other value (`1`, `declared`-derived, a
  settled zoom) fails. **What this scenario does and does not kill, stated so it
  is not read as more than it is:** the board-zoom shape is structurally excluded
  at the kit level — `readyActions` has no zoom parameter — and a literal `3`
  typed into `zoomMode.ts` is *value-indistinguishable* from the import, so it is
  a DoD code-read, not a test. The glue-level shape (`HtmlCard` posting
  `getZoom()` instead of the returned `zoomPost`) is killed by S12 [Q].

### Edge cases

- **S6** [K] **S17 preserved.** Given `"magnify"` in force and a repeat `ready`
  forging `meta:"reveal"`, when `readyActions` runs, then `adopt` is `null`,
  `logMode` is `false`, and the payload is still the magnify one — the forgery
  changes neither the mode in force nor the console strip.
- **S7** [K] **The in-force invariant.** Given `"reveal"` in force and a repeat
  `ready` forging `meta:"magnify"`, when `readyActions` runs, then it returns
  **no** zoom payload, and `adopt` is `null` and `logMode` is `false` — a repeat
  decides from the mode in force, never from its own meta, so a forgery cannot
  inject root zoom `K` into a reveal card.
- **S8** [S] **`pendingZoom`, exercised at last.** Given the shipped shim loaded
  (`loadShim("magnify")`) and a host `{tarmac:"zoom", z: 3}` delivered from
  `window.parent` **before** `domReady()`, when `domReady()` then fires, then
  `h.style.zoom` is `3` and `h.posted` contains `{tarmac:"ready", meta:"magnify"}`.
  The negative control that makes it non-vacuous: before `domReady()`,
  `h.style.zoom` is still `undefined` — the zoom was retained, not applied on
  arrival. (Today's harness covers only the reverse order, in its S5
  precondition.)
- **S9** [S] **A post-ready zoom is applied every time, not only the first** —
  the premise fix (b) rests on. Given a ready shim that has already applied
  `{tarmac:"zoom", z: 3}`, when `{tarmac:"zoom", z: 4}` arrives from
  `window.parent`, then `h.style.zoom` is `4`; when `3` is then re-sent, it is `3`
  again, and `h.posted` gains no entry across either delivery (snapshot its length
  first — the `ready` from `domReady()` is already in the array). **Distinct
  values are what make this non-vacuous:** re-sending `3` and asserting `3` cannot
  distinguish "applied again" from "ignored" against a plain `style` object, and
  "does not throw" is guaranteed by the listener's own `try`/`catch` — neither is
  asserted here as if it were evidence. **This scenario does not — and cannot —
  establish that a repeat root zoom causes no relayout or re-wrap**: the `vm` harness's `style` is a plain
  object with no layout behind it. The render-level half is S14 [Q]
  ("wrap points stay frozen"), and that is the one that matters to a user.
- **S10** [S] Given a shim that has already applied a host zoom, when a second
  zoom arrives from a source other than `window.parent`, then it is ignored
  (`h.style.zoom` keeps its first value) — the `e.source` guard still holds after
  the repeat-post change. This is a **new automated counterpart** to 2607.0006
  S15, which is a `[QA]` scenario there with no automated half; it uses the
  fixture shape 2609.0002 S27 already established for `cull`.

### QA scenarios (manual)

- **S11** [Q] **The user-visible fix.** Given a **visible, unculled** magnify card
  — `magnify-probe.html` itself, so the report panel this scenario reads is
  present — opened at board zoom > 1×, when the document reloads itself
  (`location.reload()` run with the **card's iframe** selected as the console
  execution context, the same caveat `magnify-card-qa.md` S15/S17 carry), then it
  comes back rendered at the current board zoom, not at 1/K. **Visible is a
  premise, not an accident:** a culled card is `visibility:hidden` and cannot be
  double-clicked to borrow, so the console recipe is unavailable there — which is
  why the culled path needs a cull-triggered fixture (`cull-qa.md` S36's
  `s36probe.html`) and is covered separately, by S15. Decided by instruments, not
  by eye — record the probe's report line before the reload and after it:
  1. the received-zoom panel (it resets with the document) shows **at least one**
     `{tarmac:"zoom"}` entry with `z = 3` for the new generation; today it reads
     `(none received)`, and **zero is the only failure** — two entries is also a
     pass, because the crossing-reply race can deliver a retained zoom *and* the
     reply to the new document's own `ready` (see Trade-offs);
  2. **`ICB probe offsetWidth` is the numeric tell** — it is the layout viewport
     in the document's own units, so a landed root zoom `K` makes it the
     un-zoomed box width and a missing one makes it `K×` that. It must equal its
     pre-reload value, not triple;
  3. `prose line count` matches its pre-reload value (a `K×` wider viewport
     re-wraps).
  **Do not use `window.innerWidth` as the tell.** It tracks the iframe *element*,
  which the host sizes `frame × K` either way (2607.0006 Trade-offs: zoomed
  content cannot observe its own zoom), so it is identical under the bug and
  under the fix — it is the control, not the discriminator. `wrap-probe.html`'s
  character-offset signature is the optional cross-check.

  1 receives the zoom, reloads; generation 2 must receive one too. Same premise
  (visible card, same `src`, same `lastChangedMs`), no devtools required.

  — "changed HTML card reloads and comes back at board zoom", the item that
  already carries the not-1/K check — and **S20**, the first refresh of a
  never-changed card. Not S16, which asserts an unchanged card is *not* reloaded.)
- **S14** [Q] **S17, re-worded to what still discriminates.** Given a loaded
  magnify card, when its JS posts a forged second `{tarmac:"ready"}` at

  zoom does not change and wrap points stay frozen. **The received-zoom panel MAY gain a second `z = 3` entry — that is the
  accepted trade-off of this fix, not a failure.** The panel count is no longer
  the guard's tell; the console-line count is.

  under the bug and under the fix alike, so its device-px width is *identical*

  size: add a `width: 320px` box to the rebuilt fixture (the `magnify-probe.html`
  box B shape) and compare its device-px width before the self-reload and after,
  or failing that measure the rendered device-px width of a fixed-length
  monospace run in the reporter. Decide it the way `doc-refresh-qa.md` S17
  decided the same question — against the pre-reload capture and against the
  ≈1/3 figure a missing root zoom gives — not by eye. The cull post stays first,
  unconditional and idempotent.
  **Fixture caveat:** S36 was driven by `s36probe.html`, a *scratch* file under

  a default-magnify, meta-less document — which is exactly the S4 `meta = null`
  repeat shape, and why the new render assertion applies to it at all.
- **S16** [Q] **Reveal self-reload.** Given a card declaring
  `content="reveal"` at board zoom > 1×, when it reloads itself, then it comes
  back laid out at real screen px with no root zoom applied and no second
  `zoom-mode` line — the render-level counterpart of S7.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass — [K] and [S] with
> tests that would *fail if the behavior were wrong*, [Q] by writing the
> checklist items into the QA sheets so a human can execute them. A green suite
> that passes for the wrong reason does not satisfy this contract — `/verify`
> hunts for vacuous tests by asking, of each behavior, "what is the smallest
> change that breaks this, and would any test catch it?"

Constraints that are part of the contract, not suggestions:

- **The cull post stays first, unconditional and idempotent.** `postCull(culledRef.current)`
  runs before any verdict, on every `ready`. 2609.0002 §The gate, specified
  requires it; `cull-qa.md` S36 is the regression. **What (b) changes about this
  rule:** with no early return left in the handler, *ordering* it after the
  verdict would be a benign reorder — so "first" is now insurance against a
  re-introduced early return rather than load-bearing on its own. What S36 still
  catches, and what must not happen, is the post becoming **conditional** (M8).
- **`card_shim.js` gets no source change.** If you believe it needs one, stop and
  say why — a shim edit forces a Rust rebuild (`include_str!`) and re-opens the
  2607.0006 conformance surface.
- **`MAGNIFY_K` is frozen** and the zoom `z` is always that constant.
- **The `zoom-mode declared=…` console line stays once per load** (2607.0006 S17)
  and stays silent for a meta-less document.
- **`parseCardMessage`, `cardSrcUrl`, the `?v=` path, the protocol, the daemon
  and the CLI are unchanged.**
- **The per-load ref and the `magnify` state are written at the same two sites**
  (the `lastChangedMs` reset effect and the `ready` handler), so a message
  arriving before React re-renders reads the mode actually adopted. Prefer one
  ref (`ZoomMode | null`) over a boolean plus a mode ref.
- **The handler applies `readyActions`' verdict verbatim.** Post iff `zoomPost`
  is non-null (and post *that object*, unmodified); log iff `logMode`; adopt iff
  `adopt` is non-null. The handler must not branch on `msg.meta`, on a mode, or
  on "is this a repeat" anywhere else, and must not compute a `z` of its own.
  Every decision belongs to `readyActions` because that is the only side a test
  can reach — a decision re-made in the glue is a decision with no test, and the
  mutation table's [K] rows silently stop applying to it.
- **Namespace the scenario IDs you cite.** Both target files already cite IDs
  from other specs — `card-shim.test.ts` has 2609.0002's S8/S9/S10, and
  `zoomMode.test.ts` has 2607.0006's S1 — so a bare `it("S8: …")` would be
  ambiguous to a reader and to `/verify`. Group the new tests under a `describe`
  naming this spec, e.g.
  `describe("2609.0003 (#99) — pendingZoom and repeat zoom posts (S8–S10)")`
  with `it("S8: …")` inside, and the same for the `readyActions` block. Add this
  spec to `card-shim.test.ts`'s header comment, which currently reads
  "spec 2609.0002, scenarios S5-S28 and S40".
- **Smallest correct diff; no line-noise comments.** A comment earns its place
  only by explaining a non-obvious *why*. Match surrounding style; do **not**
  `cargo fmt`.
- Extend `desktop/src/card-shim.test.ts`'s existing `vm` harness — do not fork
  it, and do not copy the shim's text into the test.
- Write [K] tests as `describe`/`it` citing scenario IDs, node-env Vitest,

## Trade-offs and Limitations

- **S17's binary tell is spent.** A forged repeat `ready` now provokes a redundant
  `{tarmac:"zoom", z: 3}` post, so "the received-zoom panel gains no entry" stops
  discriminating. What the guard still guarantees — one `zoom-mode` line per load,
  a mode that cannot be flipped by a forgery, a render that cannot change — is
  what S14 asserts instead. This is the cost of (b), and it is stated here so a
  QA run does not file it as a bug.
- **A self-reload is still silent in the console strip.** (b) deliberately keeps
  the line once-per-load, so the user sees no evidence a reload happened. 2607.0006
  already records this as accepted ("not worth a second observability channel for
  a path agent-written cards do not normally take"); this fix makes the *render*
  correct without adding that channel.
- **A forged `ready` costs one redundant root-zoom write.** Bounded by the card's
  own message rate and confined to the forging document. See Security.
- **"Exactly one zoom entry per load" becomes one-or-two on a self-reload.** When
  the host's reply to generation N's `ready` lands on N+1's unready shim, N+1
  receives that retained zoom *and* the reply to its own `ready` — two entries,
  same `z`, same render. S11 therefore fails on **zero** entries, not on two.
  Every load that does not cross a reload in flight — which is every load S12,
  S13 and `magnify-card-qa.md` S18 stage — still shows exactly one.
- **2607.0006 S18's invariant is narrowed, though no checklist step becomes
  false.** S18 reads "the count is the assertion: one per *load*". Under (b) that
  is precisely "one per genuine `ready`" — identical for every step S18 and
  `magnify-card-qa.md` S18 actually prescribe (neither forges a `ready`), and
  different only in the forged case S14 now owns. Recorded so a `/verify` pass
  reading S18 literally does not file it as a contradiction; no Correction
  paragraph is needed there.
- **M8, M9 and the glue-shaped halves of M1–M5 have no automated kill.** The
  React shell is not unit-tested, so anything relocated out of `readyActions`
  leaves the [K] tier's reach: the cull post's placement, the ref/state pairing,
  and "the handler applies the verdict verbatim" are held by QA plus the DoD
  code-reads only. Keeping every decision inside `readyActions` is not a style
  preference here — it is what determines how much of this table is testable.
- **`pendingZoom` survives as insurance, not as a mechanism.** Under (b) the
  value it retains is redundant with the reply to the same document's own `ready`
  — identical end state, one hop apart. It is kept because deleting it costs a
  shim edit (`include_str!` rebuild, 2607.0006 conformance surface) for no
  correctness gain, and because S8 now pins it. Nobody has watched the app-level
  race happen, before or after this fix; S8 exercises the shim-level order
  deterministically, which is a strict improvement on "never exercised by any
  test", not a claim of field observation.
