# 2610.0002 Native wheel for HTML cards

**Date:** 2026-10-03
**Status:** implemented
**Author:** EP Lin
**Issue:** [#144](https://github.com/pingeplin/tarmac/issues/144) `perf(cards): HTML card scrolling is relayed per event, not native — and it feels it`
**Design doc:** [2610.0002](../../docs/designs/2610.0002_native_html_card_wheel.md) (approved 2026-10-03)
**Branch:** `perf/144-unified-card-scroll`

## Gate

**Approved 2026-10-03**, after two evaluator passes, as it stands: all 32
scenarios, including S29–S32 and the `content_origin` snapshot field that go
beyond the design's list. Implementation is in the session that wrote it.

## Context

An HTML card's document runs in a sandboxed `<iframe>` inside the card's
`WKWebView` (`HTMLCardView`). Under magnify — the default — the document is laid
out once at root zoom 3 (`CardZoom.magnifyK`) and shown scaled by `zoom/3`.

A transparent shield (`CardShieldView`) covers the document until the card is
borrowed. Today a wheel over the shield is *relayed*:
`HTMLCardView.relayWheel` → `CardZoom.wheelDelta` → `CardZoom.scrollDelta` →
`CardZoom.ScrollRelay` → `CardHostMessage.scroll` → host page `postMessage` →
`card_shim.js` → `window.scrollBy`. A borrowed card has no shield, so its wheel
reaches the web view directly and WebKit scrolls natively.

Measured on `main` @ `9174ca7` (design doc, *Problem*): 100 pt of trackpad
travel moves a shielded card 33 pt on screen at every zoom, and a borrowed card
`zoom/3 × 100` pt; a notched wheel moves a shielded card 3.3 pt a line; the
relay can only scroll the document's window, never a nested scroller.

Units, measured: a magnified document's scroll units are iframe pixels, so one
unit is `zoom/3` of a screen point. WebKit moves a document one unit per point
of a precise wheel delta, and 40 units per line of a notched one.

## Motivation

A markdown card and a board pan move 1:1 with the finger; an HTML card moves at
a third of it, and at yet another speed once borrowed. The fix the relay cannot
give — nested scrollers, one speed for both states — needs WebKit to take the
event itself.

## Proposed Solution

### Overview

The HTML card's web view becomes a `WKWebView` subclass that converts every
wheel event it is handed and passes it to WebKit. The shield hands it the raw
wheel; a borrowed card's wheel arrives there by itself. The conversion is a
`TarmacKit` value: it says what to write into the event, the view writes it.
The relay and everything only it used is deleted.

### Key Components

- **`CardZoom.wheelScale`** (`app/Sources/TarmacKit/CardZoom.swift`) — document
  units per screen point of wheel travel.
- **`CardWheel`** (new, `app/Sources/TarmacKit/CardWheel.swift`, with
  `app/Tests/TarmacKitTests/CardWheelTests.swift`) — one card's conversion and
  its per-axis residue. Built on `CardZoom.quantizeScrollDelta`, which stays.
- **`HTMLCardWebView`** (new, `app/Sources/TarmacApp/HTMLCardWebView.swift`) — a
  `WKWebView` subclass. Its `scrollWheel(with:)` reads the event's two delta
  fields, asks `CardWheel.convert`, writes the answer into a copy of the
  event's `CGEvent`, and calls `super` with the rebuilt event — or with the
  original when the answer is nil, the event has no `CGEvent`, or the copy or
  the rebuild fails. An event with no `CGEvent` is not put to `convert`, so it
  leaves the residue alone.
- **`CardWebView.make`** — takes the web view's class
  (`kind: View.Type = WKWebView.self`, generic over `View: WKWebView`, and
  returns a `View`), so only an HTML card gets the subclass, typed as it.
- **`HTMLCardView`** — builds an `HTMLCardWebView`, gives it
  `wheelScale = { CardZoom.wheelScale(zoom: host.zoom, magnify: session.mode == .magnify) }`,
  resets its residue in `loadDocument()`, and hands it the shield's wheel
  unchanged. `relayWheel` and the `wheel` relay property go.
  - The zoom is the live one, `ScreenSpaceHost.zoom`, as `relayWheel` reads
    today — not `settledZoom`: while a zoom settles the card's stretch carries
    the difference. The scale is read once per event.
  - A document that has not posted its first `ready` has no mode
    (`session.mode == nil`); that is not magnify, so its wheel passes
    unchanged.
  - The residue is reset by a document load — the first, a reload on a new
    mtime, a reload after the web process died — and by nothing else: not a
    gesture's start, a zoom change or a borrow.
- **`DevSnapshot`** — gains `content_origin`, so a tool outside the app can turn
  a card's `screen_rect` into a point on the display. `DevSnapshotReader`
  measures it: the content view's origin — its top-left, the view being
  flipped — taken to the screen and through `DevSnapshot.displayPoint`.
- **QA assets** (tracked): `qa/wheel-travel-probe.html`,
  `qa/wheel-travel-probe-reveal.html`, `qa/scroll-band-control.html`,
  `scripts/qa/wheel-gesture.swift`, `qa/native-wheel-qa.md`.

### Data Flow

1. A wheel event arrives. The wheel router (`AppController.routeScroll`,
   unchanged) leaves it for the card only over the body of the selected card.
2. Shielded: AppKit sends it to `CardShieldView.scrollWheel`, which calls
   `onScroll`; `HTMLCardView` calls `webView.scrollWheel(with: event)`.
   Borrowed: AppKit sends it to the web view.
3. `HTMLCardWebView.scrollWheel` reads the delta fields of the event's
   `CGEvent` — `scrollWheelEventPointDeltaAxis1/2` when the event's
   `hasPreciseScrollingDeltas`, else `scrollWheelEventFixedPtDeltaAxis1/2` —
   and calls `wheel.convert(dx:dy:precise:scale: wheelScale())`. Axis 1 is
   vertical: it is `dy`, and axis 2 is `dx`, each with the sign the field has.
4. `nil` → `super.scrollWheel(with: event)`. Otherwise the same two fields of a
   copy take the answer (`dy` into axis 1, `dx` into axis 2), and `super` gets
   `NSEvent(cgEvent:)` of the copy. No other field is touched: phase, momentum
   phase, location and window stay, and so do the delta fields that were not
   read. A momentum event is converted like any other.
5. WebKit scrolls what is under the pointer. At the document's limit nothing
   else moves: measured in the QA run (S30), WebKit keeps a wheel it does not
   use for an HTML card, and `BoardView.scrollWheel` — where one would arrive
   — does nothing (unchanged).

### Interface Contract

```swift
// TarmacKit — CardZoom.swift
extension CardZoom {
    /// Document units per screen point of wheel travel: `magnifyK / zoom`
    /// under magnify, 1 in reveal and for a zoom that is not finite and positive.
    public static func wheelScale(zoom: CGFloat, magnify: Bool) -> CGFloat
}

// TarmacKit — CardWheel.swift
/// One HTML card's wheel conversion: what to write into the event, or nil to
/// pass it unchanged. A precise delta is written to an integer event field, so
/// each axis's residue is kept for the next event.
public struct CardWheel: Equatable, Sendable {
    public enum Delta: Equatable, Sendable {
        case points(dx: Int, dy: Int)        // a precise device: whole document units
        case lines(dx: Double, dy: Double)   // a notched wheel: lines of the document
    }
    public init()
    /// `dx`, `dy` are the event's own delta fields, sign and all — points
    /// when `precise`, lines otherwise.
    public mutating func convert(dx: Double, dy: Double, precise: Bool, scale: CGFloat) -> Delta?
}

// TarmacKit — DevSnapshot.swift
extension DevSnapshot {
    /// A Cocoa screen point (bottom-left origin) as a global display point
    /// (top-left origin), given the primary screen's height.
    public static func displayPoint(cocoa: CGPoint, primaryScreenHeight: CGFloat) -> CGPoint
}
// DevSnapshot.Input gains `contentOrigin: CGPoint?`; the snapshot gains the
// top-level key "content_origin": {"x", "y"} or null.
```

`CardWheel.convert`, exactly:

| Input | Answer | Residue |
| --- | --- | --- |
| `scale` is 1, or not finite, or ≤ 0 | `nil` | unchanged |
| `precise`, any other scale | `.points`: each axis is `quantizeScrollDelta(delta × scale, carry)`'s step | each axis takes that call's carry |
| not `precise`, any other scale | `.lines(dx × scale, dy × scale)` | unchanged |

A `.points(dx: 0, dy: 0)` is an answer, not nil: the event is still passed on,
because its phase is content.

`quantizeScrollDelta` is unchanged. Its step is `roundedHalfUp` of
delta × scale + residue — a tie goes toward +∞, so −1.5 steps −1 and 0.5
steps 1 — and the new residue is what is left.

`content_origin` is where the origin of the window's content coordinates — the
ones `screen_rect` and `view_rect` are in — lies on the display, in global
top-left points, the coordinates `CGEvent` and `CGWindowListCopyWindowInfo`
use; `null` when there is no window. A point `(x, y)` of a `screen_rect` is at
`(content_origin.x + x, content_origin.y + y)` on the display. The primary
screen is `NSScreen.screens[0]`, the one whose origin is (0, 0) — not
`NSScreen.main`.

**Deleted**, with their tests: `CardHostMessage.scroll`; the shim's
`tarmac === "scroll"` branch; `HTMLCardView.relayWheel`; `CardZoom.scrollDelta`,
`CardZoom.wheelDelta`, `CardZoom.ScrollRelay`, `CardZoom.ScrollStep`.
`CardZoom.quantizeScrollDelta` and `CardZoom.Quantized` stay.

**Breaking-change rule.** A card document that listened for the host's
`{tarmac: "scroll"}` message stops hearing it; nothing in the tree does except
`qa/scroll-band-probe.html`, a closed record. `content_origin` is additive.

### QA assets

- `qa/wheel-travel-probe.html` — a dark, tall, wide document with one nested
  `overflow: auto` element (`#inner`). It paints, as text, its `scrollX`,
  `scrollY`, `innerHeight`, `scrollHeight`, `#inner`'s `scrollTop`, the last
  scroll target (`document` or `inner`) and its counts of `wheel` and
  `mousedown` events, and, since 2610.0003,
  `document.compatMode`. It has no white pixel.
  `qa/wheel-travel-probe-reveal.html` is the same with
  `<meta name="tarmac-zoom" content="reveal">`.
- `qa/scroll-band-control.html` — the same page scrolling itself by a
  fractional `scrollBy` on a timer: the positive control for the band check.
- `scripts/qa/wheel-gesture.swift` — posts one real gesture at a card:

  ```
  swift scripts/qa/wheel-gesture.swift <card id> [--dy <n>] [--dx <n>] [--events <n>] [--lines] [--select] [--no-end] [--at center|<x>,<y>]
  ```

  It reads `TARMAC_DEV_SOCKET`, takes the card's `screen_rect`, the zoom and
  `content_origin` from `tarmac dev snapshot` (the debug CLI,
  `core/target/debug/tarmac`, as `scripts/qa/lib.mjs` runs it), and aims at
  the middle of the card's body, or at `--at`: a point measured from the
  body's top-left, in screen points. The body is the `screen_rect` less a
  border of 1 × zoom on every side and a header of 30 × zoom under the top
  border (`CardBox.borderWidth`, `CardBox.headerHeight`) — the card lays both
  out on whole device pixels (`CardBox.screen`), so this is its body to within
  two of them; the aim on the display is `content_origin` plus that point. It
  exits 1 with a one-line message, having posted nothing and left the cursor
  alone, when `TARMAC_DEV_SOCKET` is unset, no app answers, the snapshot holds
  no such card (or no `screen_rect` or `content_origin` for it), the debug CLI
  is not built, or the top
  window at the aim does not belong to the process that owns the dev socket
  (its pid is `lsof -t` of the socket's absolute path, as the dev-channel
  skill reads it). Otherwise it warps the cursor there and posts at the HID
  tap:

  - with `--select`, one single left click first (click state 1: a double
    click would borrow the card). It then waits up to 1 s for the snapshot's
    `focused_card` to read the card; if it does not, it puts the cursor back
    and exits 1 with no wheel posted;
  - `--events` wheel events of (`--dx`, `--dy`). `--dy` is the event's axis 1
    and `--dx` its axis 2, whole numbers with the event's own sign: a negative
    `--dy` scrolls down (`scrollY` grows), a negative `--dx` scrolls right
    (`scrollX` grows). Precise events are points, marked continuous, a frame
    (16 ms) apart, with phase began on the first and changed on the rest, and
    are followed by one ended event of zero delta, which `--no-end` leaves
    out. With `--lines` they are line events, 120 ms apart, with no phase and
    no ended event.

  It puts the cursor back and prints what it posted as JSON: the card, the
  display point it aimed at, and the events.
  Defaults: `--dy -10 --dx 0 --events 10 --at center` (the body's middle).
- `qa/native-wheel-qa.md` — the `[Q]` and `[H]` scenarios below and S26 as a
  checklist, each `[Q]` with its knockout, and the record of the run.

## Alternatives Considered

Argued in the design doc: keep the relay and fix its factor; lift the shield
while selected; forward the event unconverted; convert in the shield; magnify
with `WKWebView.magnification`.

**A `tarmac dev wheel` verb instead of the poster.** It would put the `[Q]`
scenarios in `make qa`. It needs the dev protocol's Rust and Swift codecs and
their conformance vectors for a debug-only verb; the poster is one script. Left
for later.

## Security Considerations

- A shielded card's document now receives a DOM `wheel` event — cancelable,
  with pointer coordinates — for every wheel over its selected card. Accepted
  in the design; look-don't-touch is *no press, no key*. S22 pins that no press
  gets through, and S32 that a card that is not selected sees no wheel.
- The poster posts real input events and moves the cursor. It is a QA script,
  run by hand, and aims only at a window owned by the dev app it was pointed at.

## Acceptance Scenarios

Unit scenarios name their test home. `[Q]` scenarios run against a live
`make run` app with the probe open, driven by the poster, and read the numbers
the probe paints (by eye, or off a `screencapture`). Each `[Q]` names a
**knockout** — a one-line temporary change that must make it fail; run it,
record it in `qa/native-wheel-qa.md`, and revert the line, never the file.
S21 and S25 name none and say why. `[H]` scenarios need a hand on real
hardware and are recorded the same way.

"Units" are the probe's own numbers. Under magnify 1 unit = `zoom/3` pt on
screen, so 100 pt of wheel is `300/zoom` units; in reveal 1 unit = 1 pt.
"Grows by" compares the probe's reading before a gesture with its reading once
the gesture's scrolling has ended. A tolerance of 1 pt on screen is `3/zoom`
units, taken down to whole units.

**Setup, for every `[Q]`.**

- The probe is opened with the debug CLI against the dev daemon:
  `env -u TARMAC_TERM_ID TARMAC_SOCKET="$PWD/.dev/tarmacd.sock" core/target/debug/tarmac open "$PWD/qa/wheel-travel-probe.html"`
  (the reveal probe and the control page likewise). `TARMAC_TERM_ID` is unset
  as `scripts/qa/lib.mjs` unsets it: from a shell inside a Tarmac terminal the
  card would be attributed to that terminal, not put on the active board. A
  card's id is its file's canonical absolute path (`realpath`), as the
  snapshot's `cards[].id` shows.
- No verb pans. Pan by hand, once for each card posted at (the probe; the
  reveal probe for S12), until the middle of its body is near the middle of
  the board: `tarmac dev zoom` keeps the viewport's centre, so the body stays
  under the poster's aim, and inside the window, at every zoom.
- *Shielded* means selected and not borrowed: the snapshot's `focused_card`
  reads the probe's id and its `cards[].borrowed` reads false. The poster's
  `--select` gets there, but a press on a window that is not key selects
  nothing (`AppController.handlePress`), so bring the dev app forward first —
  `tarmac dev focus board` does — in the same command line as the poster. With
  nothing selected the wheel pans the board and the probe does not move.
- *Borrowed* is `tarmac dev focus <probe>` (`cards[].borrowed` true), and its
  gestures are posted without `--select`. To un-borrow, do as `make qa`'s D18
  does: `tarmac dev focus <term>`, then `tarmac dev key <term> escape` until
  `borrowed` reads false.
- A magnified document's scroll position does not change with the board zoom,
  so where the painted numbers are too small to read (zoom 0.25) read them at
  zoom 1 before the gesture and again after it.

### Happy Path

- **S1** (`CardZoomTests`) — `CardZoom.wheelScale(zoom:magnify:)`: `(0.5, true)`
  → 6; `(1, true)` → 3; `(2, true)` → 1.5; `(3, true)` → 1; `(1.728, true)` →
  `3 / 1.728` ± 1e-9; `(0.5, false)` and `(2, false)` → 1.
- **S2** (`CardWheelTests`) — each on a new `CardWheel`:
  `convert(dx: 0, dy: -10, precise: true, scale: 1.5)` → `.points(dx: 0, dy: -15)`;
  `convert(dx: 4, dy: 0, precise: true, scale: 3)` → `.points(dx: 12, dy: 0)`;
  both axes at once,
  `convert(dx: 4, dy: -10, precise: true, scale: 1.5)` → `.points(dx: 6, dy: -15)`;
  and at a scale that is no whole number,
  `convert(dx: 0, dy: -10, precise: true, scale: CardZoom.wheelScale(zoom: 1.728, magnify: true))`
  → `.points(dx: 0, dy: -17)` (−17.36).
- **S3** (`CardWheelTests`) — the carry holds travel: one `CardWheel`, thirty
  `convert(dx: 0, dy: -1, precise: true, scale: 1.5)` → the answers alternate
  `.points(dx: 0, dy: -1)` and `.points(dx: 0, dy: -2)`, the first being −1
  (the tie at −1.5 goes up), and the `dy`s sum to −45.
- **S4** (`CardWheelTests`) — a slow drag is not lost: one `CardWheel`, eight
  `convert(dx: 0, dy: 0.25, precise: true, scale: 1.5)` (0.375 a time) → every
  answer is `.points` with `dx` 0, and the `dy`s are 0, 1, 0, 1, 0, 0, 1, 0 —
  the first a zero step, the fourth the tie at 0.5 going up, the sum 3.
- **S5** (`CardWheelTests`) — notched:
  `convert(dx: 0, dy: -1, precise: false, scale: 1.5)` → `.lines(dx: 0, dy: -1.5)`;
  `convert(dx: 2, dy: 0, precise: false, scale: 3)` → `.lines(dx: 6, dy: 0)`.
- **S6** (`DevSnapshotTests`) —
  `DevSnapshot.displayPoint(cocoa: (730, 1218), primaryScreenHeight: 1440)` →
  `(730, 222)`, and `(-500, 1600)` → `(-500, -160)` (a screen above and left
  of the primary one: nothing is clamped); `build` with
  `contentOrigin: (730, 222)` carries `"content_origin": {"x": 730, "y": 222}`
  at the top level, and with `nil` carries `"content_origin": null`.
- **S7 [Q] travel, shielded.** Given the probe shielded at board zoom *z*, when
  the poster posts 10 events of `--dy -10`, then the probe's `scrollY` grows by
  `300/z` units, within 1 pt on screen: 1200 ± 12 at 0.25, 600 ± 6 at 0.5,
  300 ± 3 at 1, 174 ± 1 at 1.728 (173.6; the carry lands on 174), 150 ± 1 at 2,
  100 ± 1 at 3. *Knockout:* `wheelScale` returns 1 → 100 at every zoom: a fail

- **S8 [Q] travel, borrowed.** Given the probe borrowed at each zoom of S7,
  when the same gesture is posted, then `scrollY` grows by the amounts S7
  gives. *Knockout:* `HTMLCardWebView.scrollWheel` hands `super` the event it

- **S9 [Q] carry, through the wiring.** Given the probe shielded at zoom 2,

- **S10 [Q] notched.** Given the probe shielded, when the poster posts

  left as they were).
- **S11 [Q] across.** Given the probe shielded at zoom 2, when the poster posts

- **S12 [Q] reveal.** Given `wheel-travel-probe-reveal.html` shielded at zoom

  grows by 100 ± 1 units at both. *Knockout:* `wheelScale` ignores `magnify` →
  600 and 150.
- **S13 [Q] nested scroller.** Given the probe shielded at zoom 1 and the
  poster's aim over `#inner` — the probe scrolled, by the poster, until
  `#inner` is under the body's middle, or the aim moved with `--at` — when the
  poster posts 10 events of `--dy -10`, then the scroll target reads `inner`,
  `#inner`'s `scrollTop` grows by 100 ± 1 (its own CSS pixels, three units
  each) and `scrollY` does not change.
  *Knockout:* the copy's `location` is set to `.zero` before the event is

- **S31 [Q] the aim.** Given nothing selected (`tarmac dev focus board`), the
  probe at zoom 1, and the dev window placed so that a missing flip would
  show — unflipped, the aim is off by `|H − 2 × content_origin.y|` pt, *H* the

  height: a window near the display's top does it, one whose content starts
  near half the display's height does not — when the poster is run on the
  probe with `--select`, then it exits 0, the display point it prints lies
  inside the probe's body in a `screencapture` of the display (the capture is
  in pixels: points × the display's scale), and `focused_card` reads the
  probe's id.
  *Knockout:* `DevSnapshotReader` reports the origin without
  `displayPoint` → the aim is off by the flip: the poster refuses, or exits 1
  with the probe not selected.

### Edge Cases

- **S14** (`CardZoomTests`) — `wheelScale` is 1 for a zoom of 0, of −1, of
  `.nan` and of `.infinity`, with `magnify: true`.
- **S15** (`CardWheelTests`) — pass-through: `convert` returns `nil` for
  `scale` 1, 0, −2, `.nan` and `.infinity`, `precise` true and false; and a
  `nil` leaves each axis's residue as it was — after
  `convert(dx: 0.25, dy: -0.25, precise: true, scale: 1.5)` (→ `.points(0, 0)`,
  residues 0.375 and −0.375), `convert(dx: 1.25, dy: -1.25, precise: true, scale: 1)`
  → `nil`, then the first call again gives `.points(dx: 1, dy: -1)` (±0.75).
  The 1.25 is chosen so that a `nil` that had added to the residue (2.0 → 2),
  quantized into it (0.0 → 0) or cleared it (0.375 → 0) would each answer
  otherwise; the axes go opposite ways so that one's residue written to the
  other would too.
- **S16** (`CardWheelTests`) — a zero step is an answer:
  `convert(dx: 0, dy: 0.25, precise: true, scale: 1.5)` on a new `CardWheel` →
  `.points(dx: 0, dy: 0)`, not `nil`; and `convert(dx: 0, dy: 0, …)` likewise.
- **S17** (`CardWheelTests`) — the axes do not share residue: after
  `convert(dx: 0.25, dy: 0, precise: true, scale: 1.5)` (x: 0.375 → 0),
  `convert(dx: 0, dy: 0.25, …)` → `.points(dx: 0, dy: 0)`, and a third
  `convert(dx: 0.25, dy: 0, …)` → `.points(dx: 1, dy: 0)` (x: 0.75).
- **S18** (`CardWheelTests`) — a notched event neither reads nor writes the
  residue of either axis: after
  `convert(dx: 0.25, dy: -0.25, precise: true, scale: 1.5)`, a
  `convert(dx: 1, dy: -1, precise: false, scale: 1.5)` → `.lines(dx: 1.5, dy: -1.5)`,
  and the next precise `convert(dx: 0.25, dy: -0.25, …)` → `.points(dx: 1, dy: -1)`.
- **S19** (`CardWheelTests`) — two `CardWheel`s keep their own residue: after
  `convert(dx: 0, dy: 0.25, precise: true, scale: 1.5)` on one, the same call
  on a second, new one → `.points(dx: 0, dy: 0)`, and again on the first →
  `.points(dx: 0, dy: 1)`.
- **S20** (`CardWheelTests`) — no travel made or lost: for the `dy` sequence
  `[0.25, 0.25, -0.75, 2.5, -0.25, 0.25, 1.5, -3.75]` at scale 1.5 on one
  `CardWheel`, the steps are `[0, 1, -1, 3, 0, 0, 3, -6]`, and after each call
  `|Σ steps − 1.5 × Σ deltas| ≤ 0.5`. Every value is exact in binary.
- **S21 [Q] a cut gesture.** Given the probe shielded at zoom 2, when a
  gesture is posted with `--events 5` and its ended event dropped (the poster's
  `--no-end`; it moves `scrollY` by 75), and then a whole gesture of
  10 × `--dy -10`, then the second gesture moves `scrollY` by 150 ± 1 units.
  *Knockout:* none — a regression check on WebKit's gesture state, recorded
  with its observed value.
- **S29 [Q] a reload starts with no residue.** Given the probe shielded at
  zoom 2 and just loaded (its file given a new mtime — `touch` — and its
  `wheel` count reading 0 again), when the poster posts `--dy -3 --events 1`
  (−4.5 → a step of −4, residue −0.5), the file is touched again, and the same
  gesture is posted once the reload shows, then `scrollY` grows by 4 each
  time. *Knockout:* `loadDocument()` does not reset the residue → one of the
  two grows by 5 (−4.5 − 0.5 = −5).
- **S30 [Q] at its limit, the board stays.** Given the probe shielded at zoom
  1 and at its top (`scrollY` 0), when the poster posts 10 events of `--dy 10`
  (toward the top), then `scrollY` still reads 0 and the snapshot's
  `viewport.cx` and `viewport.cy` are what they were. *Knockout:*
  `BoardView.scrollWheel` pans by the event's travel. That fails the scenario
  only if WebKit hands the leftover up the responder chain, so the knockout
  run is a measurement: record `viewport.cy` before and after it. Measured in
  the QA run, it does not move: WebKit keeps the leftover, and the scenario
  stands as a regression check like S21.

### Error Scenarios

- **S22 [Q] the shield holds.** Given the probe shielded, after every gesture
  of S7, S9–S13 and S21 (S12 on the reveal probe, which paints the same
  counts), the probe's `mousedown` count is 0 — after one posted with
  `--select` too — and its `wheel` count has grown with the gesture.
  *Knockout:* `CardShieldView.hitTest` returns nil, so the shield lets the
  press through → the `mousedown` count is 1 after a gesture posted with
  `--select`.
- **S32 [Q] a card that is not selected sees no wheel.** Given the probe at
  zoom 1 with nothing selected (`tarmac dev focus board`; `focused_card`
  null), when the poster posts 10 events of `--dy -10` over it without
  `--select`, then the probe's `wheel` count and `scrollY` are what they were,
  and the board has panned: `viewport.cy` has grown by 100 ± 1. *Knockout:*
  `BoardWheel.route` gives `.card` over any card's body, selected or not → the
  `wheel` count grows, `scrollY` grows by 300 and `viewport.cy` does not move.
  The pass leaves the board panned: post `--dy 10` the same way to bring it
  back before any other scenario. This guards routing the change leaves alone
  (design, *Out of scope*): the knockout is a probe of it, not a change to it.
- **S23** (`CardShimTests`) — the relay is gone from the shim: a
  `{tarmac: 'scroll', dx: 4, dy: -9}` message from the host does not call
  `window.scrollBy` (the stand-in records no call), and a `cull` sent after it
  still pauses the card: a frame it then requests does not reach the native
  `requestAnimationFrame`.
- **S24** (`CardHostMessageTests`) — `CardHostMessage` has two cases, `zoom`
  and `cull`: a test switches over a message with exactly those two and no
  `default`, so a third case does not compile; their `json` is unchanged.
- **S25 [Q] no band.** Given the probe and `scroll-band-control.html` side by
  side at zoom 1.728, when the probe is scrolled for 30 s with reversals —
  once by precise gestures, once by `--lines` — then no white band shows at
  either edge of the probe while the control shows one. *Knockout:* none; the
  control banding in the same run is what makes a clean probe mean something.
- **S26** (`scripts/qa/wheel-gesture.swift`, by hand) — the poster refuses:
  with another app's window over the card it exits 1, names the reason and
  posts nothing (the cursor does not move); with `TARMAC_DEV_SOCKET` unset or
  no app listening, or no debug CLI built, it exits 1 with a one-line message; with a card id the
  snapshot does not hold it exits 1 and names the id. A run that posts exits
  0, leaves the cursor where it was, and prints JSON holding the card, the
  display point and one entry per event posted.

### By hand

- **S27 [H] a real trackpad.** Given the probe shielded at zoom 0.5 and 2, a
  two-finger flick scrolls it, the coast continues after the fingers lift at
  the speed it had, and it stops like a markdown card beside it. A flick cut
  short — the pointer moved off the card's body mid-coast, or `⌃` pressed
  mid-coast — leaves the next flick scrolling the probe as the first did.
  Record the observation; there is no number.
- **S28 [H] a real notched mouse**, where one is to hand: one slow notch moves
  the probe a row, 40 pt on screen — `120/zoom` units: 120 at zoom 1, 60 at
  zoom 2. Record the units observed: a hardware wheel's line deltas are
  accelerated and fractional (design, *Riskiest assumption*), so the figure is
  an observation, not a pass mark. If none is to hand, record that; S10 stands
  in.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

Implement however you work best; only the result is checked. This repo adds:

- **TDD is mandatory** (`docs/coding-style.md` §1): write each unit test first,
  introduce the symbol as a stub, and watch the assertion fail on the
  unmodified tree. Run one suite with
  `cd app && swift test --filter TarmacKitTests.CardWheelTests`.
- **The shell is wiring** (§1.2, §1.3 exception 2): `HTMLCardWebView`,
  `HTMLCardView`, `CardShieldView` and `DevSnapshotReader` hold no decision.
  What they owe is the `[Q]` record in `qa/native-wheel-qa.md` — per scenario:
  the build, the observed values, the knockout's observed values.
- **Tests that move.** The `ScrollRelay` cases of `CardZoomTests`
  (`testS14…`, `testS15…`, `testS11…`, `testEachRelayKeepsItsOwnCarry`,
  `testARealWheelNotchBecomesWholeDocumentPxAtZoom1728`) go, and S2–S4 and
  S15–S20 in `CardWheelTests` take their place. They cannot move as written:
  `convert` takes a delta and a scale where `step` took their product, is nil
  at scale 1, and answers a zero `.points` where `step` returned nil.
  `testS12StillPostsWhenOnlyOneAxisQuantizesToZero` goes (a zero step is no
  longer withheld); the `scrollDelta` and `wheelDelta` cases go;
  `testScrollCarriesWholePixelsPerAxis` goes;
  `testAScrollFromTheHostReachesScrollByWithItsOwnDeltas` is inverted into S23.
  The `quantizeScrollDelta` cases stay where they are.
- **Tests that pin the snapshot.** `DevSnapshotTests`'
  `testS1TheSnapshotCarriesExactlyTheDocumentedTopLevelKeys` and
  `testTheSnapshotSerialisesAsCompactJSON` hold the snapshot's whole key set
  and its bytes: both gain `content_origin` (`"content_origin":null` sorts
  between `cards` and `focused_card`), and the suite's `input()` factory gains
  the argument. `scripts/qa/smoke.mjs` reads the snapshot by key and checks no
  key set, so `make qa` is not touched.
- **Docs in the same change:** `docs/architecture.md` (the *Shield and borrow*
  bullet under HTML cards — the shim bullet names no wheel relay today and
  needs no change — and the driver's `snapshot` paragraph, which gains
  `content_origin`); the `CardZoom`, `CardHostMessage` ("a state or a delta"),
  `HTMLCardView`, `CardShieldView`, `DevSnapshot` and `card_shim.js` comments,
  and the `CardZoomTests` header, which names the relay;
  `.claude/skills/dev-channel/SKILL.md` (`content_origin`); the agent guide
  `core/crates/tarmac-cli/src/SKILL.md` — a selected card's document receives
  `wheel` events; a line at the top of `qa/scroll-band-qa.md` saying the relay
  it measured is gone. Flip the design doc's
  (`docs/designs/2610.0002_native_html_card_wheel.md`) banner to HISTORICAL
  and its status to implemented.
- **Do not `cargo fmt`.** No Rust code changes; the agent guide is embedded
  text, so `make core` and the CLI's tests must still pass. `skill.rs` tests
  that file: it may name no repo path (`core/`, `app/`, `docs/`, `scripts/`,
  `packaging/`, `.github/`, `.blueprint/`) nor the words `Doc status`, hold
  no link that is not `http`, and must keep `## Surfacing a file` and
  `tarmac-zoom`.
- **Dev-channel rules** (`.claude/skills/dev-channel/SKILL.md`): never kill by
  name; the poster moves the cursor for about half a second per call.

Write tests to these principles (the ones `/verify` scores against):

- **Behavioral over structural** — assert observable output, not internals.
- **Every test can fail** — no copy-pasted expected values, no tautologies.
- **Deterministic, isolated, readable** — no cross-test state, AAA structure.

## Trade-offs and Limitations

- A shielded document sees `wheel` events (design, *Trade-offs*).
- HTML cards scroll three times faster on a trackpad and twelve times per
  notch than today.
- A notched line is not carried: at a fractional scale WebKit lands it on a
  whole unit (69 of 69.4 at zoom 1.728).
- The `[Q]` scenarios are not in `make qa`: they move the cursor and need the
  dev window on top.
- The wheel path depends on `NSEvent(cgEvent:)` keeping an event's window and
  location (measured on macOS 26). If that breaks, the fallback is the relay
  with the corrected factor.

## Open Questions

The design's two unmeasured assumptions — a real trackpad's coast, a hardware
notched mouse — are S27 and S28. Three more notes, none blocking:

- **A coast, by the poster?** "A momentum event is converted like any other"
  has no `[Q]`: the poster posts no momentum phase, and the design's figure
  (327 units converted against 218) came from events built inside the spike
  app. S27 is its only check. Whether the HID tap carries a posted momentum
  phase is not measured.
- **S30's knockout — answered.** It assumed WebKit hands an unconsumed wheel
  up the responder chain to `BoardView`. Measured in the QA run: with
  `BoardView.scrollWheel` made to pan, a wheel at the document's limit still
  left the viewport where it was. WebKit keeps a wheel it does not use for an
  HTML card, so S30 is a regression check, like S21.
- **Wiring no tool here reaches.** Four clauses of *Key Components* have no
  scenario: the scale being read from the live zoom during the 0.15 s a zoom
  takes to settle (the poster cannot be timed into that window); a document
  that has not yet declared its mode (`session.mode` nil, before its first
  `ready`) counting as not magnify, so its wheel passes unchanged (a posted
  gesture cannot be timed into that window either); the pass-through of an
  event with no `CGEvent`; and of one whose copy or rebuild fails (a posted
  event has one, and both succeed). They are checked by reading the diff.
