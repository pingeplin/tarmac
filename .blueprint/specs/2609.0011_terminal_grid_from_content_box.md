# 2609.0011 Terminal grid measured from the content box

**Date:** 2026-09-08
**Status:** draft
**Author:** EP Lin
**Issue:** [#130](https://github.com/pingeplin/tarmac/issues/130) `fix(terminal): terminal card clips its last row — FitAddon measures a padding-inclusive box`
**Supersedes the premise of:** [2606.0015](2606.0015_terminal_card_bottom_padding.md) §Motivation (factually wrong — see Context)
**Related:** [2609.0007](2609.0007_term_host_padding.md) (padding is CSS-driven — this spec keeps it that way)

## Context

`@xterm/addon-fit` computes the grid from
`parseInt(getComputedStyle(term.element.parentElement).height)` and subtracts only the padding
of `term.element` (`.xterm`, which has none). The parent is `.term-host`, and under the
repo-wide `* { box-sizing: border-box }` that height **includes** the host's
`8px 10px 16px` padding — while the element that actually paints
(`.term-host .xterm { height: 100% }`) resolves to the *content* box, `24·rs` px shorter.

So rows are counted against a box `24·rs` px taller than the one the text lives in. The surplus
row is pushed below the visible area by the top padding and clipped by
`.card-body { overflow: hidden }`.

Measured in a browser harness that rebuilds the real card DOM with the repo's CSS and the real
`@xterm/xterm` + `addon-fit` + `addon-webgl`, under playwright `webkit-2336` (the WKWebView
family Tauri renders in) at dpr 2 and dpr 1 — 15k+ samples, raw data in `.dev/term-clip-2609/`
(main checkout only — see Trade-offs):

- **clip ⟺ `(H mod cellH) < (8 + 2)·rs`**, `H = rs·(card_h − 30)` — 294/294 exact match.
  The `+2` is a second defect: `termInnerBox()` subtracts the 30px header but not the two
  `1px·zoom` card borders, so the inner box overhangs `.card-body` by `2·zoom` px.
- **≈48% of card heights clip at every zoom level**, by up to `10 × zoom` screen px (half a row).
- **`padding-bottom` 0 / 16 / 40px clip identically** (61/126 heights, max 20px) — the 16px from
  #36 has exactly zero effect, because it sits *inside* the measured box.
- Fixing the measurement box alone leaves the bottom gutter floating between **14 and 35 screen
  px** at zoom 1 (the leftover sub-row height lands under the last row).
- Re-fitting on a rasterScale change moves the PTY grid: rows change in 41% of zoom events, and
  under the WebGL renderer the app loads, a 720px card's column ladder is 74→76→75→74→75
  (dpr 2) / 78→76→75→74→76 (dpr 1) — zooming the board SIGWINCHes the running shell.

## Motivation

The visible symptom is a half-cut line of terminal output on roughly half of all card sizes,
which reappears every time the board is zoomed. Two attempts have already failed because the
measurement was never the suspect: #36 added bottom padding (zero effect, proven above) and
2606.0015 recorded a false premise (`proposeDimensions()` "reads the parent element's **content**
height … cannot clip content") that will mislead the next reader until it is corrected.

The grid also has to stop moving under zoom: a board gesture must not resize the user's PTY.

## Proposed Solution

### Overview

Own the grid math in a pure module measured off the **content** box, stop calling
`FitAddon.fit()`, pin the grid across rasterScale changes (clamped to what fits), and let CSS
bottom-anchor the painted grid so the leftover sub-row height sits above the text instead of
under it. The `.term-host` padding stays declarative — no JS writes a padding value or a slack
custom property.

### Key Components

- **`desktop/src/kit/termGrid.ts`** (new, pure) — `proposeGrid()` and `clampGrid()`. All the
  arithmetic, no DOM: the caller passes measured numbers in and gets a grid out.
- **`desktop/src/cards/TerminalCard.tsx`** — reads the box off the DOM (`host.clientHeight`,
  `host.clientWidth`, the host's and `.xterm`'s computed padding, the scrollbar reserve, and
  `term.dimensions.css.cell`) and runs **one** measurement path — `proposeGrid()` → `nextGrid()`
  → `term.resize()` — from all three sites that call `fit.fit()` today (mount, `ResizeObserver`,
  rasterScale settle). It holds the rest grid in a ref and lets `nextGrid` decide whether to
  clamp or re-establish. `FitAddon` is dropped from the card.

  **A rasterScale commit resizes the host for real** (measured: `.term-host` 288 → 432 px at
  rs 1.5 — the raster wrapper goes `rs×100%` and the host is `inset: 0` inside it, a transformed
  wrapper being the containing block). So the `ResizeObserver` fires for *zooms as well as
  resizes* and cannot be the "this is a real layout change" signal — which is exactly what the
  pre-existing comment in that file assumed. The signal is the **card box** instead.
- **`desktop/src/theme/app-only.css`** — `.term-host` becomes a bottom-anchored flex column and
  `.term-host .xterm` takes its natural height, so the sub-row remainder lands above the first
  row. Padding declarations are unchanged.
- **`desktop/src/kit/termZoom.ts`** — `termInnerBox()` subtracts the header **and** the two
  card borders.

### Data Flow

1. A layout event fires (mount, card resize, or a settled rasterScale — the last two both arrive
   through the `ResizeObserver`, and the rasterScale one also through its layout effect).
2. The card reads the host's **padding** box (`clientHeight`/`clientWidth`), the padding sitting
   inside it, the cell metrics and the scrollbar reserve — `proposeGrid` derives the content
   box from those, so no caller has to.
3. `proposeGrid()` returns `{ cols, rows }`, or `null` when it cannot measure (non-finite or
   zero cell metrics, or an empty box) — the card then does nothing, preserving today's 0×0
   guard. On the mount path that means the PTY is spawned with xterm's current `cols`×`rows`
   (its 80×24 default), which is exactly what happens today when `fit()` early-returns.
4. `nextGrid(proposed, rest, cardBox(box, rs))` decides what to do with the proposal by
   comparing the **card box** — the measurement with the rasterScale divided out — against the
   one the rest grid was recorded at:
   - **different card box** → the card was resized: take the proposal; it becomes the new rest;
   - **same card box** (within a sub-pixel epsilon) → only the rasterScale moved: return
     `clampGrid(rest.grid, proposed)` and carry the rest grid forward untouched, so a zoom can
     shrink to what fits, a later zoom restores it, and no zoom ever takes it above the rest.
   Because the decision reads the measurement rather than the event, it is the same whichever
   observer fires, in either order, any number of times — the rasterScale layout effect and the
   `ResizeObserver` firing after it reach the identical answer, and `term.resize` on an
   unchanged grid is a no-op.
5. `term.resize(cols, rows)` is called with the resulting grid. xterm fires `onResize` **only
   when the grid actually changed** (`Terminal.resize` early-returns on an identical
   cols×rows), so an unchanged grid sends no `term_resize` and the shell sees no SIGWINCH —
   as today.
6. CSS paints `rows × cellH` flush to the bottom of the content box; the remainder is gutter
   above the first row.

### Interface Contract

```ts
// desktop/src/kit/termGrid.ts

/** Everything proposeGrid needs, in CSS px. Measured by the caller; no DOM here. */
export interface GridBox {
  /** .term-host padding-box height/width (host.clientHeight / .clientWidth). */
  boxH: number;
  boxW: number;
  /** Vertical / horizontal padding inside the box that the grid must not use
   *  (host padding + .xterm padding), already scaled by rasterScale. */
  padV: number;
  padH: number;
  /** Reserved scrollbar width; 0 when no scrollbar is shown. */
  scrollbar: number;
  /** Renderer cell metrics (term.dimensions.css.cell). */
  cellW: number;
  cellH: number;
}

export interface Grid {
  cols: number;
  rows: number;
}

/** The grid that fits the CONTENT box, or null when the box cannot be measured. */
export function proposeGrid(box: GridBox): Grid | null;

/** Per-axis minimum: keep the rest grid wherever it still fits. */
export function clampGrid(rest: Grid, proposed: Grid): Grid;

/** The card's own size, with the rasterScale divided out, so the same card compares
 *  equal whatever it is currently rasterised at. */
export interface CardBox { cardH: number; cardW: number }
export interface RestGrid extends CardBox { grid: Grid }
export function cardBox(box: GridBox, rasterScale: number): CardBox;

/** The grid to apply, and the rest grid to carry forward. Same card box → the
 *  rasterScale moved, so clamp and keep the rest; different card box → a real resize,
 *  so take the proposal and re-record it. */
export function nextGrid(
  proposed: Grid,
  rest: RestGrid | null,
  card: CardBox,
): { grid: Grid; rest: RestGrid };

/** xterm's own scrollbar-reserve rule, which the grid budget must keep honouring. */
export function scrollbarReserve(options: {
  scrollback?: number;
  scrollbar?: { showScrollbar?: boolean; width?: number };
}): number;
```

`proposeGrid` returns `null` unless **every** field is a finite number (no `NaN`, no
`Infinity`) *and* `boxH`, `boxW`, `cellW`, `cellH` are all `> 0`. That covers FitAddon's
zero-cell early-out, the card's existing empty-box guard, and FitAddon's
`isNaN(cols) || isNaN(rows)` guard in `fit()` — a `NaN` cell metric or a failed `parseFloat`
of a computed padding must never reach `term.resize()`, which throws on non-integers
(`_verifyIntegers`). `padV`, `padH` and `scrollbar` may be `0` but must be finite.

Otherwise:

```
cols = max(2, floor((boxW - padH - scrollbar) / cellW))
rows = max(1, floor((boxH - padV) / cellH))
```

The floors are xterm's own minimums (2 cols, 1 row — `Terminal.resize` clamps to them
internally) and are kept so a collapsed card still yields a usable PTY size.

## Acceptance Scenarios

Automated scenarios are Vitest unit tests next to the module, per the repo convention that pure
`kit/` logic is tested and the React/Tauri shell is not (`CLAUDE.md`). Card-level behaviour is
covered by the QA scenarios, which are run by hand in the app.

**Baseline `GridBox` for the scenarios below.** Every scenario names only the fields it
constrains; the unnamed fields take these values, which are the real card's at rasterScale 1
(`.term-host` padding `8px 10px 16px` → `padV` 24, `padH` 20; xterm's default scrollbar
reserve 14; the measured WebGL cell at dpr 2):

```ts
{ boxH: 400, boxW: 720, padV: 24, padH: 20, scrollbar: 14, cellW: 9.5, cellH: 21 }
```

### Happy path (automated)

- **S1:** Given `boxH` 290, `padV` 24 and `cellH` 21, when `proposeGrid` runs, then `rows` is
  **12**. The smallest break is measuring the padding box instead of the content box — today's
  behaviour, which answers `floor(290 / 21)` = **13**, and that 13th row is the clipped one.
- **S2:** Given `boxW` 720, `padH` 20 and `cellW` 9.5, when `proposeGrid` runs, then `cols` is
  **72** with `scrollbar` 14, and **73** with `scrollbar` 0. Today's padding-inclusive
  measurement answers `floor((720 − 14) / 9.5)` = **74**. The two scrollbar values must be
  asserted on the same box: an implementation that hard-codes the 14px reserve, or that
  forgets `padH`, still passes the single-value form.
- **S3:** Given `padV` 24 and `cellH` 21, when `proposeGrid` runs for **every integer `boxH`
  from 300 to 341** (two full cell periods), then for each one the proposed grid is the
  *largest* that fits the content box — both `rows × 21 ≤ boxH − 24` **and**
  `(rows + 1) × 21 > boxH − 24` hold. The upper bound alone is satisfied by a constant
  `rows = 1`, so both clauses are required; together they are the invariant that makes
  clipping impossible without restating the formula.

### Edge cases (automated)

- **S4:** Given `boxH` 318 — a content height (318 − 24 = 294) that is an exact multiple of the
  21px cell — when `proposeGrid` runs, then `rows` is **14** and `14 × 21 == 318 − 24` exactly,
  with no 15th row. Today's measurement answers `floor(318 / 21)` = **15**: the exact-multiple
  case is where the padding-inclusive box always over-counts by a whole row.
- **S5:** Given a box smaller than one cell but still non-empty (`boxH` 10, `boxW` 10, baseline
  padding and cell), when `proposeGrid` runs, then it returns a grid — not `null` — with `rows`
  **1** and `cols` **2**. Both raw quotients are negative here, so the minimums are what stop a
  collapsed card proposing a 0×0 or negative PTY.
- **S6:** Given a rest grid of 74×31 and a proposed grid of 74×30 (the measured ≥31-row /
  rs 2 case, where cellH drifts ~+1px per row and pinning alone re-clips), when `clampGrid`
  runs, then the result is **74×30** — the pin yields on the axis where it no longer fits.
- **S7:** Given a rest grid smaller than the proposed grid on both axes (e.g. rest 70×28,
  proposed 74×30), when `clampGrid` runs, then the result **equals** the rest grid by value
  (70×28) — a zoom never takes the PTY above the rest grid. Assert the values, not object
  identity: a correct implementation is free to return a fresh object.
- **S8:** Given a rest grid larger on one axis and smaller on the other (e.g. rest 80×28,
  proposed 74×30), when `clampGrid` runs, then the result is **74×28** — each axis
  independently takes the smaller value, so neither axis's rule can be applied to both.
- **S8a:** Given the zoom-out half of a round trip — rest 74×31 (recorded at rest), a zoom-in
  that clamped to 72×31, and now a proposal of 74×31 at the restored rasterScale — when
  `clampGrid(rest, proposed)` runs, then the result is **74×31**: the columns lost on the way in
  come back. Clamping against the grid the zoom *left behind* (72) instead of the rest grid
  would ratchet it down permanently; this is the scenario that catches that.

### The rest-grid rule (automated)

- **S13:** Given a rest grid recorded at a card box, when the same card box is measured again
  with a larger proposal (the rasterScale moved), then the result is clamped to the rest grid
  **and the rest grid is carried forward unchanged**. Also holds when the card box differs only
  by the sub-pixel error of dividing an integer `clientHeight` by a fractional rasterScale.
- **S14:** Given a rest grid, when a **different** card box is measured (the card was resized,
  including by a single pixel), then the proposal is taken as-is — even when it is larger — and
  becomes the new rest grid.
- **S15:** Given no rest grid yet (mount), when a grid is proposed, then it is taken as-is and
  recorded as the rest grid.
- **S16:** Given the same card measured at rasterScale 1 and at 1.5, when `cardBox` divides the
  scale out, then the two compare equal within the epsilon — and a genuinely bigger card at the
  same scale does not.
- **S17:** Given xterm's scrollbar options, when `scrollbarReserve` runs, then it is 14px by
  default, 0 with `scrollback: 0`, 0 with `showScrollbar: false`, and the configured `width`
  when one is set. (This is the number S2's whole column budget rests on.)

### Error scenarios (automated)

- **S9:** Given cell metrics that cannot be used — zero or `NaN`, **on either axis
  independently** — when `proposeGrid` runs, then it returns
  `null` and no resize is proposed. Each of these must be asserted **on its own**, or an
  implementation that guards one field passes for the wrong reason: `cellH` 0 with `cellW` 9.5;
  `cellW` 0 with `cellH` 21; `cellH` `NaN`; `cellW` `NaN`. The `NaN` cases are the ones that
  would otherwise reach `term.resize(NaN, …)` and throw.
- **S10:** Given a box that cannot be measured, when `proposeGrid` runs, then it returns `null`
  — the running program's PTY is never shrunk to 2×1. Assert each axis separately: `boxH` 0
  with `boxW` 720; `boxW` 0 with `boxH` 400; both 0 (the hidden-board `display:none` case, in
  which the cached cell metrics are still non-zero and would otherwise yield a real grid);
  `boxH` `Infinity` (an infinite box floors to `Infinity` rows, not to `null`, unless the
  finiteness check is real).
- **S10a:** Given a padding value that is not a usable number — `padV` `NaN` with every other
  field valid — when `proposeGrid` runs, then it returns `null`. A guard that checks only the
  box and cell fields lets `NaN` through `max(1, floor((boxH - NaN) / cellH))` into
  `term.resize(…, NaN)`, which throws: the crash the contract's "every field finite" rule
  exists to prevent. `padH` `NaN` behaves the same way.

### Layout contract (automated, CSS cross-checks)

- **S11:** Given `termInnerBox()`, when its height is read, then it is
  `calc(var(--card-h) - 32px)`; and when its width is read, then it is
  `calc(var(--card-w) - 2px)` — the same border omission on the horizontal axis, which today
  makes the side gutters asymmetric. The same test proves 32 is `30 + 2 × 1` by reading
  `desktop/src/theme/card.css` off disk and asserting both declarations it mirrors are still
  there: `.card-header { height: calc(30px * var(--zoom)) }` and
  `.card { border-width: calc(1px * var(--zoom)) }`. The inner box then measures the same box
  `.card-body` clips (`card-h − header − both borders`, `card-w − both borders`) instead of
  overhanging it by `2·zoom` on each axis. This replaces the existing `termZoom.test.ts`
  assertions that the height subtracts `CARD_HEADER_H_PX` alone and that the width is exactly
  `var(--card-w)`. The two subtracted pixels come from a named `CARD_BORDER_W_PX` beside
  `CARD_HEADER_H_PX` in `kit/cardChrome.ts`, not a literal `32`/`2`.
- **S12:** Given `desktop/src/theme/app-only.css` read off disk, when the terminal-host rules
  are asserted, then all three hold: (a) `.term-host` declares `display: flex`,
  `flex-direction: column` and `justify-content: flex-end`, so the grid is bottom-anchored;
  (b) no `height: 100%` declaration applies to `.term-host .xterm` any more — whether the rule
  is deleted or the declaration changed, the assertion is on the absence — so the painted
  element takes its natural `rows × cellH` height instead of stretching over the remainder;
  (c) `.term-host`'s padding declaration is still exactly
  `calc(8px * var(--rs, 1)) calc(10px * var(--rs, 1)) calc(16px * var(--rs, 1))` — 2609.0007's
  "padding is declarative" property, which nothing in this change may take over from JS.
  This is a declaration lock, not a behavioural test: the *visible* consequence (remainder
  above the first row, constant gutter below the last) is only observable in a real layout and
  is carried by Q2 and Q3.

### Card behaviour (manual QA — record in `desktop/qa/terminal-grid-qa.md`)

- **Q1:** With a terminal card filled with output, stepping the zoom 100% → 300% → 100% leaves
  the last row complete at every step, at several card heights.
- **Q2:** The gap under the last row looks the same at every zoom step (it scales with zoom, it
  does not jump between card sizes).
- **Q3:** Dragging the card's bottom edge through a full cell of height never leaves a half row.
- **Q4:** With `vim` (or `htop`) running, zooming the board does not reflow it on a Retina
  (dpr 2) display — the shell's column count is unchanged. On a 1× display the column count
  may **shrink** (see Trade-offs); a shrink is a pass, a grow or a clipped row is a fail.
- **Q5:** Selecting text with the mouse at zoom ≠ 1 still selects the cells under the cursor
  (the `getBoundingClientRect` override is unaffected).
- **Q6:** A CJK IME's candidate window still appears at the cursor.
- **Q7:** Scrollback still scrolls, and the scrollbar spans the **painted grid** — `.xterm` no
  longer fills the host, so the bar now starts below the top remainder and ends at the last row
  rather than covering the padded box. Pass = draggable, tracks the scrollback, no horizontal
  bar; a bar that overhangs the grid at either end is a fail.
- **Q8:** With a program running in a terminal card, switching to another board and back leaves
  the shell's cols×rows unchanged (the hidden board is `display:none`, so the card must measure
  nothing rather than propose 2×1 — the S10 path, wired).

## Alternatives Considered

### Move the padding onto `.xterm`

FitAddon subtracts `term.element`'s padding, so this also fixes the measurement (measured: 0
clipping). Rejected: `.xterm-viewport` and `.xterm-helpers` are positioned against `.xterm`'s
padding box, so the scrollbar moves flush to the card's rounded border and the IME anchor shifts
by `(10·rs, 8·rs)` — a CJK regression risk for no gain over owning the math.

### `.term-host { box-sizing: content-box }`

A one-line fix that also measures 0 clipping, because `getComputedStyle().height` then reports
the content box. Rejected: it carves an exception out of the global `border-box` rule, it relies
on the very engine behaviour that caused the bug, and it leaves the grid math unowned and
untestable.

### Snap the card height to whole rows on resize

The gutter would be constant, but only at rasterScale 1: `cellH(rs) ≠ rs·cellH(1)`, so the
remainder returns at every other zoom step. It also rewrites a size the user dragged, and
persists it. Rejected on both counts.

### Push the remainder into the top padding via a CSS custom property

Works (measured: gutter constant, 0 clipping, ±0.5px sub-pixel wobble at rs 1.5). Rejected in
favour of the pure-CSS bottom anchor, which needs no JS-supplied value and keeps 2609.0007's
"padding is declarative" property intact. Note the asymmetry: this candidate is measured and
the bottom anchor is not (Open Question 4). Keep it as the fallback if QA finds a problem with
`.xterm` taking its natural height.

## Trade-offs and Limitations

- **Some cards lose a row on upgrade.** The row that disappears is the one that was never
  visible; measured 86% of card heights lose 1 row and 14% lose 2. Every affected PTY gets one
  `term_resize` when the board is first opened after the change.
- **Zoom can still shrink the column count on a 1× display.** With the clamp, a Retina board is
  measured stable (0 column changes in 32 runs), but at dpr 1 the WebGL cell width grows enough
  with rasterScale that the pinned columns genuinely stop fitting (32/32 runs shrink, worst
  −5 columns). The grid never *grows*, and never clips — that is the honest guarantee.
- **A card resized while zoomed keeps that grid until it is resized again.** The rest grid is
  re-established by whatever measurement follows a card-box change, so resizing at rasterScale 2
  records the rs-2 grid; zooming back to 1× clamps against it rather than the slightly wider grid
  the card could then hold. It never clips, and the next resize at any scale re-establishes it.
  The ordinary round trip (zoom in, zoom out, no resize) is lossless — see S8a.
- **The HTML card keeps its `2·zoom` overhang.** `HtmlCard.tsx` sizes its iframe as
  `frame.h − CARD_HEADER_H_PX` and has exactly the same border omission. It clips no text and is
  left for its own issue; `CARD_BORDER_W_PX` is exported so that fix is a one-line change.
- **The gutter is stable but not identical across zoom steps.** It is exactly `16·rs` in layout
  px, which renders as `16·zoom` screen px — it scales with zoom, as all card chrome does.
- **The harness is not a repo test.** The numeric claims above were measured with a browser
  harness that is not part of `make test`. Because `.dev/` is gitignored it exists only in the
  **main checkout** (`~/workspace/tarmac/.dev/term-clip-2609/`), *not* in this worktree — read
  `FINDINGS.md` there for the derivations (C3 = the clip rule, C4 = the 2·zoom overhang) and
  the README to re-run it. No scenario in this spec depends on the harness being present.

## Open Questions

Each has a stated default, so none of them blocks the build. They differ in cost of a late
answer: **1 and 3 touch no scenario** — answer them whenever. **2 and 4 are already encoded in
scenarios** (S6…S8 and S12 respectively); reversing either rewrites those tests, so confirm
them before the tests are written, not after.

1. **RESOLVED — in scope.** S11 now fixes both axes. Original question: S11 fixes the vertical border omission, but
   `termInnerBox().width` is `var(--card-w)` with no border subtraction either — the host
   overhangs `.card-body` by the same `2·zoom` px horizontally. It clips no text (the 10·rs
   right padding absorbs it) but it makes the visible side gutters asymmetric, and the Context
   frames the missing border subtraction as "a second defect" without qualifying it to one
   axis. **Decision: fix `width` in the same change** — it is the same defect, the same two
   pixels, and leaving one axis wrong while fixing the other would need its own explanation.
2. **RESOLVED — no ratchet; clamp against the rest grid.** Clamping against whatever the last
   zoom left behind would permanently cost a 1× display its columns until the card was resized,
   which is a worse outcome than one extra `term_resize` on the way back out. `clampGrid` takes
   the **rest grid** — recorded only by mount and the `ResizeObserver`, never by a zoom — so a
   zoom-out restores exactly what a zoom-in gave up and nothing more (S8a). Residual case,
   accepted: resizing a card *while* zoomed records the rest grid at that rasterScale, so
   zooming back out keeps that (smaller) grid until the next resize.
3. **RESOLVED — terminal-only, but the constant is shared.** `kit/cardChrome.ts` gains
   `CARD_BORDER_W_PX = 1` next to `CARD_HEADER_H_PX` so the arithmetic is named where both
   cards can reach it; only `termInnerBox()` consumes it in this change. Original question:
   `CARD_HEADER_H_PX` has one other
   consumer — `desktop/src/cards/HtmlCard.tsx` sizes its iframe as `frame.h − CARD_HEADER_H_PX`
   — so the HTML card has the same `2·zoom` overhang. Add a shared card-border constant next to
   `CARD_HEADER_H_PX` and fix both, or keep this change terminal-only and leave HtmlCard for
   its own issue? **Decision: terminal-only** — HtmlCard's iframe overhang clips no text and
   changing it drags in the HTML-card QA surface for no gain here. It gets its own issue.
4. **RESOLVED — the bottom anchor is measured.** The harness gained the variant after the
   first review copy was taken: `.term-host { display:flex; flex-direction:column;
   justify-content:flex-end }` + `.term-host .xterm { height:auto }`, swept over 73 card
   heights × zoom 1/1.5/2/3 under the WebGL renderer. **Clipping 0/73 at every zoom and the
   bottom gutter is constant to 0.0px** (14 / 21 / 28 / 42 screen px at zoom 1 / 1.5 / 2 / 3 —
   i.e. `14·zoom`, the declared `16·rs` less the `2·rs` border overhang S11 removes). A live
   DOM probe at cardH 320 / zoom 1 shows the screen element sitting exactly 16px above the
   host's bottom edge, versus 30px (16 padding + 14 remainder) without it, and `.xterm`'s
   absolutely-positioned internals are unaffected. Data: `FINDINGS.md` §C9 and `gutter.json`
   in `.dev/term-clip-2609/`, `harness/probe.mjs` for the probe. The custom-property variant
   measured equally well (0.5px wobble at rs 1.5) and stays in Alternatives as the fallback if
   Q7 finds a scrollbar problem.
