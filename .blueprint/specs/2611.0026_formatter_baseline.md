# 2611.0026 Formatter baseline

**Date:** 2026-11-22
**Status:** accepted (spec-evaluator and advisor review, 2026-11-22)
**Author:** EP Lin
**Issues:** #462 (Rust), #463 (Swift), #464 (blame)

## Context

The repo has no formatter. `CLAUDE.md` and `docs/coding-style.md` §2 say layout is "match the surrounding file" and forbid `cargo fmt`, because rustfmt with default settings disagrees with almost every committed file. No tool checks layout, so a reviewer or an agent judges it by eye.

Measured on `main` at 62d1272:

| Formatter and settings | Files changed | Diff lines |
| --- | --- | --- |
| rustfmt, defaults (`max_width = 100`) | 101 of 105 | about 11,400 |
| rustfmt, `max_width = 120`, `use_small_heuristics = "Max"` | 80 of 105 | about 1,750 |
| swift-format, 4 spaces, `lineLength = 120` | 314 of 512 | about 6,900 |

The Rust tree writes wide one-line struct literals: 699 of 28,365 lines are longer than 100 characters and 180 are longer than 120. The Swift tree already indents by 4. Of its 68,301 lines, 429 are longer than 120 characters (82 of the 31,569 lines under `app/Sources`). With the settings in the second and third rows, all 936 Rust tests and all 2,677 Swift tests pass on the formatted trees.

## Motivation

A check that a deterministic tool can do must not stay a judgment call. Layout is the simplest such check. It is also the base for the lint, hook and mutation work that follows: each of those must start from a tree that the formatter accepts, or its first run changes most files a second time.

## Proposed Solution

### Overview

Format each language once, in a commit that holds only formatter output. After that commit, a check refuses a tree that the formatter would change. The check has one definition (`make fmt-check`), and CI calls it. The work lands as three PRs, one per issue, so that each reformat is in one squashed commit on `main` (see *Migration Steps* for the two terms).

### Key Components

- **`core/rustfmt.toml`** — `max_width = 120` and `use_small_heuristics = "Max"`. No other key.
- **`rust-toolchain.toml`** — pins the channel to the version in use today (`1.99.1`) with the `rustfmt` and `clippy` components, so that local runs and CI format the same way.
- **`.swift-format`** at the repo root (#463) — the toolchain's default configuration with `indentation.spaces = 4` and `lineLength = 120`. At the root, one file covers `app/` and `scripts/qa/*.swift`.
- **`scripts/check/report.mjs`** — the one place that words a failure. Every later check (lint, architecture rules, mutants) uses it.
- **`scripts/check/fmt.mjs`** — `node scripts/check/fmt.mjs --check [<language>]` or `--write [<language>]`. It works on the git repository that holds its current directory. It takes its file list from `git ls-files` and hands each file to the formatter by itself, on stdin, with the file's directory as the working directory (so the formatter finds the nearest configuration, and `rust-toolchain.toml` selects its version). So an untracked or ignored file (`app/Vendor/`, `target/`) is never reported or rewritten, and a tracked file is always checked, whatever a `mod` line or a build target says. `cargo fmt` is not used: it reaches files through `mod` and through each build target, so it can rewrite an untracked file, miss a tracked one, and list one file many times. Each language is one entry: its files, its formatter command, and how to install the formatter. #462 knows `rust` only; #463 adds `swift`.
- **`make fmt`**, **`make fmt-check`** — the entry points. Each one runs `fmt.mjs` once. `ONLY=rust` or `ONLY=swift` limits a run to one language.
- **`make test`** also runs the unit tests of `scripts/check/` (`node --test`).
- **`.github/workflows/lint.yml`** — one job per language (#462 adds the Rust job, #463 the Swift job). Each job prints the formatter's version, then runs `make fmt-check ONLY=<language>`.
- **`.git-blame-ignore-revs`** (#464) — the squashed commits of #462 and #463.

### How the Swift check works

The same way as Rust: `swift format format -` reads one file on stdin and writes the formatted text, and the check compares that text with the file. `swift format lint` is not used, because it also reports the lint rules, which belong to a later change.

### Interface Contract

```
make fmt                    # format every tracked file of every language
make fmt ONLY=rust          # one language
make fmt-check              # check every language
make fmt-check ONLY=rust    # one language
```

The exit codes belong to `fmt.mjs`:

```
fmt.mjs --check             # exit 0: nothing to do
                            # exit 1: at least one file is not formatted
                            # exit 2: the check could not run
fmt.mjs --write             # exit 0: every file is formatted now
                            # exit 2: the formatter could not run
```

`make` returns its own status: 0 when `fmt.mjs` exits 0, and 2 (GNU make's error status) when `fmt.mjs` exits 1 or 2. Through `make`, a caller can see only "zero" or "not zero".

A failure is written to stderr in this shape. The first line names the rule. `at` lines are repo-relative paths, sorted by byte order (the order of `LC_ALL=C sort`). `fix` is a command that can be pasted. `then` is the command that repeats the check.

```
✗ fmt: 2 files are not formatted
  at   app/Sources/TarmacKit/ChannelPaths.swift
       core/crates/tarmacd/src/watch.rs
  fix  make fmt
  then make fmt-check
```

When the check cannot run:

```
✗ fmt: cannot run rustfmt
  why  rustfmt is not on the PATH
  fix  rustup component add rustfmt
  then make fmt-check
```

When the formatter refuses a file (it does not parse, or the formatter itself fails), the `why` lines name each such file and the formatter's first error line, the `fix` line is the command that shows the whole error for the first one, and no file is reported as not formatted:

```
✗ fmt: cannot run rustfmt
  why  core/crates/tarmacd/src/watch.rs: error: this file contains an unclosed delimiter
  fix  see the whole error with: rustfmt --edition 2024 --check core/crates/tarmacd/src/watch.rs
  then make fmt-check
```

`report.mjs` exports one function that takes `{ rule, summary, at, why, fix, then }` and returns the text. `at` and `why` are optional; `fix` and `then` are required, and a call without them throws.

## Alternatives Considered

### rustfmt with default settings

It is the community standard and needs no configuration file. It was not chosen because it rewrites about 11,400 lines against about 1,750, and it breaks the one-line struct literals that the tree uses on purpose for test tables.

### `swift format lint --strict` as the Swift check

It is one command. It was not chosen because it also reports the lint rules, which are not part of this change, and a formatter check must not fail for a reason that `make fmt` cannot fix.

### A formatter per commit hook only, no CI job

A local hook can be skipped with `--no-verify`. CI cannot.

## Migration & Rollback

### Migration Steps

Two names are used below:

- **Reformat commit** — the commit on the PR branch that holds formatter output and nothing else.
- **Squashed commit** — the one commit on `main` that the squash-merge of the PR makes. It holds the reformat commit and every other commit of the PR.

1. #462: add the Rust configuration, the toolchain pin, the scripts, the Makefile targets and the CI job; then one reformat commit of `make fmt ONLY=rust` output; then the docs.
2. #463: add `.swift-format` and the Swift entry; then one reformat commit of `make fmt ONLY=swift` output; then the docs.
3. #464: after both merges, add `.git-blame-ignore-revs` with the two squashed SHAs.

Each reformat commit is generated by one command on a freshly fetched `origin/main`. If `main` moves before the merge, the commit is generated again; conflicts are not resolved by hand.

A branch that is open across a reformat is carried forward by its owner: run `make fmt` on the branch, commit, then merge `main`.

### Rollback Plan

Revert the squashed commit of the PR. Nothing is persisted and no data changes.

## Acceptance Scenarios

In S1–S3, S7, S10–S12, S14, S15 and S18–S22, `make fmt-check ONLY=<l>` means `node scripts/check/fmt.mjs --check <l>` and `make fmt ONLY=<l>` means `node scripts/check/fmt.mjs --write <l>`, run in the repository under test. The exit code in these scenarios is the exit code of `fmt.mjs` (see the Interface Contract).

### Happy Path

- **S1:** Given a tree in which every tracked Rust file is formatted, when `make fmt-check ONLY=rust` runs, then it exits 0 and writes nothing to stderr.
- **S2:** Given the same tree with one tracked Rust file changed so that the formatter would rewrite it, when `make fmt-check ONLY=rust` runs, then it exits 1, the first stderr line is `✗ fmt: 1 file is not formatted`, an `at` line holds that file's repo-relative path, and the output ends with `fix  make fmt` and `then make fmt-check`.
- **S3:** Given the tree of S2, when `make fmt ONLY=rust` runs and then `make fmt-check ONLY=rust` runs, then the check exits 0.
- **S4:** Given the PR branch before the merge, and a checkout of the parent of the Rust reformat commit (which already holds `core/rustfmt.toml`, `rust-toolchain.toml` and `scripts/check/`), when `make fmt ONLY=rust` runs there, then every tracked `.rs` file is byte-identical to the same file in the reformat commit, and the reformat commit changes no file that is not a tracked `.rs` file.
- **S5:** Given the formatted Rust tree, when `cargo test` runs in `core/`, then all tests pass, and the count is the same as before the reformat.
- **S6:** Given the formatted Rust tree, when `rustfmt --edition 2024 --check` runs on each tracked `.rs` file by itself, then every run exits 0. (A later per-file hook depends on this.)
- **S7 (#463):** S1, S2, S3, S4 and S14 hold for Swift with `ONLY=swift` and tracked `.swift` files. In S4, the parent of the Swift reformat commit holds `.swift-format`. In S14, the `PATH` has no `swift`, and the first stderr line is `✗ fmt: cannot run swift-format`.
- **S8 (#463):** Given the formatted Swift tree, when `swift test` runs in `app/`, then all tests pass, and the count is the same as before the reformat.
- **S9 (#464):** Given `.git-blame-ignore-revs` that lists the squashed commits of #462 and #463, and one `.rs` line and one `.swift` line that only the reformat changed and no later commit changed, when `git blame --ignore-revs-file .git-blame-ignore-revs` runs on each line, then neither line is attributed to a listed commit, and each is attributed to a commit older than the squashed commit of its language.
- **S21:** Given a tree with one unformatted tracked `.rs` file, when `make fmt ONLY=rust` runs, then it exits 0, writes nothing to stderr, and changes no untracked file and no file of another language.

### Edge Cases

- **S10:** Given an untracked `.rs` file that is not formatted, that sits in the same directory as tracked `.rs` files, and that no `mod` declaration names, when `make fmt-check ONLY=rust` runs, then it exits 0, and `make fmt ONLY=rust` leaves that file unchanged. An untracked file that a tracked `mod` names is skipped in the same way (Decision 5).
- **S11 (#463):** Given the formatted tree, the Swift check covers `app/Package.swift` and `scripts/qa/*.swift`: a layout change in either one makes `node scripts/check/fmt.mjs --check swift` exit 1 and name the file in an `at` line. A file under `app/Vendor/` is never named.
- **S12:** Given three files that are not formatted, when the report is written, then the summary says `3 files are not formatted` and the `at` lines are in byte order.
- **S13:** Given a pull request, when the lint workflow runs, then the log of each language job shows the formatter's version before the check. In the Rust job (#462), that version is the one of the toolchain that `rust-toolchain.toml` names. The Swift job is added by #463.
- **S18 (#463):** Given a tree with one unformatted tracked `.rs` file and one unformatted tracked `.swift` file, when `make fmt-check` runs with no `ONLY`, then it exits 1, the summary says `2 files are not formatted`, and both paths are in one `at` list in byte order.
- **S19:** Given a tree with one unformatted tracked file, when `make fmt-check ONLY=rust` runs (and, after #463, `ONLY=swift`), then after the run every tracked file has the same bytes and mtime as before, and `git status --porcelain` prints the same lines as before.
- **S22:** Given a repository with no tracked file of the language, when `make fmt-check ONLY=rust` runs, then it exits 0 and writes nothing to stderr.
- **S23:** Given a test under `scripts/check/` that fails, when `make test` runs, then it exits non-zero. (Check with a knockout: break one assertion, observe the failure, revert.)

### Error Scenarios

- **S14:** Given a `PATH` on which no `cargo` and no `rustfmt` can be found, when `make fmt-check ONLY=rust` runs, then it exits 2, the first stderr line is `✗ fmt: cannot run rustfmt`, stderr has a `why` line, a `fix` line and a `then make fmt-check` line, and no `at` line. The same `PATH` makes `make fmt ONLY=rust` exit 2 and change no file.
- **S15:** Given `ONLY=<a name that is not a language>`, when `make fmt-check` runs, then it exits 2, stderr names every language that the script knows (`rust` after #462; `rust` and `swift` after #463), and stderr has a `fix` line and a `then` line.
- **S16:** Given a call to the reporter with no `fix` or no `then`, when it runs, then it throws. (A failure with no next step must not be possible to write.)
- **S20:** Given a tracked `.rs` file that the formatter cannot parse (a syntax error), when `make fmt-check ONLY=rust` runs, then it exits 2, not 1, and stderr names that file in a `why` line. (Rule: a formatter check must not fail with exit 1 for a reason that `make fmt` cannot fix.) The Swift case follows Decision 8.

### Documents

- **S17:** After #462, no ACTIVE doc and no `CLAUDE.md` line says that `cargo fmt` must not be run (today: `CLAUDE.md` *Gotchas*, "Do NOT `cargo fmt`", and `docs/coding-style.md` §2), and `make docs-check` passes. After #463, no ACTIVE doc and no `CLAUDE.md` line says that formatting is by imitation or that the repo has no formatter (today: `CLAUDE.md` *Conventions*, "Formatting is convention-by-imitation", and `docs/coding-style.md` §2, "There is no formatter").

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

Implement however you work best. Only the result is checked. Notes that are specific to this repo:

- `scripts/` is on the closed TDD exception list (`docs/coding-style.md` §1.3, item 3), and the reformat is a behaviour-preserving change (item 5). Even so, `report.mjs` and the pure parts of `fmt.mjs` hold decisions, so write their tests first with `node --test`. Put the tests beside the scripts.
- S1–S3, S7 (except its S4 part), S10, S14, S15 and S18–S22 run the real script against a small temporary git repository that the test creates. Do not run a formatter over the real tree inside a test.
- S12 and S16 are unit tests of `report.mjs` and of the pure parts of `fmt.mjs`.
- S4 (and its Swift form in S7), S5, S6, S8, S9, S11, S13, S17 and S23 are checked by a command on the real tree or by the CI run. Record each one in the PR body: the command, the tree it ran on, the observed values.
- A scenario tagged (#463) or (#464) is owed by that PR only. A scenario with no tag is owed by #462 and must still hold after #463.
- The reformat commit holds formatter output and nothing else. Configuration, scripts and docs go in other commits of the same PR.
- Do not add `#[rustfmt::skip]` or change formatter settings after the reformat commit exists; decide both before it.
- Never run `tarmacd`, `tarmac`, `TarmacApp` or `make run` for this work.

## Definition of Done

Done is when `/verify` passes against this spec:

- [ ] Test suite is green (`make test`).
- [ ] Every acceptance scenario of the issue in hand maps to a test or to a recorded command with its observed values.
- [ ] No covered-but-vacuous scenarios.
- [ ] Tests meet the Desiderata bar.
- [ ] No implementation-quality blockers.
- [ ] The PR's own CI run is green, and its log shows the formatter version. A check that is red in CI on a tree that is clean locally is a version mismatch: stop, do not reformat to match CI.

## Trade-offs and Limitations

- The check starts the formatter once per file, in parallel. Measured: about 1 second for the Rust tree (105 files) and about 6 seconds for the Swift tree (516 files). A check of only the changed files, for a hook, is a later change.
- swift-format 6.4 corrupts the header of a Swift script that starts with `#!`: it joins the comment lines under that line onto it, one more on every run. The Swift entry leaves such a file alone (one tracked file today, `packaging/icon/build-dev-icon.swift`).
- `rust-toolchain.toml` is at the repo root, so it pins the compiler for every cargo command whose current directory is inside the repo: `make core`, `make test`, CI and the release build in `scripts/bundle.sh`. It names the version already in use (`rustc 1.99.1`, the local `stable` on 2026-11-22), so no build changes today; a toolchain update becomes an explicit commit.
- A branch open across a reformat must be carried forward. One draft PR is open today (#252) and touches three Swift files; it is affected by #463 only.
- `use_small_heuristics = "Max"` lets rustfmt keep a struct literal or call on one line up to the full width. This matches the tree, and it is denser than the rustfmt default.

## Decisions

These were open after the review. Each one is decided here; the scenarios above follow them.

1. **Blame and the squashed commit (#462, #464).** Accepted. The squashed commit of each reformat PR also holds new files and a few edits to lines that existed before (the `.PHONY` and `test:` lines of the `Makefile`, the doc sentences of S17, the toolchain step of `test.yml`). With the commit in `.git-blame-ignore-revs`, `git blame` attributes those few lines to their earlier commit. Lines that the commit adds are still attributed to it. The cost is about 20 lines; a separate PR per reformat costs a window in which the tree is formatted but unchecked.
2. **The pinned version (#462).** `1.99.1`: the output of `rustc --version` on the maintainer's machine on 2026-11-22, where the `stable` channel is the default. The pin file is at the repo root (see Trade-offs).
3. **Where the `scripts/check/` tests run in CI (#462).** A job in `lint.yml` runs `make check-test` (`node --test` over `scripts/check/*.test.mjs`). `make test` runs the same target locally.
4. **Release builds (#462).** They use the pin when `make bundle` runs with the repo as its current directory, which is how it is documented. rustup takes the toolchain from the current directory, not from `--manifest-path`, so a `make -C <repo> bundle` from elsewhere is covered too, and a direct call of `scripts/bundle.sh` from outside the repo is not.
5. **An untracked `.rs` file that a tracked `mod` names (#462).** The check skips it. Only tracked files are handed to the formatter, one at a time on stdin, and in that mode the formatter does not follow a `mod` line. So the rule "only tracked files" has no exception, for a check and for a write.
6. **Two languages, one cannot run (#463).** The check runs every language, prints every report, and exits 2 if any language could not run, else 1 if any file is not formatted.
7. **The `swift format` version (#463).** The Swift entry holds the accepted `major.minor` versions. Another version is a "cannot run" failure (exit 2) that names what it found and what is accepted, for a check and for a write. CI prints the version first (S13). Accepted today: `6.4` (6.4.4 formatted the tree) and `6.3` (the `macos-26` CI image has 6.3.0; a CI run with only `6.3` accepted passed `make fmt-check ONLY=swift` on the whole tree, so the two versions agree on every file). A version joins the list only on that evidence.
8. **A `.swift` file that cannot be parsed (#463).** Exit 2, the same as S20. Measured in #463: `swift format format -` exits 1 and writes `<path>:<line>:<column>: error: …` to stderr. The check reports it as "cannot run", and the `why` line holds that line from `error:` on.
