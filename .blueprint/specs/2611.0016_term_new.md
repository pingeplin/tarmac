# 2611.0016 `tarmac term new`: an agent opens another terminal card

**Date:** 2026-11-19
**Status:** accepted (2026-11-19) by the spec-evaluator and the Fable advisor, under the author's rule (approve when both find no problem; the advisor settles open decisions). The typeahead probe (*Typeahead probe record*) added D11.
**Author:** EP Lin
**Issue:** [#415](https://github.com/pingeplin/tarmac/issues/415)
**Branch:** `feat/415-term-new`
**Branch base:** `main` at `2b0eb03` (release 0.23.0). Conformance vectors V1–V37 are taken; this spec starts at V38.

## Gate

The author made these decisions on 2026-11-19. They bind this spec:

- **G1. The app mints the terminal.** The daemon does not spawn on its own. CLI → daemon `term_new` → daemon → app `term_new` (with a `req_id`) → the app makes the card, sends the existing `spawn_term`, then `input` → the app answers `term_new_ok` → the daemon answers the CLI.
- **G2. The command is typed into a login shell.** The app sends `spawn_term` with no `cmd` (the user's login shell) and then the command as `input`. It never uses `spawn_term.cmd`. So the shell stays after the command ends.
- **G3. No rate limit and no confirmation.** Any caller can open any number of cards.

The design does not settle the decisions below. The advisor accepted D1–D11 on 2026-11-19, with the changes to D3, D5, D7, D9 and D10 that the review asked for (see *Review record*):

- **D1. Verb shape.** `tarmac term new [--cwd DIR] "<command>"`. The command is one argument, one line.
- **D2. Command rule.** The character rules of `check_resume_cmd` (not blank, no control, no invisible format character), with its own limit: **4096** chars (`TERM_NEW_CMD_MAX`). An agent prompt in the command can be long; 256 is too short.
- **D3. Folder.** Default: the CLI process's own current directory. `--cwd DIR` overrides it; a relative `DIR` is taken from the CLI's directory. The CLI makes the path absolute and stats nothing, so no slow volume can hold it past its 5 s. When the CLI cannot read its own directory and has no absolute `--cwd`, it exits 1 (`cannot read the current directory`). The **daemon** checks the folder in its `term_new` arm, through the same gate as `spawn_cwd` (`daemon.gate().run(.., is_dir)`), before it forwards anything: a relative `cwd` gives `err "not an absolute path: <path>"`, and a path that is not a directory (or a gate read that fails or runs out) gives `err "not a directory: <path>"`. So an explicit folder never falls back to `$HOME` without a word.
- **D4. Board.** The calling terminal's board. With no `TARMAC_TERM_ID`, or with an id that is not filed under a board, the active board, with no owner (as `open` does).
- **D5. A board the app has not restored.** The app builds a board at its first visit in this app run (`didInitialRestore`). It spawns on a board only after that board's `restore` came on the current daemon connection (`spawnPending`, `restoredBoards`). So after an app relaunch, a background board is not built until its first visit. After a reconnect to the daemon, a built background board has no restore on the new connection until it is shown again. A `term_new` for a board that is not built, or not restored on this connection, is refused: `board <id> is not ready in the app; show it, then retry`. The words are true also for the short time after a daemon reconnect before the active board's restore comes; that window is accepted. Nothing is spawned. The two checks are separate: a stale `restore` for a board that is no longer active marks it restored on the connection but does not build it.
- **D6. Place, prime, keys, viewport.** The card goes to the first free ring slot around the owner card (`TermPlacement.newTerminalFrame(prime: ownerFrame ?? primeFrame, ...)`), at the boot size, raised to the top z. It does **not** become prime. Keyboard focus, the selection, the active board and the viewport do not change.
- **D7. Provenance edge.** The new card shows the same dashed edge as a doc card, from the owner terminal card's centre. The owner is held by the app for this run only. It is not persisted: after an app relaunch the card comes back as a plain terminal with no edge. A closed owner removes the edge; a dead owner card that stays on the board keeps it. **The card is not attached:** it does not move when its owner is dragged (`BoardView.beginCarry` carries only attached cards). Gravity that a relaunch drops, and that the user could not break by hand, is worse than none. A term tile persists no `loose` key (`LayoutTiles` writes `loose` for docs only), so a restore reads nothing wrong.
- **D8. Input bytes.** `cmd + "\r"`, sent with `typed: false` and `hold: true` (D11): it is not the user's key, so it does not drop a report or a resume record.
- **D9. Answer order.** The app sends `spawn_term`, then `input`, then `term_new_ok`, on its one connection. The daemon handles app frames in order and `spawn_term` is awaited inline, so the terminal is in the daemon's table before the CLI gets its id. The input is queued for the PTY writer, not yet written. When `term_new_ok` comes, the daemon checks that it holds the `term_id` (live, or in the exit ring). If it does not, the spawn failed (`spawn_failed` pushes only `err` to the app), and the CLI gets `err "the terminal did not start"`.
- **D11. The daemon holds the command until the shell takes keys.** A fresh PTY is in canonical mode until the shell's line editor starts (about 0.6 s with the author's `.zshrc`). A canonical line holds at most `MAX_CANON` = 1024 bytes on macOS, and the rest, the `\r` too, is dropped with no error (*Typeahead probe record*). So:
  - **Wire.** `input` gets one optional key, `hold: true`; omitted when false, so old frames keep their bytes. The app sets it only for the `term_new` command, also for a short one.
  - **Ready.** The terminal's writer holds those bytes until the master's termios (`MasterPty::get_termios`, `tcgetattr`) shows ICANON off. It polls briefly (for example every 20 ms) and takes the term-master `std::sync::Mutex` only for each read, never across a sleep or an `.await`.
  - **Order.** The hold is in the terminal's own input queue: bytes that come after the held input are written after it.
  - **Answer.** `term_new_ok` does not wait for the write. Exit 0 means the terminal runs and the command is typed when the shell takes keys.
  - **Deadline.** `HOLD_DEADLINE` (10 s, a seam a test sets short). If the tty is still canonical then, the bytes are written when they are at most `HOLD_CANON_SAFE` = 1000 bytes (the largest size the probe saw intact); else they are dropped, the daemon logs it and pushes the existing `err` notice to the app (`input held for <term_id> dropped: the shell did not take keys`). A cut line would stay at the prompt, and a Return from the user would run it, so a larger one is never written.
  - **End.** The hold ends when the terminal ends; nothing is written.
- **D10. Failure of the app.** The app answers `term_new_err {req_id, msg}`. The daemon gives the CLI a plain `err {msg}`. **The daemon bounds its own wait** below the CLI's 5 s `DAEMON_WAIT`: at `TERM_NEW_APP_WAIT` (4 s, a seam that a test sets short) it removes the entry and answers `err "the app did not answer"`. So the CLI's `no_answer_older()` line stays true: only a daemon that predates the verb leaves it unanswered. An answer that comes after the entry is gone is dropped. `GUIDE.md` names the hazard: after `the app did not answer`, the card can still open, so check `tarmac terms` before a retry.

## Context

A terminal card today is made only by the app: ⌘T (`spawnNewTerminal`, `app/Sources/TarmacApp/AppController+Terminals.swift`), a restore, or the replacement of the last live terminal. `spawn_term` is an app → daemon message (`docs/protocol.md` §"app → daemon"), the app mints its `term_id` (`BootTerminal.mint()`), places it (`TermPlacement`), and always sends `cmd: nil`.

A process in a terminal can surface a **doc** next to itself with `tarmac open`, and can watch other terminals with `tarmac terms`, `events` and `wait` (spec 2611.0012). It cannot open a **terminal**.

## Motivation

The author wants an agent to start a second agent session in its own card, so both co-working sessions are on the board side by side. With `wait --report done --term <id>` and `wait --exit <id>`, the first agent can then wait for the second. Today the only way is the dev-only driver (`tarmac dev key cmd+t`, `tarmac dev type`), which a release build refuses.

This keeps the no-harness rule: the card is a real process that a CLI call asked for. Tarmac does not know what the command is.

## Proposed Solution

### Overview

A new CLI verb sends one request to the daemon. The daemon gives it a `req_id`, adds the board, and forwards it to the app. The app does what ⌘T does, with a different anchor and an owner, then types the command. It answers with the new id, which the daemon passes back to the CLI. The CLI prints `{"term":"<id>"}`.

### Key Components

- **`tarmac-protocol`** — three new `Msg` variants (below), `TERM_NEW_CMD_MAX`, and `check_term_new_cmd` (the `check_resume_cmd` character rules with the 4096 limit; share the character checks, do not copy them). Its causes are `empty`, `a control character`, `an invisible format character` and `over 4096 characters`. Vectors V38–V43.
- **`tarmac-cli`** — a `term.rs` module for `tarmac term new`: parse, check the command, make the folder absolute (no stat, D3), send, print. `help.rs` and `GUIDE.md` get the verb (a section beside *Waiting on Tarmac's facts*, with an example of `term new` then `wait --report done --term`).
- **`tarmacd`** — `cli_session` gets a `TermNew` arm. The daemon keeps a map `req_id → oneshot::Sender<Result<String, String>>` (`src/state/`). It checks the command (`check_term_new_cmd`), refuses at once when no app is connected, checks the folder (D3), resolves the board (D4), forwards, and awaits the answer for at most `TERM_NEW_APP_WAIT` (D10). On `term_new_ok` it checks that it holds the `term_id` (D9). When the push to the app fails (`Daemon::push` returns false), the entry is removed and the CLI gets `no app connected`. The terminal's writer (`term.rs`, the `spawn_blocking` loop over `input_rx`) takes held input as D11 says. `dispatch_app_msg` gets `TermNewOk` and `TermNewErr` arms that complete the entry. An answer with a `req_id` that has no entry is ignored. Each entry belongs to the app connection it was pushed to. When that connection ends, also when a new app connection takes its place, each of its pending entries is completed with `Err("the app went away")`.
- **`TarmacKit`** — the Swift codec (`Message`, `MsgPack`) for the three variants. A pure decision, `TermNewPlan` (name free), that takes the request, the built boards, which boards are restored on this connection, the owner's frame and the prime frame, and returns *place (board, frame, owner?)* or *refuse (msg)*. `Provenance` gains the rule for which cards draw an edge, so a term card with an owner draws one (today `BoardView.recomputeEdges` filters on `.doc`).
- **`TarmacApp`** — wiring only: `handle(_ message:)` runs the plan, calls `addTerminal` with the frame and a `SpawnRequest(cwd:)`, sets the card's owner, sends `spawn_term`, `input`, `term_new_ok`, and persists the layout. The app sends `term_new_ok` only after it sent `spawn_term` for that card. `spawnPending` holds a spawn while the app is not connected, the view is not ready, or the board is not restored; when the spawn would be held, the app sends `term_new_err` and no card stays.

### Data Flow

1. The agent in terminal `t1` runs `tarmac term new "claude --model opus"`.
2. The CLI checks the command (D2), makes the folder absolute (D3), connects, and sends `term_new {cmd, cwd, term_id: "t1"}`.
3. The daemon checks the command, then that an app is connected (else `err "no app connected"`), then the folder, and finds `t1`'s board. It stores `req_id = n` and pushes `term_new {req_id: n, cmd, cwd, term_id: "t1", board_id}` to the app.
4. The app runs `TermNewPlan`. On refuse, it sends `term_new_err {req_id, msg}`.
5. On place, it adds the card (owner `t1`), sends `spawn_term {term_id: t9, cwd, board_id}`, `input {term_id: t9, bytes: "claude --model opus\r"}`, and `term_new_ok {req_id, term_id: t9}`.
6. The daemon spawns `t9` (inline), queues the bytes for `t9`'s PTY writer, checks that it holds `t9`, then completes entry `n`.
7. The daemon answers the CLI `term_new_ok {term_id: "t9"}`. The CLI prints `{"term":"t9"}` and exits 0.

### Interface Contract

CLI:

```
tarmac term new [--cwd DIR] "<command>"
  stdout: {"term":"<term_id>"}            (one JSON line)
  exit 0  the terminal runs and the command was queued to it
  exit 1  refused (also a folder that is not a directory), no daemon, no app,
          the app did not answer, the terminal did not start, no answer in 5 s
          (one line on stderr: "tarmac: <reason>")
  exit 2  usage: no command, more than one, a bad flag, or a command that fails D2
```

Wire (additive; unknown types are ignored by older peers):

```
cli → daemon   {t:"term_new", cmd, cwd, term_id?}
daemon → app   {t:"term_new", req_id, cmd, cwd, term_id?, board_id}
app → daemon   {t:"term_new_ok", req_id, term_id}
daemon → cli   {t:"term_new_ok", term_id}               (req_id omitted)
app → daemon   {t:"term_new_err", req_id, msg}
daemon → cli   {t:"err", msg}
```

| message | key | type | missing ⇒ |
|---|---|---|---|
| `term_new` | `cmd` | string | required |
| `term_new` | `cwd` | string | required (absolute) |
| `term_new` | `term_id` | string | no owner; active board |
| `term_new` | `req_id` | uint | absent on the cli leg |
| `term_new` | `board_id` | string | absent on the cli leg; the daemon always sets it to the app |
| `term_new_ok` | `req_id` | uint | absent on the cli leg |
| `term_new_ok` | `term_id` | string | required |
| `term_new_err` | `req_id`, `msg` | uint, string | required |
| `input` | `hold` | bool | false: written at once, as today; omitted when false (D11) |

Error lines (CLI stderr, after `tarmac: `):

| cause | line | exit |
|---|---|---|
| no app connected | `no app connected` | 1 |
| app went away mid-request | `the app went away` | 1 |
| app did not answer in `TERM_NEW_APP_WAIT` (D10) | `the app did not answer` | 1 |
| spawn failed (D9) | `the terminal did not start` | 1 |
| board not built, or not restored on this connection (D5) | `board <id> is not ready in the app; show it, then retry` | 1 |
| folder (daemon, D3) | `not a directory: <path>` / `not an absolute path: <path>` | 1 |
| CLI cannot read its directory (D3) | `cannot read the current directory` | 1 |
| command (D2) | `term new command refused: <cause>` (causes: see `check_term_new_cmd`) | 2 |
| no answer | `no_answer_older()` line (`daemon.rs`) | 1 |

Docs: `docs/protocol.md` (messages, the key table, the `input.hold` rule, vectors V38–V43) and `docs/architecture.md` (the `Msg` table) must name all three variants, or `make docs-check` fails.

## Alternatives Considered

### The daemon mints the id and spawns (option b)

The CLI would get an id with no app involved, and the app would adopt a terminal it did not plan, through the `restore.live_terms` path. Rejected by the author (G1): it breaks the rule that the app plans every spawn (`board_list` is not pushed on a spawn, protocol §M3), and placement and the grid size still need the app.

### `spawn_term.cmd` instead of input

The agent would be the PTY's child, so its exit ends the card. Rejected (G2): the author wants the shell to stay.

## Security Considerations

The caller can already run any command as the user; this verb only runs it in a visible card. The command is checked for control and invisible characters (D2), so a request cannot type extra lines or hide text in the card. There is no limit on how many cards (G3).

## Acceptance Scenarios

"Automated" names the suite. "QA" is a hand or `make qa` check against a live `make run` app; the TarmacApp shell has no unit tests by design.

### Happy Path

- **Daemon forwards term new to the app (automated: tarmacd integration with a fake app):** Given an app connection and a live terminal `t1` on `board-0`, when a CLI sends `term_new {cmd: "echo hi", cwd: "/tmp", term_id: "t1"}`, then the app connection gets `term_new {req_id, cmd: "echo hi", cwd: "/tmp", term_id: "t1", board_id: "board-0"}`.
- **App answer reaches the CLI and lists terminal (automated: tarmacd integration):** Given the setup of "Daemon forwards term new to the app", when the fake app sends `spawn_term {term_id: "t9", cwd: "/tmp", board_id: "board-0"}`, `input {term_id: "t9", bytes: "echo hi\r"}` and `term_new_ok {req_id, term_id: "t9"}`, then the CLI gets `term_new_ok {term_id: "t9"}` with no `req_id`, and a `terms_list` sent by another CLI right after lists `t9` on `board-0`.
- **Forwarded frame carries a background board id (automated: tarmacd integration):** Given `t1` on background board `board-1`, when a CLI sends `term_new` with `term_id: "t1"`, then the forwarded frame carries `board_id: "board-1"`.
- **CLI sends term new and prints terminal id (automated: cli):** Given the CLI runs in `/w/api` with `TARMAC_TERM_ID=t1`, when `tarmac term new "claude"` runs against a test daemon that answers `term_new_ok {term_id: "t9"}`, then the frame sent is `term_new {cmd: "claude", cwd: "/w/api", term_id: "t1"}`, stdout is exactly `{"term":"t9"}\n`, and the exit is 0.
- **CLI cwd flag resolves relative and absolute paths (automated: cli):** Given the CLI runs in `/w`, when `tarmac term new --cwd api "x"` runs, then `cwd` is `/w/api`; with `--cwd /abs/dir`, `cwd` is `/abs/dir`.
- **Plan places card beside owner on restored board (automated: TarmacKit):** Given a request whose owner `t1` is on built, restored board `board-0` with frame F, when the plan runs, then it places the card on `board-0` at `TermPlacement.newTerminalFrame(prime: F, existing:)` with owner `t1`.
- **Plan without an owner anchors on prime card (automated: TarmacKit):** Given a request with no `term_id` (or one that names no card on the board), when the plan runs, then the frame is anchored on the prime card (or the boot frame with no prime) and there is no owner.
- **Edge joins owner card to new card (automated: TarmacKit):** Given a term card with owner `t1` and the card `t1` on the board, when the edges are computed, then one edge goes from `t1`'s centre to the new card's centre; with `t1` gone, there is none. Doc edges are unchanged.
- **New terminal card appears beside its owner (QA):** Given the dev app with a terminal `t1`, when `t1` runs `tarmac term new "echo child-ok"`, then a new card shows beside `t1` with a dashed edge, its shell prints `child-ok`, and its prompt comes back (the shell stays). Prime, keyboard focus, the active board and the viewport do not change.
- **Wait exit prints code of new terminal (QA):** Given the setup of "New terminal card appears beside its owner", when `t1` runs `tarmac wait --exit <id> --timeout 60000` and the user types `exit` in the new card, then the wait prints `{"code":0}`.

### Edge Cases

- **Request without an owner uses the active board (automated: tarmacd integration):** Given no `term_id` in the CLI frame (or one that is not filed under a board), when the daemon forwards it, then `board_id` is the active board and `term_id` is absent.
- **Plan refuses a board not ready in app (automated: TarmacKit):** Given the owner's board is built but not restored on this connection (D5), when the plan runs, then it refuses with `board <id> is not ready in the app; show it, then retry`. The same refusal comes for a board that is restored on this connection but not built, and for a board that is neither.
- **Answer for a closed CLI is dropped (automated: tarmacd integration):** Given a pending request whose CLI has closed its connection, when the app answers `term_new_ok`, then the daemon drops the answer and goes on serving (a later `terms_list` answers).
- **Command input is command plus carriage return (automated: TarmacKit or Swift codec):** The input bytes for command `c` are `c` + `"\r"` as UTF-8, and the input is not typed (D8).
- **New card returns as plain terminal after relaunch (QA):** Given the setup of "New terminal card appears beside its owner", when the app is relaunched, then the new card comes back as a plain terminal with no edge (D7).
- **Concurrent requests each get their own answer (automated: tarmacd integration):** Given an app connection, when two CLIs each send `term_new` before the app answers, then the two forwarded frames carry different `req_id`s, and when the fake app answers them in the reverse order with `t9` and `t10`, each CLI gets the `term_id` of its own request.
- **Answer with no pending request is ignored (automated: tarmacd integration):** Given no pending request, when the app sends `term_new_ok {req_id: 99, term_id: "t9"}` or `term_new_err {req_id: 99, msg}`, then the daemon ignores it and goes on serving (a later `terms_list` answers).
- **Very long command runs whole in new terminal (QA):** Given the dev app with a terminal `t1`, when `t1` runs `tarmac term new` with a command of 4096 chars (`echo ` and 4091 `x`), then the new card's shell runs it and prints the 4091 `x` characters. The same with `echo ` and 4091 `中` (about 12 KB). (D11 against the author's real `.zshrc`.)
- **Held input waits for non-canonical child (automated: tarmacd integration, PTY child given by `cmd`):** Given a child that turns ICANON off after a delay (for example `sh -c 'sleep 0.3; stty -icanon; head -c 4097 > out'`), when the app sends a 4096-byte `input` with `hold: true` and `\r`, then the child gets all 4097 bytes.
- **Later input queues behind held input (automated: tarmacd integration):** Given a held input on a child that is still canonical, when the app sends a second `input` with no `hold`, then the child gets the held bytes first and the second after.
- **Held input deadline sends small and refuses large (automated: tarmacd integration, short `HOLD_DEADLINE`):** Given a child that never turns ICANON off, when the app sends a held input of at most 1000 bytes, then the child gets it at the deadline; with a held input of more than 1000 bytes, the child gets nothing and the app gets one `err` notice.
- **Unheld input reaches canonical child at once (automated: tarmacd integration):** Given a canonical child, when the app sends an `input` with no `hold`, then the child gets it at once, as today (no regression).

### Error Scenarios

- **No app connected refuses term new (automated: tarmacd integration):** Given no app connected, when a CLI sends `term_new`, then it gets `err {msg: "no app connected"}` and nothing is spawned. The app check comes before the folder check, so a bad or relative `cwd` also gets `no app connected`, at once.
- **App disconnect fails the pending request (automated: tarmacd integration):** Given a pending request, when the app connection closes, then the CLI gets `err {msg: "the app went away"}`. The same is true when a second app connection takes the place of the first while the request is pending.
- **App error is relayed to the CLI (automated: tarmacd integration):** Given a pending request, when the app sends `term_new_err {req_id, msg: "m"}`, then the CLI gets `err {msg: "m"}`.
- **Invalid command is refused by CLI and daemon (automated: protocol + cli):** `check_term_new_cmd` refuses `""`, `"   "`, a command with `\n`, `\r`, `\u{1b}`, U+2028 or U+200B, and one of 4097 chars; it takes one of exactly 4096. The CLI then exits 2 with `tarmac: term new command refused: <cause>` and connects to nothing; the daemon answers a raw frame with such a command `err {msg: "term new command refused: <cause>"}` and forwards nothing.
- **Bad cwd path is refused (automated: tarmacd integration):** Given an app connection, when a CLI sends `term_new` with a `cwd` that names a file or a missing path, then it gets `err {msg: "not a directory: <path>"}` and the app gets nothing; with a relative `cwd`, `err {msg: "not an absolute path: <path>"}`.
- **Wrong CLI usage exits with usage line (automated: cli):** Given no command, two commands, or an unknown flag, then the exit is 2 with the usage line.
- **Silent daemon makes the CLI time out (automated: cli):** Given a daemon that never answers `term_new`, then the CLI exits 1 within about 5 s with the `no_answer_older()` line.
- **Answer without spawned terminal reports failed start (automated: tarmacd integration):** Given a pending request, when the fake app sends `term_new_ok {req_id, term_id: "t9"}` with no `spawn_term` for `t9` before it (as after a failed spawn), then the CLI gets `err {msg: "the terminal did not start"}`.
- **Silent app makes daemon answer at its bound (automated: tarmacd integration, short `TERM_NEW_APP_WAIT`):** Given an app connection that never answers, when a CLI sends `term_new`, then the CLI gets `err {msg: "the app did not answer"}` at the daemon's bound, and an answer the app sends after that is dropped (a later `terms_list` answers).
- **Removed current directory stops the CLI (automated: cli):** Given the CLI's own directory was removed and no `--cwd` is given (or a relative one), then the CLI exits 1 with `tarmac: cannot read the current directory` and connects to nothing.
- **Owned term card is not attached to owner (automated: TarmacKit):** Given a planned term card with an owner, then it is not attached: the cards that its owner's drag carries do not include it (D7).
- **Conformance vectors match in both codecs (automated: both codecs):** Vectors V38 (`term_new`, cli leg), V39 (`term_new`, app leg), V40 (`term_new_ok`, app leg, with `req_id`), V41 (`term_new_ok`, cli leg, no `req_id`), V42 (`term_new_err`), V43 (`input` with `hold: true`) decode and encode byte for byte in Rust and Swift; the Swift encoder matches Rust's (`RustEncoderParityTests`).

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

Implement however you work best. Only the result is checked. Project rules that apply:

- **TDD is mandatory** (`CLAUDE.md`, `docs/coding-style.md`): watch each new test fail on the unmodified tree first.
- **Both codecs in the same change.** Rust encodes with `rmp_serde::to_vec_named`. Add V38–V43 to `core/crates/tarmac-protocol/src/tests.rs`, `app/Tests/TarmacKitTests/ConformanceTests.swift`, and `docs/protocol.md`.
- **Lock discipline.** No `std::sync::Mutex` across `.await`. Do not hold the pending map's lock while you await the app's answer or push to the app.

## Trade-offs and Limitations

- **The hold trusts ICANON.** A start-up file that reads a key in raw mode also turns ICANON off and can take the command. This is no worse than without the hold. A shell with no line editor never turns ICANON off: it gets a command of at most 1000 bytes at the deadline, and none larger.
- **No newline in the command** (D2). A long brief goes by file: `tarmac term new 'claude "$(cat brief.md)"'`. `GUIDE.md` shows this.
- **The edge is lost on an app relaunch** (D7). Persisting it would need an owner key in the layout tile and a move through `spawn_term.succeeds`.
- **A background board that was not shown since the app started cannot get a card** (D5). The caller must show it once.
- **No limit on cards** (G3). A looping agent can fill a board.
