# 2611.0004 A sample log of memory use and pending card events

**Date:** 2026-11-12
**Status:** accepted
**Author:** EP Lin
**Issue:** #329

## Context

Nothing records the memory use of the app, the daemon or the web content
processes. `tarmacd.log` holds the daemon's own lines; the app writes to
stderr only, and an app started from Finder has `/dev/null` there (measured:
`lsof` on the installed app). So when a problem shows, there is no record of
the state before it. Two open questions need one: whether the pending events
of a card (spec 2611.0003, choice 8: no bound) ever grow, and #327 (a dev app
that got slower for 13 minutes and then ended).

Facts measured for this spec (2026-11-12, macOS 26.7.2):

- `proc_pid_rusage(pid, RUSAGE_INFO_V4).ri_phys_footprint` is the figure
  Activity Monitor and `top` show as memory. It reads the caller's own pid and
  any process of the same user with no entitlement, also from a binary with
  the hardened runtime. For another user's process it fails (EPERM).
- Footprint and resident size differ a lot (app: 149 MB against 51 MB), so the
  log says which one it holds.
- The app decodes `hello_ok.daemon_pid` and does not keep it
  (`AppController+Connection.swift`, `case .helloOK`).
- Each card's web view has its own web content process (5 views, 5 pids).
  That is WebKit's behaviour today, not a contract.
- The pid of a view's web content process comes only from the WebKit SPI
  `_webProcessIdentifier`. It is 0 before the first load commits. There is no
  public API. The owner chose to use it, guarded (2026-11-12).
- A card's pending events are taken in the next turn of the main loop, so a
  timer that reads their count sees 0. The largest count must be kept by the
  session.
- The #321 rule for `tarmacd.log`: at a spawn, a file over 1 MiB is renamed to
  `<path>.1`, then the log is opened for append (`DaemonSpawner.swift`).
- OpenTelemetry (reference only): the log data model has a time stamp, a
  severity text, an event name, attributes and a resource. `service.name` and
  `service.version` are stable attributes; `process.pid` is a release
  candidate. `process.memory.usage` is a *metric* that means physical memory
  in use, which reads as resident size: a footprint is not logged under it.

## Motivation

A cheap, local record that answers "what did memory and the event queues look
like before this?" No SDK, nothing sent off the machine.

## Proposed Solution

### Overview

The app appends one JSON line to `tarmac-app.jsonl`, beside its daemon socket
(so beside `tarmacd.log`, one file for each channel): once when sampling
starts, and then every 300 s. One more line is written when the pending events
of one HTML card go over 1,000.

### Key Components

- **`TarmacKit/ProcessFootprint.swift`** — `ProcessFootprint.bytes(of pid: Int32) -> UInt64?`: `ri_phys_footprint`, nil when the call fails.
- **`TarmacKit/SampleLine.swift`** — pure. A plain input value (`SampleLine.Sample`) and a time give the line's text; a second function gives the over-limit line. Built with `JSONValue.jsonString` (keys sorted, so the text is stable).
- **`TarmacKit/SampleLogFile.swift`** — `append(_ line: String, to path: String)`: when the file is over the cap (1 MiB, a parameter for tests), rename it to `<path>.1` first; then open with `O_WRONLY|O_CREAT|O_APPEND`, mode 0644, and write the line and `\n`. A failed rename or open drops the line and does nothing else. The path of the file for a socket path: `SampleLogFile.path(socketPath:)`, the socket's directory + `tarmac-app.jsonl`.
- **`TarmacKit/HTMLCardSession.swift`** — keeps the largest count its pending events reached since it was last asked (`takeLargestPending() -> Int`, read and reset), and gives the effect `.pendingOverLimit(Int)` once each time the count goes over `HTMLCardSession.pendingLimit` (1,000).
- **`TarmacApp`** (wiring, no unit tests): `DaemonSession` keeps `daemonPid` from `hello_ok`; a sampler (a repeating `Timer` in `.common` mode, the `KeyReleasePoller` pattern) gathers the counts and pids on the main actor, then reads the footprints and appends the line on a utility queue; `HTMLCardView` forwards `takeLargestPending()` and `webProcessID` (the SPI, guarded by `responds(to:)`, nil for 0), and hands `.pendingOverLimit` to the sampler.

### Interface Contract

**The sample line** (one JSON object, keys sorted by `JSONValue`):

```json
{"attrs":{"tarmac.app.memory.footprint":149063264,"tarmac.boards.count":2,"tarmac.boards.loaded":1,
"tarmac.card.pending_events.max":6,"tarmac.card.pending_events.path":"/a/dash.html",
"tarmac.cards.html":3,"tarmac.cards.markdown":2,"tarmac.cards.terminal":1,
"tarmac.daemon.memory.footprint":6504928,"tarmac.daemon.pid":9160,
"tarmac.webcontent.largest.memory.footprint":120390544,"tarmac.webcontent.largest.path":"/a/dash.html",
"tarmac.webcontent.memory.footprint":412876800,"tarmac.webcontent.processes":5},
"event":"tarmac.sample",
"resource":{"process.pid":9156,"service.name":"tarmac-app","service.version":"0.20.1"},
"severity":"INFO","ts":"2026-11-12T10:15:00.000Z"}
```

- `ts`: UTC, RFC 3339 with milliseconds and `Z`.
- Every memory value is a footprint in bytes.
- `service.version`: the app's version (`AppVersion`); the key is left out when the app names none.
- `tarmac.daemon.pid` and `tarmac.daemon.memory.footprint`: left out, both, when the pid is not known or its footprint cannot be read.
- `tarmac.app.memory.footprint`: left out when it cannot be read.
- Web content: `tarmac.webcontent.processes` is the count of distinct pids that were known and readable; `tarmac.webcontent.memory.footprint` their sum. `largest.*` is the one with the largest footprint and the path of its card (a doc card's path; when two cards share a pid, the first in the input). All four keys are left out when no pid is known (the SPI is missing, or no view has loaded).
- `tarmac.boards.count`: the boards the daemon lists. `tarmac.boards.loaded`: the boards this app has built. The three `tarmac.cards.*` counts are over the loaded boards.
- `tarmac.card.pending_events.max`: the largest count of pending events any HTML card reached since the sample before; `…path` is that card's path, left out when the max is 0.

**The over-limit line:**

```json
{"attrs":{"tarmac.card.pending_events.count":1001,"tarmac.card.pending_events.limit":1000,
"tarmac.card.pending_events.path":"/a/dash.html"},
"event":"tarmac.card.pending_events.over_limit",
"resource":{…as above…},"severity":"WARN","ts":"…"}
```

**The session's rule.** `event(text)` that makes the pending count `limit + 1` gives `.pendingOverLimit(limit + 1)` beside its other effects, once. It is given again only after the pending events were emptied (`takeEvents()` or `reloaded()`) and the count goes over the limit again. `takeLargestPending()` gives the largest count since the call before (0 when none) and resets it; `takeEvents()` and `reloaded()` do not reset it.

**The file.** `tarmac-app.jsonl` in the socket's directory. Before each append, a file larger than 1 MiB is renamed to `tarmac-app.jsonl.1` (replacing an older one). The check is before each append, not only at launch: the app is long-lived.

**The timer.** One sample when the sampler starts (after the app's controller has started), then one every 300 s. In a DEBUG build only, `TARMAC_SAMPLE_INTERVAL_S` (a number of seconds, at least 1) replaces the 300: it is the seam for the live check and is compiled out of a release build.

## Security Considerations

The file is local and holds memory figures, counts and the paths of cards the user opened. Nothing is read from a card's content. Nothing is sent anywhere. The file's mode is 0644, as `tarmacd.log`'s.

## Acceptance Scenarios

### Footprint (Kit)
- **S1:** Given this process's own pid, then `ProcessFootprint.bytes` is a value over 0.
- **S2:** Given a pid that names no process (the test finds one by asking for a pid far above any in use, or uses -1), then nil.

### Line (Kit, pure)
- **S3:** Given a sample with every value and a fixed time, then the line is exactly the expected text (the whole string, keys sorted), and it parses as JSON.
- **S4:** Given no daemon pid, or a daemon pid with no footprint, then neither `tarmac.daemon.*` key is in the line.
- **S5:** Given no web content process, then none of the four `tarmac.webcontent.*` keys is in the line.
- **S6:** Given three web content entries with footprints 10, 30, 20 and two of them with the same pid, then `processes` counts distinct pids, the sum counts each pid once, and `largest.*` names the 30 one and its path.
- **S7:** Given a pending max of 0, then `…pending_events.max` is 0 and there is no `…pending_events.path`; given 6 for `/a/dash.html`, then both are there.
- **S8:** Given no app version, then the resource has no `service.version`; `service.name` is `tarmac-app` and `process.pid` is the pid given.
- **S9:** Given a time with a fraction of a second in another time zone's morning, then `ts` is the UTC time with three decimals and `Z`.
- **S10:** Given a path with a quote, a backslash and a non-ASCII letter, then the line still parses and the path comes back the same.
- **S11:** Given the over-limit input (path, count, limit, time), then the line is exactly the expected text with severity `WARN` and its event name.

### File (Kit, in a temporary directory with plain ASCII names)
- **S12:** Given no file, when a line is appended, then the file holds that line and one `\n`; a second append adds a second line.
- **S13:** Given a file larger than the cap (a small cap in the test), when a line is appended, then the old content is in `<path>.1` and the file holds only the new line.
- **S14:** Given a file of exactly the cap, then no rename (the rule is "larger than").
- **S15:** Given an existing `<path>.1`, when the file is over the cap again, then `<path>.1` holds the newer old content.
- **S16:** Given a directory that does not exist, when a line is appended, then nothing is thrown and no file is made.
- **S17:** Given a socket path `/x/y/tarmacd.sock`, then `SampleLogFile.path` is `/x/y/tarmac-app.jsonl`.

### Session (Kit)
- **S18:** Given a ready session, when 3 events come before a take, then `takeLargestPending()` is 3, and a second call is 0.
- **S19:** Given batches of 2, then a take, then 5, then a take, then `takeLargestPending()` is 5 (the largest, not the last or the sum).
- **S20:** Given a session that is not ready, when events come, then `takeLargestPending()` is 0.
- **S21:** Given a ready session, when the 1,001st pending event comes, then its effects hold `.pendingOverLimit(1001)`; the 1,000th and the 1,002nd do not.
- **S22:** Given S21, when the events are taken and 1,001 more come, then `.pendingOverLimit(1001)` is given again.
- **S23:** Given pending events over the limit, when the document reloads, then the largest count is still reported by `takeLargestPending()`.

### Live (dev channel, by hand, evidence under `.dev/qa-329/`)
- **L1:** With `TARMAC_SAMPLE_INTERVAL_S=5`: lines appear in `.dev/tarmac-app.jsonl`, each parses with `jq`, and the app and daemon footprints agree with `top`/`footprint` for those pids within a few percent.
- **L2:** With HTML and markdown cards open: `tarmac.webcontent.processes` is the count of those cards' loaded views, and `largest.path` names a real card.
- **L3:** After 1,000 lines through `tarmac push`: the next sample's `pending_events.max` is over 0 and names that card.
- **L4:** With the file filled past 1 MiB by hand: the next sample makes `.1` and starts the file anew.
- **L5:** A bundle build with its sockets pinned: lines appear with `service.version` set, and no `TARMAC_SAMPLE_INTERVAL_S` effect (a release build ignores it).
- Not run live: the over-limit line (a batch over 1,000 was never seen; it is covered by S21–S22 and S11).

## Trade-offs and Limitations

- `_webProcessIdentifier` is WebKit SPI. When it is gone, the web content keys are left out and nothing else changes.
- The GPU and Networking processes of WebKit are not in the log.
- "One process for each card" is WebKit's behaviour today; the line counts distinct pids so that it stays true if that changes.
- A sample holds the paths of the user's cards, in a local file.
- The largest pending count is reset by each sample, so with the 300 s timer it is "in the last five minutes".
