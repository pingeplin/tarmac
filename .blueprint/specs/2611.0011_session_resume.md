## Gate

Written 2026-11-14 from the code at `main` 5901908. The approach is the design's. It is not open here. These owner decisions bind this spec:

- **R1.** The resume record lives in the board's `term_records` entry of the terminal, beside `last_cwd`. It moves to a new term id through `SpawnTerm.succeeds`.
- **R2.** `Input.typed` tells the user's keys from the engine's own bytes. The resume chip uses it.
- **R4.** The chip takes keys on the prime card only. The shell counts as up at the PTY's first `Output` after the spawn. The first key decides: ⏎ writes the command and a newline once. Any other key drops the chip and the record, and then goes to the shell as usual. The §1.2 restore card, when it is shown, takes the first key before the chips.
- **Q1.** A cold spawn mints a new term id.
- **Q2.** The daemon finds the agent pid from the CLI's peer pid and a ppid walk. The foreground leader is only the fallback.
- **Design §4 B, clear rule.** If the daemon sees the agent pid exit while the daemon is alive, it drops the resume record. If the daemon dies first, the record stays, and the next restore offers it.
  - Design §4 B says that the pid is "the foreground leader at that time". This spec follows Q2 and slice 2 instead: the walk finds the agent, and the leader is only the fallback.
- **Design, out of scope.** A resume command never runs without a key press.
- **UI copy is English only** (owner decision, 2026-11-14).

The design does not settle the decisions below. Each one is marked **[D1]…[D14]** in the body.

**Decisions recorded 2026-11-14, reviewed with Fable:**
- **D1–D14 are accepted**, with the amendments to D4, D7, D10 and D13 written into their text below.
- **D1, D6 and D9 depart from the design's text.** The author accepted them after Fable's review. Each of them can only lose an offer; none can run a command. That cost is real and permanent:
  - a ⏎ pressed before the key hint shows loses the offer;
  - a key typed into a focused card that is not prime loses the offer.
  
  In both cases the record is dropped too, so no later restart offers it again.
- **D13 changes the §1.2 restore card into toast lines.** The toast lines ship in this slice. The restore-card overlay (the veil and the any-key card) is deferred to issue #358, which follows this slice. Until #358:
  - nothing takes the first key after a launch;
  - `esc skip` may need two presses while the toast shows (about 7 s), because the first Esc clears the toast.
- **OQ1–OQ4** are deferred or kept as recommended (*Open Questions*).
- **Review answers (2026-11-14, with Fable):**
  - **RA1.** `FocusedClose.decide` loses its `dead` parameter and `signalClose`. An interface change; the behaviour is fixed: ⌘W on any terminal card sends `TermClose` [D12]. TarmacKit then has no D12 assertion. D12 is proven by the daemon's `TermClose` test (2611.0007 S26) and QA S35.
  - **RA2.** `ResumeChip.display` never shortens a word that starts with `-`. It shortens only an id-like word: 13 or more characters, all from `[A-Za-z0-9_-]`, with at least one digit.
  - **RA3.** After `.runResume`, repeated Return events for that terminal are ignored until a key event that is not a repeat arrives. The latch is a `KeyLadder.Facts` field that gives `.ignoreRepeat`.

- **D1. The holder pid is kept in memory only.** The wire and `state.json` carry `resume: {cmd}`. They do not carry `{cmd, pid}` as the design and the task wrote it. *Why:* a pid from a dead daemon names no process, and a reused pid could name another one. The app has no use for it. **This departs from the design text.**
- **D2. The holder is always a pid with a start time.** The walk's three results map to one rule: `Agent` stays as it is. `Shell` (a `resume set` typed at the prompt) becomes the shell itself. The `Leader` fallback becomes the leader pid. The record is dropped when that process is gone, or when its pid now has another start time. `Holder::alive`'s leader rules for `Shell` and `Leader` are not used. *Why:* a resume command lasts for a process lifetime, not until the next command.
- **D3. When a resume record ends while the daemon is alive.**
  - The poll drops it when its holder is gone.
  - A terminal that ends drops it at any exit code. The non-zero exit still keeps `last_cwd` (slice 1).
  - Neither happens once shutdown has begun (D4).
  - *Why:* a terminal that ended in a live daemon took its agent with it. The design's "offered" means "the agent was still running when Tarmac went down".
- **D4. A shutdown freeze.** `Daemon::final_save` first sets a `shutting_down` flag. The flag stops exactly two things: the poll's drop of a resume record whose holder is gone, and `term_ended`'s removal of `resume` from a record that a non-zero or signal exit keeps. It stops nothing else. A clean exit (`code: 0`) still deletes the whole entry, `TermClose` still deletes its entry, and an explicit `resume clear` still clears. *Why:* the PTYs live until the process exits, but a poll tick during the 500 ms shutdown read must not race the save.
- **D5. A `resume set` marks the state dirty.** So do a drop, a clear and a move. A set with the same command as the stored one updates the holder only and does not save. *Why:* it is rare, and it must survive a crash or a SIGKILL. A cwd change, by contrast, never saves by itself (slice 1).
- **D6. The daemon drops an unclaimed record at the first typed input.** A record that has no holder came from disk or moved through `succeeds`. The daemon drops it at the first `Input` with `typed: true` to that terminal. The app's ⏎ sends the command as typed input, so it drops the record too, and a resumed agent sets a new one. *Why:* the design gives `Resume` as cli→D only, and R2 says the chip uses `typed`. The rule also holds when the app dies between the key and a clear. The app-session `resume` clear is in *Alternatives*.
- **D7. The command check.** It is one function in `tarmac-protocol`, `check_resume_cmd`, with a Swift mirror, `ResumeCommand.check`. It refuses:
  - an empty or whitespace-only command;
  - any control character (`char::is_control`, which covers `\n`, `\r`, `\t`, ESC, DEL and C1), and also U+2028 and U+2029 (the line and paragraph separators, which are not Cc);
  - the invisible format and bidi characters U+061C, U+200B–U+200F, U+202A–U+202E, U+2060–U+2064, U+2066–U+2069 and U+FEFF;
  - more than `RESUME_CMD_MAX` = 256 `char`s.

  The CLI, the daemon and the app each apply it. The length counts Unicode scalar values in both languages: the Swift check counts `unicodeScalars`, never `Character`s (graphemes). *Why:* ⏎ must run exactly one visible command line.
- **D8. `session_id` must match `^[A-Za-z0-9][A-Za-z0-9_-]{0,127}$`.** Then the command is `claude --resume <session_id>`, with no quotes. Any other value gives no record and one stderr line. *Why:* Claude's ids are UUIDs. The set excludes every shell metacharacter and a leading `-`.
- **D9. Refinement of R4: any user byte drops the offer.** The offer is dropped by any `.user` input that reaches the PTY, whatever the card's state:
  - before the shell is up;
  - on a card that is not prime;
  - Esc, once it passes the Esc ladder.

  ⏎ runs the command only when the card has keyboard focus, is prime, and its shell is up. *Why:* if the chip outlived a key, the keys typed before the prompt would be prefixed to the command. `ls` typed early and then ⏎ would run `lsclaude --resume …`. R4's "before the first `Output` the chip takes no key" still holds: no key runs it then.
- **D10. "Reopen here" on a dead card.**
  - A dead card that has a known record shows a strip: `↻ reopen here  ⏎`.
  - The strip is a button. ⏎ on the dead card that has keyboard focus does the same. A dead card is never prime, because `TermPrime.reassign` skips dead cards. After a restart no terminal is live, so prime cannot be the owner of this key.
  - Reopen replaces the dead card in place with a cold spawn (`cwd: last_cwd`, `succeeds: <dead id>`). The new card gets the resume chip when the record has a command. So a full resume is two presses of ⏎, and each press shows what it does.
  - The app knows a record only from its board's latest `restore` (D11).
  - **Amendment: no auto-repeat.** `.reopenDead` and `.runResume` refuse a key-repeat event. `KeyPress` gets an `isRepeat` fact, set from `NSEvent.isARepeat`. A repeated plain Return on a terminal that shows an offer (a resume offer, armed or not, or a reopen offer) is taken and ignored (`.ignoreRepeat`). So a held ⏎ reopens a dead card once. Its repeats neither run the new card's command nor reach the shell, where as user bytes they would drop the offer [D9]. A held ⏎ that runs the command sends it once, and its repeats are ignored too (RA3).
- **D11. The app keeps the records of every restore.** It keeps them on the first visit and on every reconcile. A card that dies of its own exit, while its board is shown, gets an offer only at its board's next restore: a board switch or a reconnect. A push of the kept record is the upgrade path (OQ2).
- **D12. ⌘W on a dead card sends `TermClose`.** The daemon deletes the record (2611.0007 S26), and nothing is killed. This answers slice 1's OQ2: the UI that makes the record useful now exists, so a closed dead card must not leave its record behind.
- **D13. §1.2: only the content ships, in the existing toasts. The overlay is deferred.**
  - A first-visit restore with cold spawns adds two lines to the toast: `✓ N terminals back in their folders` and `↻ M with an agent session to resume`. The toast is `RestartNotice`'s when that one fires, else a new toast titled `terminals restored`.
  - The reconcile toast's body `open new terminals with ⌘T` becomes `⏎ on a dead card reopens it in its folder` when some dead card got an offer.
  - The veil and the any-key card of backlog §1.2 are deferred to issue #358, which follows this slice. The backlog entry gets the new copy and points to #358.
  - So no "restore card" takes keys in this slice, and nothing takes the first key after a launch. Only Esc meets the toast first, through the Esc ladder (S27). While the toast shows (about 7 s), `esc skip` may need two presses.
  - *Why:* the overlay's key capture is its own design. The facts fit a toast that already exists.
- **D14. A `make qa` scenario lives in a new runner.** The runner is `scripts/qa/resume.mjs`, run by `make qa-resume`, in the same shape as `qa-quit`. The dev snapshot gains each terminal's `resume` (cmd, armed) and `reopen` (bool). *Why:* the scenario kills the dev daemon by pid, which ends every terminal, so it cannot sit in `smoke.mjs`.

## Motivation

A daemon restart kills every terminal. Slice 1 brings each shell back in its folder. The agent session that ran there is still on disk (`claude --resume <id>`), but nothing on the card says so. The user has to remember which card ran which session, and find the id. This slice records the command while the agent runs. After a restart, the card offers that command, and it runs on one key press. A running app that sees its daemon die can now reopen a dead card in place, where today it can only say "open new terminals with ⌘T".

## Proposed Solution

### Overview

1. While `claude` runs in terminal T, its `SessionStart` hook runs `tarmac hooks run claude`. The hook sends `Resume {T, cmd: "claude --resume <id>"}`.
2. The daemon walks from the CLI to the agent (2611.0009). It stores `resume: {cmd}` in T's record, keeps the holder (pid, start time) in memory, and saves the state.
3. If the agent exits while the daemon lives, the poll drops the record. If the daemon dies first, the record stays in `state.json`.
4. On the next first-visit restore, the cold-spawned card shows `↻ last here: claude --resume 3f2a…`. Once the shell prints, and while the card is prime, the chip adds `⏎ run · esc skip`.
5. ⏎ writes the command and `\r` once, as typed input. Any other key drops the chip and goes to the shell. Either way, the daemon drops the record at that typed input [D6].
6. A running app that sees its daemon restart marks the cards dead, as today. A dead card with a known record shows `↻ reopen here  ⏎`. Reopen cold-spawns in place, and the new card shows the chip.

### Key Components

**Protocol** (`tarmac-protocol/src/lib.rs` and the Swift codec, same change).

- `Msg::Resume { term_id: String, cmd: Option<String> }`. `cmd` is omitted when `None`. With `cmd` it sets the record; without it, it clears the record. The direction is cli → daemon, and the reply is `Ack` or `Err`.
- `TermRecord` gets `resume: Option<ResumeRecord>`, omitted when `None`. `ResumeRecord { cmd: String }`. No pid [D1].
- `pub const RESUME_CMD_MAX: usize = 256` and `pub fn check_resume_cmd(&str) -> Result<(), &'static str>` [D7]. The `Err` text names the cause: `empty`, `a control character`, `an invisible format character`, `over 256 characters`.

**CLI — `tarmac resume`** (`tarmac-cli/src/resume.rs`, new; dispatched from `main.rs`).

```
tarmac resume set "<command>"
tarmac resume clear
```

- **Usage (exit 2).** No subcommand, an unknown subcommand, `set` without exactly one argument, or `clear` with any argument. `set` with a command that `check_resume_cmd` refuses also exits 2, with `tarmac: resume command refused: <cause>`. Nothing connects.
- **A terminal is required (exit 1).** With `TARMAC_TERM_ID` unset or empty, the CLI prints `tarmac: resume needs TARMAC_TERM_ID (run it in a Tarmac terminal)`. The usage check comes first.
- **The exchange.** It uses `report::send(&Msg::Resume{…}, DAEMON_WAIT, …)`, the same seam as `report`. `Ack` → exit 0, with nothing printed. `Err {msg}` → `tarmac: {msg}` and exit 1. No daemon → the `connect` line and exit 1. No answer → `tarmac: no answer from the daemon in 5 s (an older daemon)` and exit 1.
- `help.rs` gets the two usage lines. `GUIDE.md` gets a short section, *Resuming after a restart*.

**CLI — `hooks run claude`, `SessionStart`** (`hooks.rs`).

- `ClaudeInput` gets `session_id: Lenient`.
- The mapping function (now `claude_message`, since it no longer returns only reports) maps `SessionStart` to `Msg::Resume {term_id, cmd: Some(format!("claude --resume {id}"))}`, for every `source`. It does this only when `session_id` is a string that matches D8. Else it returns `None`, and `hook` writes `tarmac: hooks run: session_id refused` to stderr.
- Everything else in `hooks run` is unchanged: exit 0 always, no stdout, the 500 ms deadline, and no work without `TARMAC_TERM_ID`.

**Daemon — the resume store** (`tarmacd/src/state.rs`, plus a small pure module `tarmacd/src/resume.rs`).

- **One lock for the record, the holder and the flag.** `Registry` gets `resume_holders: HashMap<String, Holder>` beside `term_records`. It is in memory only [D1]: `persist::snapshot` and the `restore` do not copy it. So `boards` guards the record, its holder and the handle's flag together. `Boards::forget_term` and a board delete remove the holder with the record.
- `Daemon` gets `shutting_down: AtomicBool` [D4].
- `TermHandle` gets `resume: AtomicU8` with three states: `NONE`, `HELD` and `UNCLAIMED`. It is written only while `boards` is held, in the step that changes the record. It is read without a lock. So a poll tick or a key with no resume costs one load.
- **`Daemon::set_resume(peer, term_id, cmd: Option<String>) -> Result<(), String>`** (the `Resume` handler):
  1. The term must be live. Else `err` `unknown terminal: <id>`.
  2. **Clear** (`cmd: None`): remove `resume` from T's record and T's holder. Mark dirty when there was one. `Ack`.
  3. **Set:** `check_resume_cmd(cmd)`. Else `err` `resume command refused: <cause>`.
  4. The holder, as D2 says:
     - Run `Holder::resolve(peer, handle.pid(), handle.spawned_with_cmd(), proc_facts, leader)`.
     - Map the result to `Holder::Agent {pid, started}`: `Agent` stays as it is. `Shell` takes the child's pid. `Leader` takes the leader's pid. `started` comes from `proc_facts` of that pid.
     - When that read is not `Live`, or `resolve` gives `None`, answer `err` `no process to tie the resume command to in <id>`.
  5. Under `boards`, find T's record on T's board (`term_boards`). With no entry (deleted meanwhile), answer `err` `unknown terminal: <id>`. In the same step, store `resume: {cmd}`, store the holder in that board's `resume_holders`, and set the handle's flag to `HELD`.
  6. Mark dirty unless `cmd` equals the stored command [D5].
  7. **The race with exit.** As `Daemon::report` does, re-read `daemon.term(term_id)` after the change. When the term is gone, remove the resume and the holder again. (`term_ended` takes the term out of `terms` before its own drop, so one of the two finds it.)
  8. `Ack`. No frame goes to the app. The app reads records only from `restore`.
- **The poll** (`proc_loop`). Each tick, before the `continue` on a failed leader read, the loop calls `check_resume(term_id, handle, proc::proc_facts)` when the handle's flag is `HELD`.
  - `check_resume(term_id, handle, facts_of: impl Fn(Pid) -> Facts)` is the seam that production calls and S16 tests. It copies the holder under `boards`, and releases the lock.
  - It checks the copy with `Holder::alive(facts_of, None)`. For an `Agent` holder, that reads only the pid and the start time. `Unread` keeps the record for that tick.
  - When the holder is not alive and `shutting_down` is false, it takes `boards` again. It removes `resume` and the holder **only if the stored holder still equals the copy**, sets the flag to `NONE`, and marks dirty. So a `resume set` that stored a new holder in between is never undone.
- **Typed input** (`dispatch_app_msg`, `Input`). After the bytes are sent and the report read-mark has run, the daemon takes a slow path only when `typed` is true and the handle's flag is `UNCLAIMED` [D6]. It removes `resume` from T's record, sets the flag to `NONE` and marks dirty.
- **Move** (`adopt_term`). When the moved record has a `resume`, the new term's flag is set to `UNCLAIMED`. Holders never move: the old term is not live, so it has none. `adopt_term` takes only the plan today (`state.rs:450`); it must also get the new handle, so that the flag is written in the same `boards` step as the move.
- **A set over an unclaimed record** stores a holder and sets the flag to `HELD`. A typed key after it does not drop the record.
- **End** (`term_ended`). After the term leaves `terms`, the daemon removes the holder. When `shutting_down` is false, it also removes `resume` from a kept record (non-zero or signal exit) and marks dirty when there was one [D3]. A clean exit deletes the whole entry, as today.
- **Close** (`close_term`). Deleting the entry deletes the resume. The daemon also removes the holder.
- **Shutdown** (`final_save`). It sets `shutting_down` before it sends its request to `save_loop` [D4].
- **Locks.** `boards` alone guards the record, the holder and the flag. `resume_holders` is inside `Registry`, so it has no lock of its own. Read `term_boards` and release it before `boards` is taken, as `note_cwd` does. No `proc_facts` read or `await` runs while `boards` is held. Never hold a `std::sync::Mutex` across `.await`.

**App — codec** (`TarmacKit/Messages.swift`).

- `.resume(termID:cmd:)`, decode and encode. The app never sends it in this slice. It exists for the codec's completeness and the conformance vectors.
- `TermRecord` gets `resume: ResumeRecord?`, with `ResumeRecord { cmd: String }`. The encoder writes `resume` only when it is non-nil.

**App — the command check** (`TarmacKit/ResumeCommand.swift`, new). `ResumeCommand.check(_:) -> String?` (nil means accepted, else the cause). It has the same rules and cases as Rust's `check_resume_cmd` [D7]. Its job is to refuse to offer a record from a hand-edited or older `state.json`.

**App — the plan** (`BoardRestore.swift`). `Term` gets `resume: String?`. It is the record's `resume.cmd` for a cold spawn of a persisted tile when `ResumeCommand.check` accepts it, and nil otherwise. It is nil for a rebound term, a legacy tile with no `term_id`, and the board's one fresh terminal.

**App — the offer** (`TarmacKit/ResumeOffer.swift`, new; pure).

```
public struct ResumeOffer: Equatable, Sendable {
    public let cmd: String
    public private(set) var shellUp: Bool                   // false until the first output
    public static func make(cmd: String?) -> ResumeOffer?   // nil for nil or a refused cmd
    public func armed(prime: Bool) -> Bool                  // shellUp && prime

    public enum Event: Equatable, Sendable {
        case output(byteCount: Int)   // a chunk released to the card
        case userInput                // any `.user` bytes about to go to the PTY
        case returnKey(prime: Bool)   // the `.runResume` rung fired for this card
    }
    public enum Effect: Equatable, Sendable { case run(Data) }   // cmd's UTF-8 + 0x0D

    /// The one reducer the wiring calls; the offer is a value, so the
    /// next state is returned.
    public static func step(_ offer: ResumeOffer?, _ event: Event) -> (offer: ResumeOffer?, effect: Effect?)
}
```

- **The reducer's rules:**
  - `.output(n)` with `n > 0` sets `shellUp`, and `n == 0` changes nothing.
  - `.userInput` gives `(nil, nil)` in every state [D9].
  - `.returnKey(prime: true)` on an armed offer gives `(nil, .run(cmd + "\r"))`. In any other state it changes nothing and has no effect.
  - A nil offer stays nil and has no effect for every event, so a second ⏎ can never run the command again.
- The wiring stores the returned offer and performs the effect. It decides nothing.
- `ResumeChip.model(offer:prime:) -> Model { text, toolTip }`:
  - `text`: `↻ last here: <display>`. When `armed(prime:)` is true, `  ⏎ run · esc skip` follows.
  - `toolTip`: the whole command, verbatim.
  - `ResumeChip.display(cmd)` shortens an id-like whole word (delimited by spaces or by the ends) to its first 4 characters and `…`. A word is id-like when it has 13 or more characters, all from `[A-Za-z0-9_-]`, at least one of them a digit, and it does not start with `-` (RA2). Every other character is shown as it is. So `claude --resume 3f2a1b9c-…-uuid` reads `claude --resume 3f2a…`, a flag such as `--dangerously-skip-permissions` stays whole, and a shell metacharacter is never hidden.
- `DeadCardOffer.make(record: TermRecord?, home: String) -> Offer?`:
  - It gives nil unless the record has a `lastCwd` or a command that `ResumeCommand.check` accepts.
  - `Offer { cwd: String?, resume: String? }`.
  - Its `model` is `↻ reopen here  ⏎`, with a second line `in <cwd, with home shown as ~>` when there is a cwd, and a third line `then offers: <display>` when there is a resume.
  - `DeadCardOffer.reopen(offer, deadID:) -> (spawn: SpawnRequest, resume: String?)` gives `SpawnRequest(cwd: offer.cwd, succeeds: deadID)` and the offer's resume. The wiring spawns exactly that. Without `succeeds`, the record would stay under the dead id with no owner.
- `RestoreSummary.lines(plan: BoardRestore.Plan) -> [String]`:
  - `✓ N terminals back in their folders` counts the cold spawns whose `spawn.cwd` is non-nil. N = 1 reads `✓ 1 terminal back in its folder`.
  - `↻ M with an agent session to resume` counts the cold spawns with a `resume`.
  - A line whose count is 0 is left out.
- `ReconnectRestore.restartToastBody(reopenable: Int) -> String`. It gives `open new terminals with ⌘T` for 0, and `⏎ on a dead card reopens it in its folder` otherwise [D13].

**App — keys** (`KeyLadder.swift`).

- `Facts` gets two fields:
  - `resumeArmed`: the terminal with keyboard focus is prime, and its offer is armed;
  - `reopenOffered`: the terminal with keyboard focus is dead and has a `DeadCardOffer`.
- Two new `Action`s, `.runResume` and `.reopenDead`, for plain Return (`press.named == .enter`, no ⌘⌥⌃, and not `press.isRepeat`) while `keys == .terminal`. `Facts` also gets `offerShown`: the focused terminal has a resume offer (armed or not) or a reopen offer. A repeated plain Return with `offerShown` gives a third new action, `.ignoreRepeat`, which the wiring takes and drops.
- `Facts` also gets `afterRun` (RA3): the focused terminal ran its command by `.runResume`, and no key event that is not a repeat has come since. A repeated plain Return with `afterRun` gives `.ignoreRepeat`. A non-repeat Return with `afterRun` is decided as if `afterRun` were false (it passes through to the shell). The latch's rule is pure and in TarmacKit: `KeyLadder.afterRun(was: Bool, press: KeyPress, action: Action) -> Bool` gives `true` after `.runResume`; `false` for a press that is not a repeat and gives any other action; and `was` for a repeat. The wiring keeps one latch per terminal, passes it in `Facts`, and stores what `afterRun` returns after each decision.
- A repeated Return with neither `offerShown` nor `afterRun` passes through as today. The new actions are tried after `.newTerminal` and before `.flyToSignal`. So composing, a document, ⌘K, ⌘W and an open switcher all come first. An IME commit ⏎ never runs the command.

**App — wiring** (`TarmacApp`; no unit tests by design).

- `TerminalSession` gets `resumeOffer: ResumeOffer?` and `deadOffer: DeadCardOffer.Offer?`.
- `Board` gets `termRecords: [String: TermRecord]`. `applyRestore` stores the restore's table on every restore, first visit and reconcile alike [D11]. After a reconcile it sets `deadOffer` on each dead card of that board, and shows each offer's strip.
- `addTerminal` takes the plan's `resume` and sets `resumeOffer = ResumeOffer.make(cmd:)`. The card shows the chip.
- `showOutput` feeds `.output(byteCount:)` for each released chunk to `ResumeOffer.step`, and refreshes the chip.
- `updatePrimacy` refreshes the chip, because the key hints depend on prime.
- `terminalDidSend` feeds `.userInput` for any `.user` input, after its `reachable` guard and before it forwards the bytes [D9]. Bytes that the guard drops never reach the PTY, so they do not drop the offer. Bytes from the engine itself (a DA1 answer, a cursor or focus report) are not `.user` and do not drop it.
- `.runResume` feeds `.returnKey(prime:)`. On `.run(bytes)` it sends `client.input(termID:bytes:typed: true)`. The daemon drops the record at that input [D6].
- `holdOpen` sets `resumeOffer` to nil, beside `bellAt`, so a dead card never keeps a `↻ last here` strip. A lost connection does not clear offers. Without a restart the card's shell is still live and its record is still unclaimed. With a restart, reconcile reaches `holdOpen`.
- `.reopenDead`, and a press on the strip:
  - remove the dead card with no `TermClose`;
  - `addTerminal` a new id at the same frame and z, with what `DeadCardOffer.reopen` gives;
  - make it prime, give it keyboard focus, then `spawnPending` and `persistLayout`. The new card must hold the keys before the next key event, so that a repeat of the same ⏎ meets the new card's facts (`.ignoreRepeat`), not the board's.
- **Keyboard focus on a dead card.** `.reopenDead` needs the dead card's view to hold the keys. `select` gives focus only to a live terminal (*Context*). A press on a dead card must leave its view with keyboard focus. QA S32 checks this with a real click. S37 does not: the driver's press makes its target the first responder by itself (`Dev/DevInput.swift:88-89`).
- `closeSelectedCard` sends `TermClose` for a dead card too [D12]. `FocusedClose.decide(kind:otherLiveTerminals:)` has no `dead` parameter, and `.closeTerminal(replace:)` has no `signalClose` (RA1). `closeTerminal` always sends `TermClose`.
- `takeKey` keeps the focused terminal's `afterRun` latch with `KeyLadder.afterRun` (RA3). It decides nothing itself.
- **The strips.**
  - The resume chip and the dead-card offer are one view: a strip pinned to the bottom edge of the terminal card's body, over the content. It does not change the terminal grid.
  - It uses the report chip's metrics and form (`ChipView`: border and text, no fill, `CardScale`). It wraps inside the card's width, so no part of `<display>` is clipped.
  - It is drawn at full opacity on a dead card, though the card is dimmed. `setExited` dims the card by its own `alphaValue`, which also dims every subview. So the strip cannot be a plain subview of the dimmed view.
- **Toasts** [D13]:
  - First visit: the `RestoreSummary` lines go in `RestartNotice`'s body when that toast fires, one per line after the notice's own line. Else they go in a new toast, `terminals restored`, when there is at least one line.
  - Reconcile: the restart toast's body is `ReconnectRestore.restartToastBody(reopenable:)`. `reopenable` is the count of the board's dead cards that get an offer. `reconcile` shows the toast before `markLost` today (`AppController+Layout.swift:128-134`), so the count is taken from the lost ids and the stored table before the toast shows.
- **Dev snapshot** [D14]. Each terminal entry gets `resume: {cmd, armed}` or none, and `reopen: Bool`. `DevSnapshot` is in TarmacKit and is tested.

### Data Flow

1. In terminal T (shell S), the user runs `claude`. Claude's `SessionStart` hook runs `tarmac hooks run claude`, whose parent is `claude`.
2. The hook reads `session_id` `3f2a…` and sends `Resume {T, "claude --resume 3f2a…"}`.
3. The daemon walks P → `claude` → S. The holder is `Agent {claude pid, started}`. The daemon stores `resume` in T's record, marks dirty and answers `Ack`. The save loop writes `state.json`.
4. `brew upgrade` and an app relaunch. The app SIGTERMs the daemon. `final_save` sets `shutting_down`, reads the cwds and writes once. The process exits, and the PTYs die after it.
5. The new daemon loads the record. The app's first-visit restore plans T′ for T: `SpawnTerm {T′, cwd, succeeds: T}`, with `resume` set on the plan. The daemon moves the record to T′ and sets T′'s flag to `UNCLAIMED`.
6. The card shows `↻ last here: claude --resume 3f2a…`. The prompt prints, so the offer is armed. The card is prime, so the chip adds `⏎ run · esc skip`. The toast says `✓ 3 terminals back in their folders` / `↻ 1 with an agent session to resume`.
7. The user presses ⏎. The app sends `Input {T′, "claude --resume 3f2a…\r", typed: true}`. The daemon writes it to the PTY, sees `typed` and `UNCLAIMED`, and drops the record. `claude` starts, and its `SessionStart` sets a new record with a new holder.

### Interface Contract

Additive only. Both codecs ignore unknown keys and types.

```
resume        { t:"resume", term_id: str, cmd?: str }        cli → daemon; reply ack | err
TermRecord    { last_cwd?: str, resume?: { cmd: str } }       in restore.term_records and state.json
```

- **`resume`.** With `cmd`: set; without it: clear. `err` texts: `unknown terminal: <id>`, `resume command refused: <cause>`, `no process to tie the resume command to in <id>`. A clear with no record is `ack`, and nothing is saved.
- **`TermRecord.resume`.** Omitted when nil. A `restore` and `state.json` carry it. No pid is ever on the wire or on disk [D1].
- **`input.typed`** (2611.0009) also drops an unclaimed resume record [D6].
- **New conformance vectors.** The hex is `rmp_serde::to_vec_named` bytes, in its key order. Each vector gives the whole msgpack payload, with no length prefix, as V1–V24 do.
  - **V25:** `{t:"resume", term_id:"t1", cmd:"claude --resume ab-12"}`
  - **V26:** `{t:"resume", term_id:"t1"}` (no `cmd` key)
  - **V27:** `{t:"restore", docs:[], tiles:[], term_records:{"t1":{last_cwd:"/w", resume:{cmd:"claude --resume ab-12"}}}}`
  - Both codecs decode each one, and round-trip it. The Swift encoder's bytes equal Rust's. V1–V24 do not change; V18 in particular still has no `resume` key.
- **Docs.**
  - `docs/protocol.md`: the section *A terminal's last folder* gets `resume`; a new section *Resuming after a restart (spec 2611.0011)* for the frame and its rules; *CLI session* names `resume`; V25–V27.
  - `docs/architecture.md`: §3 *Terminal sessions* (the resume record, its holder and its drops); §4 *Terminal cards* (the chip, the dead-card strip), *Focus and keys* (the three new Return actions) and *Restore and reconnect* (the kept tables, the toast copy); §6 *What survives what* (a resume record survives a daemon restart only when its agent was still running); *Persistence*.
  - `docs/backlog.md` §1.2: the new copy, and a note that the content ships as a toast while the overlay is still open.
  - `CLAUDE.md`: its list of the verbs that talk to the daemon (`open`, `push`, `report`, `--version` and `hooks run`) gets `resume`.
  - `GUIDE.md`: *Resuming after a restart*, and *Reports from Claude Code* says that `SessionStart` now records the resume command.

## Alternatives Considered

- **Persist `{cmd, pid}` as the design wrote it.** A pid from a dead daemon names nothing, and a reused one names a stranger. Rejected [D1].
- **The app clears the record with `resume {term_id}` on the app session.** It works, and it is explicit. It is rejected for the typed-input drop [D6]: that keeps `Resume` as cli→D (the design's table), uses R2 as the design says, and holds even if the app dies between the key and the clear.
- **Keep the resume record when a terminal ends with a non-zero code.** This would let a logout, where the agent and the shell die before the daemon, still offer the session. But the app cannot see a record that is kept at an exit (D11), so the record would be stale and orphaned. Rejected for now; see OQ1.
- **A `SessionEnd` hook that sends `resume clear`.** It would be Claude-specific and redundant with the pid rule, and slice 3 installs no `SessionEnd`. Rejected.
- **The daemon fills `cwd` from the `succeeds` record.** Every dead card could then offer "reopen here", even one whose record the app never saw. It changes slice 1's `succeeds` contract. It is deferred (OQ2).
- **One press: "reopen and resume" on the dead card.** It saves a key, but it runs a command in a shell that the user has not seen start. Rejected. The two-step flow keeps R4's "shell up, first key decides".
- **The full §1.2 overlay now.** Its veil and its any-key capture need their own design against R4. Deferred [D13].
- **Put the chip in the card header.** The header lays out chips at full room and cuts only the label (`CardChrome.swift:535-560`). A long command would push the label out, and a clipped chip could hide the end of what ⏎ runs. Rejected for the wrapping strip.

## Migration & Rollback

- **Migration.** None. A record with no `resume` loads as before.
- **A new CLI with an older daemon.** The daemon ignores `resume`. `tarmac resume` waits 5 s and exits 1. `hooks run claude` waits 500 ms, at every `SessionStart`, and exits 0. This is accepted: the app restarts a daemon of another version.
- **An older daemon reading a new `state.json`.** `TermRecord` does not deny unknown keys, so `resume` is ignored. That daemon's next save drops it.
- **An older app.** It ignores `TermRecord.resume`, so it shows no chip. An app from before slice 2 sends no `typed`, so an unclaimed record stays and is offered again after the next restart.
- **Rollback.** Revert the change. A `resume` key left in `state.json` is dropped by the next save.

## Security Considerations

- **Running a stored command.**
  - Nothing runs without a key press: ⏎ on the prime, focused card, after its shell printed.
  - The chip shows the whole command, wrapped, with only id-like words shortened. The tooltip shows it verbatim.
  - The command is checked three times [D7]: by the CLI, the daemon and the app. So it is one line, with no control characters, no invisible format or bidi characters, and at most 256 characters. ⏎ cannot run a second hidden line, and a bidi override cannot make the shown text differ from the run text.
- **Shell injection from Claude's input.** `session_id` must match `^[A-Za-z0-9][A-Za-z0-9_-]{0,127}$` [D8]. So the hook builds `claude --resume <id>` with no quoting, no metacharacter, and no id that reads as a flag.
- **Stale commands.**
  - A record is offered only when its agent was still running when the daemon died (D3).
  - It is offered once: the first typed key in its card drops it [D6].
  - It may still be stale, for example when the session was resumed elsewhere since. The user sees the command before ⏎. Resuming an ended Claude session is harmless.
  - The record has no time stamp (OQ3).
- **Other processes and other users.**
  - Any process that can open the socket can set a resume command for any live term id. That is the same trust as `open`, `report` and `push`: the socket is the user's own.
  - A same-user process could plant a command for another card. The user still sees it and must press ⏎. Such a process could also edit the user's shell rc file, so this adds no new reach.
  - The socket and `state.json` live under `~/Library/Application Support`, which is `0700` here (*Context*). This slice sets no mode, and other users cannot reach either file.
  - `state.json` now holds commands. The app re-checks every one it offers.
- **The walk.** The holder pid comes from the kernel's peer pid. A caller can only make itself unattributed. It cannot name another process.

  - Plain Return with `keys: .terminal, reopenOffered: true` gives `.reopenDead`.
  - With `composing: true`, or `switcherOpen: true`, or ⌥/⌘/⌃ held, or `keys: .host`, it is not `.runResume`.
  - With `resumeArmed: false` it is `.passThrough`. This holds with `offerShown: true` too: a fresh ⏎ on an offer that is not armed reaches the shell, and so drops the offer [D9].
  - A repeated plain Return with `reopenOffered: true, offerShown: true, isRepeat: true` gives `.ignoreRepeat`, never `.reopenDead`.
  - **A held ⏎ (D10 amendment).** The first press, with `reopenOffered: true`, gives `.reopenDead`. The repeats that follow (`isRepeat: true`), with the new card prime and armed (`resumeArmed: true`), give `.ignoreRepeat`, never `.runResume`. A repeat while the new card's offer is not yet armed (`offerShown: true`, `resumeArmed: false`) also gives `.ignoreRepeat`, so it never reaches the shell. A fresh press (`isRepeat: false`) on the armed card then gives `.runResume`. A repeated Return with `offerShown: false` and `afterRun: false` is `.passThrough`.
  - **A held ⏎ that runs the command (RA3).**
    - `afterRun(was: false, press: Return, action: .runResume)` is `true`: `.runResume` sets the latch.
    - With `afterRun: true` and no offer (`offerShown: false`), a repeated plain Return gives `.ignoreRepeat`, never `.passThrough`.
    - `afterRun(was: true, press: <repeated Return>, action: .ignoreRepeat)` stays `true`.
    - `afterRun(was: true, press: <non-repeat "a">, action: .passThrough)` is `false`: the next key that is not a repeat clears it.
    - With `afterRun: true`, a fresh (non-repeat) plain Return gives `.passThrough`, and `afterRun` after it is `false`.
- **S10 (dead-card offer; TarmacKit):**
  - A record with `lastCwd: "/Users/u/w"` and home `/Users/u` gives an offer whose model lines are `↻ reopen here  ⏎` and `in ~/w`.
  - With a safe resume, a third line reads `then offers: <display>`.
  - A record with neither, or no record, gives nil.
  - A record whose only resume is refused by `ResumeCommand.check` and has no `lastCwd` gives nil.
  - A record with `lastCwd: "/w"` and a refused resume gives an offer with no third line, and `DeadCardOffer.reopen` on it gives a nil resume.
- **S11 (the summary; TarmacKit):**
  - A plan with three cold spawns, two with a `cwd` and one with a `resume`, plus one rebound term, gives `["✓ 2 terminals back in their folders", "↻ 1 with an agent session to resume"]`.
  - One cold spawn with a `cwd` and no resume gives `["✓ 1 terminal back in its folder"]`.
  - No cold spawn gives `[]`.
  - `restartToastBody(reopenable: 0)` is `open new terminals with ⌘T`; with 2 it is `⏎ on a dead card reopens it in its folder`.
- **S12 (wire):**
  - V25–V27 decode to the stated structures in both codecs and round-trip. The Swift encoder's bytes equal Rust's.
  - In both codecs, a `TermRecord` with a nil `resume` has no `resume` key, and a `resume` with a nil `cmd` has no `cmd` key.
  - V1–V24 pass unchanged.

### Edge Cases

- **S13 (a typed key does not drop a held record; integration):**
  - Given S1's set from an agent that runs `sleep 30`, so that the agent is alive for the whole check (S1's `sleep 3` is too short),
  - when the app sends `Input {T, "\r", typed: true}`,
  - then a probe 1 s later still shows `resume`. The `HELD` flag is not `UNCLAIMED`.
- **S14 (a set at the prompt lasts while the shell lives; integration) [D2]:**
  - Given a shell spawn T, and the test types `<nc resume "echo HI">; echo BA""CK` at the prompt (a foreground command whose parent is the shell),
  - when `BACK` shows, and the test then types `sleep 2` and waits 3 s,
  - then a probe still shows `resume`.
  - A `Shell` leader rule would drop it at `sleep`, and a caller-pid rule would drop it at once, so this fails under both.
- **S15 (a terminal that ends drops the command and keeps the folder; integration) [D3]:**
  - Given a shell T with a record from S1's setup (agent `sleep 30` in the background), and a `last_cwd`,
  - when the test types `exit 3`,
  - then after `Exit {code: 3}`, a saved check shows T's entry with `last_cwd` and no `resume`.
  - The same setup with `exit 0` leaves no entry (slice 1).
- **S16 (the shutdown freeze; unit) [D4]:**
  - The seam:
    - A `with_fs` daemon spawns T with a `cmd` (a plain shell `read _`), as 2611.0007's unit tests do.
    - `set_resume(None, T, Some("echo HI"))` has no peer, so the walk falls back to the leader. The leader is the PTY child, so the holder is `Agent {child, started}`.
    - `check_resume` then runs with a `facts_of` that answers `Gone` for every pid.
  - Given that state,
  - when the test calls the shutdown entry that sets `shutting_down`, then `check_resume(T, handle, gone)`, then `term_ended(T, Some(3))`,
  - then T's record still has `resume`.
  - A control run with no shutdown drops it at `check_resume`. A second control with no shutdown and a `facts_of` that answers `Live` with the holder's start time keeps it at `check_resume`, and then drops it at `term_ended(T, Some(3))`.
  - With no shutdown, `check_resume` with `Live` and another start time (a reused pid) drops the record, and with `Unread` it keeps it.
  - The freeze stops only those two drops. Under `shutting_down`, `term_ended(T, Some(0))` still deletes the whole entry, `close_term(T)` still deletes it, and `set_resume(None, T, None)` still clears `resume` (one case each, on a fresh daemon).
  - The compare-and-remove (a `resume set` between the copy and the removal) has no deterministic test, because `facts_of` is synchronous and `set_resume` is not. Review checks it, as S19.
- **S17 (a repeat does not save; integration) [D5]:**
  - Given an agent like S1's that sends `resume "echo HI"`, prints `SE""NT`, sleeps 1 s, sends the same `resume "echo HI"` again, prints `AG""AIN` and sleeps 30 s,
  - when `SENT` shows, a saved check passes, and the test keeps the inode of `state.json`,
  - then at `AGAIN`, T's output has a second `ack`, and a no-save check (the same inode 1 s later) passes.
  - Then a second agent, as in S1, sets `resume "echo HO"`, a saved check shows `echo HO`, and the inode now differs from the kept one. This is the control: the inode check can see a save.
  - The no-save check, not a byte compare, is what fails if a repeat saves: a wrong save writes the same bytes.
- **S18 (clear; integration):**
  - Given S1's state, `Resume {T}` from the test process gives `ack`, and a saved check shows no `resume`.
  - A second `Resume {T}` gives `ack`, and a no-save check passes.
- **S19 (the agent exits during a set; review).** The re-check after the change (*Key Components*, step 7) has no deterministic test. Review traces the interleavings with `term_ended`, as 2611.0009 answer 6 did.
- **S20 (offer dropped by any user byte; TarmacKit) [D9]:** For each of these, `ResumeOffer.step(offer, .userInput)` gives `(nil, nil)`, and a following `.returnKey(prime: true)` gives no effect:
  - an offer that is not yet armed;
  - an armed offer on a non-prime card;
  - an armed offer on the prime card, with input `"a"`;
  - an armed offer with an Esc byte.
- **S21 (display never hides a metacharacter; TarmacKit):**
  - `ResumeChip.display("claude --resume 3f2a1b9c-0000-4000-8000-000000000000; curl x|sh")` contains `; curl x|sh` verbatim.
  - `display("rm -rf /Users/u/work/important-directory")` is unchanged: no whole word is id-like.
  - `display("claude --dangerously-skip-permissions --resume 3f2a1b9c-0000-4000-8000-000000000000")` is `claude --dangerously-skip-permissions --resume 3f2a…`: a word that starts with `-` stays whole (RA2).
  - `display("cd important-directory")` is unchanged: a long word from the id set with no digit stays whole (RA2).
- **S22 (session ids; unit, `hooks.rs`) [D8]:**
  - `00000000-0000-0000-0000-000000000000` and `ab_12` give `claude --resume <id>`.
  - `-rf`, `../x`, `a b`, `a;b`, `$(x)`, an empty string, 129 characters, a number and a missing key each give `None`.
- **S23 (a refused id does not connect; CLI test):** The `session-start` fixture with `session_id` set to `a;b` exits 0 with empty stdout, a stderr line, and no connection.
- **S24 (⌘W: the replace rule is unchanged; TarmacKit) [RA1]:** `FocusedClose.decide(kind: .term, otherLiveTerminals: 0)` gives `closeTerminal(replace: true)`, and with 1 and 5 it gives `closeTerminal(replace: false)`. `.doc` gives `.closeDoc` and `.none` gives `.noop`. The `dead` parameter and `signalClose` are gone, so TarmacKit holds no D12 assertion. D12 (⌘W on a dead card sends `TermClose`, and the record goes) is proven by the daemon's `TermClose` test (2611.0007 S26: `TermClose` deletes the record; if that test has no case for an id that is not live, add one in `resume_integration.rs`) and by QA S35. The doc comment at `FocusedClose.swift:30-33` ("the caller must not depend on `TermClose` being a safe no-op") goes with the parameter: `close_term` on an id that is not live only deletes the record (`state.rs:494-500`).
- **S25 (reopen succeeds the dead id; TarmacKit):**
  - Given an offer with `cwd: "/w"` and resume `"echo HI"`,
  - `DeadCardOffer.reopen(offer, deadID: "T")` gives `SpawnRequest(cwd: "/w", succeeds: "T")` and `"echo HI"`.
  - An offer with no cwd gives `SpawnRequest(cwd: nil, succeeds: "T")`.

- **S26 (the dev snapshot; TarmacKit) [D14]:** A terminal with an armed offer is reported with `resume: {cmd, armed: true}`, and one with an offer that is not armed with `armed: false`. A dead card with an offer is reported with `reopen: true`. Others have neither.
- **S27 (Esc meets the toast first; TarmacKit, `KeyLadder` with `EscLadder` facts).** With `toastsShowing: true`, Esc on a terminal gives `.esc(.clearToasts)`, so it does not reach the terminal and does not drop the offer. ### Error Scenarios

- **S28 (daemon refusals; integration):**
  - `Resume` for an id that is not live → `err` `unknown terminal: <id>`.
  - For a live T, each of `"echo a\necho b"`, `"echo \u{1b}[2J"`, `"echo \u{202e}x"`, `""`, `"   "` and 257 `a`s → `err` `resume command refused: <cause>`, and a probe shows no `resume`.
  - The checks run in this order: the term, then the command, then the holder. `Resume` with `"echo a\necho b"` for an id that is not live gives `unknown terminal: <id>`.
- **S28b (no holder; unit, `state/tests/`):** A `TermHandle::detached()` in `terms` (no pid, no leader, as the report tests use):
  - `set_resume(None, T, Some("echo HI"))` gives `err` `no process to tie the resume command to in T`;
  - `set_resume(None, T, Some("echo a\necho b"))` gives `resume command refused: a control character`, which pins the command check before the holder.
- **S29 (CLI usage; CLI test):** These exit 2 with a line on stderr, and the double sees no connection:
  - `tarmac resume`, `resume frob`, `resume set`, `resume set a b`, `resume clear x`;
  - `resume set "a<LF>b"`, `resume set ""`, `resume set "echo <U+202E>x"`, and a 257-character command. Each refused one prints `tarmac: resume command refused: <cause>`.
  - The usage check comes before the term check: `tarmac resume frob` with no `TARMAC_TERM_ID` still exits 2.
- **S30 (CLI failures; CLI test):**
  - No `TARMAC_TERM_ID`, or an empty one → exit 1 with the `needs TARMAC_TERM_ID` line, and no connection.
  - The double answers `err` → `tarmac: <msg>`, exit 1.
  - No daemon → exit 1.
  - A double that never answers → the 5 s no-answer line, exit 1.
- **S31 (the check is the same in both languages; units).** One table of cases runs against `check_resume_cmd` (Rust) and `ResumeCommand.check` (Swift). Each case gives the same accept or refuse in both. It covers each refused class, U+2028 and U+2029 (refused), a 256-character command (accepted) and a CJK path (accepted). It also has a command of 256 scalars that holds combining marks, so it has fewer than 256 graphemes (accepted), and the same command with one more scalar (refused). A grapheme count would accept the second one.

## Trade-offs and Limitations

- **A logout or reboot may lose the offer.** If the agent dies a poll tick before the daemon gets its signal, the record is dropped [D3]. The design's main case, a version-mismatch restart, is safe: the PTYs die after the daemon (D4). See OQ1.
- **Two presses on a dead card.** "Reopen here", then ⏎ on the chip. Each press shows what it does.
- **The first `Output` is not always the prompt.** It can be a login banner, or a question from a shell rc file, such as oh-my-zsh's "update now? [Y/n]". The chip is then armed early, and ⏎ gives the command to whatever reads the line. R4 accepts this. The user sees the screen before pressing ⏎.
- **An offer on a dead card appears only at its board's next restore** when the card died of its own exit [D11]. A dead card from a daemon restart gets it at once, because the reconnect restore carries the table.
- **An undecided chip is lost at an app relaunch.** The term is then live, so it is rebound, not cold-spawned. The daemon still holds the unclaimed record, and the next daemon restart offers it again.
- **The old shell's environment is not restored.** The new shell is a fresh login shell. `claude --resume` runs with the shell's own `PATH` and environment, and the flags of the first launch (`--model` and the like) are not kept.
- **Nested agents.** A `claude` inside a shell inside another `claude` in the same terminal is held by the outer agent (2611.0009 limit). Its `SessionStart` overwrites the outer's command.
- **"Back in their folders" is the request, not an observed fact.** A gone folder falls back to `$HOME` with no error (slice 1). The toast counts spawns that asked for a folder (OQ4).
- **A dead card that an app relaunch drops leaves its record behind.** It stays until a `succeeds` or a `TermClose` names it (slice 1 growth). ⌘W now cleans the visible ones [D12].
- **Esc with a toast showing needs two presses to skip.** The first clears the toasts [D13]. Each other Esc rung that applies (a fly-back, a fresh doc mark) also takes one press first (S27).
- **An older daemon costs each `SessionStart` 500 ms** until the app replaces it.

## Open Questions

- [ ] **OQ1 — Does a logout or a reboot keep the record?** The order in which macOS ends the agent, the shell and the daemon at logout is not verified. If the agent goes first, D3 drops the record. A probe: log the order of `term_ended`, the resume drops and the shutdown signal across one logout of a test user. If the order is wrong, one idea is a grace period: drop only after the shell outlives the agent by one tick. That idea alone is incomplete: D3's drop at the end of a terminal also fires when the shell dies with the agent, so it would need the same guard. Deferred (2026-11-14).
- [x] **OQ2 — Should every dead card offer "reopen here"?** Today an offer needs the board's latest restore [D11]. Two upgrade paths: a push of the record kept at a non-zero exit (a new frame), or the daemon filling `cwd` from the `succeeds` record (a change to slice 1's contract). Deferred (2026-11-14) to the inbox slice, which also needs pushes for dead cards.
- [x] **OQ3 — A time stamp on the record.** `resume: {cmd, at_ms}` would let the tooltip say how old the command is, as the report chip does. Deferred (2026-11-14): it is one more wire key with no rule that uses it yet.
- [x] **OQ4 — The copy "back in their folders".** It counts requests. Kept (2026-11-14): the design's copy stays. A gone folder is rare, and the prompt shows `$HOME` at once.
- [ ] **OQ5 — `codex resume <id>`.** It comes with slice 7, through the same `Resume` frame. No change is needed here.
