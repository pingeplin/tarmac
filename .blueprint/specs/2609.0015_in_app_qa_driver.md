# 2609.0015 In-app QA driver (`tarmac dev`)

**Date:** 2026-09-16
**Status:** draft
**Author:** EP Lin
**Issue:** [#166](https://github.com/pingeplin/tarmac/issues/166) `feat(dev): in-app QA driver so agents can drive and inspect the running app`

## Context

Every interaction fix Tarmac has shipped this quarter ended with a human at the keyboard.
#155 (a `beforeinput` that didn't scroll to bottom), #156 (the keypress dedupe), #157 (mouse
reports) and #162 (keys dropped after a resize press flushed the focused terminal's selection,
fixed in #163) were each *reproduced* and *verified* by hand. The agent that wrote each fix
could not regression-check its own work, for three reasons:

1. **Input never arrives.** macOS synthetic input does not reach the Tarmac window — neither
   computer-use, nor `cliclick`, nor a raw `CGEvent` post. Only `screencapture` works.
2. **The bugs live in the shell, not in `kit/`.** #162's mechanism was `CardShell`'s grip
   `onPointerDown` calling `window.getSelection().removeAllRanges()` while xterm's hidden
   textarea held the page selection (`desktop/src/cards/CardShell.tsx:116-127`). The predicate
   that fixed it (`desktop/src/kit/resizeSelection.ts`, `flushesOnResize`) is unit-tested; the
   pointer handler that calls it is not, by design
   ([`docs/coding-style.md`](../../docs/coding-style.md) §1.2).
3. **Screen-side state is invisible.** Zoom and board rects reach `state.json` through
   `Msg::Layout`, but screen rects, focus, xterm's selection and `document.activeElement` exist
   only inside the webview — and those are exactly what the interaction bugs are about.

The two existing harnesses do not close the gap. `tauri-driver` (WebDriver) supports Linux and
Windows only. `.dev/key-harness/` runs xterm in Playwright WebKit, not in the real Tauri
WKWebView, so it misses compositor and focus behaviour that has already misled us (see
[`docs/coding-style.md`](../../docs/coding-style.md) and the `.dev/` notes). The workable path
is an endpoint **the app itself owns**.

## Motivation

Without this, every agent-authored interaction change ships on a human QA pass, and every
regression check of #155/#156/#157/#162 is a manual replay. With it, those four become a script
that runs in ~10 seconds and fails loudly — and the agent that writes the next `CardShell`
change can prove it did not break typing before it opens the PR.

The cost of not doing it is not hypothetical: #162 shipped in 0.12.1 and was found by a human
using the app, because nothing in `make test` could have caught it.

## Proposed Solution

### Overview

The Tauri app opens a **second Unix socket** — dev builds only — and a new `tarmac dev` verb
family drives it. The CLI connects, sends one length-prefixed MessagePack `DevRequest` frame,
reads one `DevReply { ok, body }` frame, prints `body` verbatim and exits 0 or 1. The CLI never
parses `body`, so it stays std-only.

**Principle: inject events, don't call handlers.** The bugs this exists to catch live in
component pointer handlers, so `resize`, `focus`, `type` and `key` dispatch *real DOM events*
(`PointerEvent`, `MouseEvent`, `KeyboardEvent`) on the *real targets* — the grip element, the
card body, `term.element`, `term.textarea` — and let React and xterm's own listeners run. `type`
is the sharp case: synthesizing `beforeinput` ourselves would *be* calling the handler, and
#162's mechanism is precisely that WebKit declines to fire `beforeinput` on a caret-less
textarea. Printable text therefore goes through `document.execCommand("insertText")` and WebKit
decides. `zoom` is the exception in the other direction: a pure view transform with no cited
bug, so it goes through `BoardEngine.setViewport`, the same commit path the wheel gesture ends
in — which fires `onViewportChange` → `App.tsx`'s `onViewport` → `schedulePersist`, so
`Msg::Layout` still lands.

**`execCommand` is settled, not a risk.** The issue's stage-2 pre-check ran in
`.dev/key-harness` (Playwright WebKit, xterm from `desktop/node_modules`) and is recorded in
[issue #166's comment](https://github.com/pingeplin/tarmac/issues/166#issuecomment):
`execCommand("insertText")` on a **caret-less** textarea fires **no** `beforeinput` and returns
`false`, on both a bare textarea and xterm's helper textarea; a synthetic `beforeinput` fires
regardless of selection state. So `execCommand` reproduces #162's mechanism and a synthetic
`beforeinput` would make the #162 scenarios vacuous. **Plan B is retired; the #162 scenarios
stay in acceptance.** `execCommand`'s `false` return is also a free per-character drop signal,
which the reply body surfaces.

### Key Components

- **`core/crates/tarmac-protocol`** — a new inline `pub mod dev` (beside the existing `pub mod frame`) holding `DevRequest` (one
  variant per verb) and `DevReply { ok: bool, body: String }`, encoded with
  `rmp_serde::to_vec_named` and framed exactly like the main socket. **Not** a `Msg` variant, so
  `Msg`, `docs/protocol.md`, the V1–V13 conformance vectors and docs-check rule 4 stay untouched.
  Also `resolve_dev_socket_path(over, home, channel)` — a sibling of `resolve_socket_path`
  sharing the same `channel_dir`, so the `dev` literal still exists exactly once.
- **`core/crates/tarmac-cli/src/dev.rs`** — the `dev` verb parser and the one-frame round trip.
  `socket_path()`-style wrapper `dev_socket_path()` reads `TARMAC_DEV_SOCKET` through the
  existing `env_override` (empty means unset) and `current_channel()`. The whole module is
  `#[cfg(debug_assertions)]`; in a release build `tarmac dev …` exits 1 with
  `driver unavailable in release builds`.
- **`desktop/src-tauri/src/dev_driver.rs`** — `#[cfg(debug_assertions)]`. Binds the dev socket,
  accepts one request per connection, emits it to the frontend as a Tauri `dev-request` event
  keyed by a request id, and awaits the frontend's `dev_reply` command before writing the
  `DevReply` frame back.
- **`desktop/src/devDriver.ts`** — the frontend shell: `listen("dev-request")`, resolve targets,
  dispatch events, wait, build the snapshot, `invoke("dev_reply", …)`. Untested wiring by
  design; every decision inside it is a `kit/` call.
- **`desktop/src/kit/dev*.ts`** — the decisions, each with a Vitest file:
  `devSnapshot.ts` (snapshot builder + `screen_rect` projection), `devKeyPlan.ts` (combo →
  event sequence), `devTypePlan.ts` (string → per-character step plan), `devUntil.ts` (the
  `--until` expression parser + evaluator), `devRouting.ts` (verb → target + preconditions),
  `devResizeGrip.ts` (board-unit target → grip pointer plan), `devCellPoint.ts` (the
  `contextmenu` click point).
- **`scripts/qa/smoke.mjs`** + a `make qa` target — the end-to-end scenario runner. Not part of
  `make test` or CI: it needs a live `make run` app.

### Data Flow

1. `tarmac dev <verb> …` parses argv into a `DevRequest` (including `until` / `timeout_ms` for
   `snapshot`), resolves `TARMAC_DEV_SOCKET` / `channel_dir(home, Dev)/tarmac-dev.sock`,
   connects, and writes one frame.
2. `dev_driver.rs` decodes the frame, mints a request id, stores a `oneshot::Sender`, and emits
   `dev-request` with `{ id, req }` as JSON.
3. `devDriver.ts` routes the verb through `kit/devRouting.ts`. A precondition failure
   (`no_such_card`, `not_focused`, `unsupported_card_kind`) short-circuits: **no event is
   dispatched**.
4. It dispatches the planned DOM events on the resolved elements, then waits **two animation
   frames**.
5. It builds a snapshot from `kit/devSnapshot.ts`. For `snapshot --until`, it re-evaluates the
   expression every **50 ms** until it holds or `timeout_ms` elapses. (50 ms, not a rAF loop:
   the facts being waited on — a `ResizeObserver` → daemon `Resize` round trip, the daemon's
   750 ms `TermProc` poll, a debounced persist — are all slower than a frame, and a rAF spin
   competes with the very render it is waiting for.)
6. It `invoke("dev_reply", { id, ok, body })`. The backend resolves the `oneshot`, writes the
   `DevReply` frame, and closes.
7. The CLI prints `body` verbatim — stdout when `ok`, stderr when not — and exits 0 or 1.

### Interface Contract

```
tarmac dev snapshot [--until <expr>] [--timeout <ms>]   # default --timeout 5000
tarmac dev zoom <z>
tarmac dev resize <card> <w>x<h>                        # board units, lowercase x
tarmac dev focus <card>|board
tarmac dev type <card> "<text>"
tarmac dev key <card> "<combo>"
```

`<card>` is a terminal's `term_id` or a doc's absolute path — the identifiers the wire protocol
already uses.

**Snapshot schema** (`screen_rect` is CSS px in the `getBoundingClientRect` space; `board_rect`
is board units; active board only; `screen_rect` is `null` for a culled card with no DOM node):

```
{ v: 1, board_id,
  viewport: { zoom, cx, cy, view_rect: {x,y,w,h} },
  cards: [{ id, kind: "term"|"doc", board_rect: {x,y,w,h}, screen_rect: {x,y,w,h}|null, focused,
            term?: { cols, rows, proc: string|null, selection: string|null, scrollback_tail: string } }],
  focused_card: id|null,
  active_element: { card: id|null, tag, classes, selection_type: "None"|"Caret"|"Range" } }
```

`term.proc` is the daemon's last `TermProc` name; `scrollback_tail` is the last 40 lines of the
xterm buffer, newline-joined. Both exist so a scenario can read OS facts through the snapshot
alone. A doc card carries **no** `term` key at all.

**`--until` grammar:** `<path> <op> <value>`, with `op` ∈ `==`, `!=`, `~=` (numeric, |Δ| ≤ 1),
`contains`. `<path>` is dotted; `cards[<id>]` indexes by card id, where the id runs to the
**last** `]` in the remainder of the path (doc paths contain dots, slashes, and may contain
`]`). `<value>` is a number, a double-quoted string (`\"` and `\\` escapes), `null`, `true` or
`false`. An **unresolvable path evaluates to `false`** so polling continues; a **malformed
expression is an immediate error**, not a spent timeout.

**Reply bodies.** `body` is always JSON. On success:

```
snapshot → the snapshot object
zoom     → { "zoom": 0.5 }
focus    → { "focused_card": "t-1", "active_element": { … } }
resize   → { "from": {w,h}, "to": {w,h}, "delta_px": {dx,dy} }
type     → { "chars": 5, "inserted": 4, "dropped": [ { "index": 2, "char": "b" } ] }
key      → { "combo": "ctrl+c", "events": ["keydown","keyup"] }
```

On failure, `ok` is `false` and `body` is `{ "error": "<code>", "message": "<human>", … }` with
codes `no_such_card`, `not_focused`, `unsupported_card_kind`, `unsupported_combo`, `bad_combo`,
`bad_expr`, `empty_buffer`, `timeout` (which also carries `expr`, `timeout_ms` and the final
`snapshot`), `app_not_ready`, `app_unresponsive`.

**CLI-originated errors stay plain text**, one line on stderr, matching `tarmac open`:
`driver unavailable in release builds`, `no tarmac app driver at <path>`, and the
`check_socket_path_len` message. Only *app*-originated errors are JSON.

### Staging

The issue asks for two stages, and they are separable: **Stage 1** is the endpoint plus
`snapshot`, `zoom` and `focus`; **Stage 2** adds `resize`, `type` and `key`. Every scenario
below is tagged `[1]` or `[2]`. Stage 1 is independently verifiable (S1–S8, S25–S42 for the
`focus`/`zoom`/`snapshot` rows, S45–S70, D1, D2, D8, D9a, Q1) and can land as its own PR.

## Decisions this spec makes beyond the issue

These are the points the issue left open or under-specified. Each is resolved here with its
reason, so the gate can push back on a specific call rather than on the whole design.

1. **The bracketing keydown/keyup for a printable character carry
   `key: "Unidentified", keyCode: 0`** — not the character's real key/keyCode.
   *Why:* if the bracketing keydown carried a real printable keyCode, xterm's key evaluator
   could deliver the character itself, and `type` would still work with the caret flushed —
   which would make the #162 scenarios (D4/D5) and their knockout (Q2) **vacuous**. With
   `Unidentified`/0, `execCommand` is provably the only delivery path. D6 is the end-to-end
   guard: `printf <sentinel>` must echo the sentinel *once*, not doubled.
2. **`ok: false` bodies are JSON with an `error` code**, rather than the issue's bare strings.
   *Why:* the scenario runner already parses `snapshot` output; a bare line forces it to
   string-match, and `timeout` needs to carry the final snapshot anyway. The issue's strings
   survive as the codes (`no such card` → `no_such_card`).
3. **`ok: false` bodies go to stderr, success bodies to stdout.** *Why:* `dev snapshot | jq`
   must not be fed an error object.
4. **`type` reports dropped characters but still exits 0.** *Why:* the driver reports facts and
   does not judge. D4 asserts both the scrollback *and* `dropped == []`, which is strictly
   stronger than an exit code.
5. **`focus <doc-card>` is an explicit `unsupported_card_kind` error**, not a silent no-op.
   A doc card has no focus target an untrusted `mousedown` would reach.
6. **`key <card> "cmd+c"` / `"meta+v"` is an explicit `unsupported_combo` error.** *Why:* those
   rely on WebKit's native Edit-menu action, which untrusted dispatched events never trigger; a
   silently-no-op verb would let a scenario claim a copy happened.
7. **A live sibling dev socket is never unlinked *and* never taken over.** The app logs one line
   and opens no dev endpoint. *Why:* the daemon's rule is "exit 1" (`docs/protocol.md:28-30`),
   which would be wrong here — killing the window over a dev nicety.
8. **`--until` polls at 50 ms** (see Data Flow step 5).
9. **`README.md` is deliberately not updated.** Its CLI verb list is user-facing and `dev` is a
   debug-build-only family. `CLAUDE.md` and `docs/architecture.md` are, because they are the
   agent-facing and engineering docs. `SKILL.md` is not updated for the same reason the issue
   gives: it ships into every agent's skills directory.

## Verified starting facts

Checked against `main` @ `9c2ba07` before this spec was written. Three of them contradict the
issue's wording and the implementation must follow the tree, not the issue:

- **The bottom-right grip is `br`, not `se`.** `Handle = Corner | Edge`,
  `Corner = "tl"|"tr"|"bl"|"br"` (`desktop/src/kit/resize.ts:11-13`); the DOM class is
  `card-handle br` (`desktop/src/cards/CardShell.tsx:196-203`). Nothing in the repo is named
  `se`. Every scenario below says `br`.
- **Vitest runs `environment: "node"` with no jsdom** (`desktop/vitest.config.ts`), and
  `include` is `src/**/*.test.ts` only. So a `kit/` module *cannot* construct a real
  `KeyboardEvent`/`PointerEvent` — and must not: the kit functions return **event-init
  descriptors** (plain `{ kind, type, init }` data) and `devDriver.ts` constructs and dispatches
  the real events. This also makes "the snapshot builder never reaches `document`" automatic
  rather than aspirational: `document` does not exist in that environment, so a builder that
  touched it would throw.
- **The term handle widening is type-level only.** `TerminalCard.tsx:277` already passes the
  whole xterm `Terminal` (`onRegister?.(model.termId, term)`); `App.tsx:268` merely *types* the
  map as `{ focus(): void; input(data: string): void }`. `.element` and `.textarea` are already
  present at runtime. Widening the declared type is the entire change — do **not** add a
  `data-term-id` attribute or restructure the registry.

Also confirmed, and relied on below: `resolve_socket_path` / `channel_dir` / `Channel`
(`core/crates/tarmac-protocol/src/lib.rs:331-375`); three `socket_path()` copies
(`tarmacd/src/main.rs:31`, `tarmac-cli/src/main.rs:61`, `bridge.rs:516` — CLAUDE.md:62 names
only two and is the stale line the issue asks to fix); `tarmac-protocol` is a **single
`lib.rs`** whose only submodule is the inline `pub mod frame` at `:411`, so `dev` should be an
inline `pub mod dev` beside it; `desktop/src-tauri/` has **no `UnixListener` anywhere** — the
only bind/stale-replacement precedent in the repo is `core/crates/tarmacd/src/main.rs:88` and
its `claim_socket`; `core/crates/tarmac-cli/tests/version.rs:59` already stands up a fake
`UnixListener` peer and is the pattern the dev round-trip tests should copy;
`docs/coding-style.md:186-200` already bans `any` in `kit/` and forbids `kit/` importing React
or `@tauri-apps`; `.blueprint/specs/*.md` is **not** scanned by `make docs-check` (only
`docs/**`, `README.md`, `CLAUDE.md` are), but `.blueprint/` *is* on its cited-path allow-list,
so a `CLAUDE.md` line naming `scripts/qa/smoke.mjs` fails `docs-check` until that file exists —
docs land **with** the code, never ahead of it.

## Acceptance Scenarios

Three tiers, because they are checked by three different things:

- **`[S]` automated, in `make test`** — Vitest (`desktop/src/kit/`) and `cargo test`. These are
  what `/verify`'s referee runs.
- **`[D]` automated, in `make qa`** — `scripts/qa/smoke.mjs` against a live `make run` app. Not
  in `make test` or CI. These are the issue's acceptance boxes, and they are the *point* of the
  feature: the driver's first customer is its own scenario suite.
- **`[Q]` hand-run** — recorded in `desktop/qa/qa-driver-qa.md`, per
  `docs/coding-style.md`'s rule that spec-driven manual scenarios live there.

Each carries its stage: `[1]` endpoint + `snapshot`/`zoom`/`focus`, `[2]` `resize`/`type`/`key`.

### Snapshot builder — `desktop/src/kit/devSnapshot.ts` [S]

- **S1 [1]:** Given a viewport, a card list and a map of measured screen rects, when the builder
  runs, then it returns `{ v: 1, board_id, viewport: { zoom, cx, cy, view_rect }, cards,
  focused_card, active_element }` with those exact key names. The test file runs in Vitest's
  default `node` environment, so a builder that read `document` would throw rather than pass —
  the purity requirement is enforced by the environment, not by inspection.
- **S2 [1]:** Given one `term` card and one `doc` card, when the snapshot is
  `JSON.stringify`-ed, then the term card's object has a `term` sub-object with
  `cols, rows, proc, selection, scrollback_tail`, and the doc card's object contains **no `term`
  key at all** (`"term" in card === false` — not `term: undefined`, which `JSON.stringify` would
  drop but `--until` would then read as a silent `false`).
- **S3 [1]:** Given a card with no measured DOM node (culled), when the snapshot is built, then
  its `screen_rect` is `null` and its `board_rect` is still the card's frame — a culled card is
  reported as unmeasured, never as absent and never as `{0,0,0,0}`.
- **S4 [1]:** Given a terminal buffer of 100 lines, when the snapshot is built, then
  `scrollback_tail` is the last 40 lines newline-joined and its first line is buffer line 61;
  given a buffer of 5 lines, it is those 5 lines with no blank padding.
- **S5 [1]:** Given a terminal for which the daemon has reported no `TermProc`, then `term.proc`
  is `null`; given a terminal with no selection, `term.selection` is `null` — not `""`, which
  `contains ""` would match vacuously.
- **S6 [1]:** Given cards belonging to two boards, when the snapshot is built for the active
  board, then only the active board's card ids appear.
- **S7 [1]:** Given a `board_rect`, a viewport and a `view_rect` with a **non-zero** `x`/`y`,
  when `boardRectToScreenRect` projects it, then both corners equal
  `worldToView(corner, zoom, {x: cx, y: cy}, {x: view_rect.x + view_rect.w/2,
  y: view_rect.y + view_rect.h/2})` at zoom `0.5`, `1` and `2.37`. The non-zero origin is the
  load-bearing part: a projection that drops `view_rect.x/y` passes at origin `(0,0)` and fails
  here, which is exactly the mistake `worldToView`'s `viewportCenter`-not-rect signature invites.
- **S8 [1]:** Given zoom 1 and `cx,cy` equal to the `view_rect` midpoint in board units, then a
  board rect projects to itself translated by the `view_rect` origin, and `w`/`h` are unchanged
  — the identity case, which pins that zoom is applied to the size and not only to the origin.

### Key-combo planning — `desktop/src/kit/devKeyPlan.ts` [S]

Each plan is a list of `{ type, init }` descriptors; `devDriver.ts` turns them into
`KeyboardEvent`s on `term.textarea`.

- **S9 [2]:** `"enter"` → `[keydown, keypress, keyup]`, each with
  `{ key: "Enter", code: "Enter", keyCode: 13, which: 13 }`.
- **S10 [2]:** `"ctrl+c"` → `[keydown, keyup]` and **no `keypress`**, with
  `{ key: "c", ctrlKey: true, keyCode: 67 }`. A plan that emitted `keypress` here would feed
  #156's dedupe a sequence WebKit never produces, making any future regression test of it lie.
- **S11 [2]:** `"shift+enter"` → `shiftKey: true` on all three events, `keypress` present.
- **S12 [2]:** `"escape"` → `[keydown, keyup]`, `keyCode: 27`, no `keypress`.
- **S13 [2]:** For every combo the parser accepts, every descriptor has `keyCode === which` and
  `bubbles: true, cancelable: true` — React listens at the root and xterm's evaluator reads
  `keyCode`, so a descriptor missing either is inert in the app while still "passing" a
  shallower test.
- **S14 [2]:** `"cmd+c"` and `"meta+v"` → `{ error: "unsupported_combo" }` whose message names
  WebKit's native Edit-menu action as the reason, and an **empty** event list. A silent no-op
  would let a scenario assert a copy that never happened.
- **S15 [2]:** `"ctrl+"`, `""` and `"frobnicate"` → `{ error: "bad_combo" }`, empty event list.
- **S16 [2]:** `"contextmenu"` is not a keyboard plan: it returns a mouse descriptor
  `{ target: "term-element", type: "contextmenu", init: { button: 2, buttons: 2, bubbles: true,
  cancelable: true, clientX, clientY } }`.

### Right-click point — `desktop/src/kit/devCellPoint.ts` [S]

- **S17 [2]:** Given buffer rows where the last non-empty row is index 7 holding 9 non-blank
  cells, an element rect and a cell size, then the point is the centre of cell `(8, 7)`. An
  off-by-one in either axis lands in a neighbouring cell, so the assertion is on the exact
  centre, not on a range.
- **S18 [2]:** Given an entirely empty buffer, then `{ error: "empty_buffer" }` — a right-click
  on blank space produces a `Caret`, not a `Range`, which would silently downgrade D5 into a
  second copy of D4.

### Type planning — `desktop/src/kit/devTypePlan.ts` [S]

- **S19 [2]:** `"ab"` → two `insertText` steps, each bracketed by a keydown and a keyup whose
  descriptors carry `key: "Unidentified", keyCode: 0`. **This is the anti-vacuity mechanism:**
  with a real printable `keyCode`, xterm's own key evaluator could deliver the character, `type`
  would keep working with the caret flushed, and D4/D5/Q2 would all pass for the wrong reason.
- **S20 [2]:** `"\n"` → a single key-event step for Enter (the S9 plan), and **no** `insertText`
  step.
- **S21 [2]:** `"\t"` → a key-event step for Tab (`keyCode: 9`), no `insertText`.
- **S22 [2]:** `"\x03"` → the `ctrl+c` key-event step (the S10 plan), no `insertText`.
- **S23 [2]:** `"a\nb"` → exactly three steps in that order: insert, Enter, insert.
- **S24 [2]:** A non-ASCII printable (`"中"`) → an `insertText` step carrying that character,
  still bracketed by `Unidentified`/0 key events — the same rule as S19, stated for the case
  where "the character's keyCode" has no meaning at all.

### `--until` expressions — `desktop/src/kit/devUntil.ts` [S]

- **S25 [1]:** `viewport.zoom == 0.5` is true against a snapshot with `zoom: 0.5` and false
  against one with `zoom: 1`.
- **S26 [1]:** `cards[t-1].board_rect.w ~= 800` is true at `799.4` and `800.9`, false at `798.9`
  and `801.5` — pinning `|Δ| ≤ 1` at both edges, so a `< 1` or `≤ 2` implementation fails.
- **S27 [1]:** `cards[/Users/e/a.b.md].focused == true` resolves — a naive split on `.` would
  fail on the doc path, which is the whole reason the grammar brackets the id.
- **S28 [1]:** `cards[/tmp/a]b.md].kind == "doc"` resolves to the card whose id is
  `/tmp/a]b.md` — the id runs to the **last** `]`, not the first.
- **S29 [1]:** `cards[t-1].term.scrollback_tail contains "hi"` is true when the tail holds `hi`
  and false otherwise.
- **S30 [1]:** `!=` works against a string and against `null`
  (`cards[t-1].term.proc != null` is true when `proc` is `"sleep"`).
- **S31 [1]:** A path that does not resolve — unknown card id, or a missing key — evaluates to
  **false**, not an error, so a card that has not rendered yet keeps polling instead of failing
  the run.
- **S32 [1]:** `contains` whose left side is a number or `null` evaluates to false and does not
  throw.
- **S33 [1]:** A malformed expression (`viewport.zoom =! 0.5`, an unterminated quote, an empty
  string) returns a **parse error**, distinguishable from `false` — the app replies `bad_expr`
  immediately instead of spending the full timeout on an expression that can never hold.
- **S34 [1]:** Values parse as their types: `0.5`, `-1`, `"a \"quoted\" \\ path"`, `null`,
  `true`, `false`.

### Verb routing and preconditions — `desktop/src/kit/devRouting.ts` [S]

- **S35 [1]:** `focus <term>` plans, in order, a `pointerdown`+`pointerup` on target
  `card-body` and a `mousedown`+`mouseup` on target `term-element`. Both halves are required:
  `CardShell`'s body `onPointerDown` only raises the card, and xterm focuses its textarea from
  its own `mousedown` listener.
- **S36 [1]:** `focus board` plans one `pointerdown` on target `board-viewport`. `Board.tsx:157`
  gates on `e.target === viewportRef.current || e.target === cardLayerRef.current`, so the event
  must be dispatched **on** that node — an event bubbling up from a descendant never satisfies
  it and the blur branch silently never runs.
- **S37 [2]:** `type` and `key` target `term-textarea`.
- **S38 [2]:** `resize` targets `card-handle-br` — the `.card-handle.br` element of that card.
- **S39 [1]:** An unknown `<card>` returns `{ error: "no_such_card" }` with an **empty** plan,
  for every verb that takes a card.
- **S40 [2]:** `type`/`key` where `active_element.card !== <card>` returns
  `{ error: "not_focused" }` with an empty plan — the precondition is evaluated before any event
  is planned, so a passing `type` proves focus was already correct rather than establishing it.
- **S41 [1]:** `focus <doc-card>` returns `{ error: "unsupported_card_kind" }`.
- **S42 [1]:** `zoom` returns a viewport-commit plan with no element target — it goes through
  `BoardEngine.setViewport`, not through a dispatched event.

### Resize grip plan — `desktop/src/kit/devResizeGrip.ts` [S]

- **S43 [2]:** `gripDelta({ w: 600, h: 400 }, { w: 800, h: 600 }, 0.5)` is `{ dx: 100, dy: 100 }`
  — board-unit deltas scaled **into** screen px. A plan that omits `zoom` returns `200` and
  fails; `CardShell.onHandlePointerMove` divides by `getZoom()`, so the driver must multiply.
- **S44 [2]:** The plan is `[pointerdown at the grip centre, pointermove at centre+delta,
  pointerup at centre+delta]`, all three on the **same grip element**, with
  `pointerId: 1, pointerType: "mouse", isPrimary: true, button: 0`, `buttons: 1` on down and
  move, `buttons: 0` on up, and `bubbles`/`cancelable` true. Dispatching all three on the grip
  is what makes the missing pointer capture harmless: `CardShell` wires `onPointerMove`/`Up` on
  the handle element itself (`CardShell.tsx:199-202`), so capture is only ever needed for a real
  pointer that leaves the element.

### End-to-end driver scenarios — `scripts/qa/smoke.mjs`, run by `make qa` [D]

These are the issue's acceptance boxes. They need a live `make run` app, so they are **not** in
`make test` and **not** on CI. `make qa` exits non-zero with a message telling you to
`make run` if it cannot reach the dev socket.

**Hygiene, binding on every scenario below:** each one starts with `focus board` then
`focus <term>` — per #162, `focus()` on an already-focused textarea does not restore the caret,
so a blur is the only clean reset — and each uses its **own sentinel string**, minted from a
per-run nonce. `scrollback_tail` spans 40 lines, so an earlier scenario's echo would satisfy a
repeated `contains` and turn a later scenario green without doing anything. The runner asserts
sentinel uniqueness across the run and fails if two scenarios collide.

- **D1 [1] — projection:** `snapshot` at zoom 1, then at zoom 1.7. In both, every card with a
  non-null `screen_rect` matches its `board_rect` projected through `viewport` (S7's function)
  within **±1 px**. The tolerance is real and bounded: `desktop/src/kit/docZoom.ts:64` rounds the
  wrapper translate to `var(--device-px)`, so the painted position differs from the exact
  projection by at most half a device pixel.
- **D2 [1] — zoom persists as an OS fact:** record `.dev/state.json`'s mtime; `dev zoom 0.5`;
  `snapshot --until 'viewport.zoom == 0.5'` exits 0; then poll the file **shell-side** until its
  mtime advances and its active board's `zoom` reads `0.5`. The persist is debounced 200 ms in
  `App.tsx`, so the wait is on the file, not on `--until`.
- **D3 [2] — resize reaches the PTY's winsize:** `zoom 1`; `focus board`; `focus <term>`;
  `resize <term> 600x400` (pinning zoom and start size so the grip delta is exact); read `cols0`
  from a snapshot; `resize <term> 800x600`;
  `snapshot --until 'cards[<term>].board_rect.w ~= 800'`;
  `snapshot --until 'cards[<term>].term.cols != <cols0>'` (the frame settles before xterm refits
  and the daemon `Resize` lands, so the two waits are separate); `type <term> "stty size\n"`;
  `snapshot --until 'cards[<term>].term.scrollback_tail contains "<rows> <cols>"'` using the
  `rows`/`cols` from that same snapshot. The last step is the OS fact: the PTY winsize changed.
- **D4 [2] — #162 regression, caret variant:** `focus board`; `focus <term>`;
  `type <term> "<sentinel>a"`; `resize <term> 700x500`; `type <term> "b\n"`;
  `snapshot --until 'cards[<term>].term.scrollback_tail contains "<sentinel>ab"'`. **No focus
  round-trip anywhere between**, and both `type` replies must report `dropped: []`. This is
  issue #162's own repro.
- **D5 [2] — #162 regression, Range variant:** `focus board`; `focus <term>`;
  `type <term> "echo <sentinel>\n"`; `key <term> contextmenu`; `snapshot` asserts
  `active_element.selection_type == "Range"` and **fails the run** if it is `Caret` — an empty
  right-click degrades to a caret and would silently re-run D4 under a different name;
  `resize <term> 720x520`; `type <term> "a"`; `type <term> "b\n"`; tail contains `ab`. This is
  the branch `flushesOnResize`'s `Range` + `TEXTAREA` case was written for.
- **D6 [2] — bytes reach the PTY, exactly once:** `focus board`; `focus <term>`;
  `type <term> "printf <sentinel>\n"`; the tail contains `<sentinel>` and **not** its
  character-doubled form. The doubling check is the end-to-end guard on S19's
  `Unidentified`/`keyCode: 0` bracket: if the keydown also delivered the character, the echo
  would show each character twice and every #162 scenario would be vacuous. Scroll-to-bottom
  (#155) is deliberately **not** asserted — no verb scrolls the viewport, so it would hold
  trivially.
- **D7 [2] — foreground process, both directions:** `focus board`; `focus <term>`;
  `type <term> "sleep 100\n"`; `snapshot --until 'cards[<term>].term.proc == "sleep"'` (the
  daemon polls `TermProc` at 750 ms, so the wait is required); `key <term> "ctrl+c"`;
  `snapshot --until 'cards[<term>].term.proc != "sleep"' --timeout 3000`. The OS fact is that
  the foreground process changed, twice.
- **D8 [1] — focus and blur:** `focus <term>` → `focused_card == <term>`,
  `active_element.card == <term>`, `active_element.tag == "TEXTAREA"`; then `focus board` →
  `active_element.card == null`. Terminal cards only (S41).
- **D9 [1/2] — the failure paths are reachable:** (a) `dev type <unknown> "x"` exits 1 with
  `no_such_card`; (b) `snapshot --until 'viewport.zoom == 99' --timeout 300` exits 1 with
  `timeout`, and the body carries the final snapshot; (c) **[2]** after `focus board`,
  `dev type <term> "<sentinel>"` exits 1 with `not_focused` **and** the tail never gains that
  sentinel — proving the precondition ran before any event was dispatched, not after.

> **Your job:** make every `[S]` scenario pass with tests that would *fail if the behaviour were

Repo-specific constraints that override any general instinct:

- **Do NOT run `cargo fmt`** on the Rust crates — local rustfmt disagrees with the whole
  committed repo. Match surrounding style by hand.
- **Do NOT add a `Msg` variant.** `DevRequest`/`DevReply` live in a new inline `pub mod dev`
  beside the existing `pub mod frame` in `core/crates/tarmac-protocol/src/lib.rs`. Encode with
  `rmp_serde::to_vec_named`. Do not touch the V1–V13 conformance vectors, `docs/protocol.md`'s

- **`kit/` rules are already law** (`docs/coding-style.md:186-200`): no React or `@tauri-apps`
  import, no `any`, world by argument, paired `.test.ts`. Vitest has **no DOM** — kit modules

- **Never `pkill tarmacd`.** `make run` pins `TARMAC_SOCKET`/`TARMAC_STATE` under
  `$(ROOT)/.dev/`; `make kill-daemon` is socket-scoped and is the only safe stop.
- **`make qa` pins `TARMAC_DEV_SOCKET` under `$(ROOT)/.dev/` exactly as `make run` pins the
  other two, and `make run` pins it too** — otherwise a second worktree's app answers.
- **Two production-code changes are in scope and nothing else is.** Call both out in the PR
  body:
  1. `CardShell.tsx`: guard `setPointerCapture` (`:124`) and `releasePointerCapture` (`:138`) in
     `try`/`catch`. An untrusted synthetic `PointerEvent` has no active pointer, so
     `setPointerCapture` throws `NotFoundError` and the resize never starts. No behaviour change
     for a real pointer. This is exception 2 (thin wiring): its discharge is D3 passing.
  2. `App.tsx:268` + `TerminalCard.tsx:86`: widen the declared handle **type** so `.element` and
     `.textarea` are visible. The runtime value is already the whole `Terminal`
     (`TerminalCard.tsx:277`) — do not add `data-term-id`, do not restructure the registry.
- **Docs land with the code, not before it.** `docs-check` rule 3 resolves backticked paths in
  `CLAUDE.md`/`docs/architecture.md`, and `.blueprint/` and `scripts/` are both on its

- **Crib the listener from `core/crates/tarmacd/src/main.rs:88` and its `claim_socket`** — the

  `core/crates/tarmac-cli/tests/version.rs:59`.
- **`make test` must pass before the PR**, and `make qa` must pass against a live `make run`.

Write tests to the project's conventions and these principles:

- **Behavioural over structural** — assert the dispatched plan and the observed snapshot, not
  the shape of an internal helper.
- **Every test can fail** — sentinel strings are per-run and unlike any shell output; the

- **Deterministic, isolated, readable** — each fake socket test binds its own scratch path; each

## Alternatives Considered

### `tauri-driver` / WebDriver

The official answer, and it would give a real automation protocol for free. Rejected because it
supports Linux and Windows only — there is no macOS WKWebView driver, and Tarmac is macOS-only.

### Extend the Playwright WebKit harness in `.dev/key-harness/`

Already exists and already found #162's mechanism. Rejected as the *shipping* answer because it
runs xterm in Playwright's WebKit, not in the real Tauri WKWebView, so it misses compositor,
focus and IME behaviour that has already misled this repo. It stays as the unit-level
complement — it is where a hypothesis gets cheap, and where the `execCommand` pre-check ran.

### Call the component handlers directly (expose a test API on `window`)

Far less code. Rejected because it tests the wrong thing: #162 lived *in* `CardShell`'s pointer
handler, and #155/#156 live in the browser's own event dispatch. A driver that calls handlers
can never catch the class of bug it exists for.

### Add `dev` verbs to the daemon socket instead of a second socket

No new endpoint, no new resolver. Rejected: the daemon owns PTYs and files and knows nothing
about screen rects, focus or selection — it would have to proxy every request to the app anyway
— and it would put a debug-only surface on the release wire contract, where the additive-only
rule makes it permanent.

### Screenshot-based assertions

`screencapture -l <windowid>` already works with no human. Rejected as the *primary* mechanism:
a pixel diff cannot tell you `activeElement` is the textarea or that the selection is a `Range`,
which is what every bug on the list turned on. Screenshots stay available to a scenario that
wants one.

## Security Considerations

The endpoint executes UI actions on request, so it is treated as debug-only machinery:

- The whole module is behind `#[cfg(debug_assertions)]` on **both** ends, and the predicate is
  the same one the audited channel mapping uses (S65), so a release build has no listener and a
  release CLI has no verb (Q1).
- The socket is mode `0600` under the user's own `channel_dir` (S66), so it is reachable only by
  the user already running the app.
- It accepts no code: every verb is a fixed enum variant with typed arguments. `--until`
  expressions are evaluated by a hand-written parser over the snapshot object (S25–S34), never
  by `eval`.
- A live sibling socket is never unlinked or taken over (S67), so one worktree's driver cannot
  reach another worktree's app.

## Trade-offs and Limitations

- **`make qa` is not CI.** The `[D]` scenarios are the ones that prove the feature works, and no
  automated gate runs them — they need a window. The mitigation is that they are one command and
  fast; the residual risk is that someone lands a `CardShell` change without running them.
- **`type` cannot drive ⌘C / ⌘V** (S14). Those depend on WebKit's native Edit-menu action, which
  untrusted dispatched events never trigger. Clipboard behaviour stays a hand check.
- **`focus <term>` has a side effect on mouse-reporting programs** (Q3): xterm's `mousedown`
  handler sends a button-press report to the PTY. Real clicks do this too, so it is faithful
  rather than wrong — but a scenario's `scrollback_tail` assertions must tolerate it.
- **The driver is one production-code change away from being free** — the pointer-capture guard.
  It is behaviour-neutral for real pointers, but it *is* production code changed for a test
  affordance, and that is called out rather than hidden.
- **Doc cards are drive-only, not type-able.** `focus` rejects them (S41) and there is no doc
  typing verb; doc cards are read-only today, so there is nothing to type into.
- **Deliberately out of scope**, each worth its own issue if wanted: `move`/`pan`;
  `reset --fixture` (needs a daemon protocol addition or a `TARMAC_STATE` restart);
  `events --follow` (needs a daemon-frame tap in `bridge.rs`); screenshots (already available
  via `screencapture`); zoom via wheel-event injection.
- **A second listener is a second thing that can leak a socket file.** S67/S68 bound it, but the
  failure mode — a stale `tarmac-dev.sock` after a hard kill — is real and is handled by the
  connect-then-replace rule rather than by never happening.

## Open Questions

- [x] **RESOLVED — `execCommand("insertText")` reproduces #162's mechanism.** The pre-check ran
      in `.dev/key-harness` (Playwright WebKit, xterm from `desktop/node_modules`): on a
      caret-less textarea `execCommand` fires **no** `beforeinput` and returns `false`, while a
      synthetic `beforeinput` fires regardless of selection state. Plan B (drop the #162 boxes)
      is retired; D4/D5 stay in acceptance and `type` reports `execCommand`'s `false` as a
      dropped character.
- [x] **RESOLVED — the bracketing key events must be inert.** With a real printable `keyCode`,
      xterm's own evaluator could deliver the character and make D4/D5/Q2 vacuous. The plan uses
      `key: "Unidentified", keyCode: 0` (S19, S24); D6's no-doubling assertion and Q2's knockout
      are the two independent guards.
- [ ] Should `make qa` be able to **start** the app itself (spawn `make run`, wait for the
      socket, tear down)? It would make the suite one command from cold. Out of scope here: it
      needs a headless-window story and would make a failing scenario much harder to inspect,
      since the window would be gone. Revisit once the scenarios have some mileage.
- [ ] `--until` polls at 50 ms with a 5000 ms default. If D7's `TermProc` wait (750 ms poll)
      turns out to dominate the suite's wall clock, consider a per-verb default rather than one
      global one. Not worth pre-optimising.
