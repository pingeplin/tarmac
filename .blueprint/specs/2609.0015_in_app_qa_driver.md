## Context

Every interaction fix Tarmac has shipped this quarter ended with a human at the keyboard.
#155 (a `beforeinput` that didn't scroll to bottom), #156 (the keypress dedupe), #157 (mouse
reports) and #162 (keys dropped after a resize press flushed the focused terminal's selection,
fixed in #163) were each *reproduced* and *verified* by hand. The agent that wrote each fix
could not regression-check its own work, for three reasons:

1. **Input never arrives.** macOS synthetic input does not reach the Tarmac window — neither
   computer-use, nor `cliclick`, nor a raw `CGEvent` post. Only `screencapture` works.
2. **The bugs live in the shell, not in `kit/`.** #162's mechanism was `CardShell`'s grip
   `onPointerDown` calling `window.getSelection().removeAllRanges()` while xterm's hidden
   textarea held the page selection (`desktop/src/cards/CardShell.tsx:116-127`). The predicate
   that fixed it (`desktop/src/kit/resizeSelection.ts`, `flushesOnResize`) is unit-tested; the
   pointer handler that calls it is not, by design
   ([`docs/coding-style.md`](../../docs/coding-style.md) §1.2).
3. **Screen-side state is invisible.** Zoom and board rects reach `state.json` through
   `Msg::Layout`, but screen rects, focus, xterm's selection and `document.activeElement` exist
   only inside the webview — and those are exactly what the interaction bugs are about.

The two existing harnesses do not close the gap. `tauri-driver` (WebDriver) supports Linux and
Windows only. `.dev/key-harness/` runs xterm in Playwright WebKit, not in the real Tauri
WKWebView, so it misses compositor and focus behaviour that has already misled us (see
[`docs/coding-style.md`](../../docs/coding-style.md) and the `.dev/` notes). The workable path
is an endpoint **the app itself owns**.

## Motivation

Without this, every agent-authored interaction change ships on a human QA pass, and every
regression check of #155/#156/#157/#162 is a manual replay. With it, those four become a script
that runs in ~10 seconds and fails loudly — and the agent that writes the next `CardShell`
change can prove it did not break typing before it opens the PR.

The cost of not doing it is not hypothetical: #162 shipped in 0.12.1 and was found by a human
using the app, because nothing in `make test` could have caught it.

## Proposed Solution

### Overview

The Tauri app opens a **second Unix socket** — dev builds only — and a new `tarmac dev` verb
family drives it. The CLI connects, sends one length-prefixed MessagePack `DevRequest` frame,
reads one `DevReply { ok, body }` frame, prints `body` verbatim and exits 0 or 1. The CLI never
parses `body`, so it stays std-only.

**Principle: inject events, don't call handlers.** The bugs this exists to catch live in
component pointer handlers, so `resize`, `focus`, `type` and `key` dispatch *real DOM events*
(`PointerEvent`, `MouseEvent`, `KeyboardEvent`) on the *real targets* — the grip element, the
card body, `term.element`, `term.textarea` — and let React and xterm's own listeners run. `type`
is the sharp case: synthesizing `beforeinput` ourselves would *be* calling the handler, and
#162's mechanism is precisely that WebKit declines to fire `beforeinput` on a caret-less
textarea. Printable text therefore goes through `document.execCommand("insertText")` and WebKit
decides. `zoom` is the exception in the other direction: a pure view transform with no cited
bug, so it goes through `BoardEngine.setViewport`, the same commit path the wheel gesture ends
in — which fires `onViewportChange` → `App.tsx`'s `onViewport` → `schedulePersist`, so
`Msg::Layout` still lands.

**`execCommand` is settled, not a risk.** The issue's stage-2 pre-check ran in
`.dev/key-harness` (Playwright WebKit, xterm from `desktop/node_modules`) and is recorded in
[issue #166's comment](https://github.com/pingeplin/tarmac/issues/166#issuecomment):
`execCommand("insertText")` on a **caret-less** textarea fires **no** `beforeinput` and returns
`false`, on both a bare textarea and xterm's helper textarea; a synthetic `beforeinput` fires
regardless of selection state. So `execCommand` reproduces #162's mechanism and a synthetic
`beforeinput` would make the #162 scenarios vacuous. **Plan B is retired; the #162 scenarios
stay in acceptance.** `execCommand`'s `false` return is also a free per-character drop signal,
which the reply body surfaces.

### Key Components

- **`core/crates/tarmac-protocol`** — a new inline `pub mod dev` (beside the existing `pub mod frame`) holding `DevRequest` (one
  variant per verb) and `DevReply { ok: bool, body: String }`, encoded with
  `rmp_serde::to_vec_named` and tagged the way `Msg` is —
  `#[serde(tag = "t", rename_all = "snake_case")]` (`lib.rs:11-12`), so a frame is a map whose
  `"t"` key names the verb — and framed exactly like the main socket. **Not** a `Msg` variant, so
  `Msg`, `docs/protocol.md`, the V1–V13 conformance vectors and docs-check rule 4 stay untouched.
  Also `resolve_dev_socket_path(over, home, channel)` — a sibling of `resolve_socket_path`
  sharing the same `channel_dir`, so the `dev` literal still exists exactly once.
- **`core/crates/tarmac-cli/src/dev.rs`** — the `dev` verb parser and the one-frame round trip.
  `socket_path()`-style wrapper `dev_socket_path()` reads `TARMAC_DEV_SOCKET` through the
  existing `env_override` (empty means unset) and `current_channel()`. The module is
  `#[cfg(debug_assertions)]` — **and `main.rs` needs a matching `#[cfg(not(debug_assertions))]`
  arm for `Some("dev")`**. Without it the verb falls through to the unknown-command arm
  (`tarmac-cli/src/main.rs:84-87`) and exits **2** with `unknown command 'dev'`, while Q1 requires
  exit **1** with `driver unavailable in release builds`. Two arms, one predicate.
- **`desktop/src-tauri/src/dev_driver.rs`** — `#[cfg(debug_assertions)]`. Binds the dev socket,
  accepts one request per connection, emits it to the frontend as a Tauri `dev-request` event
  keyed by a request id, and awaits the frontend's `dev_reply` command before writing the
  `DevReply` frame back. **The core takes its frontend channel by argument** — the driver holds a
  sink it calls with `(id, req)` rather than reaching for an `AppHandle`, so `mod tests` drives it
  with a recording sink exactly as `bridge.rs`'s `test_bridge()` / `recording_channel()`
  (`desktop/src-tauri/src/bridge.rs:1028-1045`) do. Without that seam S66–S70 cannot be tests.
- **`desktop/src/devDriver.ts`** — the frontend shell: `listen("dev-request")`, resolve targets,
  dispatch events, wait, build the snapshot, `invoke("dev_reply", …)`. Untested wiring by
  design; every *behavioural* decision inside it is a `kit/` call, and the only things it owns
  outright are the two timing margins (the two-frame settle and the 50 ms poll, Data Flow 4–5),
  whose discharge is named there. It is **installed by `App.tsx`** with its
  world passed in — `installDevDriver(deps)`, called once behind `import.meta.env.DEV`, where
  `deps` supplies: the active board's `board_id`, cards and viewport; `selectedId`; the
  `BoardEngine` (for `zoom`); the terminal handle map (`App.tsx:268`); the daemon's last
  `TermProc` name per terminal; and a `cardNode(id)` lookup. Nothing else can read those — they
  are React state and refs — so this install call is the third production touch (see *For the
  Implementing Agent*), and it is wiring: no decision lives in it.
- **The raw `TermProc` name is not kept today and must be.** `App.tsx:1108-1111`'s `term_proc`
  arm folds the name straight into the card's display label
  (`applyTermProc` → `displayLabel(undefined, name, "shell")`, `App.tsx:679-686`), and a later
  `term_title` frame overwrites that label with the OSC title. So `label` is **not** `proc`:
  reading the snapshot's `term.proc` from it would make D7's `proc == "sleep"` wait depend on
  whether the program set a title. A `termProcRef: Map<termId, string>` recorded in that same
  switch arm — the shape `bellTimeRef` (`App.tsx:227`, set at `:1116`) already uses two lines
  away — is the source `term.proc` reads, and `null` means no `TermProc` has arrived (S5).
- **`cardNode(id)` already exists.** `Board.tsx:78`'s `cardEls: Map<string, HTMLElement>`, filled
  by the `rootRef` callback at `Board.tsx:128-131` and keyed by `cardId(c)`, holds every card's
  root element for **both** kinds. The five element roles resolve from it: `card-body` and
  `card-handle-br` by `querySelector` within that root, `term-element`/`term-textarea` from the
  widened terminal handle, `board-viewport` from the board itself. **Do not add a
  `data-card-id`/`data-term-id` attribute** — both registries are already there.
- **`desktop/src/kit/dev*.ts`** — the decisions, each with a Vitest file:
  `devSnapshot.ts` (snapshot builder + `screen_rect` projection), `devKeyPlan.ts` (combo →
  event sequence), `devTypePlan.ts` (string → per-character step plan, **and** the collected step
  results → the `type` reply body, S71), `devUntil.ts` (the
  `--until` expression parser + evaluator), `devRouting.ts` (verb → target + preconditions),
  `devResizeGrip.ts` (board-unit target → grip pointer plan), `devCellPoint.ts` (the
  `contextmenu` click point).
- **`scripts/qa/smoke.mjs`** + a `make qa` target — the end-to-end scenario runner. Not part of
  `make test` or CI: it needs a live `make run` app.

### Data Flow

1. `tarmac dev <verb> …` parses argv into a `DevRequest` (including `until` / `timeout_ms` for
   `snapshot`), resolves `TARMAC_DEV_SOCKET` / `channel_dir(home, Dev)/tarmac-dev.sock`,
   connects, and writes one frame.
2. `dev_driver.rs` decodes the frame, mints a request id, stores a `oneshot::Sender`, and emits
   `dev-request` with `{ id, req }` as JSON.
3. `devDriver.ts` routes the verb through `kit/devRouting.ts`. A precondition failure
   (`no_such_card`, `not_focused`, `unsupported_card_kind`) short-circuits: **no event is
   dispatched**.
4. It dispatches the planned DOM events on the resolved elements, then waits **two animation
   frames, or 100 ms, whichever comes first**. **Measured, not assumed** (Q5,
   `desktop/qa/qa-driver-qa.md`): `requestAnimationFrame` does not fire *at all* while the app is
   hidden. Frontmost, the settle ends on the second frame and the cap is never reached — raising
   it to 1500 ms changed nothing. Hidden, the settle runs to whatever the cap is, so without one
   every verb would wait out the backend's 2 s bound and come back `app_unresponsive`. Q5's
   stage-2 re-run bounded which states those are: **hidden** (101 ms) and **minimised** (105 ms)
   run to the cap; **frontmost** (21 ms) and **behind another app's window** (24 ms) end on the
   second frame. So a driver invoked from a shell with Tarmac merely behind the terminal is *not*
   in the stalling state and pays nothing, while a hidden app stays usable because of the cap. It
   can only ever end the wait *early*, so a visible window behaves exactly as the issue
   describes.
   React flushes a discrete pointer event's state update synchronously, so the wait is
   a **margin** for what does not settle in that flush — the re-rendered layout `screen_rect` is
   measured from, xterm's refit — rather than the thing that makes the reply correct. What the
   scenarios pin is the rule it serves: a reply body reports the **observed** post-gesture state
   (D3, D10(b)). The wait itself is wiring (exception 2, no decision to extract).
   Requests are served **one at a time**: the frontend finishes one verb's dispatch → settle →
   snapshot before it starts the next, so every reply body describes the state that verb produced
   and not a neighbour's. A request queued behind a long `snapshot --until` therefore spends its
   own backend budget waiting, and can come back `app_unresponsive` while the app is perfectly
   healthy. That is acceptable and not a bug to file: `smoke.mjs` is sequential and never has two
   requests in flight — S72 pins the id routing for the case where something else does.
5. It builds a snapshot from `kit/devSnapshot.ts`. For `snapshot --until`, it re-evaluates the
   expression every **50 ms** until it holds or `timeout_ms` elapses. (50 ms, not a rAF loop:
   the facts being waited on — a `ResizeObserver` → daemon `Resize` round trip, the daemon's
   750 ms `TermProc` poll, a debounced persist — are all slower than a frame, and a rAF spin
   competes with the very render it is waiting for.) D9(b) bounds the interval observably: a
   300 ms budget must come back in under 800 ms.
6. It `invoke("dev_reply", { id, ok, body })`. The backend resolves **that id's** `oneshot`
   (a `dev_reply` naming an unknown or already-resolved id is a no-op), writes the `DevReply`
   frame, and closes.
7. The CLI prints `body` verbatim — stdout when `ok`, stderr when not — and exits 0 or 1.

**The three deadlines are nested, longest outermost**, so the innermost one is always the one
that fires: the frontend's `--until` poll ends at `timeout_ms`; the backend gives up at
`(timeout_ms ?? 0) + 2000` (S70); the CLI's socket read timeout is `(timeout_ms ?? 0) + 3000`.
`timeout_ms` is present only on `snapshot`, so every other verb gets 2000/3000. The CLI's
existing 5 s handshake timeout (`core/crates/tarmac-cli/src/main.rs:139`) is **not** reusable:
`dev snapshot --timeout 10000` would die client-side at 5 s and report a CLI error for a healthy
app.

### Interface Contract

```
tarmac dev snapshot [--until <expr>] [--timeout <ms>]   # default --timeout 5000
tarmac dev zoom <z>
tarmac dev resize <card> <w>x<h>                        # board units, lowercase x
tarmac dev focus <card>|board
tarmac dev type <card> "<text>"
tarmac dev key <card> "<combo>"
```

`<card>` is a terminal's `term_id` or a doc's absolute path — the identifiers the wire protocol
already uses.

**Snapshot schema** (`screen_rect` is CSS px in the `getBoundingClientRect` space; `board_rect`
is board units; active board only; `screen_rect` is `null` for any card the driver could not
measure — see the note below, which corrects the issue's "culled card" rationale):

```
{ v: 1, board_id, visibility: "visible"|"hidden",
  viewport: { zoom, cx, cy, view_rect: {x,y,w,h} },
  cards: [{ id, kind: "term"|"doc", board_rect: {x,y,w,h}, screen_rect: {x,y,w,h}|null, focused,
            term?: { alive, cols, rows, proc: string|null, selection: string|null,
                     scrollback_tail: string } }],
  focused_card: id|null,
  active_element: { card: id|null, tag: string, classes: string[],
                    selection_type: "None"|"Caret"|"Range" } }
// classes: document.activeElement's class list. Diagnostic only — no scenario asserts it,
// deliberately: it is what a human reads when `tag` alone does not explain where focus went.
```

`screen_rect` is `null` when no DOM node was found for the card. The issue attributes that to
culling, and that is **probably wrong**: culling is a per-card *content* listener
(`Board.tsx:96-98` → `kit/cardCull.ts`) and the wrapper registered in `cardEls`
(`Board.tsx:128-131`) stays mounted, so a culled card is still measurable. The real reachable
cases are a card mid-mount and a hidden board's card — and the latter is already
`no_such_card` (Decision 13). S3 keeps the `null` branch because the builder must handle a
missing node rather than invent `{0,0,0,0}`, but the scenario is about the builder's contract,
not about culling; do not write "culled" into the code comment.

`visibility` is `document.visibilityState`, and Q5's stage-2 re-run measured that it **does** flip
to `"hidden"` for a hidden or minimised macOS app — 12 consecutive samples over 12 s while
`System Events` reported the app hidden, and back to `"visible"` on unhide, twice. It stays
`"visible"` for a window that is merely behind another app's, which is the case where animation
frames keep being serviced anyway. So it is a usable tell for the state Data Flow step 4's cap
exists for; a scenario that starts failing intermittently should read this field before blaming
the driver. (Stage 1's Q5 recorded the opposite and Decision 16 was written from it; the re-run
reproduces the flip in both directions and supersedes that reading.) `term.alive` is the card's `live && !dead`
(`desktop/src/board/model.ts:63-64`); it is what `make qa` selects its terminal by, and what
keeps it off a held-open dead card. The xterm reads behind the rest are `term.cols` / `term.rows`,
`term.getSelection()`, and `term.buffer.active.getLine(y)?.translateToString(true)` walked up
from `baseY + cursorY` — nothing under `desktop/src/` reads the buffer today, so this is a new read,
but it needs no new capability: `buffer`, `baseY`, `cursorY` and `getLine` are all in xterm's
**stable** typings, not behind `allowProposedApi`.

`term.proc` is the daemon's last `TermProc` name. `scrollback_tail` is the **40 buffer lines
ending at the cursor's row** (`baseY + cursorY`), newline-joined — the blank rows *below* the
cursor are excluded, and a buffer with fewer than 40 lines above the cursor yields just those
lines. (Not "the last 40 lines of the buffer": `buffer.active.length` is `baseY + rows`, so on a
tall card with little output the last 40 lines are all blank and every `contains` assertion in
D3–D6 would fail against output that is plainly on screen.) Both fields exist so a scenario can
read OS facts through the snapshot alone. A doc card carries **no** `term` key at all.

**Every id the driver speaks is the bare wire id** — a `term_id`, or a doc's absolute path. That
is deliberate and it is *not* what the app uses internally: `desktop/src/board/model.ts:96-99`'s
`cardId()` produces the **prefixed** form (`term:t-1`, `doc:/Users/e/a.md`), and that prefixed
string is what `Board.tsx:185` passes to `onCardGrab`, what `App.tsx:187`'s `selectedId` holds,
and what keys `Board.tsx:78`'s `cardEls` map. So the driver owns one translation, in
`kit/devRouting.ts` and nowhere else:

- `cards[].id`, `focused_card` and `active_element.card` are **bare**; the builder strips the
  `term:` / `doc:` prefix off `cardId()`.
- `cardNode(<card>)` looks the element up as ``cardEls.get(`term:${termId}`)`` or
  ``cardEls.get(`doc:${path}`)``.
- `active_element.card` resolves through the hook that already exists: `.term-host` carries
  `data-term-id` (`TerminalCard.tsx:121`), which is how `App.tsx:307-317`'s `focusedLiveTermId`
  works. Do not add a new attribute.

Getting this wrong is the spec's most vacuity-friendly failure: an implementation that keys
everything off `cardId()` end to end passes every `[S]` and `[D]` scenario while
`tarmac dev focus t-1` answers `no_such_card` and only `tarmac dev focus term:t-1` works. S76
pins the strip in both directions.

`focused` and `focused_card` report the app's **selected** card — the thing a press on a card
body sets — as that bare id; `cards[<id>].focused` is true exactly when `focused_card == <id>`.
**Keyboard focus is a different fact and lives only in `active_element`**; the two disagree
legitimately (a selected card whose textarea was blurred), which is why both are reported.
`active_element.card` is the bare id of the nearest card ancestor of `document.activeElement`,
or `null` when focus is outside any card.

**`<combo>` grammar — a closed set, lowercase only:** one key, optionally preceded by modifiers
from `ctrl`, `shift`, `alt` joined by `+`. The key is one of `enter`, `tab`, `escape`,
`backspace`, `up`, `down`, `left`, `right`, a single lowercase ASCII letter or digit, or the bare
word `contextmenu` (no modifiers; a mouse plan, S16). Three refusals, each with a reason:

**Precedence:** the `not_focused` precondition is evaluated **before** the combo is parsed, so
`key <unfocused-card> "frobnicate"` answers `not_focused`, not `bad_combo`. That follows S40 —
"the precondition is evaluated before any event is planned" — and matches S41's house rule that a
property of the request's context outranks a property of its arguments. A caller fixing both gets
one error at a time, in that order.

- `cmd` / `meta` → `unsupported_combo`: they rely on WebKit's native Edit-menu action, which an
  untrusted dispatched event never triggers (S14).
- **A letter or digit with no `ctrl` or `alt`** — `"a"`, `"7"`, `"shift+a"` → `unsupported_combo`
  whose message says *use `type` for printable characters* (S14b). This is not tidiness: for that
  shape `kit/termKeyRoute.ts`'s `xtermHandlesKey` returns **false**, so xterm stands aside
  without `preventDefault`, and the only remaining path to the PTY is the `beforeinput`
  interceptor, which a synthetic key event never fires. `key <term> "a"` would be a **silent
  no-op** — the exact defect Decision 6 refuses to ship. A letter or digit is still valid as the
  base of a `ctrl`/`alt` chord (`ctrl+c`, `alt+left`), where `xtermHandlesKey` returns true and
  xterm encodes it.
- **Anything else** — an unknown key name, an uppercase spelling, a trailing `+`, an empty string
  — is `bad_combo` (S15).

A closed set is the point: a scenario that typos a combo fails loudly instead of silently sending
something else.

**`--until` grammar:** `<path> <op> <value>`, with `op` ∈ `==`, `!=`, `~=` (numeric, |Δ| ≤ 1),
`contains`. `<path>` is dotted; `cards[<id>]` indexes by card id, where the id runs to the
**last** `]` in the remainder of the path (doc paths contain dots, slashes, and may contain
`]`). `<value>` is a number, a double-quoted string (`\"` and `\\` escapes), `null`, `true` or
`false`. An **unresolvable path evaluates to `false`** so polling continues; a **malformed
expression is an immediate error**, not a spent timeout.

**Reply bodies.** `body` is always JSON. On success:

```
snapshot → the snapshot object
zoom     → { "zoom": 0.5 }
focus    → { "focused_card": "t-1", "active_element": { … } }
resize   → { "from": {w,h}, "to": {w,h}, "delta_px": {dx,dy} }
type     → { "chars": 5, "inserted": 4, "dropped": [ { "index": 2, "char": "b" } ],
             "mode": "insert" }
key      → { "combo": "ctrl+c", "events": ["keydown","keyup"] }
```

Every number in a reply body is an **observed** fact, never an echo of the request:

- `zoom` reports the viewport's zoom **after** `setViewport`'s clamp to `[0.1, 3.0]`
  (`desktop/src/board/BoardEngine.ts:111`), so `dev zoom 99` succeeds with `{ "zoom": 3 }`. An
  out-of-range `z` is **not** an error (D10).
- `resize` reports `from`/`to` as the card's `board_rect` before and after the gesture settles,
  and `delta_px` as the pointer delta the plan actually dispatched. A request below the card
  minimum succeeds with the clamped size (`MIN_CARD_W`/`MIN_CARD_H` = 160/90,
  `desktop/src/kit/resize.ts:15-16`), so `dev resize <term> 10x10` replies
  `to: {w: 160, h: 90}` (D10). Only the `br` grip is driven, so the card's `x`/`y` never move.
- `type` reports `chars` = the number of characters in the requested string (including those that
  become key events), `inserted` = the number of `insertText` steps `execCommand` returned `true`
  for, and `dropped` = one entry per `insertText` step that returned `false`, whose `index` is the
  character's index **in the requested string**. A key-event step (`\n`, `\t`, `\x03`) is counted
  in `chars` and is neither inserted nor dropped, so `chars > inserted + dropped.length` is normal
  for a string containing them (S71). `mode` is `"insert"` or `"key"` (S77) and is **always
  present**, not only under kitty flag 8: a caller should not have to read a missing key as a
  fact. Both counts are per *character*, counted by code point, so an astral character is one
  step and one index rather than two halves.
- `key` reports the event types actually dispatched, in order.

On failure, `ok` is `false` and `body` is `{ "error": "<code>", "message": "<human>", … }` with
codes `no_such_card`, `not_focused`, `unsupported_card_kind`, `unsupported_combo`, `bad_combo`,
`bad_expr`, `empty_buffer`, `timeout` (which also carries `expr`, `timeout_ms` and the final
`snapshot`), `app_not_ready`, `app_unresponsive`, `unsupported_verb`, `bad_request` and `driver_threw`.

The last two were added during stage 1 and are recorded here rather than left implicit.
**`unsupported_verb`** is what the app answers for a verb the CLI can parse but this build does
not implement — stage 1 ships the *whole* CLI surface (S55 and S56 require the parser to accept
`type`, `key` and `resize`, so a half-parser was never an option), and an honest "not yet"
beats a verb that silently does nothing or an argv error that blames the caller's spelling. It is
also what a `DevRequest::Unknown` decodes to, so an older app meeting a newer CLI says so instead
of dropping the frame. **`bad_request`** is an undecodable frame. **`driver_threw`** is the frontend's own
last resort: the request queue answers with it rather than letting a rejection poison the chain,
because an unanswered request would come back as `app_unresponsive` and send whoever is reading a
`make qa` failure looking at the backend. All three are app-side, so all three are JSON on stderr
like the rest.

**The driver sees the active board only** — the snapshot reports it, and every verb addresses it.
A `<card>` that is not on the active board is `no_such_card`, whether it does not exist at all or
sits on a hidden board (S39). Switching boards is not a verb (see *Trade-offs*).

**CLI-originated errors stay plain text**, one line on stderr, matching `tarmac open`:
`driver unavailable in release builds`, `no tarmac app driver at <path>`, the
`check_socket_path_len` message, and a read-deadline line naming the elapsed budget when the app
sends no frame at all. Only *app*-originated errors are JSON.

### Staging

The issue asks for two stages, and they are separable: **Stage 1** is the endpoint plus
`snapshot`, `zoom` and `focus`; **Stage 2** adds `resize`, `type` and `key`. Every scenario
below is tagged `[1]` or `[2]`, and **the per-scenario tag is authoritative** — stage 1 is
exactly the set tagged `[1]`. Two scenarios are split: **D9** ((a) and (b) are `[1]`, (c) is
`[2]`) and **D10** ((a) is `[1]`, (b) is `[2]`); **S58** is split by content, not by row. Stage 1
is independently verifiable from that set alone and can land as its own PR.

**Stage 2 does not start until three pre-checks run in `.dev/key-harness`** (Playwright WebKit,
xterm from `desktop/node_modules`), each one measuring a claim stage 2's scenarios rest on. The
issue set this precedent with the `execCommand` pre-check; these are the ones still outstanding.
Record each result in the PR, and if one comes back the other way, change the scenario rather
than the measurement:

1. **Does `execCommand("insertText")` still return `true` when a `beforeinput` listener calls
   `preventDefault()`?** D4 asserts `dropped == []`, which is `execCommand === true` on every
   step — but `TerminalCard.tsx:324-328`'s interceptor cancels `beforeinput`, and the issue's
   pre-check measured a bare textarea and xterm's helper textarea *without* it. A `false` return
   there would fail D4/D5 for a reason unrelated to #162.
2. **Does WebKit fire `keypress` for `ctrl+c`?** S10 pinned the no-`keypress` shape on the belief
   that it does not. **Ran 2026-09-16 ([#174](https://github.com/pingeplin/tarmac/issues/174)):
   confirmed** — and the same run found S9/S11 wrong about Enter, which produces no `keypress` in
   the app either. Those two were amended and S13 now asserts the absence across the whole table;
   S10 stands as written.
3. **Does `execCommand("insertText")` still work in a non-key window?** Decision 15 makes "Tarmac
   behind other windows" the *normal* case for this driver, and the 100 ms settle cap covers
   `requestAnimationFrame` only. The harness cannot answer this one — it needs the real
   WKWebView — so it is folded into **Q5**, which must therefore run before stage 2 is called
   done, not only before stage 1 is. **Ran 2026-09-16: yes.** `make qa` against a **hidden** dev
   app passes 18/18, D4 and D5 included, both reporting `dropped: []`. The editing path does not
   need a key window. (Q5 also measured that "behind other windows" is two different states: only
   hidden and minimised stall rAF.)

## Decisions this spec makes beyond the issue

These are the points the issue left open or under-specified. Each is resolved here with its
reason, so the gate can push back on a specific call rather than on the whole design.

1. **The bracketing keydown/keyup for a printable character carry the character as `key`,
   `code: ""`, `keyCode: 0`, `which: 0` and no modifiers — and there is no `keypress`.**
   *Why, read off the tree:* `desktop/src/kit/termKeyRoute.ts`'s `xtermHandlesKey` returns
   `false` for exactly this shape — a plain single-character `key`, no modifiers, no kitty
   flag 8 — which makes xterm **stand aside without `preventDefault`** and leaves
   `beforeinput` the only path to the PTY, which is #160's design. Two spellings that look
   safer are not:
   - `key: "Unidentified"` fails `key.length !== 1`, so `xtermHandlesKey` returns **true** and
     xterm owns the event; under a kitty keyboard program (Claude Code pushes flags 5) its
     encoder can emit an escape sequence for it.
   - A real printable `keyCode` is harmless to `xtermHandlesKey` (which never reads `keyCode`),
     but `keyCode: 0` is kept anyway because it is not `229`, so `kit/imeGuard.ts`'s
     `isComposingKey` can never mistake the bracket for an IME composition.
   `code: ""` is deliberate: `kit/termKeyBinding.ts` keys its #21 rows off `code`
   (`Backspace`, `ArrowLeft`…), so an empty `code` can never collide with them.
   D6 is the end-to-end guard: `printf <sentinel>` must echo the sentinel *once*, not doubled.
   If it ever doubles, the delivery path has drifted and D4/D5/Q2 are vacuous.
2. **`ok: false` bodies are JSON with an `error` code**, rather than the issue's bare strings.
   *Why:* the scenario runner already parses `snapshot` output; a bare line forces it to
   string-match, and `timeout` needs to carry the final snapshot anyway. The issue's strings
   survive as the codes (`no such card` → `no_such_card`).
3. **`ok: false` bodies go to stderr, success bodies to stdout.** *Why:* `dev snapshot | jq`
   must not be fed an error object.
4. **`type` reports dropped characters but still exits 0.** *Why:* the driver reports facts and
   does not judge. D4 asserts both the scrollback *and* `dropped == []`, which is strictly
   stronger than an exit code.
5. **`focus <doc-card>` is an explicit `unsupported_card_kind` error**, not a silent no-op.
   A doc card has no focus target an untrusted `mousedown` would reach.
6. **`key <card> "cmd+c"` / `"meta+v"` is an explicit `unsupported_combo` error.** *Why:* those
   rely on WebKit's native Edit-menu action, which untrusted dispatched events never trigger; a
   silently-no-op verb would let a scenario claim a copy happened.
7. **A live sibling dev socket is never unlinked *and* never taken over.** The app logs one line
   and opens no dev endpoint. *Why:* the daemon's rule is "exit 1" (`docs/protocol.md:28-30`),
   which would be wrong here — killing the window over a dev nicety.
8. **`--until` polls at 50 ms** (see Data Flow step 5).
9. **A reply body reports the observed result, never the request.** `zoom` reports the clamped
   viewport zoom, `resize` reports the settled `board_rect` (D10). *Why:* the driver's whole
   value is that its output is a fact; an echoed request would let a scenario assert a state the
   app cannot reach. Out-of-range is therefore **not** an error — the app already clamps, and a
   second opinion in the driver would be a second definition of the limits.
10. **`<combo>` is a closed lowercase set** (see the Interface Contract), not an open
    modifier+key expression. *Why:* an open grammar makes S13's "every accepted combo" untestable
    and lets a scenario's typo resolve to a neighbouring key. Widening it later is additive.
11. **`scrollback_tail` ends at the cursor row**, not at the end of `buffer.active`. *Why:* the
    buffer is padded to `baseY + rows`, so "the last 40 lines" is mostly blank on a tall card and
    would hide output that is plainly on screen.
12. **The three deadlines are nested** — poll `timeout_ms`, backend `+2000`, CLI `+3000`. *Why:*
    the CLI's existing 5 s handshake timeout is shorter than a legitimate `--timeout`, so reusing
    it would report a CLI error for a healthy app (S73).
13. **The driver is scoped to the active board.** A card on any other board is `no_such_card`
    (S39) and there is no board-switch verb. *Why:* the snapshot reports the active board only, so
    a verb aimed at a hidden board would dispatch events nothing could observe. If a scenario ever
    needs two boards, a `board` verb is the additive follow-up.
14. **`README.md` is deliberately not updated.** Its CLI verb list is user-facing and `dev` is a
    debug-build-only family. `CLAUDE.md` and `docs/architecture.md` are, because they are the
    agent-facing and engineering docs. `SKILL.md` is not updated for the same reason the issue
    gives: it ships into every agent's skills directory.
15. **The settle is two animation frames *or* 100 ms, whichever comes first** — the issue says
    "returns after two animation frames" flat. **Q5 measured it in the real Tauri WKWebView and
    the cap is load-bearing:** a hidden app services no animation frames at all, so a pure two-rAF
    wait would hang every verb into `app_unresponsive` in the driver's most normal posture —
    called from a shell, with Tarmac behind the terminal. Frontmost, the cap is never reached.
    (Drafted as a hedge against a documented-but-unobserved behaviour; Q5 turned it into an
    observed one, which is the form Tarmac's invariant asks for.)
16. **The snapshot carries `visibility`** (`document.visibilityState`), which the issue's schema
    does not. One string, pinned by S74. It reads `"hidden"` for a hidden app and for a minimised
    window, and `"visible"` for one merely behind another app's window — measured by Q5's stage-2
    re-run, which also measured that the two states it calls `"hidden"` are exactly the two where
    the settle hits Decision 15's cap. So it *is* the diagnostic for that case. (Stage 1's Q5 read
    `"visible"` while hidden and this decision was rewritten around that; the re-run reproduces
    the flip in both directions, 12 samples over 12 s, and supersedes it.)
17. **`term` carries `alive`**, which the issue's schema does not. *Why:* `smoke.mjs` has to pick
    a terminal and no verb creates one; a held-open dead card renders, accepts `focus`, and then
    swallows every `type`, so picking one would fail D4 for a reason unrelated to #162. Derived
    from the card model's existing `live && !dead` (`desktop/src/board/model.ts:63-64`), pinned by
    S75.

18. **Six smaller additions the issue did not ask for**, grouped because each is small and none
    is contentious — listed so the gate can still reject one individually:
    (a) per-verb **success** body schemas (the issue made `body` opaque; Decision 9 governs their
    content but not their existence);
    (b) the `empty_buffer` error code (S18);
    (c) `--timeout 0` means "evaluate once" (S54);
    (d) `dev type <card> ""` parses as a valid no-op (S55);
    (e) the CLI exit-code tests live in a new `core/crates/tarmac-cli/tests/dev.rs` rather than in
    `tests/cli.rs` as the issue says — `tests/version.rs` set the one-file-per-verb precedent and
    carries the fake-peer harness this needs;
    (f) requests are served one at a time and replies are routed by request id (Data Flow 4,
    S72).

## Verified starting facts

Checked against `main` @ `9c2ba07` before this spec was written. Three of them contradict the
issue's wording and the implementation must follow the tree, not the issue:

- **The bottom-right grip is `br`, not `se`.** `Handle = Corner | Edge`,
  `Corner = "tl"|"tr"|"bl"|"br"` (`desktop/src/kit/resize.ts:11-13`); the DOM class is
  `card-handle br` (`desktop/src/cards/CardShell.tsx:196-203`). Nothing in the repo is named
  `se`. Every scenario below says `br`.
- **Vitest runs `environment: "node"` with no jsdom** (`desktop/vitest.config.ts`), and
  `include` is `src/**/*.test.ts` only. So a `kit/` module *cannot* construct a real
  `KeyboardEvent`/`PointerEvent` — and must not: the kit functions return **event-init
  descriptors** — plain `{ kind, target, type, init }` data, where `kind` selects the constructor
  (`key` | `pointer` | `mouse`) and `target` names an element *role*, one of `card-body`,
  `term-element`, `term-textarea`, `card-handle-br`, `board-viewport` — and `devDriver.ts`
  resolves the role to a node, constructs the real event and dispatches it. Every descriptor in
  the scenarios below carries all four fields (a scenario that names only some of them is
  asserting on those) — except `zoom`, which plans no event at all but a viewport commit (S42). This also makes "the snapshot builder never reaches `document`" automatic
  rather than aspirational: `document` does not exist in that environment, so a builder that
  touched it would throw.
- **An `Unidentified` key bracket would have routed to xterm.** `kit/termKeyRoute.ts`'s
  `xtermHandlesKey` ends in
  `return (kittyFlags & 8) !== 0 || key.length !== 1`, so any `key` that is not exactly one
  character is handled by xterm — and under a kitty keyboard program its encoder can emit an
  escape sequence for it. The `type` bracket therefore carries the real character (Decision 1).
  This was found after the first draft, which specified `key: "Unidentified"`; it is recorded
  here because the mistake is easy to make again and would have made D4, D5 and Q2 vacuous
  rather than failing.
- **The term handle widening is type-level only.** `TerminalCard.tsx:277` already passes the
  whole xterm `Terminal` (`onRegister?.(model.termId, term)`); `App.tsx:268` merely *types* the
  map as `{ focus(): void; input(data: string): void }`. `.element` and `.textarea` are already
  present at runtime. Widening the declared type is the entire change — do **not** add a
  `data-term-id` attribute or restructure the registry.

Also confirmed, and relied on below: `resolve_socket_path` / `channel_dir` / `Channel`
(`core/crates/tarmac-protocol/src/lib.rs:331-375`); three `socket_path()` copies
(`tarmacd/src/main.rs:31`, `tarmac-cli/src/main.rs:61`, `bridge.rs:516` — CLAUDE.md:62 names
only two and is the stale line the issue asks to fix); `tarmac-protocol` is a **single
`lib.rs`** whose only submodule is the inline `pub mod frame` at `:411`, so `dev` should be an
inline `pub mod dev` beside it; `desktop/src-tauri/` has **no `UnixListener` anywhere** — the
only bind/stale-replacement precedent in the repo is `core/crates/tarmacd/src/main.rs:88` and
its `claim_socket`; `core/crates/tarmac-cli/tests/version.rs:59` already stands up a fake
`UnixListener` peer and is the pattern the dev round-trip tests should copy;
`docs/coding-style.md:186-200` already bans `any` in `kit/` and forbids `kit/` importing React
or `@tauri-apps`; `.blueprint/specs/*.md` is **not** scanned by `make docs-check` (only
`docs/**`, `README.md`, `CLAUDE.md` are), but `.blueprint/` *is* on its cited-path allow-list,
so a `CLAUDE.md` line naming `scripts/qa/smoke.mjs` fails `docs-check` until that file exists —
docs land **with** the code, never ahead of it.

## Acceptance Scenarios

Three tiers, because they are checked by three different things:

- **`[S]` automated, in `make test`** — Vitest (`desktop/src/kit/`) and `cargo test`. These are
  what `/verify`'s referee runs.
- **`[D]` automated, in `make qa`** — `scripts/qa/smoke.mjs` against a live `make run` app. Not
  in `make test` or CI. These are the issue's acceptance boxes, and they are the *point* of the
  feature: the driver's first customer is its own scenario suite.
- **`[Q]` hand-run** — recorded in `desktop/qa/qa-driver-qa.md`, per
  `docs/coding-style.md`'s rule that spec-driven manual scenarios live there.

Each carries its stage: `[1]` endpoint + `snapshot`/`zoom`/`focus`, `[2]` `resize`/`type`/`key`.
Ids are stable labels, not an ordering — S71–S73 and D10 were appended to the subject sections
they belong to rather than renumbering the cross-references.

### Snapshot builder — `desktop/src/kit/devSnapshot.ts` [S]

- **S1 [1]:** Given a viewport, a card list and a map of measured screen rects, when the builder
  runs, then it returns `{ v: 1, board_id, viewport: { zoom, cx, cy, view_rect }, cards,
  focused_card, active_element }` with those exact key names. The test file runs in Vitest's
  default `node` environment, so a builder that read `document` would throw rather than pass —
  the purity requirement is enforced by the environment, not by inspection.
- **S2 [1]:** Given one `term` card and one `doc` card, when the snapshot is
  `JSON.stringify`-ed, then the term card's object has a `term` sub-object with
  `cols, rows, proc, selection, scrollback_tail`, and the doc card's object contains **no `term`
  key at all** (`"term" in card === false` — not `term: undefined`, which `JSON.stringify` would
  drop but `--until` would then read as a silent `false`).
- **S3 [1]:** Given a card with no measured DOM node (culled), when the snapshot is built, then
  its `screen_rect` is `null` and its `board_rect` is still the card's frame — a culled card is
  reported as unmeasured, never as absent and never as `{0,0,0,0}`.
- **S4 [1]:** Given a buffer whose cursor sits on line 100, when the snapshot is built, then
  `scrollback_tail` is lines 61–100 newline-joined; given a cursor on line 5, it is those 5 lines
  with no blank padding. And given a **50-row** buffer whose cursor is on line 5 with 45 blank
  rows below it, the tail is still those 5 lines — a builder that took "the last 40 lines of
  `buffer.active`" would return 40 blank lines here, pass the first two cases, and silently break
  every `contains` assertion in D3–D6.
- **S5 [1]:** Given a terminal for which the daemon has reported no `TermProc`, then `term.proc`
  is `null`; given a terminal with no selection, `term.selection` is `null` — not `""`, which
  `contains ""` would match vacuously.
- **S6 [1]:** Given cards belonging to two boards, when the snapshot is built for the active
  board, then only the active board's card ids appear.
- **S74 [1]:** Given `visibilityState: "hidden"` in the builder's input, the snapshot's
  `visibility` is `"hidden"`; given `"visible"`, it is `"visible"`. Trivial to implement and
  trivial to forget — and the field's whole purpose is to be readable when a `make qa` run is
  behaving oddly behind another window, so a hard-coded `"visible"` would be worse than no field.
- **S75 [1]:** Given a term card with `live: true, dead: false`, `term.alive` is `true`; with
  `live: true, dead: true` (a held-open exited card) and with `live: false`, it is `false`. Both
  false cases matter: `smoke.mjs` picks its terminal by this field, and a dead card accepts
  `focus` and then swallows every `type`, which would fail D4 for a reason that has nothing to do
  with #162.
- **S76 [1]:** Given cards whose internal ids are `term:t-1` and `doc:/Users/e/a.b.md` and a
  `selectedId` of `term:t-1`, the snapshot's `cards[].id` values are `t-1` and
  `/Users/e/a.b.md`, `focused_card` is `t-1`, and `cards[t-1].focused` is `true`. And in the
  other direction: resolving `<card> = "t-1"` yields the node registered under `term:t-1`, while
  resolving `"term:t-1"` is `no_such_card`. Both directions are needed — an implementation that
  never strips passes every other scenario in this spec while `tarmac dev focus t-1` answers
  `no_such_card`, which is the one thing a user of the CLI would type.
- **S7 [1]:** Given a `board_rect`, a viewport and a `view_rect` with a **non-zero** `x`/`y`,
  when `boardRectToScreenRect` projects it, then both corners equal
  `worldToView(corner, zoom, {x: cx, y: cy}, {x: view_rect.x + view_rect.w/2,
  y: view_rect.y + view_rect.h/2})` at zoom `0.5`, `1` and `2.37`. **One row is a hand-computed
  literal**, not a call to `worldToView`: oracle and implementation would otherwise share any
  convention error, and the scenario would catch only an argument-wiring slip. (The convention
  itself was checked against `BoardEngine.ts:288-291` — `tx = rect.width/2 − cx·zoom` — and
  against `EdgeLayer.tsx:41`, which works in element-local `{w/2, h/2}`; the driver's extra
  `+ view_rect.x/y` is what turns board-local into client coordinates, and is genuinely needed.)
  The non-zero origin is the other load-bearing part: a projection that drops `view_rect.x/y` passes at origin `(0,0)` and fails
  here, which is exactly the mistake `worldToView`'s `viewportCenter`-not-rect signature invites.
- **S8 [1]:** Two rows, because either alone proves nothing. **At zoom 1**, with `cx,cy` equal to
  half the `view_rect`'s `w`/`h` (the viewport centre measured from the viewport's own origin), a
  board rect projects to itself translated by the `view_rect` origin, `w`/`h` unchanged — the
  pure-translation case. **At zoom 2.37**, the same rect's `w`/`h` are `2.37×` the board values,
  as a hand-computed literal. The second row is the load-bearing one: at zoom 1, `w` and
  `w · zoom` are numerically identical, so an implementation that scales the origin and copies the
  size straight through passes the first row.

### Key-combo planning — `desktop/src/kit/devKeyPlan.ts` [S]

Each plan is a list of descriptors; `devDriver.ts` turns them into `KeyboardEvent`s on
`term.textarea` — except `contextmenu` (S16), the one member of the combo set that plans a mouse
event on `term.element`, because that is where xterm's right-click handler lives.

- **S9 [2]:** `"enter"` → `[keydown, keyup]` and **no `keypress`**, each with
  `{ key: "Enter", code: "Enter", keyCode: 13, which: 13 }`. WebKit does fire a `keypress` for
  Enter on a bare textarea, but the app never sees one: `xtermHandlesKey` returns true for it
  (`key.length !== 1`), xterm cancels the keydown, and no `keypress` follows. Measured by the
  stage-2 entry pre-check below — the earlier `[keydown, keypress, keyup]` was the engine's shape,
  not the app's.
- **S10 [2]:** `"ctrl+c"` → `[keydown, keyup]` and **no `keypress`**, with
  `{ key: "c", ctrlKey: true, keyCode: 67 }`. A plan that emitted `keypress` here would feed
  #156's dedupe a sequence WebKit does not produce, making any future regression test of it lie.
  **Measured** by the stage-2 entry pre-check below: `ctrl+c` and `ctrl+d` each produce keydowns
  and zero keypresses on a bare textarea as well as in the app, so the absence is WebKit's own
  shape and not xterm's interference.
- **S11 [2]:** `"shift+enter"` → `shiftKey: true` on both events, and no `keypress` — the
  modifier does not change what the app produces for Enter (S9).
- **S12 [2]:** `"escape"` → `[keydown, keyup]`, `keyCode: 27`, no `keypress`.
- **S12c [2]:** `"alt+tab"` parses and plans normally, **and the `key` docs say what it does**:
  `App.tsx:1366` catches `altKey && !meta && !ctrl && !shift && code === "Tab"` at the window
  capture phase and cycles the prime terminal, so the combo never reaches the PTY and it moves
  focus — breaking the `not_focused` precondition for every later verb in the same scenario. It
  stays drivable because cycling is a real thing to drive; it is documented because a scenario
  that used it as a keystroke would fail three steps later for no visible reason.
- **S12b [2]:** `"alt+left"` → `[keydown, keyup]` with
  `{ key: "ArrowLeft", code: "ArrowLeft", altKey: true, keyCode: 37 }` and no `keypress`. This is
  the one scenario that makes the descriptor's `code` field non-vacuous: `App.tsx`'s window
  keydown handler routes #21's Ghostty-parity rows through `kit/termKeyBinding.ts`, which matches
  on `code` alone (`ArrowLeft` + alt-only → `ESC b`). A plan that left `code` empty would drive
  every named key except those rows, and nothing else in the suite would notice.
- **S13 [2]:** The accepted set is the `<combo>` grammar's closed list, enumerated in the test as
  a table (every named key — `enter`, `tab`, `escape`, `backspace`, the four arrows — each
  modifier, and a letter and a digit **as the base of a `ctrl` and an `alt` chord**, which is the
  only form they are accepted in). For **every** row: the plan is non-empty,
  every descriptor has `keyCode === which` and `bubbles: true, cancelable: true`, and the
  modifier flags named in the combo are the only ones set. React listens at the root and xterm's
  evaluator reads `keyCode`, so a descriptor missing either is inert in the app while still
  "passing" a shallower test. And every row's plan is exactly `[keydown, keyup]`: **a `keypress`
  anywhere in a keyboard plan is a failure.** The closed grammar is what makes that flat rule
  true — named keys and `ctrl`/`alt` chords are all owned by xterm, which cancels the keydown, and
  the one family that would fire a `keypress`, a bare letter or digit, is refused by S14b. The
  table is keyboard plans only; `contextmenu` (S16) is a mouse plan and is not in it. Asserting
  the absence across every row is what keeps this non-vacuous: reinstating Enter's `keypress`
  fails a test instead of silently diverging from the app.
- **S14b [2]:** `"a"`, `"7"` and `"shift+a"` → `{ error: "unsupported_combo" }` with an **empty**
  event list and a message naming `type` as the remedy. The test asserts the reason as well as
  the refusal: it feeds the same descriptor `"a"` would have produced to the real
  `xtermHandlesKey` from `kit/termKeyRoute.ts` and asserts it returns `false` — so if that
  predicate ever changes and the combo becomes deliverable, this scenario fails and tells you the
  refusal is now wrong, rather than silently enforcing a stale rule.
- **S14 [2]:** `"cmd+c"` and `"meta+v"` → `{ error: "unsupported_combo" }` whose message names
  WebKit's native Edit-menu action as the reason, and an **empty** event list. A silent no-op
  would let a scenario assert a copy that never happened.
- **S15 [2]:** `"ctrl+"`, `""`, `"frobnicate"`, `"CTRL+C"` and `"ctrl+shift"` →
  `{ error: "bad_combo" }`, empty event list. The uppercase row pins that the grammar is
  lowercase-only rather than case-folded, so a scenario's typo can never resolve to a
  neighbouring combo.
- **S16 [2]:** `"contextmenu"` is not a keyboard plan: it returns **two** mouse descriptors on
  `term-element`, in order — a `mousemove` at the point, then a `contextmenu` at the same point —
  each `{ bubbles: true, cancelable: true, clientX, clientY }`, the second also
  `{ button: 2, buttons: 2 }`. The leading `mousemove` is load-bearing, not politeness:
  `TerminalCard.tsx:241-262` patches `getBoundingClientRect` on `term.element` and
  `term.screenElement`, anchoring the patched rect on `lastMouseX/lastMouseY` — which it tracks
  from **real `mousedown`/`mousemove` only**, never from `contextmenu`. A bare synthetic
  `contextmenu` leaves those at whatever the last human mouse event set (`0,0` on a fresh window),
  and xterm's `getCoords` then resolves a cell far from the one S17 computed at any zoom ≠ 1. (A
  synthetic, untrusted `mousemove` does reach that listener: capture-phase propagation runs for
  dispatched events regardless of `isTrusted`.) Because the `contextmenu` event itself never
  re-anchors, the pair is ordered — and that ordering is what lets S17 compute its point from the
  *unpatched* rect. **State in the `key contextmenu` docs what it leaves behind:** xterm's
  `rightClickHandler` runs `moveTextAreaUnderMouseCursor`, which sets the helper textarea to
  20×20 px under the cursor with `zIndex: 1000` and refocuses it. D5 types into that displaced
  textarea afterwards and it works — but any later scenario that reads geometry out of
  `active_element` would be reading a 20 px box, so the state change is documented rather than
  discovered.

### Right-click point — `desktop/src/kit/devCellPoint.ts` [S]

- **S17 [2]:** Given buffer rows where the last non-empty row is index 7 holding 9 non-blank
  cells, plus the rect and the `cols`/`rows` grid, then the point is the centre of cell `(8, 7)`,
  computed as `rect.x + (col + 0.5) * rect.w / cols` and the `rows` mirror. An off-by-one in
  either axis lands in a neighbouring cell, so the assertion is on the exact centre, not a range.
  **The rect must be the *unpatched* one** —
  `Element.prototype.getBoundingClientRect.call(term.screenElement)` — even though xterm's own
  `getCoords` reads the **patched** one. That is not an inconsistency, it is the algebra.
  `TerminalCard.tsx:249-256`'s `fakeBCR` returns `left' = lastMouse − (lastMouse − r.left)/s` with
  `width' = r.width/s`, and by the time xterm reads it the leading `mousemove` (S16) has set
  `lastMouse` to the very point `p` we dispatched at — so xterm computes
  `x_rel = p − left'(p) = (p − r.left)/s`, where `r` is the **unpatched** rect. Setting that equal
  to the wanted `(col + 0.5) · r.width / (s · cols)` gives
  **`p = r.left + (col + 0.5) · r.width / cols`** — the unpatched rect, with no `s` in it at all.
  Computing `p` from the patched rect instead feeds in a *stale* anchor (whatever the last real
  mouse event left) and lands a full cell or more off at zoom 1.7. At zoom 1 the patch is a no-op
  anyway (`deriveRasterScale(1) === 1`, `kit/rasterScale.ts:44-48`: `s = 1`, so `fakeBCR` returns
  `r` unchanged), which is why D5 pins zoom 1 and leans on none of this. The kit function takes
  the rect by argument, so the test states both rects explicitly.
  **Correction (stage 2): "a patched-rect implementation fails it" is false, at every tier.** The
  kit test cannot see which rect the *caller* passes, and no `[D]` scenario can either: swapping
  `devDriver.ts`'s `Element.prototype.getBoundingClientRect.call(screen)` for the patched
  `screen.getBoundingClientRect()` was driven against a live app at zooms 1.05, 1.1, 1.4, 1.7,
  2.1, 2.5 and 2.9, with a 3-character target at the row's left edge — the most displaced case —
  and **every one still right-clicked the cell it aimed at**. The reason is in the algebra above:
  the leading `mousemove` re-anchors the patched rect on the very point being dispatched, which
  cancels most of the error back out. A D5 variant was written to catch it, passed under the
  knockout, and was **deleted rather than kept** — a check that passes identically with and
  without the behaviour is the vacuity this spec's own Definition of Done forbids. The
  `Element.prototype` call stands on the algebra and on a comment that says so; it has no test,
  and that is recorded here rather than implied.
- **S18 [2]:** Given an entirely empty buffer, then `{ error: "empty_buffer" }` — a right-click
  on blank space produces a `Caret`, not a `Range`, which would silently downgrade D5 into a
  second copy of D4.

### Type planning — `desktop/src/kit/devTypePlan.ts` [S]

- **S19 [2]:** `"ab"` → two `insertText` steps, each bracketed by a keydown and a keyup whose
  descriptors carry `key: "a"` / `key: "b"`, `code: ""`, `keyCode: 0`, `which: 0`, no modifiers —
  and **no `keypress`**. **This is the anti-vacuity mechanism** (Decision 1): the test asserts the
  descriptor shape *and* asserts that `xtermHandlesKey` returns `false` for it, importing the real
  predicate from `kit/termKeyRoute.ts` rather than restating its rule. A bracket xterm would own
  can deliver the character itself, and D4/D5/Q2 would then all pass for the wrong reason. The
  bracket is a marker, not a replica: the stage-2 pre-check measured that a real printable *does*
  get a `keypress` in the app, and this one deliberately omits it. Nothing in the app listens for
  `keypress` — xterm's handler is the only one, and `xtermHandlesKey` stands it down for a plain
  printable — so the event would be inert, while adding it would rest the bracket's one contract
  (inert under the real predicate) on a further row of that predicate.
- **S77 [2]:** `devTypePlan` takes the terminal's current **kitty flags**. Given
  `kittyFlags: 0` or `5`, `"a"` plans the inert bracket plus `insertText` (S19). Given
  `kittyFlags: 8` — a program that asked for every key as an escape code — it plans a **plain key
  event and no `insertText`**, and the reply body reports `mode: "key"` for those characters.
  *Why:* under flag 8 `xtermHandlesKey` returns `true` for any key, so xterm owns the bracket
  keydown and encodes the character as CSI u — while `execCommand` would *also* fire
  `beforeinput` and deliver it a second time. Every character would arrive twice. The switch is
  not a special case for the driver's convenience; it is what real typing does in that mode
  (xterm `preventDefault`s and no `beforeinput` follows), and the predicate is imported from
  `kit/termKeyRoute.ts` rather than restated. **Consequence to state in the `type` docs:** under
  flag 8, `type` does not exercise the `beforeinput` path at all, so the #162 scenarios are
  meaningful only against a plain shell — which is what D4/D5/D6 use.
- **S20 [2]:** `"\n"` → a single key-event step for Enter (the S9 plan), and **no** `insertText`
  step.
- **S21 [2]:** `"\t"` → a key-event step for Tab (`keyCode: 9`), no `insertText`.
- **S22 [2]:** `"\x03"` → the `ctrl+c` key-event step (the S10 plan), no `insertText`.
- **S23 [2]:** `"a\nb"` → exactly three steps in that order: insert, Enter, insert.
- **S24 [2]:** A non-ASCII printable (`"中"`) → an `insertText` step carrying that character,
  still bracketed by `key: "中"`, `code: ""`, `keyCode: 0` — the same rule as S19, stated for the
  case where "the character's keyCode" has no meaning at all. `keyCode: 0` also keeps it clear of
  `kit/imeGuard.ts`'s `229` composition sentinel, which a CJK character is otherwise the most
  likely thing to be confused with.
- **S71 [2]:** Given the plan for `"a\nb"` and the per-step results the driver collected, the
  summariser returns the `type` reply body: with both inserts returning `true`,
  `{ chars: 3, inserted: 2, dropped: [] }` — the Enter step counts in `chars` and is neither
  inserted nor dropped; with the `b` insert returning `false`,
  `{ chars: 3, inserted: 1, dropped: [ { index: 2, char: "b" } ] }`. `index` is the character's
  index in the requested string. D4's `dropped == []` assertion is only as strong as this: a
  summariser that hard-coded an empty list would make #162's headline scenario unfalsifiable.

`make run` if it cannot reach the dev socket.

**Preconditions, asserted by `smoke.mjs` before any scenario runs — no verb creates a
terminal**, so the suite needs one that already exists:

- The active board holds at least one card with `kind: "term"` and `term.alive === true`.
  `smoke.mjs` takes the **first** such card in snapshot order as `<term>` and prints the id it
  chose. With none, it exits non-zero saying "open a terminal card on the active board first" —
  never by picking a doc card or a held-open dead one. (`term.alive` exists for exactly this:
  a dead card still renders and would accept `focus`, then swallow every `type`.)
- That terminal runs a POSIX shell at a prompt: the scenarios call `printf` and `stty`, and
  D3 reads `stty size`'s output back. A shell mid-program, or one whose prompt re-wraps the
  echoed command across lines, can break a `contains` — `smoke.mjs` prints `scrollback_tail`
  on any failure so that is diagnosable rather than mysterious.
- `visibility` is reported in the run header. It is not a precondition — the driver is meant to
  work behind other windows (Data Flow step 4) — but a `"hidden"` run that fails intermittently
  should be re-read with that in view before the driver is blamed.

**Hygiene, binding on every scenario below that types or keys into a terminal — D3–D7:** each
one starts with `zoom 1`, then `focus board`, then
`focus <term>` — per #162, `focus()` on an already-focused textarea does not restore the caret,
so a blur is the only clean reset — and each uses its **own sentinel string**, minted from a
per-run nonce. `scrollback_tail` spans 40 lines, so an earlier scenario's echo would satisfy a
repeated `contains` and turn a later scenario green without doing anything. The runner asserts
sentinel uniqueness across the run and fails if two scenarios collide. The leading `zoom 1` is
not decoration: zoom persists to `state.json`, so without it a re-run after D2 starts at 0.5 and
every grip delta, cell point and patched `getBoundingClientRect` in D3–D7 shifts. The geometry-only
scenarios (D1, D2, D8, D9(a), D9(b), D10) need no focus reset, and **D9(c) is the deliberate
exception**: it mints a sentinel like the rest but leaves the terminal *unfocused* on purpose,
because that is the condition under test.

- **D1 [1] — projection:** `snapshot` at zoom 1, then at zoom 1.7. In both, every card with a
  non-null `screen_rect` matches its `board_rect` projected through `viewport` (S7's function)
  within **±1 px**. The tolerance is real and bounded: `desktop/src/kit/docZoom.ts:64` rounds the
  wrapper translate to `var(--device-px)`, so the painted position differs from the exact
  projection by at most half a device pixel.
- **D2 [1] — zoom persists as an OS fact:** record `.dev/state.json`'s mtime; `dev zoom 0.5`;
  `snapshot --until 'viewport.zoom == 0.5'` exits 0; then poll the file **shell-side** until its
  mtime advances and its active board's `zoom` reads `0.5`. The persist is debounced 200 ms in
  `App.tsx`, so the wait is on the file, not on `--until`.
- **D3 [2] — resize reaches the PTY's winsize:** `zoom 1`; `focus board`; `focus <term>`;
  `resize <term> 600x400` (pinning zoom and start size so the grip delta is exact); read `cols0`
  from a snapshot; `resize <term> 800x600`, whose reply must report `to` within **1e-6** of
  `{w: 800, h: 600}` (zoom is pinned to 1 so the grip delta is exact, but the card's stored frame
  can be a float from an earlier gesture and `w0 + (800 − w0)` need not be bit-identical to 800 —
  a runner comparing with `===` would flake);
  `snapshot --until 'cards[<term>].board_rect.w ~= 800'`;
  `snapshot --until 'cards[<term>].term.cols != <cols0>'` (the frame settles before xterm refits
  and the daemon `Resize` lands, so the two waits are separate); `type <term> "stty size\n"`;
  `snapshot --until 'cards[<term>].term.scrollback_tail contains "<rows> <cols>"'` using the
  `rows`/`cols` from that same snapshot. The last step is the OS fact: the PTY winsize changed.
- **D4 [2] — #162 regression, caret variant:** `focus board`; `focus <term>`;
  `type <term> "<sentinel>a"`; `resize <term> 700x500`; `type <term> "b\n"`;
  `snapshot --until 'cards[<term>].term.scrollback_tail contains "<sentinel>ab"'`. **No focus
  round-trip anywhere between**, and both `type` replies must report `dropped: []`. This is
  issue #162's own repro.
- **D5 [2] — #162 regression, Range variant:** `focus board`; `focus <term>`;
  `type <term> "echo <sentinel>\n"`; `key <term> contextmenu`; `snapshot` asserts
  `active_element.selection_type == "Range"` and **fails the run** if it is `Caret` — an empty
  right-click degrades to a caret and would silently re-run D4 under a different name;
  `resize <term> 720x520`; `type <term> "<sentinel2>a"`; `type <term> "b\n"`; tail contains
  `<sentinel2>ab`. **A second sentinel, not a bare `ab`:** D4's echo is still inside the 40-line
  tail and would satisfy `contains "ab"` on its own, which is the same hygiene this section
  mandates two paragraphs above. This is
  the branch `flushesOnResize`'s `Range` + `TEXTAREA` case was written for. **Named dependency:**
  the `Range` comes from xterm's `rightClickSelectsWord`, which `TerminalCard.tsx` does not set,
  so it takes xterm's own default — which is `isMac`, i.e. `true` here (the typings declare it a
  plain `boolean?`; the bundle defaults it to the platform check, not to an `'auto'` sentinel). That default is an assumption, and the
  hard `selection_type == "Range"` assert above is precisely its guard: if xterm ever changes it,
  D5 fails loudly at that line instead of quietly degrading into a second D4.
- **D6 [2] — bytes reach the PTY, exactly once:** `focus board`; `focus <term>`;
  `type <term> "printf <sentinel>\n"`; the tail contains `<sentinel>` and **not** its
  character-doubled form. The doubling check is the end-to-end guard on S19's inert bracket
  (Decision 1): if the keydown also delivered the character, the echo
  would show each character twice and every #162 scenario would be vacuous. Scroll-to-bottom
  (#155) is deliberately **not** asserted — no verb scrolls the viewport, so it would hold
  trivially.
- **D7 [2] — foreground process, both directions:** `focus board`; `focus <term>`;
  `type <term> "sleep 100\n"`; `snapshot --until 'cards[<term>].term.proc == "sleep"'` (the
  daemon polls `TermProc` at 750 ms, so the wait is required); `key <term> "ctrl+c"`, whose reply
  body reads `{ "combo": "ctrl+c", "events": ["keydown","keyup"] }` — no `keypress`, matching S10;
  `snapshot --until 'cards[<term>].term.proc != "sleep"' --timeout 3000`. The OS fact is that
  the foreground process changed, twice.
- **D8 [1] — focus and blur:** `focus <term>` → `focused_card == <term>`,
  `active_element.card == <term>`, `active_element.tag == "TEXTAREA"`; then `focus board` →
  **both** `focused_card == null` (the app's selection cleared) and `active_element.card == null`
  (keyboard focus left the card) — the two are separate facts and a blur that moved only one of
  them is the failure this scenario exists to catch. Terminal cards only (S41).
- **D9 [1/2] — the failure paths are reachable:** (a) **[1]** `dev focus <unknown>` exits 1 with
  `no_such_card` (a stage-1 verb, so the whole of D9(a) lands with stage 1); (b) **[1]**
  `snapshot --until 'viewport.zoom == 99' --timeout 300` exits 1 with `timeout`, the body carries
  the final snapshot, and the command **returns in under 800 ms** (a 300 ms budget plus at most
  one 50 ms poll plus process start) — the only observable discharge of the 50 ms poll interval,
  which a 1 s loop would blow; (c) **[2]** after
  `focus board`,
  `dev type <term> "<sentinel>"` exits 1 with `not_focused` **and**
  `snapshot --until 'cards[<term>].term.scrollback_tail contains "<sentinel>"' --timeout 500`
  exits 1 with `timeout` — the operational form of "the tail never gains that sentinel", proving
  the precondition ran before any event was dispatched rather than after.
- **D10 [1/2] — a clamped request is reported, not refused:** (a) **[1]** `dev zoom 99` exits 0
  with `{"zoom": 3}` and the next `snapshot` reads `viewport.zoom == 3`; `dev zoom 0.01` exits 0
  with `{"zoom": 0.1}`; restore with `dev zoom 1`. (b) **[2]** `dev resize <term> 10x10` exits 0,
  its reply's `to` is `{w: 160, h: 90}` (the card minimum), and the next snapshot's `board_rect`
  agrees — then **restore with `resize <term> 600x400`**, because a card left at 160×90 is ~15
  columns wide and would wrap every later scenario's sentinel across lines, breaking `contains`
  for reasons that have nothing to do with the bug under test. Both halves pin that a reply body carries the **observed** result rather than an echo of
  the request — the failure mode is a driver that reports `{"zoom": 99}` and lets a scenario
  believe the board is somewhere it cannot be. (b) is also the closest thing to a check on the
  two-frame settle: it fails for any driver that builds the reply from the request or from
  pre-gesture state.

## Alternatives Considered

### `tauri-driver` / WebDriver

The official answer, and it would give a real automation protocol for free. Rejected because it
supports Linux and Windows only — there is no macOS WKWebView driver, and Tarmac is macOS-only.

### Extend the Playwright WebKit harness in `.dev/key-harness/`

Already exists and already found #162's mechanism. Rejected as the *shipping* answer because it
runs xterm in Playwright's WebKit, not in the real Tauri WKWebView, so it misses compositor,
focus and IME behaviour that has already misled this repo. It stays as the unit-level
complement — it is where a hypothesis gets cheap, and where the `execCommand` pre-check ran.

### Call the component handlers directly (expose a test API on `window`)

Far less code. Rejected because it tests the wrong thing: #162 lived *in* `CardShell`'s pointer
handler, and #155/#156 live in the browser's own event dispatch. A driver that calls handlers
can never catch the class of bug it exists for.

### Add `dev` verbs to the daemon socket instead of a second socket

No new endpoint, no new resolver. Rejected: the daemon owns PTYs and files and knows nothing
about screen rects, focus or selection — it would have to proxy every request to the app anyway
— and it would put a debug-only surface on the release wire contract, where the additive-only
rule makes it permanent.

### Screenshot-based assertions

`screencapture -l <windowid>` already works with no human. Rejected as the *primary* mechanism:
a pixel diff cannot tell you `activeElement` is the textarea or that the selection is a `Range`,
which is what every bug on the list turned on. Screenshots stay available to a scenario that
wants one.

## Security Considerations

The endpoint executes UI actions on request, so it is treated as debug-only machinery:

- The Rust halves are behind `#[cfg(debug_assertions)]` on **both** ends, and the predicate is
  the same one the audited channel mapping uses (S65), so a release build has no listener and a
  release CLI has no verb (Q1). The **third** piece is TypeScript and has no `cfg`: `App.tsx`'s
  `installDevDriver` call is gated on `import.meta.env.DEV`, so the listener is not installed —
  and, Vite dead-code-eliminating the branch, not even bundled — in a production build. Q1
  observes all three at once: no socket, no verb, no listener.
- The socket is mode `0600` under the user's own `channel_dir` (S66), so it is reachable only by
  the user already running the app.
- It accepts no code: every verb is a fixed enum variant with typed arguments. `--until`
  expressions are evaluated by a hand-written parser over the snapshot object (S25–S34), never
  by `eval`.
- A live sibling socket is never unlinked or taken over (S67), so one worktree's driver cannot
  reach another worktree's app.

## Trade-offs and Limitations

- **`make qa` is not CI.** The `[D]` scenarios are the ones that prove the feature works, and no
  automated gate runs them — they need a window. The mitigation is that they are one command and
  fast; the residual risk is that someone lands a `CardShell` change without running them.
- **`type` cannot drive ⌘C / ⌘V** (S14). Those depend on WebKit's native Edit-menu action, which
  untrusted dispatched events never trigger. Clipboard behaviour stays a hand check.
- **`focus <term>` has a side effect on mouse-reporting programs** (Q3): xterm's `mousedown`
  handler sends a button-press report to the PTY. Real clicks do this too, so it is faithful
  rather than wrong — but a scenario's `scrollback_tail` assertions must tolerate it.
- **The driver turned out to be free of behavioural production-code change.** This spec expected
  one — the `CardShell` pointer-capture guard — and stage 2 measured the premise away (see the
  scope list above): the requirement is a constraint on the driver's own plan, not a guard in the
  component. Every remaining touch costs nothing at runtime: two type-level widenings
  (`TermHandle`, `xtermKittyFlags`'s parameter) and `App.tsx`'s `installDevDriver` call, which is
  dead code in a production build.
- **Doc cards are drive-only, not type-able.** `focus` rejects them (S41) and there is no doc
  typing verb; doc cards are read-only today, so there is nothing to type into.
- **Deliberately out of scope**, each worth its own issue if wanted: switching the active board
  (the driver reads and drives the active board only, and a card on any other board is
  `no_such_card`, S39); `move`/`pan`;
  `reset --fixture` (needs a daemon protocol addition or a `TARMAC_STATE` restart);
  `events --follow` (needs a daemon-frame tap in `bridge.rs`); screenshots (already available
  via `screencapture`); zoom via wheel-event injection.
- **A second listener is a second thing that can leak a socket file.** S67/S68 bound it, but the
  failure mode — a stale `tarmac-dev.sock` after a hard kill — is real and is handled by the
  connect-then-replace rule rather than by never happening.

      `kit/termKeyRoute.ts`'s `xtermHandlesKey`, whose last line is
      `return (kittyFlags & 8) !== 0 || key.length !== 1` — so the bracket must carry the **real
      single character** as `key`, which is exactly the shape it returns `false` for.
      `key: "Unidentified"` was the first draft's answer and is wrong in the opposite direction:
      12 characters fails `key.length !== 1`, xterm owns it, and under a kitty program its
      encoder can emit an escape sequence. `code: ""` keeps it clear of `kit/termKeyBinding.ts`'s
      code-keyed #21 rows and `keyCode: 0` keeps it clear of `kit/imeGuard.ts`'s `229` sentinel;
      neither is read by `xtermHandlesKey` (S19, S24). D6's no-doubling assertion and Q2's
      knockout are the two independent guards.
- [ ] Is the closed `<combo>` set wide enough for stage 2? It is pinned as the **floor** — the
      keys the scenarios here need (`enter`, `tab`, `escape`, `backspace`, the four arrows,
      letters and digits, `ctrl`/`shift`/`alt`). Widening it is purely additive, but if the first
      scenarios written against the driver want function keys, `home`/`end`, or `page up`/`down`,
      that should land in stage 2 rather than as a follow-up.
- [ ] Should `make qa` be able to **start** the app itself (spawn `make run`, wait for the
      socket, tear down)? It would make the suite one command from cold. Out of scope here: it
      needs a headless-window story and would make a failing scenario much harder to inspect,
      since the window would be gone. Revisit once the scenarios have some mileage.
- [ ] `--until` polls at 50 ms with a 5000 ms default. If D7's `TermProc` wait (750 ms poll)
      turns out to dominate the suite's wall clock, consider a per-verb default rather than one
      global one. Not worth pre-optimising.
