# 2611.0008 The bell dot clears on user input only

**Date:** 2026-11-14
**Status:** accepted (2026-11-14, decision Q4 of design 2611.0006)
**Author:** EP Lin
**Issue:** [#343](https://github.com/pingeplin/tarmac/issues/343) `fix(terminal): clear the bell dot on user input only, not on engine replies`
**Branch:** `fix/343-bell-user-input`, from `main` at `1059618`
**Design doc:** [2611.0006](../../docs/designs/2611.0006_agent_reports_inbox_wait_resume.md), Q4 (with R2)

## Context

What the code does today (`e5ce4c9`):

- **One callback for everything.** `TerminalView` (`app/Sources/TarmacTerm/TerminalView.swift`) sends every byte for the PTY through one callback, `onInput: (([UInt8]) -> Void)?`. The bytes come from two kinds of source:
  - **The user:**
    - key presses (`keyDown` → `sendKey` → `sendTyped`). The ⌘ and ⌃ chords that `performKeyEquivalent` takes also end in `keyDown`;
    - bytes from the host's `keyOverride` for a chord (`keyDown` → `sendTyped`, before any `sendKey`);
    - key releases (`keyUp` → `sendKey` with `action == .release` → `send`, not `sendTyped`);
    - modifier-key events (`flagsChanged` → `send`);
    - text and IME commits (`insertText` outside a key event, and `sendText` → `sendTyped`);
    - paste (`paste(_:)` → `sendTyped`);
    - mouse reports (`report` → `send`), from `mouseDown`, `mouseDragged`, `mouseUp`, the right and other buttons, and wheel steps while the program tracks the mouse (`scrollWheel`);
    - wheel steps in the alternate screen, sent as arrow keys (`scrollWheel` → `send`).
  - **The terminal, by itself:**
    - engine replies to a program, such as DA1 or a cursor report (`engine.effects.onWritePty`, wired at `wireEffects`). `replay(_:)` mutes this hook, so a replay sends nothing;
    - focus reports (`reportFocus`, from `becomeFirstResponder` and `resignFirstResponder` → `send`);
    - the colour-scheme report on a theme change (`theme` setter → `send`).
  - `send(_:)` drops an empty byte array. A key that the encoder turns into no bytes sends nothing, so it clears nothing.
- **Other code that sets or wraps `onInput`.** These break at compile time when the signature changes:
  - `AppController+Terminals.swift`, `makeTerminalView` (the real host);
  - `app/Sources/TarmacApp/Dev/DevVerbs.swift`, `insert(_:into:)`, which wraps `onInput` to see whether an insertion sent bytes, and forwards them;
  - `app/Sources/tarmac-term-demo/main.swift`;
  - three setters in `TerminalViewTests.swift` (`setUp`, and two tests that build their own view).
  
  `TerminalEffects.onWritePty` is not a host callback and keeps its signature.
- **The app clears the bell on all of them.** `AppController.terminalDidSend` (`app/Sources/TarmacApp/AppController+Terminals.swift`) forwards the bytes with `client.input` and calls `clearBell(termID:)` for all of them. So a program can put out its own bell: it rings, then asks a query or gets a focus change. A focus-out report is the common case: the user clicks another card and the card that rang gets `\e[O` and loses its dot.
- **The documented rule.** `docs/architecture.md` (*Terminal cards*, "Honest signals") says the dot shows "until bytes leave for that PTY or the card becomes prime by a press".

## Motivation

The bell `●` must mean "this terminal rang, and the user has not touched it since". Design 2611.0006 uses the same predicate to mark agent reports read (`Input.typed`, R2) and to arm the resume chip (R4). This fix makes the predicate exist and gives the bell the meaning it was meant to have. It ships before slice 2 of that design.

## Proposed Solution

- **Each send gets a source.** `TerminalView` tells the host the source of every byte it sends:

  ```
  public enum InputSource: Sendable, Equatable { case user, terminal }
  public var onInput: (([UInt8], InputSource) -> Void)?
  ```

  Each call site in *Context* passes the source listed there. Every user site passes `.user`. The engine-reply hook, `reportFocus` and the `theme` setter pass `.terminal`.
- **No default source.** The view's internal `send` takes a required `source` argument with no default value. `sendTyped` always sends `.user`. A new send site then does not compile until it picks a source.
- **The app clears on user input only.** `AppController.terminalDidSend(termID:_:source:)` still forwards every byte to the daemon unchanged, for both sources. It calls `clearBell` only when `source == .user`. The comments on `terminalDidSend` and `clearBell` say this (they now say "any bytes").
- **Other `onInput` users keep working.** `DevVerbs.insert(_:into:)` passes the source through to the callback it wraps. `tarmac-term-demo` accepts the new signature and forwards bytes as before.
- **Nothing else changes.** The other clear rule, "the card becomes prime by a press" (`AppController+Focus.swift`, `select`), is unchanged. The wire is unchanged. A change of keyboard focus alone does not clear a lit dot any more: the focus report that it sends (only to a program that asked for it) is `.terminal`.
- **Docs.** `docs/architecture.md` *Terminal cards* ("Honest signals") changes "until bytes leave for that PTY" to "until the user sends input to that PTY (a key, a paste, text, a mouse report)". Engine replies and focus reports never clear the dot. The `TerminalView` bullet in the same section says "everything the user does leaves through `onInput`"; it adds that the terminal's own replies and reports leave there too, tagged with their source.

## Acceptance Scenarios

All automated scenarios are XCTest in `app/Tests/TarmacTermTests/TerminalViewTests.swift`. The tests already deliver every input in this list to the view:

| Input | How the existing tests deliver it |
|---|---|
| Key press | `view.keyDown(with:)` with an `NSEvent.keyEvent`, helper `key(_:code:)` |
| Key release | `view.keyUp(with:)`, after `feed("\u{1b}[>3u")` (kitty flags 1 and 2) |
| Paste | `NSPasteboard.general.setString`, then `view.paste(nil)` |
| Text | `view.sendText(_:)` or `view.insertText(_:replacementRange:)` |
| Mouse | `view.mouseDown(with:)` with the `mouse(_:col:row:)` helper, after `feed("\u{1b}[?1000h\u{1b}[?1006h")` |
| Wheel | `view.scrollWheel(with:)` with the `wheel(lines:)` helper |
| Focus | `feed("\u{1b}[?1004h")`, then `window.makeFirstResponder(nil)` and `window.makeFirstResponder(view)` |
| Engine reply | `feed("\u{1b}[c")` |
| Theme | `feed("\u{1b}[?2031h")`, then `view.theme = light` |

Two things are new. A `flagsChanged` event (`NSEvent.keyEvent(with: .flagsChanged, …)`) is not delivered by any test today. A test for a source needs a capture that records the source with each call. The `setUp` capture keeps the flat `sent` bytes (so the old tests stay as they are) and also records `(bytes, source)` for each call. Each new test asserts the bytes **and** the source of that call. A test that sees no bytes (empty `sent`) fails; it does not pass.

### Happy Path (user)

- **S1:** Given a view, when a printable key press is delivered (`keyDown`), then the bytes arrive with `.user`. Also, when `keyOverride` returns bytes for the chord, those bytes arrive with `.user`.
- **S2:** Given a view, when `paste(_:)` runs with text on the pasteboard, then the paste bytes arrive with `.user`.
- **S3:** Given a view, when `sendText("x")` runs, then `x` arrives with `.user`. Also, when `insertText("你", …)` runs outside a key event (an IME commit), then `你` arrives with `.user`.
- **S4:** Given a view whose program turned on the kitty keyboard's report-events flag (`\e[>3u`), when a key is released (`keyUp`), then the release bytes arrive with `.user`. Given a program that makes the encoder report modifier keys, when a modifier changes (`flagsChanged`), then its bytes arrive with `.user`. The test first asserts that the bytes are not empty. It uses the kitty flags that make the encoder report a Shift press. Those flags are found by running the test (the report-all-keys flag, bit 8, is the first to try).
- **S5b:** Given a program in any-motion mouse mode (`\e[?1003h`) and a focused view, when a hover `mouseMoved` with no button is delivered, then the motion report arrives with `.terminal`.
- **S5:** Given a program that enables mouse reporting (`\e[?1000h\e[?1006h`), when a mouse press is delivered, then the report arrives with `.user`. The same holds for a wheel step in this mode, and for a drag (`mouseDragged`).
- **S6:** Given the alternate screen (`\e[?1049h`) and no mouse reporting, when a wheel step is delivered, then the arrow-key bytes arrive with `.user`.

### Edge Cases (terminal)

- **S7:** Given a program that enables focus reporting (`\e[?1004h`), when the view loses and then gains focus, then `\e[O` and `\e[I` each arrive with `.terminal`.
- **S8:** Given a view, when the output `\e[c` (DA1) is fed, then the engine's reply arrives with `.terminal`.
- **S9:** Given a program that asks for colour-scheme reports (`\e[?2031h`), when the theme changes between dark and light, then the report arrives with `.terminal`.
- **S12:** Given a view, when `replay(_:)` is given output with a DA1 query, then no call arrives at all (not even a `.terminal` one). This is today's behavior. It guards the new signature: a replay must not start to send.
- **S13:** Given a program that enables focus reporting, when the view loses focus, a key press is delivered, and the view gains focus, then the calls arrive in this order with these sources: `.terminal` (`\e[O`), `.user` (the key), `.terminal` (`\e[I`). One call's source does not leak into the next.

### QA (dev channel, not automated; `TarmacApp` has no unit tests by design)

Use a `make run` app with its own `DEV_DIR`. Drive keys with `tarmac dev key` and `tarmac dev type`. Both reach the view as real key events, so they count as `.user`.

- **S10:** Click card A so it is the prime terminal. In A, run `printf '\e[?1004h'; sleep 3; printf '\a'; sleep 10`. When the amber `●` shows on A, click another terminal card B. A gets a focus-out report.
  - The `●` on A stays lit after the click.
  - Clicking A again clears it (the press rule, unchanged).
- **S11:** In prime card A, run `sleep 2; printf '\a\e[c'` and click another terminal card B before the 2 seconds end. When the bell and the DA1 reply have both happened, the `●` on A is lit and stays lit.
- **S14:** With a `●` lit on a prime card, `tarmac dev type x` into that card clears the `●`.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

- **TDD.** Write each test first and watch it fail on the unmodified tree (`docs/coding-style.md`).
- **Every send site in *Context* must carry a source.** A new send site added later must not compile without one. The callback signature and the required `send` argument enforce this.
- **Update every `onInput` user** named in *Context* (the app host, `DevVerbs.insert`, `tarmac-term-demo`, and the three test setters) to the new signature. Do not weaken the existing tests.
- **Check the app wiring by hand.** `AppController` has no unit tests, so S10, S11 and S14 are the only check of `terminalDidSend`. Run them on the dev channel before you hand off, and record the result.
- `make test` and `make docs-check` must pass. Do not `cargo fmt`.

Test principles: behavioral over structural; every test can fail; deterministic, isolated, readable (AAA, inline setup).

## Trade-offs and Limitations

- **A wheel step in the alternate screen counts as user input.** The user moved the wheel over that card on purpose.
- **A key release with no press** (for example after a focus change) counts as user input. The user's own key action caused it.
- **Mouse hover does not count (decided 2026-11-14, with Fable).** A hover report (`mouseMoved` with no button down) goes out only when the view has focus and the program's mouse mode takes motion (1003). It takes the `.terminal` source, so it is forwarded but clears nothing. **Why:** on a pannable board the pointer crosses cards on its way elsewhere. Later consumers would then mark an agent report read, or decide the resume chip, for a card the user never looked at. A dot that stays until the next key or click costs almost nothing. This changes today's behaviour on purpose: hover cleared the dot before. A drag (motion with a button down) stays `.user`.
- **A key that sends no bytes clears nothing.** If the encoder gives no bytes (for example a modifier key when no program asked for it), nothing leaves the view and the dot stays. This is the same as today.
- **A dev-driver key or type counts as user input.** `tarmac dev key` and `tarmac dev type` post real key events (or an IME commit) to the view.
