# 2608.0002 Doc-card raster cost — de-promote `.doc-prose pre`

**Date:** 2026-08-28
**Status:** implemented (S12/S13 pending manual QA under `make run` — see Definition of Done); PR [#98](https://github.com/pingeplin/tarmac/pull/98)
**Author:** EP Lin
**Design doc:** [2608.0002](../../docs/designs/2608.0002_doc_card_raster_cost.md) — the decision record; this spec does not re-open any decision it closes
**Issue:** [#76](https://github.com/pingeplin/tarmac/issues/76) (mechanism superseded — see Non-goals)
**Relates to:** spec [2607.0006](2607.0006_magnify_zoom_mode_for_html_cards.md) (frozen-K magnify)

> `2608.0002 S1 — …` so the two namespaces never collide.

## Context

Doc cards lay the prose out once at K× (`DOC_OVERSAMPLE_K = 3`) and hang `scale(zoom/K)` on the bare `.doc-prose-scaler`
(`desktop/src/kit/docZoom.ts:91`, `desktop/src/cards/DocCard.tsx:165`). That transform promotes the scaler to its own composited layer, and a composited
layer is sized by its **element's box**, not by what it paints — so WebKit allocates the full K× box (1176 × 13064 for a 392×310 card) and keeps it that
size at every board zoom. That is the whole 9×, and it is paid at zoom 1 and below as well as above.

The design doc measured each plausible promoter in isolation and found **exactly one survivor**: `.doc-prose pre { overflow: auto }`
(`desktop/src/theme/card.css:302-307`), and only when a code block actually overflows horizontally. `scroll` also promotes; `hidden`, `clip` and `visible`
de-promote identically; `<img>`, `<iframe>` and non-overflowing `auto` divs never promote. A doc with no horizontally-overflowing `<pre>` is therefore
already on the cheap path today.

## Motivation

Six 392×310 doc cards on one board, dpr 2, board zoom 1, real WKWebView: **261 MB** short-doc corpus, **178 MB** long-doc corpus. De-promoting takes the
same board to **81 MB** and **93 MB**. Prose wrap points are byte-identical either way — the oversample survives as a rendering technique; only the
private backing store goes away. No JS, no DOM change, no protocol change.

The reachability half matters as much as the bytes. `white-space: pre-wrap` alone still hides overflow rather than preventing it: with a 200-char
unbreakable token (a path, a URL, base64, a minified line — all common in agent-authored markdown) it leaves `scrollWidth` **4693** against `clientWidth`
1044, clipped at the card edge and unreachable, *the same UX as `overflow: clip`*. `word-break: break-word` is what buys every character back.

## Proposed Solution

### The change

Three declarations in `desktop/src/theme/card.css`, replacing `overflow: auto`:

```css
.doc-prose pre {
  background: var(--term-bg);
  padding: 0.8571em 1em;
  border-radius: 0.5714em;
  overflow: visible;
  white-space: pre-wrap;
  word-break: break-word;
}
```

### What does not change

`desktop/src/kit/docZoom.ts` (no edit of any kind), `DOC_OVERSAMPLE_K`, `MAX_ZOOM`, `.doc-prose`, `.doc-prose-sizer`, `.doc-prose-scaler`, `.doc-scroll`,
`relayout()`, `savedScrollFrac`, `proseNatH`, the MutationObserver/ResizeObserver wiring, the wire protocol, and every existing test. No JS is added and no
DOM node moves.

### The instruments, and what each tier can decide

This is the load-bearing part of the spec. `make test` **cannot** decide most of what matters here, and saying so is not a licence to skip it.

| Tier | Instrument | Can decide | Cannot decide |
|---|---|---|---|
| **1** | Vitest (`make test`) | CSS **rule text** read off disk, pure kit logic | anything requiring layout, paint or composition — Vitest has no layout engine |
| **2** | `desktop/qa/` probe pages on a real engine; WebKit Inspector `LayerTree` (`Layer.memory`, `compositedBounds`); `footprint -p` on `com.apple.WebKit.WebContent` | wrap fingerprints, box geometry, layer presence, process memory | how it feels; 1× crispness |
| **3** | `make run`, by eye, on real hardware | crispness, gesture feel, the R1 invariant in live markdown | nothing automatable — that is why it is Tier 3 |

Two instrument rules carried verbatim from the design doc, because getting them wrong has already cost this repo a session:

- **`ps -o rss=` is blind here** and must not be used: K=3 → 363 MB, K=1 → 390 MB, empty board → 364 MB, no signal, because composited backing stores are
  IOSurface-backed.
- **`LayerTree` alone is insufficient.** It reported *zero* accumulation for the hover-scoped `overflow: auto` defect that `footprint -p` measured growing
  to 394 MB. Every memory claim reads process footprint **beside** layer state, on real WKWebView.
- **dpr is verified at the window**, not at the machine (`backingScaleFactor ≥ 2`), and absolute MB levels compare **within one session only** — earlier
  captures put the same base configuration at 260, 246 and 261 MB. Deltas inside one pinned table are decision-grade; levels across sessions are not.

### Instrument extension the implementer must land first (Tier 2 prerequisite)

`desktop/qa/doc-prose-zoom-probe.html` as committed **cannot decide any Tier 2 scenario**: its `<pre>` carries `data-b-skip` so `armSignature()` never
fingerprints it, its pre content is a single 34-char line that does not overflow, `.prose pre` is a single shared `overflow: auto` rule across all three
arms, and there is no arm for the chosen spelling. Extend it (the design doc's Verification §1 and Follow-up #2 licence exactly this):

1. Give the `<pre>` a `data-b` so it is fingerprinted like every prose block.
2. Add a genuinely overflowing code block and a separate block containing a **200-char unbreakable token**.
3. Make the `<pre>` spelling switchable per run (`base` = `overflow: auto`, `wrapx` = `visible` + `pre-wrap`, `wrap` = the chosen arm) via a URL param, in
   the style of the existing `w`/`h` params, so base and chosen are measurable back-to-back in one pinned session.
4. Report `scrollWidth`/`clientWidth`/`offsetHeight` per code block, and a **composited-layer count for `.doc-prose-scaler`** (`scalerN`).

Then add the standing R1 detector as its own page rendering a doc card's real DOM and reporting whether `.doc-prose-scaler` has its own composited layer,
plus a QA checklist `.md` beside it in the style of `desktop/qa/magnify-card-qa.md`.

## Non-goals

- **`MAX_ZOOM > 3` is not delivered.** Issue #76's second goal stays closed; docZoom S13 (`DOC_OVERSAMPLE_K >= MAX_ZOOM`) applies unchanged to the one and
  only path. Whether de-promotion changes z > K upscale behaviour is UNKNOWN and unmeasured — nothing here licenses a claim either way.
- **Lowering K is out of scope and stays out.** The design's Decision 2 is deliberately still open; the implementer must not resolve it, in either
  direction, as part of this work.
- **Issue #76's CSS-`zoom` mechanism is not built.** It was falsified (seven distinct layouts over nine zoom steps, `savedScrollFrac` spread ≈ 13 lines).
- The stale comment at `desktop/src/kit/docZoom.ts:23` is a known follow-up and stays unfixed here — `docZoom.ts` is byte-unchanged by this spec.

## A premise a scenario must not assert

**`scrollHeight` is not constant across zoom, in any arm.** It is `ceil(natH·z/K)` in the shipped build, under `clip`, and under the chosen arm alike — the
LONG corpus reads 2261 / 4521 / 9042 / 13563 at z = 0.5 / 1 / 2 / 3. The "3278 at every z" figure from an earlier draft belongs to probe arm C, where no JS
sets the sizer height. The zoom-invariant quantity is **natH**; the round-tripping quantity is the **scroll fraction**. No scenario below asserts a constant
`scrollHeight`, and none may be added.

## Acceptance Scenarios

Figures in brackets are the **measured instance** from the design doc's canonical table (dpr 2, z = 1, K = 3, six 392×310 cards, 1400×900 window, macOS
26.6.1). Character offsets are corpus-bound: a re-authored probe corpus will produce different offsets, so the invariant is the pass criterion and the
figure is the reference reading.

### Tier 1 — decided by `make test`

- **S1:** Given `desktop/src/theme/card.css` on disk, when the `.doc-prose pre` rule body is extracted by exact selector (the `ruleBody()` helper already in
  `docZoom.test.ts`), then it declares `overflow: visible`, `white-space: pre-wrap` and `word-break: break-word`.
- **S2:** Given the same rule body, when it is searched for `overflow: auto`, then there is no match — **and** `.doc-scroll` still declares
  `overflow-y: auto`. The assertion is scoped to the rule body precisely because a whole-file grep would trip on `.doc-scroll`; the second half fails if the
  edit was made too broadly.
- **S3:** Given the change, when the existing suite runs, then **docZoom S12 passes unchanged**. This holds for a reason worth stating rather than
  discovering: `ruleBody()` matches the exact string `".doc-prose {"`, which occurs **once** in `card.css` (line 260) and is **not** a substring of
  `".doc-prose pre {"`. S12 therefore reads the `.doc-prose` body only, which this change does not touch — it still contains no `var(--zoom)` and still
  references `var(--oversample-k)`.
- **S4:** Given the change, when the existing suite runs, then **docZoom S13 passes unchanged** — `DOC_OVERSAMPLE_K >= MAX_ZOOM` and
  `MAX_ZOOM / DOC_OVERSAMPLE_K <= 1` still hold, because this change alters neither K nor `MAX_ZOOM`.
- **S5:** Given the change, when the existing suite runs, then **docZoom S1–S6/S14** (which assert the exact `docWrapperBox()` / `docProseScaler()`
  strings) **pass unchanged** — decided by `make test`, the same as S3/S4. Separately, when the PR diff is read, `desktop/src/kit/docZoom.ts` shows no
  change. *This half is not a Vitest assertion* — a test that shells out to `git diff` is vacuously green post-merge (working tree vs. HEAD is empty by
  definition) and reports nothing about the PR itself — so it is decided by **PR diff review**, not `make test`.

### Tier 2 — [QA] decided by a probe on a real engine

- **S6:** Given the extended probe with the `base` and `wrap` arms measured back-to-back in one pinned session, when a 0.5 / 1 / 2 / 3 / 1 sweep is run,
  then every **prose** block's line-start character-offset signature (every heading, paragraph and list item — `h1`, `p0`…`p10` in the design's corpus) is
  **byte-identical between the two arms at every step**, and the cross-arm diff names `pre` as the **only** differing block. *Instrument:* probe
  `armSignature()`. The return leg to 0.5 is load-bearing — it separates
  "re-wrapped once" from hysteresis. Line counts are not an acceptable substitute: the design measured a count holding at 6 while the breaks moved through
  three distinct regimes.
- **S7:** Given the same sweep, when the `<pre>` signature is compared across arms and across zoom, then it changes **exactly once** — base → chosen — and
  is then identical at every zoom step of 0.5 / 1 / 2 / 3 / 1 on both corpora. *Measured instance:* signature `"0"` → `"0,38,76,113,150,181,216,254"`
  (1 line → 8), `offsetHeight` 143 → 643 K-px (+167 visual px per code block), `scrollWidth` 6257 → 1044. *Instrument:* probe `armSignature()` + per-block
  `scrollWidth`/`offsetHeight`. Deliberate one-time reflow of code blocks on upgrade, then no drift.
- **S8:** Given a `<pre>` containing a 200-char unbreakable token, when it is measured under the `wrap` arm, then `scrollWidth == clientWidth` [1044] — every
  character reachable. Under `wrapx` (`pre-wrap` without `word-break`) the same token reads `scrollWidth` **4693** against `clientWidth` 1044, 4.5× overflow
  clipped at the card edge. *Instrument:* probe per-block `scrollWidth`/`clientWidth`. This scenario is what makes `word-break` load-bearing rather than
  cosmetic: without it the chosen arm collapses to `clip`'s behaviour on exactly the lines that matter, and the premise "long code lines wrap instead of
  being cut off" is **FALSE**.
- **S9:** Given the chosen arm over the same sweep, when the sizer and scroller are read, then (a) `proseNatH` is **zoom-invariant**, (b) the sizer height
  equals `ceil(natH·z/K)` at every step [held 30/30 rows across every arm and zoom], (c) `scrollHeight == sizerHeight` exactly, and (d) a stored scroll
  fraction round-trips, its worst drift being integer-`scrollTop` quantisation at z = 0.5 — *smaller* for the wrapping arm than for `clip`, a taller
  document having more scroll range. *Instrument:* probe geometry readout. **Not** a constant `scrollHeight` (see the premise section above).
- **S10:** Given six doc cards on both corpora in one session with dpr verified at the window (`backingScaleFactor ≥ 2`) and a calibration row reproducing
  the base reading first, when the chosen arm is measured, then (a) **`scalerN == 0` and `.doc-prose-scaler` is absent from the layer tree at every step of
  the 0.5 / 1 / 2 / 3 / 1 sweep**, including the adversarial case of a `<pre>` that really overflows under `visible`; and (b) process footprint on both
  corpora reproduces the canonical table against a **same-session** base row: **261 → 81 MB** SHORT and **178 → 93 MB** LONG (Engine A layer bytes
  240.44 → 64.50 and 157.41 → 75.39). *Instrument:* `LayerTree` for (a), `footprint -p` for (b) — **both**, per the instrument rules above. Record the
  exact readings and the full configuration beside every figure.

  (a) is the sharp criterion and the one that decides this scenario: it is binary, engine-independent, and a single promoted scaler falsifies it. (b) is
  corroborating and carries **no numeric pass floor on purpose** — the design doc sets none, and inventing one here would be a fabricated number. Absolute
  MB do not compare across sessions (the same base configuration has read 260, 246 and 261 MB), so (b) fails only if the drop is absent or is inside that
  session's own calibration spread, and the base row must be captured in the same session to make the comparison at all.

  Two readings that are expected and must **not** be logged as regressions: the chosen arm costs **+6 MB (+7.9%) against `clip` on SHORT** and nothing on
  LONG — attributed entirely to `.doc-scroll`'s own tiled backing store, and the price of reachability; and footprint drifts **93 → 97 MB after 48 scroll
  cycles → 99 after 96** — sub-linear, matched by controls under the same driver (`clip` 93 → 95, base 178 → 181), with a rest re-read returning 93. That
  is a scroll-position-dependent working set, not a leak. Contrast the disqualified `:hover` arm at +6.3 MB *per event*, to 394 MB — that is what a real
  ratchet looks like. Known gap carried forward from the design: **z = 0.5 process memory is unmeasured**, and the 260-vs-246 base spread between earlier
  sessions is still open.

### Tier 3 — [QA] decided only by hand in the real app (`make run`, fresh dev daemon, installed `tarmacd` killed first)

No available instrument can automate these. That is a fact about the instruments, not a reason to skip them.

- **S11 (R1 — the new invariant is load-bearing and silently reversible):** Given a markdown doc whose raw HTML carries `will-change` or a 3D transform,
  when it is opened as a doc card, then the standing detector page **reports `.doc-prose-scaler` as composited** and the reader is told. *Measured
  instance:* 59.69 → 238.55 MB on Engine A — read the ~4× ratio, not the levels. The failure degrades to *today's* cost and never worse, and it is
  otherwise silent: no error, no visual difference, only memory. Promotion is an engine heuristic observed on these builds, not a specced contract, so a
  WebKit update is a second way it flips with no code change here. *Instrument:* the new `desktop/qa/` detector page + `footprint -p`; explicitly **not**
  Vitest, which can pin the rule text (S1/S2) but can never observe promotion.
- **S12 (R2 — 1× crispness):** Given a true 1× panel, when a doc card with code blocks is read at board zoom 0.5 / 1 / 2, then glyphs are no softer than
  before the change. *Instrument:* by eye under `make run`, the same procedure as `desktop/qa/one-x-display-crispness.md`. Open because the compositor
  capture of the de-promoted arm reads 1.2% mean luminance difference and **−1.6% sharpness** against base — pixel-aligned, so real rather than a
  registration artifact — and that delta has **no K=1 calibration**, so how much is inherent to compositing versus caused by de-promotion is unknown.
  "Indistinguishable at 2×" is the strongest claim currently available, and it is a 2× claim only.
- **S13 (R3 — gesture feel):** Given a board of de-promoted doc cards, when it is pinch-zoomed and panned continuously across 0.5 → 3 → 0.5, then it feels
  no worse than before. *Instrument:* by hand under `make run`. Open because the only frame timing available was headless **under a 30 fps cap** — p99 38 ms
  for the de-promoted arm against base's 49 ms, which is "no regression detected", not a win.

## Alternatives Considered

All measured and closed in the [design doc](../../docs/designs/2608.0002_doc_card_raster_cost.md#rejected-and-disqualified-alternatives--measured); listed
here only so nobody re-derives them.

| Option | Verdict | The deciding fact |
|---|---|---|
| `overflow: clip` | runner-up | de-promotes identically (76/93 MB) but truncates long code lines where nobody can reach them |
| `overflow: hidden` + JS wheel handler | rejected | the only spelling that adds JS; reaches wheel users, never keyboard-only ones |
| `pre:hover { overflow: auto }` | **disqualified** | each promote↔de-promote of a *tiled* scaler adds ~6.3 MB, unreturned: 93 → 394 MB over 48 hovers |
| Issue #76's CSS `zoom` = board zoom | **falsified** | seven distinct layouts over nine zoom steps; `savedScrollFrac` spread ≈ 13 lines |
| frozen `zoom: K` + outer `scale(z/K)` | rejected | no measured benefit, against a silent 3×-short sizer hazard |
| `content-visibility: auto` / windowing | not viable | both preserve the *box*, and the box is what sizes the layer |
| lower K (2 or 2.5) | **still open — out of scope here** | attacks the multiplier, not the promotion; does not stack, and costs `MAX_ZOOM` 3 → 2 |

## Trade-offs and Limitations

- **Code blocks re-wrap once, deliberately.** Every existing doc card's `<pre>` gets taller on upgrade (+167 visual px per block on the probe corpus). This
  is the cost of reachability and is not a regression.
- **+6 MB on SHORT against `clip`.** The chosen arm is not the cheapest spelling; it is the cheapest one where every reader sees every character.
- **The invariant is new, silent and user-content-reversible** (S11). Markdown is user content; there is no code guard, only a detector.
- **One document family, one machine, one OS.** What fraction of a real corpus carries horizontally-overflowing `<pre>` is unknown — a doc without one is
  already on the cheap path today, so the win is REASONED to be typical of agent-authored markdown, not measured across a corpus.
- **1× crispness and gesture feel are UNKNOWN**, not verified-good (S12, S13).
