## Gate

Written 2026-11-14 from the code at `main` 882aa59, and from spec 2611.0009 as accepted on `feat/348-agent-report` (9e57d19). Slice 2 then merged (#350, `main` 617f1d2). Each slice 2 fact used here is marked **(2611.0009)**, and was checked against the code at 617f1d2 on 2026-11-14 (*Context*). Line numbers are those of 617f1d2.

The approach is the design's, and it is not open here. These rules of the design and of slice 2 bind this spec:

- **One fixed entry.** The agent's config holds only a call to `tarmac hooks run claude`. The mapping lives in the binary, so `brew upgrade` updates it (design §5).
- **`install` merges** and backs up first. It finds its own entries by the command string. A re-run changes nothing. `uninstall` removes only its own entries. `status` reports three things: whether the entries are there, whether they have the current form, and whether `tarmac` is on `PATH`.
- **`hooks run` always exits 0.** With no daemon it ends in 200 ms or less. It never prints to stdout. With no `TARMAC_TERM_ID` it does nothing.
- **Only the CLI knows an agent.** The daemon and the app get plain `Report` frames. This slice changes **no protocol, no daemon and no app code**.
- **(2611.0009) answer 4.** `tarmac report clear ""` exits 0, so that a generic hook never gets exit 2.
- **The flags are `skill install`'s.** That means `--target`, `--scope`, `--dry-run`, the `Target`/`Scope` enums, the `Env` that reads `$CLAUDE_CONFIG_DIR`, and the aggregate exit code.

**Step 0, before any mapping code: capture real hook input.** 2611.0009 OQ1 leaves the `Notification` hook and interactive mode to this slice, "before it maps them". The `notification_type` field (D3) is known from the docs only. So the implementer first does this:

- Use a temp `CLAUDE_CONFIG_DIR` (OQ2), or the owner's hand run. Install by hand a handler `cat > <tmp>/hook-<event>-$$.json` for `Notification` (no matcher), `Stop`, `UserPromptSubmit` and `SessionStart`. (`<tmp>` here and below is a directory made with `mktemp -d` for the run, never a path under the user's home config.)
- Run one interactive `claude` session in a dev Tarmac terminal. It must reach a permission prompt and end one turn. In the same session, make Claude ask a question with `AskUserQuestion`, and reach a plan approval (plan mode).
- Keep the captured files as the fixtures of S5, S6 and S19, with any personal text replaced.
- Record whether the permission `Notification` payload has `notification_type: "permission_prompt"`.
- Record the `notification_type` (if any `Notification` comes) for `AskUserQuestion` and for plan approval (OQ4). They are not mapped in this slice.
- **The pipe buffer (D9).** Install, by hand, a handler `exit 0` (it reads nothing) on `Stop`, and get a `Stop` whose `last_assistant_message` is over 64 KiB (ask for a long answer). Record whether Claude shows a hook error or logs one in `claude --debug`. If it does, `hooks run` changes: with no `TARMAC_TERM_ID` it drains stdin (to the same 4 MiB and 1 s limits) before it exits, and S23 changes with it. The owner is told.
- **If the permission `Notification` has no `notification_type: "permission_prompt"`** (the fourth bullet), D3 falls back to the matcher form: the `Notification` group gets `"matcher": "permission_prompt"`, and the binary maps every `Notification` that it gets to `blocked`. The spec's current form, S5, S10(e) and S19 change with it. The owner is told before code is written.

**Owner decisions (2026-11-14, reviewed with Fable).** The design does not settle these, so this spec had to make them. Each one is marked **[D1]…[D12]** in the body. All twelve are accepted as recommended, with these caveats:

- **D1–D4, D11, D12:** accepted as written.
- **D5.** A user who edits our handler (for example its `timeout`) makes it "old form", and `install` overwrites the edit with the current handler. The help text says so.
- **D6.** `preserve_order` goes in `[workspace.dependencies]`, so a `cargo build -p tarmacd` gets the same `serde_json` as the shipped workspace build. The `state.json` before-and-after comparison stays.
- **D7.** Every write prints the backup path. In project scope the backup is a new untracked file in the repository.
- **D8.** A target that is not writable (a read-only file or directory) fails closed: exit 1, nothing written, no backup.
- **D9.** Step 0 also checks what Claude does when a hook exits before it reads a payload larger than the pipe buffer.
- **D10.** The hook removes control characters (such as ESC) itself, before it folds whitespace (clarified in review, 2026-11-14). At 617f1d2 `cap_report_text` only caps; it removes nothing (*Context*).
- **OQ3 → project scope writes `.claude/settings.local.json`** (the personal file), not `.claude/settings.json`. Claude git-ignores `settings.local.json` only when Claude creates it. A file that `tarmac` creates, and its backup, can be committed, so a project-scope write prints a one-line hint.
- **OQ4 → `idle_prompt` is not mapped.** After a `Stop`, an idle notification would turn a true `done` into a false `blocked`. Step 0 records which `notification_type` values `AskUserQuestion` and plan approval send. They are real blocked states with no `Stop`, and mapping them later is a binary-only change (D3).

- **Answers to the spec review (2026-11-14, with Fable):**
  1. **Removing control characters.** Remove only the characters that are control characters and not whitespace (`is_control() && !is_whitespace()`). Then fold each run of `char::is_whitespace`, trim, and cap. A blanket "remove every control character" would delete `\n`, `\v`, `\f` and U+0085, which are also whitespace (measured).
  2. **A handler with our exact command plus an `args` key** is foreign, and it is left alone.
  3. **The hook's stderr line** is `tarmac: hooks run: no answer from the daemon in 500 ms`.
  4. **Symlinks.** The result lines name the link path. The `backup:` line names the real (target) path, and so does the project-scope git hint.
  5. **Status.** The `PATH` line says `(this binary)` or `(another binary than this one)`. The check compares canonical paths.
  6. **The backup keeps the original file's permission bits.** Measured: `fs::copy` gives 0600.
  7. **An empty `settings.json`, or one with a BOM, is refused** (exit 1). The message names the cause, and the file is not treated as `{}`.
  8. **Step 0 also captures a real `settings.json`.** Claude writes it through `/config` in a temp `CLAUDE_CONFIG_DIR`, and it becomes a byte-identity fixture. Step 0 first confirms that this file, and not another config file, appears and holds nested arrays.
  9. **S21 takes the fastest of N runs, as S20 and S23 do.** Both bounds are asserted on that run: at least 450 ms and at most 1000 ms.

## Context

What the code does today (617f1d2, with slice 2 merged):

- **The CLI has no JSON.** `tarmac-cli/Cargo.toml` depends on `tarmac-protocol` only. Its comment says: "std-only on purpose: `tarmac open` is called by agents/hooks and must start fast". `tarmac-protocol` depends on `serde`, `rmp-serde` and `serde_bytes`, but not on `serde_json` (`tarmac-protocol/Cargo.toml`). `push.rs:1-3` says that the CLI does not parse JSON on purpose: the daemon is the one checker.
- **`serde_json` is in the workspace.** `core/Cargo.toml` has `serde_json = "1"` (locked at 1.0.150). `tarmacd` uses it for `state.json` (`persist.rs:79,181`: typed structs whose only map is a `BTreeMap`, `persist.rs:52`; no `serde_json::Value` is persisted) and for the `push` check (`docs.rs:93`, parse only). `indexmap` is **not** in `core/Cargo.lock`.
- **Plain `serde_json` sorts keys.** Without the `preserve_order` feature, `serde_json::Map` is a `BTreeMap`. A parse-and-write would then sort every object of the user's file.
- **`preserve_order` has two traps** (`serde_json` 1.0.150 `src/map.rs`). `Map::remove` is `swap_remove`: it moves the last key into the removed key's place. Only `shift_remove` keeps the order of the other keys. `Map::insert` of a key that is already there keeps the first position and takes the new value, so a duplicate key keeps its first position and its last value.
- **`skill.rs`** owns `Target {ClaudeCode, Codex}` with `Target::ALL`, `Scope {User, Project}` and `Env {home, claude_config_dir, cwd}` (`skill.rs:27-100`). The three types and `Env::from_process` are `pub`. `Target::parse`, `Scope::parse`, `Target::config_dir`, `Target::user_root`, `InstallArgs` and `parse_install` are private. `skill_path` (`skill.rs:104-110`) uses `user_root` and `config_dir`. `--target` defaults to all targets (`skill.rs:127`). `install` tries every target and exits 1 if any target fails (`skill.rs:170-203`). `USAGE` is a `pub const` that `help.rs` uses (`help.rs:150`). `Env::from_process` refuses an unset or empty `HOME`, and treats an empty `CLAUDE_CONFIG_DIR` as unset (`env_override`, `main.rs:26-28`).
- **Dispatch.** `main.rs:60-103` matches the first argument. An unknown command prints `unknown command` and **exits 2** (`main.rs:94-97`). So every released `tarmac` up to 0.21.0 exits 2 on `tarmac hooks run claude`.
- **The connection.** `handshake` sets fixed 5 s read and write timeouts (`main.rs:171-172`). `connect()` (`main.rs:232-243`) calls it. A failed `UnixStream::connect` is `NoDaemon` at once: a missing socket gives ENOENT, and a stale one gives ECONNREFUSED. `exchange` (`main.rs:139-145`) writes one request and reads until `Ack` or `Err`. A read timeout becomes `no_answer(why)`, whose text has a fixed "in 5 s" (`main.rs:147-149`).
- **(2611.0009) `tarmac report`** (`report.rs`). `run` reads `TARMAC_TERM_ID` through `env_override` (so an empty value is unset), caps the text with `cap_report_text`, and builds `Msg::Report {term_id, kind, text}`. `kind` is a `String` on the wire (`tarmac-protocol/src/lib.rs:219-224`); there is no `Kind` type. The private `fn send(msg: &Msg) -> Result<(), String>` (`report.rs:48-52`) calls `crate::connect()` and then `crate::exchange(.., "an older daemon")`. **There is no seam with a deadline.** `Ack` gives exit 0 and prints nothing. `Err` gives exit 1. With no answer in 5 s it prints `tarmac: no answer from the daemon in 5 s (an older daemon)` (pinned by `tests/report.rs:14`) and exits 1. An older daemon ignores `report` and never answers. The *Migration* section of 2611.0009 says: "Slice 3's hook adapter must not wait this long".
- **`cap_report_text`** (`tarmac-protocol/src/lib.rs:342-347`) only caps: a text over 280 Unicode scalar values becomes its first 279 and `…`. It removes no control character. The daemon caps again and drops an empty text (`tarmacd/src/state.rs:527`). Nothing removes control characters.
- **(2611.0009) OQ1.** With Claude Code 2.1.325, `claude -p`, in a Tarmac terminal: `SessionStart`, `UserPromptSubmit` and `Stop` hooks fired. The hook's parent is `claude` itself. `TARMAC_TERM_ID` reaches the hook. **Not checked:** the `Notification` hook, interactive mode, and Codex. That spec leaves those checks to this slice.
- **PTY environment.** `term.rs:215-222` sets `TERM`, `TARMAC_TERM_ID` and `LC_CTYPE`. A PTY child inherits the rest of the daemon's environment. `make run` puts `core/target/debug` first on `PATH` and pins `TARMAC_SOCKET` (`Makefile:79-87`), so a dev terminal starts with the dev `tarmac` first. A user rc file can still put another `tarmac` before it.
- **CLI tests.** `tests/common/mod.rs` `tarmac()` pins `TARMAC_SOCKET` to an absent socket. It does **not** pin `HOME`, `CLAUDE_CONFIG_DIR` or `TARMAC_TERM_ID`; `tests/report.rs:67` removes `TARMAC_TERM_ID` itself, because the tests often run in a Tarmac terminal. `Report::with_open_stdin` (`:96-109`) runs the binary with a stdin pipe that never closes. `Report::of_input` (`:82-91`) pipes given bytes. `Double` (`tests/common/double.rs`) is a one-connection daemon stand-in that records raw **frames**, not connections. `Double::frames()` waits for its handler, and with no client the handler waits up to 30 s for an accept (`double.rs:52-57,71-87`). `scratch()` makes a per-test temp dir under `std::env::temp_dir()`; on macOS that path starts with `/var`, and its canonical form with `/private/var`. The tests of `tarmac report` are in `tests/report.rs` (2611.0009 S6, S22–S25).
- **Docs that name the verbs.** `CLAUDE.md` *Architecture* (slice 2 made it "four verbs that talk to the daemon" and added `report`; the bullet still says "std-only"), `docs/architecture.md:25-35` (still "`open`, `push` and `--version`", with no `report`) and its diagram at `:64` ("tarmac CLI (Rust, std-only)"), `README.md:167-187` (already stale: it says "two verbs" and names neither `push` nor `report`), `help.rs`, and `GUIDE.md` (it has *Reporting blocked or done* from slice 2, and no hooks section).

**Claude Code hook facts.** Read from code.claude.com/docs/en/hooks on 2026-11-14. They are not yet run against this version except where 2611.0009 OQ1 says so.

- **Shape.** `hooks` → event name → an array of matcher groups `{matcher?, hooks: [handler…]}`. A handler is `{type: "command", command, timeout?, args?}`. With no `args`, the command runs through `sh -c` on macOS. With `args`, it is exec form, with no shell.
- **Merge and dedupe.** Hook entries from the user, project and local settings files are merged. "If you define the same handler in more than one settings file, it runs once."
- **Parallel.** All matching hooks of an event run in parallel.
- **Timeout.** The default is 600 s for a command hook, and 30 s on `UserPromptSubmit`.
- **Exit codes.** Exit 0: on `UserPromptSubmit` and `SessionStart`, plain stdout is **added to Claude's context**. Claude never sees the stderr of a hook that exits 0. Exit 2 on `UserPromptSubmit` **blocks the prompt**. Exit 2 on `Stop` **continues the turn**, up to a cap of 8 times in a row. Exit 2 on `Notification` is ignored. Any other non-zero exit is a non-blocking error, and Claude shows a `hook error` notice.
- **Inputs.** Every event has `session_id`, `transcript_path`, `cwd` and `hook_event_name`. `Notification` adds `message`, an optional `title`, and `notification_type`. Its matcher values include `permission_prompt` and `idle_prompt`, among about a dozen others. `Stop` adds `stop_hook_active` and `last_assistant_message`. `UserPromptSubmit` adds `prompt`. `SessionStart` adds `source` (`startup`, `resume`, `clear`, `compact` or `fork`).
- **Trust.** An interactive session holds back hooks from every settings file until the folder is trusted. A `-p` session treats the folder as trusted.
- **Reload.** "Direct edits to hooks in settings files are normally picked up automatically by the file watcher." This is not checked here.

## Motivation

Slice 2 gives a terminal a report and a chip. Nothing calls it yet, except a user who types `tarmac report`. This slice makes Claude Code call it. One command installs the hooks, and from then on each Claude session in a Tarmac terminal shows `blocked` when it asks for permission and `done` when it ends a turn. A new prompt clears the chip. The installed text never changes, so a `brew upgrade` updates the mapping with no re-install.

## Proposed Solution

### Overview

```
tarmac hooks install   [--target claude-code|codex|all] [--scope user|project] [--dry-run]
tarmac hooks uninstall [--target claude-code|codex|all] [--scope user|project] [--dry-run]
tarmac hooks status
tarmac hooks run <agent>        # the entry the agent runs; Claude's hook JSON on stdin
```

1. `install` merges four handlers, one for each of `Notification`, `Stop`, `UserPromptSubmit` and `SessionStart`, into Claude's settings file (`settings.json` for user scope, `.claude/settings.local.json` for project scope). It backs the file up first. It writes nothing when the file already has the current form.
2. Claude runs `tarmac hooks run claude || true` on each of those events, with the event's JSON on stdin.
3. `hooks run claude` maps the event to a report and sends `Report` through slice 2's code path, under a short deadline. It exits 0, and it prints nothing on stdout.

### Key Components

**Shared agent config** (`tarmac-cli/src/agents.rs`, new; moved from `skill.rs`).

- `Target` (with `Target::ALL`), `Scope`, `Env` (with `Env::from_process`), `Target::parse`, `Scope::parse`, `Target::config_dir`, `Target::user_root` and the flag parser move here as `pub(crate)`. `skill.rs` keeps its paths (`skill_path`, which calls `config_dir` and `user_root`), its documents and its own `USAGE`.
- The flag parser is `parse_flags(args) -> Result<Flags, String>`, with `Flags {targets, scope, dry_run}`. It is the same code that `parse_install` (with `InstallArgs`) is today. `skill install`, `hooks install` and `hooks uninstall` all use it.
- **Tests.** The four parser tests (`install_defaults_…`, `install_flags_…`, `install_rejects_…`, and `usage_text_documents_…`, which reads `skill::USAGE`) move with the parser, or call it from where they are. The three path tests stay in `skill.rs`, because they test `skill_path`. All keep their assertions. Only names change (`InstallArgs` → `Flags`, `parse_install` → `parse_flags`), and the PR lists each changed line.
- `Target` keeps `Codex`, so `--target codex` and `all` parse in every verb [D1].

**Settings path** (`hooks.rs`).

- `settings_path(Target::ClaudeCode, scope, env)`:
  - user scope: `user_root(env).join("settings.json")`. That is `$CLAUDE_CONFIG_DIR/settings.json` when the variable is set and not empty, else `$HOME/.claude/settings.json`;
  - project scope: `env.cwd.join(".claude/settings.local.json")` (OQ3). This is Claude's personal per-project file. Note the difference from `skill install --scope project`, which writes the shared `.claude/skills`.
- Codex has no settings path in this slice [D1].

**The installed form** (`hooks.rs`; one constant for the current form).

```json
"hooks": {
  "Notification":     [ { "hooks": [ { "type": "command", "command": "tarmac hooks run claude || true", "timeout": 5 } ] } ],
  "Stop":             [ { "hooks": [ …the same handler… ] } ],
  "UserPromptSubmit": [ { "hooks": [ …the same handler… ] } ],
  "SessionStart":     [ { "hooks": [ …the same handler… ] } ]
}
```

- **The command is guarded: `tarmac hooks run claude || true`** [D2]. The command keeps a bare `tarmac`, as the design says. `|| true` turns the exit of a `tarmac` that predates this slice (2, from `main.rs:94-97`) and of a missing `tarmac` (127) into 0. So an old or missing binary can never block a prompt, or make a turn continue, and Claude shows no error notice.
- **No matcher on any group** [D3]. `Notification` reaches the binary for every type, and the binary keeps `permission_prompt` only. So a future mapping change, for example `elicitation_dialog`, needs no re-install.
- **`SessionStart` is installed now, as a no-op** [D4]. Slice 4 then changes only the binary. Each session start costs one short process.
- **`timeout: 5`** is a backstop. The binary bounds itself at about 1.5 s (below). If it ever hangs, Claude ends it after 5 s, not after 600 s.
- **Shell form**, not exec form (`args`): `|| true` needs a shell.

**Our handler** is a JSON object with `"type": "command"`, with no `args` key, and with a `command` that, after trimming, equals one of these two strings:

- the current form: `tarmac hooks run claude || true`;
- the design's bare form: `tarmac hooks run claude`. A user may write it by hand from the design.

Any other handler is **foreign**, even one that is close to ours: an absolute path (`/opt/homebrew/bin/tarmac hooks run claude`), other arguments, exec form (any `args` key, even with our exact `command`), another type, or a value that is not an object. Foreign handlers are never changed or removed [D5].

**The current form, exactly.** A file has the current form when the handlers that are ours are exactly four: one under each of the four events, each one alone in a group with no `matcher`, and each one equal (as a JSON value, where key order does not count) to the current handler. These are all *not* current: a handler in the bare form, a missing event, a fifth handler of ours, ours inside a user's group, ours with a matcher, or ours with any key changed by hand (for example `timeout`). `install` replaces such a handler with the current one, so a hand edit of ours is overwritten [D5].

**`install`** (claude-code; once for each target in `--target`).

1. Read the file. If it is missing, start from `{}`, with the file and its directory still to be made.
2. Parse it. Refuse the target (exit 1 at the end, file untouched) when the file does not parse, or when any of these values has the wrong type: the root (must be an object), `hooks` (an object), an event under `hooks` (an array), a group in an array (an object), or a group's `hooks` (an array). A handler that is not an object is foreign and is left as it is.
3. If the file has the current form: print `already installed: <path>`, write nothing, and make no backup.
4. Else, from the parsed value:
   - remove every handler of ours, and prune what that removal emptied (see `uninstall`);
   - then, for each of the four events in the order above, append one new group `{"hooks": [current handler]}` at the end of that event's array. A missing event key is added at the end of `hooks`. A missing `hooks` key is added at the end of the root.
5. Write the result (*Writing*). Print `installed: <path>`, and `backup: <backup path>` when there was a file [D7]. In project scope, also print the hint line (*Writing*).

**`uninstall`** (claude-code; same flags).

1. Read and parse as `install` does. A missing file prints `not installed: <path>` and is not an error.
2. Remove every handler of ours, under every event, in every group.
3. **Prune only what this removal emptied.** A group whose `hooks` array was emptied by the removal is removed. An event array that was emptied by it is removed, and so is a `hooks` object. A container that was already empty stays. A group keeps any key that is not `hooks` (for example a user's `matcher`) when it still has another handler. A removal keeps the order of every key that stays (with `preserve_order`, `Map::shift_remove`; `Map::remove` moves the last key, see *Context*).
4. If nothing was ours: print `not installed: <path>`, and write nothing.
5. Else write (*Writing*), and print `uninstalled: <path>` and the backup line.

So, for a file with no `hooks` key, `install` and then `uninstall` give back the original bytes (S4).

**`--dry-run`** reads and parses. It prints `would install: <path>`, `would uninstall: <path>`, `already installed: <path>` or `not installed: <path>`. It writes nothing. A file that would be refused is refused, with exit 1, as without `--dry-run`.

**`--target codex`** [D1]. `install` and `uninstall` print `skipped codex: hooks are not supported for codex yet` on stdout. That target counts as success. `all`, which is the default, does claude-code and prints the same line for codex. So `tarmac hooks install` with no flags exits 0. Slice 7 replaces the line with the real target. The CLI shape does not change.

**Writing** (one function; used by `install` and `uninstall`).

- **Formatting** [D6]. The value is written by `serde_json` with the `preserve_order` feature, through `PrettyFormatter::with_indent(unit)`:
  - `unit` is the indent of the first indented line of the original file: a tab, or that many spaces. A one-line file, or a new file, gets 2 spaces. That is the form that Claude Code writes.
  - A final newline is kept when the original had one. A new file ends with one.
  - Key order and array order are kept.
  - **The accepted changes outside `hooks`** are those of a parse and a re-write: a `\uXXXX` escape of a printable character becomes the character, `\/` becomes `/`, number spellings change (`1.50` → `1.5`, `1e3` → `1000.0`), a duplicate key keeps only its last value, at the position of its first occurrence, an inline array or object is spread over lines, `{ }` becomes `{}`, and CRLF line ends become LF. A file that Claude Code wrote itself has none of these, so it changes only in `hooks`. (This assumes that Claude Code writes `JSON.stringify(value, null, 2)` form; it is not checked on a real file.)
  - A file that `serde_json` cannot parse is refused (*install* step 2). That includes an empty file, a file with a UTF-8 BOM, and a lone surrogate escape such as `"\ud800"`.
- **Backup** [D7]. Before the first byte is written, the original is copied to `<file>.tarmac-backup`, beside the file that is really written (see the next item). The backup has the original's permission bits (as `std::fs::copy` gives), so a `0600` file never gets a wider backup. One backup only: a later write replaces it. So the backup always holds the state just before the last change by `tarmac`. No backup is made for a new file, a no-op, or `--dry-run`.
- **Symlinks** [D8]. If the settings file is a symlink (a dotfiles manager), the write goes to the link's resolved target, and the link stays. `std::fs::canonicalize` gives the target. A symlink whose target is missing is refused with exit 1. The result lines (`installed: <path>`, and the others) name the settings path as `settings_path` gives it (the link), and the `backup:` line names the real backup path.
- **Not writable** [D8]. Before the backup, the CLI checks that the target file (if it exists) and its directory are writable by the user. The crate has no `libc`, and `std` has no `access`, so a probe that writes nothing serves: for example, open the file for writing with no truncation, and make the temp file before the backup. If not, the target is refused with exit 1: nothing is written, and no backup or temp file is made. Without this check a rename would replace a read-only file in a writable directory.
- **Atomic.** The new bytes go to a temp file in the target's directory (`.<file name>.tarmac-tmp`). The temp file is flushed and synced, given the original's permission bits (or the default mode for a new file), and renamed over the target.
- **New file.** A missing `.claude` directory, or `$CLAUDE_CONFIG_DIR`, is made with `create_dir_all`.
- **The project-scope hint** (OQ3). Every project-scope write (install or uninstall) prints one line: `hint: git ignores <path> only if you add it to .gitignore (Claude does this only for a file it made); the same holds for <path>.tarmac-backup`. The exact words may change; the line names both files.

**`status`** (reads both scopes; writes nothing).

```
claude-code  user     /Users/u/.claude/settings.json          installed
claude-code  project  /work/repo/.claude/settings.local.json  not installed
codex        -        -                                       not supported yet
tarmac on PATH: /opt/homebrew/bin/tarmac (another binary than this one)
```

- For claude-code, it prints one line for each scope (user, then project from the cwd). Each line has one of these states:
  - `installed`: the current form;
  - `installed, old form (run tarmac hooks install)`: some handlers are ours, but the form is not the current one;
  - `not installed`: no handler is ours, or there is no file;
  - `unreadable: <why>`: the file does not parse, or a type is wrong.
- **The `PATH` line** searches the `PATH` of the `status` process, in order, for a file named `tarmac` that, after any symlink is followed, is a regular file with an execute bit (Homebrew's `bin/tarmac` is a symlink). A file without one is skipped. It prints the first one found, as the `PATH` entry joined with `tarmac` (not resolved), and then `(this binary)` when its canonical path equals this binary's (`std::env::current_exe`, canonical), else `(another binary than this one)`. If none is found it prints `tarmac on PATH: not found (the hooks will do nothing)`. This is the caller's `PATH`. A hook inherits `claude`'s environment, so it sees the same `PATH` only when `claude` started from the same shell. The help text says so.
- Exit 0, even with `not installed`. Exit 1 when a file is `unreadable`.

**`hooks run <agent>`** (`hooks.rs`). The design's rules hold, and **every path exits 0 with empty stdout.**

1. **Agent.** If the argument is `claude`, go on. Any other value, no argument, or extra arguments: write one stderr line, exit 0. `codex` takes this path in this slice. (Claude never sees the stderr of an exit 0.)
2. **Terminal.** If `TARMAC_TERM_ID` is unset or empty: exit 0 **before reading stdin**, and do not connect.
3. **Stdin** [D9]. If stdin is a terminal (`IsTerminal`), exit 0. Otherwise read it on a helper thread, up to `HOOK_STDIN_MAX` = 4 MiB, and wait at most `HOOK_STDIN_WAIT` = 1 s for the end of the input. Over the limit, past the wait, or a read error: exit 0, with no connection.
4. **Parse.** The input must be one JSON object. Else exit 0.
5. **Map** (`claude_report(&Value) -> Option<(Kind, Option<String>)>`, pure). No `Kind` type exists today: `Msg::Report.kind` is a `String`. `Kind` here is the wire string `"blocked"`, `"done"` or `"clear"`, or a small CLI-local enum that this slice adds; the tests compare the wire value.

   | `hook_event_name` | Condition | Report |
   | --- | --- | --- |
   | `Notification` | `notification_type == "permission_prompt"` | `blocked`, text from `message` |
   | `Notification` | any other type, or no `notification_type` | none |
   | `Stop` | always | `done`, text from `last_assistant_message` |
   | `UserPromptSubmit` | always | `clear` |
   | `SessionStart` | always | none (slice 4) |
   | anything else, or not a string | | none |

   - **Text** [D10]. Take the field when it is a string. Then, in this order:
     1. Remove every control character that is not whitespace: C0 (U+0000–U+001F, for example ESC), DEL (U+007F) and C1 (U+0080–U+009F), except the whitespace ones of step 2.
     2. Replace each run of whitespace with one space. Whitespace is what `char::is_whitespace` says: space, `\t`, `\n`, `\v`, `\f`, `\r`, U+0085, U+00A0 and the other Unicode spaces.
     3. Trim the ends, and cap with `cap_report_text`.
     
     Step 1 comes first, so `"a \u001b b"` gives `"a b"`, not `"a  b"`. `cap_report_text` removes nothing (*Context*), so the hook must. An empty result, or a missing field or one that is not a string, gives no text. `stop_hook_active` is ignored: the hook never blocks.
6. **Send** [D11]. Call the report seam (below) with the `HOOK_DEADLINE` of 500 ms. The deadline covers everything from connect to `Ack`. On `Ack`, exit 0. On `Err {msg}`, no daemon, a timeout or any failure, write one stderr line `tarmac: hooks run: <why>` and exit 0. There is no retry.
7. **Panics.** The body runs inside `std::panic::catch_unwind`. A panic exits 0, with the panic message on stderr only.

The longest path is 1 s of stdin plus 500 ms of exchange, which is under the 5 s `timeout`. With no daemon, the connect fails at once, so the 200 ms rule holds.

**The report seam** (this slice makes it; slice 2 has none, see *Context*).

- `report::send(term_id: &str, kind: Kind, text: Option<&str>, deadline: Duration) -> Result<(), String>`, or an equal shape (for example the present `send(&Msg)` with a `deadline` argument). It connects, does the handshake, sends `Report` and waits for `Ack` or `Err`, all inside `deadline`. Each read and write gets the time that is left as its timeout. It prints nothing. `Err` carries the line that the verb would print.
- `tarmac report` calls it with 5 s, and prints and exits as 2611.0009 says. `hooks run` calls it with 500 ms. That is the "same code path".
- The change is in `main.rs` too. Today `handshake` sets fixed 5 s timeouts (`main.rs:171-172`), `connect()` calls it, and `exchange`'s read timeout becomes `no_answer`, which says "in 5 s" (`main.rs:139-149`). `handshake` gets a timeout argument, or a deadline. `open`, `push` and `--version` keep 5 s, and keep their messages.
- **The no-answer line.** For `tarmac report` it stays byte-for-byte `tarmac: no answer from the daemon in 5 s (an older daemon)`. For `hooks run` the stderr line must not claim 5 s: it is `tarmac: hooks run: no answer from the daemon in 500 ms` (stderr only, so Claude never shows it).
- No change of behaviour for `tarmac report`, `open`, `push` or `--version`: every test now in `core/crates/tarmac-cli/tests/` stays green with unchanged assertions (S29).

**Dependency** [D6]. `core/Cargo.toml` `[workspace.dependencies]` changes to `serde_json = { version = "1", features = ["preserve_order"] }`, and `tarmac-cli/Cargo.toml` gets `serde_json.workspace = true`. The feature is in the workspace entry, so `cargo build -p tarmacd` alone builds the same `serde_json` as the shipped workspace build. The cost:

- `indexmap`, with its own dependencies (`hashbrown`, `equivalent`), enters `core/Cargo.lock`.
- `tarmacd` also builds `serde_json` with `preserve_order`. `tarmacd` uses typed structs for `state.json` (its only map is a `BTreeMap`, and no `serde_json::Value` is persisted) and parses only in `docs.rs:93`, so its output does not change. Its tests that build a `Value` with `json!` and compare `Value`s are not affected, because `Map` equality does not count key order. The implementer confirms this: the `tarmacd` tests stay green, and a `state.json` written before and after the change is compared.
- The `Cargo.toml` comment changes from "std-only" to say what the crate allows and why: no runtime start-up cost, and parse only.

### Data Flow

1. The user runs `tarmac hooks install`. `~/.claude/settings.json` gets the four groups. The old file is in `settings.json.tarmac-backup`.
2. In Tarmac terminal T, `claude` starts. `SessionStart` runs `tarmac hooks run claude || true`, which reads the input, maps it to none, and exits 0.
3. Claude asks for permission. `Notification` arrives with `notification_type: "permission_prompt"` and `message: "Claude needs your permission to use Bash"`. The hook sends `Report {T, blocked, "Claude needs your permission to use Bash"}`. The daemon walks from the CLI to `claude` (2611.0009) and pushes `TermReport`. An amber chip shows.
4. The turn ends. `Stop` sends `Report {T, done, "<the start of the last message>"}`. The chip turns green.
5. The user types the next prompt. `UserPromptSubmit` sends `Report {T, clear}`. The chip goes.
6. Outside Tarmac, the same hooks run with no `TARMAC_TERM_ID`, and exit 0 at once.

### Interface Contract

- **CLI.** These are the four lines of *Overview*.

  | Verb | Exit 0 | Exit 1 | Exit 2 |
  | --- | --- | --- | --- |
  | `hooks install` / `uninstall` | every target succeeded, skipped, or had nothing to do | a target was refused or failed (the others are still tried) | usage: an unknown flag or value, a missing value, a stray argument |
  | `hooks status` | all files readable | a file is `unreadable` | an argument was given |
  | `hooks run …` | **always** | never | never |
  | `hooks`, `hooks <unknown>` | | | usage |

- **Output.** `install`, `uninstall` and `status` print their result lines on stdout and their errors on stderr, as `skill install` does. `hooks run` never writes stdout.
- **The settings file.** The four groups shown in *The installed form*, in that key order: `type`, `command`, `timeout`.
- **The backup.** `<real file>.tarmac-backup`, which a later write replaces.
- **No protocol change.** No new message, no new key, no new vector. No conformance vector changes. `hooks run` sends slice 2's `Report`.
- **Help.** `help.rs` gets the four usage lines, a paragraph on `hooks`, the `PATH` note, and an `EXIT STATUS` remark: `tarmac hooks run` always exits 0.

## Alternatives Considered

- **The design's bare command** (`tarmac hooks run claude`). It is simpler, and it matches the design's text. It is rejected [D2]: a `tarmac` from before this slice exits 2, and on `Stop` that makes Claude continue the turn, up to 8 times. That happens after a downgrade, with an old worktree's build first on `PATH`, or for a teammate who reads a committed project file. With no `tarmac` at all, the exit is 127, and Claude shows an error notice for every event.
- **Exec form** (`"command": "tarmac", "args": ["hooks","run","claude"]`). It has no shell to start. It is rejected because it cannot carry `|| true`.
- **Keep the `permission_prompt` matcher in the file.** This gives fewer process starts. It is rejected [D3] because a change in which types map to `blocked` would need a re-install, against the design's "the mapping lives in the binary".
- **Leave `SessionStart` out until slice 4.** It is rejected [D4]. Every user would have to re-install at slice 4, and `status` would show "old form" until they do.
- **No JSON crate: a hand-written ordered JSON parser and printer.** This keeps the crate free of new dependencies. It is rejected [D6]: escapes, surrogate pairs and numbers are easy to get wrong, in a file that controls the user's agent.
- **A text splice** that replaces only the bytes of the `hooks` value. It would keep every other byte. It is rejected because it needs a parser that tracks positions, which `serde_json` does not give, and so the same hand-written parser as above.
- **Plain `serde_json` (sorted keys).** It adds no crate. It is rejected because it reorders every object in the user's file.
- **A timestamped backup per write.** It keeps every old state. It is rejected [D7] because the files pile up in `~/.claude`. One backup of the last state, plus `uninstall`, is enough.
- **Refuse `--target codex` with exit 1.** This is honest, but it makes the default `all` fail [D1]. **Accept it silently as a no-op.** This hides that nothing was done. A skip with a line on stdout is between the two.

## Migration & Rollback

- **Migration.** None in Tarmac's state. A user runs `tarmac hooks install` once.
- **Upgrades.** The mapping is in the binary, so `brew upgrade` changes it with no re-install. Slice 4 fills in `SessionStart`, and slice 7 adds codex.
- **Rollback: an older `tarmac` with the entries installed.** `tarmac hooks run claude` exits 2 in the old binary. `|| true` makes it 0, so Claude does not block, and only the reports stop. To remove the entries, run `uninstall` with a new binary, or restore `settings.json.tarmac-backup`.
- **An older daemon** (from before slice 2). It never answers `report`. Each hook then waits its 500 ms deadline and exits 0. A version-mismatch restart replaces such a daemon at the next app launch.
- **The bare form in a file.** A hand-written bare entry is "old form" in `status`. `install` replaces it with the guarded form.

## Security Considerations

This slice writes the configuration of another program that runs commands. That is the main risk.

- **Scope of a write.** The CLI writes only the one settings file that `--scope` names (and its backup and temp file): the user's `settings.json`, or the project's `.claude/settings.local.json`. It never reads or writes `~/.claude.json`, a project's shared `.claude/settings.json`, or any other file.
- **What it adds.** Only four handlers with a fixed command. No text from the user's file, from the environment or from stdin ever goes into a command string.
- **What it removes.** Only handlers whose command is one of the two exact strings. Foreign handlers, and their groups, stay as they are.
- **Fail closed.** A file that does not parse, or has an unexpected type, is not written. A symlink is written through, never replaced. The write is atomic, so a crash leaves the old file or the new one, never half of one. The original's permission bits are kept.
- **Project scope is personal, but can leak** (OQ3). It writes `.claude/settings.local.json`, not the shared `.claude/settings.json`. Claude git-ignores that file only when Claude creates it, so a file that `tarmac` creates, and its backup, can be committed by mistake. Each project-scope write prints the hint line. If one is committed, a teammate with no `tarmac` gets a hook that runs `sh -c 'tarmac … || true'`, exits 0, and does nothing.
- **Trust.** A `-p` session runs the hooks of a project file in a folder that was never trusted (Claude docs, *Workspace trust*). This slice adds nothing that runs code from the repository: the command is fixed.
- **Hook input is untrusted.** The `message` and `last_assistant_message` texts are claims. They are capped, and the daemon caps them again (2611.0009). The app shows them as quoted plain text. Nothing in the CLI evaluates them.
- **Output safety.** On `UserPromptSubmit` and `SessionStart`, stdout goes into Claude's context. `hooks run` writes nothing to stdout on any path, so it cannot inject text into the model.
- **A spoofed `TARMAC_TERM_ID`.** It can only send a report to a live terminal of the same user. That is the same trust as `tarmac report` (2611.0009).

## Acceptance Scenarios

**Where the tests live.**

- **Pure units** in `hooks.rs` (`#[cfg(test)]`): `claude_report`, the text rule, "ours", the current-form check, the merge, the prune, and the indent detection. They work on `serde_json::Value` and strings, with no file system.
- **CLI tests** in a new `core/crates/tarmac-cli/tests/hooks.rs`. They run the real binary on temp dirs, and against `Double` for `hooks run`.
- **The `agents.rs` move.** The `skill.rs` tests for parsing and paths move with the code, unchanged.

**Safety rule for every CLI test.** A new helper, `hooks_cmd(dir)`, builds every `hooks` command:

- `dir` is a `scratch()` dir, canonicalized first (on macOS `/var/…` is `/private/var/…`), so that a printed path can be compared with a path the test builds.
- It makes `dir/home` and `dir/proj`. It sets `HOME` to `dir/home`, `current_dir` to `dir/proj`, and `TARMAC_SOCKET` to an absent socket (or the `Double`'s).
- It **always** sets `CLAUDE_CONFIG_DIR`: either to a dir under `dir`, or to the empty string, which `env_override` treats as unset, so that `HOME` decides. That way a `CLAUDE_CONFIG_DIR` exported by the implementer's own shell never reaches a test.
- It **always** removes `TARMAC_TERM_ID` (`env_remove`). The tests often run inside a Tarmac terminal, which sets it. A test that needs it sets it after.
- A test never builds a `hooks` command with `tarmac()` directly.

**"No connection", as a test sees it.** `Double` records frames, not connections, and `frames()` waits up to 30 s when no client comes. So a scenario that says "no connection" checks it this way: the socket is absent, and stderr does not contain `no tarmac daemon running` (the text of `connect()`'s error, `main.rs:235-239`). A hook that tried to connect would print it (step 6 of `hooks run`), as `tests/report.rs:63-64` uses for `report`. Where a scenario needs a live `Double`, its handler sets a flag when it runs (that is, on an accept). The test waits at least 100 ms after the child exits, then drops the `Double` and reads the flag. (The accept loop polls every 10 ms and returns at once when the `Double` is dropped, so a drop with no wait can miss a connection.)

**Fixtures.**

Every fixture except F-odd is a byte string in the form that `JSON.stringify(value, null, 2)` gives (with the indent that the fixture names): one key or element on each line, `": "` after a key, `[]` and `{}` for empty containers, no escapes of printable characters. The groups below are written compact here only to keep the spec short.

- **F-claude.** A Claude-style file, written by the test: 2-space indent, a final newline, keys in an order that is not sorted (`"permissions"`, then `"env"`, then `"model"`), nested arrays, non-ASCII text (`"é"`, `"表"`), integers only, and no `hooks` key.
- **F-own-hooks.** F-claude plus a `hooks` key with the user's own handlers: a `Stop` group `{"hooks":[{"type":"command","command":"say done"}]}`, and a `PreToolUse` group with `"matcher": "Bash"`.
- **F-mid.** F-claude with a `hooks` key **between** `"permissions"` and `"env"` (so two root keys follow it). Inside `hooks`, in this order: `"Stop"` with one group that holds only the bare-form handler, then `"PreToolUse"` (a user group), then `"PostToolUse"` (a user group).
- **F-mid-only.** F-claude with a `hooks` key between `"permissions"` and `"env"` that holds only `"Stop"` with one group of the bare-form handler.
- **F-4.** F-claude with a 4-space indent and no final newline.
- **F-odd.** A file with `"é"`, `"a\/b"`, `1.50`, `1e3`, a compact inline array, and a duplicate key.

### Happy Path

- **S1 (install into a missing file; CLI).**
  - Given no `settings.json` and no `.claude` dir under the test's `HOME`,
  - when `tarmac hooks install --target claude-code` runs,
  - then it exits 0, prints `installed: <HOME>/.claude/settings.json`, and the file parses to exactly `{"hooks": <the four groups>}`, with 2-space indent and a final newline. No backup file exists.
- **S2 (merge keeps everything else; CLI).**
  - Given F-own-hooks at user scope,
  - when `install` runs,
  - then the file has the four groups, and every non-`hooks` key keeps its value and its position. The user's `Stop` group is still the first element of `Stop`, and ours is the last. The `PreToolUse` group is unchanged.
  - The bytes of the file, outside the `hooks` value, are equal to those of F-own-hooks. The test checks this with the S4 round trip.
  - `settings.json.tarmac-backup` is byte-for-byte F-own-hooks.
- **S3 (idempotent; CLI).**
  - Given the file and the backup after S2, with their bytes and mtimes kept by the test,
  - when `install` runs again,
  - then it exits 0 and prints `already installed: <path>`. The file and the backup are byte-for-byte the same, and neither mtime changed.
  - This is the design's success criterion "the config file is unchanged byte-for-byte". It fails if a write happens on a no-op, even one with the same bytes, because the mtime would change.
- **S4 (install and uninstall give the original back; CLI).**
  - For each of F-claude, F-own-hooks and F-4: `install` then `uninstall` leave the file byte-for-byte equal to the fixture.
  - This fails if the indent is not detected (F-4), if the final newline is not kept, if keys are sorted, if non-ASCII text is escaped, if an emptied `hooks` is not pruned (F-claude), or if a user group is removed or moved (F-own-hooks).
- **S4b (a removal moves no other key; CLI).**
  - `uninstall` on F-mid gives F-mid without the `Stop` key: `hooks` holds `"PreToolUse"` then `"PostToolUse"`, and the root order is unchanged.
  - `uninstall` on F-mid-only gives F-claude byte-for-byte: the `hooks` key goes, and `"env"` and `"model"` keep their order.
  - `install` on F-mid also removes the bare form first: after it, `hooks` holds `"PreToolUse"`, `"PostToolUse"`, then the four events in the order of *The installed form*, and the root order is unchanged.
  - The expected bytes are written by hand in the test. This fails if a removal uses `Map::remove` (a swap remove) instead of `Map::shift_remove`. S4 cannot catch it, because there every removed key is the last one.
- **S5 (the mapping; unit `claude_report`).**
  - `Notification` with `notification_type: "permission_prompt"` and `message: "Claude needs your permission to use Bash"` gives `(blocked, Some("Claude needs your permission to use Bash"))`.
  - `Stop` with `last_assistant_message: "Done.\n\n  All   tests pass.\n"` gives `(done, Some("Done. All tests pass."))`.
  - `UserPromptSubmit` gives `(clear, None)`, also when `prompt` is long.
  - `SessionStart` gives `None`.
- **S6 (hooks run sends the report; CLI with Double).**
  - Given a `Double` that answers `hello_ok` and then `ack`, and `TARMAC_TERM_ID=t9`,
  - when `tarmac hooks run claude` runs with a `Stop` input on stdin,
  - then the double got `Report {term_id: "t9", kind: "done", text: Some(<the normalized text>)}`. The exit code is 0, and stdout is empty.
  - The same holds for `Notification`/`permission_prompt` (`blocked`, with the `message`) and for `UserPromptSubmit` (`clear`, with no `text` key on the raw payload).
- **S7 (status; CLI).**
  - Given user scope after S1, and a project file `<cwd>/.claude/settings.local.json` with the bare-form handler under `Stop` only, and a `<cwd>/.claude/settings.json` that holds the current form (which `status` must not read),
  - when `tarmac hooks status` runs with `PATH` set to a scratch dir that holds a `tarmac` symlink to the binary under test,
  - then the user line says `installed`, the project line names `settings.local.json` and says `installed, old form (run tarmac hooks install)`, the codex line says `not supported yet`, and the `PATH` line names the symlink and says `(this binary)`. Exit 0.
  - With `PATH` set to an empty scratch dir, the `PATH` line says `not found`.
  - With `PATH` set to `<a>:<b>`, where `<a>` holds a `tarmac` file with mode `0644` and `<b>` holds an executable `tarmac` script, the `PATH` line names `<b>/tarmac` and says `(another binary than this one)`.
- **S8 (uninstall; CLI).**
  - Given F-own-hooks after `install`,
  - when `tarmac hooks uninstall` runs,
  - then it exits 0 and prints `uninstalled: <path>`. The file has no handler of ours, and the user's `Stop` and `PreToolUse` groups are as in the fixture. The backup holds the installed file.

### Edge Cases

- **S9 (what counts as ours; unit and CLI).**
  - A file with these handlers in one group under `Stop`: the current form; the bare form; ` tarmac hooks run claude ` (with spaces, so trimmed to the bare form); `/opt/homebrew/bin/tarmac hooks run claude`; `tarmac hooks run claude --x`; exec form `{"type":"command","command":"tarmac","args":["hooks","run","claude"]}`; `{"type":"command","command":"tarmac hooks run claude","args":[]}` (our exact command, with `args`); `{"type":"prompt","command":"tarmac hooks run claude"}`; `{"command":"tarmac hooks run claude"}` (no `type`); and the string `"tarmac hooks run claude"` (not an object).
  - `uninstall` removes the first three, and leaves the other seven exactly as they were, in their order.
- **S10 (old forms are replaced; unit and CLI).** Each of these files is "old form" in `status`, and `install` turns it into the current form with exactly four handlers of ours:
  - (a) the bare form under all four events;
  - (b) the current form, but missing `SessionStart`;
  - (c) the current form, with a second copy under `Stop`;
  - (d) the current form, with ours inside a user's group next to `say done`. After `install`, that user group keeps `say done` only, and ours is in its own group;
  - (e) the current form, with `"matcher": "permission_prompt"` on the `Notification` group;
  - (f) the current form under `Notification`, `Stop`, `UserPromptSubmit` and `SessionStart`, plus one of ours under `PreToolUse`.
- **S11 (the prune removes only what it emptied; unit).**
  - `"hooks": {"Stop": []}` with no handler of ours: `uninstall` writes nothing, and the empty array stays.
  - A user group `{"matcher":"x","hooks":[ours, foreign]}` keeps `matcher` and `foreign`.
  - A user group `{"matcher":"x","hooks":[ours]}` is removed.
  - When every event is removed, the `hooks` key goes too.
- **S12 (codex and all; CLI).**
  - `tarmac hooks install --target codex` exits 0, prints `skipped codex: hooks are not supported for codex yet`, and makes no file under the test's `HOME`.
  - `tarmac hooks install` (default `all`) exits 0, installs claude-code, and prints the codex line.
  - `uninstall --target codex` does the same.
- **S13 (`CLAUDE_CONFIG_DIR` and project scope; unit and CLI).**
  - With `CLAUDE_CONFIG_DIR=<dir>/cfg`, user scope writes `<dir>/cfg/settings.json`, and nothing under `HOME`.
  - With it empty, user scope writes `<HOME>/.claude/settings.json`.
  - `--scope project` writes `<cwd>/.claude/settings.local.json` with either setting, prints the backup line when there was a file and the hint line that names the file and its backup, and leaves an existing `<cwd>/.claude/settings.json` byte-for-byte unchanged.
- **S14 (dry run; CLI).** For `install` and `uninstall`, `--dry-run` prints the `would …` or `already …`/`not installed` line, and leaves no new or changed file: no settings file, no backup, no temp file, and no new directory (with no `.claude` dir before, there is none after). A refused file still exits 1.
- **S15 (a symlinked settings file; CLI).**
  - Given `<HOME>/.claude/settings.json` as a symlink to `<dir>/dotfiles/claude-settings.json`,
  - when `install` runs,
  - then the link is still a symlink to the same target, the target has the hooks, and the backup is `<dir>/dotfiles/claude-settings.json.tarmac-backup`.
  - A symlink to a missing file is refused with exit 1, and nothing is created.
- **S16 (permission bits; CLI).** A file with mode `0600` still has mode `0600` after `install`, and its backup has mode `0600` too. A new file has the mode that `File::create` gives under the test's umask: the test makes a reference file with `File::create` in a scratch dir and compares the two modes (`std` cannot read the umask).
- **S16b (not writable fails closed; CLI) [D8].**
  - (a) A settings file with mode `0444` in a writable directory; (b) a writable settings file in a directory with mode `0555`.
  - `install` exits 1 with a stderr line that names the path. The file is byte-for-byte unchanged, its mode is unchanged, and no backup or temp file exists.
  - (The test restores the directory mode before cleanup.) A test run as root cannot see this. The crate has no `libc`, so the test probes instead of calling `geteuid`: if it can open its own `0444` file for writing, it skips with a message.
- **S17 (formatting outside the merge; unit).**
  - The indent detection gives 2 spaces for F-claude, 4 for F-4, a tab for a tab-indented file, and 2 for `{}` written on one line.
  - F-odd, after `install` and `uninstall`, parses to a value equal to F-odd's value, except for the duplicate key. Its bytes show only the changes on the accepted list (*Writing*). The test compares with an expected text that the spec's list predicts, written by hand: `"é"`, `"a/b"`, `1.5`, `1000.0`, the array spread over lines, and the last value of the duplicate key at the position of its first occurrence.
  - The float spellings, and the position of the duplicate key, are a prediction of `serde_json` (with `preserve_order`), not a measured fact. If a run gives other bytes, the implementer does not copy them into the test. They report the difference, and the owner amends the accepted list.
- **S18 (text normalization and cap; unit).**
  - A 400-character `last_assistant_message` gives a text of 280 `char`s that ends in `…`.
  - Only whitespace, an empty string, a number, or no field gives `(done, None)`.
  - `\t`, `\r\n`, `\v` and `\f` count as whitespace: `"a\t\r\n\u000b\u000cb"` gives `"a b"`.
  - `"a\u001b[31mb\u0007c\u009bd"` (ESC, BEL, C1 CSI) gives `"a[31mbcd"`: the control characters are gone, and nothing else changes [D10].
  - `"a \u001b b"` gives `"a b"` (control characters go before whitespace folds).
  - `"\u001b\u0007"` alone gives no text.
  - A text of 280 letters with one ESC in the middle (281 `char`s) gives the 280 letters, with no `…`: the cap counts the text after removal.
- **S19 (other notification types; unit).** `Notification` with `idle_prompt`, with `elicitation_dialog`, or with no `notification_type` gives `None`.

### Error Scenarios

- **S20 (no daemon is fast and silent; CLI).**
  - Given `TARMAC_TERM_ID=t9` and `TARMAC_SOCKET` set to (a) an absent path and (b) a socket file with no listener (a bound and dropped `UnixListener`),
  - when `hooks run claude` runs with a `Stop` input,
  - then it exits 0 with empty stdout, and one stderr line that starts with `tarmac: hooks run:` and says that no daemon runs. The line proves that the hook mapped the input and tried to connect; without it, a hook that maps nothing would pass.
  - The wall time from spawn to exit is 200 ms or less. That is the design's success criterion.
  - **How it is measured.** A debug binary under parallel `cargo test` can be slow to start. The test runs the case 5 times and asserts on the fastest run. The PR records all the times.
- **S21 (a daemon that never answers; CLI).**
  - Given a `Double` that answers `hello_ok` and then nothing, or a `Double` that accepts and never answers the `hello`,
  - when `hooks run claude` runs with a `Stop` input,
  - then it exits 0 with empty stdout and one stderr line that starts with `tarmac: hooks run:` and does not say `5 s`. For the `hello_ok`-then-silence double, that line is `tarmac: hooks run: no answer from the daemon in 500 ms`. (A silent `hello` fails inside `handshake`, whose read error is `daemon connection lost: …`, `main.rs:105-107,180`; that wording stays.) The wall time is at least 450 ms and at most 1000 ms. (Without the deadline it would take the 5 s of `connect()`.)
- **S22 (a refusal; CLI).** A `Double` that answers `err {msg: "unknown terminal: t9"}` gives exit 0, empty stdout, and one stderr line that contains `unknown terminal: t9`.
- **S23 (no terminal; CLI).**
  - With `TARMAC_TERM_ID` unset, and again set to the empty string, and with an absent socket,
  - when `hooks run claude` runs through `with_open_stdin` (a pipe that never closes),
  - then it exits 0 within 200 ms (the fastest of 5 runs, as S20), with empty stdout and no connection (*"No connection"*). It did not wait for stdin (else the 1 s stdin wait would show).
- **S24 (bad input never fails; CLI).** With `TARMAC_TERM_ID=t9` and an absent socket, each of these exits 0 with empty stdout and no connection (*"No connection"*):
  - empty stdin; `not json`; `[]`; `{"hook_event_name": 7}`; a `SessionStart` input; an `idle_prompt` notification;
  - a valid `Stop` input whose `last_assistant_message` is padded so that the input is 4 MiB + 1 byte. Its control: the same input padded to exactly 4 MiB does try to connect (its stderr contains `no tarmac daemon running`, as in S20). Without the control, the case could pass on a parse failure;
  - a stdin that never closes (`with_open_stdin`). The exit comes within 1.5 s.
- **S25 (bad arguments never fail; CLI).** `tarmac hooks run`, `tarmac hooks run codex`, `tarmac hooks run cursor` and `tarmac hooks run claude extra`, each with `TARMAC_TERM_ID=t9`, an absent socket and a valid `Stop` input, exit 0, with empty stdout, one stderr line, and no connection.
- **S26 (a file that is refused; CLI).** Each of these is refused by `install` and by `uninstall`, with exit 1 and a stderr line that names the path. The file is byte-for-byte unchanged, and no backup or temp file is left:
  - (a) `{"a": 1,}` (does not parse); (b) `[]`; (c) `{"hooks": []}`; (d) `{"hooks": {"Stop": {}}}`; (e) `{"hooks": {"Stop": [1]}}`; (f) `{"hooks": {"Stop": [{"hooks": {}}]}}`.
  - `status` shows `unreadable` for (a) and exits 1.
- **S27 (one target does not stop the other; CLI).** The default `all`, with an unparsable claude-code file, exits 1. The codex skip line is still printed.
- **S28 (usage; CLI).**
  - `hooks`, `hooks frob`, `hooks install --target cursor`, `hooks install --scope system`, `hooks install extra`, `hooks uninstall --target` and `hooks status --x` each exit 2, with a usage line on stderr. No file is created under `HOME` or the cwd.
- **S29 (the other verbs are unchanged; CLI).** After the seam change, every test that is in `core/crates/tarmac-cli/tests/` at 617f1d2 passes with unchanged assertions. That includes `tests/report.rs` (2611.0009 S6, S22–S25, with the exact no-answer line of `:14`) and the tests of `open`, `push` and `--version`, which share `handshake` and `exchange`.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

Implement however you work best. Only the result is checked. Repository rules that bind you:

- **TDD.** Write each test first and watch it fail on the unmodified tree (`docs/coding-style.md`). Start with the pure units (`claude_report`, "ours", the current-form check, merge, prune, indent). Then the CLI tests.
- **Safety: the user's real agent config.**
  - Never read or write the real `~/.claude`, `~/.claude.json`, `~/.codex` or `~/.agents`. Not in a test, not in QA, and not by hand to "just check".
  - Every CLI test goes through `hooks_cmd(dir)`, which pins `HOME`, `CLAUDE_CONFIG_DIR` and the cwd to the test's `scratch()` dir (*Safety rule*). Do not run `tarmac hooks install` in your own shell without `HOME` and `CLAUDE_CONFIG_DIR` pinned to a temp dir.
  - In QA, use a temp `CLAUDE_CONFIG_DIR`, as S30 says.
- **Daemon safety.** `hooks run` tests use the `Double`, never a real daemon. Never run `tarmacd` or a file under `target/` by hand. Never use `pkill`. Stop a dev daemon only with `make kill-daemon` or by the pid of its socket. Never create file names that are not UTF-8: every fixture name is ASCII.
- **Exit 0 and stdout.** On every path of `hooks run`, assert both. A stray `println!` is the bug that matters most here: on `UserPromptSubmit` it goes into Claude's context.
- **Two paths have no scenario.** The panic path (`catch_unwind`) needs a seam only a test would use. The tty path (stdin `IsTerminal`, step 3 of `hooks run`) needs a pseudo-terminal, which the test harness does not have. Review checks both, under exception 2 of `docs/coding-style.md`, and the PR body says so.
- **The seam on slice 2.** Slice 2 has no deadline seam (*Context*), so make it. Keep every existing CLI test green with unchanged assertions (S29). Report every assertion that you had to change.
- **Dependency.** Set `preserve_order` on the `serde_json` entry of `[workspace.dependencies]`, and add `serde_json.workspace = true` to `tarmac-cli`. Check that the `tarmacd` tests stay green, and that a `state.json` written before and after the change has the same bytes.
- **Do not `cargo fmt`.**
- **Docs.** Update every doc in *Docs to update*. `make docs-check` must pass.
- `make test` must pass.

Test principles (the same ones `/verify` scores against):

- **Behavioral over structural** — assert observable output/effects, not internals; the suite must survive refactoring.
- **Every test can fail** — no copy-pasted expected values, no asserting a constant, no tautologies.
- **Deterministic, isolated, readable** — inject clocks/randomness, no cross-test state, AAA structure with inline setup.

## Trade-offs and Limitations

- **Agent-specific code in the CLI** (design). A Claude change of an event name or field gives "no reports", never a wrong mark, and never a blocked prompt.
- **The command is not the design's literal string** [D2]. It is guarded with `|| true`. The cost: a real failure of the new binary is silent too. `tarmac hooks status` and the stderr line (seen with `claude --debug`) are the ways to find it.
- **A write reformats an unusual file** [D6]. Escapes, number spellings, compact arrays and duplicate keys change (the list in *Writing*). A file that Claude Code wrote changes only in `hooks`. The backup holds the old bytes.
- **A race with Claude.** If Claude writes `settings.json` (for example through `/config`) between our read and our rename, its change is lost. The window is a few milliseconds. The backup holds the state that we read.
- **`status` sees its own `PATH`**, not the `PATH` that a hook gets from `claude`.
- **Each event starts a process**, and `SessionStart` does nothing yet [D4]. With no matcher, each `Notification` starts one too [D3]. Outside Tarmac each start ends at once, before any read.
- **An older daemon costs 500 ms per hook.** That ends at the next app launch, which replaces it.
- **A `Stop` with a long answer is cut** to 280 characters, with its line breaks folded [D10]. The chip is a pointer, not the answer.
- **User and project scope both installed.** Claude runs an identical handler once (Claude docs, *Deduplication*), so there are no double reports.
- **Codex is not supported** until slice 7. `--target codex` is accepted and skipped [D1].

## Open Questions

- [x] **OQ1 — The decisions D1–D12. Accepted as recommended on 2026-11-14,** with the caveats in *Gate*.
  - **D1 (accepted). codex and `all`.** Accept `--target codex` and `all`. Skip codex with one line on stdout, as a success (exit 0). `status` says `not supported yet`. `hooks run codex` is the unknown-agent path (exit 0). *Why:* the default `all` must not fail, and the CLI shape stays stable for slice 7.
  - **D2 (accepted). The command string.** `tarmac hooks run claude || true` (shell form), not the bare string. The bare string is still recognised as ours. *Why:* an older or missing `tarmac` must never exit 2 into `Stop` or `UserPromptSubmit`, or put an error notice on every event.
  - **D3 (accepted). No matcher.** `Notification` with no matcher; the binary keeps `permission_prompt`, from `notification_type`. *Why:* the mapping stays in the binary. **Risk:** the brief verified the matcher value `permission_prompt`; the payload field `notification_type` is known from the docs only. If the real payload lacks it, `blocked` never fires and every unit test still passes. So Step 0 (*Gate*) checks it on real input first, and the matcher form is the fallback.
  - **D4 (accepted). `SessionStart` installed now, as a no-op.** *Why:* slice 4 then needs no re-install.
  - **D5 (accepted). "Ours" is an exact match** of the two command strings, after a trim, on a `type: "command"` handler with no `args` key (clarified in review 2026-11-14: the body already listed exec form with `args` as foreign). Near-matches are foreign. A hand edit of our handler (such as `timeout`) is "old form", and `install` overwrites it.
  - **D6 (accepted). JSON.** `serde_json` with `preserve_order` in `tarmac-cli`. This adds `indexmap` (and `hashbrown`, `equivalent`) to the lockfile, and the feature is unified onto `tarmacd`. The feature is set in `[workspace.dependencies]`, so `-p tarmacd` builds match the shipped build. The indent is detected, the final newline is kept, and the reformat list in *Writing* is accepted.
  - **D7 (accepted). Backup.** One `<file>.tarmac-backup`, replaced at each write, and only when we write. Its path is printed at each write.
  - **D8 (accepted). Symlinks.** Write through to the target, and keep the link. A target that is not writable fails closed (S16b).
  - **D9 (accepted). Stdin.** Check `TARMAC_TERM_ID` first. Then read at most 4 MiB, with a wait of at most 1 s. A tty on stdin is not read. Step 0 checks the pipe-buffer case.
  - **D10 (accepted). Text.** Fold whitespace runs to one space, remove other control characters, trim, then `cap_report_text`. An empty text is no text. (Clarified in review 2026-11-14: the removal runs before the fold, so that `"a \u001b b"` gives `"a b"`, and whitespace is `char::is_whitespace`. See *hooks run* step 5.)
  - **D11 (accepted). The hook's deadline.** 500 ms for the whole exchange, with no retry, through a `report::send` seam that takes a deadline. The `timeout: 5` in the handler is the backstop.
  - **D12 (accepted). `uninstall` flags.** `uninstall` takes `--scope` and `--dry-run` as well as `--target`. The design lists only `--target`, but without `--scope` a project install cannot be removed.
