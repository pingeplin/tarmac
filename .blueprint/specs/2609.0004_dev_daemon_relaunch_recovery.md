## Context

`make run` pins a per-worktree socket and state (`Makefile:54–55`,
`$(ROOT)/.dev/`) and an absolute `TARMAC_DAEMON` (`:56`), then launches
`npm run tauri dev`. The Tauri backend's
`connection_loop` (`bridge.rs:235–262`) is the only thing that ever starts a
daemon: `connect()` (`:394–421`) tries the socket, and **on the first miss only**
spawns `tarmacd` and latches `spawned = true`. `spawn_daemon` (`:480–493`) sets
`.stdin(Stdio::null())` and injects `PATH`, and nothing else — the child inherits
tauri-dev's stdout/stderr and stays in its session and process group.

### Ground truth (probed, not inferred)

| # | Probe | Result |
|---|---|---|
| A | `kill -HUP` a running `tarmacd` | **Dies. Socket file left behind.** |
| B | Start a daemon over that stale socket file | **Recovers** — logs `removing stale socket`, unlinks, binds |
| C | Start a second daemon while the first is listening | **`exit(1)`** — `another tarmacd is already listening` |
| D | Poll `connect()` against a SIGHUP-dying daemon every 20 ms | **`ECONNREFUSED` from the first sample**, socket file still present |

Probe D **disproves the race as filed.** The issue claimed the run-1
daemon stays "transiently reachable" *while dying*, so the newly spawned daemon's
`claim_socket` connects and exits 1. It does not: the listener is refused from the
first observable moment after the signal. Probe B disproves the other half of the
folk explanation — a stale socket file on its own is **not** a stuck state, because
any fresh daemon clears it.

### The failure's necessary conditions

The permanent disconnect does not need a race. It needs exactly two things:

1. **One missed `connect()` that latches the spawn.** `connect()` sets
   `*spawned = true` whenever it takes the spawn branch (`:402–406`).
2. **The daemon spawned in response never ends up listening.**

Once both hold, D3 makes the state permanent: `spawned` is reset **only** on a
version-mismatch restart (`:245`), so no later pass ever spawns again, and probe
B's stale-socket recovery — which only a *starting daemon* performs — is never
reached. After the bounded 10 attempts (`:498–501`, ≈ 2 minutes: ~90 s of backoff
plus ten 3 s connect windows) `connection_loop` `break`s, and the loop is dead for
the lifetime of the process — there is no retry affordance in the app.

Three causes of (2) are verified in the code. **This spec does not claim to know
which one fired on #26:**

- **The spawn never happened.** `spawn_daemon` returns `()` and swallows
  `Command::spawn()`'s `Err` (`:486–492`), while `connect()` latches
  `*spawned = true` regardless (`:402–406`). A `tarmacd` that is missing,
  mid-relink, or non-executable therefore locks the app out with **no race at
  all**. This is the strongest instance of D3.
- **The daemon died after binding.** `main.rs` binds at `:81` and only then builds
  `state::Daemon` (`:84`), whose `?` can fail — any exit after the bind leaves a
  bound-then-dead socket file behind.
- **A foreign daemon held the socket.** `claim_socket` `exit(1)`s against a live
  listener (probe C) — e.g. a second `make run`, or a daemon that binds between the
  app's miss and the new daemon's claim.

The run-1 daemon is orphaned but alive across a window close (the app never kills
it — there is no `RunEvent::Exit` handler anywhere in `desktop/src-tauri`;
`daemon_child` is used only for the version-mismatch SIGTERM at
`bridge.rs:297–306`).

#### What is ruled out

The chain as filed on #26 routed condition (2) through the *run-1* daemon: the app
misses, spawns daemon #2, daemon #2 finds daemon #1 still alive and `exit(1)`s,
then daemon #1 dies leaving debris. The probes and `claim_socket` rule that out
three separate ways:

- A daemon connectable to daemon #2's `claim_socket` at T0+δ was connectable at T0
  on the same path — a dying process does not become reachable again — so the app's
  own `connect()` at T0 would have **succeeded** and there would have been no spawn.
- If the miss came from the unlink window instead (`main.rs:96` removes the file
  *before* `exit(0)`, so a daemon can be listening with its path gone), then
  `claim_socket` finds `path.exists() == false` (`main.rs:46`), skips the connect
  probe entirely, and **binds**. It cannot reach `exit(1)` down that path.
- A daemon on the SIGTERM path has already unlinked and is calling `exit(0)`; it
  cannot then "die by SIGHUP" and leave debris. The two halves of the filed story
  need different deaths of the same process.

Probe D disposes of the "transiently reachable while dying" step independently: the
listener is refused from the first observable sample after the signal.

**None of this changes the fix.** Four defects are verified on their own terms, and
each is worth closing regardless of which one fired:

- **D1 — the daemon is not detached, despite its own comment saying it is.**
  `spawn_daemon`'s doc comment reads "Launch the daemon detached"; the code does no
  `setsid`, no `pre_exec`, no `process_group`. It shares tauri-dev's session, so it
  is in the blast radius of every SIGHUP aimed at that session — the opposite of
  the "persistent observatory" role `docs/architecture.md` gives it.
- **D2 — SIGHUP is unhandled** (`main.rs:88–96` installs SIGTERM and SIGINT only),
  so it is the one death that skips the unlink (probe A) — and it is exactly the
  signal a dev terminal sends its session on teardown. Note that SIGPIPE, named in
  the issue as a co-cause, is **not** one: Rust's std sets it to `SIG_IGN` before
  `main` and `tarmacd` never resets it, so a write to a closed stderr returns
  `EPIPE`.
- **D3 — `spawned` is a latch with no reset for a spawn that died, or that never
  happened.** `connect()` sets it inside `if let Some(daemon) = …` without
  consulting whether `Command::spawn()` succeeded, because `spawn_daemon` discards
  that result. One doomed spawn permanently removes the app's ability to start a
  daemon.
- **D4 — the reconnect budget is finite and terminal.** Once spent, the loop
  breaks and nothing in the app can restart it (see Out of Scope).

D1 and D2 govern **how often** condition (1) is met — together they make "stale
socket file, no daemon" the resting state after a dev-terminal teardown. D3 governs
whether condition (1) is **survivable**. Only D3 turns a transient miss into a
terminal one.

## Motivation

The workaround is `make kill-daemon && make run`, which every developer on this
repo has to learn by being bitten, and which the app gives no hint toward — the
status just reads disconnected. Worse, the app takes ~2 minutes of visible
retrying before it gives up, so the failure looks like slowness first and
permanence second.

D1 is the one with reach beyond dev. The daemon is specified as the persistent
observatory that owns every PTY; a daemon that dies with the terminal that
happened to start it is not that, and the comment claiming otherwise means the
next person to read the file will not look. D2 means the one death mode that
survives D1 leaves debris.

## Proposed Solution

### Overview

Close D1–D3. Each is small and independently verifiable. D3 is the one that
removes the *permanence*: whatever caused the miss, the app can try again. D1 and
D2 reduce how often the app faces a stale socket at all — the daemon stops
receiving the terminal's SIGHUP (D1), and an explicit SIGHUP stops leaving debris
(D2).

### Key Components

- **`desktop/src-tauri/src/bridge.rs` — detach the spawn (D1).** Extract the
  `Command` construction into a builder that **returns the `Command` rather than
  spawning it**, taking the program path, the base `PATH`, the `cli_dir`, and the
  log path as parameters — so a test can point it at `/bin/sh`, append its own
  `.arg()`s, and spawn it without an `AppHandle` or a real daemon. It adds:
  - `pre_exec(|| { libc::setsid(); Ok(()) })` — a **new session**, not merely a new
    process group: `process_group(0)` would leave the daemon in tauri-dev's session
    and still in the path of a session-wide SIGHUP.
  - stdout/stderr redirected to `tarmacd.log` **beside the socket** (i.e. in
    `socket_path().parent()`, which is `.dev/` under `make run` and the per-channel
    dir otherwise). Not `/dev/null`: dev logging is the reason the pipe was
    inherited in the first place, and `tail -f .dev/tarmacd.log` must replace it.
    Three details are contractual, not incidental:
    - **the parent dir is created first** (`create_dir_all`) — `.dev/` does not
      exist on a fresh clone, and today it is the *daemon* that creates it, after
      the app has already tried to open the log;
    - **the file is opened truncate-and-create** (`create(true).truncate(true)`),
      so each daemon launch starts a fresh log and the file is bounded by one
      session's output rather than growing without limit. This is a **decided
      product call** (2026-09-06), not a default: it applies in release builds too,
      where the packaged `.app` spawns its daemon through this same code. The cost
      is that the previous daemon's log is gone the moment a new one starts — if
      you are chasing a crash-then-relaunch, copy the file before relaunching;
    - **if the open fails, the daemon is still spawned** with inherited stdio —
      today's behaviour, so a read-only or missing log dir can never become a new
      way to lose the daemon.
  - Fix the doc comment so it describes what the code does.
- **`core/crates/tarmacd/src/main.rs` — handle SIGHUP (D2).** Add
  `SignalKind::hangup()` to the existing `select!` (`:91–94`, alongside the handler
  installs at `:89–90`) so it takes the same unlink-then-`exit(0)` path as
  SIGTERM/SIGINT. D1 stops the *app-spawned* daemon from being in a terminal's
  session, but a hand-started `tarmacd` still is — and that is precisely the case
  where the clean shutdown matters. An explicit `kill -HUP` deserves it too.
  **Register the three signals before `bind`.** Today the handlers are installed
  inside a `tokio::spawn`ed task (`:87–90`) that runs *after* `bind` (`:81`), so the
  socket is connectable — and `wait_for_socket` satisfied — before any handler
  exists. `signal()` registers its `sigaction` synchronously, but the task must
  first be scheduled: a signal delivered in that gap takes the **default** action
  and kills the process. Construct the three `Signal` streams in `main` between
  `claim_socket` (`:80`) and `bind` (`:81`), then move them into the task. This is
  not test hygiene — it closes a real, narrow startup race that SIGTERM already has
  today, and without it S4 is intermittently red on the *fixed* daemon.
- **`desktop/src-tauri/src/bridge.rs` — make the latch a fact (D3).** Replace the
  bare `spawned` boolean test with a decision over an **observable OS fact**: we are
  not currently supervising a live daemon child. Expressed as a pure function beside
  `reconnect_delay`:

  ```
  fn may_spawn(already_spawned: bool, prior_child_exited: bool) -> bool
  ```

  `prior_child_exited` means **"no live child we spawned"**. Only an
  *observed-live* child blocks a respawn, so it covers three cases that must
  behave identically: `daemon_child` is `None` (the `Command::spawn()` itself
  failed — see D3), `try_wait()` returned `Ok(Some(_))`, **or `try_wait()`
  errored**. The error arm is deliberate: it is the "we don't know" case, and
  answering it with `false` would reintroduce exactly the defect this function
  exists to remove — an unknown state that locks the app out for good. Erring the
  other way costs at most one extra spawn per pass and is bounded by the
  reconnect budget. Because that
  derivation is where the defect actually hides, it gets its own testable helper
  rather than an inline `map(...).unwrap_or(false)`:

  ```
  fn prior_child_exited(child: Option<&mut std::process::Child>) -> bool
  ```

  Additionally, `connect()` must **not latch on a spawn that failed**: `spawn_daemon`
  returns the `Result`/`Option` it currently discards, and `*spawned = true` is set
  only when a child actually exists.

  Together this keeps the "don't pile on a daemon we just started" property that the
  latch was there for, while removing the "one doomed spawn locks us out forever"
  property that was never intended.
- **`docs/architecture.md:174`** — the sentence "A SIGTERM/SIGINT handler removes
  the socket and `exit(0)`s" becomes SIGHUP/SIGTERM/SIGINT. ACTIVE doc; must move
  with the code.

### Data Flow

1. App `connect()` misses the socket.
2. It consults `may_spawn(spawned, prior_child_exited(daemon_child.as_mut()))`. The
   `daemon_child` lock is taken and released around that call only — it is a
   `std::sync::Mutex` inside an `async fn`, so its guard must never be held across
   an `.await`.
3. If allowed, it spawns via the detached builder: new session, log file, injected
   `PATH`. `spawned = true` **only if a child was actually created**; the handle
   replaces whatever `daemon_child` held.
4. If that daemon exits for any reason (`exit(1)` against a live foreign daemon, or
   an exit after binding), the next pass sees `prior_child_exited == true` and is
   allowed to spawn again — bounded in practice by the same 10-attempt reconnect
   budget. If the spawn never happened, `daemon_child` is `None` and the next pass
   is likewise allowed.
5. On SIGHUP/SIGTERM/SIGINT the daemon unlinks its socket and exits 0, so the next
   daemon never has to reason about debris.

### Interface Contract

No wire-protocol change. `docs/protocol.md:28–30` (startup socket claim: connect
to decide live vs. stale) is **unchanged** — `claim_socket` keeps its `exit(1)`.

One changed observable: a `tarmacd` sent SIGHUP now **exits 0 with its socket file
removed**, where it previously died by signal leaving the file. SIGTERM/SIGINT are
unchanged.

The daemon's *outbound* use of SIGHUP is also unchanged: `term_close` and
board-delete signal a terminal's process group with `libc::kill(-pid, SIGHUP)`
(`docs/architecture.md:233–234`, `docs/protocol.md:416`). The daemon is never a
member of those groups — each PTY child is its own group leader — so D2 does not
make the daemon a target of its own kill path. That stays true after `setsid()`:
the ctty hazard it would have needed was probed on macOS and does not exist (see
Trade-offs).

One new observable artefact: `<socket dir>/tarmacd.log`, truncated at each daemon
launch, written by
app-spawned daemons only. A daemon started by hand keeps writing to its terminal.

## Alternatives Considered

### Make `claim_socket` retry instead of `exit(1)`

Rejected. It changes a contract stated in an ACTIVE doc (`docs/protocol.md:28–30`)
to paper over a race the app can simply stop losing, and it weakens the single
useful guarantee `claim_socket` gives — *one daemon per socket, deterministically*.
It also does nothing for D1 or D2. Kept here as the named fallback for the one
condition-(2) cause D3 cannot remove — a racing *foreign* daemon holding the socket
— should S10 show D1–D3 insufficient.

### Have the app SIGTERM its daemon on window close (`RunEvent::Exit`)

Rejected. It contradicts the daemon's specified role: the observatory outlives the
cockpit on purpose, so terminals and boards survive an app restart. This would trade
a dev-loop annoyance for the loss of the product's central property.

### `process_group(0)` instead of `setsid()`

Rejected. A new process group in the same session still receives a session-wide
SIGHUP on terminal teardown, so it does not close D1.

### Redirect the daemon's output to `/dev/null`

Rejected. `RUST_LOG=debug` on the dev daemon is a routine debugging tool here;
silently discarding it would be a regression traded for one line saved.

## Out of Scope

- **D4, the terminal reconnect budget.** After 10 attempts `connection_loop` breaks
  and the app can never reconnect without a restart. With D3 closed, exhausting the
  budget takes ten consecutive failures to both spawn and connect rather than one,
  which no longer describes any cause named above — but it is still reachable (a
  daemon binary that stays broken for two minutes will do it). Fixing D4 is a
  separate UX decision
  (retry forever at the 15 s cap, or a visible Retry affordance in the status
  chrome) and belongs in its own issue. **This spec deliberately leaves a
  permanent-disconnect path open**; that is the honest cost of keeping this diff
  scoped.
- The installed-daemon-hijacks-dev problem (`CLAUDE.md` Gotchas). `make run`'s
  per-worktree `TARMAC_SOCKET` already separates dev from installed.

## Acceptance Scenarios

Legend: **[R]** Rust test in `desktop/src-tauri/src/bridge.rs` `mod tests` (the
app-cargo pass of `make test`) — several spawn short-lived probe children, which is
deliberate: the assertions are OS facts, not mocks; **[I]** daemon integration test
under `core/crates/tarmacd/tests/`; **[Q]** manual QA against `make run`.

### D1 — detachment

- **S1 [R]:** Given the daemon command builder pointed at `/bin/sleep` with a `30`
  argument, when the returned `Command` is spawned, then
  `libc::getsid(child.id() as libc::pid_t)` **equals the child's own pid** — it is a
  session leader — and differs from the test process's `getsid(0)`. The equality is the
  load-bearing half: a `getsid` that merely *errors* (`-1`) would satisfy a
  difference test vacuously, and `process_group(0)` would leave the sid equal to
  the test process's. Kill the probe child at the end of the test. No polling is
  needed — `Command::spawn` returns only after the child has exec'd, so `pre_exec`
  has already run; if that proves flaky, poll to a deadline rather than sleeping.
- **S2 [R]:** Given the builder pointed at `/bin/sh -c 'echo out; echo err >&2'`
  and a log path inside a **not-yet-existing** subdirectory of a temp dir, when the
  child is spawned and waited on, then that file exists and contains both `out` and
  `err`. One assertion covers three requirements: the parent dir is created, stdout
  is redirected, stderr is redirected. It fails if either stream is left inherited.
- **S2b [R]:** Given the same log path used twice, when a second probe child writes
  a different marker, then the file contains **only the second** marker — the log is
  opened truncate-and-create, so each launch starts fresh and one session's output
  is the file's upper bound. An `append(true)` implementation fails this, and so
  does an implementation that opens the file without either flag and leaves the
  first marker's bytes behind the second's.
- **S2c [R]:** Given a log path that cannot be opened (point it at a directory),
  when the builder is asked for a `Command`, then it still returns one and the
  probe child still runs to completion. A missing or unwritable log dir must never
  become a new way to fail to start the daemon.
- **S3 [R]:** Given the builder constructed with base `PATH` `/usr/bin:/bin`,
  `cli_dir` `/x/bin`, and `/bin/sh -c 'printenv PATH'`, when the child is spawned
  and waited on, then the log file contains exactly `/x/bin:/usr/bin:/bin`. The
  expectation is a literal, not a second call to `inject_cli_path` — otherwise the
  test asserts `f(x) == f(x)` and passes against any `f`.

### D2 — SIGHUP leaves no debris

- **S4 [I]:** *(Requires the pre-`bind` signal registration in Key Components — see
  D2. Without it this scenario is flaky on the fixed daemon, because
  `wait_for_socket` returns as soon as the socket binds and does not prove the
  handler task has run.)* Given a running daemon on a temp socket, when it is sent
  **SIGHUP**,
  then it exits with **status code 0** (exited, not killed by a signal) and the
  socket file is gone within a bounded wait. This is the D2 defect assertion:
  against `main` the process is killed by signal (`status.code() == None`) and the
  file remains — probe A. Belongs beside `socket_claiming` in
  `daemon_basics_integration.rs`, per the subject-named-suite convention.
- **S5 [I]:** *Already pinned — write no new test.*
  `daemon_basics_integration.rs::socket_claiming` (`:200–208`) SIGKILLs a live
  daemon, asserts the socket file survives, starts a fresh daemon, and proves it
  binds and serves a `hello`. That is probe B as a standing guarantee. The D2 change
  must leave it green: SIGHUP handling makes stale sockets rarer, and must not make
  the recovery path unreachable or untested.
- **S6 [I]:** Given a running daemon, when a second daemon is started on the same
  socket, then the second exits `1` **and the first still serves a `hello`**.
  `socket_claiming` (`:188–198`) already pins the exit-1 half; only the survival
  clause is uncovered. Extend that test with a `Conn::hello(&sock, "cli")` against
  the still-running first daemon immediately after the second exits — do not write a
  second copy of the test.

### D3 — the app can always try again

- **S7 [R]:** Given `may_spawn`, when no daemon has been spawned yet
  (`already_spawned = false`), then it returns `true`.
- **S8 [R]:** Given `may_spawn`, when a daemon was spawned and **has not exited**,
  then it returns `false` — the app does not pile a second daemon onto one it just
  started. An implementation that simply always allows a spawn fails here.
- **S9 [R]:** Given `may_spawn`, when a daemon was spawned and **has exited**, then
  it returns `true`. **This is the D3 defect assertion**: a `may_spawn` written as
  today's rule (`!already_spawned`) passes S7 and S8 and fails only this one.
- **S9b [R]:** Given `prior_child_exited`, then: `None` → `true` (the spawn itself
  failed, so there is nothing to pile onto); a live child (`/bin/sleep 30`) →
  `false`; a child that has exited (`/bin/true`, after `wait()`) → `true`. The
  `None` case is the one the obvious `map(...).unwrap_or(false)` gets backwards,
  re-creating the permanent lockout for a spawn that never produced a child.
  **Defense in depth, not the headline.** Once this spec's own latch fix lands —
  `*spawned = true` only when a child exists — `None` is unreachable through
  `connect()`. And "missing or mid-relink `tarmacd`" is a weak motivation under
  `make run`: its `core` and `sidecars` prerequisites rebuild *and re-uplift* the
  binary immediately before launch, so "missing" cannot happen and "mid-relink"
  (`ETXTBSY`) needs a concurrent `cargo build` inside a ~1 s window. S9b earns its
  place by pinning the truth table's fourth row, not by naming a likely cause.

- **S9c [R]:** Given the spawn decision driven with a **real `Child`**, when the
  child is killed and reaped and the decision is asked again, then it permits a
  second spawn. **This is the only automated scenario that can fail because of
  wiring rather than arithmetic.** S7–S9b test a pure function that nothing forces
  `connect()` to call — an implementation can make all four green and fix nothing.
  Extract the decision behind a seam a test can drive (a small struct owning the
  `Option<Child>` with a `may_spawn(&mut self) -> bool` that consults `try_wait`,
  or an equivalent), so the observable — *a dead child re-enables spawning* — is
  asserted rather than grepped for. If the design makes this untestable, say so and
  the DoD's grep item stands alone; do not delete the scenario silently.

### End-to-end

- **S10 [Q]:** Given `make run` connected, when the app window is closed and
  `make run` is issued again, then the app reaches connected without
  `make kill-daemon` in between. Run it three times in a row, and also with the
  dev terminal itself closed between runs (the SIGHUP path).
- **S10b [Q]:** *The positive repro — red before, green after.* Given
  `make kill-daemon` was run first (so the app itself is the spawner and latches
  `spawned = true`) and `make run` has reached connected, when `make kill-daemon` is
  run again **from a second shell**, then the app reconnects on its own within the
  reconnect budget. **On `main` it must not**: `run_connection` sees EOF,
  `connect()` misses the stale socket, `!*spawned` is already false, no respawn ever
  happens, and after ~123 s of retries `connection_loop` `break`s — dead for the
  lifetime of the process. This is the deterministic demonstration the spec lacked;
  it uses existing `make` targets only, needs no close/relaunch and no hand-built
  command line, and it forces exactly the two necessary conditions.
- **S11 [Q]:** Given `make run`, when the daemon has been spawned by the app, then
  `.dev/tarmacd.log` exists and grows, and `RUST_LOG=debug make run` puts debug
  lines into it (`spawn_daemon` overrides only `PATH`, so `RUST_LOG` is inherited)
  — the dev logging that D1 moves off the inherited pipe is still reachable.
- **S12 [Q]:** Given `make run` with the detached daemon, when a terminal card is
  spawned, used, and closed, then output flows and the card exits cleanly, and the
  daemon is still connected afterwards. Note that `make test`'s existing PTY suites
  are **not** evidence here: D1 changes only the app's spawn, so the harness daemon
  is not a session leader and those suites never exercise the changed condition.
  This is a human check with no automated counterpart **on purpose** — an earlier
  draft specified an integration scenario for it, and that scenario was cut because
  it cannot fail: the controlling-terminal hazard it guarded against was probed
  directly on macOS and does not exist (see Trade-offs). A test that cannot go red
  is not insurance, it is noise.

Tests follow the project's conventions and these principles:

- **Behavioral over structural** — assert observable OS facts (session id, file
  presence, exit status), not internals.
- **Every test can fail** — S4 must fail against today's daemon, and S9/S9b must
  fail against the two obvious wrong implementations named in the Definition of
  Done. A scenario nobody can make red is not a scenario.
- **Deterministic, isolated, readable** — temp dirs per test, bounded polling with a
  deadline (the harness's `LONG` and `wait_for_socket` are the precedent), no sleeps

## Trade-offs and Limitations

- **The mechanism is narrowed, not reproduced.** Two candidate chains have now been
  written down and both were wrong: the one filed on #26 — daemon #1 *transiently
  reachable while dying* (probe D refutes it) — and its first correction, daemon #1
  *fully alive* at the claim (`claim_socket` and the app's own retry loop refute it;
  see §What is ruled out). What
  survives is a pair of *necessary conditions* and three verified causes of the
  second, with no evidence about which one fired. The fix is therefore justified as
  closing four defects each verified against the source, **not** as a demonstrated
  repro. S10 is the closest thing to a repro gate and it is a negative test — the
  failure must stop happening — which is weaker evidence than watching it happen
  once. If S10 still fails after D1–D3, the cause is a fourth thing and this spec
  is incomplete rather than wrong.
- **`setsid()` changes PTY ownership in principle, but the hazard was probed and
  is not real on macOS.** A session leader with no controlling terminal can acquire
  one by opening a tty, and `portable-pty` calls `openpty` in the *parent*
  (`portable-pty-0.9.0/src/unix.rs:36`) — so a `setsid()` daemon could in theory
  adopt a card's PTY as its ctty and then be taken down by that card's teardown. A
  C probe replicating exactly that sequence (`setsid()` → `openpty()` →
  `open("/dev/tty")`) returns **ENXIO both before and after** the `openpty`: macOS
  grants no controlling terminal on open, and the PTY child claims it explicitly
  via `TIOCSCTTY` in `pre_exec` (`unix.rs:257, 271`). An integration scenario for
  this was specified and then **cut, because it could not go red under any
  implementation** — a non-falsifiable test is not insurance. S12 keeps a human
  check; the residual risk is a future macOS that changes ctty-on-open semantics.
- **After `setsid()`, Ctrl-C on `make run` no longer stops the daemon** — and this
  cuts against D1's own dev-loop motivation. Today the daemon sits in the
  terminal's foreground process group, so Ctrl-C delivers SIGINT and it shuts down
  cleanly via `main.rs:90`. Detached, it survives every Ctrl-C. Combined with
  `should_restart` comparing `CARGO_PKG_VERSION`s — which a same-version rebuild
  never trips — a developer will keep reconnecting to **stale daemon code** until
  they run `make kill-daemon`. This makes the standing `CLAUDE.md` gotcha ("kill any
  running daemon before testing daemon changes") load-bearing rather than advisory.
  Mitigation is out of scope here; the honest options are a `make run` that kills
  first, or a build-id (not version) check in the handshake.
- **Handling SIGHUP makes one failure quieter.** A daemon killed by a stray SIGHUP
  used to die loudly (killed-by-signal, socket left behind); it will now log
  `shutting down` and `exit(0)` like any clean stop. That is the point of D2, but it
  does mean a mysteriously-vanished daemon leaves a less distinctive trace.
- **D4 is knowingly left open** (see Out of Scope): after 10 failed attempts the app
  still gives up permanently, with no way back but a restart.
- **The log is bounded by one session, and the previous session's is destroyed.**
  Truncate-on-open (the decided option) caps the file at whatever one daemon writes
  before it exits, which is what makes shipping it in release builds acceptable —
  the packaged `.app` spawns its daemon through the same code, so release users get
  an `info`-level `tarmacd.log` under `~/Library/Application Support/tarmac/` where
  a Finder-launched daemon's output is today discarded. The cost is real and
  asymmetric: **a daemon that dies and is respawned erases the log of the death you
  were trying to diagnose.** A long `RUST_LOG=debug` session can still grow the file
  without limit *within* that session; nothing rotates it.
- The daemon's stdout/stderr moving off the terminal changes a habit: output that
  used to appear inline in the `make run` terminal now needs `tail -f`.

## Open Questions

- **Resolved: there *is* a deterministic positive repro, and it is S10b.**

  ```
  make kill-daemon      # app becomes the spawner, so it latches `spawned`
  make run              # wait for connected
  make kill-daemon      # from a second shell
  ```

  The kill leaves a stale socket, `connect()` misses it, `!*spawned` is already
  false, and no respawn ever happens — ~123 s of retries, then `break`. Existing
  targets only. This replaces an earlier draft's
  `make kill-daemon && chmod -x core/target/debug/tarmacd && make run`, which
  **does not work**: `make run`'s `core` prerequisite runs `cargo build`, and
  cargo's uplift step re-copies `deps/tarmacd-<hash>` over `target/debug/tarmacd`
  and restores mode 755 *even on a no-op build* (reproduced three times). The app
  would spawn a perfectly executable daemon and connect normally.

  Note the naive version — connect, close the window, relaunch — also does **not**
  reproduce it: run 1's daemon is orphaned but alive, so run 2 simply reconnects
  and never takes the spawn branch. What remains genuinely unproven is which cause
  fired on #26 itself; S10b demonstrates the *lockout*, not the original trigger.
- **Resolved (2026-09-06): release writes `tarmacd.log`, opened truncate-on-open.**
  D1's redirection is motivated by dev logging, but the packaged `.app` spawns its
  daemon through the same code, so the question was whether release users should get
  the file at all. Decision: **keep it in release, and truncate at each launch.**
  Truncation is what makes keeping it acceptable — the file is bounded by one
  session instead of growing unrotated for the life of an install, and it stays
  available as a support artefact when a user reports a problem. The rejected
  alternatives were `/dev/null` in release (loses the support artefact) and
  append-and-create (unbounded). The accepted cost is recorded in Trade-offs: a
  respawn erases the previous daemon's log.
