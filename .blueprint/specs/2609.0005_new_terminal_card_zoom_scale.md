# 2609.0005 A terminal card mounts at the board's settled raster scale

**Date:** 2026-09-06
**Status:** draft
**Author:** EP Lin
**Issue:** [#87](https://github.com/pingeplin/tarmac/issues/87) `fix(terminal): newly spawned terminal card doesn't immediately pick up board's current zoom scale`
**Design doc:** none — the terminal oversample model is already settled by `desktop/src/kit/rasterScale.ts` and the header comment at `desktop/src/cards/TerminalCard.tsx:12–21`. (The *doc-card* half of `rasterScale.ts:6–9` predates frozen-K and no longer describes `DocCard`; see Out of Scope. Do not read it as current.) This spec fixes one mount-ordering defect inside the terminal model; it changes no policy.

All line citations below were re-checked against `9175b49`.

## Context

`BoardEngine` owns a single settled `rasterScale` and pushes it to `Board`
(`BoardEngine.ts:319–323` → `Board.tsx:87`), which passes it down as a prop to
every **terminal** card — `Board.tsx:188` is the only `rasterScale={…}` in the
tree. `TerminalCard` consumes it by the **oversample** route
documented at the top of `TerminalCard.tsx`: the raster wrapper is sized
`rasterScale × 100 %` and counter-scaled `scale(1 / rasterScale)`, while
`term.options.fontSize` and the host padding are multiplied by the same factor,
so `FitAddon.fit()` lands on the *same* `cols × rows` at `rasterScale × DPR`
pixel density.

Both halves are required, but they do **different** jobs — and the file's own
header comment is wrong about this. `TerminalCard.tsx:16–17` claims the padding is
scaled "so `FitAddon.fit()` recomputes the SAME cols×rows". It does not.
`tokens.css:56–61` applies a global `* { box-sizing: border-box }`, and `FitAddon`
sizes itself from the *computed* width/height of the host — which for a border-box
element already includes the padding. Measured with a real `Terminal` + `FitAddon`
in this card's exact DOM nesting, in the WebKit engine Tauri ships: a 470 × 300
slot computes `width: 470px` under `border-box` against `450px` under
`content-box`, and a **font-only** fix at `rs = 2` yields `48 × 16` — *identical*
to the full fix.

- **`fontSize` alone governs the grid.** If the wrapper grows to `rs ×` while the
  font stays at `1 ×`, `fit()` measures an `rs ×`-large host against a `1 ×`-large
  cell and returns ≈ `rs ×` the intended grid (measured: `96 × 33` at `rs = 2`
  against a correct `48 × 16`).
- **The padding governs the visual gutter only** — the inset between the card
  body's edge and the first glyph. Left at `1 ×` inside an `rs ×` host it is
  counter-scaled to `1/rs` of its intended on-screen size: the gutter halves at
  `rs = 2`, thirds at `rs = 3`. No `cols × rows` consequence at all.

That distinction is load-bearing for the scenarios below: `stty size` is **blind**
to the padding half, so it cannot be the only tell (see S1).

That is exactly what happens on mount today, because of effect ordering:

- The correction lives in a `useLayoutEffect` (`TerminalCard.tsx:345–356`).
- The `Terminal` is constructed in a **passive** `useEffect` declared earlier
  (`:102`), which assigns `termRef.current = term` at `:132`.
- React runs *all* layout effects at commit, then the passive effects. So on the
  first commit the layout effect runs **first**, finds `termRef.current === null`
  (`:346–348`), and returns early.

The resulting mount sequence when a card is created while the board is settled at
`rs > 1`:

1. Render. The wrapper already carries `width/height: rs × 100 %` and
   `transform: scale(1 / rs)` (`:396–401`) — it reads `props.rasterScale` during
   render, so it is correct from the first frame.
2. The layout effect fires and no-ops (no terminal yet).
3. The mount effect constructs the `Terminal` with the **unscaled**
   `fontSize: termFontSize` (`:110`), and never touches `host.style.padding`, so
   the host keeps the `8px 10px 16px` from `.term-host`
   (`desktop/src/theme/app-only.css:73`, in the rule at `:70–75`) — both `1 ×`
   values inside an `rs ×`-sized host.
4. `fit.fit()` at `:206` therefore returns ≈ `rs ×` the intended grid — that
   blow-up is the `fontSize` half alone — and
   `onSpawn(cols, rows)` at `:212` ships **that inflated grid to the PTY**. The
   damage is not cosmetic: the shell, and any full-screen TUI in it, is told the
   terminal is `rs ×` wider and taller than the user can see.
5. Glyphs render at `1 / rs` of the intended size once the counter-scale applies.

It self-corrects only when `props.rasterScale` **changes value**.
`scheduleRasterSettle` fires the callback only on an actual change
(`BoardEngine.ts:321–323`), and the value is the bucketed output of
`deriveRasterScale` (step `0.5`, cap `3.0`). So a zoom gesture that settles
inside the same bucket — e.g. 1.6 → 1.9, both bucket `2.0` — does **not** repair
the card. The user must zoom far enough to cross a bucket boundary.

## Motivation

Every terminal card spawned away from rest is born wrong, and the wrongness is
invisible as a cause: the user sees tiny text and a mis-sized shell, with nothing
naming the reason. Because the repair is gated on a *bucket change*, the obvious
remedy ("zoom a bit and back") frequently does nothing, which reads as a flaky
app rather than a deterministic bug.

The PTY half is the expensive half. A shell that believes it has `2 ×` the
columns will wrap its prompt, its `ls` output, and any TUI at the wrong width for
the rest of that terminal's life — a wrong observable fact about the OS, which is
precisely the invariant Tarmac exists to preserve.

Spawning a card while zoomed in is not a corner case: zooming in to read a card
and then opening a terminal beside it is ordinary board use.

## Proposed Solution

### Overview

**Seed the terminal's raster metrics at construction from the value the same
render already used for the wrapper.** `rsRef.current` is assigned during render
(`:100`), so the settled scale is available inside the mount effect. Set
`fontSize` and the host padding from it *before* the first `fit()`, so the
grid `onSpawn` reports is correct from the first frame.

The `useLayoutEffect` at `:345` is unchanged and keeps owning every *subsequent*
change. After the fix the two paths agree by construction: mount applies the
metrics for `rs`, and a later settle applies the metrics for the new `rs`.

### Key Components

- **`desktop/src/cards/TerminalCard.tsx`** — the only behavioral change. In the
  mount effect: read `rsRef.current` once into a local, build the `Terminal` with
  `fontSize: termFontSize * rs`, and set `host.style.padding = termHostPadding(rs)`
  before `fit.fit()` at `:206`.
- **`desktop/src/kit/termHostPadding.ts`** — reused unchanged; it is already the
  single source of the padding string. It buys the **visual gutter**, not the
  grid (see Context), so it is the half no `stty size` check can see. Its
  file comment at `:2` still names `theme.css`; the rule now lives in
  `theme/app-only.css:70` — fix that comment with the S5 work. Its existing test
  pins only the **JS** side — `termHostPadding.test.ts:6` asserts the literal `"8px 10px 16px"`, which
  cannot fail when the stylesheet changes. The CSS side is pinned by S5, which
  this spec adds; do not assume it is already there.

### Data Flow

1. `BoardEngine` settles → `Board` state → `props.rasterScale` on the card.
2. Render assigns `rsRef.current = props.rasterScale` and sizes the wrapper.
3. Mount effect reads `rsRef.current` and constructs the terminal at those metrics.
4. `fit()` measures an `rs ×` host against an `rs ×` cell → intended `cols × rows`
   (the `fontSize` half does this); the `rs ×` padding separately keeps the visual
   gutter at its intended on-screen size through the counter-scale.
5. `onSpawn(cols, rows)` reports the intended grid to the daemon.
6. Any later settle re-runs the layout effect at `:345`, which is now a *change*
   handler rather than the only initialiser.

### Interface Contract

No wire-protocol change, no new module, no new export. `spawn_term`'s
`cols`/`rows` keep their meaning — the fix makes the app send the values the
contract always implied.

## Alternatives Considered

### Convert the terminal-construction effect to `useLayoutEffect`

Would make `termRef.current` non-null by the time the raster effect runs, if the
construction effect is also declared first. Rejected: it makes correctness depend
on **declaration order between two layout effects** — an invariant nothing in the
file states and no test can hold — and it moves xterm construction and the first
`fit()` onto the synchronous commit path, where they block paint. The defect
would come back the moment someone reorders the hooks.

### Re-run the raster effect on mount by keying it on the terminal instance

Adding `termRef.current` to the deps does not work (a ref is not reactive), and
promoting the terminal to state to make it reactive adds a render pass on every
card mount to fix two lines. Rejected as disproportionate.

### Have `BoardEngine` re-emit the settled scale whenever a card mounts

Rejected: it pushes a per-card concern into the board engine, makes the settle
callback fire without a settle (breaking the "only on change" contract at
`BoardEngine.ts:321`), and would still repair the card one frame *after* the PTY
was spawned at the wrong size.

## Out of Scope

- **Board restore at zoom > 1 — checked against the code, and *not* a defect.**
  `Board.tsx:80` seeds `rasterScale` at `1` and `BoardEngine._settledRasterScale`
  at `1` (`BoardEngine.ts:83`), but restore does not leave them there:
  `App.tsx:378` and `:926` call `engine.setViewport(vp)`, `setViewport` calls
  `apply()` (`BoardEngine.ts:112`), and `apply()` calls `scheduleRasterSettle()`
  (`:302`). A board restored at zoom 2 therefore fires a genuine settle ~150 ms
  later (`2 !== 1` at `:321`) and every card on it receives `rasterScale = 2`.
  Cards that mount inside that 150 ms window are *internally consistent* at
  `rs = 1` — 1× font and 1× padding in a 1× wrapper — so the grid they hand
  `onSpawn` is the intended one; the settle then reaches them through the layout
  effect at `:345`, which by then has a live terminal to act on. Nothing to fix
  and nothing to file. This is recorded rather than dropped because an earlier
  draft of this spec asserted the opposite.
- Doc cards and HTML cards. Neither takes a `rasterScale` prop at all — the
  oversample prop stops at `TerminalCard`. `DocCard` lays its prose out once at
  the frozen `DOC_OVERSAMPLE_K` and down-scales it with `docProseScaler`
  (`DocCard.tsx:9–11`, `:17`); `HtmlCard` uses frozen `MAGNIFY_K` for magnify and,
  for reveal, a `settledZoom` seeded from the live zoom at mount
  (`HtmlCard.tsx:75`). Both are right on their first frame by a different
  mechanism, and neither is touched here.

## Acceptance Scenarios

Legend: **[K]** desktop kit unit test (Vitest, `desktop/src/kit/`); **[Q]** manual
QA checklist item in a new `desktop/qa/new-card-zoom-scale-qa.md`.

> **Why the behavioral scenarios are [Q], not [K].** Per the repo's testing
> convention only pure `kit/` logic is unit-tested; the React/Tauri card shell is
> not, and there is no jsdom or xterm harness in `desktop/`. The contract here —
> *what `fit()` computes for a real xterm inside a real `rs ×` host* — cannot be
> asserted without one. A kit test asserting `termFontSize * rs === termFontSize * rs`
> would be a tautology (AP-4) and is explicitly **not** wanted. S1–S4 are the
> contract; S5 is a drift tripwire on the shared padding constant and does **not**
> by itself demonstrate the fix. Read plainly: the fix ships verified by hand.

### Happy path

**Shared setup for S1–S4 — the reference card.** Every behavioral scenario is
decided by comparison against a second terminal card **of the same frame size**
that was already open before the board settled. Same frame size is a
precondition, not a detail: `cols × rows` is derived from the card's box, so two
differently sized cards legitimately disagree and the comparison would carry no
information. Every spawned terminal uses `Place.termFrame = { w: 470, h: 330 }`
(`kit/placement.ts:14`), so two un-resized cards satisfy it by default.

Three tells, and each one is needed because each detects something the others
cannot:

1. **`cols × rows`**, read from *inside* each shell (`stty size`, or `tput cols`
   and `tput lines`) — detects the `fontSize` half, which is the PTY-visible half.
2. **Glyph size**, by eye against the reference card side by side — the same
   `fontSize` half, seen from the user's side.
3. **Gutter width**, the inset from the card body's left/top edge to the first
   glyph — the **only** tell for the padding half (Context: `stty size` is blind
   to it). Compare the two cards' gutters directly; at `rs = 2` a missing padding
   fix makes the new card's gutter half the reference's.

- **S1 [Q]:** Given a board settled at `rasterScale = 2` and a reference terminal
  card already open on it, when a new terminal card of the same frame size is
  spawned and **no pan or zoom gesture is made afterwards**, then the new card's
  glyphs are the same on-screen size as the reference card's, and `stty size`
  inside the new terminal reports the same `cols × rows` as the reference card,
  **and** the gutter between the card body's left edge and the first glyph column
  is the same width on both cards. **The gutter clause is not decoration** — it is
  the *only* stated criterion that can detect the padding half of the fix, because
  `stty size` is provably blind to it and glyph size is set by `fontSize` alone
  (see Context). Without the padding, that gutter is `1/rs` of the reference's.
  *"No gesture afterwards" is the whole point* — the bug's only repair path is a
  bucket-crossing settle, so any scenario that permits a gesture can be passed by
  the broken build. `rasterScale = 2` requires a board zoom in **(1.5, 2.0]**:
  `deriveRasterScale(1.5)` is `1.5`, not `2` (`rasterScale.ts:41–45`).
- **S2 [Q]:** Given a board at rest (`rasterScale = 1`, board zoom ≤ 1) and a
  reference terminal card already open on it, when a new terminal card of the same
  frame size is spawned, then its glyphs are the same on-screen size as the
  reference card's and `stty size` reports the same `cols × rows`. Stated against
  a same-session reference card rather than as "unchanged from today's behaviour",
  so the item is decidable without a pre-fix build to compare against. Be honest
  about what this buys: at `rs = 1` the fix is an exact no-op by construction
  (`termFontSize * 1`, and `termHostPadding(1)` *is* the CSS literal), so S2 is a
  no-regression pin that can only catch a botched implementation — a wrong
  variable, a `NaN`, a `rs` read before it is assigned. It is not a behavioural
  contract, and it is not evidence the fix works.

### Edge cases

- **S3 [Q]:** Given a terminal card spawned at **`rasterScale = 1.5`** that passes
  S1's criteria at that scale, when the board is zoomed *within the same bucket* —
  120 % → 144 %, both derive `1.5` — and allowed to settle, then **S1's criteria
  still hold afterwards** and none of the three values moved across the gesture.
  Both halves are required, and the first is the load-bearing one: the no-change
  half alone is satisfied by the *broken* build, where the same-bucket settle never
  fires (`BoardEngine.ts:321`) so a wrong card simply stays wrong. What this pins
  is that the card is correct **without** ever needing a settle to repair it.
  **Stated at bucket 1.5 on purpose:** 120 % and 144 % are two consecutive presses
  of the 1.2× zoom control (`App.tsx:104`), so this is runnable with the keyboard
  alone. At bucket 2.0 no two reachable levels share a bucket and the scenario
  would require a pinch. Accept that S3's first half is largely S1 re-run at a
  second scale — its distinct value is the *no-movement* half.
- **S4 [Q]:** Given a terminal card spawned at `rasterScale = 2` that passes S1,
  when the board is zoomed across a bucket boundary to `rasterScale = 3` (board
  zoom in `(2.5, 3.0]`) and allowed to settle, then the glyphs keep the same
  on-screen size, the gutter keeps the same width, and `stty size` reports a
  `rows` that is **unchanged** and a `cols` that is unchanged **or differs by at
  most one column**. This is the existing settle path still landing on a card whose
  metrics the mount already set. (The layout effect assigns *absolute* metrics,
  `termFontSize * rs` at `:350`, not a multiplier, so a compounding
  double-application is prevented by construction; S4 is the observable check that
  the assignment still happens and still agrees — a compounding bug would show as
  a gross jump, not one column.)
  **Why `cols` is not exactly invariant.** `FitAddon` subtracts a fixed
  `DEFAULT_SCROLL_BAR_WIDTH = 14` px that does **not** scale with `rs`, so
  `cols(rs) = floor((rs·W − 14) / (rs·c))` drifts upward with `rs` — measured
  `47` at `rs = 1` against `48` at `rs = 2` on the default `470 × 330` frame
  (`kit/placement.ts:14`). Rows carry no such term and are exactly invariant. This
  is pre-existing and out of scope; the QA doc must **record `cols` at each `rs`**
  and pre-authorise a ±1 column difference as the scrollbar term rather than a
  regression. It also means a settle from `rs = 1` to `rs = 2` legitimately
  resizes the reference card's PTY by one column.

### Regression tripwire

- **S5 [K]:** Given the `.term-host` rule in `desktop/src/theme/app-only.css`,
  when its `padding` shorthand is read **off disk** and compared with
  `termHostPadding(1)`, then the two are equal.
  **The test must read the stylesheet, not restate it.** `termHostPadding.test.ts`
  today asserts the literal `"8px 10px 16px"` (`:6`), which pins the JS side and
  cannot fail when the CSS changes — so it does not yet enforce this invariant.
  The house precedent for the disk-reading form is
  `desktop/src/kit/termZoom.test.ts:18–23`, which regexes `theme/card.css` for the
  header height `termInnerBox()` subtracts; follow it, keeping the existing literal
  test as the JS-side pin.
  **Why it matters here** — and *not* for the reason an earlier draft gave (it
  claimed a mismatch would make every `cols × rows` comparison measure the wrong
  box; per Context, the padding has no grid effect at all). After this fix the
  mount effect writes an **inline** `host.style.padding` on every terminal card at
  every `rs`, which means the `.term-host` CSS rule becomes inert for terminal
  hosts: it is now dead weight that no running card reads, and an edit to it would
  silently change nothing while an edit to `termHostPadding` silently changes the
  gutter. S5 is the tripwire that keeps the stylesheet and the only live source of
  that value from drifting apart unnoticed. Note the tripwire is string-shaped: a
  semantically identical CSS rewrite (four-value shorthand, or longhands) fails it
  spuriously, which is an accepted cost of the house `termZoom.test.ts` form.

  refactor the mount effect, do not introduce a new kit module for

- If you add a comment, it must explain the *why* (layout effects run before

- `make` must pass before the PR: `make docs-check`, `cd core && cargo test`,

Tests follow the project's conventions and these principles:

- **Behavioral over structural** — assert observable output/effects, not internals.

## Trade-offs and Limitations

- **The core fix is verified by hand, not by the suite.** That is the standing
  consequence of the repo's app-layer testing convention, not a choice made here.
  The mitigation is that the QA doc states the *tells* precisely enough
  (`cols × rows` from inside the shell; gutter width against a reference card)
  that the check is objective rather than a judgement about blurriness. It remains
  the weakest part of this spec: the one automated scenario, S5, would still pass
  on a completely unfixed build.
- **The `rs = 1` path is untouched**, which is the common case: a card mounting at
  rest, or inside the ~150 ms window after a board restore at zoom > 1, takes
  exactly today's path. That is *correct* rather than merely unimproved (see Out
  of Scope) — but it does mean the new code is inert on the commonest mount, and
  only a spawn onto an already-settled `rs > 1` board exercises it at all. S1 is
  the only scenario that runs it.
- **The two halves of the fix are detected by disjoint tells, and one of them is
  invisible to the obvious check.** Forgetting the `fontSize` half leaves
  `cols × rows` off by ≈ `rs ×` — unmissable. Forgetting the *padding* half costs
  **exactly zero columns and zero rows**: measured in the shipping WebKit engine,
  a font-only fix at `rs = 2` produces `48 × 16`, byte-identical to the full fix,
  because the global `border-box` reset (`tokens.css:56–61`) makes `FitAddon` read
  a computed width that already contains the padding. A runner checking only
  `stty size` cannot tell the two apart. That is why S1 carries a gutter clause,
  why the "read `rsRef.current` once into a local and use it for both" instruction
  is a requirement rather than a style preference, and why S5 pins the padding
  constant separately.
- Reading `rsRef.current` inside the mount effect is a render-value-in-an-effect
  read. Note the effect **already re-runs** — its dep array is `[model.termId]`
  (`:332`), so a term-id change rebuilds the terminal. It is safe anyway, and for
  a better reason than proximity to mount: `rsRef.current` is reassigned on *every*
  render (`:100`), so it always matches the wrapper the DOM currently carries. A
  props-closure read would be the unsafe form. What would break it is caching the
  value outside the effect.
- **A card that mounts on a backgrounded board is unaffected by this fix and still
  wrong** — with a `0 × 0` host it fits to the 2 × 2 floor regardless of `rs`. The
  guard at `:300–303` covers only *subsequent* ResizeObserver fires, not the mount
  `fit()` at `:206`. Pre-existing, untouched here, and not filed by this spec.
