Decisions the user made on 2026-10-06, before the draft and during the gate:

- The Settings window gets a place of its own for the theme, and its
  sections are listed on the left, as in macOS System Settings.
- Tarmac ships two themes: Breeze Dark (the look today) and Breeze Light.
- The control is three preview tiles, as in macOS System Settings >
  Appearance. One of them follows the macOS appearance.
- With nothing saved, the theme is Breeze Dark. Nothing changes for a user
  who does nothing, with two exceptions: G9, and the HTML cards of the last
  point of this list.
- A theme from a file of the user is not in this change.
- **An HTML card follows the theme by default, and a scheme its author
  states wins.** This replaces the issue's line "HTML cards are not themed".
  The user accepts the cost: a page that sets only its text colour, or only
  its background, can become hard to read under the dark theme; and under
  the default theme a card that states nothing changes from a white page to
  a dark one.

Decisions the draft made, which the user accepted at the gate:

- **G1.** The tiles are named and ordered as macOS does: *Auto*, *Light*,
  *Dark*.
- **G2.** The font rows move into a *Fonts* section and take the grouped
  look. Their controls, their order and what they do are not changed.
- **G3.** The Breeze Light values (see *The palettes*). No light Breeze
  terminal palette exists upstream, so some values are a proposal.
- **G4.** In Breeze Light, ANSI 7 (white) and ANSI 15 (bright white) are
  dark greys, so that text a program prints in white can be read.
- **G5.** The scroll thumb has the same colours in the two themes.
- **G6.** A terminal tells a program that asked for it (mode 2031) when the
  theme goes from dark to light or back. The issue asks only for the answer
  to a query.
- **G7.** The Settings window, the menus and the system-drawn controls go
  light with the light theme. (The menus of the menu bar do not: see
  *Changed after the gate*.)
- **G8.** The check that Auto follows a change of the macOS appearance needs
  the Mac's own appearance changed for a few seconds (S57, S58). It is run
  by the user, or by the agent with the user's leave.
- **G9.** A doc page states its `color-scheme`, also under Breeze Dark. So
  a doc card changes for a user who does nothing: the parts of a doc that
  the template does not style (a form control of a doc's raw HTML, for
  example) take the system's dark look. Today they take the light one on
  the dark page.

## Context

Tarmac has one look: Ghostty Breeze on a dark window. It is written into the
code in these places (read at `289d208`):

| What | Where | How it is fixed |
| --- | --- | --- |
| 19 chrome colour tokens and 4 repo colours | `Theme` (`app/Sources/TarmacApp/Theme.swift`) | `static let`, sRGB hex |
| Alpha variants for the minimap and the off-screen hints | `OverlayPalette` | one `static let`, the rest functions over `Theme` |
| The console's error colour | `CardConsoleView.errorColor` (`HTMLCardChrome.swift`) | `static let`, a literal |
| The terminal palette | `TerminalTheme.breeze` (`app/Sources/TarmacTerm/TerminalTheme.swift`) | given to `TerminalView` at `init` only |
| The doc page | six custom properties in `DocTemplate.html` (`--bg1`, `--bg2`, `--term-bg`, `--text`, `--agent`, `--agent-dim`), and one literal, `.doc-prose { color: #ced3d7 }` | static CSS; nothing sets them at run time |
| The HTML card host page | `html, body { background: #2b3036 }` in `Resources/Web/card-host.html` | static CSS |
| The system appearance | `app.appearance = .darkAqua` (`main.swift`) and `window.appearance = .darkAqua` (`AppDelegate.swift`) | set once |

`Theme` colours are used at 99 places in 16 files of `TarmacApp`. About half
are read once, at `init` or in a stored `let`, and written to a layer as a
`CGColor`. A layer colour is a copy: it does not change when the token does.
38 more are read when a state changes (hover, select, bell, prime). Only the
minimap reads its colours each time it draws.

The font change of #204 has the same shape and solved it: `FontSettings`
puts the values in effect in `Theme`, and `broadcastFontsChanged` walks the
view tree, children first. `AppController.fontsChanged` also walks the
boards that are not mounted. A culled card is hidden but still in the tree,
so the walk reaches it. That walk carries no colour today: `ChromeLabel`
keeps the colour it was given at `init`.

The Settings window (`SettingsWindowController`) is one `NSGridView` of
three font rows, with no sections.

`app-prefs.json` (`AppPrefs`) holds `warn_before_quit`, three font families
and two font sizes. `AppPrefs.encode` writes the known keys as a literal, so
a key it does not know is dropped at the next save. `AppPrefsStore` is the
one owner of the file.

`tarmac dev snapshot` is built by `DevSnapshot.build` in `TarmacKit`. Its
top-level keys are pinned by `DevSnapshotTests`. The Rust side prints the
body as it comes, so a new key needs no Rust change.

Facts measured on 2026-10-06 (macOS 26, the dev machine, `289d208`), by a
throwaway test in `TarmacTermTests` and a live `make run` app:

- **libghostty-vt answers colour queries by itself**, from the defaults the
  app sets with `ghostty_terminal_set`. On a live card today: `OSC 10;?`
  gives `rgb:cece/d2d2/d6d6`, `OSC 11;?` gives `rgb:3131/3636/3b3b`,
  `OSC 12;?` gives `rgb:efef/f0f0/f1f1`, `OSC 4;1;?` gives
  `rgb:eded/1515/1515`. After `engine.apply` with other colours, the answers
  are the new colours at once.
- **`CSI ? 996 n` answers `CSI ? 997 ; 1 n` (dark) always.** The callback
  `colorScheme` in `TerminalEffects.swift` is fixed to
  `GHOSTTY_COLOR_SCHEME_DARK` and does not read its `userdata`.
- **Mode 2031 is known to the engine and nothing sends its report.**
  `ghostty_color_scheme_report_encode` (vendored `color_scheme.h`) writes
  `CSI ? 997 ; 1 n` for dark and `CSI ? 997 ; 2 n` for light. No code calls
  it.
- **A colour a program set stays.** After a program sends `OSC 11` or
  `OSC 4`, `engine.apply` changes the default under it, and the program's
  value is still the one in use. `OSC 111` and `OSC 104` go back to the
  current default.
- **A new palette reaches text that is already drawn.** Each of the palette,
  foreground and background options alone makes the next frame read report
  every row dirty. Cells with no colour follow the frame's foreground and
  background. Cells with an ANSI colour (`SGR 31`, `SGR 44`) take the new
  palette entry. Cells with a 256-colour index above 15, or an RGB colour,
  do not change.
- **A `TerminalView` does not read a frame by itself after
  `engine.apply`.** 0.3 s later, with nothing fed, its frame was the old
  one. No public member of `TerminalView` sets a theme: the renderer's
  `theme` (selection colour, cursor fallback) and `readFrame` are private.
- **A web view's `prefers-color-scheme` follows the app's appearance.**
  With both appearance lines changed to `.aqua`, `matchMedia('(prefers-color-scheme: dark)')`
  is `false` in an HTML card's page and in a doc page. A live change of
  `NSApp.appearance`, with no appearance set on the window, reached visible
  HTML and doc cards in about 10 ms with no reload.
- **An HTML card with `:root { color-scheme: light dark }`** and no
  background of its own is painted dark with white text under dark and
  `#ffffff` with black text under light. One with no `color-scheme` is
  white with black text under both. The host's `#fff` frame colour does not
  show through the first kind under dark.
- **A culled doc card** gave the right `matches` when asked, but its
  `change` event came only when a script ran in the page. So a hidden page
  cannot be trusted to restyle itself from a listener.
- **`NSApp.effectiveAppearance` can be observed** with key-value observing
  when `NSApp.appearance` is `nil`: it fired for both changes made from
  code. A change made in System Settings was not measured.

Facts measured the same day for the HTML card's default scheme, on a live
`make run` app with twelve probe pages, under both appearances:

- **The app does not rewrite an author's document.** `CardProtocol.respond`
  answers with `<script>` + `card_shim.js` + `</script>` and then the
  file's bytes, and sets the CSP header. So the shim runs in the page's own
  world, first in the implicit `<head>`, before any byte of the author.
- **A `<meta name="color-scheme" content="light dark">` that the shim adds
  makes a page that states nothing follow the appearance**: `1e1e1e` with
  white text under dark, `ffffff` with black text under light. The dark
  canvas is the system's, not a Breeze value. (The first measurement
  sampled `282828` for it while the computed value was `rgb(30, 30, 30)`;
  this one sampled `1e1e1e`, read in sRGB.)
- **Any `color-scheme` the author declares in CSS beats that meta** with no
  code: on `:root`, on `html`, as `only light`, in the `style` attribute of
  `<html>`, inside `@layer`, and under `:where()`.
- **The author's own meta loses to it,** because the first meta in the tree
  is the one read. It wins when the shim's meta is removed as soon as a
  second one is parsed (a `MutationObserver`, whose callback runs before the
  next paint). Removed only at `DOMContentLoaded`, a page whose body came
  1.5 s after its head was dark for that time and then white.
- **A style rule in place of the meta is too strong.** A `:where(:root)`
  rule beats the author's meta, and an author rule inside `@layer` loses to
  it.
- **To decide after the parse is late.** A page that states nothing was
  white, then dark, on the same slow page.
- **A page opened with a normal file read never painted white under dark**
  (5 of 5 runs of a 60 fps recording). When the response itself was held for
  1.5 s, the card was white for that time: the frame paints white while it
  has no document. A change of the frame's background to `Canvas` did not
  remove the white; hiding the frame until the shim's first message did.
  That it is so at `289d208` too is inferred, not recorded. (Both results
  were wrong for the final build: it showed white in every run with a normal
  read, and hiding the frame did not remove it. See *Changed after the
  gate*.)
- **A live change of the appearance** restyled the pages that follow, with
  no reload, and did not change the pages that state one scheme. The card
  that was culled and then brought back took the change in 0.2 to 0.4 s and
  was right in the first frame after it came back; other culled cards took
  up to 1.4 s.
- **A page that sets only `color: #222`** is `222222` on `1e1e1e` under
  dark. **A page that sets only `background: #fff`** has white text on white
  under dark. These are the accepted cost.
- **Card documents are in quirks mode** at `289d208`, because the shim's
  `<script>` comes before the author's doctype. This change does not alter
  that.

Not measured: the cards of a board that is not mounted, and whether the
host page's `#2b3036` is ever on screen.

No light Breeze terminal palette exists upstream. Konsole ships one
`Breeze.colorscheme`, which is dark. Ghostty's theme set has one `Breeze`,
which is dark. KDE Plasma does ship `BreezeLight.colors`
(`KDE/breeze`, `colors/`), which gives window, view, header and text
colours.

## Motivation

A user who works in a bright room, or whose Mac changes its appearance
through the day, cannot change how Tarmac looks. The Settings window exists
since #204 and already carries a change to every card on every board with no
restart. A theme can use the same path.

## Proposed Solution

### Overview

The Settings window gets a sidebar with two sections, **Fonts** and
**Theme**. The Theme section has one row, *Appearance*, with three preview
tiles: *Auto*, *Light*, *Dark*. A choice applies at once to every terminal
card, the chrome and every doc card on every board, and is saved in
`app-prefs.json`. An HTML card follows it too, unless its author states a
colour scheme.

*Light* is Breeze Light and *Dark* is Breeze Dark. *Auto* is the one of the
two that fits the macOS appearance, and changes when macOS does.

The colour values of both themes are one value in `TarmacKit`. The shell
reads its colours from the palette in effect and takes them again when it
changes, by the walk the font change uses.

### Key Components

- **`ThemeChoice`**, **`ThemeVariant`** (`app/Sources/TarmacKit/ThemeChoice.swift`)
  — what the user chose (`auto`, `light`, `dark`), what is in effect
  (`light`, `dark`), and the pure rule from one to the other.
- **`Palette`** (`app/Sources/TarmacKit/Palette.swift`) — every colour of a
  theme: the chrome tokens, the four repo colours and the terminal colours.
  Two values, Breeze Dark and Breeze Light.
- **`Contrast`** (`app/Sources/TarmacKit/Contrast.swift`) — the WCAG
  contrast ratio of two colours. The tests of the light palette use it.
- **`ThemeCSS`** (`app/Sources/TarmacKit/ThemeCSS.swift`) — the pure rule
  that turns a palette into the doc page's CSS declarations, and puts them
  into a page template.
- **`SettingsPane`** (`app/Sources/TarmacKit/SettingsPane.swift`) — the
  sections of the Settings window, in sidebar order, and their titles.
- **`AppPrefs.Values.theme`** — the saved choice, the key `theme`.
- **`DevSnapshot.theme`** — an additive `theme` object in
  `tarmac dev snapshot`.
- **`TerminalView.theme`** (`app/Sources/TarmacTerm/`) — a settable theme on
  a live terminal; `TerminalTheme.isDark`; the colour-scheme answer and
  report.
- **The shell** (`app/Sources/TarmacApp/`) — `ThemeSettings` (resolves the
  theme in effect, watches the macOS appearance, tells the views), `Theme`
  (reads the palette in effect), `ThemeFollowing` (the walk),
  `SettingsWindowController` (the sidebar, the two sections, the tiles),
  `DocWebView` and `HTMLCardView` (the pages).
- **`card_shim.js`** (`app/Sources/TarmacApp/Resources/Web/`) — gives an
  author's document the default colour scheme.
- **`scripts/qa/settings-window.swift`** — two verbs for the new controls.

### Data Flow

Launch:

1. `AppPrefsStore` loads `AppPrefs.Values`. `ThemeSettings` is built before
   the first view, as `FontSettings` is.
2. `ThemeSettings` sets `NSApp.appearance`: `nil` for *Auto*, `.aqua` for
   *Light*, `.darkAqua` for *Dark*. The main window sets no appearance of
   its own.
3. For *Auto* it reads whether `NSApp.effectiveAppearance` is dark.
   `ThemeChoice.inEffect(systemIsDark:)` gives the variant.
4. `Theme.palette` is `Palette.of(variant)`. Every colour token of `Theme`
   reads it.
5. Each terminal card is made with the terminal colours of the palette.
6. Each doc card loads a page that already holds the palette's CSS
   declarations (`ThemeCSS.page`), so its first paint is in the theme.

A choice in the window:

1. A tile reports its `ThemeChoice`. A choice equal to the saved one does
   nothing.
2. `ThemeSettings` saves it through `AppPrefsStore`, sets
   `NSApp.appearance`, and resolves the variant.
3. If the variant changed, it sets `Theme.variant`, from which
   `Theme.palette` is computed, and calls its `onChange`.
4. `AppController` walks the root view and every board that is not mounted,
   children first, and tells each `ThemeFollowing` view. Each one takes its
   colours again.
   - A terminal card sets `TerminalView.theme`.
   - A doc card hands the page the new declarations
     (`tarmacDoc.theme`), with no reload, and sets its under-page colour.
   - An HTML card sets its own layer and under-page colour, and `--bg1` on
     its host page. The app sends its author's page nothing: a page that
     follows the appearance restyles itself.
5. The selected tile changes.

A change of the macOS appearance while the choice is *Auto*: the observer of
`NSApp.effectiveAppearance` resolves the variant again, and then runs steps
3 and 4 of *A choice in the window*. Nothing is saved. With *Light* or
*Dark* chosen, a change of macOS does nothing.

A card made after a change takes the theme in effect at that moment.

### Interface Contract

**The file.** `app-prefs.json` gains one key.

| Key | Type | Absent means |
| --- | --- | --- |
| `theme` | string: `"auto"`, `"light"` or `"dark"` | `"dark"` |

```swift
public enum ThemeVariant: String, Sendable { case light, dark }

public enum ThemeChoice: String, CaseIterable, Sendable {
    case auto, light, dark                  // the order of the tiles
    public static let standard = ThemeChoice.dark
    public static let prefsKey = "theme"
    public var title: String                // "Auto", "Light", "Dark"
    public func inEffect(systemIsDark: Bool) -> ThemeVariant
}

extension AppPrefs.Values {
    public var theme: ThemeChoice           // default .standard
}
```

- `theme` is a stored member of `Values`, and `Values.init` gains
  `theme: ThemeChoice = .standard` as its last parameter.
- `inEffect`: `light` gives `.light`, `dark` gives `.dark`, `auto` gives
  `.dark` when `systemIsDark` and `.light` when not.
- Decode: `theme` reads as a choice only when it is a JSON string equal to
  one of the three raw values, compared exactly (`"Light"` is not one).
  Anything else, and no key, is `.dark`. It is read on its own: a bad
  `theme` changes no other key, and a bad other key does not change `theme`.
  The rules for a damaged file do not change: the whole file reads as
  `Values()`, so the theme is `.dark`.
- Encode: `,"theme":"<raw value>"` is the last member, after every font
  size, and is written only when the choice is not `.dark`. So the bytes for
  every `Values` that exists today do not change.
- `decode(encode(v)) == v` still holds.
- `AppPrefsStrictnessTests` passes unedited. The cases of `AppPrefsTests`
  that exist pass unedited.

The rule of a proposal for a colour that is drawn as text or as a mark
(`agent`, `amber`, the repo colours, the ANSI colours): keep the hue and the
saturation of the dark value and lower its lightness until it has a contrast
of 4.5 on white. Such a value is changed only when the dark value has less
than 3 on the light background. The proposals for fills, lines and borders
(`bg3`, `primeHeaderBg`, `line`, `lineSoft`, `liftBorder`) and for `muted`
and `prose` are chosen by eye to keep the order of lightness the dark
palette has; the preview at the gate shows them.

Contrast, computed for these values:

- Light, every ANSI colour on `fcfcfc`: the lowest are ANSI 14 (3.20) and
  ANSI 8 (3.39); every other is 4.19 or more.
- Light and dark, `text` and `muted` on `bg0`, `bg1` and `bg2`: 5.07 or
  more.
- Light and dark, `agent`, `amber`, `ok` and `consoleError` on `bg0`, `bg1`
  and `bg2`: 3.21 or more.
- Dark ANSI on `31363b` is not held to a floor: red (2.74), magenta (2.61),
  bright red (2.24) and bright magenta (2.08) are upstream Breeze values and
  are the look today.

**The doc page.**

```swift
public enum ThemeCSS {
    public static let marker = "/*tarmac-theme*/"
    public static let backdropMarker = "/*tarmac-backdrop*/"
    /// The declarations, in the order they are written.
    public static func properties(_ variant: ThemeVariant) -> [(name: String, value: String)]
    /// `template` with `marker` replaced by every declaration, and
    /// `backdropMarker` by the `--bg1` declaration alone.
    public static func page(_ template: String, _ variant: ThemeVariant) -> String
}
```

`properties` gives eight pairs, in this order: `--bg1`, `--bg2`, `--term-bg`,
`--text`, `--prose-text`, `--agent`, `--agent-dim`, `color-scheme`. A colour
is `#rrggbb` in lower case. `--agent-dim` is `rgba(r, g, b, 0.16)` with
decimal channels, as the template has it today. `color-scheme` is `light` or
`dark`. For `.light`:

```
--bg1: #eff0f1; --bg2: #dee0e2; --term-bg: #fcfcfc; --text: #232629;
--prose-text: #31363b; --agent: #12846e; --agent-dim: rgba(18, 132, 110, 0.16);
color-scheme: light;
```

`page` writes each pair as `name: value;` in place of `marker`, and
`--bg1: <value>;` alone in place of `backdropMarker`. A marker is replaced
only when the template holds it exactly once. A template with neither marker
comes back unchanged.

`DocTemplate.html` holds the marker once, inside `:root`, in place of its six
colour properties. `.doc-prose` takes `var(--prose-text)`. The template holds
no other colour literal. `color-scheme` makes the parts the template does not
style (a blockquote, a rule, a table, a form control of a doc's raw HTML)
take the system's light or dark defaults.

A live change calls `tarmacDoc.theme(properties)` in `doc-render.js`, which
sets each pair on the root element. The page is not loaded again and its
scroll position stays. The pairs are passed as arguments, as the fonts are,
never put into the script text.

`card-host.html` gains a `:root` rule that holds `backdropMarker` once. Its
`html, body` backdrop is `var(--bg1)` in place of `#2b3036`. The frame's own
`#fff` stays, and its comment is brought up to date: it is what shows under
a document that states a light scheme. (A document that states only its
text colour has the dark canvas under the dark theme: S66.) The host page
gets no `color-scheme`:
it has none today, and the measurement in Context (an author's page with
`color-scheme: light dark` paints its own dark backdrop over the frame's
`#fff`) was taken under a host page with none. A `color-scheme` on the host
page could change that.

Both pages are loaded through `ThemeCSS.page` with the variant in effect at
that moment: `DocWebView` loads `page(DocTemplate.html, variant)` and
`HTMLCardView` loads `page(card-host.html, variant)`. Loaded raw, a marker
is a CSS comment and `var(--bg1)` has no value. A live change sets `--bg1`
on the host page's root element, with the value passed as an argument, and
does not load the page again.

**The HTML card.** An author's document follows the theme unless it states
a colour scheme of its own.

| The document | Under the dark theme | Under the light theme |
| --- | --- | --- |
| P0: states no scheme and no colour | dark canvas, light text | light canvas, dark text |
| P1: `:root { color-scheme: light dark }` | dark | light |
| P2: `:root { color-scheme: light }` | light | light |
| P3: `html { color-scheme: dark }` | dark | dark |
| P4: `:root { color-scheme: only light }` | light | light |
| P5: `<html style="color-scheme: light">` | light | light |
| P6: `<meta name="color-scheme" content="light">` | light | light |
| P7: `<meta name="color-scheme" content="dark">` | dark | dark |
| P10: `@layer base { :root { color-scheme: light } }` | light | light |
| P11: `:where(html) { color-scheme: dark }` | dark | dark |

- *Dark* is the system's dark canvas with the system's light text
  (measured: `1e1e1e` and `ffffff`). *Light* is `ffffff` and `000000`. They
  are the engine's colours, not values of `Palette`.
- The default is in force before the document's first paint.
- Until its document is shown, an HTML card shows the theme's `bg1` and no
  white: the web view is hidden from the moment it is given a page or a
  document until the host page says the document is on screen. The host
  page says so after the shim's first message, or after the frame's `load`
  event for what is served with no shim, so a card is shown whichever
  comes. One case stays at `bg1`: a request that is never answered. There is
  no timeout.
- A change of the theme reaches a loaded document with no reload. A document
  of P2 to P7, P10 and P11 does not change.
- `prefers-color-scheme` reports the theme in every case.
- The default is one `<meta name="color-scheme" content="light dark">` that
  the shim adds. An author's script can see it, as the first such meta in
  the document.
- The app does not change the author's bytes, the CSP, the frame's sandbox
  or the frame's own `#fff`.
- A meta that an author's script adds after the document is parsed is not a
  statement the default gives way to.

**The snapshot.** `tarmac dev snapshot` gains one top-level key:

```json
"theme": { "choice": "auto", "in_effect": "light" }
```

`theme` is always an object with the two members. `choice` is the choice the
app holds: what `AppPrefs` decoded, or the last tile pressed. So it is
`"dark"` with nothing saved, and with a saved value that is not one of the
three. `in_effect` is the variant whose palette the app holds.

**The terminal.**

```swift
extension TerminalTheme {

    public var isDark: Bool { get }
}

extension TerminalView {
    public var theme: TerminalTheme { get set }
}
```

Setting `theme` on a live view:

- gives the engine the new defaults (`TerminalEngine.apply`), and the
  renderer the new selection colour and cursor colour;
- reads a frame and draws it, with nothing fed: text already on screen is
  in the new colours (see Context for which cells follow). One exception:
  while a program holds its output (mode 2026) the view keeps the frame it
  shows, as today, and the new colours show when the hold ends, 1 s at
  most;
- does not change the grid: `onResize` is not called;
- stays through a later change of `fontFamily`, `fontSize` or the backing
  scale;
- when `isDark` changed and the program has set mode 2031, writes one
  colour-scheme report to the PTY (`CSI ? 997 ; 1 n` dark, `CSI ? 997 ; 2 n`
  light). With the mode not set, or `isDark` the same, it writes nothing.

`CSI ? 996 n` is answered from the view's theme at that moment:
`CSI ? 997 ; 2 n` when it is not dark.

`isDark` compares the WCAG relative luminance of the background and the
foreground.

`TerminalTheme.breeze` stays in `TarmacTerm` as the default of its tests and
of `tarmac-term-demo`. `TarmacApp` does not name it: the app builds a
`TerminalTheme` from `Palette.Terminal`.

## Alternatives Considered

### Dynamic `NSColor`s that follow the appearance

`NSColor(name:dynamicProvider:)` tokens would need no walk where a view
draws with `NSColor`. But most uses are `layer.backgroundColor = x.cgColor`,
and a `CGColor` is resolved once, when it is made. Each of those views would
still need a hook (`viewDidChangeEffectiveAppearance`), and that hook was not
measured for a view of a board that is not mounted. The walk is known to
reach those views.

### Let the pages follow `prefers-color-scheme` alone

The doc template could hold both sets of values under a media query, with no
push. The values would then be written twice, in CSS and in Swift, and the
drawing of a hidden page would depend on WebKit: a culled doc card did not
get its `change` event until a script ran in it. A push is one source of
values and has a moment the app chooses.

### Load the doc page again on a change

Simple, but it loses the scroll position of every doc card and draws each
one again from the markdown.

### A checkbox, a pop-up or a segmented control

The user saw all four as a mock-up and chose the tiles. The pop-up is the
least code. The tiles show the look before the choice.

### The palettes in `TarmacTerm` and `TarmacApp`

Where the colours are today. Then no test can see them: `TarmacApp` has no
tests, and `TarmacTerm` cannot see the chrome. In `TarmacKit` one value
holds a theme, and the terminal body colour is written once.

### A style rule, or a late decision, for the HTML card's default

A `:where(:root) { color-scheme: light dark }` rule put before the author's
bytes is the least code. Measured: it beats an author's meta, and an
author's rule inside `@layer` loses to it. To look at the computed scheme
after the parse and then add a default is exact, but a slow page paints
white first. The meta is the weakest statement CSS has, so every CSS
declaration of the author wins with no code, and only the author's own meta
needs the observer.

### One walk for fonts and colours

`FontFollowing` could become one protocol with one method for both. A view
that keeps a colour and no font would then run font code, and a font change
would repaint colours. Two narrow protocols cost one more walk function.

## Migration & Rollback

### Migration Steps

1. No step for a user. A file with no `theme` key reads as Breeze Dark, and
   is not written until the user changes a preference.
2. The release note says: Settings has a Theme section with Auto, Light and
   Dark; and an HTML card that states no colour scheme now follows the
   theme, so under the default theme its page is dark where it was white.

### Rollback Plan

Revert the change. An older app ignores the `theme` key and drops it when it
next saves the file. No data is lost.

## Security Considerations

The `theme` value is compared with three fixed strings and is never put into
CSS, a script or a path. The CSS values come from `Palette` only, and reach
the page as arguments of `callAsyncJavaScript`, not as script text. The CSP
of the doc page and of the HTML card host does not change. An HTML card's
author can already read `prefers-color-scheme`; it now reports the user's
theme, which is one bit. The shim adds one `meta` element to the author's
document and no value of the user's: the element is the same for every card
and every theme.

## Acceptance Scenarios

Each scenario is marked **[auto]** (a test in the named suite, or a
command) or **[QA]** (run against a live `make run` app, and recorded in
`qa/theme-qa.md` with the observed values). A QA scenario that names a
colour is checked by a pixel of a `screencapture -l <window id>` capture of
the dev app's window, addressed by pid.

The rules for a sampled colour:

- The capture is read in sRGB, because the tokens are sRGB. The record names
  the display's colour profile.
- The tolerance is measured, not assumed, and on a tree this change did not
  touch: the app built from `289d208` is captured, the five fills of S26 are
  sampled (their values are in `Theme.swift` and `DocTemplate.html`
  there), and the record gives the largest difference in a channel. The
  tolerance is that difference plus 1. A sampled value agrees with a named
  one when each channel is within the tolerance. Two tokens whose values
  are no more than twice the tolerance apart in every channel cannot be
  told apart by value (in the light palette `primeHeaderBg` and `bg3` are 3
  apart; in the dark one `lineSoft` and `bg3` are 1 apart): where a scenario
  must tell such a pair apart, it compares them as *lighter* and *darker*
  in one capture, and the record says so.
- A part that is a window of its own (the Settings window, an open menu, an
  open pop-up) is captured by its own window id, or by a region capture.
- A fill is sampled at a point with no text and no shadow on it.
- A card is sampled while it is not dimmed. A terminal card that is not
  prime is dimmed while its board has a prime card (`CardDim`), and the
  prime card's header has `primeHeaderBg`. So the header value `bg2` is
  sampled on the header of a doc card.
- For a fill drawn with alpha, the record gives the blend it computes beside
  the sampled value, and the two agree.
- *Lighter* and *darker* compare the WCAG relative luminance of two sampled
  values.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

Implement however you work best. Only the result is checked. The
repository's own rules still bind (`docs/coding-style.md`): red first and
observed red; the smallest correct diff; no line-noise comments; do not run
`cargo fmt`; verify with `make`, not the editor.

Points that are easy to get wrong here:

- **A layer colour is a copy.** `layer.backgroundColor = Theme.x.cgColor`
  at `init` stays the old colour for ever. Each such view must take its
  colours again in the walk. The list in *The shell* was read at `289d208`:
  run `grep -rn 'Theme\.' app/Sources/TarmacApp` again and account for every
  hit.
- **A colour read on a change of state** (hover, select, bell, prime, lift,
  exit, connection) is right only after that state next changes. The walk
  must apply the current state's colours again. S46 is the check.
- **`ChromeLabel` keeps its colour from `init`,** and `fontsChanged` sets
  only the font. The status bar, the toasts and the hint pills all use it.
- **`CardConsoleView` colours its text when it is shown.** After a change
  the text already there has the old colours.
- **`OffscreenHints` reuses a pill** while its content is equal. A colour
  change does not change the content: use `forget()`, as the font change
  does.
- **`static let` colours** freeze at first use. S59's second command finds
  them.
- **The palette is set before the first view,** as the fonts are. The order
  in `AppDelegate.applicationDidFinishLaunching` is load-bearing.
- **`TerminalView` does not read a frame after `engine.apply`.** The setter
  must read one and draw. Do not add a second `FrameReader`: with two
  readers, a forced full read gave old palette cells.
- **`rebuildFonts` makes a new renderer** from `renderer.theme`. The theme
  set later must be the one it carries (S25).
- **The 996 callback gets `userdata`** and ignores it today. It must read
  the live theme of its own terminal, not a global.
- **The 2031 report goes out only when `isDark` changed and the mode is
  set.** Read the mode from the engine; do not track the escape sequence by
  hand.
- **Do not let a hidden page restyle itself.** Push the declarations. A
  culled doc card did not get its media-query event until a script ran.
- **A doc page made under the light theme must not paint dark first.** The
  page is loaded from `ThemeCSS.page`, and `DocWebView.page` and
  `HTMLCardView.page` are each a `static let` today: neither can stay one
  string for both themes. A page loaded raw passes S17 and draws with no
  `--bg1`. Set the web view's
  `underPageBackgroundColor` again on a change too, on both kinds of card.
- **Whether the host page's backdrop is ever painted was not measured.** It
  takes `backdropMarker` at load and `--bg1` on a change either way. Look
  for it (a card being resized, a page still loading) and give its colour in
  the QA record if it can be seen.
- **The host page must not get a `color-scheme`.** It takes
  `backdropMarker`, which gives `--bg1` alone. Every row of the HTML card
  table was measured under a host page with none. S62 is the check that this
  still holds.
- **The default scheme is a meta, removed when the author's meta is
  parsed.** That is the one mechanism that passed every row (see Context).
  The shim makes the meta as its first act, appends it to `document.head`,
  and watches `document.documentElement` for another
  `meta[name="color-scheme" i]` (the name in any letter case) until
  `DOMContentLoaded`. A style rule fails
  P6 and P10. A meta that is never removed fails P6. Removal at
  `DOMContentLoaded`, or a decision after the parse, shows the wrong scheme
  first on a slow page.
- **The shim must never throw.** Every path in it is defensive today; the
  new lines are too.
- **`CardShimTests` runs the shipped shim in JavaScriptCore**, in a
  stand-in window whose `document` has no `head`, no `createElement` and no
  `MutationObserver`. So new shim code that is wrapped in `try` throws into
  its own `catch` there and all 56 tests stay green with nothing tested.
  S67 to S69 need the stand-in to grow those three; S70 keeps the old one.
  What the engine then does with the meta is S62 to S66: JavaScriptCore has
  no CSS.
- **`document.head` exists when the shim runs.** The shim's `<script>` is
  the first bytes of the document, and the parser makes `<html>` and
  `<head>` for it. The author's doctype comes later and is ignored, which
  is why the document is in quirks mode.
- **Do not put the document in standards mode here.** It is in quirks mode
  today because the shim's script comes first. Changing that changes the
  layout of every card.
- **A frame read after `feed` is not immediate, and a draw reads no
  frame.** `viewportCells()` (the suite's `read()`) is what reads it. S21
  and S44 read and draw once before the change, and do not read again after
  it: a `read()` after the change would hide a setter that reads no frame.
- **`NSApp.appearance` must be `nil` for Auto,** or
  `NSApp.effectiveAppearance` reports the forced value and not the Mac's.
  Read the Mac's value after setting `nil`.
- **The main window must not pin an appearance.** With `.darkAqua` left on
  the window, the web views stay dark.
- **Auto on a Mac in Light changes the variant, and Auto to Light on that
  Mac does not.** `onChange` is for a change of the variant; the file is
  written for a change of the choice (S48).
- **The font QA script reads the window by the order of its controls.**
  Moving the rows into a pane must keep `rows`, `pick`, `size` and `step`
  working (S51).
- **The tiles must be real controls** the Accessibility API can press, with
  a title. A drawn view with a click handler cannot be driven, and then
  every live scenario needs a person.
- **`DevSnapshotTests` pins the top-level keys and the compact bytes.**
  Both tests change.
- **Never launch `dist/Tarmac.app`** and never kill a daemon by name. All
  live QA is against `make run`; stop its daemon with `make kill-daemon`.
- **Do not change the Mac's appearance** without the user's leave (S57,
  S58). S38, S39 and S48 are written to run on a light Mac and on a dark
  one with no change of it.

Test principles, the ones `/verify` scores against:

- **Behavioral over structural** — assert observable output, not internals.
- **Every test can fail** — S9 and S10 compare with the tables of this
  spec, which is the contract for the values; S12 to S14 are the tests that
  fail when a light value is a dark one.
- **Deterministic, isolated, readable** — temp directories per test, no
  shared state, no dependence on the Mac's appearance: `systemIsDark` is an
  argument.

## Trade-offs and Limitations

- **Two themes, both built in.** A theme from a file, and more themes, are
  later work. `Palette` is one value for a theme, so a third is one more
  value and one more tile.
- **Breeze Light is partly Tarmac's own.** No light Breeze terminal palette
  exists upstream.
- **ANSI white is dark in the light theme.** A program that draws white on
  a coloured background gets dark on that background.
- **The 256-colour cube and the grey ramp do not change.** Indices 16 to
  255 keep libghostty-vt's defaults in both themes. The vendored header has
  `ghostty_color_palette_generate` for a later change.
- **A colour a program set stays** until the program resets it (S50). Text
  drawn with an RGB colour or an index above 15 keeps that colour.
- **The dark palette is not held to the ANSI contrast floor.** It is the
  look today.
- **Shadows and the switcher's veil are black in both themes,** and the
  quit notice is a dark slab in both.
- **The scroll thumb is the same in both themes** (G5).
- **An HTML card that sets half of its colours can become hard to read.**
  A page with only a text colour keeps it on the dark canvas, and a page
  with only a white background gets white text under the dark theme (S66).
  The user accepts this. The skill's text tells an author to set both or
  neither, or to state `color-scheme: light`.
- **Under the default theme, an HTML card that states nothing changes** from
  a white page to a dark one.
- **A following HTML card has the system's canvas, not a Breeze colour:**
  `1e1e1e` under dark, beside a doc page of `2b3036`.
- **An HTML card shows `bg1` for a few frames when it opens and when its
  file changes,** in place of the white it showed for 1 or 2 frames. Under
  the dark theme a page that states a light scheme goes from `bg1` to white.
- **The menus of the menu bar follow the Mac's appearance,** not the theme.
- **`TarmacTerm` cannot see `TarmacKit`, and three things follow.** The
  dark terminal colours are written twice: in `Palette` for the app, and in
  `TerminalTheme.breeze` for `TarmacTerm`'s own tests and demo. The WCAG
  luminance is written twice: in `Contrast` and for `isDark`. And the step
  from `Palette.Terminal` to a `TerminalTheme` is in `TarmacApp`, with no
  unit test: S31 is its check, because it reads the foreground, the
  background and one ANSI colour back from a live terminal.
- **The host page's backdrop after a live change has no check** unless it
  can be seen (see *For the Implementing Agent*).
- **`theme` in the snapshot reports what the app resolved**, not what each
  view drew. A view that missed the change is found only by the captures of
  S29, S45, S46 and S47.
- **A program that holds its output (mode 2026) holds the new colours
  too.** `TerminalView` keeps the frame on screen while output is held, for
  1 s at most. A theme change in that time shows when the hold ends.
- **An older app drops the `theme` key** when it next saves the file.
- **Auto reads the appearance of the app, not of each display or window.**
