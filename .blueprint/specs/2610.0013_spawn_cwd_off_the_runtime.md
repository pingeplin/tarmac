# 2610.0013 Check a new terminal's cwd off the runtime, with a time limit

**Date:** 2026-10-30
**Status:** accepted
**Author:** EP Lin
**Issue:** [#279](https://github.com/pingeplin/tarmac/issues/279) `fix(terminal): a terminal whose cwd is on a hung volume freezes the daemon at spawn`
**Builds on:** [2610.0012](2610.0012_doc_path_reads_off_the_runtime.md) (`reader::PathGate`, #274–#277)

## Context

`SpawnTerm` (`conn.rs:239`) runs two blocking calls on a tokio worker:

- `spawn_cwd` (`conn.rs:358`): for `inherit_cwd_from`, it calls `TermHandle::live_cwd` → `proc::pid_cwd` → `proc_pidinfo(PROC_PIDVNODEPATHINFO)`.
- `term::spawn` (`term.rs:130`): it calls portable-pty 0.9.0 `spawn_command`. That calls `Path::is_dir` on the cwd (`cmdbuilder.rs:506`), and falls back to `$HOME` when the answer is false.

Measured on the #267 WebDAV mount with requests held (`scratchpad/hang267/q279/`):

- A `SpawnTerm` whose cwd is on the mount froze the whole daemon. Six hellos over 12 s got no answer. The blocked stack was `spawn_command → … → Path::is_dir → stat`. No child had been forked yet.
- A `SpawnTerm` with `inherit_cwd_from` a terminal whose cwd is on the mount froze it too. The blocked stack was `spawn_cwd → live_cwd → pid_cwd → proc_pidinfo`, and `proc_pidinfo` did not return within 5 s in 3 of 3 runs.
- With `is_dir` bounded at 1 s and falling back to `$HOME`, the shell started in `$HOME` about 1.02 s after the send, and every hello answered in under 1.3 ms. portable-pty never ran `chdir` into the dead dir.

## Decision

Both calls go through the daemon's `PathGate`, with `READ_LIMIT` (1 s). An `Out` is treated as "no usable cwd", and the terminal starts in `$HOME`. That is what portable-pty already does for a cwd that is not a directory. The spawn does not fail.

- `pid_cwd(pid)`: `Out` means no cwd to inherit. The spawn then uses `$HOME`, as it does today when `live_cwd` gives `None`.
- `is_dir(cwd)`: this check runs on the gate before `spawn_command`. `Out` or `false` gives `$HOME`. `true` passes the cwd to portable-pty, whose own `is_dir` then runs on a path that just answered.

## Interface

- `PathFs` gets `is_dir(&Path) -> bool` and `pid_cwd(pid) -> Option<String>`. `RealFs` implements them with `Path::is_dir` and `proc::pid_cwd`. The test double can hold them, as it holds the other calls.
- The key of `pid_cwd` must give one call per pid at a time. The implementer picks a key that cannot collide with a real path. Document it in the `PathGate` doc comment.
- No protocol change. No new error text.

## Trade-offs

- A cwd on a slow but live volume (more than 1 s) starts in `$HOME`. The user sees the shell in their home dir, with no error. The same trade-off as #267 (Decision 1).
- **Accepted race:** `is_dir` answers `true`, and then the volume dies before the child's `chdir`. `Command::spawn` then blocks a worker until the volume answers. The window is the time between two syscalls, and the harness could not produce it. Closing it would need `spawn_command` on a blocking thread with a limit, plus cleanup of a late child. That is not done here.

## Acceptance Scenarios

Unit tests go in `state.rs` / `conn.rs` / `term.rs` tests as fits. They use the `PathFs` double (hold by method and path or pid). `LIMIT = 200 ms`. "At once" means `< LIMIT`, and "waits the limit" means `< 3 × LIMIT`, as in 2610.0012. A spawned terminal's cwd is read from its output (for example, `pwd` as the command) or from `pid_cwd` of its pid once it runs.

- **S1:** A `SpawnTerm` with an explicit `cwd` whose `is_dir` is held answers within `< 3 × LIMIT`, and the shell runs in `$HOME`. During that wait, a request on another connection or task is answered at once.
- **S2:** The same as S1, but `is_dir` answers `false` at once (a missing dir). The shell runs in `$HOME` at once, as today.
- **S3:** A `SpawnTerm` with a live, reachable `cwd` runs in that cwd. This is the regression guard.
- **S4:** A `SpawnTerm` with `inherit_cwd_from` a terminal whose `pid_cwd` is held answers within `< 3 × LIMIT`, in `$HOME`, and another request is answered at once.
- **S5:** A second `SpawnTerm` with the same held `pid_cwd` (or the same held `is_dir` path) makes no second call (the double's count stays 1), and answers at once in `$HOME`.
- **S6:** When the held call returns, the next spawn with that cwd uses it (the key is cleared).
- **Q1 (hand QA, WebDAV harness):** With the mount held, run a `SpawnTerm` with `cwd` on the mount, and one with `inherit_cwd_from` a terminal in the mount. The second connection's hello must be answered in under 100 ms during each. Each shell starts in `$HOME` within 1.1 s. Run the same on `main` as the baseline.
