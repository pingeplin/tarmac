# 2611.0024 Markdown card: the tile keeps the sidebar's width and open state

**Date:** 2026-11-21
**Status:** accepted (2026-11-21) by the spec-evaluator, an independent verifier (two rounds, clean) and the advisor, under the owner's rule. Only two paths make a doc card (`build` seeded, `handleDocOpened` fresh; checked).
**Author:** EP Lin
**Issue:** [#445](https://github.com/pingeplin/tarmac/issues/445) `feat(protocol): a doc tile keeps its sidebar width and open state`
**Branch:** `feat/445-doc-sidebar-state`, from `main` at `88625eb` (slices 1 and 2 merged).
**Design:** [2611.0020](../../docs/designs/2611.0020_markdown_card_reading_layout.md), slice 3 (O5 "each card keeps its own width and open state"; design D15, D16; review decision A3). Decision ids below are this spec's own. Builds on spec [2611.0022](2611.0022_doc_sidebar.md) D7 and D21.

## Gate

The owner's decision O5 and the design's D15, D16 and A3 bind this spec:

- Each markdown card keeps its own sidebar width and open state. They survive an app restart and a daemon restart.
- They are two OPTIONAL keys on the layout `Tile`: `sidebar_w` (float | nil) and `sidebar_open` (bool | nil). Additive: both codecs in the same change, conformance vectors on both sides, `docs/protocol.md` and `docs/architecture.md`.
- What is stored: the width after a drag or a reset; a collapse keeps the width from before the drag and stores open = false (A3). The open state only after the user opened or closed the docked sidebar. An overlay never writes the open state.
- An older frame without the keys decodes as before.

## Decisions

### Wire

- **D1. Rust keys.** `Tile` gets two fields after `term_id`, in this order, each `#[serde(default, skip_serializing_if = "Option::is_none")]`: `sidebar_w: Option<f64>` (the docked or overlay sidebar width, world px) and `sidebar_open: Option<bool>` (the docked sidebar's open state). Field order is wire order: `rmp_serde::to_vec_named` writes them after `term_id`. The vector 8 `Tile` literal (`tests.rs:191-202`) gains `sidebar_w: None, sidebar_open: None`; this is the one edit to an existing test. Its hex and its message stay the same, so vector 8 itself is not edited (`docs/coding-style.md` §1.1, *The wire contract*): Rust only needs every field named in a full literal. It is the only full `Tile` literal in `core/`; every other one ends in `..Default::default()`, `..doc_tile(…)` or `..term_tile()`. No dependency changes: the pinned serde stack stays as it is.
- **D2. Swift keys.** `LayoutTile` gets `sidebarW: Double?` and `sidebarOpen: Bool?`, last in the initializer, both `= nil`, so no existing call site or assertion changes. `layoutTile(from:)` reads `sidebar_w` with `\.doubleValue` and `sidebar_open` with `\.boolValue` through `MapReader.opt`. `layoutTileValue` writes them after `term_id`, `unlessNil`.
- **D3. Strict types.** A key of the wrong type fails the frame, in both codecs, as `x` does today. The codecs check no range: the range is `DocSidebar`'s (D6).
- **D4. Older versions.** An older daemon or app decodes a tile with the keys and drops them (no `deny_unknown_fields`; `MapReader` reads only the keys it knows). A downgrade loses the stored choices, with no error. The app and its daemon run the same version (`AppVersion`), so this happens only on a downgrade.

### Daemon

- **D5. No logic change.** `set_tiles` keeps the tile whole and `persist.rs` writes it with serde (Context). The daemon's tests only prove that the keys reach `state.json` and come back in `restore`.

### App: what is stored, and its check (`TarmacKit`)

- **D6. Read check.** `DocSidebar.restored(width: Double?, open: Bool?) -> Stored`: `width` is kept only when `minimum...maximum` (160...420) contains it, else nil (this drops NaN and ±infinity too); `open` is kept as it is. The two are judged apart: a bad width does not drop `open`. A width outside the range never comes from this app (Context, `apply`), so a value outside it is a hand edit or a corrupt file, and the card then uses the standard 240.
- **D7. What is stored is `Stored`, as `apply` gives it.** No change to `apply` (D12 adds one separate rule beside it): design D16 holds as built (Context). `sidebar_w` is `Stored.width` and `sidebar_open` is `Stored.open`; nil writes no key. A narrow card's open overlay (`overlayOpen`) is never on the wire, so a narrow card comes back with the strip (design D12).

### App: build and parse (`TarmacKit`)

- **D8. Build.** `LayoutTiles.DocInput` gets `sidebar: DocSidebar.Stored`, last in its initializer, `= DocSidebar.Stored()`. `build` writes `sidebarW: doc.sidebar.width, sidebarOpen: doc.sidebar.open` on the doc tile. A term tile never has the keys.
- **D9. Parse.** `LayoutTiles.ParsedDoc` gets `sidebar: DocSidebar.Stored` (initializer default `Stored()`). `parse` sets it to `DocSidebar.restored(width: tile.sidebarW, open: tile.sidebarOpen)`. The keys on a term tile are ignored.
- **D10. Plan.** `BoardRestore.Doc` gets `sidebar: DocSidebar.Stored` (initializer default `Stored()`). `plan` copies it from the `ParsedDoc`. A doc tile that `plan` drops (path not in the registry) takes its choice with it.

### App: wiring (`TarmacApp`, exception: thin wiring, discharged by QA) D12's `storesChange` is a kit rule with its own test ("Action that changes nothing stores nothing"); the rest is wiring.

- **D11. Seed.** `landDocCard` gets `sidebar: DocSidebar.Stored = DocSidebar.Stored()`, before `on board:`. Right after `addCard` it sets `card.docSidebar = sidebar` on every card (no predicate in the shell). `build` passes `doc.sidebar`; `handleDocOpened` passes nothing, so a doc opened anew (also one closed and opened again) starts with no choice. This is in time: the body is made in `addCard`, but `DocWebView` reads `stored()` only once its page has loaded (Context), never in this main-thread turn. An HTML card's `docSidebar` is read only by `sendLayout`: it stays what its tile gave (empty for any tile the app wrote, since only a markdown card's page reports actions), and `LayoutTiles.build` writes no key for nil values. A hand-edited HTML tile with the keys keeps them; that is harmless and accepted.
- **D12. Persist trigger.** `CardView` gets `onSidebarChanged: ((CardView) -> Void)?`. A new kit rule `DocSidebar.storesChange(_ action:, stored:, overlayOpen:, cardWidth:) -> Bool` is `apply(...).stored != stored` ("Action that changes nothing stores nothing"); `apply` and its 2-tuple stay as they are (2611.0022 D7 is unchanged, and no existing test or helper changes). `DocWebView.sidebarReported` calls `onStoredChanged` only when `storesChange` is true; in `wireMarkdownBody`, `onStoredChanged` sets `docSidebar` and calls `onSidebarChanged`. No predicate stays in the shell. `BoardView.wire` sets it to call `onLayoutChanged?(viewport)`, as `endGesture` does, so the board's layout goes out after the 200 ms debounce. A narrow card's overlay open or close changes no `Stored` and sends no layout. "Action that changes nothing stores nothing" checks the rule.
- **D13. Send.** `sendLayout` passes `sidebar: card.docSidebar` in each `DocInput`.
- **D14. A board already built.** A later restore does not seed (Context): cards keep the choice they hold, and the next layout writes it. After a daemon restart with the app still up, the new daemon has the last layout the old one wrote.

## Out of scope

- The sidebar side and the Documents pane (slice 4, #446).
- Keeping a narrow card's open overlay. Keeping a choice for a doc after its card closes (the tile has the card's lifecycle; design *Alternatives*).
- HTML cards. A migration of old state files (they have no keys: no choice).

## Acceptance scenarios

Unless a scenario says otherwise, "the D1 tile" is `{kind:"doc", path:"/a.md", sidebar_w:300.5, sidebar_open:false}`. 300.5 catches a width kept as an integer; `false` catches a `false` that is skipped like a nil.

The hex below was computed by hand from the msgpack rules. The spec evaluator decoded "Rust frame with both sidebar keys matches vector" and "Rust frame with one sidebar key matches" again by those rules and `Tile`'s field order and found no byte error ("Rust frame with both sidebar keys matches vector": tile map `84`, `a9`/`ac` key lengths, 300.5 = `cb 40 72 c8 00 00 00 00 00`; "Rust frame with one sidebar key matches": tile map `89`, 10/20/1280/600 = `40 24…`/`40 34…`/`40 94…`/`40 82 c0…`). ### Live (QA, `make run`)

Setup. From the worktree root, use a QA channel of its own: `QA="$PWD/.dev/qa-sidebar"`, and give `DEV_DIR="$QA"` to every `make run` and `make kill-daemon` (`.claude/skills/dev-channel/SKILL.md`, *A second channel*). A kill ends every terminal of the channel, so it must not be the developer's `.dev`. Start with `make kill-daemon DEV_DIR="$QA"`, so `make run DEV_DIR="$QA"` starts a daemon of this build: an older dev daemon drops the keys (D4) and gives a false fail. Run `tarmac open` and `tarmac dev …` only in one of these two ways: in a terminal of the QA app (its `PATH` and `TARMAC_*` point at this channel), or as `TARMAC_SOCKET="$QA/tarmacd.sock" TARMAC_DEV_SOCKET="$QA/tarmac-dev.sock" core/target/debug/tarmac …`. Never use a bare `tarmac` from another shell: it reaches the installed Tarmac. Docs A, B and C are three different files with YAML front matter and headings (copies of the slice-2 QA doc fit); doc H is an HTML file. `tarmac dev resize <path> <w>x<h>` sets a card's size. A drag or a click on the sidebar is a HID event from `scripts/qa/wheel-gesture.swift`, as in 2611.0022 "Drag on an unselected card resizes the sidebar". Before each one, run `tarmac dev focus board` and check that the window under the point belongs to the QA app's pid. The sidebar's mode and width come from window captures (of the QA app's window, by pid), in world px, ±2. The keys come from reading `$QA/state.json` (read it; never edit it). A HID drag does not end on an exact width, so a width in `state.json` passes at ±2 of the number a scenario names, and a width after a restart passes at ±2 of the one `state.json` holds. To read a change in `state.json` (before a `kill -9`, or after a quit), poll it every 100 ms for up to 5 s, else fail: the app sends a layout 200 ms after the change (at once at quit) and the daemon writes 150 ms after that. In the scenarios, `make run` and `make kill-daemon` mean those commands with `DEV_DIR="$QA"`, and `state.json` means `$QA/state.json`. The dev daemon is detached and outlives a quit of the app, and an app that is up reconnects to a new daemon after a kill (`.claude/skills/dev-channel/SKILL.md`, *There is no hot reload*; `scripts/qa/resume.mjs` `CASE=reopen`). A kill ends every dev terminal: their cards come back dead, which these scenarios do not judge. Teardown: quit the QA app, then `make kill-daemon DEV_DIR="$QA"` (the daemon outlives the app).

## Risks

- **A hand-made hex that is wrong.** "Rust frame with both sidebar keys matches vector" and "Rust frame with one sidebar key matches" run `assert_frame` first; Rust's bytes are the truth (see *Acceptance scenarios*).
- **`kill -9` before a write.** `make kill-daemon` loses a layout the daemon has not written. QA waits for `state.json`. Real users lose at most a change of the last 350 ms (the app's 200 ms debounce plus the daemon's 150 ms) and the write itself, as for a card move today.
