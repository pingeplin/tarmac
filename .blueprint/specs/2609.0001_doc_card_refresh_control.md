# 2609.0001 Doc card refresh control

**Date:** 2026-09-04
**Status:** accepted
**Author:** EP Lin
**Issue:** [#89](https://github.com/pingeplin/tarmac/issues/89) `feat(board): add refresh button to doc card`
**Related:** [#99](https://github.com/pingeplin/tarmac/issues/99) (magnify card renders at 1/K after a self-reload)

## Context

A doc card refreshes only when the daemon pushes `file_event`. That message comes
from exactly one place — `watch_loop` in `core/crates/tarmacd/src/docs.rs`, driven by
a `notify` watch on the doc's **parent directory**, debounced to one event per 100 ms
per path. The app's `file_event` arm (`desktop/src/App.tsx`) then does two things:

```
case "file_event":
  stampDocChange(msg.path, msg.mtime_ms);   // real mtime → docMeta.lastChangedMs → "✎ Ns"
  refreshDoc(msg.path);                     // → fetchDoc → read_doc (markdown only)
```

and, because `HtmlCard`'s iframe `src` is `cardSrcUrl(path, lastChangedMs)`, a changed
`lastChangedMs` also bumps `?v=`, which reloads the HTML document and — via the
`useEffect([props.lastChangedMs])` that resets `readyHandledRef` — re-posts its zoom.

That single path covers ordinary editor/agent writes. It has no fallback: when the
watch misses a change (network or slow filesystem, an event the debouncer swallowed,
a watch that never established), the card silently shows stale content and there is
nothing the user can do about it. There is also no way to ask for certainty.

One miss is not exotic but structural: `watch_loop` matches hits against
`active_registry()` — evaluated when the debounced batch is *processed* — so **an edit
made while the doc's board is in the background is dropped**, and switching back does
not heal it. Under the P5 warm-board
model App keeps every board mounted (`display: none` for the inactive ones), and
`applyRestore` latches on `didRestore`: a restore for an already-visited board takes
the reconnect-revive branch and **returns before the card rebuild**, so no `docMeta` is
re-read and no `fetchDoc` runs. The card keeps its old markdown, its old recency label,
and its old `?v=` for as long as the app is up. That is the reproducible stale card the
QA scenarios below use, and the plainest case of the bug #89 reports.

`doc_open` is not that fallback. `handle_open` stats the file only for its `is_file`
check; its existing-doc branch leaves `last_changed_ms` untouched and `doc_opened`
carries no content. A re-open does reach `landDoc` → `fetchDoc`, so markdown content
would refresh — but the recency label stays stale and `fetchDoc` is a no-op for HTML
docs, so `?v=` never moves.

## Motivation

Tarmac's core promise is that **every on-screen mark is backed by an observable OS
fact**. A doc card that may be stale, with no user-reachable way to re-establish the
fact, breaks that promise quietly — the worst way. A refresh control restores it: one
click, one real `stat`, and the card's content and recency label are known-current.

Without it the only recovery is closing and re-opening the card, which loses card
placement intent and (for HTML cards) all document JS state anyway.

## Proposed Solution

### Overview

Add a refresh control to the shared `CardHeader`. **`CardHeader` renders the control
itself**, at the recency/✕ seam — immediately before the `children` slot that
`HtmlCard`'s console badge occupies — driven by a new optional `onRefresh?: () => void`
prop. So `DocCard` and `HtmlCard` both get it from one place. Clicking it sends a new
additive app→daemon message, `{t:"doc_refresh", path}`. The daemon stats the file,
records the real mtime in the active board's registry, and pushes the ordinary
`file_event`.

> **Deliberate divergence from #89's wording.** The issue asks for the control "in the
> `children` slot region … so `DocCard` and `HtmlCard` both get it". Rendering it
> literally *through* the `children` slot would defeat that goal: `children` is passed
> **by each card**, so both `DocCard` and `HtmlCard` would have to construct and pass
> their own control, duplicating it — and `DocCard` passes no `children` today. An
> `onRefresh` prop puts the markup in `CardHeader` alone, which is what the issue
> actually wants. The *position* on screen is exactly as the issue describes.

Nothing new happens on the app's **receive** path. The refresh **ends in the existing
`file_event` arm**, so recency, the markdown re-read, and the HTML `?v=` bump all keep
coming from one code path. The correct per-kind behavior then falls out of the existing
data flow rather than from a new branch:

- **Markdown** — `refreshDoc` → `fetchDoc` → `read_doc` re-reads from disk every
  time. Identical bytes produce an identical `markdown` prop, so `DocCard`'s
  `useLayoutEffect([markdown])` does not re-run: the prose DOM is not rebuilt and the
  scroll position is untouched (the component itself still re-renders — `fetchDoc`
  always sets a new `docContents` Map — but nothing observable changes). Changed bytes
  re-render with scroll position preserved, exactly as a watcher-driven change does.
- **HTML** — the iframe `src` is `cardSrcUrl(path, lastChangedMs)`. An unchanged mtime
  yields a byte-identical `src` string, so React does not touch the `<iframe>` and the
  document is **not** reloaded. The iframe reloads if and only if `lastChangedMs`
  actually changed — which is also the only thing that resets `readyHandledRef`, so
  every reload gets its zoom. That is precisely the #99-safe rule, enforced by data
  flow rather than by a guard someone can forget.

### Key Components

- **`Msg::DocRefresh { path }`** (`core/crates/tarmac-protocol/src/lib.rs`) — new
  additive app→daemon variant, wire tag `doc_refresh`. Modeled on `Msg::DocClose`
  (issue #34).
- **A shared stat-and-push helper** (`core/crates/tarmacd/src/docs.rs`) — **extract**,
  do not duplicate. `watch_loop`'s per-hit body (`docs.rs`, the `for path in hits` loop:
  `metadata` → `modified` → `mtime_ms` → `active_registry_mut()` write → `mark_dirty` →
  `push(FileEvent)`) is ~10 lines and is exactly what `DocRefresh` needs. Lift it into
  one `pub async fn` in `docs.rs` — the module that owns doc facts — and call it from
  both `watch_loop` and the new arm. That keeps the always-push rule, the registry-
  before-push ordering and the active-board scoping defined once (CLAUDE.md: SOLID,
  smallest correct diff). The helper owns the whole decision — **including the
  active-registry membership check** — and returns whether it pushed.
- **Daemon `DocRefresh` arm** (`core/crates/tarmacd/src/conn.rs`) — thin to the point of
  triviality: call the helper, and `debug!` when it returns `false`. **No lookup of its
  own.** An arm-side "is this path in the active registry?" check before the call would
  take a second `boards.lock().await` for a question the helper must ask anyway, and open
  a TOCTOU seam between the two locks (a board switch or `DocClose` landing in between).
  One lock, one decision, in the module that owns doc facts.
- **`doc_refresh` Tauri command** (`desktop/src-tauri/src/commands.rs`,
  registered in `desktop/src-tauri/src/lib.rs`) — one-liner forwarding
  `Msg::DocRefresh { path }`, alongside `doc_close`.
- **`docRefresh(path)` sender** (`desktop/src/ipc/daemon.ts`) — `invoke("doc_refresh", { path })`.
- **`CardHeader` refresh control** (`desktop/src/cards/CardHeader.tsx`) — markup owned
  by `CardHeader`, emitted before `props.children` so a card's own chrome (the console
  badge) keeps its place next to the close button. Driven by the new optional
  `onRefresh?: () => void` prop; rendered only when that prop is present.
- **Prop threading** — `desktop/src/board/Board.tsx`'s `shared` doc-card prop object gains
  `onRefresh: () => props.onDocRefresh(c.path)`; `App.tsx` passes a handler that calls
  the IPC sender. `DocCard` and `HtmlCard` forward it to `CardHeader`.

### Data Flow

1. User clicks the refresh control on a doc card (either kind).
2. `pointerdown` is stopped (`e.stopPropagation()` + `e.preventDefault()`) so
   `CardShell`'s drag never starts; the `click` then fires the handler.
3. App sends `doc_refresh(path)` over Tauri IPC → bridge → `Msg::DocRefresh { path }`.
4. Daemon looks the path up in the **active board's** registry. Unknown ⇒ silent no-op.
5. Daemon `stat`s the file. Unstat-able (deleted, permissions) ⇒ silent no-op — the
   same rule `watch_loop` already applies to deleted files.
6. Daemon writes the real `mtime_ms` into the registry entry's `last_changed_ms`,
   marks state dirty, then pushes `Msg::FileEvent { path, mtime_ms }` — registry
   before push, so a crash between the two never loses the fact.
7. App's existing `file_event` arm runs `stampDocChange` + `refreshDoc`; the recency
   label, markdown content, and (only on a real mtime change) the HTML `?v=` follow.

### Interface Contract

```rust
// core/crates/tarmac-protocol/src/lib.rs — additive app→daemon variant.
// msgpack tag "t":"doc_refresh"; encoded with rmp_serde::to_vec_named.
DocRefresh {
    path: String,   // required — the absolute registry key, as received in doc_opened
},
```

| key | type | missing ⇒ | semantics |
|---|---|---|---|
| `path` | string (required) | — | the doc to re-stat; must be the registry key |

**Additive-only rules that apply:**

- No existing key or message is changed. Conformance vectors **V1–V10 stay untouched**.
- One **new vector V11** is added in `core/crates/tarmac-protocol/src/lib.rs` and
  documented in `docs/protocol.md`: `{t:"doc_refresh", path:"/a.md"}` ⇒
  `82 a1 74 ab 64 6f 63 5f 72 65 66 72 65 73 68 a4 70 61 74 68 a5 2f 61 2e 6d 64`.
  Vectors assert decode-equivalence plus an encode→decode round-trip, not byte-exactness.
- `make docs-check` (rule 4) fails unless `DocRefresh` appears in `docs/architecture.md`
  and `doc_refresh` appears in `docs/protocol.md`. Both must be updated in the same change.
- **Never run `cargo fmt`** on the Rust crates.

```ts
// desktop/src/ipc/daemon.ts
export function docRefresh(path: string): Promise<void>;
```

```ts
// desktop/src/cards/CardHeader.tsx — additive optional prop; absent ⇒ no control.
onRefresh?: () => void;
```

**Daemon behavior contract (`DocRefresh { path }`):**

- **Always pushes on a successful stat.** No mtime comparison daemon-side: the push
  carries whatever the file's real mtime is, changed or not. The "did anything change"
  question is answered app-side, by value equality, in code that already exists.
- **Silent on failure.** Unknown path or failed stat ⇒ no push and no `Err` frame; the
  only trace is a `debug!` line, as in the `DocClose` arm. Matches `DocClose`'s no-op
  contract and `watch_loop`'s deleted-file rule.
- **The `path` must be the registry key, byte-for-byte.** The handler does not
  canonicalize, so an alias of an open doc (`/tmp/a.md` for a doc registered as
  `/private/tmp/a.md`) is an unknown path and no-ops. Safe by construction: the app
  only ever sends a path it received in `doc_opened`/`restore`, which is already the
  canonical key `handle_open` inserted.
- **Active-board scoped.** Lookup and update use the active board's registry, exactly
  as `watch_loop` does (`active_registry()` / `active_registry_mut()`). A doc open only
  on a background board is a no-op (S5). App renders every board simultaneously and
  hides the inactive ones with `display: none`, so a background card's control is
  mounted but unclickable — the daemon-side scoping is the real guard, not the UI.
- **No side effects beyond the stat.** No `doc_opened` re-push, no `read` flip, no
  `fresh` change, no `last_opened_ms` bump, no `ensure_watched`, no `canonicalize`.
- **Idempotent and race-tolerant.** A `doc_refresh` racing `watch_loop` for the same
  path yields two `file_event`s carrying the same mtime; the second is a no-op app-side.

**UI contract:**

- The control's markup lives in `CardHeader` and is gated on the `onRefresh` prop, so
  both card kinds get it from one component without passing their own (see the
  divergence note in the Overview).
- **Glyph `↻`, always rendered when `onRefresh` is present** — not hover-gated, exactly
  like the close ✕ (decided at the spec gate; see Open Questions).
- **Header order is fixed:** recency label, refresh control, `props.children` (the
  HTML card's console badge, when present), close ✕. The refresh control renders
  before `props.children` so a card's own chrome keeps its place next to the ✕.
- `onPointerDown` must `stopPropagation()` **and** `preventDefault()`, like the
  existing close ✕ and console badge — without it the click starts a card drag.
- **The send is fire-and-forget**, exactly like `removeDoc`'s `void docClose(path)`:
  the `doc_refresh` Tauri command returns unit, so the click never awaits a reply and
  never surfaces an error. Everything the user sees arrives later, on the `file_event`.
- **No click-driven pending/loading state.** A spinner would be a mark not backed by
  an OS fact. The only feedback is the recency label reflecting the real post-refresh
  mtime. It follows that refreshing an unchanged file whose mtime is older than the
  30 s recency window produces **no visible change at all** — stated behavior, not an
  accident (see Open Questions).

## Alternatives Considered

### Extend `handle_open`'s existing-doc branch to re-stat and push `file_event`

No protocol change, no new Tauri command, and the app already has a `docOpen(path)`
sender. **Rejected:** `handle_open` inserts new docs with `last_changed_ms: None` and
only `watch_loop` ever populates it, so "mtime differs from the registry" is true on
the *first* re-open of every doc — meaning a plain `tarmac open` on an already-open
HTML card would fire `file_event`, bump `?v=`, reload the document and destroy its JS
state, for no change at all. It also collapses two responsibilities ("surface a doc"
and "re-establish a doc's facts") into one handler.

**The trade-off in one sentence:** a new additive message costs a `Msg` variant, vector
V11, two doc rows and a Tauri command, but it keeps `handle_open`'s contract untouched —
whereas extending `handle_open` would make every first `tarmac open` re-open reload
HTML cards and lose their JS state.

### Refresh entirely app-side (re-read the file from the webview)

`read_doc` already reads markdown from the frontend, and the `tarmac-card://` handler
reads HTML bytes. A client-only refresh could bump a local nonce. **Rejected:** the
daemon owns the doc registry and the mtime that backs the recency label; a client-side
nonce is a mark with no OS fact behind it, and it would reload HTML cards on every
click regardless of whether the file changed — the #99 failure path.

### Compare mtimes daemon-side and push only on a change

Fewer messages on the wire. **Rejected:** it moves the change decision into the daemon,
where it would have to be duplicated for the markdown re-read (which we want
unconditionally, for certainty) and re-derived for the HTML case. Pushing the real
mtime unconditionally lets one existing app-side value comparison serve both kinds.

## Acceptance Scenarios

Legend: **[P]** protocol crate, **[D]** daemon integration, **[K]** desktop kit
(Vitest), **[Q]** manual QA checklist.

### Protocol

- **S1 [P]:** Given the V11 hex vector `82 a1 74 ab 64 6f 63 5f 72 65 66 72 65 73 68
  a4 70 61 74 68 a5 2f 61 2e 6d 64`, when it is decoded in Rust, then it decodes to
  `Msg::DocRefresh { path: "/a.md" }` and survives an encode→decode round-trip.
- **S2 [P]:** Given the existing conformance vectors V1–V10, when the suite runs after
  `DocRefresh` is added, then every one of them still decodes to its documented
  structure unchanged.

### Daemon — happy path

- **S3 [D]:** Given a doc open on the active board whose file has been rewritten with a
  new mtime since it was opened, when the daemon receives `DocRefresh { path }`, then it
  pushes `FileEvent { path, mtime_ms }` carrying the file's **real current** mtime, and
  **no `doc_opened` frame accompanies it** (a refresh is not a re-open).
- **S4 [D]:** Given the doc from S3, when `DocRefresh` has been handled, then the
  registry entry's `last_changed_ms` equals that same mtime — observed in the persisted
  `state.json` and again in the `Restore` that follows a daemon restart, so the fact is
  recorded and durable, not just announced — while that entry's `read`, `via`,
  `last_opened_ms` and dock position are unchanged from their pre-refresh values.
- **S5 [D]:** Given a doc opened onto a **background** board (`Open { path, board_id }`
  for a board that is not active), when `DocRefresh { path }` is received while another
  board is active, then **no `file_event` is pushed** for it and that board's persisted
  `last_changed_ms` stays `null`; and when the app then switches to that board and sends
  the **same** `DocRefresh { path }`, a `file_event` **is** pushed. The positive control
  is what makes the silence meaningful — it proves the first refresh was scoped out, not
  mis-set-up. (Wait for the background board's entry to appear in `state.json` before
  asserting "still null", so the assertion is a post-condition and not an unwritten file.)
- **S21 [D]:** *(numbered out of sequence — added after review; existing IDs are stable
  references and were not renumbered.)* **The watcher-missed-it case, which is #89's
  acceptance bullet 6 and the feature's reason to exist.** Given a doc opened onto a
  **background** board, when the file is edited while a **different board is active** —
  so the edit's event is dropped, and the app then switches to that board and sends
  `DocRefresh { path }` — then the pushed `FileEvent.mtime_ms` equals the **post-edit**
  mtime and that board's persisted `last_changed_ms` moves from `null` to that value.
  This is the only scenario in which a refresh delivers a change the watcher never
  announced: S3 and S6 both refresh an edit the watcher already reported (their tests
  drain it first), and S7 has no edit at all. Assert the post-edit mtime **by value** —
  "a `file_event` arrived" is not enough, since S5's positive control already covers that.

  > **The suppression is a race, not a guarantee — sequence the test accordingly.**
  > `watch_loop` evaluates `active_registry()` at event-**processing** time, and the
  > debouncer holds each batch ~100 ms; the daemon watches *every* board's dock dirs, so
  > the edit's event is genuinely in flight, merely filtered on arrival. A test that goes
  > edit → `BoardSwitch` → `DocRefresh` back-to-back will routinely let the switch land
  > first, at which point the watcher matches the **now-active** board's registry, pushes
  > a `file_event` carrying the post-edit mtime and writes `last_changed_ms` — satisfying
  > *both* assertions with a `DocRefresh` handler that does nothing at all. Required
  > sequence: edit → `none_within(app, ~300 ms, is_file_event)` **while the other board is
  > still active** (this both proves the silence and lets the debounce window expire) →
  > `BoardSwitch` → `wait_for_state` confirming that board's `last_changed_ms` is *still*
  > `null` → only then `DocRefresh`.
  >
  > **Make the mtimes distinguishable.** `mtime_ms` truncates to milliseconds, so an edit
  > in the same millisecond as the open is indistinguishable from it and the mutant below
  > survives. Sleep ≥ 5 ms before the edit (the suite already uses 300 ms sleeps), capture
  > the pre-edit mtime, and assert the pushed value **differs from it** as well as
  > equalling the post-edit mtime.
- **S22 [D]:** *(added after the first referee pass — see the note below.)* **The
  refresh re-stats; it never re-announces what the registry already believes.** Given a
  doc on the active board whose registry `last_changed_ms` is **populated** (an earlier
  edit the watcher did report) and whose file has since been edited again while its
  board was backgrounded — so the stored value is populated *and stale* — when
  `DocRefresh { path }` is received, then the pushed `mtime_ms` is the **second** edit's,
  not the stored first one, and the registry catches up to it.

  > **Why this is not redundant with S21.** S21's registry is `None`, so a handler that
  > answers from `last_changed_ms` and stats only as a fallback —
  > `info.last_changed_ms.unwrap_or(stat_derived)`, the natural shape given the field is
  > an `Option` — falls through to the real stat and passes. The first referee pass
  > executed that mutant arm-side and it **survived every test then present**: S3/S6 drain the
  > watcher so registry and file already agree, S7/S8 never write the file, and
  > S5/S21 have a null registry. No test had a populated-*and*-stale registry on the
  > active board — which is precisely the state #89 exists to repair (see the
  > "Asymmetric across boards" limitation, and every watcher-miss cause in the Context).
  > S22 is the only test that distinguishes "re-establish the fact" from "re-announce
  > what we already believed", and it is also the stable kill for a handler that pushes
  > without writing the registry.

### Daemon — edge cases

- **S6 [D]:** Given a doc whose file has **not** changed since the last `file_event`,
  when `DocRefresh { path }` is received, then a `file_event` is **still** pushed, and
  its `mtime_ms` equals the mtime **captured from that earlier `file_event`** (not
  re-derived by the test) — the always-push contract, and the scenario that kills both
  a `now_ms()`-instead-of-mtime handler and a daemon-side "skip if unchanged" compare.
- **S7 [D]:** Given a doc that nothing has written since it was opened, when
  `DocRefresh { path }` is received, then a `file_event` carrying the file's real mtime
  is pushed and the registry records that value. With no edit for a watcher event to
  ride on, the push is attributable to the refresh alone — this is the unconditional
  kill for a do-nothing handler.

  > **Corrected during implementation — the baseline is quiescence, not `None`.** This
  > scenario originally required `wait_for_state` to observe `last_changed_ms: null`
  > immediately beforehand. That is unattainable: opening a just-written doc makes
  > FSEvents replay the file's own creation to the freshly-attached dir watch, so
  > `watch_loop` populates `last_changed_ms` within milliseconds of the open. Measured
  > on this harness: a persisted entry with `last_changed_ms` **3 ms earlier than**
  > `last_opened_ms`. Waiting for `null` timed out in 2 of 3 runs. The test therefore
  > drains any watcher event for the path (~800 ms, well past the 100 ms debounce) and
  > only then refreshes; the drain's result is deliberately not asserted, since whether
  > FSEvents replays a create is the platform's business. The same settle is applied in
  > S3, S4 and S6 before they consume "the watcher's event", because without it those
  > tests could consume the *create* and mistake the edit's event for the refresh's —
  > the exact vacuity this suite is arranged to avoid.
- **S8 [D]:** Given two `DocRefresh` messages for the same unchanged path in sequence,
  when both are handled, then both push a `file_event` and both carry the identical
  `mtime_ms`.

### Daemon — error scenarios

- **S9 [D]:** Given a `path` that is not in the active board's registry, when
  `DocRefresh { path }` is received, then nothing is pushed for it, no `err` frame is
  sent, and an unrelated open doc's registry entry is untouched.
- **S10 [D]:** Given an open doc whose file has since been **deleted**, when
  `DocRefresh { path }` is received, then nothing is pushed and no `err` frame is sent
  (matching `watch_loop`'s "deleted files emit nothing" rule), and the daemon stays
  live enough to answer a subsequent `DocRefresh` for a different, existing doc.

### App-side change detection (the #99 guard)

**Read this before scoring S11.** `cardSrcUrl` is **not modified by this change**, so
S11 is green before a line is written. It is a **regression guard, not delivered
behavior** — it exists because this feature makes `cardSrcUrl`'s purity load-bearing in
a way it was not before (every refresh click now re-evaluates it), and the obvious
"make refresh actually refresh" mistake is to add a nonce. `/verify` should treat S11
as a standing guard against a named future mutant, not as evidence the feature works —
S3–S10, S21, S22 and the QA items are what demonstrate that.

S11 extends the existing `cardSrcUrl` describe block in
`desktop/src/kit/docKind.test.ts`. It pins purity, which is a *necessary condition* for
the unchanged-mtime no-reload — the reload itself is React's `<iframe src>`
reconciliation and is not unit-testable here (S16/S20 [Q] observe it). It must not
restate the `?v=<mtime>` / `?v=0` shape assertions already at `docKind.test.ts`.

- **S11 [K]:** Given one path and one mtime value, when `cardSrcUrl` is called twice
  with those same inputs at different moments, then it returns two identical strings —
  the URL is a pure function of `(path, mtime)` with no clock- or random-derived
  component. This is the scenario that fails if anyone adds a nonce (`Date.now()`, a
  counter, `Math.random()`) to force reloads: an unchanged-mtime refresh must leave the
  iframe `src` byte-identical, or every click reloads an HTML card and costs its JS
  state (the #99 failure path).
- **S12 — withdrawn, deliberately not renumbered.** It read "two different mtimes give
  different URLs", which the existing `docKind.test.ts` `cardSrcUrl` cases already
  establish (they assert `?v=1234` and the `?v=0` fallback) — adding it would restate
  coverage this very section forbids restating, and like S11 it would be green before
  any change. If the existing block does not make "a different mtime yields a different
  URL" evident on reading, strengthen an assertion **there** rather than adding a
  scenario here. The ID is retired so S1–S11 references stay stable. Its original
  wording: the two URLs differ, so a real change does bump `?v=` and
  reload the document (which is what resets `readyHandledRef` and re-posts the zoom).
  Fails if `?v=` is ever dropped or pinned to a constant, which would strand an HTML
  card on its first-loaded bytes forever.

### Manual QA — UI shell

The React/Tauri shell has no unit tests by design (only pure `kit/` logic and Rust are
tested). These are checklist items in a new `desktop/qa/doc-refresh-qa.md`, each
recorded VERIFIED / NOT VERIFIED with the observation, following the existing
`desktop/qa/html-card-qa.md` and `magnify-card-qa.md` convention.

**The new QA file must open with the dev-daemon caution**, worded as
`desktop/qa/magnify-card-qa.md` does: run against `make run` with a fresh dev daemon
(`make kill-daemon` first), and kill any *installed* `tarmacd` (`pkill tarmacd`) before
testing, since a persistent installed daemon hijacks the dev app. This matters more here
than for any previous QA sheet: every item below is an observation of daemon-side
behavior that does not exist in an installed build, so a hijacked session would fail
S15–S20 for the wrong reason and look like a broken feature.

> **The stale-card recipe** (used by S15, S17, S19). On macOS + FSEvents there is no
> user-reachable way to make the *active* board's watcher miss an edit, so "the watcher
> missed it" must be staged the way the daemon actually produces it: park the card on
> board-0, switch to board-1 (the doc must **not** also be open on board-1), edit the
> file — `watch_loop` matches only the active board's registry, so no `file_event` is
> emitted — then switch back to board-0. The switch heals nothing: `applyRestore`
> early-returns for an already-visited board, so the card still shows the **old
> content**, the old recency label and the old `?v=`. Everything the refresh does is
> therefore visible against that baseline. Confirm the stale baseline before clicking —
> a scenario that clicks refresh on an already-current card proves nothing.

- **S13 [Q]:** A markdown doc card shows the refresh control in its header without
  hovering; a live HTML card shows it too, in the order recency label → refresh →
  console badge (when present) → close ✕.
- **S14 [Q]:** Pressing and dragging from the refresh control does **not** move the
  card (pointerdown propagation is stopped).
- **S15 [Q]:** With a markdown card made stale by the recipe above and scrolled partway
  down, clicking refresh renders the **new** content — verifiably the edited bytes, not
  the pre-edit ones — with the scroll position preserved (no jump to the top). This is
  the #89 user story end to end.
- **S16 [Q]:** With a magnify HTML card at board zoom ≠ 1 whose file has **not** changed
  **and whose `lastChangedMs` is already populated** — the card has taken at least one
  `file_event`, from a prior edit or a prior refresh (S20 covers the un-populated card,
  which behaves differently on purpose) — clicking refresh does not reload the document
  (page-local state such as a running counter survives) and the card's rendered size
  does not change.
- **S17 [Q]:** With a magnify HTML card at board zoom ≠ 1 made stale by the recipe
  above (`desktop/qa/magnify-probe.html` is the ready-made document — it declares
  `tarmac-zoom`, so `HtmlCard` logs a host-side `zoom-mode declared=…` console line
  per load; copy it outside the repo before editing so the QA run doesn't dirty the
  worktree), clicking refresh reloads it: page-local state resets and the console
  badge count **continues** from where it stood — the card is never unmounted, so
  the reload appends to the existing buffer instead of restarting at the per-load
  count, which is what a remount would do. How many entries one load emits depends
  on the document (`magnify-probe.html` emits five), so the observable is
  continuation, not a fixed increment. The document comes back at the current board
  zoom, not at 1/K (the #99 shape).
- **S18 [Q]:** Clicking refresh on an unchanged doc older than the 30 s recency window —
  a markdown card, or an HTML card whose `lastChangedMs` is already populated — produces
  no visible change at all: no spinner, no synthetic "just refreshed" label, and on a
  markdown card scrolled partway down neither the rendered content nor the scroll
  position moves.
- **S19 [Q]:** With a markdown card made stale by the recipe above and the click made
  ~10 s after the edit (inside the 30 s recency window), the header carries no recency
  label for that edit beforehand; clicking refresh makes it show `✎ Ns` where **N is
  the age of the edit (≈10 s), not `✎ 1s`** — the label is stamped from the file's real
  mtime, never from the click. This is the scenario that catches a click-time
  `Date.now()` stamp app-side.
- **S20 [Q]:** Given a magnify HTML card **freshly opened and never changed since** — so
  its `lastChangedMs` is unset and its iframe is at `?v=0` — at board zoom ≠ 1, when
  refresh is clicked the **first** time, then the document reloads once even though the
  file did not change (page-local state resets, and the console badge count **continues**
  past its previous value by this document's per-load count rather than restarting at it
  — see S17) and it comes back at the current board zoom, **not** at 1/K; and when refresh
  is clicked a **second** time with still no edit, then nothing reloads (page-local state
  survives). This is the one-time-reload trade-off made observable: it confirms the
  reload is #99-*safe* and self-limiting, and it is the evidence the human needs to
  settle Open Question 1. If the first click leaves the card at 1/K, that is the #99
  shape and a blocker, not an accepted trade-off.

`/verify` scores against — see
`/Users/eplin/.claude/plugins/cache/runway/blueprint/4.0.0/references/test-desiderata.md`
and `.../references/anti-patterns.md` in the same directory):

- **Behavioral over structural** — assert observable output/effects, not internals.
- **Every test can fail** — no copy-pasted expected values, no asserting a constant.
- **Deterministic, isolated, readable** — no cross-test state, AAA structure.
- **S3/S6: consume the watcher's `file_event` first.** Both scenarios begin by writing
  the file, which the watcher reports on its own. A test that writes, sends
  `DocRefresh`, then reads "the next `file_event`" may be asserting on the *watcher's*
  message — same path, same mtime — and would pass against a handler that does nothing
  at all. `recv_until` the write's `file_event` **before** sending `DocRefresh`, so the
  event under assertion can only be the refresh's.
- **Do not write a race test.** The `doc_refresh`-vs-`watch_loop` race in the contract
  is deliberately not a scenario: forcing the interleaving is nondeterministic and would
  buy a flaky test. Race tolerance follows from the always-push rule (S6, S8) plus the
  app's existing by-value handling of `file_event` — two `file_event`s carrying the same
  mtime are indistinguishable from one, because `cardSrcUrl` is a pure function of

  having been suppressed, so it sequences the debounce window closed with an explicit

## Trade-offs and Limitations

- **A first refresh of a never-changed doc reloads an HTML card once.** `handle_open`
  inserts `last_changed_ms: None`, so the app sees `lastChangedMs: undefined` and
  renders `?v=0` until something populates it. The first `doc_refresh` therefore moves
  `?v=0 → ?v=<real mtime>` and reloads the document even though the file did not
  change, costing its JS state. This is #99-*safe* (the `lastChangedMs` effect fires,
  `readyHandledRef` resets, the zoom is re-posted) and self-limiting — every subsequent
  unchanged refresh is a genuine no-op. Populating `last_changed_ms` at open time would
  remove it but pulls `handle_open`/`doc_opened` into this change; see Open Questions.
- **Active-board scoped.** A doc card on a background board cannot be refreshed. That
  matches `watch_loop`. Its control is still mounted (App keeps every board mounted and
  hides the inactive ones with `display: none`) but unclickable, and the daemon no-ops
  even if a message arrives — so a background card stays stale until its board is
  active. Switching to that board does not itself refresh anything (`applyRestore`
  early-returns for a visited board); it only makes the control clickable. The click is
  the recovery.
- **Asymmetric across boards.** The daemon records the mtime only in the **active**
  board's registry, while the app's `stampDocChange`/`refreshDoc` apply the resulting
  `file_event` to **every** board that knows the path. So a doc open on two boards ends
  up correct on the glass but persisted on one board only; the other board's
  `last_changed_ms` catches up the next time it is active and something changes. This
  is `watch_loop`'s existing asymmetry, inherited unchanged, not a new one.
- **The path must be the registry key.** The handler does not canonicalize, so an
  uncanonicalized alias (`/tmp/a.md` for a doc registered as `/private/tmp/a.md`) is an
  unknown path and silently no-ops. Nothing in the app can produce such a path today —
  every path it holds came from `doc_opened`/`restore` — but a future non-app client
  would have to canonicalize first.
- **No user-visible failure signal.** A refresh of a deleted or unreadable file is
  silent, per the daemon's existing no-op discipline. The user sees the card unchanged
  and must infer the file is gone.
- **The wire grows.** One more variant, one more vector, two more doc rows, one more
  Tauri command. The additive-only rule keeps it safe, but the surface is not free.
- **Markdown always re-reads.** Every refresh does a real `read_doc` even when nothing
  changed. That is the point (certainty), and it costs one small file read per click.

## Open Questions

All three were decided at the spec gate. Kept here as the record of what was chosen.

- [x] **The one-time HTML reload on a doc's first refresh: accepted.** `handle_open`
      keeps inserting `last_changed_ms: None`, so a doc's first refresh moves
      `?v=0 → ?v=<mtime>` and reloads an HTML card once. It is #99-safe and
      self-limiting; S20 [Q] observes it. `handle_open`/`doc_opened` stay out of #89.
- [x] **An unchanged refresh does not acknowledge itself.** No spinner, no synthetic
      label, nothing on click (S18). If acknowledgement is ever wanted, the honest form
      is a marker rendered on `file_event` *receipt* — a follow-up issue, not this one.
- [x] **Glyph `↻`, always visible, between the recency label and the ✕.** Not
      hover-gated, exactly like the close ✕; rendered by `CardHeader` immediately before
      `props.children`, so the order is recency → `↻` → console badge → ✕.
