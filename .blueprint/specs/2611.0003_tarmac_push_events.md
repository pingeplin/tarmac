# 2611.0003 `tarmac push`: events for a loaded HTML card

**Date:** 2026-11-12
**Status:** accepted
**Author:** EP Lin
**Design doc:** [2611.0001](../../docs/designs/2611.0001_html_card_data_push.md) (phase 2; decisions 3–7, 17–21)
**Issue:** #326

## Context

Phase 1 (spec 2611.0002, #313) gives a loaded HTML card the whole content of
one JSON file: latest wins, and changes that come faster than the watcher
looks are joined. It left two things phase 2 uses:

- the shim's dispatcher (`card_shim.js`: `window.tarmac`, the `data` message
  from the host page);
- the load stamp on `ready`: `HTMLCardSession.namedLoad` is the load whose
  stamped `ready` was heard, for a card with a `tarmac-data` meta and for one
  without.

Facts read in the code at `0c7b37a`:

- `cli_session` (`core/crates/tarmacd/src/conn.rs`) loops over frames on one
  connection, with no idle limit, and answers `open` with `ack` or `err`. A
  frame that does not decode gets `err "malformed frame: <decoder's message>"`
  and the loop goes on. A frame whose length is over `MAX_FRAME_LEN` ends the
  connection with no answer.
- `Daemon::push` (`state.rs`) awaits a bounded channel (256) to the app's
  writer and returns false when no app is connected. So a producer is slowed
  when the app's socket is slow, and frames keep their order.
- The app's writer task (`app_session`) cancels the app connection when a
  frame it writes fails, and `frame::write_async` fails for a payload over
  `MAX_FRAME_LEN` (16,777,216 bytes).
- A message type the daemon does not know gets no answer.
- The cli's socket has a read timeout of 5 s (`main.rs`, `handshake`).
- `AppController.handleFileEvent` walks all boards the app holds.
- `DaemonClient.deliver` puts each frame on the main queue as a block of its own.
- Test seams. The cli's tests run the `tarmac` binary against a scripted
  daemon double (`tarmac-cli/tests/common/double.rs`) with stdin set to null.
  The daemon's integration tests run `tarmacd` and speak the wire through raw
  `Conn`s, as `cli` or `app`. No test runs the cli binary against a real
  daemon: each crate's tests see only their own binary (`CARGO_BIN_EXE_*`).
  The daemon's in-crate tests count each gate call (`StuckFs::calls`) and
  use an mpsc receiver as the app (`state/tests`, `connect_app`).

## Motivation

A producer with single things to say (a log line, a step that ended) must
today rewrite the whole state file for each one. Events give it a second
mode: one value at a time, in order, to the cards loaded at that moment.

## Proposed Solution

### Overview

```
tarmac push <html-path> '<json>'          one value, then exit
<producer> | tarmac push <html-path> -    one value per line of stdin, one connection
```

The cli sends `push {path, data}` for each value and waits for `ack` or
`err`. The daemon checks that `data` is one JSON value and that `path` is an
open doc, and pushes `doc_event {path, data}` to the app. The app hands the
text to each card of that path whose document is ready for its current load.
The shim parses it and dispatches `tarmac:event` on `window` with the value as
`detail`. Nothing is kept anywhere for a card that is not ready.

### Key Components

- **`tarmac-protocol`** — `Msg::Push { path, data }`, `Msg::DocEvent { path, data }`, fields in that order (the bytes of vectors 16 and 17 depend on it).
- **`tarmac-cli`** — a new module `push.rs`: argument parse, the line reader (pure, over `impl Read`, the limit a parameter), the frame-size check (pure, the limit a parameter), the stream loop, exit codes. Std only; it does not parse JSON.
- **`tarmacd`** — `cli_session` takes `Msg::Push`; a new function in `docs.rs` (`handle_push`) with the JSON check, the path lookup and the size check. The path cache is owned by the connection and passed to `handle_push`, so a test can push twice with one cache.
- **`TarmacKit`** — `Message.push` (the conformance tests need it; the app never gets one) and `Message.docEvent`; `HTMLCardSession.event(_:)`; `CardEventBatch` (the texts of one main-loop turn).
- **`TarmacApp`** — `AppController.handleDocEvent`, `HTMLCardView` (the batch flush, `tarmacCard.events(texts)`).
- **`card-host.js` / `card_shim.js`** — `tarmacCard.events(texts)` → `{tarmac:"events", texts}` → one `tarmac:event` for each text.

### Data Flow

1. The cli makes `<html-path>` absolute with `std::path::absolute` (no file-system call, as `open`) and sends `push`.
2. The daemon: `data` is one JSON value, else `err`. `path` is absolute, else `err`. It looks `path` up as a doc key in every board's registry. On a miss: when this connection's cache has `path`, it looks the cached resolved path up and makes no resolve; else it resolves `path` through the path gate (`RealFs::resolve`), puts given → resolved in the cache when the resolve succeeds, and looks the resolved path up. No board has it: `err`. A resolve that fails is not cached, so the next push of that path resolves again.
3. The daemon encodes `doc_event {path: <the registry's key>, data}`. A payload over `MAX_FRAME_LEN`: `err`, and nothing is pushed (an over-limit frame would end the app's connection). Else it calls `Daemon::push`. False: `err`. True: `ack`. One push gives one `doc_event`, however many boards hold the doc.
4. The app (`handleDocEvent`): for each board it holds, the card `.doc(path)` with an HTML body gets `event(data)`. A markdown card gets nothing. A board the app has not built (not visited in this run) has no cards and gets nothing.
5. The session returns `.event(text)` when the card is ready for its current load, else nothing.
6. The view appends the text to its batch and, when the batch was empty, schedules one flush on the main queue. The flush calls `tarmacCard.events(texts)` once, with the texts as an argument (never spliced into the script). The view empties the batch when it asks for a new document (`loadDocument`) or a new host page (`loadPage`, also after the web process ended). A flush while the host page is not loaded posts nothing and empties the batch, as `deliver` posts nothing. A flush that takes no text makes no script call. These view rules are `TarmacApp` wiring: the batch's own rules are tested (S31–S33), the wiring is not, and L6 runs it only in part.
7. The host page posts `{tarmac:"events", texts}` to the frame. The shim, for each text in order: `JSON.parse`; on success `dispatchEvent(new CustomEvent("tarmac:event", {detail}))`. Each text has its own `try`, so one text that fails stops none after it.

### Interface Contract

**Wire (additive).**

```
{t:"push",      path:<str>, data:<str>}    cli → daemon; answered with ack | err
{t:"doc_event", path:<str>, data:<str>}    daemon → app; no reply
```

Vector 16 (`push`, path `/a/dash.html`, data `{"n":1}`):

```
83 a1 74 a4 70 75 73 68 a4 70 61 74 68 ac 2f 61 2f 64 61 73 68 2e 68 74 6d 6c
a4 64 61 74 61 a7 7b 22 6e 22 3a 31 7d
```

Vector 17 (`doc_event`, same fields):

```
83 a1 74 a9 64 6f 63 5f 65 76 65 6e 74 a4 70 61 74 68 ac 2f 61 2f 64 61 73 68
2e 68 74 6d 6c a4 64 61 74 61 a7 7b 22 6e 22 3a 31 7d
```

The implementer checks both against the Rust encoder; if the encoder gives
other bytes, the encoder is right and this text is corrected.

**Daemon answers to `push`** (the `msg` of `err`; `<path>` is the path as given):

| Case | Answer |
| --- | --- |
| the frame does not decode as a message (a `push` with no `path` or no `data`, a `data` that is not a msgpack str) | `err "malformed frame: <decoder's message>"` (the existing arm); the connection stays open |
| `data` is not one JSON value (`serde_json`; empty text and trailing text included) | `err "not one JSON value: <serde_json's message>"` |
| `path` is not absolute | `err "path is not absolute: <path>"` |
| the resolve fails | the resolve's own text, as `open` gives it: `cannot open <path>: <io error>`, `cannot stat <resolved>: <io error>`, or `not a regular file: <resolved>` |
| the resolve is out | `cannot open <path>: did not answer in <limit>` (`PathGate::did_not_answer`), as `open` gives it |
| no board has the doc | `err "not an open doc: <path>"` |
| the encoded `doc_event` is over `MAX_FRAME_LEN` | `err "value is over the frame limit (16 MiB)"`; nothing is pushed |
| no app is connected | `err "no app is connected"` |
| otherwise | `ack`, after the frame is queued for the app |

The checks run in that order. `ack` means "queued for the app", not "drawn".
A frame whose length prefix is over `MAX_FRAME_LEN` gets no answer: the
daemon ends the connection (existing rule). The cli never sends one (choice 10).

**The cli.**

```
tarmac push <html-path> <json>
tarmac push <html-path> -
```

- Any other argument count: usage on stderr, exit 2.
- The second argument is stream mode only when it is exactly `-`. Any other text, `-1` included, is one value.
- In one-value mode the argument is sent as it is, also when it is empty or blank; the daemon refuses it. (Blank lines are skipped in stream mode only, choice 6.)
- A path that `std::path::absolute` refuses (the empty path): one line on stderr that names the path and the reason, exit 1, and no connection is made.
- Success prints nothing on stdout and nothing on stderr.
- One value: `err` → `tarmac: <msg>` on stderr, exit 1. No daemon, or a refused handshake → the message `open` gives, exit 1. A lost connection → `tarmac: daemon connection lost: …`, exit 1.
- **The frame limit.** A `push` is not sent when its encoded payload (the msgpack map, not the 4-byte length) is over `MAX_FRAME_LEN`, 16,777,216 bytes: `tarmac: value is over the frame limit (16 MiB)`, exit 1. In one-value mode this is likely out of reach, as macOS limits the size of an argument list (the implementer checks `getconf ARG_MAX`); the check is shared with stream mode and tested there (S42).
- An answer that is not `ack` or `err` is skipped, as `open` does, and the cli reads on.
- No answer within the socket's read timeout (5 s): `tarmac: no answer from the daemon in 5 s (an older daemon, or the app is not reading)`, exit 1. In stream mode the line is prefixed (`tarmac: line <n>: no answer …`) and the stream ends there: answers carry no id, so a late answer could be taken for the next line's.
- A lost connection in stream mode ends the stream: `tarmac: line <n>: daemon connection lost: …`, exit 1.

**Stream framing** (stdin, read as bytes):

- A line ends at `\n`. One `\r` before it is dropped. Input that ends with no `\n` gives a last line.
- Lines are numbered from 1, every line counted.
- A line that is empty or holds only ASCII white space (space, tab, `\r`) is skipped: not sent, not refused.
- Any other line is sent as it is, white space around the value included. A JSON value written over more than one line is sent line by line, and the daemon refuses each part.
- A line longer than `MAX_FRAME_LEN` bytes is refused by the cli: `tarmac: line <n>: value is over the frame limit (16 MiB)`. The reader keeps no more than `MAX_FRAME_LEN` bytes of it in memory and reads on to the line's end. This check comes before the UTF-8 check. A shorter line whose encoded `push` is over the limit gets the same message (the frame limit, above).
- A line that is not UTF-8 is refused by the cli: `tarmac: line <n>: not UTF-8`.
- A line the daemon refuses: `tarmac: line <n>: <msg>`.
- A refused line, by the cli or by the daemon, does not end the stream. The cli waits for each answer before it sends the next line.
- Exit 0 when no line was refused, 1 when any was. Empty input: exit 0.
- A read error on stdin ends the stream: one line on stderr that names stdin and the error, exit 1.
- The handshake is made before the first line is read; no daemon → exit 1 with nothing read.

**The document.**

```js
addEventListener("tarmac:event", e => apply(e.detail));
```

- `tarmac:event` is a `CustomEvent` on `window`; `detail` is the parsed value.
- Text the shim cannot parse (the daemon and `JSON.parse` do not agree on every text) gives no event and one error line, `tarmac:event: not valid JSON`, in the card's console; the texts after it in the batch are still dispatched.
- A listener that throws does not stop the texts after it in the batch.
- A `texts` that is not an array gives nothing; an entry that is not a string gives nothing and the other entries are dispatched.
- `window.tarmac.data` is not touched by an event.
- An `events` message from anything but the host page is ignored, as `data` is.

**Which card gets an event** (session rule): the card whose `namedLoad` is its current load. `namedLoad` is set by the first stamped `ready` of the current load, also for a card with no `tarmac-data` meta (phase 1). So: not before the first stamped `ready` of a load; not after a `ready` with no stamp or the stamp of an old load only; not between a reload and the new document's `ready`; not after the web process ended (the session is not told until the new host page loads and asks for the document, which is a reload; until then the view's flush drops the texts, step 6); a culled card and a card on a board in the background do get it. A card on a board the app has not built gets nothing (it has no card). A document that sends its own frame to another address stays in the same load (phase 1), so the next document gets events from its start, also before its own `ready`.

## Alternatives Considered

### The cli parses the JSON

It would refuse a bad line with no round trip. Not chosen: the cli is std-only, and one checker (the daemon) is what the design says.

### An id on each answer

It would let the cli pipeline lines. Not chosen: it changes `ack`, and the design has the cli wait for each answer.

### No batch in the app

One script call for each event. Not chosen: the design has the events of one turn go in one call. The batch has no bound of its own. Each frame is its own block on the main queue (`DaemonClient.deliver`), and the flush is a block queued after the first event, so what bounds a batch is the `doc_event` frames that were queued on the main queue before the flush block.

## Security Considerations

- A push reads no file and gives the document nothing but the value a local caller of the socket sent. A caller of the socket can already `open` any path.
- The text goes into the page as a script argument and then through `JSON.parse`; it is never evaluated.
- The path cache is per connection and holds only given → resolved for paths that resolved.

## Acceptance Scenarios

### Wire (Rust and Kit)
- **S1:** Given `Msg::Push`/`DocEvent` with the vector fields, when encoded in Rust, then the bytes are vectors 16 and 17; when decoded, the same values come back.
- **S2:** Given vectors 16 and 17, when the Swift codec decodes and encodes them, then it gives `.push`/`.docEvent` with those fields and the same bytes (conformance and Rust-parity tests).

### cli parse and framing (Rust, pure)
- **S3:** Given `push <p> <json>`, then one-value mode with that text; given `push <p> -`, then stream mode; given `push <p> -1`, then one-value mode with the text `-1`; given 0, 1 or 3+ arguments after `push`, then usage and exit 2.
- **S4:** Given input `a\nb\n`, when read, then lines 1 `a` and 2 `b`; given `a\nb` (no last newline), then the same two lines.
- **S5:** Given `a\r\nb\r\n`, then lines `a` and `b` (the `\r` is dropped).
- **S6:** Given `a\n\n \t\nb\n`, then `a` is line 1 and `b` is line 4, and lines 2 and 3 are skipped (not sent, not refused).
- **S7:** Given a line with the bytes `ff fe`, then that line is refused as `not UTF-8` with its number, and the next line is still read.
- **S8:** Given a line longer than the limit (the reader takes the limit as a parameter; the test uses a small one, e.g. 8), then it is refused as over the limit with its number, the reader held no more than the limit of it (the test reads this from the reader, e.g. its buffer's length), and the next line is read whole. A line of exactly the limit is read whole. A line over the limit whose bytes are also not UTF-8 is refused as over the limit.
- **S9:** Given empty input, then no line.
- **S42:** Given the frame-size check with a small limit, when a `push` whose encoded payload is exactly the limit is checked, then it passes; one byte more, then it is refused as over the limit.

### cli binary against the daemon double (Rust integration, `tarmac-cli/tests/`)
The double (`tests/common/double.rs`) answers the handshake, records each frame, and answers each `push` as the test says. Stream tests need a helper that pipes stdin to the child; it spawns under the harness's `SPAWN` lock, as `output` does (#190). The cli binary and a real daemon meet only in the live runs (L1, L4, L5, L8).
- **S10:** Given a double that answers `ack`, when `tarmac push /a/dash.html '{"n":1}'` runs, then exit 0, nothing on stdout or stderr, and the double received the `hello` and then exactly one frame: `push {path: "/a/dash.html", data: '{"n":1}'}`, `data` byte for byte. A relative path is sent made absolute against the cwd, as `open` sends it.
- **S11:** Given a double that answers `ack` to each `push`, when 1,000 lines `{"n":0}` … `{"n":999}` are piped to `tarmac push <path> -`, then exit 0 and the double received 1,000 `push` frames, in that order, on one connection.
- **S12:** Given a double that answers `err "not one JSON value: x"` to the second `push` and `ack` to the others, when the stream `{"n":1}\nnot json\n{"n":2}\n` is piped, then stderr is exactly `tarmac: line 2: not one JSON value: x\n`, the double received three `push` frames, and the exit code is 1.
- **S13:** Given a double that answers `err "not an open doc: /p"`, when `tarmac push /p '1'` runs, then stderr is exactly `tarmac: not an open doc: /p\n` and exit 1.
- **S14:** Given a stream whose second line is refused by the cli (bytes `ff fe`), then the double received two `push` frames (lines 1 and 3), stderr names line 2, and the exit code is 1.
- **S15:** Given no daemon, then the message `open` gives for no daemon, and exit 1; in stream mode the same, and nothing is read from stdin first (the stream is a pipe that stays open: the cli exits anyway).
- **S16:** Given a double that answers the handshake, reads the first `push`, never answers it, and records any frame after it, then `no answer from the daemon` on stderr and exit 1, after the 5 s read timeout (the test pays it, as `version.rs`'s timeout test does). In stream mode the stderr line names line 1 and the double received no second `push`.
- **S43:** Given a double that closes the connection after it reads the first `push`, then in one-value mode `tarmac: daemon connection lost: …` and exit 1; in stream mode `tarmac: line 1: daemon connection lost: …` and exit 1, with more lines still on stdin (the stream ends there).
- **S44:** Given a double that waits 300 ms before each of its first three answers, then it receives no frame while an answer is owed (the cli waits for each answer before it sends the next line).
- **S52:** Given a double that answers a `push` first with a `hello_ok` and then with `ack`, then exit 0 (an answer that is not `ack` or `err` is skipped).
- **S53:** Given `tarmac push '' '1'` (the empty path), then exit 1, one line on stderr, and the double accepted no connection.
- **S54:** Given `tarmac push <p> ''` and `tarmac push <p> ' '`, then the double received one `push` whose `data` is `` (and ` `), byte for byte: one-value mode sends a blank argument.
- **S55:** Given the line reader over a `Read` that gives one line and then an I/O error, then line 1 is given and then the error, and no further line (the stream loop ends with exit 1 and a stderr line that names stdin).

### Daemon (Rust)
S17–S24 and S45–S51 run in-crate (`state/tests`: a `gated` daemon on `StuckFs`, `connect_app`'s receiver as the app, `handle_push` called with a cache the test owns) or as integration tests (`tarmacd/tests/`: a `cli` `Conn` and an app `Conn`). S17's count, S20 and S49 need the in-crate seam: only there are resolves counted and held.
- **S17:** Given `data` of ``, `{`, `1 2`, `{"a":1}x`, then `err` beginning `not one JSON value`; given `1`, `"s"`, `null`, `[1,{"a":[]}]`, ` {"a":1} ` (white space around), then `ack`. Each `err` here comes with no resolve (counted: 0), as the JSON check runs first (choice 1).
- **S18:** Given a relative path, then `err "path is not absolute: …"`.
- **S19:** Given a doc opened through a symlinked directory, when `push` names the symlinked spelling, then `ack` and `doc_event.path` is the registry's (resolved) path.
- **S20:** Given the doc of S19, when one cache is used for two pushes of the symlinked spelling, then the count of resolves rises by one in all; with a new cache for the second push, it rises by two. A push that names the registry's own spelling makes no resolve.
- **S21:** Given a stream that has pushed to a doc, when the doc is closed and the same connection pushes again, then `err "not an open doc: …"` (the cache does not stand in for the registry).
- **S22:** Given a doc open only on a board in the background, then `ack` and the `doc_event` is pushed. Given a doc open on two boards, then exactly one `doc_event`.
- **S23:** Given an open markdown doc, then `ack` and the `doc_event` is pushed (the app drops it).
- **S24:** Given `push` on an app connection (role `app`), then it is ignored as any message the app session does not take: no `err` and no `doc_event` comes to that connection, and the next message the app sends is still served.
- **S45:** Given a cli connection and an app connection (integration), when the cli connection sends `push {path: <open HTML doc>, data: '{"n":1}'}`, then it gets `ack`, and the app gets `doc_event` with the registry path and `data` `{"n":1}` byte for byte.
- **S46:** Given 1,000 `push` frames `{"n":0}` … `{"n":999}` on one cli connection (integration), each sent after the answer to the one before, then 1,000 `ack`s and the app gets 1,000 `doc_event`s in that order.
- **S47:** Given an open doc and no app connected, then `err "no app is connected"`.
- **S48:** Given a path whose file exists and is not an open doc on any board, then `err "not an open doc: <path>"` and no `doc_event`. Given a path whose file does not exist, then the resolve's text (`cannot open <path>: …`).
- **S49:** Given a path whose resolve the test holds (`StuckFs::hold(Call::Resolve, …)`), then `err "cannot open <path>: did not answer in …"` within the gate's limit.
- **S50:** Given a `push` frame whose `data` is a msgpack int (bytes the test writes), then `err` beginning `malformed frame`, and a valid `push` sent next on the same connection gets its answer.
- **S51:** Given an open doc and a `data` whose `push` frame is under `MAX_FRAME_LEN` and whose `doc_event` frame is over it (the type name is 5 bytes longer; a symlinked spelling that resolves to a longer path adds more), then `err "value is over the frame limit (16 MiB)"`, no `doc_event`, and the app connection stays up (a later push reaches it).

### Session (Kit)
- **S25:** Given a session that heard the stamped `ready` of its current load (no `tarmac-data` meta), when `event(text)`, then `[.event(text)]`.
- **S26:** Given a session with no `ready` yet, when `event(text)`, then no effect.
- **S27:** Given a ready session, when `reloaded()` and then `event(text)`, then no effect; after the new load's stamped `ready`, `event(text)` gives the effect again.
- **S28:** Given a ready session that is culled, when `event(text)`, then `[.event(text)]`.
- **S29:** Given a `ready` stamped with an old load only, then `event(text)` gives no effect. Given a `ready` with no stamp (`load` nil) only, then no effect.
- **S30:** Given a card with a data file and a read in flight, when `event(text)`, then `[.event(text)]` and the read's later outcome is unchanged (events and state do not touch each other).

### Batch (Kit)
- **S31:** Given an empty `CardEventBatch`, when a text is added, then it says a flush is to be scheduled; a second text before the flush says none is.
- **S32:** Given texts a, b, c added, when taken, then `[a, b, c]` and the batch is empty; the next add schedules again.
- **S33:** Given texts added, when the batch is dropped (the document reloads), then a later take gives nothing.

### Host page and shim (JS under XCTest)
- **S34:** Given `tarmacCard.events(["1","2"])`, then the frame is posted one message `{tarmac:"events", texts:["1","2"]}`.
- **S35:** Given the shim gets `{tarmac:"events", texts:['{"n":1}','{"n":2}']}` from the host, then two `tarmac:event`s fire on `window`, in order, with details `{n:1}` and `{n:2}`.
- **S36:** Given texts `['{"n":1}','{bad','{"n":3}']`, then events n=1 and n=3 fire, and the parent is posted exactly one console entry `{tarmac:"console", level:"error", args:["tarmac:event: not valid JSON"]}`.
- **S37:** Given an `events` message whose source is not the host page, then no event.
- **S38:** Given an event, then `window.tarmac.data` is what it was, and no `tarmac:data` fires.
- **S39:** Given a listener for `tarmac:event` that throws, then the next text of the batch is still dispatched. (In WebKit `dispatchEvent` reports a listener's error and does not throw; `CardShimTests`' stand-in `dispatchEvent` lets it out, so this checks the shim's own guard.)
- **S40:** Given `texts` that is not an array, or holds a value that is not a string, then that message (or that entry) gives no event and no throw.

### App message (Kit)
- **S41:** Given a `doc_event` frame, when `Message` decodes it, then `.docEvent(path:data:)`; a frame with no `data` throws `MessageError.missingField("data")`, and one whose `data` is not a str throws `MessageError.badField("data")`, as other messages with a required key do.

### Live (dev channel, hand-run, evidence under `.dev/qa-326/`)
The probe card counts events, checks `n === last + 1` itself, and writes the count and the count of order faults into its page height.
- **L1:** 1,000 lines through `tarmac push <card> -`, card in view: 1,000 events, 0 order faults, load count unchanged. Wall time noted.
- **L2:** The same for a card that is culled (more than one viewport off screen): 1,000, 0 faults, read after it is back in view.
- **L3:** The same for a card on a board in the background (`tarmac dev board`): 1,000, 0 faults, read after the switch back.
- **L4:** One `tarmac push <card> '<json>'`: the card has it; `time` of the call noted (10 runs).
- **L5:** A stream with a bad line: stderr names line and reason, the others arrive, exit 1.
- **L6:** A push while the HTML file is rewritten in a loop: no crash; after the rewrites stop, a push arrives. (Events during a reload are dropped; the count is not asserted.)
- **L7:** A push to a markdown doc: exit 0, nothing visible.
- **L8:** A push to a path that is not open: exit 1 with the message.
- **L9:** CPU of the dev app for 3 minutes after 1,000 events to a card on a background board, against 3 minutes before (the design's open finding: about 1 s of CPU a minute after a post to a card off screen).
- **L10:** Terminals stay live (the design's method, *How we will know it worked*): the delay of a terminal's echo while a card on the active board takes 100 events a second through one stream, against the same delay with no events. Median and 95th percentile noted for each. Pass: choice 12.
- **L11:** The main-thread time of one `tarmacCard.events(texts)` call: a batch of 1,000 texts of about 40 bytes, and a batch of one 1 MB text. Noted beside the design's figures for one string argument (0.41 ms for 1 MB). The design did not measure an array argument, and the dictionary cost (165–186 ms for 10 MB) may apply to it.
- Not run, stated in the PR: the screen locked, the display asleep, the lid closed, another Space, battery power, a bundled build.

## Choices made in this spec

1. The checks of a `push` run JSON first, then the path: the JSON check costs no file-system call.
2. The path cache maps given → resolved only. Each push still asks the registry, so a doc closed mid-stream is refused.
3. `doc_event.path` is the registry's key (the resolved path), which is what the app's cards are keyed by.
4. A markdown doc as the target is `ack`: the daemon does not know a doc's kind as the app sees it.
5. Success prints nothing. `open` prints a line, but a verb that is called a thousand times a minute must be quiet.
6. Blank lines are skipped, not refused: a producer that ends with an empty line is common.
7. A read timeout ends a stream: answers carry no id.
8. The app's batch has no bound of its own.
9. The shim says `console.error` for text it cannot parse; that line goes to the card's console as any error of the page does.
10. The 16 MiB limit is checked by the cli on the encoded frame, so the daemon never sees an oversize frame from this verb.
11. The runs the design owes and this phase does not make (the screen locked, the display asleep, the lid closed, another Space, battery power, a bundled build) are stated as not run in the PR. They need the owner at the machine.
12. L10 passes when, over 200 echoes through `cat`, the median delay with events is no more than twice the median with none, and the 95th percentile is under 50 ms.
13. L11: when one flush of 1,000 small texts holds the main thread for more than 5 ms, the batch goes as one JSON array in text form (one string argument) and the shim parses the array. Under that, the array argument stays.
14. The daemon's JSON rule is what `serde_json` takes as one `Value`. S17 also pins a byte-order mark, `1e400`, a lone `"\ud800"` and the nesting boundary, each as the daemon really answers; the implementer reports any case where that differs from phase 1's `StrictJSON` (127 levels taken, 128 refused), and the guide states the daemon's rule.
15. A read timeout ends a stream and a refused line does not (decision 19): a timeout is a failure of the connection, not a refusal.
16. The timeout text names both causes: `no answer from the daemon in 5 s (an older daemon, or the app is not reading)`.
17. Supersedes 9: the shim reports text it cannot parse through its own `relay`, as its other lines go, which a page cannot replace. The entry is an error with the text `tarmac:event: not valid JSON`.
18. The daemon refuses a push whose `doc_event` would be over the frame limit, with `value is over the frame limit (16 MiB)`. Without it the `ack` is sent and the app's connection is then cut.
19. Only a resolve that succeeds is cached. A stream to a path with no file costs one resolve for each line.

## Trade-offs and Limitations

- No replay: an event for a card that is not ready is gone. A document that needs the whole picture takes it from its state file.
- No order between state and events (decision 21).
- `ack` is not delivery: an app that goes away after it loses the event, and the card may still be reloading.
- The app's script call is not delivery either: it completes before the card's listener runs (107 and 162 ms later in the design's run). Nothing in the app waits on it.
- A slow app slows the answer: the daemon waits while the app's queue (256) is full. When that wait is over 5 s, the cli says `no answer from the daemon in 5 s (an older daemon, or the app is not reading)` and ends, and the event can still reach the app later.
- A stream to a path that is not open prints one line for each input line.
- One push is a process start and a round trip; the stream is for more than a few values a second.
