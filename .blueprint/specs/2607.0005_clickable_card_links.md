# 2607.0005 Clickable card links

**Date:** 2026-07-03
**Status:** draft
**Author:** EP Lin

## Context

Doc cards (`desktop/src/cards/DocCard.tsx`) render markdown via `marked.parse`
straight into `.doc-prose`'s `innerHTML`, so `<a href="…">` elements exist in
the DOM but nothing routes their clicks anywhere useful. Terminal cards
(`desktop/src/cards/TerminalCard.tsx`) build a plain `@xterm/xterm` `Terminal`
with `FitAddon`/`Unicode11Addon`/`WebglAddon` only — no link-matching addon —
so URLs typed into PTY output aren't even detected as links.

The Tauri `opener` plugin is **already wired up**: `tauri-plugin-opener = "2"`
is a Cargo dep, `desktop/src-tauri/src/lib.rs:19` registers
`.plugin(tauri_plugin_opener::init())`, `@tauri-apps/plugin-opener` is an npm
dep, and `desktop/src-tauri/capabilities/default.json` already grants
`opener:default`. GitHub issue #60's "Notes" section is stale on this point —
no Rust/capability changes are needed.

## Motivation

Docs and terminal sessions frequently contain URLs (PR links, doc
references). They're visually present but not clickable — closes GitHub
issue #60.

## Proposed Solution

### Overview

Add one pure, unit-tested URL classifier in `kit/`, one thin untested IPC
wrapper around `@tauri-apps/plugin-opener`'s `openUrl`, and wire both card
types' click paths through it.

### Key Components

- **`desktop/src/kit/externalLink.ts`** (new, pure, unit-tested) —
  `isExternalHttpUrl(href: string): boolean`, true iff `href` parses as an
  absolute URL with protocol `http:` or `https:` (via `new URL(href)`,
  `try/catch` → `false` for relative/malformed strings).
- **`desktop/src/ipc/shell.ts`** (new, thin wrapper, untested — same
  "app-layer isn't unit-tested" convention as `ipc/daemon.ts`) —
  `openExternal(url: string): Promise<void>`, calls `openUrl` from
  `@tauri-apps/plugin-opener`.
- **`DocCard.tsx`** — `.doc-prose` gets `onClick` and `onPointerDown` React
  props (event delegation; the injected `<a>` children aren't React elements,
  but React's synthetic dispatch still walks up through `.doc-prose` as a
  real ancestor, exactly like the existing close-button
  `onPointerDown={(e) => { e.stopPropagation(); e.preventDefault(); }}`
  pattern at `DocCard.tsx:166`). On `pointerdown`, if `e.target` is inside an
  `<a>`, `stopPropagation()` so `CardShell`'s `onBodyPointerDown` (→
  `onGrab`) never fires. On `click`, if the closest ancestor is an `<a>`,
  `preventDefault()` unconditionally (the webview is the whole app — letting
  a relative-href or `mailto:`/`javascript:` anchor navigate it natively
  would blank out or break the SPA, not open a new browser tab like it would
  on the open web); additionally, if that anchor's `href` passes
  `isExternalHttpUrl`, call `openExternal(href)`. Non-http(s) links are
  therefore inert (no navigation, no `openExternal` call) rather than
  silently navigating the app away.
- **`TerminalCard.tsx`** — add `@xterm/addon-web-links` as a package.json dep,
  pinned `^0.13.0-beta.287` (the exact `-beta.287` suffix already pinned by
  every sibling `@xterm/*` package in this file — `0.13.0` is that package's
  own major/minor line, `beta.287` is the shared suffix; do not use `.288`,
  which is unpinned by every other `@xterm/*` dep here) and
  `term.loadAddon(new WebLinksAddon((_event, uri) => openExternal(uri)))`
  alongside the existing `FitAddon`/`Unicode11Addon`/`WebglAddon` loads. The
  addon owns its own link-range click detection (xterm renders to canvas, not
  DOM anchors); no CardShell interaction is needed here.

### Data Flow

1. User clicks in a card body.
2. **Doc card:** `pointerdown` bubbles to `.doc-prose`; if target is inside
   an `<a>`, propagation stops before reaching `CardShell`'s body handler.
   `click` bubbles the same path; if target is inside an `<a>`, default
   navigation is always prevented (protects the app webview from navigating
   away on a relative/`mailto:`/`javascript:` href); if the anchor's href is
   also `http(s)`, `openExternal(href)` fires.
3. **Terminal card:** `WebLinksAddon` detects a click on a matched URL range
   and invokes its handler with the matched `uri`, which calls
   `openExternal(uri)` directly (no `isExternalHttpUrl` gate needed — the
   addon's default `urlRegex` only matches `http(s)://` URLs).
4. `openExternal` calls `@tauri-apps/plugin-opener`'s `openUrl`, which shells
   out to the OS default-browser opener via the already-registered Tauri
   plugin.

### Interface Contract

```ts
// desktop/src/kit/externalLink.ts
export function isExternalHttpUrl(href: string): boolean;

// desktop/src/ipc/shell.ts
export function openExternal(url: string): Promise<void>;
```

## Alternatives Considered

### Native `pointerdown`/`click` listeners (bypassing React's synthetic system)

`CardShell`'s wheel handler already uses a native listener where it must run
*before* a separate native listener elsewhere (the board's pan handler).
Here there's no such race — `.doc-prose`'s ancestor relationship to
`CardShell`'s body handler is exactly what React's synthetic bubble-and-
`stopPropagation` model already handles (proven by the existing close-button
code), so plain React props are simpler and consistent with precedent.

## Acceptance Scenarios

### Happy Path
- **S1:** Given a doc card rendering `[label](https://example.com)`, when the
  rendered link is clicked, then `openExternal` is called with
  `"https://example.com"` and the click's default navigation is prevented.
- **S2:** Given terminal output containing a bare `https://example.com` URL,
  when that text is clicked, then `openExternal` is called with
  `"https://example.com"`.
- **S3:** Given `isExternalHttpUrl`, when called with `"https://x.com"` or
  `"http://x.com"`, then it returns `true`.

### Edge Cases
- **S4:** Given `isExternalHttpUrl`, when called with a relative href
  (`"#section"`, `"/local/path"`) or a non-http scheme (`"mailto:a@b.com"`,
  `"javascript:alert(1)"`), then it returns `false`.
- **S4b:** Given a doc card rendering a relative-href or `mailto:`/
  `javascript:` link, when that link is clicked, then `openExternal` is not
  called, and the click's default navigation is still prevented (the app
  webview does not navigate away).
- **S5:** Given a doc card with a mix of prose text and a link, when
  clicking prose text outside any `<a>`, then `openExternal` is not called
  and `CardShell`'s existing body-click (select/raise) behavior is
  unaffected.
- **S6:** Given a doc card link, when clicked with the Cmd modifier held,
  then exactly one `openExternal` call is made (same as a plain click) — no
  duplicate open, no thrown error.
- **S7:** Given a doc card link, when a `pointerdown` lands on the link, then
  the event's `stopPropagation` is invoked before it reaches `CardShell`'s
  `onBodyPointerDown` (i.e., `onGrab` is not triggered by the link
  pointerdown).

### Error Scenarios
- **S8:** Given `openExternal` rejects (plugin call fails), when a link is
  clicked, then the click handler does not throw synchronously (the
  rejection is not awaited inline in a way that crashes the render).

## Trade-offs and Limitations

- Terminal-card link clicks may still also raise/select the card via
  `CardShell`'s pre-existing any-click-selects behavior — `WebLinksAddon`
  detects link ranges independently of DOM bubbling (xterm renders to
  canvas, no real `<a>` elements to `stopPropagation` from), so this is not
  practically suppressible without reaching into xterm internals. This is
  harmless (selecting the card on interaction is normal), so it's accepted
  rather than engineered around.
- Middle-click on a doc-card link does not trigger `click` in most browsers
  (it fires `auxclick` instead), so it will not open via this feature's
  handler; the acceptance bar is "no crash / no double-open," not "opens on
  middle-click."
