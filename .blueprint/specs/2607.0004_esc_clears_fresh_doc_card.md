# 2607.0004 ESC clears a fresh doc card's highlight instead of removing it

**Date:** 2026-07-02
**Status:** draft
**Author:** EP Lin

> Fixes GitHub issue #50 — `fix(board): ESC destroys a freshly-opened doc card instead of just clearing its "fresh" state`.

## Context

Tarmac's board holds terminal cards and doc cards. A doc card opened via `tarmac open <path>` lands with `fresh: true` (a visible halo/"✚ now" signal — see `desktop/src/kit/cardChrome.ts`), which is cleared the first time the user interacts with the card (e.g. `onCardMoveEnd`, `desktop/src/App.tsx:1551`, sets `fresh: false` in place).

The window-level ESC handler (`desktop/src/App.tsx`, inside the `keydown` capture-phase listener) runs a ladder of checks — undock, clear toasts, fly-back, then a last rung that looks for a fresh doc card:

```ts
const b = activeBoard();
const fresh = b?.cards.find((c) => c.kind === "doc" && c.fresh) as DocCardModel | undefined;
if (fresh) {
  e.preventDefault();
  e.stopPropagation();
  removeDoc(fresh.path);
}
```

`removeDoc` (`App.tsx:552-569`) is a full teardown: it filters the card out of `board.cards`, drops its `docMeta`/`dockOrder` entries, deletes its cached content, and calls `docClose(path)` over the daemon socket (stops the file watch, drops the provenance edge). This is the same teardown the ✕ affordance uses.

This conflates "I'm done looking at this" (should just clear the highlight) with "remove this card" (should stay behind the explicit ✕ / Cmd+W affordance). Issue #15 (`ad27f4f`, shipped 0.4.0, spec `2606.0004_board_cmdw_close_and_esc_defocus.md`) established exactly this split on the prior Swift build — ESC on a fresh/focused doc card was scoped down to a pure focus/highlight change, never a removal. The Tauri/React rewrite (PR #27, `ed3c92a`) reintroduced the overload when this rung of the ladder was reimplemented.

## Motivation

A user who runs `tarmac open` from an agent's terminal and then presses ESC for an unrelated reason (e.g. to stop a fly-back animation, or out of habit) currently loses the doc card and its provenance edge outright — silent, surprising data loss with no undo. The fix is small and mechanical: swap the teardown call for an in-place state update, matching a pattern (`{ ...c, fresh: false }`) already used elsewhere in the same file.

## Proposed Solution

### Overview

Extract the "clear fresh flag" transform into a small pure function in `desktop/src/kit/`, mirroring the existing `focusedClose.ts` / `termExit.ts` pattern (pure decision logic lives in `kit/` where it's unit-testable; `App.tsx` only wires the result — see repo convention: the React/Tauri shell itself is not unit-tested). Wire the ESC ladder's last rung to call this function via `setActiveCards` instead of `removeDoc`.

### Key Components

- **`clearFreshDoc` — pure card-array transform** (new, `desktop/src/kit/clearFreshDoc.ts`). Given the active board's `CardModel[]`, returns a new array where any doc card with `fresh: true` has `fresh: false`; every other card (non-fresh docs, all term cards) is returned by the **same reference**, matching the unchanged-reference convention already used by `onCardMoveEnd` (`App.tsx:1547-1552`).
- **ESC ladder wiring change** (`App.tsx`, the last rung of the `Escape` branch, ~line 1477-1483). Replace the `removeDoc(fresh.path)` call with `setActiveCards(clearFreshDoc)`. The existing `if (fresh) { e.preventDefault(); e.stopPropagation(); ... }` guard — and therefore the "no fresh card ⇒ ESC still falls through to the terminal" behavior — is unchanged.
- **No changes** to `removeDoc`, the ✕ affordance, or the Cmd+W `focusedClose` routing (`App.tsx` ~1186-1209) — those remain the only paths that actually remove a doc card.

### Data Flow

1. User presses ESC; the capture-phase `keydown` handler runs the existing ladder (undock → toasts → fly-back) and none of those consume the event.
2. `activeBoard()?.cards.find(...)` locates the fresh doc card, if any.
3. If found: `preventDefault`/`stopPropagation` (unchanged), then `setActiveCards(clearFreshDoc)` — the active board's `cards` array is replaced with the output of `clearFreshDoc(cards)`.
4. `clearFreshDoc` maps the array: the matched card becomes `{ ...card, fresh: false }`; all other cards pass through unchanged. The card and its provenance edge stay on the board; `docClose` is never called.
5. If not found: the block is skipped entirely — `preventDefault`/`stopPropagation` are not called, so ESC continues to the next handler (eventually the focused terminal), exactly as today.

### Interface Contract

```ts
// desktop/src/kit/clearFreshDoc.ts
import type { CardModel } from "../board/model";

/**
 * ESC's "dismiss fresh doc" rung: clears `fresh` on any doc card that has it
 * set, leaving every other card (including non-fresh docs and all term
 * cards) untouched — same reference, not a new object — so removal stays
 * reserved for the ✕ / Cmd+W path (`removeDoc` / `focusedClose`).
 */
export function clearFreshDoc(cards: CardModel[]): CardModel[];
```

- Input/output: `CardModel[]` → `CardModel[]` (matches `setActiveCards`'s `(cs: CardModel[]) => CardModel[]` signature exactly — no new state shape).
- Pure: no side effects, no `docClose`, no daemon calls.
- At most one card is expected to have `fresh: true` at a time in current app usage, but the function must handle zero or multiple fresh cards identically (clear all of them) — it must not assume a single match.

## Alternatives Considered

### Clear focus/highlight via a new board-level flag instead of the existing `fresh` field

Rejected — `fresh` already is the highlight signal (`cardChrome.ts`), and `onCardMoveEnd` already establishes the "clear in place" pattern for it. Introducing a second flag would duplicate meaning for no benefit.

### Inline the map in `App.tsx` instead of extracting `clearFreshDoc`

Rejected — the App/UI layer has no unit tests (see repo convention); inlining would make this transform's correctness unverifiable except by manual QA. A one-line pure function costs almost nothing and gets full unit coverage, consistent with `focusedClose.ts`/`termExit.ts`.

## Acceptance Scenarios

### Happy Path
- **S1:** Given a `CardModel[]` containing one doc card with `fresh: true`, when `clearFreshDoc(cards)` is called, then the returned array's matching entry has `fresh: false` with all its other fields (`path`, `frame`, `z`, `ownerTermId`, `repoColor`, `attached`) unchanged.
- **S2:** Given a `CardModel[]` containing a fresh doc card, a non-fresh doc card, and a term card, when `clearFreshDoc(cards)` is called, then only the fresh doc card's object changes — the non-fresh doc card and the term card are returned as the **same object reference** as in the input array (`toBe`, not just `toEqual`).

### Edge Cases
- **S3:** Given a `CardModel[]` with no fresh doc card (all `fresh: false`, or no doc cards at all), when `clearFreshDoc(cards)` is called, then the returned array is element-wise reference-equal to the input (no card object is replaced).
- **S4:** Given a `CardModel[]` containing more than one doc card with `fresh: true`, when `clearFreshDoc(cards)` is called, then every fresh doc card is cleared to `fresh: false` (the function does not assume/enforce a single match).
- **S5:** Given an empty `CardModel[]`, when `clearFreshDoc(cards)` is called, then it returns an empty array without throwing.

## Trade-offs and Limitations

- The App.tsx wiring change (swapping which function is called) is verified by code review + manual repro, not an automated test — consistent with this repo's existing App/UI-shell testing gap, not a new gap introduced by this fix.
- `clearFreshDoc` clears *every* fresh doc card it finds rather than just the first `Array.prototype.find` match the old code used; in current app usage at most one card is ever fresh at a time, so this is not an observable behavior change today, but it does make the function's contract slightly broader than the exact old `find`-based code. This is intentional (see S4) — a pure "clear all" transform is simpler and more robust than replicating a single-match `find`.
