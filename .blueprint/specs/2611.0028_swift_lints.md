# 2611.0028 Swift lints

**Date:** 2026-11-22
**Status:** accepted (spec-evaluator review and advisor scoping, 2026-11-22)
**Author:** EP Lin
**Issue:** #474

## Context

The Swift package is formatted by `swift format` (spec 2611.0026) and has no linter. `make lint` (spec 2611.0027) runs clippy over the Rust workspace through `scripts/check/lint.mjs`, with these exit codes: 0 clean, 1 findings, 2 could not run.

`swift format` also has lint rules. Measured on `main` at `fefdc26`, on the 515 tracked Swift files that the formatter handles:

- With the configuration as it is (31 rules on), `swift format lint` reports 15 findings: `ReplaceForEachWithForLoop` 12, `EndOfLineComment` 2, `OneCasePerLine` 1.
- With ten more rules on, `make fmt` rewrites 3 files (`UseEarlyExits` turns an `if … else { return }` into a `guard` in two of them, and one loses a blank line), and lint then reports 44: `NeverForceUnwrap` 17, `ReplaceForEachWithForLoop` 12, `NeverUseImplicitlyUnwrappedOptionals` 7, `NeverUseForceTry` 3, `EndOfLineComment` 2, and one each of `ValidateDocumentationComments`, `UseWhereClausesInForLoops`, `OneCasePerLine`.

Compiler strictness (warnings as errors, upcoming features) is a separate issue, #475.

## Motivation

A rule that a tool can decide must not depend on a reviewer. A force unwrap or a `try!` is a decision about when the app may crash; today nothing shows where those decisions are.

## Proposed Solution

### Overview

Turn the rules on in `.swift-format`, clear the findings, and make `make lint` cover Swift with the reporter and the exit codes it has for Rust.

### Key Components

- **`.swift-format`** — ten more rules on: `NeverForceUnwrap`, `NeverUseForceTry`, `NeverUseImplicitlyUnwrappedOptionals`, `UseEarlyExits`, `UseWhereClausesInForLoops`, `ValidateDocumentationComments`, `NoEmptyLinesOpeningClosingBraces`, `OmitExplicitReturns`, `AlwaysUseLiteralForEmptyCollectionInit`, `NoLeadingUnderscores`. Two stay off: `AllPublicDeclarationsHaveDocumentation` and `BeginDocumentationCommentWithOneLineSummary` (a maintainer decision).
- **`scripts/check/languages.mjs`** — one table for the formatter check and the lint check: for each language its tracked files, the files it leaves alone (a Swift script that starts with `#!`), and the version gate (swift-format 6.3 or 6.4). `fmt.mjs` and `lint.mjs` both read it, so the two checks cannot disagree about scope.
- **`scripts/check/lint.mjs`** — takes an optional language name. `rust` runs clippy as before. `swift` runs `swift format lint` on the tracked file list (never on a directory: a checkout can hold untracked Swift files), then checks the ignore directives (below).
- **`make lint`** — `ONLY=rust` or `ONLY=swift` limits a run, as for `make fmt`.
- **`lint (swift)` job in `.github/workflows/lint.yml`**, on `macos-26`.

### Suppressing a finding

Swift has no `#[expect]`. `swift format` has an ignore comment, and it behaves like this (measured with 6.4.4):

- `// swift-format-ignore: RuleName` on the line before a statement or a declaration turns that rule off for that node. Formatting stays on. A comment line may stand above it.
- The bare form, `// swift-format-ignore`, also turns formatting off for the node.
- The same text as a trailing comment on the line has no effect.
- A name that is not a rule has no effect and gives no message.
- A directive on a node that no longer has the finding gives no message: a stale directive is not detected.

So the script holds four rules of its own. Each one is a finding:

| Name in the report | What it refuses |
| --- | --- |
| `ignore-without-rule` | the bare form |
| `ignore-file` | `// swift-format-ignore-file`, with or without rule names |
| `ignore-unknown-rule` | a name that is not a key of `rules` in `.swift-format` |
| `ignore-without-reason` | a directive whose previous line is not a `//` comment with text that is not itself a directive |

A directive with more than one rule name (`// swift-format-ignore: A, B`) is checked name by name. The `at` line of a directive finding gives the line and column of the directive's `//`.

### How a finding is cleared

1. `make fmt`, for a rule that the formatter applies (one commit, tool output only).
2. A hand fix that changes no run-time result: a comment moved to its own line, one `case` per line, a `where` clause, a corrected doc comment, and `forEach` to `for` only where the two are plainly equal (a `return` in the closure becomes `continue`; a closure that is passed on, or that the receiver may call later, is not equal).
3. A directive with a reason, for `NeverForceUnwrap`, `NeverUseForceTry` and `NeverUseImplicitlyUnwrappedOptionals`: every fix of those changes when the app stops, which is a decision for the maintainer at each site. The reason states a fact only when the code beside it shows the fact; otherwise it names the follow-up issue.

### Interface Contract

```
make lint               # every language
make lint ONLY=swift    # one language
node scripts/check/lint.mjs [<language>]
                        # exit 0: no finding
                        # exit 1: at least one finding
                        # exit 2: a check could not run
```

For Swift, the tool's own lines go to stderr unchanged, then:

```
✗ lint: 2 findings from swift-format
  at   app/Sources/TarmacApp/BoardView.swift:120:17 NeverForceUnwrap
       app/Sources/TarmacKit/Cull.swift:44:5 ignore-without-reason
  fix  correct each one above; `make fmt` clears a layout finding; to keep one, put the reason in a comment and `// swift-format-ignore: <Rule>` on the next line
  then make lint
```

The `fix` and `then` lines are the same text for every Swift report; they do not change with the kind of finding.

With no language named, each language that has findings or that cannot run writes its own block (clippy's, then swift-format's), and the exit code is 2 if any check could not run, else 1 if any has a finding.

The Swift check cannot run, with exit 2, when: `swift` is not on the `PATH`; swift-format is not 6.3 or 6.4; a rule that `.swift-format` turns on is not a rule of the running swift-format (the `why` line names the rule and the version); or a file does not parse.

## Alternatives Considered

### SwiftLint

More rules, and `// swiftlint:disable` with a reason convention. It is a second tool to install and pin, on every contributor's machine and in CI. The toolchain's own linter covers the rules that were asked for.

### Fix the force unwraps

Each fix replaces a crash with another path (a default, an early return, an error). That changes what the app does, one decision at a time, and must not ride on a lint change.

## Acceptance Scenarios

S1–S9 and S17–S19 are `node --test` tests in a temporary git repository that the test creates. S10–S16 are recorded commands on the real tree.

### Happy Path

- **S1:** Given a repository whose tracked Swift files have no finding, when `node scripts/check/lint.mjs swift` runs, then it exits 0 and writes nothing.
- **S2:** Given `.swift-format` with `NeverForceUnwrap` on and a tracked file that holds `x!`, when the script runs with `swift`, then it exits 1, stderr holds the tool's own line, and the report says `✗ lint: 1 finding from swift-format` with the `at` line `<path>:<line>:<column> NeverForceUnwrap`, a `fix` line and `then make lint`.
- **S3:** Given the file of S2 with a reason comment and `// swift-format-ignore: NeverForceUnwrap` on the two lines before the statement, when the script runs, then it exits 0.
- **S10:** Given the real tree at the head of this change, when `make lint` runs, then it exits 0.
- **S11:** Given the real tree, when `swift test` runs in `app/`, then 2,677 tests pass, the same count as before.
- **S12:** Given a checkout of the parent of this change's formatter commit, with that parent's `.swift-format` already holding the ten new rules, when `make fmt ONLY=swift` runs there, then every tracked file is byte-identical to the same file in the formatter commit.

### Edge Cases

- **S4:** Each of these in a tracked Swift file is a finding with the name shown: the bare directive (`ignore-without-rule`); `// swift-format-ignore-file` (`ignore-file`); `// swift-format-ignore-file: NeverForceUnwrap` (`ignore-file`); a directive that names `NoSuchRule` (`ignore-unknown-rule`); a directive that names `NeverForceUnwrap, NoSuchRule` (`ignore-unknown-rule`); a directive with no comment on the line before it (`ignore-without-reason`); a directive whose previous line is another directive (`ignore-without-reason`); a directive whose previous line is a bare `//` (`ignore-without-reason`). Each case is in its own repository, has a reason comment above it unless the case is about the reason, and gives exit 1 with exactly that one directive finding, its `at` line at the directive's line.
- **S5:** Given an untracked Swift file with a finding and a bare directive, and a tracked Swift script that starts with `#!` and has a finding and a bare directive, when the script runs, then it exits 0.
- **S6:** Given a tracked Rust finding and a tracked Swift finding, when the script runs with no language, then it exits 1 and writes both blocks, clippy's first.
- **S7:** Given a tracked file with a layout finding only (two spaces where the formatter wants one), when the script runs with `swift`, then it exits 1, the `at` line names the rule that the tool's own line names for it, and the `fix` line names `make fmt`.

### Error Scenarios

- **S8:** Given a `swift` on the `PATH` that reports version 5.9.2, when the script runs with `swift`, then it exits 2 with `✗ lint: cannot run swift-format` and a `why` line that names both versions. With no `swift` on the `PATH`, the `why` line is `swift is not on the PATH`.
- **S9:** Given `.swift-format` that turns on a rule the running swift-format does not have, when the script runs with `swift`, then it exits 2 and the `why` line names the rule. Given a language name that is not one, it exits 2 and names the languages it knows.
- **S17:** Given a tracked Swift file that does not parse, when the script runs with `swift`, then it exits 2 with `✗ lint: cannot run swift-format` and a `why` line that names the file.
- **S18:** Given a tracked Rust finding and no `swift` on the `PATH`, when the script runs with no language, then it exits 2 and writes clippy's findings block, then swift-format's cannot-run block.
- **S19:** Given a tracked Swift finding and a clean Rust workspace, when the script runs with `rust`, then it exits 0; with `swift`, it exits 1.

### The rules fire (on the real tree; each one is a knockout that is reverted)

- **S13:** A force unwrap, a `try!` and an implicitly unwrapped optional property, each added to a file under `app/Sources/TarmacKit`, are each named by `make lint ONLY=swift`. The same three in a file under `app/Tests` are recorded as named or not named, and the docs say which.
- **S14:** A `forEach` with a closure literal in `app/Sources` is named `ReplaceForEachWithForLoop`.

### Documents and counts

- **S15:** `docs/coding-style.md` §2 and §4 and `CLAUDE.md` describe `make lint ONLY=swift`, the four directive rules, that a stale directive is not detected, and what S13 showed about test files. No ACTIVE doc says there is no Swift linter. `make docs-check` passes.
- **S16:** The PR body lists every directive this change adds (rule, place, reason), and its row count equals `git grep -c 'swift-format-ignore:' -- '*.swift'` summed over the tree. `lint (swift)` passes in CI on the image's swift-format, and the job log shows its version.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

- Write the tests of the script first (`node --test`, beside the script). The existing 56 tests of `fmt.mjs`, `lint.mjs` and `report.mjs` must pass unchanged, except where a test names a message that this change words differently on purpose.
- The formatter commit holds `make fmt ONLY=swift` output only. Hand fixes and directives go in another commit.
- A fix must not change a run-time result. When in doubt, add a directive with a reason and list the site.
- Do not state a fact in a reason that the code beside it does not show.
- Revert a knockout by restoring the file's bytes, never with `git checkout <file>`.
- Never run `tarmacd`, `tarmac`, `TarmacApp` or `make run`.

## Trade-offs and Limitations

- A stale ignore directive is not detected, unlike a stale `#[expect]` in Rust. The directives are counted in the PR and held by a follow-up issue.
- The "reason" is a convention the script checks only by position and form (a `//` comment with text, not a directive, on the line before). It cannot check that the comment is a reason.
- `swift format lint` also reports layout findings, which `make fmt-check` reports too. A tree that fails one fails the other.
- The CI image has swift-format 6.3.0 and a current Xcode has 6.4.4. This change alters `.swift-format`, so the earlier evidence that the two agree is void; the CI run of this PR is the new evidence, and the rule-name check of S9 makes a missing rule a failure and not a silent pass.

## Decisions

1. **A directive as a trailing comment** (`x!  // swift-format-ignore: Rule`). The tool ignores it, so the comment says something that is not true. The script reports it as `ignore-has-no-effect`. (S20.)
2. **The order of `at` lines.** One list for the tool's findings and the directive findings together, in byte order of the whole line, as `report.mjs` sorts every list.
3. **Open questions.** None; this section holds what was decided after the review.

- **S20:** Given a tracked Swift file with `// swift-format-ignore: NeverForceUnwrap` as a trailing comment on a line that holds a force unwrap, when the script runs with `swift`, then it exits 1 and the report names `NeverForceUnwrap` and `ignore-has-no-effect` for that line.
