# 2609.0017 Say so when a version-mismatch restart cold-spawns terminals

**Date:** 2026-09-17
**Status:** implemented
**Author:** EP Lin
**Issue:** [#172](https://github.com/pingeplin/tarmac/issues/172)

## Context

After a `brew upgrade`, the first relaunch replaces every terminal with a fresh,
empty shell and says nothing ([#172]). This is the documented outcome
(`docs/architecture.md` §6, *Version-mismatch restart* row). The bug is that it
happens silently.

**Verified before writing this spec** (source read on `main` @ 94ce43c by one
investigator plus an independent verifier; line numbers are current, the issue's
are stale):

1. `tarmacd` outlives ⌘Q: `pre_exec` → `libc::setsid()`
   (`desktop/src-tauri/src/bridge.rs:614-619`).
2. `run_connection` reads the first frame. If it is `HelloOk`, it takes
   `daemon_version` and `daemon_pid`; any other frame gives `(None, None)`
   (`bridge.rs:395-398`). `should_restart(CARGO_PKG_VERSION, reported,
   already_restarted)` is `reported != Some(expected) && !already_restarted`
   (`bridge.rs:267-269`). On a mismatch the bridge SIGTERMs `reported_pid` (or
   the tracked child), waits up to 2 s for the socket to vanish, and returns
   `true` **before** `dispatch(app, first_msg)` (`bridge.rs:400-424`). Nothing
   from the stale daemon reaches the frontend.
3. `connection_loop` then sets its local `already_restarted = true` (never
   reset) and reconnects in the same task (`bridge.rs:341-353`). **A value
   recorded in the mismatch branch is therefore always set before any restore
   from the new daemon is dispatched.**
4. The daemon's SIGTERM handler `exit(0)`s (`core/crates/tarmacd/src/main.rs:97-104`).
   Every PTY master closes and every shell gets SIGHUP. The new daemon's
   `Restore.live_terms` is empty (`conn.rs:208-216`), so `plan()`
   (`desktop/src/kit/termRestore.ts:30-36`) returns `coldSpawn` for every tile,
   and `applyRestore`'s first-visit branch mints new ids (`App.tsx:861-887`).
5. The "daemon restarted — terminals lost" toast lives only in the
   `!isFirstVisit` branch (`App.tsx:792-809`). A fresh launch is a first visit,
   so it never fires here. The branches are mutually exclusive per restore
   (`return` at `App.tsx:839`).
6. The mismatch reason is lost in two ways. `emit_status(false, "version
   mismatch / restarting")` is overwritten by the reconnect's
   `emit_status(true, None)` (`bridge.rs:347`, cache at `:92-94`). Tauri 2.11.3
   `emit` also does not buffer: a webview with no JS listener yet simply misses
   the event (`tauri-2.11.3/src/event/listener.rs:269-293`). The bridge connects
   inside `.setup()` (`lib.rs:46-58`, `bridge::start` at `:51`), before JS `listen()`.
7. Non-PTY daemon messages reach the frontend as `serde_json::to_value(&Msg)`,
   an object tagged `"t"`, on the Tauri event `"daemon"` (`bridge.rs:458-469`).
   Only `board_list` is cached (`:96-100`). The frontend type is hand-written
   (`desktop/src/ipc/protocol.ts:48-64`, restore variant `:51-58`). A key added to that JSON never touches
   msgpack or the conformance vectors.
8. **Every ⌘N board yields a `coldSpawn` with nothing lost.**
   New boards are seeded with a term tile whose `term_id` is `None`
   (`term_tile()`, `core/crates/tarmacd/src/state.rs:37`; `Registry::empty()` at
   `:54`, and ⌘N goes through `Boards::create`, `state.rs:303-312`). So "≥1 `coldSpawn`" does not prove
   a terminal was lost. "≥1 tile with a persisted `term_id` absent from
   `live_terms`" does.
9. `daemon_version` is compile-time `env!("CARGO_PKG_VERSION")` (`conn.rs:43`).
   There is no runtime override. `core/Cargo.toml` and
   `desktop/src-tauri/Cargo.toml` are both 0.12.3.

## Motivation

A running agent dies with its shell. The user comes back to an empty shell in
the same spot and no explanation: the board shows a mark with no fact behind it.
The fix is to state the fact the app already has (it SIGTERMed a daemon of a
different version) together with the observed consequence (persisted terminals
came back not live).

## Proposed Solution

### Overview

The bridge records that it replaced a daemon. From then on it annotates every
`restore` JSON it emits with that record. The fact then travels *with* the
restore that triggers `applyRestore`, so event ordering and the missing listener
at launch no longer matter. On the first-visit path, a pure kit function decides
whether that restore warrants a notice. `App.tsx` pushes the notice through the
existing restart latch, so one restart produces at most one restart toast until
something re-arms that latch (a disconnect or a webview reload; see Trade-offs).

Out of scope: keeping PTYs alive across the restart (`docs/backlog.md`,
*Daemon-restart PTY re-parenting*), the `open_log` truncation note in #172
(appending would break the "bounded by one session" invariant; rotating is a
separate decision), and the pre-existing second-restore race (see Trade-offs).

### Key Components

- **`DaemonReplaced` record — `desktop/src-tauri/src/bridge.rs`.** Held on
  `Bridge` as `Mutex<Option<DaemonReplaced>>`. `from` is the `reported_version`
  seen in the mismatch branch, which may be `None` (a daemon with no version, or
  a non-`HelloOk` first frame). The record is created once, on the first
  mismatch, with `to: None`, and never cleared (the latch allows one restart per
  process). `to` is filled from a connection that **proceeds** past the version
  check: while a record exists and its `to` is `None`, a proceeding connection
  sets `to` to its `reported_version`. Once `to` is `Some`, later connections
  leave it unchanged. A proceeding connection that reports no version leaves
  `to` as `None`, so a later proceeding connection may still fill it. With no
  record, a proceeding connection creates nothing.
  `to` is set before that connection dispatches any frame, so the connection's
  `restore` already carries it. It is not the app's version: if the respawned
  daemon still mismatches, `to` names what is actually running.
- **`annotate_restore` — `bridge.rs`, pure.** Given a dispatched JSON value and
  the current record, it returns the value with a `daemon_replaced` key added
  when the tag is `restore` and the record is present. Otherwise the value is
  returned unchanged. `dispatch` calls it before `app.emit("daemon", …)`.
- **`restartNotice` — new `desktop/src/kit/restartNotice.ts`, pure.** Decides
  whether a first-visit restore gets a toast, and with what text.
- **Wiring — `desktop/src/App.tsx`, `desktop/src/ipc/protocol.ts`.** Add the
  optional key to the `restore` type. In the first-visit branch, after `plans`,
  call `restartNotice` with `daemonRestartToastedRef.current` as
  `alreadyNotified`. If it returns non-null, set the ref and `pushToast`; the
  component makes no latch check of its own. Reusing that ref (instead of adding a
  second latch) is what prevents a double toast when the reconnect-path toast
  already fired for the same restart. That happens when the app was running
  during the upgrade, its daemon died, and the respawn mismatched.

### Data Flow

1. The bridge connects to the stale daemon. `HelloOk.daemon_version` is 0.12.2
   and the app is 0.12.3, so `should_restart` is true.
2. The bridge sets `DaemonReplaced { from: Some("0.12.2"), to: None }`, SIGTERMs,
   and returns `true`.
3. The bridge reconnects to the new daemon (`HelloOk` 0.12.3). The connection
   proceeds, so `to = Some("0.12.3")`.
4. The new daemon's `restore` passes through `dispatch` → `annotate_restore`,
   which adds `daemon_replaced: { from: "0.12.2", to: "0.12.3" }`.
5. `applyRestore` runs its first visit and computes `plans`, then calls
   `restartNotice(msg.daemon_replaced, tileTermIds, liveTerms,
   daemonRestartToastedRef.current)`. The result is a notice.
6. `App.tsx` sets the ref and pushes the toast. Later first visits of other
   boards return `null` because the latch is already set (a ⌘N board is `null`
   regardless, S4).

### Interface Contract

Bridge → webview JSON (bridge-only; **not** part of the msgpack wire protocol,
`docs/protocol.md` unchanged):

```
restore JSON gains, only after a version-mismatch restart this process:
  "daemon_replaced": { "from": string | null, "to": string | null }
absent otherwise. No other message is annotated.
```

Rust (signatures, not implementations):

```rust
struct DaemonReplaced { from: Option<String>, to: Option<String> }
fn annotate_restore(value: serde_json::Value, replaced: Option<&DaemonReplaced>) -> serde_json::Value
// Called by the proceeding branch of run_connection; applies the `to` rule above.
// Name is free; the shape (record + reported version in, record updated) is fixed.
fn note_proceeding(record: &mut Option<DaemonReplaced>, reported: Option<&str>)
```

TypeScript:

```ts
// desktop/src/ipc/protocol.ts — restore variant
daemon_replaced?: { from: string | null; to: string | null };

// desktop/src/kit/restartNotice.ts
export interface RestartNotice { title: string; body: string }
export function restartNotice(
  replaced: { from: string | null; to: string | null } | undefined,
  tileTermIds: (string | null)[],   // parseTiles(...).termTiles.map(t => t.termId)
  liveTerms: Set<string>,
  alreadyNotified: boolean,
): RestartNotice | null
```

`restartNotice` returns non-null **iff** `replaced` is present, `alreadyNotified`
is false, and at least one `tileTermIds` entry is a non-null id not in
`liveTerms`. Let `lost` be that count.

- **title:** `tarmacd restarted: {from} → {to}`. A null version renders as
  `unknown`. The arrow does not claim a direction, because a mismatch is `!=`,
  not "older".
- **body:** `{lost} terminal on this board was restarted` when `lost === 1`,
  otherwise `{lost} terminals on this board were restarted`.
- **icon, chips:** follow the existing restart toast (`"¶"`, `[]`).
- **Length:** the body must fit one line of `.tm-toast-body` (280 px, `nowrap`, ellipsis; `desktop/src/theme/chrome.css`). Agent-driven QA found a longer wording ("…restarted as fresh shells") cut off, so the body was shortened.

## Alternatives Considered

- **Emit a dedicated `daemon-upgraded` event.** It would be lost on a fresh
  launch (no listener yet, and Tauri does not buffer) and would race the
  restore. Caching and replaying it adds the same coupling the annotation gets
  for free.
- **Reuse the `daemon-status` reason.** It is overwritten by the reconnect's
  `emit_status(true, None)` before any listener can read it (Context 6).
- **Trigger on "≥1 `coldSpawn`".** False positive on every ⌘N board (Context 8).
- **Frontend `getVersion()` for the "to" version.** It gives the app's version,
  not the running daemon's, which is wrong when the respawn still mismatches.
- **Read the stale daemon's `board_list.running` before SIGTERM** to prove
  terminals were live. That is more honest about "were running", but it means
  reading frames the mismatch branch deliberately skips. Persisted ids that
  come back not live are already an observed fact. Deferred.

## Acceptance Scenarios

### Happy Path

- **S1 (kit):** Given `replaced = {from:"0.12.2", to:"0.12.3"}`, tiles `["t1","t2"]`,
  `liveTerms = {}`, not yet notified, when `restartNotice` runs, then it returns
  title `tarmacd restarted: 0.12.2 → 0.12.3` and body
  `2 terminals on this board were restarted`.
- **S2 (bridge):** Given a `restore` JSON value and a record
  `{from: Some("0.12.2"), to: Some("0.12.3")}`, when `annotate_restore` runs,
  then the result carries `daemon_replaced: {from:"0.12.2", to:"0.12.3"}` and
  every original key is unchanged.

### Edge Cases

- **S3 (kit):** Given `replaced` absent (normal cold start, e.g. after a reboot)
  and tiles `["t1"]` with `liveTerms = {}`, when `restartNotice` runs, then `null`.
- **S4 (kit):** Given `replaced` present and tiles `[null]` (a fresh ⌘N board),
  when `restartNotice` runs, then `null`.
- **S5 (kit):** Given `replaced` present, tiles `["t1","t2"]`, `liveTerms = {t1,t2}`
  (the stale daemon was never actually killed), when `restartNotice` runs, then `null`.
- **S6 (kit):** Given `replaced` present, tiles `["t1","t2",null]`, `liveTerms = {t1}`,
  when `restartNotice` runs, then body is `1 terminal on this board was restarted`.
- **S7 (kit):** Given `replaced = {from:null, to:"0.12.3"}` and one lost tile, when
  `restartNotice` runs, then title is `tarmacd restarted: unknown → 0.12.3`.
- **S7b (kit):** Given `replaced = {from:"0.12.2", to:null}` and one lost tile, when
  `restartNotice` runs, then title is `tarmacd restarted: 0.12.2 → unknown`.
- **S8 (kit):** Given S1's inputs but `alreadyNotified = true`, when
  `restartNotice` runs, then `null`.
- **S9 (kit):** Given `replaced` present and tiles `[]`, when `restartNotice` runs,
  then `null`.
- **S10 (bridge):** Given a `board_list` JSON value and a present record, when
  `annotate_restore` runs, then the value is returned unchanged.
- **S11 (bridge):** Given a `restore` JSON value and no record, when
  `annotate_restore` runs, then there is no `daemon_replaced` key.
- **S12 (bridge):** Given a record `{from: None, to: None}` (neither daemon
  reported a version), when `annotate_restore` runs on a restore, then
  `daemon_replaced` is present with both `from` and `to` keys present as JSON
  `null`. A missing version must not read as "no restart".
- **S13 (bridge):** Given a record `{from: Some("0.12.2"), to: None}` and a
  proceeding connection reporting `Some("0.12.2")` (the respawn is still stale),
  when `note_proceeding` runs, then the record is
  `{from: Some("0.12.2"), to: Some("0.12.2")}`, not the app's version.
- **S13b (bridge):** Given no record (`None`) and a proceeding connection
  reporting `Some("0.12.3")` (an ordinary connect with matching versions), when
  `note_proceeding` runs, then the record is still `None`.
- **S13c (bridge):** Given a record `{from: Some("0.12.2"), to: Some("0.12.3")}`
  and a later proceeding connection reporting `Some("0.12.9")`, when
  `note_proceeding` runs, then the record is unchanged.
- **S13d (bridge):** Given a record `{from: Some("0.12.2"), to: None}` and a
  proceeding connection reporting `None` (no version), when `note_proceeding`
  runs, then the record is unchanged (`to` stays `None`, and is not filled
  with the app's version).
- **S13e (bridge):** Given a record `{from: Some("0.12.2"), to: None}` and a
  proceeding connection reporting `Some("0.12.3")` (Data Flow step 3), when
  `note_proceeding` runs, then the record is
  `{from: Some("0.12.2"), to: Some("0.12.3")}` (`from` is preserved).

### Manual QA (dev channel; record in `desktop/qa/upgrade-restart-notice-qa.md`)

Use the worktree's `make run` and its `.dev/` socket only. Never touch the
installed app, and never `pkill`.

**These need a human operator.** `tarmac dev` has no verb for ⌘Q, ⌘N, or
board switching, its snapshot does not report toasts, and synthetic input
does not reach the window. A toast lives for 7 s (`TOAST_TTL_MS`,
`desktop/src/kit/toasts.ts:10`), and more than 3 at once evicts the oldest.
Watch right after launch, or take a region screencapture, so that a toast you
missed is not recorded as "no toast".

Run S14 → S15 → version revert → S16 → S17 in that order.

- **S14:** `make run`. On board A, keep its terminal. Press ⌘N to create board
  B and let its shell spawn. Switch back to A and add a second terminal
  (⌘T). Confirm `.dev/state.json` shows `active` = A, A with exactly 2 and B
  with exactly 1 `kind:"term"` tiles carrying a non-null `term_id`. Note `lsof -t .dev/tarmacd.sock`. Quit (⌘Q; the daemon survives).
  With no `make run` live, bump `version` in `core/Cargo.toml`
  (`[workspace.package]`) and `desktop/src-tauri/Cargo.toml` (e.g. 0.12.4), then
  `make run`. Expected: exactly one toast titled `tarmacd restarted: …`, with
  title `tarmacd restarted: 0.12.3 → 0.12.4` and body
  `2 terminals on this board were restarted`; both A cards hold fresh shells;
  the socket's pid differs from the one noted. A "tarmacd connection lost"
  toast (body "version mismatch / restarting") may also appear if JS mounted
  in time; that is expected. **Known pre-existing race (see Trade-offs):** if
  A's fresh cards turn dead right after spawning and only one
  `tarmacd restarted` toast shows, record it and file it separately. It is not
  a failure of this spec.
- **S15:** In the same app session as S14, switch to board B (its first visit
  this session, with a persisted `term_id` that is not live). Expected: B's card
  holds a fresh shell and no second toast appears. Then press ⌘N and visit the
  new board. Expected: no toast.
- **Version revert (between S15 and S16):** Switch back to board A and confirm
  `.dev/state.json` shows `active` = A (`make kill-daemon` sends SIGKILL, so a
  save still inside the 150 ms persist debounce is lost), then quit. With no `make run` live,
  revert both `Cargo.toml` files and both lockfiles (`core/Cargo.lock`,
  `desktop/src-tauri/Cargo.lock`), then `make kill-daemon` (the surviving daemon
  is 0.12.4). Do not revert while `make run` is live: an edit under
  `desktop/src-tauri` relaunches the app against the 0.12.4 daemon and triggers
  a second, unrelated mismatch restart.
- **S16 (negative control):** With app and daemon both 0.12.3 and board A
  active with its two persisted terminals, quit if running, `make kill-daemon`,
  `make run`. Expected: the terminals cold-spawn and no toast titled
  `tarmacd restarted: …` appears.
- **S17 (regression):** With the S16 app running, `make kill-daemon`. Expected:
  the existing "daemon restarted — terminals lost" toast appears exactly once
  (the existing "tarmacd connection lost" toast also appears, as before this
  change), and no toast titled `tarmacd restarted: …` appears.

## Trade-offs and Limitations

- **Terminals are still lost.** This only makes the loss visible. Re-parenting
  is backlog.
- **"Were restarted", not "were running".** The app sees persisted ids that
  came back not live. A card whose shell had already exited before the upgrade
  is counted too.
- **The count covers only one board**: the first board visited since the latch
  was armed that has lost terminals (normally the board restored at launch).
  Other boards' persisted terminals are lost too (hence "on this board"), but
  their first visits find the latch set, so they cold-spawn without a notice
  (S15).
- **The versions can read `0.12.3 → 0.12.3`.** Suppose the app was running
  during the upgrade and its daemon died. The respawned binary is the new
  cask's daemon, which mismatches the old app, so the app kills and respawns
  it, and `from == to`. The reconnect toast normally takes the latch first. If
  the active board had no live cards, the first visit to another board shows
  the equal versions. This is true to the `!=` check, not a bug.
- **Webview reload re-arms the JS latch.** The bridge record is never cleared,
  so after a reload a later first visit with lost ids can toast again. Release
  builds do not reload in normal use.
- **A disconnect also re-arms the JS latch.** `handleStatus` resets
  `daemonRestartToastedRef` on every connected → disconnected transition
  (`App.tsx:1171-1175`). After a later socket drop in the same process, if the
  reconnect-path toast does not take the latch, the first visit to a board not
  yet visited, whose persisted terminals are not live, shows the upgrade notice
  again. It counts only terminals on a board never restored in this process,
  so none of them were revived after the upgrade restart.
- **Pre-existing race, not fixed here.** If the connect-time restore lands
  between `listen()` and `frontend_ready`, the replayed `BoardSwitch` produces a
  second restore. That restore takes the reconnect path with empty
  `live_terms` and marks the fresh cards dead. The shared latch suppresses the
  duplicate toast but not the dead marking. File it separately if S14 hits it.
- **Only the first mismatch per process is described.** The `already_restarted`
  latch allows exactly one restart per process.
