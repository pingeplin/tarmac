## Context

An HTML card is a web view that holds a host page (`card-host.html`). The author's file runs in `<iframe sandbox="allow-scripts">` at `tarmac-card://doc/<path>?v=<mtime>`. New data reaches the document today only when the HTML file is rewritten: the address changes with the file's change time, the frame loads again, the JavaScript state is lost and the web view is covered until the new document is on screen (`HTMLCardView.refresh`, `loadDocument`).

What the code does today (`468baf1`):

- **Shim → host page → app.** `card_shim.js` posts `{tarmac:"started", source}` as its first word and `{tarmac:"ready", meta}` once at `DOMContentLoaded` (`postReady`); `meta` is the content of `meta[name="tarmac-zoom"]`. `card-host.js` hears only the frame's own window, keeps `started` for itself, drops a card's `shown`, and passes on any other object whose JSON text is at most 1,000 characters (`carried`, `small`); a larger one is dropped whole. It numbers loads: `asked` is the app's number for the source the frame was last given, `started` the last one whose document has started. A load starts at the shim's `started` word (unless it names `replaced`, the source before) or at the frame's `load` event, whichever is first (`documentStarted`). Its own word `shown` carries that number. `ready` carries none, and the card's own script can post one. Within one host page the app never gives the frame the same address twice in a row (`HTMLCardView.refresh` returns when the address is unchanged), so `replaced === null` happens only at the first load of a host page.
- **App.** `CardConsole.parse` turns a message into `CardConsole.Message` (`.ready(meta:)`, `.shown(load:)`, …). `HTMLCardSession.handle` returns effects; `HTMLCardView.received` applies them. `HTMLCardSession.reloaded()` numbers the next load (`LoadCount`).
- **App → document.** `HTMLCardView.post` runs `tarmacCard.post(<json>)`; the host page posts it into the frame; the shim accepts a message only from `window.parent`. `CardHostMessage` has `zoom`, `cull`, `scrollTo`, `fonts`. A text that is not the app's own goes as an argument of `callAsyncJavaScript` (`WKWebView.runInCardWorld(_:arguments:)`), never spliced into a script.
- **Culling.** `HTMLCardView.setCulled` records `session.culled` and posts `cull`. Every card of a board that is not in the window is culled.
- **Daemon.** A doc is registered per board (`Registry.docs`, `DocInfo`). The watcher watches each doc's parent directory, not recursive (`watch.rs`); a wake carries no detail. `BURST` (100 ms) after a wake, `docs::report_changes` stats every doc of the active board, and each restored doc not read yet on any board (`Daemon::look`), and pushes a `file_event {path, mtime_ms}` for each doc of the active board whose `FileStamp` (mtime, length, inode) differs from what was seen. `Registry::take_changes`, `hold` and `take_untold` look up `Registry.docs` only. `doc_refresh` stats one doc of the active board, takes it as seen, and pushes whenever the file exists, changed or not (`docs::stat_and_push`, `Registry::refresh`). `Boards::registry_mut` falls back to the active board for an unknown board id. On a board switch the changes of the new active board are sent after its `restore` (`conn::change_and_send_active_board`). `seen`, `untold` and `unread` are in memory only.
- **App, `file_event`.** `AppController.handleFileEvent` finds the doc of that path on every board it has built and calls `docBody.refresh(lastChangedMs:)`.
- **App, cards and boards.** An `HTMLCardView` knows its doc path, not its board. The controller wires each card when it lands it (`landDocCard`). On a reconnect a board that was built already keeps its cards (`applyRestore` → `reconcile`): their documents do not load again. Requests made while the link is down are queued and sent after the next `hello_ok` (`DaemonClient`).
- **Files.** `FileBytes.read(path:)` reads a regular file of at most `FileBytes.sizeCap` (64 MiB); it opens the path it is given, following links. `FileBytes.resolved(path:)` resolves a path (`realpath`). `ImageProtocol.respond(path:file:read:)` is the kit's pattern for "judge the resolved file, then read that file": it takes the resolve result and a `read` closure, so a test injects both. `StrictJSON.isValid(_:)` is the kit's JSON check (serde_json's grammar, at most 127 levels); today it is internal and used by `AppPrefs` only.
- **Doc paths are canonical.** `docs::handle_open` resolves the path before it registers the doc, so the path of a card is a resolved path.

## Motivation

A dashboard that is rewritten many times a minute flashes on every update and cannot keep state in its script. Issue #306 has the full case. This phase gives the state mode: the document names one JSON file beside it, and each change of that file reaches the loaded document as an event.

## Proposed Solution

### Overview

The document names its data file with a meta tag. The shim puts that name in its `ready` word. The host page stamps the first `ready` of each load with the load's number. The app judges the name with a path rule, registers the data file with the daemon (`doc_data`, new on the wire), and the daemon reports the file as it reports a doc: a `file_event` at once, and one for each change. On each such `file_event` the app reads the file off the main thread, checks it, and hands the text to the shim, which parses it, keeps it and dispatches `tarmac:data`.

### Key Components

- **Shim (`card_shim.js`).** Reads `meta[name="tarmac-data"]` for `ready`. Defines `window.tarmac`. Handles the host message `data`.
- **Host page (`card-host.js`).** Stamps `ready` with the load number; a card cannot stamp one itself.
- **Path rule (new, `TarmacKit`, pure).** From the HTML file's path and the name: the data file's absolute path, or a refusal with its reason. No file-system call.
- **Session (`HTMLCardSession`, and what it needs beside it in `TarmacKit`).** Decides, from a stamped `ready`, what the card's data file now is; and, from "the file changed", "the read ended", "culled / not culled" and "reloaded", when to read and what to deliver. All of it pure and tested; the view is wiring.
- **Read (new, `TarmacKit`, pure).** Resolve, check the resolved path, read, check the bytes; it takes `resolve` and `read` as arguments, as `ImageProtocol.respond(path:file:read:)` does, and gives the text or a reason.
- **View (`HTMLCardView`).** Runs the read off the main thread with `FileBytes.resolved` and `FileBytes.read`, and runs the delivery call.
- **Data registrations (new, `TarmacKit`, pure).** Which data path each card (board id + doc path) registered. It answers: the cards to tell for a `file_event` path; the `doc_data` to send again after a reconnect; and it forgets a card that is closed or a board that is removed.
- **Controller (`AppController`).** Wiring only: sends `doc_data`, feeds the registrations, hands a `file_event` to the cards they name, sends again at `hello_ok`.
- **Wire (`tarmac-protocol`, `Messages.swift`).** One new message, `doc_data`.
- **Daemon (`tarmacd`).** Keeps a doc's data file with the doc entry, in memory; includes it in its looks; reports it.
- **Docs.** `docs/protocol.md` (message, vectors), `docs/architecture.md` (message table, HTML cards), `tarmac-cli/src/GUIDE.md` (how a card takes data).

### Data Flow

1. The document is parsed. At `DOMContentLoaded` the shim posts `{tarmac:"ready", meta, data, source}`; `data` is the name, or `null`, and `source` is the document's own address, as in its `started` word.
2. The host page sees the first `ready` after the start of load *N* that does not come from the document that load replaced, and passes it on with `load: N`. Any other `ready` is passed on with no `load`.
3. The app takes the data name only from a `ready` whose `load` is the card's current load. It applies the path rule. A refusal is one error line in the card's console, and the card has no data file.
4. The app sends `doc_data {board_id, path, data}` for an accepted name. When the current load names no file (or a refused one) and the card has a registered file, it sends `doc_data {board_id, path}` with no `data`, which clears it.
5. The daemon records it and, when the doc is on the active board and the file exists, pushes `file_event {path: <data path>, mtime_ms}` at once. After that it pushes one for each change it sees in a look.
6. The app gets a `file_event` whose path is a registered data path and tells each card that registered it.
7. The card, when it is not culled, reads the file off the main thread: resolve, check that the resolved file is in the HTML file's directory, read the resolved file with the 64 MiB cap, check UTF-8 and `StrictJSON`.
8. The app hands the text to the host page as an argument; the host page posts `{tarmac:"data", text}` into the frame; the shim parses it, sets `window.tarmac.data` and dispatches `tarmac:data` on `window`.

### Interface Contract

**For the author of a card** (goes in `GUIDE.md`):

```html
<meta name="tarmac-data" content="stats.json">
<script>
  addEventListener("tarmac:data", e => render(e.detail));
  if (window.tarmac.data !== undefined) render(window.tarmac.data);
</script>
```

- `tarmac-data` names one file. The first such meta in the document at `DOMContentLoaded` is the one read; a meta added later is not seen. A relative name is taken from the directory of the HTML file. The file must be in that directory: a name that leads to another directory, a subdirectory included, is refused in this phase.
- `tarmac:data` is a `CustomEvent` on `window`. `detail` is the parsed content. It fires after each load of the document (when the file exists and is valid) and after each change of the file that the app delivers. The app does not compare the content with what it delivered before: a change that leaves the same bytes, and the answer to a `doc_data` that is sent again (a reload, a reconnect), fire the event again.
- `window.tarmac` is defined before any script of the page runs. `window.tarmac.data` is `undefined` until the first delivery, then the same value as the last event's `detail`.
- A page that gives `window.tarmac` another value keeps its own: the shim does not write to it, and the events still fire.
- A card that is out of view gets no state. It gets the latest content once when it is back in view.
- Not delivered, with the document keeping what it has: a file that is gone, is not a regular file, is over 64 MiB, is not UTF-8, or does not pass strict JSON. Strict JSON is `StrictJSON`'s rule: RFC 8259 in UTF-8, at most 127 levels of arrays and objects, no byte-order mark, no number too large for a double (`1e400`), no unpaired surrogate escape (`"\ud800"`), not empty. White space before and after the value is allowed; any JSON value is allowed at the top (`3`, `"x"`, `null`).
- A data file that is not there when it is registered writes no console line: the daemon reports nothing for a file that is not there. The content comes when the file is made. (A read that loses a race with a delete does write a line: S30.)

**Shim ↔ host page ↔ app** (inside the app, not on the wire):

```
card → host page   {tarmac:"ready", meta:<string|null>, data:<string|null>, source:<string>}
host page → app    {tarmac:"ready", meta, data, load:<int>}     first ready after the start of a load
                   {tarmac:"ready", meta, data}                 any other; a `load` key from the card is removed
                   (`source` is for the host page alone: it is taken off before the message is measured and passed on)
app → host page    tarmacCard.data(text)                        text as an argument of callAsyncJavaScript
host page → card   {tarmac:"data", text:<string>}
```

- The shim sends `data: null` when there is no such meta and when its content is empty. It also sends `data: null` when the name does not fit: when the JSON text of `{tarmac, meta, data}` is over 1,000 characters with the name and not over without it. In that case it posts one `error` console entry that says so, through its own relay (a page that replaced `console.error` does not stop it). So a long name costs the card its data and not its `ready`.
- The host page's 1,000-character bound is on the JSON text of the card's message without `source`, and it stays: a `ready` over it is dropped whole, as today, and its cull, fonts and zoom go with it. The shim's own `ready` is over it only when its `tarmac-zoom` meta alone makes it so, as today. `source` is not counted: a card's address holds its percent-encoded path, and a long path must not cost a card the `ready` it gets today.
- "The first `ready` after the start of load *N*": the first `ready` the host page hears from the frame after `started` became *N* (see Context) and before the app asks for load *N+1*, whose `source` is not `replaced` (the source the frame had before this load). The host page's `started` rule has the same test: the frame's `load` event names no document, so the document that was replaced can still speak after `started` became *N*, and its `ready` must not take the stamp. Before the first load is asked, no `ready` is stamped. A `ready` that the host page drops for its size does not use up the stamp. A card's own script can post a `ready` before the shim's; if it is the first after the start, it takes the stamp. It names one file for that load all the same.
- A `ready` with no `load`, or with a `load` that is not the card's current load, does what `ready` does today (cull, fonts, zoom, mode) and has no say on the data file.

**Path rule** (`TarmacKit`, pure):

```
dataFile(html: "/a/b/dash.html", name:) -> .file("/a/b/<leaf>") | .refused(path, reason)
```

- The name is joined to the HTML file's directory when it is relative, and normalised with no file-system call (`.` and `..` components are resolved in the text; an empty component, as in `.//x`, is dropped as POSIX drops it).
- Accepted: the result's parent directory is the HTML file's directory, and the result has a last component.
- Refused, each with its own reason; the refusal carries the normalised path, and the reason text does not repeat it: a result in a directory under the HTML file's directory (`"in a subdirectory: not read yet"`), a result anywhere else (`"outside this card's directory"`), and a name that names no file (`"names no file"`): an empty name, a name whose result is the directory itself, a name that ends in `/` (it names a directory), a name that holds a NUL character (no path can).

**At each read** (a pure `TarmacKit` function that takes `resolve` and `read`; the view runs it off the main thread with `FileBytes.resolved` and `FileBytes.read`): the data path and the HTML file's path are resolved (design, Paths: "the resolved paths of both files"); the resolved data path's parent must be the resolved HTML file's parent; `read` is called with the resolved data path, never with the name. A resolved path elsewhere, and a resolve of either path that fails, are refused with one console line, and `read` is not called. No resolve and no read has a time limit of its own in this phase (choice 21).

**Console lines.** A refusal or a failed read is one `error` entry in the card's console, of the form `tarmac-data: <path>: <reason>`, where `<path>` is the normalised data path. The same line is not written twice in a row for one card: it is written again only after a delivery, or after any other entry in that card's console. A reload does not reset this: the console is kept across reloads (`HTMLCardSession.reloaded`).

**Wire** (additive; both codecs; app → daemon; no reply):

```
{t:"doc_data", board_id:<str>, path:<str>, data:<str>}    the doc `path` on board `board_id` reads the file `data`
{t:"doc_data", board_id:<str>, path:<str>}                 it reads none
```

- Rust: `Msg::DocData { board_id: String, path: String, data: Option<String> }`, `data` omitted when `None`.
- Swift: a `Message` case with the same three fields, encoded byte-for-byte as Rust encodes it (`RustEncoderParityTests`).
- Two new conformance vectors, 14 and 15 in `docs/protocol.md`, in both codecs. Both codecs are tested against these bytes (key order as Rust's `to_vec_named` writes the variant: `t`, `board_id`, `path`, `data`):

  14. `{t:"doc_data", board_id:"board-0", path:"/a/dash.html", data:"/a/stats.json"}`

          84 a1 74 a8 64 6f 63 5f 64 61 74 61 a8 62 6f 61 72 64 5f 69
          64 a7 62 6f 61 72 64 2d 30 a4 70 61 74 68 ac 2f 61 2f 64 61
          73 68 2e 68 74 6d 6c a4 64 61 74 61 ad 2f 61 2f 73 74 61 74
          73 2e 6a 73 6f 6e

  15. `{t:"doc_data", board_id:"board-0", path:"/a/dash.html"}` (no `data`: the doc reads none)

          83 a1 74 a8 64 6f 63 5f 64 61 74 61 a8 62 6f 61 72 64 5f 69
          64 a7 62 6f 61 72 64 2d 30 a4 70 61 74 68 ac 2f 61 2f 64 61
          73 68 2e 68 74 6d 6c
- A daemon that does not know the type ignores it (existing rule). An app with an older daemon gets no `file_event` for a data file, and the card gets no data.

**Daemon behaviour for `doc_data`:**

- Unknown board, unknown doc on that board, a `data` that is not absolute, or a `data` whose parent directory is not the doc's parent directory (compared component by component, as bytes; no file-system call): ignored (a debug line), nothing recorded. An unknown board does not fall back to the active board (unlike `registry_mut`).
- A `doc_data` with a `data` replaces the doc's data file; one with no `data` clears it.
- Recorded with the doc entry, in memory only. It is not in `state.json`, and it is gone when the doc is closed or its board is deleted.
- The data file is stat'ed in the looks that compare docs for a change: `report_changes` (for the active board) and the look at a board switch, create or connect (`change_and_send_active_board`, for the board made active). `doc_refresh` does not have to look at it. A change is a `FileStamp` that differs from the one last seen for that data path on that board, as for a doc. A file that is gone sends nothing and is a change when it is back.
- **At once:** when the doc is on the active board and the file exists, a `file_event` for the data path is pushed in answer to every `doc_data` that names it, the same name again included. The file is then taken as seen, as `doc_refresh` takes a doc: the next look sends nothing unless the file changes again.
- A data `file_event` that reaches no app does not have to be held (no `untold` is needed): the app sends `doc_data` again after it connects, and the answer at once brings the content.
- **Background board:** nothing is pushed. When that board is made active, a `file_event` for the data path follows the `restore` if the file exists and differs from what was seen for it; a file registered while the board was in the background has nothing seen, so it is reported.
- **One event for one path in one look:** a data path that is also a doc of the board, or that two docs of the board name, gives one `file_event` for a change.
- No directory is watched or counted for a data file: its directory is its doc's, which is watched already.

**App behaviour:**

- `doc_data` is sent on the first stamped `ready` of each load that names an accepted file, also when the name is the one already registered: the daemon's answer brings the content to the new document.
- After a reconnect (`hello_ok`), `doc_data` is sent again for each card, on every built board, that has a data file.
- A `file_event` carries no board. It goes to every card, on every built board, that has that path as its registered data file; a culled card only marks itself (below). A path that is also a doc is handled as a doc too.
- One read at a time for each card. The session says when a read starts: its answers to "the file changed", "the read ended" and "culled / not culled" carry the read to run, so the view keeps no rule of its own. A change that arrives during a read marks the card "read again", once. A change that arrives while the card is culled marks it too; the read starts when the card is no longer culled.
- A read's result is delivered only when the card's data file and load are still the ones the read was started for, and the card is not culled. A valid result that ends while the card is culled is not delivered; the card is marked "read again", so it reads and delivers once when it is back in view (Gate, decision 18).
- When a card is closed, its registration is forgotten in the app; `doc_close` (existing) makes the daemon forget it.

## Acceptance Scenarios

Automated scenarios are S-numbered. Each names where its test lives: **JS** = the shim or the host page run under XCTest through JavaScriptCore (`CardShimTests`, `CardHostScriptTests`); **Kit** = `TarmacKitTests`; **Rust** = `tarmac-protocol` tests or a `tarmacd` integration suite. Live scenarios (L-numbered) need a window and are run on a dev channel; they are not in `make test`.

What the harnesses need first (test code only; none is a reason to skip a scenario):

- `CardShimTests`' stand-in window answers `querySelector` for `tarmac-zoom` only, and has no `CustomEvent` and no `dispatchEvent`. S1–S9 add a `tarmac-data` meta to the stand-in, a `CustomEvent` class that keeps `type` and `detail`, and a `window.dispatchEvent` that calls the `addEventListener` listeners of that type.
- `CardHostScriptTests`' `cardWindow` has no `postMessage`. S14 adds one that records what it is given.
- A Rust "no `file_event` comes" check (`none_within`, `quiet`) passes for the wrong reason when no look runs. Each such scenario first forces a look of the board: it changes a doc that is open in the same directory and waits for that doc's `file_event`, then checks that none came for the data path.

### Shim (JS)

- **S1:** Given a document with `<meta name="tarmac-data" content="stats.json">`, when `DOMContentLoaded` fires, then the `ready` posted to the parent has `data: "stats.json"`, the `meta` it has today, and `source` equal to the document's address (the `source` of its `started` word).
- **S2:** Given a document with no such meta, or with an empty `content`, when `DOMContentLoaded` fires, then `ready` has `data: null`.
- **S3:** Given a `tarmac-data` content that makes the JSON text of `{tarmac, meta, data}` exactly 1,000 characters, when `DOMContentLoaded` fires, then `data` is the content and no error message is posted. With one character more, `ready` has `data: null` and one `{tarmac:"console", level:"error"}` message about the name was posted, also when a page script replaced `console.error` before `DOMContentLoaded`. A content of `"` characters is measured as JSON writes it (two characters each).
- **S4:** Given the shim has run and no data came, when a page script reads `window.tarmac.data`, then it is `undefined` and `window.tarmac` is an object.
- **S5:** Given a listener for `tarmac:data` on `window`, when the parent posts `{tarmac:"data", text:'{"n":1}'}`, then the listener runs once with an event of type `tarmac:data` whose `detail` is deep-equal to `{n:1}`, and `window.tarmac.data === detail`.
- **S6:** Given two deliveries `'{"n":1}'` then `'[2]'`, then the listener ran twice in that order and `window.tarmac.data` is `[2]`.
- **S7:** Given the same `data` message posted by a window that is not the parent, then no event fires and `window.tarmac.data` does not change.
- **S8:** Given a delivery whose `text` is not a string, or does not parse, then no event fires, nothing is thrown out of the handler, and `window.tarmac.data` keeps its value.
- **S9:** Given a page script that set `window.tarmac = {mine: true}`, when a delivery comes, then the listener runs with the parsed content and `window.tarmac` is still `{mine: true}` with no `data` key.

### Host page (JS)

- **S10:** Given load 3 was asked for and its document said `started`, when the frame posts `ready`, then the app gets `ready` with `load: 3` and the frame's `meta` and `data`.
- **S11:** Given S10, when the frame posts a second `ready`, then the app gets it with no `load` key.
- **S12:** Given a `ready` from the frame that has its own `load: 99`, then what the app gets has the page's number when it is the first of the load, and no `load` when it is not; never 99.
- **S12a:** Given load 1 started, when the frame posts a `ready` whose JSON text without `source` is exactly 1,000 characters and whose `source` is 2,000 characters long, then the app gets it with `load: 1` and with no `source` key. When, in a new load, the frame posts a `ready` whose JSON text without `source` is 1,001 characters, then the app gets nothing; and when the frame then posts a short `ready` in that load, the app gets it with that load's number.
- **S13:** Given load 4 was asked for and its document has not started, when the frame (the document of load 3) posts `ready`, then the app gets it with no `load`; and when the document of load 4 then starts and posts `ready`, the app gets `load: 4`.
- **S13b:** Given load 3 had source A, load 4 was asked for with source B, and the frame's `load` event fired before the document of load 4 spoke, when the frame posts `ready` with `source: A`, then the app gets it with no `load`; and when the frame then posts `ready` with `source: B`, the app gets `load: 4`.
- **S13a:** Given no load was asked for yet, when the frame says `started` and posts `ready`, then the app gets `ready` with no `load`.
- **S14:** Given `tarmacCard.data("…text…")`, then the frame's window is posted `{tarmac:"data", text:"…text…"}`.

### Path rule and parse (Kit)

- **S15:** Given the HTML file `/a/b/dash.html`, the names `stats.json`, `./stats.json`, `.//stats.json`, `x/../stats.json` and `/a/b/stats.json` each give the file `/a/b/stats.json`.
- **S16:** The names `sub/stats.json` and `/a/b/sub/stats.json` are refused as a subdirectory, and the refusal carries `/a/b/sub/stats.json`.
- **S17:** The names `../stats.json`, `/etc/passwd`, `sub/../../x.json` are refused as outside the card's directory.
- **S18:** The names `""`, `.`, `./`, `x/..`, `stats.json/` and `"st\u0000ats.json"` are refused as naming no file.
- **S18a:** Paths are judged as bytes. `sub/` followed by a combining mark and `x.json` is refused as a subdirectory; `../` followed by a combining mark is refused as outside; a card whose own file name starts with a combining mark still reads beside itself; and a directory written with a precomposed letter is not the directory written with the letter and a combining mark. The read's directory check (S30) is made the same way.
- **S19:** `CardConsole.parse` reads `ready` with `data` a string, `data` null or absent (no data file), and `load` an integer or absent; a `data` or a `load` of another type makes the message unparseable, as a bad `meta` does today.

### Session and delivery decisions (Kit)

- **S20:** Given a card at load *N*, when a `ready` with `load: N` and `data: "stats.json"` is handled, then the effects have what `ready` gives today and one that registers `/…/stats.json`.
- **S21:** Given S20, when a second `ready` (no `load`) with another `data` is handled, then no registration effect is given.
- **S21a:** Given S20 and a read of the file in progress, when a second `ready` stamped with the same load names another file, then no registration effect is given, the read's text is still delivered, and the next change reads the first file.
- **S22:** Given a `ready` with a `load` that is not the current one, then no registration effect is given.
- **S23:** Given a `ready` with `load: N` whose name the path rule refuses, then no registration is given, the console gains one error entry that names the path and the reason, and the console is reported as changed.
- **S24:** Given a card whose load *N* registered a file, when it is reloaded and the `ready` of load *N+1* names no file, then one effect clears the registration. The same when it names a file that the path rule refuses (and the console gains that line). When load *N+1* names the same file, the effect registers it again. When it names another accepted file, the effect registers that one.
- **S25:** Given a card that never had a data file, when a `ready` names none, then there is no registration effect at all.
- **S26:** Given a registered, not culled card with no read in progress, when the file changes, then a read starts.
- **S27:** Given a read in progress, when the file changes two times, then no second read starts; when the read ends, exactly one more read starts.
- **S28:** Given a culled card, when the file changes, then no read starts; when the card is no longer culled, one read starts. With no change while it was culled, none starts.
- **S28a:** Given a card that registered one file and has a change of it waiting (the card is culled, or a read is in progress), when the card is reloaded and the new load names another file, then no read of the new file starts when the card is back in view or when the old read ends; one starts when the new file is reported as changed.
- **S29:** Given a read that ended with valid text, when the card's load and data file are those of the read, then the text is delivered. When the card was reloaded, or its data file changed, in between, then nothing is delivered. Two reads in a row that end with the same text give two deliveries.
- **S29a:** Given a read that started while the card was not culled, when the card is culled and then the read ends with valid text, then nothing is delivered; when the card is no longer culled, one read starts, and its text is delivered.
- **S30:** Given the read function with a stand-in `resolve` and `read`: when `resolve` leads the name to a file in another directory, then `read` is not called, and the result is a refusal; when `resolve` leads it to another file in the same directory, then `read` is called with that resolved path; when `resolve` fails for either path, the result is a refusal and `read` is not called. Given a read that failed (each of: resolved outside the directory, not a regular file, too large, not UTF-8, not strict JSON), then nothing is delivered and the console gains one error entry `tarmac-data: <path>: <reason>`.
- **S31:** Given the same failure two times in a row, then the console gains one entry, not two. After a delivery, the same failure gives an entry again. After any other console entry of the card (a `console.log` of the document), the same failure gives an entry again. A reload between the two failures, with no other entry and no delivery, gives no second entry.
- **S32:** The check of a read's bytes: valid UTF-8 that passes `StrictJSON` gives the text; bytes that are not UTF-8 are refused; JSON 128 levels deep is refused and 127 is taken; a top-level scalar (`3`, `"x"`, `null`) is taken; white space before and after the value is taken; an empty file, a UTF-8 byte-order mark before `{}`, `1e400` and `"\ud800"` are refused.

### Data registrations (Kit)

The scenarios below are numbered after S46 so that S1–S46 keep their numbers.

- **S47:** Given card `(board-0, /a/dash.html)` registered `/a/stats.json`, card `(board-1, /a/dash.html)` registered it too, and card `(board-0, /a/other.html)` registered `/a/x.json`, when a `file_event` for `/a/stats.json` is routed, then the answer is the first two cards and not the third. A path that no card registered gives no card.
- **S48:** Given the registrations of S47, when the link connects again (`hello_ok`), then the `doc_data` to send are exactly one for each registered card, each with its board, doc path and data path. A card that cleared its file is not in them.
- **S49:** Given the registrations of S47, when card `(board-0, /a/dash.html)` is closed, then S47's routing gives only the board-1 card, and S48 does not name the closed card. When board-1 is removed, its cards go too.
- **S50:** Given a card registered `/a/stats.json`, when it registers `/a/y.json`, then a `file_event` for `/a/stats.json` is routed to no card, and one for `/a/y.json` is routed to it.

### Wire (Rust and Kit)

- **S33:** The two new vectors decode to `doc_data` with and without `data`, and survive encode → decode, in both codecs.
- **S34:** The Swift encoder's bytes for both forms equal Rust's.
- **S35:** `doc_data` is in the message tables of `docs/protocol.md` and `docs/architecture.md` (`make docs-check` passes; it fails when the variant is missing from either).

### Daemon (Rust integration)

- **S36:** Given an HTML doc on the active board and a data file that exists beside it, when the app sends `doc_data` with that file, then the app gets a `file_event` for the data path with the file's mtime.
- **S36a:** Given S36, when a look of the board is forced (another doc beside it is changed) and the data file is not changed, then no second `file_event` for the data path comes.
- **S37:** Given S36, when the data file is changed with one write (the harness's `edit`), then the app gets exactly one more `file_event` for the data path (one, then none within the `quiet` window). A truncate and a later write can fall in two looks, so "exactly one" is asked of one write only.
- **S38:** Given S36, when the app sends the same `doc_data` again, then it gets a `file_event` for the data path again.
- **S39:** Given a `doc_data` for a file that does not exist, then no `file_event` comes after a forced look; when the file is made, one comes.
- **S40:** Given S36, when the app sends `doc_data` with no `data` and the file is then rewritten (a look runs: the directory is watched for the doc), then no `file_event` for the data path comes.
- **S40a:** Given S36, when the app sends `doc_data` that names another file beside the doc, then it gets a `file_event` for the new file; when the first file is then rewritten, none comes for it.
- **S41:** Given a `doc_data` whose `data` is in another directory (a subdirectory, a parent, elsewhere), or is relative, or whose doc is unknown on that board, or whose board is unknown (the doc being on the active board, so that a fall-back to the active board would be seen), then no `file_event` for that path comes at once, nor after the file is rewritten and a look of the active board is forced.
- **S42:** Given S36 and a second doc open in the same directory (so the directory stays watched), when the HTML doc is closed (`doc_close`) and the data file is rewritten, then no `file_event` for the data path comes after a forced look.
- **S43:** Given two HTML docs on the active board that name one data file, and the `file_event`s that answer the two `doc_data` have come, when the file is changed with one write (`edit`), then exactly one `file_event` for the data path comes. The same with a data file that is also an open doc of the board.
- **S44:** Given a doc on a board that is in the background, when `doc_data` names an existing file, then no `file_event` for it comes; when that board is made active, a `file_event` for the data path comes after the `restore`.
- **S45:** Given a registered data file on the active board, when the app switches to another board, the file is rewritten, and the app switches back, then a `file_event` for the data path comes after the `restore`.
- **S46:** Given a registered data file, when a later change makes the daemon save its state (for example a `layout`, waited for with `wait_for_state`), then `state.json` has no trace of the data path.

### Live (dev channel, hand-run with evidence kept under `.dev/`)

- **L1:** A card with a data file is opened; the document shows the file's content with no rewrite of the HTML.
- **L2:** The data file is rewritten 100 times, slower than the watcher's look: the document's own load counter stays at 1, a counter in its script reaches 100 less the changes that fell in one look, and the last content shown is the last written.
- **L3:** During L2 the card is never covered (the web view's alpha stays 1; no `shown` word after the first).
- **L4:** A symlink beside the HTML file that leads to a file in another directory is named as the data file: nothing of that file reaches the document, and the console names the path and the reason. A `../` name and a subdirectory name: the same, with their reasons.
- **L5:** The card is scrolled out of view, the file is rewritten 3 times, the card is brought back: the document gets exactly one `tarmac:data`, with the last content.
- **L6:** The board is switched away, the file is rewritten, the board is switched back: the document gets the new content.
- **L7:** The dev daemon is stopped and started with the card open: after the reconnect, a rewrite of the file reaches the document.
- **L8:** A 10 MB JSON file: the content arrives; the time the app's main thread is held by one delivery is measured and recorded. A hold over 16 ms is reported as a finding, not as a failure of this spec.
- **L9:** A file that is not valid JSON, then is made valid: the console gains one line for the bad content, and the valid content arrives.
- **L10:** A data file whose strings hold `"`, `\`, U+2028, U+2029, `</script>` and `${x}`: the document's `detail` is deep-equal to the file's content (the text reached the shim as an argument, not as script text).

## Choices made in this spec

The design left these to the spec ("For the specs", phase 1). None changes the product's direction.

1. **An old load's `ready`** (S13, S22): passed on without a stamp, so it does what it does today and names no file.
2. **A document that sends its own frame to another card URL, or reloads itself,** gets no new load number, so its `ready` is a second one of the load and names no file (S11). It gets the data of the card's registration when the file next changes, not at once. If the first document left before its own `ready` (a script that navigates during the parse), the next document's `ready` is the first of the load and names the file; the name is judged against the card's own HTML file, so this names one file in that directory and no more.
3. **`StrictJSON` refuses more than 127 levels**, which `JSON.parse` takes. The app's check stands: the content is not delivered and the console says so (S32). `StrictJSON` becomes usable by this feature inside the kit; its rules do not change.
4. **A data file that is also an open doc, and two cards on one data file**: one `file_event` for a change; the app routes it to every card that registered the path, and to the doc card (S43).
5. **A `file_event` that arrives while the card reloads**: the read's result is dropped unless the load and the data file still match (S29); the new document's `ready` brings the content again.
6. **The same `doc_data` again** records nothing new and watches nothing; it is answered with a `file_event` (S38).
7. **After a switch back**, `restore` carries no data stamp; the data `file_event` follows it (S44, S45).
8. **A page's own global named `tarmac`** is the page's (S9).
9. **`doc_data` for a board in the background** is recorded and answered at the switch (S44).
10. **`ready` is sized by the shim** (S3): it leaves the name out when the name is what takes the message over the host page's bound, so that a long name costs the data and not the `ready` (S12a).
11. **The daemon checks the directory too** (S41): a `doc_data` from any app can make it stat only a name in the doc's own directory. A link of that name is followed by the stat (only the stamp reaches the app); the app's read refuses it (S30).
12. **The resolved file is the one read.** Between the resolve and the read a file can be replaced by a link; the read then opens the resolved path, which was judged. A link put in the place of the resolved path itself in that window is not caught. Accepted: the local process that can do it can read the file itself.

Added by the review of this spec (2026-11-12); none changes the product's direction:

13. **A read that ends while the card is culled** is dropped and read again when the card is back in view (S29a), so a culled card gets no state (Gate, decision 18).
14. **A `file_event` goes to every built board's cards that registered the path** (S47), as a doc's does (`handleFileEvent`). A card of a board in the background is culled, so it only marks itself.
15. **A data `file_event` that reaches no app does not have to be held**: the `doc_data` sent again after the reconnect brings the content.
16. **The console line's repeat rule spans reloads**, since the console does (S31). "Twice in a row" is read as two entries in a row in that card's console.
17. **The routing table is a kit type** (S47–S50), so the controller holds no rule (`docs/coding-style.md`, placement table).
18. **A `ready` dropped for its size does not use up the stamp** (S12a): the host page measures before it stamps.
19. **The path rule's texts**: the refusal carries the path and the reason does not repeat it, so the console line names the path once. A name that ends in `/` or holds a NUL names no file (S18); the NUL rule follows `CardProtocol.rejectingNul`.
20. **The stamp cannot be taken by the document that was replaced** (S13b). `ready` carries `source`, and the host page does not stamp a `ready` whose source is `replaced`, the test it already has for `started`. Whether WebKit fires the old document's `load` event after the new source is asked for was not measured; with this rule the answer does not matter.
21. **No time limit on the resolve or the read in this phase.** The design's draft gave the resolve one. The read is off the main thread and one at a time for each card, so a volume that does not answer holds that one card's data and nothing else; the HTML file itself is read with no limit today (`CardSchemeHandler`), and a card on such a volume shows nothing anyway. The design doc is changed to say so.
22. **A `ready` whose name does not fit keeps its cull, fonts and zoom** (choice 10): this replaces the fixed 512-unit rule of the first draft.
23. **The file swapped between the resolve and the read** stays as choice 12 says: it is the kit's pattern for images (`ImageProtocol.respond`), with the same window. A check on the open descriptor's own path would close it; it is noted for phase 3, where a subdirectory makes the check wider.
24. **The reason texts and the two extra refusals** (a name that ends in `/`, a name with a NUL) are taken as the review wrote them (choice 19).
25. **A change that waits is for the file it was seen for** (S28a). A registration drops the "read again" mark: the daemon reports the newly named file in answer to the `doc_data`, so nothing is lost, and a file that is not there is not read (and writes no line). Found while the code was cleaned up; the first implementation carried the mark over.
26. **Paths are split and compared as bytes** (S18a). The first implementation worked on Swift strings, which join a `/` to a combining mark after it and compare by canonical equivalence: a file in a subdirectory passed as a file beside the card. Found by the referee's review; fixed test-first.
27. **The session holds "the first stamped `ready` of a load" too** (S21a), and does not rest on the host page for it. A read's outcome is then the card's whenever its load is still the current one.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

Project rules that bind the work (`CLAUDE.md`, `docs/coding-style.md`):

- **TDD, red first.** Each new test is seen to fail on the unmodified tree before the change that makes it pass. Keep the red record under the worktree's `.dev/`.
- **Decisions live in `TarmacKit`.** The AppKit shell (`HTMLCardView`, `AppController`) has no unit tests by design: it is wiring. If a rule ends up in the shell, move it to the kit and test it there. Do not widen visibility for a test.
- **`card_shim.js` and `card-host.js` have tests** (JavaScriptCore): change them test-first.
- **Wire: additive only**, in both codecs in the same change, with the two vectors and the encoder parity test. Rust encodes with `rmp_serde::to_vec_named`.
- **Daemon locks** are never held across `.await`; nothing is pushed from inside `Daemon::look`.
- Do not `cargo fmt`. Match the code around the change. No comment that restates the code.
- Never run a daemon by hand, and never kill one by name; daemons run only inside the test harness, or through `make run` with its pinned sockets.
- `make test` must pass. The docs named in Key Components are part of the change.

Write tests to these principles (the same ones `/verify` scores against):

- **Behavioral over structural** — assert observable output and effects, not internals; the suite must survive refactoring.
- **Every test can fail** — no copy-pasted expected values, no asserting a constant, no tautologies.
- **Deterministic, isolated, readable** — inject clocks, no cross-test state, setup inline.

## Security Considerations

- **What a card can now read.** One file at a time, in the directory of its own HTML file, when its content is strict JSON. The user's act of consent is `tarmac open` on the HTML file. An HTML card is not a network boundary (`docs/architecture.md`, design decision 13), so what a card reads it may also send away. That is the reason for the directory rule and it is accepted (design, Trade-offs).
- **The name comes from the card's own document**, which is not trusted: it is judged in the text (no disk), again on the resolved path at each read, and the daemon checks the directory by itself.
- **A card cannot stamp a load.** Only the first `ready` of a load, as the host page counts it, names a file, so one document cannot make the app register file after file.
- **The content never enters a script as text**: it is an argument of `callAsyncJavaScript`, then a posted message; the shim uses `JSON.parse`.
- **Console lines** carry a path that the card's script chose. They are capped by `CardConsole` as every entry is.

## Trade-offs and Limitations

- **State is never faster than the watcher**: a change is seen at the next look, 100 ms or more after the one before. Changes inside one look are one delivery.
- **A subdirectory is refused** until phase 3. *(Changed by [2611.0005](2611.0005_html_card_data_file_subdirectory.md), 2026-11-13: a file in a directory under the HTML file's is read and its directory watched, and a hidden name below that directory is refused, beside the HTML file too.)*
- **One data file for each card.** A document that needs two reads one file that holds both.
- **The whole file is read and parsed for each change.** The only bounds are the 64 MiB cap and one read at a time.
- **A card on a board that is in the background gets no state** until the board is back: the daemon looks at the active board only.
- **Deeper than 127 levels is refused**, though a browser takes it.
- **A handler that draws in a frame callback** draws when the card is on screen; state comes only to a card that is not culled, so this matters less than it does for events (phase 2).
- **An older daemon** ignores `doc_data`: the card gets no data and no error.
- **A volume that does not answer** holds the data of the cards whose files are on it, with no console line (choice 21).
- **A name with a typo is silent**: a data file that is not there writes no console line (Open Questions).

## Open Questions

Nothing stops the work. Two things are left for after it:

- **A data file that is not there writes no console line** (the author contract). A typo in the name gives silence, as the design has it. A hint line would change what the author of a card sees, so it is the user's to decide; it is named in the hand-over.
- **L8's figure** decides whether the delivery path needs a second look before phase 2.
