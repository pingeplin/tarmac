# 2611.0031 Checks from hooks

**Date:** 2026-11-22
**Status:** accepted (spec-evaluator review and advisor scoping, 2026-11-22)
**Author:** EP Lin
**Issue:** #483

## Context

The checks exist as `make` targets, and CI runs them: `fmt-check`, `lint`, `arch-check`, `docs-check`, `test`. Nothing runs them earlier, so a finding is seen after a push.

Two places can run them where the work happens: Claude Code hooks (an agent's edits and turns) and git hooks (a commit, a push). Measured facts that the design rests on, with Claude Code 2.1.330 in a throwaway repository and the current hooks documentation:

| Fact | Source |
| --- | --- |
| A `PostToolUse` hook may rewrite the edited file. Claude Code then tells the model: "PostToolUse hook modified … after your edit (likely a formatter). Your next Edit will not fail with a stale-file error, but if its old_string targets a region the hook reformatted, Read the file first." | measured |
| Exit 2 from a `PostToolUse` hook shows the hook's stderr to the model; the edit stays. The hook cannot undo it. | measured, docs |
| `PostToolUse` does not fire for an Edit that failed, or for a file that Bash or another program changed. | measured, docs |
| `tool_input.file_path` is an absolute path. | measured, docs |
| A running session picks up a changed `.claude/settings.json` by itself. | docs |
| Project hooks and user hooks for one event are merged and all run. | docs |
| `Stop` has no matcher. `SubagentStop` fires for a subagent and carries `agent_type`. Exit 2 from either keeps the agent going with the stderr as its next instruction. | docs |
| The `if` filter of a `PreToolUse` hook is best-effort. | docs |
| One Swift file: format 0.16 s, lint 0.21 s. `arch-check` 0.10 s, `docs-check` 0.09 s. The whole tree: `fmt-check` 7 s, Swift lint 1.6 s, clippy 0.4 s warm and 12 s cold, the compiler-warning lint 22 s. | measured |

## Motivation

A finding that reaches an agent while it still has the file open costs one edit. The same finding after a push costs a CI round. The hooks move each check to the earliest point where the one who made the change can still fix it.

## Proposed Solution

### Overview

Every hook calls a script under `scripts/check/` that already has one definition. The hook files hold no rule of their own: `.claude/settings.json` and `lefthook.yml` only say when a script runs.

### Key Components

- **`scripts/check/hook.mjs`** — the adapter for Claude Code. It reads the hook's JSON on stdin and takes the event name as its argument: `edit`, `stop`, `bash`.
- **`.claude/settings.json`** — three hooks: `PostToolUse` for `Edit|Write`, `Stop`, and `PreToolUse` for `Bash`. No `SubagentStop` hook.
- **`lefthook.yml`** — `pre-commit`, `commit-msg`, `pre-push`. `make setup` installs it.
- **`scripts/check/commit-msg.mjs`** — the form of a commit message.
- **`scripts/check/staged.mjs`** — what `pre-commit` runs.

### What each hook does

**After an edit (`hook.mjs edit`).** For the file in `tool_input.file_path`, when it is in a git repository, not ignored, exists, and is of a language that `fmt.mjs` knows (else exit 0, no output): format it in place, lint it if a lint can judge one file (only Swift's can), and run `arch-check` in the file's repository. A finding, or a check that could not run, is written to stderr and the hook exits 2, so that the model sees it. The edit is never undone. An input with no `tool_input.file_path` exits 0 with no output.

**At the end of a turn (`hook.mjs stop`).** The files it checks are the changed files of the repository: tracked files that differ from `HEAD` in the index or the working tree, plus untracked files that git does not ignore. A deleted file is not checked. On those files: the format check (`--check`, never `--write`) and the Swift lint; then `arch-check` and `docs-check` on the whole repository. It does not run clippy or the compiler-warning lint.

- **The set of findings** is the stderr text of each check that exited 1, joined in the fixed order fmt, Swift lint, arch, docs. Its key is the SHA-256 of that text. The text of a check that could not run (exit 2) is not part of the set. So a change to the files named, to a lint's `at` line, or to the rule changes the key; the same findings in the same places give the same key.
- A non-empty set blocks the stop (exit 2) when its key differs from the key in the session's state file, and then writes its key to that file. When the key is the same, the hook writes the note line and the report to stderr and exits 0. The file holds one key only, so findings A, then B, then A again block three times.
- An empty set exits 0 and removes the session's state file.
- A check that could not run is reported on stderr and does not block. With findings as well, the exit code comes from the findings only.
- `stop_hook_active` does not change any of the above.
- A state file that is missing or cannot be read counts as no key. A state file that cannot be written does not change the exit code.

**Before a Bash call (`hook.mjs bash`).** It refuses a command that kills a Tarmac process by name: on this machine that can end the installed app and every terminal it owns. The command text is split into simple commands at `;`, `&&`, `||`, `|` and newlines. A simple command is refused when its first word, after any `sudo` and `NAME=value` words, is `pkill` or `killall`, and one of its later words holds `tarmac` in any letter case. The refusal is exit 2 with a reason on stderr that names `make kill-daemon`. Any other command passes with exit 0 and no output.

**`pre-commit`.** For the staged files: the format check and the Swift lint on those files; clippy when a staged file is a Rust file; `arch-check`; `docs-check`. It reads the working tree, not the index (see *Trade-offs*).

**`commit-msg`.** Lines that start with `#` are ignored. The subject is the first line that is left.

- The subject passes when it matches `^(feat|fix|refactor|perf|test|docs|chore|release)(\([^()\s]+\))?!?: \S`, or starts with `fixup! ` or `squash! `. This list of types is closed; it is the list in the report below.
- A generated subject also passes: one that starts with `Merge ` (git's merge subject) or with `Revert "` (git's revert subject).
- Every message except a merge (subject starts with `Merge `) must hold a line, from column 0, in the form `Signed-off-by: <name> <<email>>`, as `dco-check.mjs` reads it. The email of that line must equal the author's or the committer's, as `dco-check` requires.
- A failure exits 1 and writes a `✗ commit-msg:` report to stderr.

**`pre-push`.** `make test`.

### Why these choices

- **No clippy at the end of a turn.** The first step of a red test is a `todo!()` stub, which clippy refuses, so a clippy gate there would block every red phase. clippy also waits on cargo's build lock while a test runs. It runs at `pre-commit`, where a stub must be gone.
- **No `SubagentStop` hook.** A subagent that only reads (a referee, a verifier) must not be told to fix a tree it may not edit. A subagent that edits gets the edit hook; the parent's turn gets the stop hook.
- **Once for each set of findings.** A stop hook that blocks on every stop holds an agent on findings it cannot fix. Claude Code itself lets an agent go after 8 blocks with no tool call between them, and never while the agent keeps calling tools.

### Interface Contract

```
node scripts/check/hook.mjs edit   < hook JSON     exit 0, or 2 with a report on stderr
node scripts/check/hook.mjs stop   < hook JSON     exit 0, or 2 with a report on stderr
node scripts/check/hook.mjs bash   < hook JSON     exit 0, or 2 with the reason on stderr
node scripts/check/commit-msg.mjs <file>           exit 0, or 1 with a report on stderr
node scripts/check/staged.mjs                      exit 0, 1 findings, 2 a check could not run
```

The reports are the scripts' own, unchanged (`✗ fmt: …`, `✗ lint: …`, `✗ arch: …`). The stop hook adds one line before them when it does not block:

```
(the same findings as at the last stop of this session: reported, not blocking)
```

A commit message that is refused:

```
✗ commit-msg: the subject is not `type(scope): summary`
  at   fix the thing
  why  types in use: feat, fix, refactor, perf, test, docs, chore, release
  fix  write the subject as, for example, `fix(board): close a doc card on ⌘W`
  then git commit
```

The state of the stop hook is one small file for each session: `<git dir>/tarmac-hooks/<session id>`, where `<git dir>` is `git rev-parse --absolute-git-dir` of the repository that the stop hook checks (in a linked worktree, that worktree's own git directory) and `<session id>` is the input's `session_id`. It is not tracked and it holds one SHA-256 key only. A `session_id` that does not match `^[A-Za-z0-9_-]+$` is not used as a file name: the hook then acts as if no state file exists and writes none.

## Alternatives Considered

### Block every stop while a finding is left

Simple, and nothing unfixed is ever reported as done. Not chosen as the default: in this repository's workflow an agent's turn often ends while another agent is in the middle of an edit, and a read-only agent cannot fix anything. Commit, push and CI stay hard gates.

### Report only; never block a stop

No agent is ever held. Not chosen: an agent then ends its turn on findings in its own files.

### Hand-written `.githooks/`

No tool to install. Not chosen: lefthook gives the staged file list, runs the commands of a hook in parallel, and is one YAML file.

## Acceptance Scenarios

All scenarios other than the five recorded runs and "Docs name the six hooks and no verify" are `node --test` tests. The hook inputs are the JSON that Claude Code 2.1.330 sent in a real run, with paths and ids replaced. "Main history subjects pass the subject rule", "Hooks install and run in a linked worktree", "Headless Claude run sees the hook reports", "Subagent worktree hooks are recorded" and "Check test time is recorded" are recorded runs. "Docs name the six hooks and no verify" is checked by reading the documents and by `make docs-check`.

### The edit hook

- **Edit hook formats a new Swift file:** Given a real `PostToolUse` input for a `Write` of a new, untracked Swift file with a layout fault, when `hook.mjs edit` runs, then the file is formatted, the hook exits 0 and writes nothing.
- **Edit hook reports a Swift lint finding:** Given the same for a Swift file with a force unwrap (the rule on in `.swift-format`), then the file is formatted, the hook exits 2 and stderr holds the lint's report with the `at` line of the unwrap.
- **Edit hook ignores files it cannot judge:** Given an input whose file is outside any repository, is ignored by git, does not exist, or is of no language, then the hook exits 0 and writes nothing.
- **Edit hook reports an arch violation:** Given a `TarmacKit` file that now imports AppKit, then the hook exits 2 with the `arch` report.
- **Edit hook leaves an unparseable Rust file:** Given a Rust file that does not parse, then the hook exits 2 with `✗ fmt: cannot run rustfmt` and the file is unchanged.

### The stop hook

- **Stop hook with no changed file passes:** Given a tree with no changed file, when `hook.mjs stop` runs, then it exits 0 and writes nothing.
- **Stop hook blocks once per session:** Given a changed Swift file with a finding, then the first run exits 2 with the report; a second run for the same session, with nothing changed, exits 0, and stderr holds the note and the same report; a run for another session id exits 2.
- **Stop hook blocks again when findings change:** Given "Stop hook blocks once per session" after the first run, when the findings change (a Swift lint finding moves to another line, or a format finding is in another file), then the next run exits 2.
- **Stop hook does not lint Rust:** Given a changed Rust file with a `todo!()`, then the hook exits 0: no lint of the stop hook judges it.
- **Stop hook reports a check that cannot run:** Given a check that cannot run (a Swift file changed, and a `swift` on the `PATH` of another version), then the hook exits 0 and stderr holds the "cannot run" report.

### The Bash hook

- **Bash guard refuses a kill by name:** Each of these commands is refused with exit 2 and a reason that names `make kill-daemon`: `pkill tarmacd`, `pkill -f tarmac-app`, `killall TarmacApp`, `sudo pkill -9 tarmacd`, `cd x && pkill -f TarmacApp`. Each of these passes: `make kill-daemon`, `kill 1234`, `pkill -f some-other-thing`, `echo pkill tarmacd is forbidden`, `git log --grep pkill`.

### Git hooks

- **Commit message hook checks subject and sign-off (`commit-msg`):** these subjects pass: `fix(board): close a doc card`, `feat: editable docs`, `release: 0.24.0`, `feat!: drop a key`, `fixup! fix: y`, `Merge branch 'main' into x`, `Revert "fix: y"`, each with a `Signed-off-by:` line. These fail with a report: `fix the thing`, `Fix(board): x`, `fix(board) x`, `fix: ` with no summary, a good subject with no `Signed-off-by:` line (a merge excepted).
- **Staged script checks staged files only (`staged.mjs`):** Given a staged Swift file with a finding and an unstaged one with a finding, then the script exits 1 and names the staged file only. Given a staged Rust file with a `todo!()` in a workspace whose lint table refuses it, then it exits 1 and names `clippy::todo`. Given nothing staged, it exits 0.
- **Lefthook runs one command per hook:** Given `lefthook.yml`, when it is parsed, then each of `pre-commit`, `commit-msg` and `pre-push` runs exactly one command, and each command is a `make` target or a script under `scripts/check/`.

### Recorded runs

- **Main history subjects pass the subject rule:** Every subject of `git log` on `main` passes the subject rule of `commit-msg.mjs`. The record gives the count, and each subject that does not pass, if any.
- **Hooks install and run in a linked worktree:** In a throwaway clone with `core.hooksPath` set to an absolute path, as this repository has: `make setup` installs the hooks, a commit with a bad subject is refused, and a commit made in a linked worktree of that clone runs the same hooks with that worktree's `lefthook.yml`. The record says what was observed for each.
- **Headless Claude run sees the hook reports:** In a throwaway repository with these three hooks, a headless Claude run that writes a file with a finding, ends its turn, and is asked to end it again: the record gives what the model was shown at each point. Expected: after the write, the edit hook's report; at the first stop, a block with the report; at the second stop with the same findings, the note line and no block.
- **Subagent worktree hooks are recorded:** Whether a subagent that runs in its own worktree gets the project hooks: observed in a headless run, or listed as not verified with the reason.
- **Check test time is recorded:** `make check-test` time before and after this change. A record only; no limit is set.

### Documents

- **Docs name the six hooks and no verify:** `CLAUDE.md`, `docs/workflow.md` and `CONTRIBUTING.md` each name: `make setup` as the step that installs the git hooks; for each of the six hooks, its event and what makes it block; that the edit hook does not lint Rust and the stop hook runs no clippy; and `--no-verify` as the way a git hook is skipped. The list of commit types in `CLAUDE.md` is the same as the list in `commit-msg.mjs`. `make docs-check` passes.

### Added cases

- **Stop hook blocks again on a returning finding (stop):** Given findings A at the first run (exit 2), then findings B (exit 2), then A again, then the third run exits 2.
- **Stop hook blocks when stop hook is active (stop):** Given the input has `stop_hook_active: true` and findings that differ from the stored key, then the hook exits 2.
- **Stop hook ignores a changed cannot run text (stop):** Given one changed Swift file with a lint finding and one check that cannot run, then the first run exits 2 and stderr holds both reports. Given a second run where only the "cannot run" text changes, then it exits 0 with the note.
- **Stop hook checks only existing changed files (stop):** Given a deleted tracked file, an ignored new file and a staged-only change, then only the staged-only file is checked.
- **Session id cannot escape the state directory (stop):** Given a `session_id` of `../x`, then no file is written outside `<git dir>/tarmac-hooks/` and two runs with the same findings both exit 2.
- **Bash guard refuses kills inside compound commands (Bash):** Each of these is refused: `ls; pkill tarmacd`, `ps aux | killall -9 TARMACD`, `FOO=1 pkill -f tarmac`. Each of these passes: `grep pkill notes.txt`, `pkill -f nginx && echo tarmac`.
- **Commit message hook skips comment lines (`commit-msg`):** Given a message whose first lines are `#` comments, then a good subject after them passes. Given a message that is all comments, then it fails. Given `Revert "fix: y"` with no `Signed-off-by:` line, then it fails.
- **Staged script reports a wrong swift version (`staged.mjs`):** Given a staged Swift file and a `swift` on the `PATH` of another version, then it exits 2 with the "cannot run" report. Given a staged deletion only, then it exits 0.
- **Edit hook ignores input with no file path (edit):** Given an input with no `tool_input.file_path`, then the hook exits 0 and writes nothing.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

- The adapter is thin: it parses the input, calls the existing scripts and maps their exit codes. A rule belongs in the script it is about.
- The repository of a file is found from the file's path, never from `$CLAUDE_PROJECT_DIR`, which stays at the session's root when the agent works in a worktree.
- Do not run `lefthook install`, `make setup` or any `git config` write in the maintainer's clone or in a worktree of it. Use a throwaway clone.
- Never run `tarmacd`, `tarmac`, `TarmacApp` or `make run`.

## Definition of Done

- [ ] `make test`, `make lint` and `make arch-check` are green.
- [ ] Every scenario maps to a test or to a recorded run with its observed values.
- [ ] No covered-but-vacuous scenarios; tests meet the Desiderata bar; no implementation-quality blockers.
- [ ] The PR's own CI run is green.
- [ ] The PR is **not merged on green**. A running session picks up the hooks as soon as its checkout holds them, so the maintainer chooses the moment.

## Trade-offs and Limitations

- The stop hook lets an agent stop on findings it was already told about once. That is the price of not holding an agent on another agent's files. `pre-commit` and CI do not have this exit.
- The edit hook does not lint Rust: clippy needs the whole build. A Rust finding is seen at `pre-commit`.
- `pre-commit` reads the working tree. With a file staged in part, it checks the file as it is on disk, not as it is staged.
- A local hook can be skipped (`git commit --no-verify`, a missing `make setup`). CI is the gate that cannot.
- The Bash hook reads the command as text. A kill by name hidden in a script file, or built from variables, is not seen. `CLAUDE.md` keeps the rule in words.
- `pre-push` runs `make test`, several minutes.

## Decisions

These settle what the review left open. Where a sentence above says otherwise, this section wins.

1. **Commit types.** `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `chore`, `release`: the eight that the 653 subjects on `main` use. No `ci`.
2. **Findings A, then a clean stop, then A again.** The second A blocks. A stop with no finding removes the session's state file, so the hook remembers only the last blocked set while findings last.
3. **Which repository the stop hook checks.** The one that holds the input's `cwd`. Files that the agent edited in another worktree are not checked at the stop; the edit hook checked each of them.
4. **State files.** One for each session that was blocked and has not had a clean stop since. They are a few bytes each and are not cleaned up otherwise.
5. **Subjects with a marker.** `feat!: x` and `fix(board)!: x` pass (a breaking change). `fixup! …` and `squash! …` pass (git writes them, and a later rebase removes them). `fix(board):x`, with no space, fails.
6. **The sign-off.** Checked as `scripts/dco-check.mjs` checks it in CI: the email of a `Signed-off-by:` line equals the author's or the committer's. A hook that only looked for the line would pass a commit that CI then refuses.

7. **Whose checks run.** `.claude/settings.json` starts the adapter of the session's root. When the event is about another repository (the edited file's, or the `cwd` of a stop), that adapter hands the event to that repository's own `scripts/check/hook.mjs` and gives back its answer. A repository with no such file (a worktree on a branch from before this change, or another project) is not judged: its scripts may not take a file list. The Bash guard needs no repository and always runs in the session's adapter.
8. **What the Bash guard reads** (`scripts/check/kill-guard.mjs`; this replaces the splitting rule above). It reads the command as a shell would, as far as text allows. It is a backstop for a slip, not a wall: the rule in `CLAUDE.md` stays in words. The contract is this decision and the cases of `kill-guard.test.mjs` and of "Bash guard refuses a kill by name" and "Bash guard refuses kills inside compound commands" in `hook.test.mjs`; a form that neither names is not promised.
   - *Commands.* A command ends at an unquoted `;`, `&`, `|` or newline. A subshell `( … )`, a `$( … )` and a backtick pair hold commands of their own, also inside double quotes, and the text after them goes on in the state it was in. Text in quotes (`'…'`, `"…"`, `$'…'`), a `#` comment and the body of a here-document (`<<`, `<<-`, with or without a quoted delimiter; `<<<` is a here-string and has no body) start no command. A backslash before a newline joins the two lines.
   - *The program.* In a command, `NAME=value` words, a redirection (`2>/dev/null`, `&>out`, or `2>` or `&>` with its target in the next word) and the keywords `if`, `elif`, `then`, `else`, `while`, `until`, `do`, `!`, `{` are passed over. A `function name` before `{` is passed over too. `2>&1` and `&>` end no command. After a wrapper come its flags, then `--`, then `NAME=value` words and redirections; the next word is the program, or another wrapper. A flag is a word that starts with `-`. It stands alone, unless the table gives it a value in the next word: `sudo` (`-u -g -h -p -C -D -R -T -U -r -t --user --group --host --prompt --chdir`), `doas` (`-u -C`), `env` (`-u -C -P --unset --chdir`), `nice` (`-n --adjustment`), `timeout` (`-s -k --signal --kill-after`, and one argument before the command: the duration, with `NAME=value` words and redirections passed over after it too), `caffeinate` (`-t -w`), `xargs` (`-n -I -L -P -s -E -d -a -J -R -S --max-args --max-procs --replace --delimiter`), `time` (`-o -f`), `exec` (`-a`); `command`, `builtin`, `nohup`, `noglob` and `coproc` have none. A value joined to its flag (`-n5`, `--signal=KILL`) is one word. So `timeout -s KILL 5 pkill tarmacd` runs `pkill`, and `xargs grep pkill` runs `grep`. `command -v` and `command -V` run nothing. A program is named without its directory and in any letter case.
   - *Refused:* `pkill` or `killall` with a later word that holds `tarmac` (any letter case, with `[`, `]`, `\`, `^`, `$` removed), or under `xargs` with `tarmac` anywhere in the line; `kill` without `-0` (which only asks) and with a `pgrep` or `pidof` of such a name in a `$( … )` or backticks among its words, or under `xargs` with such a search anywhere in the line; `sh`, `bash`, `zsh` or `dash` with an argument that, read as a command line, is refused; `eval` when its arguments, joined, are refused.
   - *Too deep to read.* `eval` and a shell's argument are followed 20 deep. A command nested deeper, or so deep in `$(`, `(` or backticks that the reader runs out of stack (some thousands of levels), is refused when its text holds `pkill`, `killall`, `pgrep` or `pidof` and `tarmac`, and passes otherwise.
   - *Known to be refused though harmless:* an `xargs kill` on a line that also holds a `pgrep` of such a name in another pipeline; a wrapper before a word that is no program (`nice A=1 pkill tarmacd`, where `nice` would fail); text nested more than 20 deep that only mentions such a kill.
   - *Not read:* a variable, an alias, a script file, a script on a shell's standard input, a name that a `$( … )` builds (`pkill -f "$(echo tarmacd)"`), a search that is not `pgrep` or `pidof` (`ps | grep`), a search inside another `$( … )` (`kill $(echo $(pgrep tarmacd))`), a loop over what a search found, a command in a string for `xargs` (`xargs sh -c 'pkill {}'`), a flag with a value that the table does not hold (`sudo --chroot /`), a command in a flag's value (`env -S "pkill tarmacd"`), a program that runs another and is not in the table (`su -c`, `find -exec`, `watch`, `ssh`), and another way to end a process by name (`osascript`).
9. **A merge and the sign-off.** The hook asks no sign-off while git makes a merge commit (`MERGE_HEAD` is in the git directory), as CI goes by a commit's parents. A subject that starts with `Merge ` on a commit that is not a merge needs the sign-off. This replaces "a merge excepted" above.
10. **A file name that starts with `-`.** The Swift lint passes the names after `--`, so such a name is a file and not an option.
