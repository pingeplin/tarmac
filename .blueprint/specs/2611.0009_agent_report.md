## Gate

Written 2026-11-14 from the code at `main` 1059618; the #343 facts are checked at `main` 882aa59. The approach is the design's and is not open here. These decisions of the owner bind this spec:

- **R2.** `Input` gets an optional `typed` key. Only an `Input` with `typed: true` marks a report read. The app sets it only for `.user` input (#343).
- **R3.** The copy places the report in time only: `回報 · 在 <proc> 期間`. It never says who sent the report.
- **Q2.** The daemon finds the agent pid from the CLI's socket peer pid and a ppid walk. The foreground leader is only the fallback.
- **Principle 6.** Reports and their read flags live in the daemon. They survive an app relaunch. They are not persisted: a daemon restart kills the processes they describe.
- **`/simplify` notes.** `clear` with no current report sends nothing to the app. (The design's "an identical repeat refreshes `at_ms` only" is changed by D3 below.)
- **Riskiest-assumption check: done (2026-11-14).** See *Open Questions*, OQ1.

Decisions this spec had to make, that the design does not settle, are marked **[D1]…[D10]** in the body. **All ten were decided on 2026-11-14** (owner, reviewed with Fable):

- **D1 (accepted).** `TermHandle.spawned_with_cmd`: a terminal spawned with a `cmd` has its PTY child as the agent. Limit: `exec claude` in a shell makes the flag stale (the child is now `claude`, but the flag says "shell"). The chip is then lost early, never wrong.
- **D2 (accepted, reworded).** A caller whose parent is the PTY shell (a report typed at the prompt) is held by the shell. It ends when the foreground leader changes (about the next command, within one 750 ms poll) or when the shell exits.
- **D3 (changed).** An identical repeat is an ordinary replacement: a new `at_ms`, `read: false`, the holder and `proc` found again, one frame pushed. **This departs from design §1** ("refreshes `at_ms` only"): a new call is a new fact, and the user should see it as unread.
- **D4 (accepted, extended).** No `TermReport` at an exit; the app drops the report on `Exit`. The app also drops it when a card is held dead (`holdOpen`, `AppController+Terminals.swift:276`), because a missed `Exit` arrives through reconcile → `markLost` → `holdOpen`.
- **D5 (changed limit).** Keep the per-restore replay (one frame for each live terminal of the restored board, no `kind` when it has none). Also, the app clears every report chip when it loses the daemon connection (`terminalsLostConnection()`, `AppController+Terminals.swift:325`), so no stale chip survives a reconnect. Accepted limit: a background board shows no report until it is shown. The inbox slice will need an all-board replay.
- **D6 (accepted).** Age `<1m` / `Nm` / `Nh` / `Nd`, floored; the quote in `「」`; the title `回報` alone with no `proc`; a one-line tool tip with no text.
- **D7 (accepted).** The text is optional for `blocked` and `done`. `GUIDE.md` gets a short section now.
- **D8 (accepted).** The cap counts Unicode scalar values (Rust `char`). A text of exactly 280 is not cut. A longer one keeps 279 and gets `…` (280 in all). The daemon applies the same cap.
- **D9 (changed).** `sysctl` `KERN_PROC_PID` only, no `proc_pidinfo` path. Measured on Darwin 25.6 arm64: `proc_pidinfo` fails on pid 1, on root-owned pids (EPERM) and on zombies (ESRCH); `sysctl` reads all three. On a size mismatch or any other failure in the walk, the caller is unattributed (the foreground-leader fallback).
- **D10 (accepted).** A read chip keeps the kind's colour on its border; its text goes to `Theme.faint`. It is checked on a white page too (QA S28).

- **Spec-review answers (2026-11-14, with Fable):**
  1. A poll-driven removal frame may come just before the terminal's `Exit`. This is accepted: the end state is the same.
  2. A command shorter than one 750 ms tick is not seen. So a report held by the shell or the leader stays until a longer command or a newer report. This is an accepted limit, and `GUIDE.md` states it.
  3. The daemon stores an empty `text` as no text, and it ignores a `text` sent with `clear`. The daemon is lenient; the CLI is strict.
  4. The CLI treats `tarmac report clear ""` the same as plain `clear` (exit 0). A generic hook `tarmac report "$kind" "$text"` must never get exit 2, because Claude treats a hook's exit 2 as blocking. `clear "x"` (a non-empty text) and two or more arguments after the kind stay a usage error (exit 2).
  5. QA uses two checks:
     - a stand-in agent that reports and then sleeps, for a deterministic chip check;
     - one best-effort interactive `claude` step. A `Notification` `permission_prompt` gives a `blocked` chip that stays.
     
     The `claude -p` run checks the daemon's frames, not the brief chip.
  6. The race "a report is stored after the terminal exits" is checked by review. It uses exception 2 of `docs/coding-style.md`: thin wiring over `forget`, which S11(g) tests. The PR body states the verification. The three interleavings were traced: one `forget` always finds the entry.

## Motivation

A bell has no text and no kind. With four agent terminals on two boards, the user must look at each card to find the one that waits, and to learn why. This slice lets a process in a terminal say "blocked" or "done" with a short text. The card shows a small chip that quotes it and places it in time. Slice 3 (`hooks install`) makes Claude Code call it. Slice 5 (the inbox) lists the reports.

## Proposed Solution

### Overview

1. A process in terminal T runs `tarmac report blocked|done "<text>"` or `tarmac report clear`.
2. The CLI sends `Report {term_id: T, kind, text?}`. The daemon answers `Ack` or `Err`.
3. The daemon finds the agent process from the CLI's peer pid (the walk), or else the foreground leader (the fallback). It stores T's current report.
4. The daemon pushes `TermReport` to the app on each change. The app shows a chip in T's card header.
5. The 750 ms poll removes the report when its process ends. A typed key marks it read.

### Key Components

**CLI — `tarmac report`** (`tarmac-cli/src/report.rs`, new; dispatched from `main.rs`).

```
tarmac report blocked ["<text>"]
tarmac report done ["<text>"]
tarmac report clear
```

- **Usage (exit 2).** No kind, a kind other than the three, `clear` with a text, or more than one text argument. The text is optional for `blocked` and `done` [D7]. An empty text is no text.
- **A terminal is required (exit 1).** With `TARMAC_TERM_ID` unset or empty, the CLI prints `tarmac: report needs TARMAC_TERM_ID (run it in a Tarmac terminal)` and exits 1. It does not connect. The usage check comes first.
- **The text cap** [D8]. The CLI caps the text with `tarmac_protocol::cap_report_text`. The unit is the Unicode scalar value (Rust `char`), so the cut never splits a UTF-8 sequence. A text of at most 280 scalars, exactly 280 included, is kept as it is. A longer text keeps its first 279 scalars and gets `…` (U+2026), so the result is exactly 280. The daemon applies the same function to every `Report` it gets.
- **The exchange.** `connect()`, send `Report`, then `answer()`. `Ack` → exit 0, and nothing is printed. `Err {msg}` → `tarmac: {msg}` on stderr, exit 1. No daemon → the `connect()` message, exit 1.
- **No answer.** A read that times out (5 s) prints `tarmac: no answer from the daemon in 5 s (an older daemon)` and exits 1. An older daemon ignores `report` (*Context*).
- **Help.** `help.rs` gets the three usage lines and one paragraph. `EXIT STATUS` line 1 names `report`.

**Protocol** (`tarmac-protocol/src/lib.rs` and the Swift codec, same change).

- `Msg::Report { term_id: String, kind: String, text: Option<String> }`. `text` is omitted when `None`.
- `Msg::TermReport { term_id, kind: Option<String>, text: Option<String>, at_ms: Option<u64>, proc: Option<String>, read: bool }`. Every optional key is omitted when `None`. `read` is omitted when `false` (`#[serde(default, skip_serializing_if = "std::ops::Not::not")]`), so a missing `read` decodes as unread. This is the reverse of `DocEntry.read`, whose default is true.
- `Msg::Input` gets `typed: bool` with the same attributes as `read`. An `Input` with `typed: false` encodes as today, byte for byte (V3 does not change).
- `pub const REPORT_TEXT_MAX: usize = 280` and `pub fn cap_report_text(&str) -> String`. The CLI and the daemon both use it.
- `kind` stays a string on the wire, as `Tile.kind` and `Hello.role` do. Unknown values are handled by each side (below).

**Daemon — the peer pid** (`main.rs` accept loop, `conn.rs`).

- Right after `accept()` returns, and before any `await`, the daemon calls tokio's `UnixStream::peer_cred()` (a synchronous call) and keeps `UCred::pid()`. On macOS this is `LOCAL_PEEREPID`. An error, or no pid, gives `None`.
- `conn::handle` takes the value as a new argument, `peer_pid: Option<libc::pid_t>`, and passes it to `cli_session`. The app session ignores it.
- The read must come before the first `await`, because the pid can be read only while the client's end is open (design Q2). The CLI keeps its end open until `Ack`, so the read is safe for a well-behaved CLI.

**Daemon — the walk** (`tarmacd/src/agent.rs`, new; pure).

```
fn find_agent(caller: Option<pid>, child: Option<pid>, child_is_cmd: bool,
              parent_of: impl Fn(pid) -> Option<pid>) -> Found
enum Found { Agent(pid), Shell, Unattributed }
```

- `caller` is the peer pid. `child` is the PTY child pid (`TermHandle.pid`). `child_is_cmd` is true when the terminal was spawned with a `cmd`. `parent_of` reads one parent pid.
- It returns `Unattributed` when:
  - `caller` or `child` is `None`;
  - `parent_of` gives `None` on the way (the process is gone, or the read failed);
  - the chain reaches a pid ≤ 1 before it reaches `child` (the caller was re-parented to launchd);
  - the chain has more than `MAX_HOPS` = 32 members (a guard against a cycle).
- When the chain reaches `child`, the agent is [D1]:
  - `Agent(child)`, if `child_is_cmd` (the PTY child is the agent itself, design §1). This rule comes first [D1];
  - `Shell`, if the caller *is* `child`, or the caller's parent is `child` (a report typed at the prompt). The caller itself is never the agent: the CLI exits right after `Ack`, so a report tied to its pid would end at once [D2];
  - else `Agent(m)`, where `m` is the chain member just below `child` (shell → agent → … → caller).
- `TermHandle` gets `spawned_with_cmd: bool`, set in `term::spawn` from `plan.cmd`, and a read-only accessor for `pid`.

**Daemon — process facts** (`proc.rs`).

- `pub fn proc_facts(pid) -> Facts`, with `Facts = Live { ppid, started } | Gone | Unread`. It reads `sysctl` `{CTL_KERN, KERN_PROC, KERN_PROC_PID, pid}` only, never `proc_pidinfo` [D9]. `proc_pidinfo` fails on pid 1, on root-owned pids (EPERM) and on zombies (ESRCH); `sysctl` reads all three.
- The pinned `libc` has no Apple `kinfo_proc`. The read is into a buffer of `KINFO_PROC_SIZE` = 648 bytes, and the fields are taken at fixed offsets (measured on Darwin 25.6 arm64):
  - `p_starttime` (`timeval`) at 0: `tv_sec` i64 at 0, `tv_usec` i32 at 8;
  - `p_stat` (i8) at 36; `SZOMB` = 5;
  - `e_ppid` (i32) at 560.
  A local `#[repr(C)]` struct with these offsets and a compile-time size assert is equally fine.
- The result:
  - returned size 0 (a reaped or unknown pid) → `Gone`;
  - size 648 and `p_stat == SZOMB` → `Gone`. So "exited" includes "exited but not yet reaped";
  - size 648 otherwise → `Live`;
  - a `sysctl` error, or any other size → `Unread`.
- **In the walk,** `Gone` or `Unread` on the way makes the caller `Unattributed` (the fallback). So a layout change in a future macOS degrades to the fallback, never to a wrong pid.
- **In the lifetime check,** `Gone` or a `Live` with another start time removes the report; `Unread` keeps it for that tick.
- `parent_of(pid)` is `Live.ppid`, or `None` for `Gone` and `Unread`.
- On a target that is not macOS, `proc_facts` gives `Unread` (the `proc.rs:24-27` convention: the crate only stays buildable there).
- The walk and the facts make no file-system call, so they do not go through `PathGate`. They run inline in the CLI session (a few `sysctl` calls).

**Daemon — the report store** (`tarmacd/src/reports.rs`, new; pure, with an injected clock).

- `Reports` maps a term id to its current report:

  ```
  CurrentReport { kind: Blocked | Done, text: Option<String>, at_ms: u64,
                  holder: Holder, proc: Option<String>, read: bool }
  Holder = Agent { pid, started } | Shell { pid, caller } | Leader { pid }
  ```

- Each method returns the `TermReport` frame to push, or `None` when the app needs nothing:
  - `report(term, kind, text, now_ms, holder, proc)`:
    - Replace the current report, if any, with the new one, `read: false`. Push the frame.
    - An identical repeat (same kind and text) is no special case [D3]: it gets the new `at_ms`, `read: false`, and the holder and `proc` that the handler found again. This departs from design §1.
  - `clear(term)`: remove it. Push `TermReport {term_id}` when there was one. Push nothing when there was none.
  - `mark_read(term)`: when the report is unread, set `read: true` and push the frame. Else nothing.
  - `check(term, alive)`: `alive` is a function of the holder. When it is false, remove the report and push `TermReport {term_id}`.
  - `forget(term)`: remove it at terminal exit. Push nothing [D4].
  - `snapshot(terms)`: one frame for each term in `terms`: its report, or `TermReport {term_id}` (no `kind`) when it has none.
- **Holder liveness is one pure function** that production uses and the tests call: `Holder::alive(&self, facts_of: impl Fn(pid) -> Facts, leader: Option<pid>) -> bool`. The `alive` that the poll gives to `check` is this function with the real `proc_facts` and a fresh `foreground_pid()`. It returns:
  - `Agent {pid, started}`: false for `Gone`, and for `Live` with another start time; true for `Live` with the same start time, and for `Unread`.
  - `Shell {pid, caller}`: true when `leader` is `pid` or `caller`, or is `None`; else false.
  - `Leader {pid}`: true when `leader` is `pid`, or is `None`; else false.
- **The holder decision is one pure function** too: `decide_holder(found: Found, child, peer, facts_of, leader: impl FnOnce() -> Option<pid>) -> Option<Holder>`. It maps `Found` to a `Holder` as the `Report` handler says (below). `None` means "no process to tie the report to". `leader` is called only in the fallback.
- The daemon keeps `reports: tokio::sync::Mutex<Reports>` on `Daemon`. **Each change and its push happen under this lock.** So the frames of one terminal reach the app's channel in the order of the changes.
- **The two flags on `TermHandle`** (`has_report`, `unread_report`, both `AtomicBool`) are written only while `reports` is held, in the same step as the change: `has_report` is true while the store has a report for the term; `unread_report` is true while that report is unread. They are read without the lock.
- **Lock order:** `reports`, then `app` (inside `push`). No path takes `app` and then `reports`. `reports` is never held while `boards` or `terms` is taken.
- **Reports are never persisted.** No method calls `mark_dirty`. `state.json` gets no report key.

**Daemon — the `Report` handler** (`cli_session`).

1. The term must be live (`daemon.term(&term_id)`). Else `Err {msg: "unknown terminal: <term_id>"}`.
2. `kind` must be `blocked`, `done` or `clear`. Else `Err {msg: "unknown report kind: <kind>"}`.
3. `clear` → `Reports::clear`, then `Ack`. A `text` sent with `clear` is ignored.
4. `blocked` / `done`:
   - The daemon caps `text` again with `cap_report_text` (any socket client can send a `Report`). An empty `text` is stored as no text, as in the CLI.
   - `holder`, from `find_agent(peer_pid, handle.pid(), handle.spawned_with_cmd, parent_of)` and then `decide_holder`:
     - `Agent(a)` → `Agent {pid: a, started}`, with `started` from `proc_facts(a)`. If that read is not `Live`, the caller is taken as unattributed.
     - `Shell` → `Shell {pid: child, caller: peer_pid}` [D2].
     - `Unattributed` → the fallback: a fresh `handle.foreground_pid()`, as `Leader {pid}`.
   - Fallback with no leader → `Err {msg: "no process to tie the report to in <term_id>"}`.
   - `proc`: `proc::process_name(holder pid)`. `None` is allowed.
   - `at_ms`: the daemon's wall clock, in ms since the Unix epoch.
   - With `reports` held: `Reports::report`, the two flags of the handle, and the push of the frame. Then `Ack`. So the app's channel has the frame before the CLI gets `Ack`.

**Daemon — the lifetime in the poll** (`term.rs`, `proc_loop`).

- Each tick, before the `foreground_pid()` read and its `continue` (`term.rs:350`), the loop runs `Reports::check` for its term, with `Holder::alive`, when the term has a report (`has_report`):
  - `Agent {pid, started}` is alive while `proc_facts(pid)` is `Live` with the same `started`. A different start time is a reused pid. `Unread` keeps it for this tick.
  - `Shell {pid, caller}` is alive while `foreground_pid()` is the shell or the reporting CLI (which is the leader for the moment until it exits). Any other leader (the next command) removes it. A `None` read keeps it for this tick. The shell's exit ends it with the terminal.
  - `Leader {pid}` is alive while `foreground_pid() == Some(pid)`. A `None` read keeps it for this tick.
- So an agent-held report goes within one tick (≤ 750 ms) of its process's exit, even when the leader read fails. A leader-held or shell-held report goes at the first tick that sees another leader. A command that starts and ends between two ticks is never seen (see *Trade-offs*).
- In a tick that sees a new leader, `check` runs before the `TermProc` push. So the removal frame can come before the `TermProc` frame of that tick.
- A terminal with no report takes no `reports` lock in the tick (it reads `has_report` only).

**Daemon — read on typed input** (`dispatch_app_msg`, `Msg::Input`).

- The bytes go to `input_tx` first, as today, whatever `typed` is.
- Then, only when `typed` is true and `handle.unread_report` reads true, the daemon takes the slow path: with `reports` held, `Reports::mark_read` marks the stored report read (if it is still unread), the flag is cleared, and the frame is pushed.
- So a key costs one atomic load when no unread report exists. An `Input` with no `typed` key never marks a report read.

**Daemon — terminal exit.** `term_ended` calls `Reports::forget` before the `Exit` push. No `TermReport` is sent for an exit: the `Exit` frame ends the card's report in the app [D4].

**Daemon — reports to a connecting app.** After each `restore` that `change_and_send_active_board` sends, and after its `file_event`s, the daemon sends one `TermReport` for **every** live terminal of that board, on the same `conn.tx`, under the `reports` lock. A terminal with no report gets `TermReport {term_id}` (no `kind`). So a report removed while no app was connected is also removed in the app. The scrollback replay follows. This runs on every restore, not only the first per connection: the frames are idempotent, and the app drops a frame for a card that it has not built [D5].

**Daemon — a report that races the exit.** A `Report` whose terminal exits while the handler runs must leave no entry behind. No report outlives its terminal. The lock rule forbids a `terms` read while `reports` is held, so the mechanism is this: after `Reports::report` returns and `reports` is released, the handler reads `daemon.term(&term_id)` again. When the term is gone, it calls `Reports::forget`. `term_ended` removes the term from `terms` before its own `forget`, so one of the two `forget`s finds the entry. A frame that this race pushes reaches the app before `Exit` (which then drops the chip) or after it (the app ignores a frame for no card or a dead card). This is not observable on the wire in a deterministic test; review checks it.

**App — codec** (`TarmacKit/Messages.swift`).

- `.report(termID:kind:text:)` and `.termReport(termID:kind:text:atMs:proc:read:)`, decode and encode. `read` decodes as false when missing and is written only when true.
- `.input(termID:bytes:typed:)` with `typed: Bool = false`. `typed` is written only when true.
- `DaemonClient.input(termID:bytes:typed:)`.

**App — the chip decision** (`TarmacKit/ReportChip.swift`, new; pure).

- `TermReport` (a value type): `kind: Kind (.blocked, .done)`, `text: String?`, `atMs: UInt64`, `proc: String?`, `read: Bool`. `TermReport.from(message)` gives `nil` for a frame with no `kind`, an unknown `kind`, or no `at_ms`.
- `ReportChip.model(report:nowMs:) -> Model`, with `Model { text, tone, dimmed, toolTip }`:
  - `text`: `回報 · <age>`.
  - `tone`: `.blocked` (amber) or `.done` (green, `Theme.ok`).
  - `dimmed`: `read`. The tone stays the kind's when dimmed [D10].
  - `toolTip`: line 1 is the title, `回報 · 在 <proc> 期間`, or `回報` when `proc` is `nil`. Line 2, only when there is a text, is the text in `「…」` [D6].
- `ReportChip.age(elapsedMs:)` [D6]: under 60 s `<1m`; under 60 min `Nm`; under 24 h `Nh`; else `Nd`. Each is floored. An `at_ms` in the future counts as 0.
- `ReportChip.refreshInterval` = 30 s: how often a shown chip re-reads its age.

**App — wiring** (`TarmacApp`; no unit tests by design).

- `terminalDidSend(termID:_:source:)` calls `client.input(termID:bytes:typed: source == .user)`.
- `AppController+Connection` routes `.termReport` to `handleTermReport(termID:_:)`. It finds the session with `anySession`. It ignores a frame for a term with no card, or with a dead card. It stores the report on `TerminalSession.report` and calls `card.setReport(model or nil)`.
- The session's report is dropped, and the card's chip hidden, in `holdOpen` (`AppController+Terminals.swift:276`), beside `s.bellAt = nil`. Every path to a dead card goes there: an `Exit` that holds the card, and a missed `Exit` found by reconcile (`markLost` → `holdOpen`) [D4]. A clean exit removes the card, and its chip with it.
- `terminalsLostConnection()` (`:325`) clears the report of every session on every board, and hides every chip [D5]. The restore after the reconnect sends the current reports of the shown board.
- `CardHeaderView` gets `reportChip`, placed in the terminal header's trailing items just before `bellDot`: `›_ label … 回報 · 2m ●`.
- **The chip looks like the doc card's chips.** It reuses `OwnerChipView`'s metrics (font, padding, radius, border, `CardScale`) and its form (a border and text, no fill), through one shared chip view with a tone. So the same chip form reads the same on every card kind and in either theme (memory: shared chrome renders the same on every card kind). An unread chip has text and border in the tone colour. A read chip keeps the tone colour on its border, and its text takes `Theme.faint`, so a read `blocked` and a read `done` still differ [D10]. Dimming never uses transparency.
- A shown chip re-reads its age every `ReportChip.refreshInterval`, as `RecentMetaLabel` does with its own timer.
- **Not in this slice:** `card.signal`, the offscreen pills, the minimap and the board switcher's counts do not change (slice 5).

### Data Flow

1. A hook in terminal T runs `tarmac report blocked "May I run rm?"`. Its parent is `claude`; `claude`'s parent is the shell, T's PTY child.
2. The daemon accepts the connection and reads the peer pid P (the CLI) before any await.
3. The CLI sends `hello`, then `Report {term_id: T, kind: "blocked", text}`.
4. The daemon walks P → `claude` → shell. The agent is `claude`. It stores `{blocked, text, at_ms, Agent{pid, started}, proc: "claude", read: false}`, pushes `TermReport`, and answers `Ack`. The CLI exits 0.
5. The app shows `回報 · <1m` in amber on T's card. Hover shows `回報 · 在 claude 期間` and `「May I run rm?」`.
6. The user types `y` into T. The app sends `Input {typed: true}`. The daemon marks the report read and pushes `TermReport {…, read: true}`. The chip dims.
7. `claude` exits. At the next tick the poll finds the pid gone, removes the report and pushes `TermReport {term_id: T}`. The chip goes.

### Interface Contract

Additive only. Both codecs ignore unknown keys and unknown types.

```
report       { t:"report", term_id: str, kind: "blocked"|"done"|"clear", text?: str }   cli → daemon; reply ack | err
term_report  { t:"term_report", term_id: str, kind?: "blocked"|"done", text?: str,
               at_ms?: u64, proc?: str, read?: bool }                               daemon → app
input        { …existing…, typed?: bool }                                            app → daemon
```

- **`report`.** `text` is omitted when there is none. It is at most 280 `char`s after the daemon's cap. The daemon stores an empty `text` as no text, and ignores a `text` sent with `clear`. `err` texts: `unknown terminal: <id>`, `unknown report kind: <kind>`, `no process to tie the report to in <id>`.
- **`term_report`.** No `kind` means "no report" (removed or cleared). Then only `term_id` is sent. With a `kind`, `at_ms` is always sent; `text` and `proc` are sent when known. `read` is sent only as `true`. A receiver treats a missing `read` as unread, and a `kind` it does not know as no report.
- **`input.typed`.** Sent only as `true`, and only for input from the user (a key, a paste, text, a mouse report, a wheel step; #343's `.user`). Missing means false.
- **Not persisted.** No key in `state.json`.
- **New conformance vectors** (hex = `rmp_serde::to_vec_named` bytes, in its key order; each vector gives the whole frame):
  - **V20:** `{t:"report", term_id:"t1", kind:"blocked", text:"ok?"}`
  - **V21:** `{t:"report", term_id:"t1", kind:"clear"}` (no `text` key)
  - **V22:** `{t:"term_report", term_id:"t1", kind:"done", text:"ok", at_ms:1700000000000, proc:"claude", read:true}` (`at_ms` is a msgpack uint64, `cf`)
  - **V23:** `{t:"term_report", term_id:"t1"}`
  - **V24:** `{t:"input", term_id:"t1", bytes:"a", typed:true}` (`bytes` is `bin`, `c4 01 61`)
  - Both codecs decode each one, and round-trip it. The Swift encoder's bytes equal Rust's (`RustEncoderParityTests`). V1–V19 do not change.
- **Docs.**
  - `docs/protocol.md`: a new section *A terminal's report (spec 2611.0009)* for the three frames and their rules; *CLI session* names `report`; V20–V24.
  - `docs/architecture.md`: §3 *Process & connection model* (the peer pid at accept), §3 *Terminal sessions* (the report store, the walk, the lifetime in the poll, read on typed input), §4 *Terminal cards* "Honest signals" (the chip, its copy, and that it quotes a claim), §6 *What survives what* (a report survives an app relaunch and reconnect; a daemon restart loses it).
  - `CLAUDE.md`: "`open`, `push` and `--version` are the three verbs that talk to the daemon" becomes four, with `report`.
  - `core/crates/tarmac-cli/src/GUIDE.md`: a short section on `tarmac report` [D7].

## Alternatives Considered

- **Infer the state from the screen.** Rejected by principle 1 (design, *Alternatives*).
- **The foreground leader only (no walk).** Simpler, but inside tmux or a wrapper the leader is the wrapper, so a report outlives its agent. The design adopted the walk (Q2).
- **The hook's direct parent as the agent.** It matches the check in OQ1 (the hook's parent is `claude`). It fails for a manual `tarmac report` through an agent's Bash tool: the parent is then a short-lived shell. Rejected (coordinator note, 2026-11-14).
- **Persist reports.** The processes that they describe die with the daemon. A stale report after a restart would claim a state that no process holds. Rejected (principle 6 covers app relaunch only).
- **A `TermReport` with no `kind` at each exit.** It gives one rule to the app, but it adds a frame per exit. The `Exit` frame already ends the card's report [D4].

## Migration & Rollback

- **Migration.** None. Nothing is persisted.
- **A new CLI with an older daemon.** The daemon ignores `report` (*Context*). The CLI waits 5 s and exits 1 with the *no answer* message. Slice 3's hook adapter must not wait this long (its own 200 ms rule); that is slice 3's concern.
- **A new daemon with an older app.** The app ignores `term_report` (unknown type). It sends no `typed`, so no report is ever marked read. Nothing breaks.
- **A new app with an older daemon.** The daemon ignores `typed` (`Input` has no `deny_unknown_fields`). It sends no `term_report`, so no chip shows.
- **Rollback.** Revert the change. No state to clean.

## Security Considerations

- **Who can report.** Any process that can open the socket can send a `Report` for any live term id. The socket is the user's own, in the user's application-support directory. This is the same trust as `open` and `push`.
- **The text is a claim.** The app shows it only in quote marks, in a tooltip, as plain text. It is never parsed as markup, and it has no links. The copy says when, not who (R3).
- **The text is bounded twice.** The CLI caps it at 280 `char`s for the user. The daemon caps it again, because a raw client can send up to the 16 MiB frame limit.
- **`proc` is observed.** It is the name that `proc_pidpath` gives for the holder pid, never a name that the caller sent.
- **The peer pid.** It comes from the kernel (`LOCAL_PEEREPID`), not from the client. A caller can only make itself unattributed (for example by a double fork). It then gets the weaker fallback rule; it cannot name another process.

Where the tests live:

- **App:** `app/Tests/TarmacKitTests/ReportChipTests.swift` and the codec tests (`MessagesTests`, `ConformanceTests`, `RustEncoderParityTests`).

Terms used below:

- **A report frame** is a `term_report` the test app connection reads, matched by `term_id`.

The harness gets this helper. Each time bound below is measured from a step that the test itself does (a send or a typed line), or from a frame in the log.

### Happy Path

- **S1 (the walk finds the agent below the shell; integration):**
  - Given a shell spawn T (`cmd: None`), and at its prompt the test types `/bin/zsh -f -c '<nc reporter>; echo SE""NT; sleep 2' &` and a newline, so agent A runs in the background and the shell stays the foreground leader,
  - when the reporter sends `Report {T, blocked, "ok?"}` and gets `Ack`,
  - then a report frame comes with `kind: "blocked"`, `text: "ok?"`, `proc: "zsh"`, no `read`, and an `at_ms` within 2 s of the test's clock. In the frame log, the report frame comes before the `Output` chunk that completes the `Ack` payload (`81 a1 74 a3 61 63 6b`) in T's concatenated output: the daemon pushes before it answers. (`frame::write_async` writes the length prefix and the payload in two writes, `frame.rs:54-55`, so a PTY read can split them; the test searches the concatenated output, as `collect_output_into` does.) This meets the design's "≤ 1 s from the CLI's exit" (*Success criteria*) with no timing margin.
  - Precondition: T's own `TermProc` name is not `zsh` (`/bin/sh` on macOS can show another name, so the test does not hard-code `sh`). The fallback would give that name. This proves the walk.
- **S2 (the report ends with its agent, not with the leader; integration):**
  - Given S1's state after its report frame,
  - when A's `sleep 2` ends and A exits (the test sees `SENT`, then waits),
  - then within 3.5 s of `SENT` a frame `TermReport {term_id: T}` with no `kind` comes, and T is still live (no `Exit`).
  - The foreground leader (the shell) did not change in this time, so a leader rule would keep the report. This proves the agent rule.
- **S3 (the fallback for an unattributed caller; integration):**
  - Given a job-control shell T (`/bin/zsh -f -i`, as `folder_restore_integration.rs:17`) running `sleep 5` in the foreground, and a `TermProc {name: "sleep"}` for T,

  - Then a `TermReport {term_id: T}` with no `kind` comes not earlier than 4 s and not later than 6.5 s after the test typed `sleep 5` (so not at once, and not later than one tick after `sleep` ends), and T is still live.
- **S4 (the PTY child is the agent when spawned as `cmd`; integration):**
  - Given T spawned with `cmd: ["/bin/zsh", "-f", "-c", "/bin/sh -c '<nc reporter>; echo MID'; echo SENT; read _"]`, so a short-lived middle process (`sh -c`) stands between the reporter and the PTY child. The middle script has a second command, so `sh` must fork the reporter and cannot `exec` it in place (a shell may `exec` the only command of `-c`; then there is no middle process, the walk gives `Shell` with the same `proc`, and the test cannot fail),

  - then the report frame has `proc: "zsh"` (the child), and no removal frame comes within 2 s after `SENT`.
  - Without the `cmd` rule the agent would be the middle process: `proc` would be `sh`'s name, not `zsh`, and the report would go when it exits. So this fails if `spawned_with_cmd` is ignored.
- **S5 (typed input marks it read; integration):**

  - when the app sends `Input {T, "\n", typed: false}` then waits 1 s, and then `Input {T, "\n", typed: true}`,
  - then no frame comes for the first input, and one report frame with `read: true` and the same `at_ms` comes for the second.
  - A second `typed: true` input sends no frame.
- **S6 (CLI happy path; CLI test):**
  - Given a double that acks `report`, and `TARMAC_TERM_ID=t9`,

  - then the double got `Report {term_id: "t9", kind: "blocked", text: Some("May I?")}`, the exit code is 0, and stdout and stderr are empty.

- **S7 (the chip model; TarmacKit):**

  - then `text == "回報 · 2m"`, `tone == .blocked`, `dimmed == false`, `toolTip == "回報 · 在 claude 期間\n「May I?」"`.

  - The Swift encoder's bytes equal Rust's for each.

### Edge Cases

- **S9 (the walk; unit, `agent.rs`).** With a fake `parent_of` table, `find_agent` gives:
  - (a) caller → X → A → child, `cmd: false` → `Agent(A)`;
  - (b) caller → child, `cmd: false` → `Shell` (a report typed at the prompt);
  - (c) caller == child, `cmd: false` → `Shell`;
  - (d) caller → X → A → child, `cmd: true` → `Agent(child)`;
  - (i) caller → child, `cmd: true` → `Agent(child)` (the `cmd` rule comes first);
  - (e) caller → X → 1 → `Unattributed` (re-parented);
  - (f) caller → X, and `parent_of(X)` is `None` → `Unattributed`;
  - (g) caller is `None`, or child is `None` → `Unattributed`;
  - (h) a cycle X → Y → X → `Unattributed` within 32 steps.
- **S10 (process facts; unit, `proc.rs`, macOS):**
  - `proc_facts(own pid)` is `Live` with `ppid == getppid()` and a non-zero start time.
  - `proc_facts(1)` (launchd, root-owned) is `Live` with `ppid == 0`. (`proc_pidinfo` fails here; this guards D9.)
  - A child that the test spawns (for example `/bin/cat` with a piped stdin) is `Live` while it runs. Then the test closes its stdin and does not call `wait`, so the child exits and stays a zombie (nothing else reaps it). The test polls `proc_facts` to a deadline until it is `Gone`; a `Live` to the deadline fails. Then it calls `wait`, and `proc_facts` is still `Gone`.
  - For `-1` it is not `Live`.
- **S11 (the store; unit, `reports.rs`, injected clock):**
  - (a) `report` on an empty store gives a frame with `read: false`.
  - (b) An identical repeat (same kind and text) at a later `now`, with a new holder and `proc`, gives a frame with the new `at_ms`, the new `proc` and `read: false`, and stores the new holder [D3]. Start from a read report, so a store that keeps `read` fails the test.
  - (c) A repeat with a new text gives `read: false`.
  - (h) `check` with `Holder::alive` on a `Shell {pid: S, caller: C}` holder keeps the report while the leader is S, C or `None`, and removes it once the leader is another pid. The test calls the production `Holder::alive` with injected facts and leader reads; a closure written in the test does not count.
  - (i) `snapshot([T, U])`, with a report for T only, gives T's frame and `TermReport {term_id: U}` with no `kind`.
  - (d) `clear` with no report gives `None`. `clear` with one gives `TermReport {term_id}` and empties the store.
  - (e) `mark_read` twice gives one frame, then `None`.
  - (f) `check` with `alive = true` gives `None`; with `false` it gives the removal frame once.
  - (g) `forget` gives `None` and empties the store.
- **S12 (holder liveness; unit, `reports.rs`, the production `Holder::alive`):**
  - An `Agent {pid, started: s1}` holder with facts `Live {started: s2}` for that pid is not alive (a reused pid), so `check` removes the report.
  - The same holder with `Live {started: s1}` is alive. With `Unread` it is alive (kept for the tick). With `Gone` it is not alive.
  - A `Leader {pid: L}` holder is alive for a leader read of `L` or `None`, and not alive for another pid.
- **S36 (the holder decision; unit, the production `decide_holder`):**
  - `Agent(a)` with `Live` facts for `a` gives `Agent {pid: a, started}`.
  - `Agent(a)` whose facts are `Gone` or `Unread` falls back: with a leader `L` it gives `Leader {pid: L}`.
  - `Shell` gives `Shell {pid: child, caller: peer}`.
  - `Unattributed` with a leader `L` gives `Leader {pid: L}`. With no leader it gives `None`, which the handler answers with `err` `no process to tie the report to in <id>`.
- **S13 (a report that is not saved; integration):**
  - Given a live T, spawned first, then a `Layout` that the daemon saves to `state.json`, and 500 ms more, the test keeps the bytes,
  - when the test process sends a report for a live T and its frame comes,
  - then `state.json` is byte-for-byte the kept bytes 1 s later, and has no `report` text in it.
- **S14 (reports reach a new app connection; integration):**
  - Given a live T with a report that the test marked read (S5), and then the app connection is closed,
  - when the test sends a second report for another live term U while no app is connected, and then a new app connects,
  - then after the connect's `restore` the new connection gets T's frame with `read: true` and its first `at_ms`, and U's frame with no `read`. Each comes after the `restore` and before the first replayed `Output`.
  - Precondition: T and U each have scrollback (their shell prompts), so the replay is not empty; the test asserts that an `Output` for each follows the report frames in the frame log. With an empty replay, "before the first replayed `Output`" could not fail.
- **S15 (a background board's reports come with its restore; integration):**
  - Given T spawned on board-1, with board-0 active, a report for T, and the test has read the live frame of that report,
  - when the app sends `BoardSwitch {board-1}`,
  - then the `restore` for board-1 is followed by a second report frame for T, with the same `at_ms`.
  - When the app then switches to board-0 and back to board-1, the second `restore` for board-1 is again followed by a report frame for T. (The scrollback replay is sent only on a board's first restore per connection, `conn.rs:181`; the report frames are not. This step fails if the report frames share that gate.)
- **S32 (a removal while no app is connected; integration):**
  - Given a live job-control shell T running `sleep 5`, a report for T from the test process (fallback, held by `sleep`) whose report frame (with a `kind`) the test has read, and then the app connection is closed,
  - when `sleep` ends while no app is connected (the report is removed), and then a new app connects 7 s after the test typed `sleep 5` (the test cannot see `sleep` end with no connection, so it waits a fixed time),
  - then after the connect's `restore` the new connection gets `TermReport {term_id: T}` with no `kind`.
  - The same restore also carries `TermReport {term_id: U}` with no `kind` for a live U that never had a report.
- **S16 (exit ends the report; integration):**
  - Given T (a plain shell `read _; exit 0`) with a report from the test process, whose report frame (with a `kind`) the test has read,
  - when the test types a newline into T and T exits,
  - then the app gets `Exit`, and no `term_report` for T comes within 1 s after the `Exit`. A new `Report` for T gets `err` `unknown terminal: T`.
  - A removal frame that comes *before* `Exit` is allowed: the poll can see the process gone before the pump ends the term (the pump drains output for up to 2 s, `term.rs:307`). That `forget` pushes nothing is S11(g).
  - Then the test spawns a new terminal with the same id T and connects a new app. Its restore carries `TermReport {term_id: T}` with no `kind`. This fails if the exit left the old entry in the store.
- **S17 (clear with no report sends nothing; integration):**
  - Given a live T with no report,
  - when the test process sends `Report {T, clear}`,
  - then `Ack` comes, and no `term_report` comes within 1 s.
- **S18 (the cap; unit, `tarmac-protocol`):**
  - A 280-`char` text is unchanged. A 281-`char` text becomes 279 `char`s + `…`.
  - A text of 300 CJK characters (3 UTF-8 bytes each) is cut at a `char` boundary: valid UTF-8, 280 `char`s, ends with `…`.
  - An emoji with a combining sequence at the cut is cut between scalars, never inside one.
  - The daemon applies it: a `Report` with a 1000-`char` text from a raw client gives a frame whose `text` has 280 `char`s (integration).
- **S19 (copy without proc or text; TarmacKit):**
  - A report with `proc: nil` has the title `回報`.
  - A report with no text has a one-line tool tip (the title only).
  - A frame with no `kind`, or `kind: "later"`, or no `at_ms`, gives no `TermReport` value (no chip).
- **S20 (age; TarmacKit):** `ReportChip.age` gives `<1m` for 0 and 59 999 ms, `1m` for 60 000, `59m` for 3 599 999, `1h` for 3 600 000, `23h` just under a day, `1d` for a day, and `<1m` for an `at_ms` in the future.
- **S21 (an identical repeat is a new, unread report; integration) [D3]:**
  - Given T with a read report `{blocked, "ok?"}` from the test process,
  - when the same report comes again 1.1 s later,
  - then one frame comes, with a larger `at_ms` and no `read` key (unread).
  - When the app then sends `Input {T, "\n", typed: true}`, a frame with `read: true` comes. This fails if the replacement does not set `unread_report` again.
- **S33 (a report typed at the prompt is held by the shell; integration) [D2]:**
  - Given a shell spawn T (`cmd: None`, as S1), and at its prompt the test types `<nc reporter>; echo BA""CK` and a newline, so the reporter is a foreground command whose parent is the shell,
  - when its `Report {T, done}` is acked and `BACK` shows in T's output (the reporter has exited),
  - then a report frame comes whose `proc` is T's shell name (the precondition of S1), and no removal frame comes within 2 s after `BACK` while the shell is idle.
  - When the test then types `sleep 2` and a newline, a `TermReport {term_id: T}` with no `kind` comes within 1.5 s after the newline. In the frame log it can come before or after the `TermProc` for `sleep` (the check runs first in a tick). `sleep 2` outlasts two ticks, so the poll sees it.
  - (With the caller as agent the report would go at once; with the shell as `Agent` it would stay through `sleep`. This fails under both.)

### Error Scenarios

- **S22 (CLI usage, exit 2):** `tarmac report`, `tarmac report later`, `tarmac report clear "x"`, and `tarmac report done a b` each exit 2 with a usage line on stderr and do not connect (the double sees no connection).
- **S23 (CLI with no terminal, exit 1):** With `TARMAC_TERM_ID` unset, and again set to an empty string, `tarmac report done "x"` exits 1 with the `needs TARMAC_TERM_ID` line and does not connect.
- **S24 (CLI errors, exit 1):**
  - The double answers `err {msg: "unknown terminal: t9"}` → stderr `tarmac: unknown terminal: t9`, exit 1.
  - No daemon → the `no tarmac daemon running` line, exit 1.
  - A double that never answers → the *no answer* line after about 5 s, exit 1.
- **S25 (the CLI caps the text; CLI test):** A 400-`char` argument reaches the double as 279 `char`s + `…`.
- **S26 (daemon refusals; integration):**
  - `Report` for an id that is not live → `err` `unknown terminal: <id>`, no frame.
  - `Report` with `kind: "later"` for a live T → `err` `unknown report kind: later`, no frame. (The term check comes first, so the test needs a live T.)
  - `Report {T, blocked, text: ""}` from the test process gives a frame with no `text` key.
- **S27 (an old app never marks a report read; integration):** Given an unread report for T, when the app sends `Input` with no `typed` key (an encoded frame from today's encoder), then no report frame comes within 1 s.

Implement however you work best. Only the result is checked. Repository rules that bind you:

- **TDD.** Write each test first and watch it fail on the unmodified tree (`docs/coding-style.md`). The `TarmacApp` change is wiring only. The chip decision is in `ReportChip`, and that is what you test. The walk and the store are pure modules; test them first.
- **Protocol.** Use `rmp_serde::to_vec_named`. Change both codecs in the same change. Add V20–V24 to `tarmac-protocol/src/tests.rs`, `ConformanceTests.swift`, `RustEncoderParityTests.swift` and `docs/protocol.md`. Do not change V1–V19. Do not `cargo fmt`.

- **Locks.** Never hold a `std::sync::Mutex` across `.await`. Take `reports` before `app`, never the reverse. Do not take `boards` or `terms` while you hold `reports`.
- **The poll.** The agent-pid check must run before the `continue` at `term.rs:350`, so a failed leader read does not skip it.
- **Harness.** Add to `tests/common/mod.rs`: a `Spawn` option for `cmd: None`; the `nc` reporter command builder; a `recv_report_for(term_id)` helper; the frame log (*Terms used below*). Keep existing tests green.

- **The exit race.** Use the re-check after `Reports::report` (*Daemon — a report that races the exit*). It has no scenario; review checks it.
- **Daemon safety.** Run daemons only through the `common` harness with a pinned temp socket and state. Never run `tarmacd` or a file under `target/` by hand. Never use `pkill`. Never create file names that are not UTF-8.
- **Docs.** Update `docs/protocol.md`, `docs/architecture.md`, `CLAUDE.md` and `GUIDE.md` as *Interface Contract* says. `make docs-check` must pass.

Test principles (the same ones `/verify` scores against):

- **Behavioral over structural** — assert observable output/effects, not internals; the suite must survive refactoring.
- **Every test can fail** — no copy-pasted expected values, no asserting a constant, no tautologies.
- **Deterministic, isolated, readable** — inject clocks/randomness, no cross-test state, AAA structure with inline setup.

## Trade-offs and Limitations

- **Nested agents in one terminal.** With `claude` running a shell running a second `claude` in the same terminal, the walk stops at the PTY child and takes the member just below it: the *outer* `claude`. The report's lifetime then follows the outer agent, not the inner one that reported. This is rare, and accepted (2026-11-14).
- **The fallback is weaker.** An unattributed caller (a double fork, a parent that exited mid-walk, a failed peer read) gets the leader rule. Inside tmux or a wrapper script the leader is the wrapper, so the report can outlive its agent. The age on the chip is the guard.
- **A report typed at the prompt is held by the shell** [D2]. It ends at the next command that the poll sees (the leader changes, within one poll), at a `clear` or a new report, or when the shell exits. A key dims it. A command that starts and ends between two 750 ms ticks (`ls`, `cd`) is not seen, so the report stays until a longer command. The same holds for a `Leader` holder.
- **A process that was spawned as the PTY's `cmd` is the agent for every caller in that terminal** [D1]. The app never sends `cmd` today, so this case is for scripts and tests.
- **`exec` in a shell makes `spawned_with_cmd` stale** [D1]. After `exec claude`, the PTY child is `claude` but the flag says "shell". A hook's parent is then the child, so the report is taken as typed at the prompt (`Shell`): it ends when `claude` runs its next foreground job, or earlier. The chip is lost early, never wrong.
- **A background board shows no report until it is shown** [D5]. The app drops a frame for a card it has not built, and a lost connection clears every chip. The shown board's restore brings its reports back. The inbox slice (5) needs an all-board replay.
- **Every repeat is unread again** [D3]. A hook that sends the same `done` twice makes the chip bright again. That is a new fact, so it is shown as one.
- **A report is lost at a daemon restart.** The processes it describes die with the daemon.
- **A click with mouse reporting on, or a wheel step, marks a report read.** They are `.user` input (#343). A press that only selects the card does not: it sends no bytes, and so no `Input`. The bell dot clears on that press; the report does not dim.
- **Up to 750 ms of a stale chip.** A report stays until the next tick after its process ends.
- **The `reports` lock is held across a push.** A slow app reader can make a `report` call, a poll tick and a typed-input mark wait for the app channel. This keeps the frames in order. The CLI gives up after its 5 s timeout, but the lock stays held until the channel takes the frame. With no app connected, `push` drops the frame at once, so the lock is not held.

## Open Questions

- [x] **OQ1 — The riskiest assumption: is a Claude Code hook a ppid-descendant of `claude`? Answered yes, 2026-11-14.**
  - Checked with Claude Code 2.1.325, `claude -p`, in a Tarmac terminal.
  - `SessionStart`, `UserPromptSubmit` and `Stop` hooks fired. The hook's parent is the `claude` process itself: one hop, no shell between, nothing re-parented to pid 1.
  - `TARMAC_TERM_ID` reaches the hook. `/dev/tty` does not open in a hook.
  - **Not checked:** the `Notification` hook (the source of `blocked`), interactive mode, and Codex (not installed). Slice 3 checks these before it maps them. The walk does not depend on them: any descendant of the agent is attributed.
- [x] **OQ2 — Decisions D1–D10. Answered 2026-11-14;** see *Gate*.
- [x] **OQ4 — The shell spawn in the harness. Answered yes, 2026-11-14** (a harness-only probe, then S1 and S33). `cmd: None` with `SHELL=/bin/sh` and a temp `HOME` gives `/bin/sh -il`, whose process is `bash` (POSIX mode): `$-` is `himBH` and `set -o` shows `monitor on`, so it has job control; a typed `sleep 2` became the foreground leader (`TermProc sleep`); the prompt is the default `\h:\W \u\$`, so no rc file of the user is read. The first `TermProc` is `tarmacd` (before the exec), so S1 and S33 take the last `TermProc` after the prompt shows.
- [x] **OQ3 — Does `nc -U -w 2 <sock> < <frames>` work as the in-PTY reporter? Answered yes, 2026-11-14.** In the probe, a background `zsh -f -c '<nc>; echo SENT' &` sent `hello` and `open`; the `ack` bytes reached the PTY output and `SENT` showed right after. S1 (background), S33 (foreground at the prompt) and S4 (the `cmd` chain) use it and assert the `ack` bytes or the marker. The `ack` frame's length prefix `00 00 00 07` holds a BEL, so the reporter's terminal also gets a `bell`; the tests assert nothing about bells.
