## Context

HTML doc cards (spec 2607.0004) size their sandboxed iframe in **real screen px**: `cardIframePx({w: frame.w, h: frame.h - HEADER_H}, settledZoom)` gives a `round(frame.w × z)` × `round(frame.h' × z)` element (`desktop/src/kit/cardZoom.ts:13`, consumed at `desktop/src/cards/HtmlCard.tsx:149`), untransformed at rest, with a temporary `scale(zoom/settledZoom)` during a gesture and one resize per `RASTER_SCALE_SETTLE_MS` settle. The inner document therefore lays out against a viewport that **grows with board zoom** — zooming in reveals more content and re-wraps text. That was a deliberate choice (2607.0004 S6: self-contained D3/Canvas dashboards need an honest viewport).

A 2026-07-03 spike (Playwright-bundled WebKit builds, probing Tarmac's exact `sandbox="allow-scripts"` opaque-origin setup) established that modern WebKit ≥ 26.x and Chromium apply standardized CSS `zoom` homothetically inside such an iframe, while WebKit 17.4 (≈ Safari 17.4 / macOS 14 field) no-ops it completely — **and `CSS.supports('zoom','2')` returns `true` on the no-op build**, so capability must be measured, never queried.

## Motivation

Not all agent-written HTML is a dashboard. Prose reports, tables, and static diagrams read badly under reveal-more: zooming in to inspect a chart legend re-flows the paragraphs around it, and the reader loses their place. Magnify gives those documents the same "the page just gets bigger" semantic the rest of the board already has, without taking the honest viewport away from cards that need it.

The runtime capability probe this feature lands is also the blocker on #76 (migrating markdown doc cards off the always-on 9×-area K× oversample). Building it once here, observable and reusable, is the point of doing #75 first.

## Proposed Solution

### Overview

Magnify is achieved by **adding one thing** to the existing render path, not by branching it: the iframe element keeps exactly today's real-px sizing, and the shim additionally sets `document.documentElement.style.zoom = z` at settle. The inner layout viewport then measures `round(frame.w × z) / z ≈ frame.w` CSS px — **constant at every board zoom** — so wrap points freeze while glyphs render at native resolution.

This framing is load-bearing, not incidental. Because sizing is untouched, a WebKit build that no-ops `zoom` lands on byte-identical reveal-more behavior with no fallback code path to maintain. (The alternative sketched in #75 — gate the *sizing* instead, holding the iframe at a fixed logical size — inverts this: a no-op `zoom` there freezes content at 1× inside a growing frame, which is the exact silent failure the issue set out to prevent.)

Mode is declared **in the file** by the agent that wrote it — `<meta name="tarmac-zoom" content="magnify">` — so no board state, no `state.json` key, and no wire-protocol change. Absent the meta tag, a card behaves exactly as it does today.

The shim stays a **dumb sensor and actuator**: it reports raw measurements and the raw meta string upward, and applies whatever zoom value it is handed. Every decision — is this build zoom-capable, did the document ask for magnify, what is the effective mode — is pure TypeScript in `desktop/src/kit/`, where it is unit-testable. No logic is duplicated across the JS/TS boundary.

### Milestone 0 — geometry gate (spike-first, blocks the rest)

The whole design rests on one unverified claim: that root-level `zoom: z` inside an iframe of `W` real px yields a layout viewport of `W / z` CSS px (rather than leaving the initial containing block at `W` units and simply overflowing the frame). Before any card wiring, build `desktop/qa/magnify-probe.html` — a self-contained page holding auto-width prose, a fixed-px box, and a `width:100%` box, which reports after every load and every zoom change: its own rendered line count, `document.compatMode`, `document.documentElement.clientWidth`, `document.body.clientWidth`, an ICB-resolved probe element's `offsetWidth` (`position:absolute; width:100%` — the same read the shim performs), `window.innerWidth`, and the three boxes' `getBoundingClientRect().width`. It reports both on-page and through `console.log`, so the numbers also land in the host console strip (the `sandbox-probe.html` pattern), and it logs every `{tarmac:"zoom"}` message it receives (which is what makes S8's negative observable). It carries **its own root-zoom control** — buttons that set `document.documentElement.style.zoom` to 1 and to 2 — so the gate runs with no shim listener and no `HtmlCard` change: the operator borrows the card (double-click) and clicks the control matching the current board zoom.

Load it as a normal HTML card and compare board zoom 1× (root zoom 1) against board zoom 2× (root zoom 2):

1. **Proceed** iff, across that step: the reported line count is identical, the ICB probe's `offsetWidth` is unchanged within 2 px, `window.innerWidth` doubles within 2 px, the box rect widths double, and no content overflows the card frame. Geometry confirmed — the layout space is `W / z`. The two width readings move differently on purpose, and that difference *is* the gate: `innerWidth` doubles because the iframe **element** doubled (real-px sizing), not because `zoom` touched it — zoom leaves it alone, per Trade-offs — while the ICB probe holds constant only if root `zoom` divided the layout space by exactly the amount the element grew. Both doubling means the assumption is false.
2. **Stop and report** on any other outcome — in particular the ICB probe doubling alongside `innerWidth` (zoom left the initial containing block at `W`), or a changed line count. The `W / z` assumption is false; the sizing split has to be redesigned before anything else is built. Do **not** paper over it by also scaling the element.
3. **Record `compatMode`, root `clientWidth`, and `body clientWidth` regardless of outcome.** They are not gate criteria — they are the evidence that the ICB probe is the compat-independent read and the two `clientWidth` values are not. Expect `BackCompat`, and expect the two `clientWidth` readings to disagree with each other about which one halved.

`magnify-probe.html` stays in the repo as the permanent QA artifact for this feature, mirroring `desktop/qa/sandbox-probe.html`.

### Key Components

- **`kit/zoomMode.ts`** — new pure module, all decision logic, Vitest-tested (node env, no DOM):
  - `declaredZoomMode(metaContent)` — the mode the document asked for.
  - `zoomCapable(probe)` — verdict from the shim's two raw measurements.
  - `effectiveZoomMode(declared, capable)` — magnify only when both hold.
- **`kit/cardConsole.ts`** — `parseCardMessage()` gains a third variant, `ready`, carrying the raw meta string and the raw probe measurements. Unknown/malformed `ready` payloads return `null` like every other bad message (the iframe is untrusted).
- **`desktop/src-tauri/src/card_shim.js`** — three additions, all defensive and decision-free:
  1. On `DOMContentLoaded`: probe **the load-bearing effect itself** — how wide the initial containing block is, in the coordinate space content is laid out in. Append a throwaway `position:absolute; left:0; top:0; width:100%; height:0; visibility:hidden` element as a child of `documentElement`, read its `offsetWidth` (→ `base`), set `documentElement.style.zoom = ZOOM_PROBE_FACTOR`, read `offsetWidth` again (→ `zoomed`), restore, remove the element. Then read `<meta name="tarmac-zoom">` and post `{tarmac:"ready", meta, probe}` to the parent. Four constraints on this measurement, each of which has a known way to go wrong:
     - **It must resolve against the ICB, and nothing else.** An absolutely-positioned element with no positioned ancestor takes the initial containing block as its containing block, so a `width:100%` probe measures the ICB directly — in local CSS px, which is exactly the space wrap points live in. Under root `zoom: 2` a divided ICB reads half. This is why the probe is a **synthetic element and not `documentElement.clientWidth`**: `clientWidth` on the root returns the viewport in standards mode but the `<html>` element's own padding box in quirks mode, and *every* `tarmac-card://` document is quirks mode (`card_protocol.rs` writes the shim's `<script>` ahead of the file's `<!DOCTYPE>`, so the doctype token is discarded). Measured in headless Chromium with the real shim: root `clientWidth` gives ratio 0.5 under the shipped composition and 1.0 with a doctype first — the same engine returning opposite verdicts. A root-`clientWidth` probe is therefore both silently coupled to a file the DoD requires to have an empty diff, and — in quirks mode — measuring an element box, i.e. the proxy this spec rejects in Alternatives Considered. The synthetic probe is compat-mode-independent, and immune to the cases that break a root-`clientWidth` read — `html { width: 900px }`, `html { padding: 24px }`, `html { filter: … }`, and `body { position: relative; width: … }` all measure 0.5 (verified). One narrow exception remains: a card that makes `html` itself a containing block (`position`, `transform`, `filter`, `contain`) **and** fixes its width traps the probe against `html`'s padding box and reads 1.0 — magnify silently off on capable hardware. It fails closed, so this is a documented limitation, not a gate.
     - **Rendering ≠ layout.** Rendering 2× larger and dividing the ICB are separate engine behaviours; only the latter is what magnify needs, and a build that does the first without the second must report incapable.
     - Mutate → read → restore must happen **synchronously in one task**. No paint occurs between synchronous style writes, so the probe cannot flash. Splitting it across a `requestAnimationFrame` or `await` would make it visible.
     - **A zero reading is "not measurable yet", not "incapable" — and `ready` must be deferred until it is measurable.** `App.tsx` renders every board at once and `Board.tsx` puts `display:none` on the inactive ones, so a card whose document loads on a non-active board has no layout at `DOMContentLoaded` and probes `{0, 0}` (measured; the `visibility:hidden` cull path is unaffected and probes normally). Posting that as a verdict makes `zoomCapable` false and, because `ready` is honored once per load, strands the card in reveal until the file is rewritten again — and this is the *dominant* path at app launch for every restored card on a non-active board, not an edge case. So: if `base` is 0, do **not** post; observe with a `ResizeObserver` until the document first has measurable width, then probe and post `ready` once. Three details, each learned by measurement:
       - **`probe.base > 0` is the whole gate.** Do not add a second precondition on `documentElement`'s own box (`getBoundingClientRect().width` or similar): it measures the `<html>` border box, not the ICB — the distinction this probe exists to make. It is *not necessary* (a hidden card with `html{width:900px}` reports a non-zero root width on WebKit while still unrendered, so only `base > 0` blocks the bad verdict) and *not sufficient* (a card with `html{width:0}` on a fully visible board would be stranded forever, never posting, while the ICB probe would have measured 800).
       - **Stay armed, and hop the probe to a macrotask.** Any `ResizeObserver` work that mutates layout *during* delivery makes the engine raise `ResizeObserver loop completed with undelivered notifications`; the shim's own error listener catches it and relays a `Script error.` line into the card's console strip, which also lights the console badge — a phantom error attributed to the card's own JS, in the one surface this feature uses for observability. The shape that pays nothing, measured over 48 hidden loads (4 card styles × reveal/never-reveal × 3 runs × both engines, uninstrumented cards): **leave the observer armed, and run the probe from a one-shot `setTimeout(…, 0)` out of the delivery cycle**, disconnecting only once the verdict is settled. Zero relayed errors in all 16 cells, `ready` correct in all 16.

         Every other shape was measured and each fails a different way. Probing while observed: 1 relayed error per hidden load on WebKit. Disconnect-then-re-observe inside the callback: 14–31 per load on WebKit *and* introduces the error on Chromium. Re-arming from a **microtask** is no better — microtasks drain inside the delivery loop, so the deferred `observe()` still lands in the cycle. And any variant that re-arms at all re-delivers every frame on a non-rendered root, which burns the attempt cap and posts `{0, 0}` **while hidden** at ~240 ms — the stranding the bullet above forbids. The distinction that matters is therefore *never re-observe while waiting*, not merely *when* the re-arm runs. Note also what the errors are not keyed to: they fire during the hidden **load**, not on reveal, and a bare card with no stylesheet reproduces them — CSS is incidental.

         This is the one place the file may use a timer, and it is a one-shot hop per delivery — not the bounded poll rejected below.
       - **A probe that throws is terminal; only a clean zero defers.** If `probeZoom()` throws, post `{base: 0, zoomed: 0}` immediately and once. That fails closed to reveal *and* still emits the capability line, where retrying a throwing probe spins forever (measured: 85 probes and 85 relayed errors in 700 ms against a card whose `offsetWidth` getter throws, terminating on neither engine). Distinguish the two cases explicitly — a clean `base === 0` means "not laid out yet" and defers; an exception means "cannot measure" and is answered now. Bound the deferral with a modest attempt cap regardless, and post the last reading on exhaustion rather than observing forever.
       - **No polling fallback.** `ResizeObserver` is universally present on the macOS 14+ WKWebView floor, and a bounded `rAF` poll is measurably wrong where it would matter: WebKit services `rAF` at ~22 fps inside a `display:none` iframe, so the budget expires while hidden and strands the card permanently. A dead path that is also incorrect is worse than no path; without `ResizeObserver` the card simply stays in reveal, which fails closed. This forbids a *poll* — it does not forbid the single `setTimeout(…, 0)` hop the bullet above requires. `ready` stays exactly-once-per-load, the host's first-ready-wins rule is untouched, and a card on a hidden board simply reports and magnifies the moment its board is first shown. A document that never gets layout never posts — correct, since it is not visible either.
     - `documentElement`'s inline styles must be restored **exactly**, including `overflow` forced to `hidden` for the probe's duration so an appearing or disappearing scrollbar cannot perturb the two reads. Save and restore `documentElement.style.cssText` rather than individual properties: `overflow` is a shorthand, so `style.overflow` reads `""` when only `overflow-x` is set inline and writing `""` back would `removeProperty` both longhands, silently deleting a card author's declaration; the property-wise round-trip also drops `!important` priority, which the getter cannot see.
  2. A `message` listener — **the first parent→child direction in this contract** — accepting `{tarmac:"zoom", z}` only when `event.source === window.parent`, and applying `document.documentElement.style.zoom = z`.
  3. A zoom message arriving before `DOMContentLoaded` is retained — most recent value wins — and applied at ready time (settle and document load race).
  Origin is **never** checked: the shim's document is opaque-origin and the host's origin string is not a stable value to assert on. `ZOOM_PROBE_FACTOR` is the one value mirrored across the JS/TS boundary — the shim hardcodes the numeral it applies to the root, `zoomCapable()` compares against `ZOOM_PROBE_EXPECTED_RATIO` derived from the kit constant — and the two must be kept in sync (the `socket_path()` duplication precedent). `card_protocol.rs` is untouched — the shim is `include_str!`-embedded, so its existing shim-precedes-content tests continue to cover ordering.
- **`desktop/src/cards/HtmlCard.tsx`** — on `ready`, computes the effective mode from the kit helpers and, when it is magnify, posts the current settled zoom; on each settle, posts the new zoom while magnify is effective. When the document carries a `tarmac-zoom` meta tag at all — `meta !== null`, whatever its content, since an unrecognized value is a typo worth surfacing — one `info` line **per document load** is pushed into that card's existing console buffer recording declared mode, capability, and effective mode; a document with no meta tag logs nothing. This is the observability requirement, and it costs no new UI.
- **`desktop/qa/magnify-probe.html`** — the Milestone 0 gate above, retained as permanent QA.

**Unchanged on purpose:** `cardZoom.ts` (both helpers), the iframe element's style and sizing, `card.css`, `Board.tsx`, `App.tsx`, `card_protocol.rs`, the daemon, the CLI, and `tarmac-protocol`. If a diff appears in any of them, something has gone wrong with the approach.

### Data Flow

1. **Load.** Iframe loads `tarmac-card://doc/...?v=<mtime>`; the shim runs before the file's bytes, so `<meta name="tarmac-zoom">` does not exist yet — the meta read is deferred to `DOMContentLoaded`.
2. **Ready.** At `DOMContentLoaded` the shim runs the root-zoom probe (synchronous mutate → read → restore), reads the meta, and posts `{tarmac:"ready", meta, probe}`.
3. **Decide.** `HtmlCard` filters the message to its own `contentWindow`, `parseCardMessage()` validates it, and the kit helpers resolve `declared` → `capable` → `effective`. A non-null `meta` (the tag was present, whatever it said) is logged into the card's console buffer as declared / capable / effective.
4. **Apply.** If effective is magnify, the host posts `{tarmac:"zoom", z: settledZoom}`; the shim sets `documentElement.style.zoom`. If effective is reveal, nothing is posted and nothing changes.
5. **Settle.** The existing MutationObserver path resizes the iframe element to the new real-px box exactly as today, and additionally posts the new zoom while magnify is effective — one relayout per settle, not per frame.
6. **Reload.** A `file_event` bumps `?v=`, the document is replaced, and the handshake repeats from step 2 — a rewritten file may add, change, or drop its meta tag and the mode follows.

### Interface Contract

```
// kit/zoomMode.ts (Vitest, node env)
type ZoomMode = "magnify" | "reveal"

ZOOM_PROBE_FACTOR = 2              // the root zoom the shim applies while probing
ZOOM_PROBE_EXPECTED_RATIO = 1 / ZOOM_PROBE_FACTOR   // the layout space must SHRINK
                                   //   by the zoom, not grow by it. Must be DERIVED,
                                   //   not the literal 0.5 — see below.
ZOOM_PROBE_TOLERANCE = 0.02        // allowed |measured ratio − expected ratio|

declaredZoomMode(metaContent: string | null | undefined): ZoomMode
  // trimmed, case-insensitive "magnify" → "magnify"; everything else → "reveal"

zoomCapable(probe: { base: number; zoomed: number }): boolean
  // base   = the ICB-resolved probe element's offsetWidth before the probe zoom
  // zoomed = the same read under root zoom: ZOOM_PROBE_FACTOR
  // true iff base and zoomed are finite, base > 0, and
  // |zoomed / base − ZOOM_PROBE_EXPECTED_RATIO| <= ZOOM_PROBE_TOLERANCE
  // Ratio 1.0 → false. That single verdict rejects BOTH failing engines: a
  // build that no-ops zoom entirely (WebKit 17.4) and a build that magnifies
  // rendering while leaving the initial containing block at W. Only a build
  // that divides the layout viewport reads ≈ 0.5.
  // The boundary is INCLUSIVE: a measured ratio of exactly 0.48 or 0.52 is
  // capable. Ratios that land on the boundary are never asserted by a
  // scenario or a test — they are not decidable across IEEE-754 rounding.

effectiveZoomMode(declared: ZoomMode, capable: boolean): ZoomMode
  // "magnify" iff declared === "magnify" && capable; otherwise "reveal"

// kit/cardConsole.ts — parseCardMessage() return type gains:
| { kind: "ready"; meta: string | null; probe: { base: number; zoomed: number } }
  // meta must be a string or null; probe.base and probe.zoomed must each be
  // typeof "number" — NaN and Infinity PASS the parse and are rejected later
  // by zoomCapable(), which owns every finiteness/range verdict. Anything
  // else → null. Host→shim payloads arriving inbound ({tarmac:"zoom"}) are
  // not a host message kind → null.

// wire: shim → host (existing direction, one new payload)
{ tarmac: "ready", meta: <string|null>, probe: { base: <number>, zoomed: <number> } }

// wire: host → shim (NEW direction)
{ tarmac: "zoom", z: <number> }
  // posted with targetOrigin "*" (the sandboxed document has an opaque origin,
  // so it cannot be addressed specifically)
  // shim accepts iff event.source === window.parent; origin is never asserted

// document opt-in
<meta name="tarmac-zoom" content="magnify">
```

## Alternatives Considered

### Gate the sizing instead of the zoom

#75's own mechanism sketch: hold the iframe at a fixed logical size in magnify mode and let internal `zoom` do the growing. Rejected — it puts the capability gate on the load-bearing dimension, so a no-op `zoom` yields content frozen at 1× inside a frame that keeps growing. The chosen split makes the fallback free by construction rather than by a correctly-implemented branch.

### `CSS.supports('zoom', '2')` for capability

Rejected on direct spike evidence: returns `true` on WebKit 17.4 where the property has zero layout effect.

### Host-side capability probe in the main document

Simpler to test, and closer to what #76 will eventually need. Rejected for #75 because it measures the wrong document — the effect has to land inside a sandboxed opaque-origin iframe, and only a probe there proves it does. The verdict travels up as data, so #76 can consume it or run the same measurement in its own context.

### Probing a throwaway element's *rendered* size

Zoom an off-screen element and see whether its rendered box grows. Cheaper and safer-looking — no mutation of the live document root at all. Rejected because it measures a *proxy*: whether `zoom` scales rendering, not whether root `zoom` divides the layout space. The spike covered WebKit 17.4 (no-op) and 26.5 (both behaviours) but nothing between, and the Safari 18–25 range plausibly carries a legacy `zoom` that magnifies rendering while leaving the initial containing block alone. A proxy probe reports `capable` there, magnify engages, and wrap points never freeze — a silent wrong-mode failure on field hardware that Milestone 0 on a modern dev machine cannot catch.

Note the chosen probe is also a synthetic element, but it is not this: it is never itself zoomed. Root zoom is applied, and the element is measured in **local layout units** to see whether the ICB it resolves against was divided. Rendering and layout are the distinction, not synthetic versus real.

### Reading `documentElement.clientWidth` under root zoom

The obvious way to ask "did the layout viewport halve", and what this spec originally called for. Rejected on measurement: root `clientWidth` returns the viewport in standards mode but the `<html>` element's own padding box in quirks mode, and every `tarmac-card://` document is quirks mode because the shim's `<script>` precedes the file's doctype. Running the real shim through headless Chromium gave ratio 0.5 under the shipped composition and 1.0 with a doctype first — one engine, opposite verdicts. That makes the verdict silently dependent on `card_protocol.rs`'s composition order (a file the DoD requires to have an empty diff, which reads as decoupled), and in the mode that actually ships it degenerates into measuring an element box — the proxy rejected above. It also breaks outright for any card that fixes its root width (`html { width: 900px }`): `base === zoomed`, magnify disabled on fully capable hardware.

### Per-card chrome toggle instead of `<meta>`

Rejected for this pass: it needs a persistence decision (ephemeral vs. an additive `state.json` key) that buys nothing until magnify has proven itself. The file-declared mode fits the file-as-pipe model — the agent that wrote the content knows whether it is a dashboard or a report.

## Security Considerations

- The host→child message is posted with `targetOrigin: "*"` because an opaque-origin document cannot be addressed specifically. The payload is a single zoom number — no secret, no capability, no path.
- The shim's listener accepts only `event.source === window.parent`, so content nested inside a card cannot spoof a zoom instruction to its parent card.
- `ready` payloads are attacker-controlled (the card wrote them). `parseCardMessage()` must reject malformed ones, and `zoomCapable()` must fail closed to `reveal` on garbage — a hostile card can at worst opt *itself* into a rendering mode.
- No change to the sandbox, the CSP, the `tarmac-card://` handler, or the filesystem trust model.

## Acceptance Scenarios

Verification tags per repo convention (only pure `kit/` logic is unit-tested; the React/Tauri shell is QA'd): **[kit]** Vitest, **[QA]** probe card / manual checklist.

### Happy Path

- **S1** [kit] Given meta contents `"magnify"`, `"  MAGNIFY  "`, and `"Magnify"`, when `declaredZoomMode()` runs, then each returns `"magnify"`; given `null`, `undefined`, `""`, `"reveal"`, and `"magnifying"`, then each returns `"reveal"`.
- **S2** [kit] Given a probe of `{base: 400, zoomed: 200}` (the layout viewport halved), when `zoomCapable()` runs, then it returns `true`; given `{base: 400, zoomed: 400}` — the reading produced both by a build that no-ops `zoom` outright and by one that magnifies rendering while leaving the initial containing block at `W` — then it returns `false`; given `{base: 400, zoomed: 800}` (viewport grew instead of shrank), then it returns `false`.
- **S3** [kit] Given `declared="magnify"` with `capable=true`, when `effectiveZoomMode()` runs, then it returns `"magnify"`; given each of the other three combinations of declared and capable, then it returns `"reveal"`.
- **S4** [kit] Given a `{tarmac:"ready", meta:"magnify", probe:{base:400,zoomed:200}}` message, when `parseCardMessage()` runs, then a `ready` event carrying that meta string and both probe numbers is returned; given `{tarmac:"ready", meta:null, probe:{base:400,zoomed:400}}`, then a `ready` event with `meta === null` is returned.
- **S5** [QA] **Milestone 0 gate.** Given `desktop/qa/magnify-probe.html` opened as a card and borrowed, with its own root-zoom control set to match the board zoom, when board zoom goes from 1× (root zoom 1) to 2× (root zoom 2), then the probe's reported line count is identical at both levels, the ICB probe element's `offsetWidth` is unchanged within 2 px, `window.innerWidth` doubles within 2 px, the fixed-px and `width:100%` boxes' reported rect widths both double, and no content overflows the card frame. `compatMode`, root `clientWidth`, and `body clientWidth` are recorded as evidence but are not pass criteria.
- **S6** [QA] *(rewritten for frozen-K, #95.)* Given a magnify document — the default, so no `tarmac-zoom` meta is needed — when the card is swept continuously from 0.25× to 3×, then **text wrap points never change anywhere in the sweep**: the same line breaks at every zoom, scaled but never reflowed. There is no settle step in this procedure, because there is no settle to wait for — root zoom is posted once at `ready` and the outer `scale(zoom/K)` carries everything after. Decide it by character offset (`desktop/qa/wrap-probe.html`), not by eye or by line count: a count can hold while a break moves. `desktop/qa/wrap-probe-reveal.html` — byte-identical, declaring `reveal` — is the control, and must reflow over the same sweep; a run where both report "no change" is a broken instrument, not a pass. Glyphs are crisp at rest **and mid-gesture** on both a 1× and a 2× display, since `scale(zoom/K)` is a down-scale at every board zoom ≤ K. A document that declares a mode logs exactly one console line per load, reporting declared and effective; a meta-less one logs nothing.

  **History: why settle-time magnify was abandoned.** This scenario originally required "text wrap points never change". Under the settle-time shape, direct measurement in WebKit 26.5 with the real shim falsified it, and S6 was weakened to an ICB-only claim (`700862f`). The measurements below are the record of that falsification — they are *not* a live caveat on the current design. Frozen-K removes the variable they identify, so the original assertion is restored above. Prose line count for one fixed paragraph, settle-time magnify vs reveal-more, across the full board-zoom range:

  | board zoom | 0.5 | 1 | 2 | 3 |
  |---|---|---|---|---|
  | magnify (ICB constant at 460) | 9 | **7** | **7** | 6 |
  | reveal-more | 16 | 7 | 4 | 2 |
  | magnify, Chromium 149 | 7 | 7 | 7 | 7 |

  Settle-time magnify was dramatically more stable than reveal-more and exactly stable over 1×–2×, but two WebKit-specific effects moved wrap points at the extremes, and **neither was a bug in the feature** — the ICB check passed perfectly in all four cells:
  - **z > 2: non-linear text metrics.** The same sentence measures 496 → 461 → 455 layout units at z = 1 → 2 → 3 in WebKit; text is ~7–8% narrower per layout unit as zoom rises, so words migrate up a line. Chromium is perfectly linear (486 at every level). No preference controls this.
  - **z < ~0.6: a used-font-size floor.** WebKit clamps the *used* font size under zoom < 1 — a declared 15px resolves to 18px in layout units at z = 0.5 — which widens text ~20% and adds lines. This is `minimumLogicalFontSize` semantics; a size the author already set below the floor is exempt. **Open item:** measured under Playwright WebKit's defaults; `minimumLogicalFontSize` is not exposed on `WKPreferences`, so whether Tarmac's real WKWebView applies the same floor is unverified.

  Both effects are functions of the *changing* `zoom` value, not of `zoom` itself. Freezing the root zoom at `MAGNIFY_K` removes the variable: the document is laid out exactly once, at one value, so neither the non-linear metrics nor the used-font-size floor has anything left to vary across. That is why the invariance assertion above is decidable again — and why it is now the pass criterion, in place of "judge on the ICB invariant and on magnify being conspicuously more stable than reveal-more".

- **S18** [QA] *(rewritten for frozen-K, #95.)* Given a magnify card, when the document loads, then `magnify-probe.html`'s received-message panel shows **exactly one** `{tarmac:"zoom"}` entry for that load, whose `z` equals the constant `MAGNIFY_K` (not the board zoom) and whose source is `window.parent`; zooming the board to further levels adds **no** further entries, and a reload starts the count again at one. ## Trade-offs and Limitations

- **JS that sizes itself off viewport metrics will not track magnify.** The spike found zoomed content cannot observe its own zoom (`innerWidth`, `devicePixelRatio`, `visualViewport.scale` unchanged), so a D3 chart reading `window.innerWidth` gets a number in a different unit space than its CSS layout. This is precisely why reveal-more stays the default and magnify is opt-in per document — 2607.0004 S6 is unaffected.
- **Two rendering semantics coexist.** Until the minimum supported macOS ships zoom-capable WebKit, HTML cards can behave either way depending on the field build. The console line is the only thing that tells a user which they got.
- **Capability is probed per document load,** not once per app — two forced layouts per HTML card load. Cheap, but not free, and the same verdict is recomputed for every card.
- **The probe mutates the live document root** (`zoom` and `overflow`, both restored in the same task). It cannot flash, but it does force two synchronous layouts at `DOMContentLoaded`, and a document whose own script reads `documentElement.style` during that window would observe the probe's transient values. Accepted: the alternative is a proxy measurement that mis-classifies legacy-`zoom` builds as capable.
- **Magnify has no mid-gesture crispness advantage.** Both modes rely on the existing transform during a gesture and are equally subject to WebKit bug 27684 blur until settle.
- **A card that reloads itself keeps its old mode and logs nothing.** The host's per-load state resets on `lastChangedMs`, which a `location.reload()` from inside the card does not change — so the new document's genuine `ready` is discarded as a repeat, capability is never re-probed, and no second capability line appears. The mode carried over is the one the file declared, so nothing breaks; the strip is simply silent about a load the user cannot see happening. Not worth a second observability channel for a path agent-written cards do not normally take.
- **Magnify freezes the layout viewport, not the wrap points.** The ICB is provably constant, and that is all the mechanism controls; wrap points additionally depend on glyph advances, which WebKit does not scale linearly under `zoom` (~7–8% narrower per layout unit from z=1 to z=3) and which a used-font-size floor widens below z≈0.6. Measured line counts and the Chromium comparison are in S6. Practically: magnify is exactly stable over the 1×–2× range most reading happens in, and drifts by a line at the extremes — still far better than reveal-more's 7→2 over the same span, but "the words never move" is not a promise this can make on WebKit.
- **The probe has a small-card floor.** `offsetWidth` is integer-rounded, so the ratio carries an error of about `0.5 / base`. Negligible at a few hundred px (0.0006 at base 800), but it reaches `ZOOM_PROBE_TOLERANCE` somewhere below ~25 px of card width, and a card with a universal border rule crosses it below ~60 px. A card that small is unreadable anyway, and the failure is closed (reveal), so this is a floor to know about, not to engineer around.
- **No user-facing override.** A document that declares magnify cannot be forced back to reveal-more from the UI, and vice versa; the file is the only control surface.
