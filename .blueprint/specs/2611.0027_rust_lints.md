# 2611.0027 Rust lints

**Date:** 2026-11-22
**Status:** accepted (spec-evaluator and advisor review, 2026-11-22)
**Author:** EP Lin
**Issue:** #468

## Context

The Rust workspace has no lint configuration. `cargo clippy` with its default groups reports 11 findings on `main`, and nothing fails on them. Rules that a tool can decide are written in `CLAUDE.md` and `docs/coding-style.md` and are left to review:

- a `std::sync::Mutex` must not be held across an `.await`;
- Rust must encode with `rmp_serde::to_vec_named`, never `to_vec`;
- never `.unwrap()` in `tarmacd` production code;
- the daemon logs with `tracing`, and the protocol crate logs nothing;
- an `unsafe` block says why it is safe.

The formatter baseline (spec 2611.0026) left two reusable parts: `scripts/check/report.mjs`, which words every failed check, and the exit codes of `scripts/check/fmt.mjs` (0 clean, 1 findings, 2 could not run).

## Motivation

A rule that a deterministic tool can check must not depend on a reviewer or an agent remembering it. Once the tool holds a rule, the prose copy can point at the tool, and a later change removes the rules from prompts.

## Proposed Solution

### Overview

Turn the lints on in one place, clear every finding, and add `make lint`, which fails on a new one. CI runs the same target.

### Key Components

- **`[workspace.lints]` in `core/Cargo.toml`**, inherited by the three crates with `[lints] workspace = true`. Every lint is at `warn`. The one switch that makes a warning fail is `make lint`. (A `deny` in the table would also break `cargo test` during the red phase of TDD, where a `todo!()` stub is the documented first step.)
- **`core/clippy.toml`** — `disallowed-methods` (the two paths of `rmp_serde`'s `to_vec`), `too-many-lines-threshold = 100`, and `allow-unwrap-in-tests`, `allow-dbg-in-tests`, `allow-print-in-tests`.
- **Crate-root attributes** for the rules that belong to one crate. Cargo refuses a crate that inherits the workspace table and also adds lints, so these are `#![warn(...)]` lines: `clippy::unwrap_used`, `clippy::print_stdout`, `clippy::print_stderr` in `crates/tarmacd/src/main.rs`; the two `print_*` lints in `crates/tarmac-protocol/src/lib.rs`. An attribute in `main.rs` covers the production target and its inline test modules, and not the integration tests under `tests/`.
- **`scripts/check/lint.mjs`** — runs `cargo clippy --workspace --all-targets` in `core/`, prints clippy's own text unchanged, then one reporter block. It uses `scripts/check/report.mjs`.
- **`make lint`** — the entry point. `make test` does not run it (it compiles the workspace); CI does.
- **`lint (rust)` job in `.github/workflows/lint.yml`**, on macOS: the daemon's `unsafe` code is behind macOS-only syscalls, so Linux does not compile it.

### The lints

All at `warn`. "Default groups" are clippy's `correctness`, `suspicious`, `style`, `complexity` and `perf`, which are on without a table entry.

| Lint | Why it is here |
| --- | --- |
| default groups | the baseline |
| `clippy::await_holding_lock` | lock discipline; already in a default group, listed so that it is not turned off by accident |
| `clippy::disallowed_methods` | `to_vec_named` only |
| `clippy::undocumented_unsafe_blocks` | every `unsafe` block has a `SAFETY:` comment |
| `clippy::dbg_macro`, `clippy::todo`, `clippy::unimplemented` | a stub or a debug print does not reach a commit |
| `clippy::exit`, `clippy::mem_forget` | one legitimate use each; a new one needs a reason |
| `clippy::cast_possible_truncation`, `clippy::cast_possible_wrap`, `clippy::cast_sign_loss`, `clippy::cast_lossless` | an `as` cast that can lose a value is a decision |
| `clippy::needless_pass_by_value`, `clippy::option_option`, `clippy::too_many_lines` | interface shape |
| `clippy::single_match_else`, `clippy::manual_let_else`, `clippy::match_same_arms`, `clippy::map_unwrap_or`, `clippy::semicolon_if_nothing_returned`, `clippy::redundant_closure_for_method_calls` | one way to write a common form |
| `unused_qualifications`, `trivial_casts`, `unsafe_op_in_unsafe_fn` (rustc) | noise, and unsafe scope |
| `clippy::unwrap_used` (`tarmacd` only) | `docs/coding-style.md` §3 |
| `clippy::print_stdout`, `clippy::print_stderr` (`tarmacd`, `tarmac-protocol`) | `docs/coding-style.md` §3, logging |

Not in this change, each with its own issue: `unreachable_pub` (415 findings, all with a machine fix) and `clippy::significant_drop_tightening` (a nursery lint; its fix narrows a lock scope, which changes run-time behaviour). No lint of clippy's `nursery` group is adopted here; `redundant_clone` is in it.

### How a finding is cleared

In this order:

1. **`cargo clippy --fix`**, then `make fmt`. One commit holds exactly that output and can be made again from its parent.
2. **A hand fix that changes no run-time result**: a signature that borrows where it took a value, a `let … else`, a merged match arm, a `SAFETY:` comment, an `.unwrap()` that becomes `.expect("why")` where the reason is visible in the code beside it.
3. **`#[expect(lint, reason = "…")]` on the narrowest item that compiles**, for a finding whose fix would change what the daemon or the CLI does at run time, or would be a design change (a lossy cast, a function with too many arguments, a function that is too long, a complex type). The reason states a bound only when the code beside it shows the bound; otherwise it names the follow-up issue. `expect`, not `allow`: when the code stops triggering the lint, the stale attribute is itself a finding.

A site that can truncate or wrap a value from outside the process (a pid, a length read from a frame, a size from the terminal) is listed first in the PR body for the maintainer.

### Interface Contract

```
make lint         # exit 0: no finding
                  # not zero: see lint.mjs below
node scripts/check/lint.mjs
                  # exit 0: no finding
                  # exit 1: at least one finding
                  # exit 2: clippy could not run, or the workspace does not compile
```

The script writes nothing to stdout. On stderr it writes clippy's text unchanged, then one report block. "clippy's text" is the rendered text of each compiler message. Cargo's progress lines (`Checking …`, `Finished …`) are not written.

A **finding** is one compiler message at level `warning` or `error` that has a lint name (`clippy::todo`, or a rustc lint such as `unused_variables`) and a primary place. A lint at `deny` level is still a finding (exit 1). A message with an error code (`E0425`), a compiler error with no lint name, or a cargo failure with no compiler message is "cannot run" (exit 2). A count line such as `2 warnings emitted` is not a finding.

Example:

```
✗ lint: 2 findings from clippy
  at   core/crates/tarmacd/src/watch.rs:42:9 clippy::todo
       core/crates/tarmac-cli/src/dev.rs:17:5 clippy::cast_possible_truncation
  fix  correct each one above; `cargo clippy --fix` applies the ones clippy marks as fixable
  then make lint
```

`at` lines are `<repo-relative path>:<line>:<column> <lint>`, one for each finding, sorted by the bytes of the whole line as `report.mjs` sorts them (so `:42:` comes before `:7:`), each one once (clippy reports a shared file once for each target that compiles it).

When the workspace does not compile:

```
✗ lint: cannot run clippy
  why  core/crates/tarmacd/src/watch.rs:42:9 error[E0425]: cannot find value `x` in this scope
  fix  make the workspace compile: cd core && cargo check --all-targets
  then make lint
```

## Alternatives Considered

### `deny` in the lint table, no script

It needs no script. It was not chosen because `cargo test` would then refuse a `todo!()` stub, and because the failure would not carry the next command.

### `RUSTFLAGS=-D warnings`

It changes the flags of every dependency build and so discards the build cache between a lint run and a test run.

### Fix every finding, suppress none

A lossy cast is fixed with `try_from` and an error path, which changes what the program does on a value that does not fit. That is a behaviour decision for the maintainer, one site at a time, and it must not ride on a lint change.

## Acceptance Scenarios

In S1–S5, S9, S10 and S18–S21, the script runs in a small temporary git repository with a one-crate workspace under `core/` that the test creates.

### Happy Path

- **S1:** Given a workspace with no finding, when `node scripts/check/lint.mjs` runs, then it exits 0 and writes nothing to stdout or stderr.
- **S2:** Given a workspace whose lint table has `clippy::todo` at `warn` and one `todo!()`, when the script runs, then it exits 1, stderr holds clippy's own text for that finding, the report's first line is `✗ lint: 1 finding from clippy`, its `at` line is `core/src/main.rs:<line>:<column> clippy::todo`, and it ends with a `fix` line and `then make lint`.
- **S3:** Given two findings, one of them in a module that two targets compile, when the script runs, then the summary says `2 findings from clippy` and each place is listed once, in the byte order of the whole `at` text.
- **S6:** Given the real tree at the head of this change, when `make lint` runs, then it exits 0.
- **S7:** Given the real tree, when `cargo test --workspace` runs in `core/`, then 936 tests pass, the same count as before. The count is the sum of `passed` over every `test result:` line, and every line has `0 failed`.
- **S8:** Given the parent of the `--fix` commit, when these run there in a loop until a pass changes no file — `cargo clippy --fix --workspace --all-targets --allow-dirty` in `core/`, then `make fmt` — then every tracked file is byte-identical to the same file in the `--fix` commit. (One pass is not enough: a fix can produce code that the next pass fixes again, and the formatter can do the same.)

### Edge Cases

- **S4:** Given a workspace that does not compile, when the script runs, then it exits 2, the first report line is `✗ lint: cannot run clippy`, a `why` line holds the place and the compiler's error, and no `at` line is written.
- **S5:** Given a `PATH` with no `cargo`, when the script runs, then it exits 2 with `✗ lint: cannot run clippy` and `why  cargo is not on the PATH`, followed by a `fix` line and `then make lint`.
- **S9:** Given a rustc warning that is not a lint of the table (an unused variable), when the script runs, then it is a finding like any other (exit 1), and its `at` line ends with the rustc lint name (`unused_variables`).
- **S10:** Given an `#[expect(clippy::todo, reason = "…")]` on an item that holds no `todo!()`, when the script runs, then the unfulfilled expectation is a finding (exit 1), and its `at` line ends with `unfulfilled_lint_expectations`.

### The rules fire (on the real tree; each one is a knockout that is reverted)

In S11–S15 and S22, "names X" means: `make lint` exits not zero (make gives its own status), `lint.mjs` exits 1, and an `at` line of the report ends with X. "Does not name X" means no `at` line ends with X.

- **S11:** A `std::sync::MutexGuard` bound to a local and held across an `.await` in `tarmacd` names `clippy::await_holding_lock`. The same holds when a helper function returns the guard.
- **S12:** A call of `rmp_serde::to_vec`, and a call of `rmp_serde::encode::to_vec`, in `tarmac-protocol` (the one crate that depends on `rmp-serde`) each name `clippy::disallowed_methods`. A call of `rmp_serde::to_vec_named` does not.
- **S13:** An `.unwrap()` in non-test code of `tarmacd` names `clippy::unwrap_used`; the same call inside a `#[test]` function, in an integration test under `crates/tarmacd/tests/`, and in `tarmac-cli`, does not.
- **S14:** A `println!` in non-test code of `tarmacd` and of `tarmac-protocol` names `clippy::print_stdout`, and an `eprintln!` there names `clippy::print_stderr`; in `tarmac-cli` neither does.
- **S15:** A `todo!()`, a `dbg!()` outside a test, and an `unsafe` block with no `SAFETY:` comment are each named.

### Documents

- **S16:** `docs/coding-style.md` §3 names the lint beside each rule that a lint now holds, says what `clippy::await_holding_lock` does not see (a guard stored in a struct field), and its §1 says that a `todo!()` stub is for the red phase and that `make lint` refuses it. `CLAUDE.md` describes `make lint`. No ACTIVE doc says the repo has no linter: the sentence "There is no linter and no `.editorconfig` yet." in `CLAUDE.md` and "is no linter yet." in `docs/coding-style.md` are changed. `make docs-check` passes.
- **S17:** Every `#[expect]` that this change adds has a `reason`, and it adds no `#[allow]`. Recorded commands: the count of `#[expect(` attributes in the Rust sources equals the count of `reason = ` strings inside them (an attribute can span lines), and `git diff origin/main...HEAD -- core | grep -c '^+.*#!\?\[allow'` prints 0.

### Added after review

- **S18:** Given a crate with `#![deny(clippy::todo)]` and one `todo!()`, when the script runs, then it exits 1, the report has an `at` line that ends with `clippy::todo`, and no `cannot run` line.
- **S19:** Given a `core/Cargo.toml` that cargo cannot parse, when the script runs, then it exits 2, the first report line is `✗ lint: cannot run clippy`, and a `why` line holds cargo's error.
- **S20:** Given a `PATH` with a `cargo` that has no `clippy` subcommand, when the script runs, then it exits 2 with `✗ lint: cannot run clippy`, a `why` line, and a `fix` line that names `rustup component add clippy`.
- **S21:** Given a directory outside any git repository, when the script runs there, then it exits 2 and the first report line is `✗ lint: not in a git repository`.
- **S22:** On the real tree (a knockout that is reverted), a `todo!()` in the production code of each of `tarmacd`, `tarmac-cli` and `tarmac-protocol` names `clippy::todo`. This shows that each crate inherits the workspace table.
- **S23:** `.github/workflows/lint.yml` has a job named `lint (rust)` on a macOS runner whose last step runs `make lint`. The `test` target of the `Makefile` does not depend on `lint`.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above pass with tests that would *fail if the behavior were wrong*. A green suite that passes for the wrong reason does not satisfy this contract — `/verify` will hunt for vacuous tests by asking, of each behavior, "what is the smallest change that breaks this, and would any test catch it?"

Notes that are specific to this repo:

- S1–S5, S9, S10 and S18–S21 are `node --test` tests beside the script. The pure part (clippy's JSON messages to findings) is tested with messages captured from a real clippy run, not hand-written.
- S6–S8, S11–S15, S17 and S22 are recorded commands on the real tree: put the command and the observed values in the PR body. S16 and S23 are checked by reading the changed files. Revert each knockout by inverting the edit, never with `git checkout <file>`.
- The `--fix` commit holds tool output only. Hand fixes and `#[expect]` attributes go in other commits.
- A fix must not change a run-time result. When in doubt, use `#[expect]` and list the site.
- Do not state an invariant in a `reason` that the code beside it does not show.
- Never run `tarmacd`, `tarmac`, `TarmacApp` or `make run` for this work. Daemons start only through the test harness.

## Trade-offs and Limitations

- `clippy::await_holding_lock` sees a guard bound to a local, also when a helper returned it. It does not see a guard stored in a struct field. The prose rule stays for that case.
- The lint table is at `warn`, so a bare `cargo clippy` or `cargo build` shows findings and does not fail. Only `make lint` and CI fail.
- The toolchain is pinned (`rust-toolchain.toml`), so the set of lints is fixed. A toolchain update can add findings; the commit that updates the pin clears them.
- Suppressed sites are debt. They are counted and listed in the PR, and a follow-up issue holds the lossy casts.
- `make lint` compiles the workspace: about 12 seconds from cold and 1 second after a small edit, measured before this change.

## Decisions

1. **The `correctness` group.** It stays at clippy's own level, `deny`: a correctness finding is a bug, and failing every build on it is right. "Every lint is at `warn`" means every entry of the table. For the script, a lint at `deny` is a finding like any other (exit 1).
2. **`#[allow]`.** This change adds none. Every suppression is an `#[expect]` with a `reason`.
3. **`allow-expect-in-tests`.** Not set: `clippy::expect_used` is not in the list.
4. **A workspace that does not compile.** One `why` line for each compiler error, each one once.
5. **The suppressed sites.** S24 below records them.

- **S24:** The PR body holds a table of every `#[expect]` this change adds: lint, place, reason. Its row count equals the count that `git diff origin/main...HEAD -- core | grep -c '^+.*#\[expect('` prints, and the sites that can truncate or wrap a value from outside the process are first.
