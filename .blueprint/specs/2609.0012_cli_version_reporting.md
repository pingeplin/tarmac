# 2609.0012 `tarmac --version` reports CLI, daemon, and app versions

**Date:** 2026-09-08
**Status:** implemented
**Author:** EP Lin
**Issue:** [#129](https://github.com/pingeplin/tarmac/issues/129) `feat(cli): add --version reporting cli, daemon, and app versions`

## Context

Tarmac ships three components from one version bump — the `tarmac` CLI, `tarmacd`, and
`Tarmac.app` — but they **install and restart independently**, so skew is normal. Issue #129
documents a live instance minutes after `brew upgrade` to 0.10.1: the on-disk CLI and bundle
were 0.10.1 while the *running* daemon (pid 8275) and app (pid 8261) were still executing the
now-unlinked 0.10.0 inodes.

Nothing can report that state today. `tarmac --version` falls into the unknown-command arm and
is a usage error (exit 2, `core/crates/tarmac-cli/src/main.rs:70-73`), while `tarmacd --version`
already exists (`core/crates/tarmacd/src/main.rs:64-67`). The app's restart-on-mismatch check
(`desktop/src-tauri/src/bridge.rs:383-388`) compares only *its own* version against
`HelloOk.daemon_version` — in the state above both were 0.10.0, so it correctly did nothing.
Nothing anywhere compares the **CLI** against the daemon it just spoke to.

The CLI already performs the `Hello`/`HelloOk` handshake and **discards** `daemon_version` and
`daemon_pid` (`core/crates/tarmac-cli/src/main.rs:124-126`). The app version is the only piece
with no source at all: `Msg::Hello { role, v }` carries no version, and the daemon knows only
its own.

A dev worktree compounds this: a debug `core/target/debug/tarmac` earlier on `PATH` shadows the
installed release CLI **and** resolves a different channel and socket
(`current_channel()`, spec 2606.0003), so it may be ringing a different daemon than the user
thinks.

## Motivation

"Which three versions am I actually running?" is the first question when behaviour is off, and
it currently needs `defaults read /Applications/Tarmac.app/Contents/Info.plist` plus `lsof` on
the daemon pid. One CLI verb should answer it — and must answer with the **running** versions,
because the running/installed distinction is precisely where the bug hides.

## Proposed Solution

### Overview

Three additive optional protocol keys carry the app's identity to the CLI, and a new
`--version` verb renders all three versions plus the resolved channel and socket path.

1. **`Hello.app_version`** (`Option<String>`) — the app stamps its `CARGO_PKG_VERSION` on its
   handshake. The CLI never sets it.
2. **`HelloOk.app_version`** (`Option<String>`) — the daemon retains the connected app's
   reported version and hands it back to CLI clients.
3. **`HelloOk.app_connected`** (`Option<bool>`) — whether an app currently holds the daemon's
   app slot, independent of whether that app reported a version. Without it, "an app is connected
   but predates `app_version`" is indistinguishable from "no app is connected", and the CLI would
   print `not connected` while an app *is* connected. That state is reachable (the app's
   daemon-restart is restart-once-guarded — see Trade-offs), and printing an inferred absence
   would break Tarmac's core invariant that every reported mark is backed by an observed fact.
4. **`tarmac --version`** — one handshake, five labelled lines, exit 0 in every socket/daemon
   state (a wrong argument count stays a usage error, exit 2, like every other verb).

This is **route 1** of issue #129's open question. Route 2 (reading
`Tarmac.app/Contents/Info.plist`) is rejected in Alternatives: it reports the *installed*
bundle, which in the motivating skew is exactly the version that is **not** running — it would
have printed 0.10.1/0.10.1 and hidden the problem.

### Key Components

- **`core/crates/tarmac-protocol/src/lib.rs`** — `Hello` gains `app_version: Option<String>`;
  `HelloOk` gains `app_version: Option<String>` and `app_connected: Option<bool>`. All three carry
  `#[serde(default, skip_serializing_if = "Option::is_none")]`, matching the existing
  `daemon_version`/`daemon_pid` treatment. `None` omits the key, so conformance vector 2's
  **bytes are unchanged**; only its struct literal gains `app_version: None`.
- **`core/crates/tarmacd/src/state.rs`** — `AppSlot` gains `version: Option<String>`;
  `install_app(tx, version)` stores it. The slot is already cleared generation-safely by
  `remove_app` on app-session exit (`conn.rs:220`), so a dead app is never reported as running.
  Slot *presence* is what `app_connected` reports; the stored `version` is what `app_version`
  reports.
- **`core/crates/tarmacd/src/conn.rs`** — the handshake destructures `Hello.app_version`. The
  reply builder takes what to report about the app: the **`cli` arm** passes the current slot's
  presence and stored version; the **`app` arm** passes "absent / no version" (it must not echo a
  stale predecessor's version back at a freshly connecting app). Only `role == "app"` stores a
  version.
- **`desktop/src-tauri/src/bridge.rs`** — the app's `Hello` sets
  `app_version: Some(env!("CARGO_PKG_VERSION").into())`.
- **`core/crates/tarmac-cli/src/main.rs`** — connect + handshake is extracted from `open()` into
  a helper returning the `HelloOk` fields; `open()`'s observable behaviour is unchanged. A new
  `--version` arm renders the report. `HELP_HEAD` lists the verb.
- **Docs** — `docs/protocol.md` §Handshake documents `hello.app_version`, `hello_ok.app_version`,
  `hello_ok.app_connected`, and the already-shipped-but-undocumented `hello_ok.daemon_pid`.
  **Three** files assert "`open` is the only verb that talks to the daemon" — now false — and all
  three must instead name `open` and `--version`: `docs/architecture.md:24-25`, root
  `CLAUDE.md:11`, and `README.md:159` (whose CLI verb list at `:153-156` must also gain the
  `tarmac --version` line). And `docs/architecture.md`'s handshake summary (line ~113,
  `HelloOk { v, daemon_version? }`) plus its message table (line ~129-130, `Hello {role, v}` /
  `HelloOk {v}`) go stale the moment the keys ship — both must name the new keys.

### Data Flow

1. The app connects and sends `Hello { role:"app", v:1, app_version:Some("0.10.2") }`.
2. The daemon replies `HelloOk { .., app_version: None, app_connected: None }` **and then** fills
   the app slot with that version — reply first, store second (`conn.rs:64` writes the reply;
   `install_app` is not reached until `conn.rs:173`). The reply makes no claim about any app,
   because at the moment it is built the daemon's own slot state is not yet what this connection
   is about. This ordering is what the S4/S8/S30/S31 race guidance below depends on.
3. `tarmac --version` connects and sends `Hello { role:"cli", v:1, app_version: None }`.
4. The daemon replies `HelloOk { v, daemon_version, daemon_pid, app_version, app_connected }`,
   where `app_connected` is whether the app slot is occupied **at that moment** and `app_version`
   is that app's reported version (`None` if it reported none, or if the slot is empty). Both keys
   are omitted entirely for an `app` client (step 2).
5. The CLI prints the report and exits 0. It sends no further frames and closes.

### Interface Contract

Wire (additive, optional; a missing key decodes to `None`):

```
{t:"hello",    role:"cli"|"app", v:1, app_version?:"<semver>"}
{t:"hello_ok", v:1, daemon_version?:"<semver>", daemon_pid?:<u32>,
               app_version?:"<semver>", app_connected?:<bool>}

`app_version` and `app_connected` are **only** sent to a `cli` client. To an `app` client the
daemon sends neither key (both `None`) — it makes no claim about any app to an app. Sending
`app_connected: false` to a second app while the first still holds the slot would be an
observably false statement, which is precisely what this key exists to avoid.
```

`tarmac --version` (exactly one argument) writes its report to **stdout**, writes **nothing to
stderr**, and exits **0** in every reachable socket/daemon state — including no daemon, a refused
connect, and a rejected handshake. `tarmac --version <anything>` is a usage error (exit 2, message
on stderr), matching `tarmac open`'s and `tarmac skill`'s existing wrong-arity handling.

The report is exactly **five** lines, in this order. Each line is
`format!("{:<8} {}\n", label, value)` — the label left-aligned and **right**-padded with spaces to
8 columns, then a single space, then the value, so every value begins at column 10:

```
cli      0.10.2
daemon   0.10.0 (pid 8275)
app      0.10.0 (running)
channel  release
socket   /Users/ep/Library/Application Support/tarmac/tarmacd.sock
```

Every value is a single line: any embedded newline in a reason string is replaced by a space, so
the report is five lines in every state.

Per-line value grammar:

| line | condition | value |
|---|---|---|
| `cli` | always | the CLI binary's `CARGO_PKG_VERSION` |
| `daemon` | `HelloOk` with version and pid | `<ver> (pid <n>)` |
| `daemon` | `HelloOk` with version, no pid | `<ver>` |
| `daemon` | `HelloOk` without a version | `connected (version not reported)` |
| `daemon` | `UnixStream::connect` failed — for **any** reason (socket absent, connection refused, permission denied, path is not a socket) | `not running` |
| `daemon` | connected, but no `HelloOk` arrived — an `Err` reply, a non-`hello_ok` reply, EOF before the reply, or the 5s read timeout; **or** the socket path was never dialled because it exceeds the `sun_path` cap | `unreachable (<reason>)`, where the reason for an `Err` reply **contains the daemon's `Err.msg`, newline-flattened**, and for the over-long path is `proto::check_socket_path_len`'s own message |
| `app` | `HelloOk.app_version` is `Some` | `<ver> (running)` |
| `app` | `app_version` is `None`, `app_connected` is `Some(true)` | `connected (version not reported)` |
| `app` | `app_version` is `None`, `app_connected` is `Some(false)` | `not connected` |
| `app` | `app_version` and `app_connected` both `None` (a daemon older than these keys) | `unknown (daemon predates this key)` |
| `app` | no `HelloOk`, because the daemon is `not running` | `unknown (no daemon)` |
| `app` | no `HelloOk`, because the daemon is `unreachable` | `unknown (daemon unreachable)` |
| `channel` | always | `dev` or `release` — `proto::channel_label(current_channel())` |
| `socket` | always | the resolved socket path, `TARMAC_SOCKET` honoured |

The `app` value **always** states the source: `(running)` — the app that is currently connected
to this daemon. The installed bundle is never read, so the output can never be mistaken for it.
Every non-`(running)` value names *why* no version is available, so an absent version is never
confusable with a reported one, and "no app" is never inferred from "no version".

**`app_connected` is what makes `not connected` an observed fact rather than an inference.** With
`app_version` alone, a connected app that predates the key would render `not connected` — a
statement about a process the CLI never observed. The two rows above that mention it are the whole
reason the key exists; an implementation that renders `not connected` for a `None`/`None` reply
is wrong even though every other scenario would still pass.

`tarmac open`'s contract is unchanged, including its exit-1-on-absent-socket behaviour.
`HELP_TAIL`'s `EXIT STATUS` block currently attributes exit 1 to "no daemon is running", which is
now wrong for `--version`; it must state that `tarmac --version` exits 0 even when no daemon is
running.

## Alternatives Considered

### Route 2 — the CLI reads `Tarmac.app/Contents/Info.plist`

No protocol change, but it guesses the bundle path and reports the **installed** app. In the
motivating skew that is 0.10.1 while the running app is 0.10.0 — it would have printed a
matching pair and hidden the defect the feature exists to expose. Rejected.

### An offline `--version` that skips the socket probe

`docs/architecture.md` currently claims `open` is the CLI's only daemon-talking verb; a flag
could preserve that. But the daemon and app versions are the *point* of the verb, and a
CLI-version-only mode is `--version | head -1`. The invariant is documentation, not a
constraint — update the docs instead. Rejected (raised as an Open Question).

### `-V` / bare `version` aliases

Not in the issue's acceptance list; `tarmacd` accepts only `--version`. Keeping one spelling
keeps the two binaries consistent. Rejected.

## Acceptance Scenarios

### Protocol additivity (automated — `core/crates/tarmac-protocol`)

- **S1:** Given `Hello { role:"app", v:1, app_version:None }`, when encoded, then the bytes are
  **equal to conformance vector 2's pinned hex** (`83 a1 74 a5 68 65 6c 6c 6f a4 72 6f 6c 65 a3
  61 70 70 a1 76 01`), and that pinned hex still decodes back to the same value. (Byte equality,
  not just "no `app_version` substring" — `assert_vector` alone never checks encode output.)
  **Deliberately stricter than the wire contract:** `docs/protocol.md:489` says byte-exact encoder
  output is *not* required and key order may legally differ. S1 asserts it anyway because the
  point being pinned is narrower — that adding an `Option` field with `skip_serializing_if` emits
  **no extra key and no map-size change** for the existing message. It holds regardless of where
  the field is declared in the struct. This is a regression guard on additivity, not a new wire
  requirement, and protocol.md must not be edited to claim otherwise.
- **S2:** Given `Hello` and `HelloOk` values carrying `app_version: Some("9.9.9")`, when
  encode→decode round-trips them, then the value survives on both types.
- **S3:** Given a `hello_ok` wire frame written without an `app_version` key, when decoded, then
  `app_version` is `None`.

### Daemon relay (automated — `core/crates/tarmacd/tests/`)

- **S4:** Given an app client whose `Hello` carried `app_version: Some("9.9.9")`, when a `cli`
  client handshakes, then its `HelloOk.app_version` is `Some("9.9.9")`.
- **S5:** Given a daemon no app has ever connected to, when a `cli` client handshakes, then
  `HelloOk.app_version` is `None` **and `app_connected` is `Some(false)`** — the daemon reports
  the empty slot as an observed absence, not as an unset key.
- **S6:** Given an app that connected reporting a version and then disconnected, when a `cli`
  client handshakes, then `HelloOk.app_version` is `None` and `app_connected` is `Some(false)` —
  a dead app is never reported as connected.
- **S7:** Given a `cli` client that sends `app_version: Some("6.6.6")` in its own `Hello`, when a
  second `cli` client handshakes, then `HelloOk.app_version` is `None` **and `app_connected` is
  `Some(false)`** — a `cli` hello never fills the app slot, so only the `app` role's version is
  retained and a cli client is never mistaken for an app.
- **S8:** Given an app connected reporting `"9.9.9"`, when a **second** app connects reporting
  `"7.7.7"` and reads its own `HelloOk`, then `app_version` is `None` — neither the predecessor's
  stored version nor its own is echoed back to an app. (The two-app form catches *any*
  implementation that consults the slot while building an `app` reply, whether it stores before or
  after replying; the one-app form only catches store-then-echo-own.)
- **S9:** Given a connected app, when a `cli` client handshakes, then `HelloOk.daemon_version`
  equals the daemon binary's `CARGO_PKG_VERSION` and `daemon_pid` equals the daemon process's
  pid (existing behaviour must survive the change).
- **S30:** Given an app client whose `Hello` carried **no** `app_version` (a pre-key app), when a
  `cli` client handshakes, then `HelloOk.app_version` is `None` but `app_connected` is
  `Some(true)` — the presence of an app is reported independently of its version. This is the
  scenario `app_connected` exists for; without the key it is indistinguishable from S5.
- **S31:** Given an app connected reporting `"9.9.9"`, when a **second** app connects and reads
  its own `HelloOk`, then **both** `app_version` and `app_connected` are `None` — the daemon makes
  no claim about any app to an app. `Some(false)` would be worse than silence here: app 1 still
  holds the slot, so it would be an observably false statement.

### CLI rendering (automated — `core/crates/tarmac-cli/tests/cli.rs`, against an in-test
fake daemon speaking the wire protocol)

- **S10:** Given a fake daemon replying
  `HelloOk { daemon_version:"9.9.9", daemon_pid:4242, app_version:"8.8.8", app_connected:true }`,
  when `tarmac --version` runs against it, then it exits 0 and stdout contains the lines
  `daemon   9.9.9 (pid 4242)` and `app      8.8.8 (running)` verbatim.
- **S11:** Given that same fake daemon, when `tarmac --version` runs, then the `cli` line reports
  the CLI binary's own `CARGO_PKG_VERSION` — which differs from the daemon's `9.9.9`, so the skew
  is visible in the output.
- **S12:** Given a fake daemon replying `HelloOk` with `app_version: None` and
  `app_connected: Some(false)`, when `tarmac --version` runs, then it exits 0 and the app line
  reads `app      not connected` — and no digit from the daemon's `9.9.9` leaks onto the app line
  (no version string is invented).
- **S32:** Given a fake daemon replying `HelloOk` with `app_version: None` and
  `app_connected: Some(true)`, when `tarmac --version` runs, then it exits 0 and the app line
  reads `app      connected (version not reported)` — an app that is observed but silent is
  **not** rendered as absent. Distinguishing S32 from S12 is the whole point of `app_connected`;
  an implementation that ignores the key passes S12 and fails here.
- **S33:** Given a fake daemon replying `HelloOk` with **neither** `app_version` nor
  `app_connected` (a daemon older than these keys — the exact motivating skew, a freshly upgraded
  CLI against a still-running old daemon), when `tarmac --version` runs, then it exits 0, the
  daemon line still reports that daemon's version and pid, and the app line reads
  `app      unknown (daemon predates this key)` — neither `not connected` nor an invented
  version.
- **S13:** Given `TARMAC_SOCKET` pointing at a path with no socket, when `tarmac --version` runs,
  then it exits **0**, **stderr is empty**, the daemon line reads `daemon   not running`, the app
  line reads `app      unknown (no daemon)`, and the CLI version is still reported — it must not
  fail the way `tarmac open` does (exit 1) in the same state.
- **S14:** Given the same absent-socket run, when the output is inspected, then the channel line
  reads `channel  ` followed by the label the *test binary's own build config* implies
  (`if cfg!(debug_assertions) { "dev" } else { "release" }`, so `cargo test --release` does not
  make the test lie), and the socket line is `socket   <the exact TARMAC_SOCKET value>` — so a
  shadowing debug CLI pointed at the wrong socket is self-evident.
- **S15:** Given `TARMAC_SOCKET` set to a path of 104 bytes or more (the macOS `sun_path` cap
  enforced by `proto::check_socket_path_len`), when `tarmac --version` runs, then it exits 0, the
  daemon line starts `daemon   unreachable (` — **not** `not running`, because the daemon was
  never dialled and its absence was never observed — the app line reads
  `app      unknown (daemon unreachable)`, and the socket line still shows that over-long path.
  It must not error out the way `open` does.
- **S16:** Given a fake daemon that answers the handshake with `Err { msg: "go away\nnow" }`, when
  `tarmac --version` runs, then it exits 0, the whole report is **exactly 5 lines**, the daemon
  line starts `daemon   unreachable (` and contains `go away now` (the embedded newline flattened
  to a space), and the app line reads `app      unknown (daemon unreachable)`.
- **S17:** Given a fake daemon replying `HelloOk` with `daemon_version: None` but
  `app_version: Some("8.8.8")`, when `tarmac --version` runs, then it exits 0, the daemon line
  reads `daemon   connected (version not reported)`, **and the app line still reads
  `app      8.8.8 (running)`** — a missing daemon version does not suppress the app line.
- **S18:** Given `tarmac --help`, when it runs, then it exits 0, its usage block lists
  `tarmac --version`, and its `EXIT STATUS` block says `tarmac --version` exits 0 even with no
  daemon running.
- **S29:** Given a fake daemon replying `HelloOk { daemon_version:"9.9.9", daemon_pid: None }`
  (a pre-`daemon_pid` daemon), when `tarmac --version` runs, then it exits 0 and the daemon line
  is exactly `daemon   9.9.9` — no empty `(pid )` suffix.
- **S19:** Given `tarmac open <path>` with `TARMAC_SOCKET` pointing at an absent socket, when it
  runs, then it still exits **1** with the existing one-line `no tarmac daemon running` error —
  the handshake extraction did not change `open`.
- **S23:** Given the fake daemon of S10, when `tarmac --version` runs, then stdout is **exactly**
  these five lines (byte-for-byte, values computed in-test):
  `cli      <the test crate's CARGO_PKG_VERSION>`, `daemon   9.9.9 (pid 4242)`,
  `app      8.8.8 (running)`, `channel  <the label S14 computes>`,
  `socket   <the temp socket path>` — the whole format, not just its parts. The channel line uses
  the same computed placeholder as S14, **not** a hardcoded `dev`: hardcoding it would make this
  test fail under `cargo test --release`, contradicting S14. Stderr is empty here too, pinning the
  stdout-only rule on the success path as well as S13's failure path. One exact-match test
  satisfies S10, S11, and S23 together; they are kept as separate IDs only because they are
  referenced individually.
- **S24:** Given a fake daemon that records every frame it receives, when `tarmac --version` runs,
  then the **only** frame it received is `Hello { role:"cli", v:1 }` whose encoded payload
  contains no `app_version` key — the CLI never sets `app_version` and sends nothing after the
  handshake. **Not assertable, deliberately omitted:** "and then closed the connection". A
  subprocess's fds are closed by process exit either way, so a fake daemon observes the same EOF
  whether or not the CLI drops the stream — an assertion on it can never fail and would be
  decorative. "Sent no second frame" is the observable half, and it is what the test pins.
- **S25:** Given a fake daemon that accepts the connection and closes it without replying, when
  `tarmac --version` runs, then it exits 0, the daemon line starts `daemon   unreachable (`, and
  the app line reads `app      unknown (daemon unreachable)`.
- **S26:** Given `tarmac --version extra`, when it runs, then it exits **2** with a usage error on
  stderr and prints no report — matching `tarmac open` / `tarmac skill` wrong-arity handling.
- **S27:** Given a fake daemon that replies `Err { msg }` to `tarmac open <path>`, when it runs,
  then it still exits **1** with the existing `daemon rejected handshake: <msg>` error — the
  handshake extraction preserved `open`'s reject path too.
- **S34:** Given a fake daemon that accepts the connection and then holds it open **without ever
  replying**, when `tarmac --version` runs, then it terminates on its own within 15s wall clock,
  exits 0, and the daemon line starts `daemon   unreachable (`. This is the only scenario pinning
  the 5s read timeout, and the only failure mode where a bug makes the CLI **hang forever** rather
  than print something wrong — worth its ~5s of suite time. (S25 covers the fast EOF path; a
  silent-but-open peer is a different code path.)

### App handshake (automated — `desktop/src-tauri/src/bridge.rs`'s `mod tests`, `cargo test`)

- **S28:** Given the encoded payload returned by `bridge.rs`'s app-hello builder, when it is
  decoded, then it equals
  `Hello { role:"app", v:1, app_version: Some(env!("CARGO_PKG_VERSION").into()) }` — the app, not
  just the protocol, actually reports its version. Nothing else in the suite covers this: without
  it, `bridge.rs` could keep sending the old two-key hello and S1–S27 would all stay green.

  **Making it observable.** The hello is currently built inline inside `run_connection`
  (`bridge.rs:369`), an `async fn` taking a real `AppHandle` and `UnixStream` — untestable as-is.
  Extract the payload into a pure helper (`fn app_hello_payload() -> Vec<u8>`, the encode
  included) and have `run_connection` write exactly that helper's return value, so the call site
  is a single expression with nothing left to get wrong. `bridge.rs`'s `should_restart` (`:267`)
  and `resolve_daemon_path_pure` (`:518`) are the precedent for this seam, and `#[cfg(test)] mod
  tests` (`:676`) is where the assertion goes. **Named residual risk:** no test proves
  `run_connection` calls the helper — that link is held by code review of a one-line call site.
  This is accepted rather than papered over; the alternative is standing up a fake daemon plus a
  Tauri `AppHandle` in a unit test, which buys less than it costs.

### Docs (refereed by `/verify` — `make docs-check` plus the named greps below)

`docs-check.mjs` has no prose rule (rule 4 only checks that each `Msg` *variant* is named in both
docs), so it cannot catch S21/S22 — those are deterministic greps a reviewer or a `/verify` step
runs, not unit tests.

- **S20:** Given the implemented change, when `make docs-check` runs, then it passes — a guard on
  rules 1–3 (banner, link rot, cited paths) against the docs edits, not on their content.
- **S21:** Given `docs/architecture.md`, root `CLAUDE.md`, **and `README.md`**, when grepped for
  `verb that talks to the daemon`, then none of the three still claims `open` is the CLI's only
  daemon-talking verb,
  each names `--version` as the second one, and `README.md`'s CLI verb list includes a
  `tarmac --version` line. (All three carry the claim today — `architecture.md:24-25`,
  `CLAUDE.md:11`, `README.md:159` — so grepping only the first two would leave a false statement
  shipped in the most-read file of the three.) **The needle matters:** in `architecture.md` the
  phrase wraps a line break (`:24` ends "`open` is its only", `:25` begins "verb that talks to the
  daemon"), so `grep "only verb"` matches `CLAUDE.md` and `README.md` but **not**
  `architecture.md` — it would pass a file that still carries the stale claim.
  `verb that talks to the daemon` matches all three.
- **S22:** Given `docs/protocol.md`, when grepped for `app_version`, `app_connected`, and
  `daemon_pid`, then its §Handshake documents `hello.app_version`, `hello_ok.app_version`,
  `hello_ok.app_connected`, and `hello_ok.daemon_pid`, each stated as optional and each stating

Repo-specific constraints that override any general instinct:

  committed repo. Match surrounding style by hand.

  `app_version: None`); its hex does not.

  Encoding stays `rmp_serde::to_vec_named`.
- Grep every `Msg::Hello {` / `Msg::HelloOk {` **construction and exhaustive destructure** across
  `core/` and `desktop/src-tauri/`. The literals that must be updated today:
  `core/crates/tarmac-protocol/src/lib.rs` (vector 2, `all_message_types_roundtrip`,
  `hello_ok_daemon_version_additive`), `core/crates/tarmac-cli/src/main.rs:124`,

- The daemon **must not** hold a `std::sync::Mutex` across an `.await`; `daemon.app` is a
  `tokio::sync::Mutex` — read the version and drop the guard.
- **The daemon writes `hello_ok` *before* `install_app` runs** (`conn.rs`: the reply is sent in
  `handshake`, the slot is filled at the top of `app_session`). So receiving an app's `HelloOk` is
  **not** proof the slot is populated — a `cli` probe fired straight after it can legitimately read
  an empty slot. Every daemon-relay test that connects an app and then probes (S4, S8, S30, S31)

  sleep.

  `tarmac_protocol` throughout `tests/`. `frame::write_sync` / `read_sync`
  (`tarmac-protocol/src/lib.rs:407,419`) are **not** behind the `async` feature gate (that starts

  tokio or the `async` feature.
- Verify with `make test` (which runs `make docs-check` first). `make` must pass before the PR.

Write tests to the project's conventions and these principles:

- **Behavioral over structural** — assert observable output/effects, not internals.
- **Every test can fail** — the sentinel versions (`9.9.9` daemon, `8.8.8` app, `7.7.7`/`6.6.6`
  second-client, pid `4242`) are deliberately unlike any real version, and distinct from each
  other, so no assertion can pass by coincidence or by reading the wrong field.
- **Deterministic, isolated, readable** — no cross-test state; each fake daemon binds its own
  temp socket.

## Trade-offs and Limitations

- **A version-less app is reported as `connected (version not reported)`, not by version.** A
  pre-key app connecting to a post-key daemon sends no `app_version`. The app SIGTERMs+respawns any
  daemon whose version differs from its own (`bridge.rs:383-410`), which usually clears the skew —
  **but that restart is guarded to happen at most once per app session**
  (`docs/protocol.md:63-66`), so an old running app that has already used its restart proceeds
  against a newer daemon indefinitely. `app_connected` makes that state honest rather than a false
  `not connected`, but the app's *version* genuinely is unknowable there; the CLI says so instead
  of guessing. The same is true in reverse for a pre-key **daemon** (`unknown (daemon predates this
  key)`) — which is the common case for the first release that ships this verb, since the whole
  point is that the running daemon is often the older binary.
- **`app_connected` is a third protocol key for a comparatively rare state.** Weighed and accepted:
  the alternative renders a *wrong* fact (`not connected` for a connected app) in exactly the skew
  scenario the verb exists to diagnose, and Tarmac's stated invariant is that every reported mark
  is backed by an observed fact rather than inferred. The key is `Option<bool>`, set in the same
  place as `app_version`, and costs one match arm.
- **Every `connect` failure renders `not running`, whatever the errno.** A permission-denied or
  not-a-socket `TARMAC_SOCKET` is reported the same as an absent one. Accepted deliberately: an
  errno taxonomy in the output would need platform-dependent tests for renderings no user acts on
  differently, and the `socket` line already names the exact path to inspect. The one
  pre-connect failure that *is* distinguished is an over-long path, because
  `check_socket_path_len` runs before `connect` (`tarmac-cli/src/main.rs:113-114`) — nothing was
  ever dialled, so "not running" would be an unobserved claim.
- **`--version` reports the app connected to *this* daemon**, not every Tarmac on the machine. A
  second app on another channel's socket is invisible — which is the intent: the `channel` and
  `socket` lines say exactly which daemon was asked.
- **The installed bundle version is not reported.** Deliberate (see Alternatives); the running
  app is the version that matters for skew.
- `--version` now touches the socket, so it is no longer instantaneous when the socket path is
  unreachable in a way that blocks (NFS, etc.). Mitigated by the same 5s read/write timeouts
  `open` uses.

## Open Questions

- [ ] Should a future `--version --offline` (or `--no-probe`) restore a socket-free version
      query? Not in scope here; the docs invariant is being updated instead.
- [x] **RESOLVED — a connected-but-version-less app must not render as `not connected`.** The
      evaluator showed the state is reachable (the app's daemon-restart is restart-once-guarded,
      so a pre-key app can sit connected to a post-key daemon indefinitely). Rendering an inferred
      absence there is the exact false-negative this feature exists to prevent, and it would
      violate Tarmac's observed-fact invariant. **Decision: add `HelloOk.app_connected`
      (`Option<bool>`)** and render four distinct app states — `<ver> (running)`,
      `connected (version not reported)`, `not connected`, `unknown (daemon predates this key)`.
      Pinned by S30, S32, and S33.
- [x] **RESOLVED — the `app` line no longer blames "no daemon" when a daemon answered.** Split
      into `unknown (no daemon)` (connect failed) and `unknown (daemon unreachable)` (connected or
      un-dialable, but no usable `HelloOk`). Pinned by S13, S15, S16, S25.
