## Gate

Written 2026-11-15 from the code at `main` 07f503e. Every `file:line` below is from 07f503e.

These owner decisions (2026-11-15, issue #377) bind this spec. They are not open here:

- **O1. The restore card, once per board.** It shows as today: after a first-visit restore whose plan has a line. When some cold spawn of the board has a resume command, the card gives three choices:
  - `resume all`: **Return**, the default. Each such card runs its command once, when its shell is ready, by the rules of today's single Return: one carriage return, sent as typed input, autorepeat ignored.
  - `decide per card`: any other key, or a click on it. The card closes. Each card keeps its own offer (O2).
  - `skip all`: **Esc**. Every offer of the board is dropped.
  - ⌘Q still quits. The line `✓ N terminals back in their folders` stays.
- **O2. A per-card offer panel** replaces the `last here:` strip on each card that has a resume command. It has a title line, the **whole** command, and two buttons, `resume` and `skip`. A click works on any card, prime or not; `resume` makes the card prime and runs. On the prime card the buttons also show `⏎` and `esc`, and the keys work as today. Typing into the terminal still drops the offer.
- **O3. A header chip `resume`** on any terminal card whose terminal has a recorded resume command, also while the terminal runs as usual. The tool tip is the whole command. A click copies the command to the clipboard and says so in a short toast. It never runs anything.
- **O4. `↻` means "refresh" only** (owner, 2026-11-15, by the coordinator). No new element uses `↻`, and every resume or reopen use of `↻` in the app goes [D14]. The doc card's refresh button keeps `↻`.
- **O5. UI copy is English only.**
- **O6. The protocol is additive only,** in two codecs, with conformance vectors.

**What this spec changes in earlier rules** (each one follows from O1–O4):

- **2611.0006, "a resume command never runs without a key press."** It still needs a key or a click. But one Return on the restore card now allows a run on each card of the board, each at a later time, when that card's shell is ready [D1].
- **2611.0011 R4 ("the first key decides", on the prime card only).** A click decides on any card [D3]. The restore card's Return or Esc decides for every card of the board [D1, D4].
- **2611.0011 D9 stays.** Any user byte drops the offer of the card it goes to, also an offer that waits to run [D2].
- **2611.0011, *Alternatives*: "the app clears the record with `resume {term_id}` on the app session" was rejected,** because typed input covered every way to say no. A click on `skip`, and Esc on the restore card, send no byte. So this spec adds that clear, with a guard [D4].
- **2611.0011, "No push. The app reads the records from each `restore`"** (`docs/protocol.md` § Resuming after a restart). The daemon now pushes `term_resume` [D10].
- **2611.0011, *Alternatives*: "Put the chip in the card header" was rejected,** because a long command would push the label out. That reason does not apply here: the header chip is the fixed word `resume`, and the command is only in its tool tip.
- **#358, "any key but ⌘Q closes the restore card."** It holds only for a card with no resume line [D6].
- **2611.0011 D13 and #358 copy.** `↻ last here:`, `↻ reopen here  ⏎` and `↻ M with an agent session to resume` change [D14].

The decisions that this spec makes are marked **[D1]…[D15]** in the body.

## Motivation

Today only the prime card can take a resume offer, and only by keyboard. A board with four agent cards needs four focus changes and four Returns, in order, after each shell prints. A card that is not prime cannot be resumed by a click. A user who does not want the sessions back must type into each card. And a live terminal's recorded command cannot be seen anywhere: the record exists in `state.json`, but the app shows it only after a restart. The owner also wants `↻` to keep one meaning: refresh.

## Proposed Solution

### Overview

1. **One rule for a run that waits.** A resume offer gets a third state, *queued*. A request to resume (Return on the restore card, or a click on `resume`) runs the command at once when the card's shell is up. Else it queues the run, and the run goes at that card's first output. Any user byte to the card still drops its offer, queued or not.
2. **The restore card** with a resume line shows three choices instead of the footer. Return queues or runs every offer of the board. Esc skips every offer. Any other key, a click on `decide per card`, or a click anywhere else closes the card and leaves each offer.
3. **The per-card panel** replaces the strip. Its buttons take clicks on any card. On the prime card, when the offer is armed, the buttons show `⏎` and `esc`, and the keys act as today.
4. **A skip is a no to the daemon too.** `skip`, and `skip all`, send `resume {term_id}` (no `cmd`) on the app session. The daemon clears the record only when no agent claimed it since the restore.
5. **The daemon tells the app** each change of a live terminal's command with a new frame, `term_resume {term_id, cmd?}`. The app keeps one recorded command for each terminal, from the restores and the pushes. The header chip `resume` shows it.
6. **`↻` goes** from every resume and reopen text. Plain words take its place.

### Key Components

#### Decisions

- **D1. `resume all` queues or runs each offer, and each card runs at its own time.**
  - The restore card's `resume all` feeds `.request` to the offer of each terminal of that board.
  - For an offer whose shell is up, `.request` runs at once: `(nil, .run(cmd + "\r"))`.
  - For an offer whose shell is not up, `.request` sets `queued`. The first `.output(byteCount: n)` with `n > 0` then runs it: `(nil, .run(…))`. Each card runs at its own first output. No card waits for another, and prime plays no part.
  - "Shell ready" is the 2611.0011 R4 rule, the first output, with no timer. *Why:* the owner said "same rules as today's single Return". A quiet-period timer would add a clock to a pure reducer, and the first output is a fact the app can see.
  - A run is sent as typed input, so the daemon drops the record at it (2611.0011 D6). A run happens once: after it the offer is nil.
  - A queued offer survives a board switch. Output of a background board still reaches its sessions (`showOutput` uses `anySession`), so the run goes while the board is not shown. `holdOpen` drops the offer (the card died). An app quit loses it. The daemon's record then stays `Unclaimed`, the next app launch rebinds the live shell with no offer, and the header chip shows the command [D11].
- **D2. Input to one card cancels only that card's queued run.**
  - `.userInput` gives `(nil, nil)` in every state, queued too (2611.0011 D9 kept). Bytes typed before the prompt would otherwise go ahead of the command. The other cards keep their queued runs.
  - The typed byte also drops the daemon's `Unclaimed` record (D6), and the daemon pushes a clear [D10], so the card's header chip goes.
  - **A fresh plain Return on the focused card whose offer is queued is taken and dropped** (`.ignoreRepeat`, which now means "a Return taken and dropped"). *Why:* that Return means "yes, run it", and it is already queued. Passed on, it would drop the queued run (D9) and give the shell an empty line. Any other key passes on and drops the queued run, as today.
  - A plain Return on an offer that is not queued and not armed (the shell is not up) passes on and drops the offer, as today (2611.0011 S9). This is an asymmetry with a click on `resume`, which queues [D3]. *Why:* O2 says "the keys work as today", and the panel shows no `⏎` hint then.
- **D3. A click on `resume` works on any card.** It makes the card prime (`setPrime`, which gives it the keyboard), then feeds `.request` (D1): a run at once when the shell is up, else a queued run. A click on `skip` feeds `.skip` [D4]. Neither click selects another card or changes the board's viewport.
- **D4. `skip` and `skip all` delete the daemon's record.**
  - `ResumeOffer.step(_, .skip)` gives `(nil, .skip)` for an offer and `(nil, nil)` for no offer. The wiring performs `.skip` as `client.send(.resume(termID:, cmd: nil))` on the app session.
  - The daemon takes `resume` with no `cmd` from the app session: it removes `resume` from T's record **only when T's handle flag is `Unclaimed`**, sets the flag to `None`, marks dirty and pushes `term_resume {T}` [D10]. With any other flag, or no live T, it does nothing. There is no reply: app-session frames have none.
  - A `resume` with a `cmd` on the app session is ignored, with a debug log. Only the CLI sets a command, because only a CLI caller can be tied to a process.
  - *Why delete:* Esc on the prime card already deletes the record, because it reaches the PTY as a typed byte (D6). A click on `skip`, or Esc on the restore card, sends no byte. Without the clear, the skipped offer would come back after the next daemon restart, and the header chip would keep the command, though the user said no. *Why the guard:* a record that an agent set after the restore is `Held`. A skip must never undo it.
- **D5. `decide per card` only closes the restore card.** The offers and the records stay. The keys go back to the prime terminal, as `closeRestoreCard` does today.
- **D6. A restore card with no resume line keeps today's rules.** Any key but ⌘Q closes it, Return and Esc too, and any click closes it. Its footer is `any key to continue`.
- **D7. The restore card's keys** (`KeyLadder`; the card is still the first rung, before a composition, a document, the switcher, the inbox and the Esc ladder):
  - ⌘Q gives `.passThrough` (the menu's Quit).
  - A repeat gives `.ignoreRepeat`. So a key held from before the card showed never decides.
  - With a resume line (`restoreChoices`): a plain Return (`press.named == .enter`, no ⌘, ⌥ or ⌃) gives `.restoreResumeAll`. A plain Esc gives `.restoreSkipAll`. Any other key gives `.closeRestoreCard` (decide per card). ⇧Return and ⇧Esc count as plain, as for `offerAction` today, which reads only ⌘, ⌥ and ⌃.
  - With no resume line: every key gives `.closeRestoreCard` (D6).
  - `afterRestoreCard` is set by any of the three actions. So the repeats of the Return that chose `resume all` are dropped, and none reaches the prime terminal as a user byte, which would drop its queued run (D2).
  - Esc on the card never clears the toasts first: the card comes before the Esc ladder.
- **D8. The restore card's clicks.** With a resume line, the card shows three buttons in a row where the footer was: `⏎ resume all`, `decide per card`, `esc skip all`. A click on a button does its choice. A click anywhere else over the board area, the veil or the card, is `decide per card`. *Why:* today any click closes the card, and `decide per card` is the choice that changes nothing.
- **D9. The per-card panel.**
  - `ResumePanel.model(offer:prime:)` gives `{title, command, buttons}`:
    - not queued: title `agent session to resume`; buttons `resume` and `skip`. When `offer.armed(prime:)`, they read `⏎ resume` and `esc skip`;
    - queued: title `resumes when the shell is ready`; one button, `skip`, with no hint.
    - `command` is `offer.cmd` verbatim, never shortened (O2: "the whole command"). It is safe to show whole, because `ResumeCommand.check` passed it: one line, no control, format or bidi character.
  - The panel is `OfferStripView`, grown to a title line, the wrapped command and a button row. It stays a sibling of the card, pinned to the bottom of the body, with the opaque fill of 2611.0011. Only its buttons take a press. A press elsewhere on it falls through to the card, which selects it as today.
  - The dead card's strip stays one press target, with its new text [D14].
- **D10. The protocol: `term_resume`, daemon → app.**
  - `Msg::TermResume { term_id: String, cmd: Option<String> }`; `cmd` is omitted when `None`. No `cmd` means "no command".
  - The daemon pushes it with `Daemon::push`, not `emit`: it is not a `tarmac events` kind, and `Events::publish` would drop it anyway.
  - The push is sent after `boards` is released. The step that changes the record returns whether it changed; the caller pushes after.
  - **When it is pushed** (only for a terminal that is live at the change):

    | Change | Push |
    | --- | --- |
    | `set_resume` with a new or different command | `term_resume {T, cmd}` |
    | `set_resume` with the stored command | none (nothing changed; no save, D5 of 2611.0011) |
    | cli clear that removed a command | `term_resume {T}` |
    | cli clear with no command | none |
    | the poll's drop (`check_resume`) | `term_resume {T}` |
    | the typed-input drop (`claim_resume`) | `term_resume {T}` |
    | the app-session clear (D4) that removed one | `term_resume {T}` |
    | the end of a terminal (`term_ended`, `end_resume`) | none: the `exit` frame ends the card, and a dead card shows no chip [D12] |
    | a set that raced the terminal's end (`set_resume`'s re-check) | none, for the same reason |
    | the `succeeds` move (`adopt_term`) | none: the app planned that spawn and knows its command |
    | `TermClose` | none: the card is gone |
    | the shutdown freeze (2611.0011 D4) | no drop, so no push |

  - **No replay.** Each `restore` already carries the board's whole `term_records`, live terminals included. That is the baseline, and the pushes keep it current.
  - With no app connected, a push is dropped. The next restore carries the record.
- **D11. The app's recorded command for each terminal.** `TerminalSession.recordedResume: String?`. Each value passes `ResumeCommand.check` first, or it is nil. That check guards the copy too: a copied command is pasted into a shell.
  - A first-visit restore: for a cold spawn, the plan's `resume`; for a rebound term, `termRecords[termID]?.resume?.cmd`. `RecordedResume.command(for:termRecords:)` decides it.
  - A later restore (reconcile): for each live session of the board, `termRecords[termID]?.resume?.cmd`, checked (`RecordedResume.command(liveTermID:termRecords:)`). So a restore corrects a stale value.
  - A `term_resume` frame: the session of that term id on any **built** board gets the checked `cmd`, or nil. A frame for a term on no built board is dropped; that board's first restore carries the record.
  - `reopenDead`: the new card gets `DeadCardOffer.reopen`'s resume.
  - A new terminal (⌘T, a fresh board): nil.
  - It is not changed by the offer. When a run or a skip drops the offer, the daemon's push clears the value. The app does not clear it ahead of the push, so the chip has one source.
- **D12. The header chip.**
  - `ResumeHeaderChip.model(cmd:dead:)` gives `{text: "resume", toolTip: cmd}`, or nil when `cmd` is nil, when `ResumeCommand.check` refuses it, or when the card is dead.
  - *Why not on a dead card:* its terminal is gone. Its reopen strip already shows the command (`then offers: …`). The whole dead card is dimmed, so the chip could not look like a control.
  - It shows while the panel shows too. *Why:* one rule (a record means a chip) is easier to trust than a rule with an exception, and copy is useful while the user decides.
  - It is a header control (`CardPress.headerControl`), in the trailing row just before the report chip: `[…, closeButton, resumeChip, reportChip, bellDot]`. It uses the chip metrics and the neutral tone, and it takes a press, as `HeaderButton` does. The header's `hitTest` must let the press reach it (today only a `HeaderButton` gets one, `CardChrome.swift:610-614`). A press does not select the card, make it prime, or move the keyboard. *Why:* a copy must not change where the user types, and O3 says it never runs anything.
  - A click puts `cmd` verbatim on the general pasteboard as a string, and shows the toast `ResumeHeaderChip.copiedToast` = title `resume command copied`, with no body.
  - The tool tip is the whole command, verbatim.
- **D13. The keys of the per-card panel.** `KeyLadder.Offer` gets `.resumeQueued`. The wiring gives it for the focused terminal whose offer is queued.
  - Plain Return: `.resumeArmed` gives `.runResume` (today); `.resumeQueued` gives `.ignoreRepeat` (D2); `.resumeIdle` passes on (today).
  - A repeated plain Return with any offer, `.resumeQueued` included, gives `.ignoreRepeat` (today's D10 amendment and RA3).
  - Esc on the prime card climbs the Esc ladder and, with no rung, reaches the PTY as a typed byte. That drops the offer (D9) and the record (D6), as today. The `esc skip` hint is shown only when the offer is armed.
- **D14. `↻` goes from every resume and reopen text. Plain words take its place.**
  - The restore card line: `M with an agent session to resume`, with no glyph. `RestoreCard.Line.glyph` becomes `String?`; the resume line has nil. `RestoreCardView` places a line with no glyph at the text column of the `✓` line, so the two texts align. `Line.string` is the text alone when there is no glyph.
  - The dead card's strip: `reopen here  ⏎`, then `in <cwd>` and `then offers: <display>` as today.
  - The resume strip `↻ last here: …` is gone; the panel (D9) replaces it, and its title has no glyph.
  - The doc comments that show `↻` for resume or reopen (`ResumeOffer.swift:4`, `DeadCardOffer.swift:9`, `OfferStripView.swift:5`) change with the code. `CardPress.swift:5`, `CardChrome.swift:110`, `:327`, `:380`, `:389`, `CardView.swift:37`, `BoardView.swift:36` and `AppController+Docs.swift:133` are about refresh and keep `↻`.
  - *Why plain words:* `↻` is the doc card's refresh control (O4). No other glyph in the app means "resume" or "reopen". A new glyph would need a meaning of its own, and the words already say it. `⏎` stays only as a key hint, which is its one meaning in the app (`⏎ switch`, `⏎ on a dead card reopens it`).
- **D15. QA.** The dev snapshot grows (below). `make qa-resume` covers the keyboard and snapshot steps. Clicks and the restore card are hand QA: the driver has no sub-view click verb, and the restore card needs an app relaunch after a daemon kill, which a runner cannot do. A new driver verb is out of scope.

#### TarmacKit (pure; TDD)

- **`ResumeOffer`** (`ResumeOffer.swift`):
  - gets `public private(set) var queued: Bool` (false from `make`);
  - `Event` gets `.request` (D1, D3) and `.skip` (D4);
  - `Effect` gets `.skip`;
  - `armed(prime:)` stays `shellUp && prime`. A queued offer is never armed, because it runs at the output that would arm it.
  - The reducer's full rules:

    | State | Event | Result |
    | --- | --- | --- |
    | nil | any | `(nil, nil)` |
    | any | `.userInput` | `(nil, nil)` |
    | any | `.skip` | `(nil, .skip)` |
    | shell up | `.request` | `(nil, .run(cmd + 0x0D))` |
    | shell not up | `.request` | `(queued, nil)` |

### Data Flow

1. The app quits and the daemon is killed. Cards A and B had `claude --resume …` records; C had only a folder.
2. `make run`. The first-visit restore plans A′, B′ and C′ as cold spawns. A′ and B′ get offers, and `recordedResume`. The restore card shows `✓ 3 terminals back in their folders`, `2 with an agent session to resume`, and the three buttons.
3. The user presses Return. The card closes. A′'s shell has printed, so A′ runs at once. B′'s has not, so B′ queues. The Return's repeats are dropped (`afterRestoreCard`).
4. B′'s first output arrives. B′ runs: `Input {B′, "claude --resume …\r", typed: true}`. The daemon drops B′'s `Unclaimed` record and pushes `term_resume {B′}`. B′'s header chip goes.
5. `claude` starts in B′. Its `SessionStart` hook sets a new command. The daemon pushes `term_resume {B′, cmd}`. The chip shows again, with the new command.
6. In card D (live, no restart), `claude` was started earlier. Its record was set while the app ran, so D's chip shows `resume`. A click copies the command, and the toast says `resume command copied`.

### Interface Contract

Additive only. Both codecs ignore unknown keys and types.

```
term_resume   { t:"term_resume", term_id: str, cmd?: str }   daemon → app; no reply
resume        { t:"resume", term_id: str }                   app → daemon (new direction; D4); no reply
```

- **`term_resume`.** No `cmd` means "no command". It is pushed only at the changes in the D10 table. It is not a `tarmac events` kind.
- **`resume` on the app session.** Only the clear form acts, and only on an `Unclaimed` record. A `cmd` is ignored. The cli session's `resume` is unchanged.
- **New conformance vectors.** The hex is `rmp_serde::to_vec_named` output, the whole msgpack payload with no length prefix. The bytes below were worked out by hand from the V25/V26 pattern. **Rust's encoder is the authority**: if its bytes differ, take Rust's and fix this spec and `docs/protocol.md`.
  - **V36:** `{t:"term_resume", term_id:"t1", cmd:"claude --resume ab-12"}`

        83 a1 74 ab 74 65 72 6d 5f 72 65 73 75 6d 65 a7 74 65 72 6d
        5f 69 64 a2 74 31 a3 63 6d 64 b5 63 6c 61 75 64 65 20 2d 2d
        72 65 73 75 6d 65 20 61 62 2d 31 32

  - **V37:** `{t:"term_resume", term_id:"t1"}` (no `cmd` key)

        82 a1 74 ab 74 65 72 6d 5f 72 65 73 75 6d 65 a7 74 65 72 6d
        5f 69 64 a2 74 31

  - Both codecs decode each one and round-trip it. The Swift encoder's bytes equal Rust's. V1–V35 do not change. The app-session `resume` clear is V26's bytes.

## Alternatives Considered

- **A quiet-period timer for "shell ready".** Wait for no output for, say, 300 ms after the first chunk before a queued run. It would skip a login banner. Rejected [D1]: the owner asked for today's rule, and a timer makes the reducer depend on a clock.
- **Skip keeps the record until the first typed key.** No protocol change. Rejected [D4]: the header chip would keep a command the user said no to, and a daemon restart before any key would offer it again.
- **The app sends a clear with no guard.** Simpler on the daemon. Rejected [D4]: a skip could then undo a command an agent set later.
- **Reuse `resume` for the daemon → app push.** No new type. Rejected [D10]: each direction has its own type today (`report` / `term_report`), and one type in two directions with two meanings is harder to read and to test.
- **A replay of `term_resume` frames after each restore.** It would close the race in *Trade-offs*. Rejected: the restore already carries the table, and the race costs at most a wrong chip until the next push or restore. The chip only copies.
- **No chip on a card that shows the panel.** Less chrome. Rejected [D12]: two rules are harder to trust than one.
- **A new glyph for resume.** Rejected [D14]: the words say it, and the app has no glyph with that one meaning.

## Migration & Rollback

- **No state migration.** `state.json` does not change.
- **App and daemon versions.** The app replaces a daemon of another version, so a mixed pair is short-lived. An older daemon sends no `term_resume`: the chip then shows only what restores carry. It ignores the app-session `resume`: a skip then keeps the record until the first typed key, as today. An older app ignores `term_resume`.
- **Rollback.** Revert the change. Nothing persists that an older build cannot read.

## Security Considerations

- **More runs from one key.** Return on the restore card allows a run on each card with an offer, each later, unseen at the moment it runs. Each command was recorded by an agent-attributed CLI call (2611.0011), passed `check_resume_cmd` in the daemon and `ResumeCommand.check` in the app, and was shown on the panel of its card under the restore card's veil. The restore card's line counts them.
- **The first output is not always a prompt** (2611.0011 *Trade-offs*). A queued run can go into an rc file's question. With `resume all` the user does not see that card when it runs. Accepted, as in 2611.0011; listed in *Trade-offs*.
- **The clipboard.** A copy puts the command verbatim on the general pasteboard. Only a command that `ResumeCommand.check` accepts is copied: one line, no control character, no invisible format or bidi character. So a paste shows exactly what runs, and cannot add a second line.
- **The app-session clear** can only remove an `Unclaimed` record of a live terminal. Any process that can open the socket could already do more (2611.0011).

Test principles (the same ones `/verify` scores against):

- **Behavioral over structural** — assert observable output/effects, not internals; the suite must survive refactoring.
- **Every test can fail** — no copy-pasted expected values, no asserting a constant, no tautologies.
- **Deterministic, isolated, readable** — inject clocks/randomness, no cross-test state, AAA structure with inline setup.

## Definition of Done

Done is when `/verify` passes against this spec:

- [ ] `make test` is green, and `make docs-check` passes.
- [ ] Every acceptance scenario S1–S24 maps to at least one test. S25–S32 are recorded as a QA run; S29 and S30 have their automated parts in `make qa-resume`.
- [ ] No covered-but-vacuous scenarios. In particular:
  - S1 fails if a queued offer runs at a zero-byte chunk, runs twice, or runs before any output;
  - S3 fails if Esc on the card clears the toasts first, or a repeat chooses;
  - S4 fails if the repeats of `resume all` reach a terminal;
  - S11 fails if a same-command set pushes (its control shows a push can be seen);
  - S14 fails if the `succeeds` move pushes, or the typed drop does not;
  - S15 fails if the app-session clear removes a `Held` record, or a `cmd` from the app sets one;
  - S16 fails if one card's input cancels another's run;
  - S17 fails if a Return on a queued offer passes on;
  - S18 fails if a card with no resume line acts on Return or Esc;
  - S5, S6, S8 and S19 fail if any resume or reopen text has `↻`;
  - S8 and S23 fail if a refused command gets a chip.

- [ ] No implementation-quality blockers (stubs, dead code, stale doc comments with the old `↻` text).
- [ ] The docs describe the frame, the app-session clear, the choices, the panel and the chip.

## Trade-offs and Limitations

- **Return is the default.** A user who presses Return out of habit as the card shows runs every agent of the board. Today's guards stop only a held key: a repeat never decides, and a key held from before the card showed never decides. A fresh Return typed at that moment still chooses `resume all`. See OQ1.
- **Unattended runs.** With `resume all`, a card runs when its first output arrives, which may be a banner or an rc question, not a prompt (2611.0011). The user does not see that card then.
- **A push can arrive before a restore that is older than it** (*Context*, timing of a restore). The app then shows the restore's older value until the next push or restore. The cost is a wrong chip; the chip only copies.
- **A queued run on a board not shown** goes when its shell prints, out of the user's view.
- **The asymmetry before the shell is up.** A click on `resume` queues; a Return on the prime card passes on and drops the offer (D2). The panel shows no `⏎` hint then.
- **Clicks are hand QA.** The dev driver has no sub-view click verb (D15).

## Open Questions

- [ ] **OQ1 — A guard for a reflex Return.** Should the restore card ignore Return for a short time after it shows (for example 300 ms), so that a Return typed for a terminal at that moment does not resume every agent? This spec adds no such guard: the owner made Return the default, and the repeat guards stay as they are.
- [ ] **OQ2 — The panel's title copy.** This spec uses `agent session to resume` and, while queued, `resumes when the shell is ready`. The mockup canvas ("Restore resume offers") was not readable for this spec. The owner may give other words; only the strings in `ResumePanel` and S6 change.
- [ ] **OQ3 — A `tarmac dev` verb for a click on a sub-view** (a panel button, the header chip, a restore card button). It would let `make qa-resume` drive S26–S29. Deferred: not needed to build this.
