## Gate

Written 2026-11-14 from the code at `main` d5ff6bd. The approach is the design's and is not open here. These owner decisions bind this spec:

- **R5.** `Subscribe` fans out through one bounded tokio `broadcast` channel, one receiver for each `Subscribe` connection. A subscriber that falls behind gets one last `Err {msg: "lagged"}` and is closed. The daemon never waits for a subscriber. The app's channel is not touched.
- **R6 (revised by Q3).** `wait` keeps the CLI's 0 = ok, 1 = failure, 2 = usage, and adds 124 for a timeout. `--exit` prints `{"code": N}`, or `{"signal": true}` for a signal death, on stdout and exits 0. `--changed` prints `{"deleted": true}` when the file went away. **Note:** design §3 also says that a deletion is "a change with its own exit code". That line predates Q3. This spec follows the R6 table: a deletion exits 0.
- **`--timeout` is in milliseconds**, as `tarmac dev snapshot --timeout` is.
- **`/simplify` notes (§3).**
  - No new event schema. The stream carries the existing `Exit`, `Bell` and `FileEvent` frames and slice 2's `TermReport`, tapped at `Daemon::push`.
  - A short snapshot comes first, for the filter only: one exit lookup, the current report of the named terminal, and nothing for `bell` and `changed`.
  - The daemon keeps a ring of the last 64 exits (`term_id`, code), bounded by count, with no timer.
  - The tap costs nothing when there is no subscriber.
  - `tarmac terms` lists id, board, cwd and process. It has no title (titles are the app's).
  - `wait --changed PATH` runs in the CLI only. It stats `(dev, ino, mtime, size)` every 100 ms for 2 s, then every 250 ms. Only changes after the start count. The first change ends the wait unless `--settle MS` is given. A missing file is a state: a creation is a change, and a deletion is a change reported as deleted. It never touches the daemon's watcher.
  - `tarmac events [--term ID] [--kind exit,bell,changed,report]` prints JSON lines, each with a receive time stamped by the CLI.
  - `changed` events cover open docs and their data files only.
  - Excluded on purpose: any match on terminal output.

The design does not settle the decisions below. They are marked **[D1]…[D18]** in the body. **All eighteen were accepted on 2026-11-14** by the author, after a review with Fable, with the additions noted on D8, D11, D12, D14 and D16:

- **D1. No new handshake role.** `Subscribe` and `TermsList` are messages of a `cli` session, as `report` is.
- **D2. The reply.** `Subscribe` gets `Err` and a close, or the snapshot frames, then `Ack`, then live frames. `Ack` marks the end of the snapshot.
- **D3. Unknown terminal.** A `term_id` that is neither live nor in the exit ring gets `Err {msg: "unknown terminal: <id>"}`. A live terminal wins over a ring entry with the same id.
- **D4. The ring is written before the term leaves `terms`.** So an id is always live, or in the ring, or unknown for good.
- **D5. Where the tap is.** In `Daemon::push`, before the app send, with the return value unchanged. Also in the board-switch tell loop (`conn.rs:195`), which does not pass `push`. Not in the `TermReport` replay (`conn.rs:203`). A `changed` event means "the daemon told the app about this file", so it can repeat an `mtime_ms`.
- **D6. Capacity 1024.** It is the bound for each subscriber. It is a seam, so a unit test can use 2.
- **D7. Subscriber lifetime.** The session selects on a socket read and the receiver. EOF ends it. A frame read after `Subscribe` is ignored. The last `lagged` write has a 1 s limit.
- **D8. The filter.** `kinds` uses the CLI's names (`exit`, `bell`, `changed`, `report`). Missing means all four. Unknown names are ignored, and no known name left is an `Err`. A `term_id` filter drops every `FileEvent`, because it has no terminal. The CLI refuses `--term` with an explicit `--kind changed`. **Added:** `help.rs` and `GUIDE.md` say that `--term` alone gives no `changed` events.
- **D9. JSON line shapes.** The event type is the key `event`; the CLI's time is `received_ms`; snapshot lines carry `"snapshot": true`. The report's own `kind` and `at_ms` keep their names.
- **D10. What `wait` prints.** `--exit` as R6. `--report` prints the report object. `--bell` prints nothing. `--changed` always prints one line, `{"deleted": false}` or `{"deleted": true}` (R6 fixes only the second).
- **D11. A wait that can no longer happen.** `--bell` and `--report` also take that terminal's `Exit`, and then exit 1 with `tarmac: terminal <id> exited`. **Added (GUIDE hazard):** a waiter that starts after "report done, then exit" gets exit 1, not the report: the daemon forgets a report at its terminal's exit (`state.rs:511`), so the snapshot has the `Exit` and no report.
- **D12. A current report counts.** `wait --report KIND` ends at once when the snapshot's current report has that kind, read or unread. **Added (GUIDE hazard):** a loop that waits on a report that stays returns at once on each pass. The loop must compare `at_ms` with the last one it saw. A future `--since AT_MS` is preferred over `--new` (OQ2).
- **D13. The daemon goes away.** `wait` and `events` exit 1 with the `daemon connection lost` line. There is no reconnect.
- **D14. The deadline.** `--timeout` counts from the start of the command, the connect included. Running out at any point is 124, also before `Ack`. A value must be at least 1. **Added:** when 124 comes before `Ack`, the CLI prints one line on stderr, `tarmac: wait: timed out before the daemon answered`, so an older daemon under a short timeout is not silent.
- **D15. `terms` output and reads.** JSON lines, one per live terminal, sorted by board order, then term id. The process name and the cwd are fresh reads. The cwd reads run at the same time, each on the gate; a read that is out, or has no answer, leaves out `cwd`.
- **D16. `events` and a closed stdout.** A failed write to stdout ends `events` with exit 0 and nothing on stderr. **Added:** a closed stdout is seen only at the next write, so `events | head -1` waits for the next event after the first line. `GUIDE.md` says so.
- **D17. `wait --changed` details.** The stat follows symlinks. `NotFound` and `NotADirectory` mean "missing". Any other stat error exits 1. A wait that times out while it settles exits 124.
- **D18. Vectors: the next free numbers at merge.** The current proposal is V28–V32. Slice 4 (V25–V27) is not merged, and slice 5 adds `board_id` on `Bell`/`Exit` and new `term_report` keys, which may take vectors too.

Four of them depart from the letter of owner-bound text. Each was accepted as **"the letter departs, the intent holds"**:
- **D5** departs from design §3 ("tapped at the one place they all pass, `Daemon::push`"). The board-switch tell loop sends `FileEvent`s on `conn.tx` and does not pass `push` (`conn.rs:195-199`), so it gets a second tap.
- **D8** narrows the design's usage line, which allows `--term` with `--kind changed`. A `FileEvent` has no terminal, so the pair is refused.
- **D10** adds `{"deleted": false}` and the report object on stdout. R6 fixes only `{"code": N}`, `{"signal": true}` and `{"deleted": true}`.
- **D14** makes an older daemon under a `--timeout` shorter than 5 s exit 124, where R6 says a Tarmac failure is 1.

## Motivation

The daemon sees exits, bells, file changes and reports, but it gives them to the app only. A Makefile, a git hook or a second agent cannot say "go on when the test terminal exits" or "go on when `plan.md` changes". They poll, or they ask the user. This slice gives out those facts, read-only, over the existing socket. It adds no state to Tarmac's view and no new watch.

## Proposed Solution

### Overview

1. `tarmac terms` asks the daemon for its live terminals: id, board, cwd and process. It is how a caller outside a terminal names one.
2. `tarmac events` and the daemon-side `tarmac wait` send `Subscribe {kinds?, term_id?}`. The daemon answers with a short snapshot, then `Ack`, then the matching live frames, until the client goes or falls behind.
3. `tarmac wait --changed PATH` stats the path in the CLI. It never connects.

### Key Components

**Protocol** (`tarmac-protocol/src/lib.rs` and the Swift codec, same change).

```
Msg::Subscribe { kinds: Option<Vec<String>>, term_id: Option<String> }   cli → daemon
Msg::TermsList                                                           cli → daemon
Msg::Terms { terms: Vec<TermInfo> }                                      daemon → cli
TermInfo { term_id: String, board_id: String, cwd: Option<String>, proc: Option<String> }
```

- Every `Option` is omitted when `None` (`skip_serializing_if`), and a missing key decodes as `None`.
- Wire tags: `subscribe`, `terms_list`, `terms`.
- The Swift codec gets `.subscribe(kinds:termID:)`, `.termsList` and `.terms([TermInfo])`, decode and encode. The app never sends or reads them. They exist for the codec's completeness and the vectors, as `.report` did in slice 2.

**Daemon — the fan-out** (`tarmacd/src/events.rs`, new).

- `Fanout` wraps one `broadcast::Sender<Msg>`, made with `Fanout::new(capacity)`. Production uses `EVENTS_CAPACITY` = 1024 [D6]. `Daemon` gets `events: Fanout` and `exits: std::sync::Mutex<ExitRing>`.
- `Fanout::publish(&self, msg: &Msg)`:
  - It returns at once when `msg` is not `Exit`, `Bell`, `FileEvent` or `TermReport` (`is_event(msg)`, pure). So `Output` costs one discriminant check.
  - It returns at once when `receiver_count() == 0`. So with no subscriber nothing is cloned.
  - Else it sends `msg.clone()`. `broadcast::send` never waits. Its error (no receiver left) is ignored.
- `Fanout::subscribe() -> broadcast::Receiver<Msg>`.
- **The bound** [D6]. One broadcast ring of 1024 frames. Each receiver can fall behind by at most that many; then its next `recv` gives `Lagged`. Filtered frames count too, because the filter runs at the receiver. 1024, not the app channel's 256, because the app's channel waits and this one does not: one look over a board with many open docs pushes one `FileEvent` per changed doc in a burst, and a fast reader whose task was not scheduled in that burst must not lag. The ring is allocated once, at start.
- `ExitRing` (pure): a `VecDeque<(String, Option<i64>)>` of at most `EXIT_RING` = 64. `record(term_id, code)` pushes at the back and drops the front past 64. `lookup(term_id)` gives the latest entry for that id.
- `Filter` (pure): `Filter::new(kinds: Option<Vec<String>>, term_id: Option<String>) -> Result<Filter, String>` [D8].
  - Names: `exit` → `Exit`, `bell` → `Bell`, `changed` → `FileEvent`, `report` → `TermReport`.
  - `kinds` missing: all four. Present: the known names; unknown names are ignored, so a newer CLI can ask an older daemon for a kind it lacks. No known name left (an empty list included): `Err("no known event kind")`.
  - `admits(&Msg) -> bool`: the frame's kind is in the set, and, with a `term_id`, the frame's `term_id` is that id. A `FileEvent` has no `term_id`, so a term filter never admits it.

**Daemon — the tap** [D5].

- `Daemon::push` calls `self.events.publish(&msg)` first, then does what it does today. Its return value still means "the app's channel took it". A subscriber is not an app: a `FileEvent` that reaches only a subscriber is still held for the app.
- `change_and_send_active_board` calls `daemon.events.publish(&file_event)` for each `(path, mtime_ms)` of `tell` (`conn.rs:195-199`), next to the `conn.tx.send`. This is how a change of a doc on a background board reaches a subscriber when that board is shown (design §3).
- The `TermReport` replay (`conn.rs:200-207`) is **not** published. It is a replay to one app, not a change.
- **What `changed` means.** A `changed` event is a `FileEvent` that the daemon told the app. It can repeat an `mtime_ms`:
  - `doc_refresh` pushes one with no change (`stat_and_push`);
  - `data_file` pushes one for the same file again;
  - a change held while no app was connected is published when it is first pushed, and again when a later restore re-tells it.

  A consumer that wants file changes only compares `mtime_ms` with the last one it saw for that path.
- **Limits that come with the looks** (design §3). A look reads the active board only, and there is no timer. A data file's registration is dropped when the app goes (`drop_data`, `state.rs:439-444`), so with no app there are no data-file events. Doc events still come with no app.

**Daemon — the exit ring** [D4].

- `term_ended` records `(term_id, code)` in `exits` **first**, before it removes the term from `terms`. The pump then pushes `Exit`, which publishes it.
- So at every moment an id is live, or in the ring, or not known. No window exists where an exiting term is neither (between `terms.remove` and the push).

**Daemon — the `Subscribe` handler** (`cli_session` gets one arm; the stream is `events::serve`).

The order is fixed. It leaves no gap between the snapshot and the live frames:

1. `filter = Filter::new(kinds, term_id)`. On `Err(msg)`: write `Err {msg}` and end the session.
2. `rx = daemon.events.subscribe()`. Every frame published from here on reaches `rx`.
3. With a `term_id` [D3]:
   - live = `daemon.term(&id)` is `Some` (takes `terms` alone);
   - else exited = `exits.lookup(&id)` (takes `exits` alone);
   - neither: write `Err {msg: "unknown terminal: <id>"}`, drop `rx`, end the session.
4. The snapshot, for the filter only, written in this order:
   - `report` admitted and a `term_id`: the one frame of `daemon.reports.lock().snapshot(&[id])` (its report, or a `TermReport` with no `kind`). The lock is held only for this read.
   - `exit` admitted, a `term_id`, the term **not** live, and in the ring: `Exit {term_id, code}` from the ring. A live term wins over a ring entry with the same id (an id reused by a new spawn).
   - Nothing for `bell` or `changed`, and nothing at all with no `term_id`.
5. Write `Ack` [D2].
6. `events::serve(rx, filter, read_half, write_half)` until it ends.

Why no frame is lost:
- A report change publishes under the `reports` lock (`change_report`). `rx` exists before step 4 takes that lock. So a change is either in the snapshot, or after it in `rx`, or in both.
- An exit is recorded in the ring before it is published. `rx` exists before step 3 reads the ring. So an exit is in the ring read, or in `rx`, or in both.
- "In both" gives a repeated frame. Every frame here is a state (an exit, a current report) or carries its own `mtime_ms`, so a repeat is harmless. `wait` ends at the first one.

Lock order: `terms`, `exits` and `reports` are each taken alone and released before the next. `publish` takes no lock. Inside `change_report` it runs with `reports` held, which is the existing order `reports` → `app`.

**Daemon — `events::serve`** [D7] (generic over `AsyncRead` and `AsyncWrite`, so a unit test drives it on a `tokio::io::duplex`).

```
loop select:
  read half: a raw read into a small buffer
    0 bytes or an error            → end
    any bytes                      → drop them (the stream is one-way)
  rx.recv() == Ok(msg)             → if filter.admits(&msg): write it; a failed write ends
  rx.recv() == Err(Lagged(_))      → write Err {msg: "lagged"} within 1 s, then end
  rx.recv() == Err(Closed)         → end (only at daemon shutdown)
```

- The read arm must be cancel-safe. `frame::read_async` is not (two `read_exact`s, `frame.rs:39-46`): when the receiver arm wins, the bytes it read are lost. So the read arm is a plain `AsyncReadExt::read`, which is cancel-safe, and the bytes are dropped. The client is not meant to send anything after `Subscribe`.
- A dropped receiver is the whole unsubscribe. A subscriber has no id. The app slot, its generation and `install_app`/`remove_app` are not touched. `hello_ok.app_connected` still reports only the app.
- An ordinary write has no time limit. A client that stops reading blocks only its own task; the broadcast ring goes on, and the receiver lags. When the client reads again, it gets `lagged`. When it exits, the write fails and the task ends.

**Daemon — `TermsList`** [D15].

1. `live_terms_by_board()` gives the live ids by board.
2. The handles are cloned out of `terms`; no lock is held after this step.
3. For each term, at the same time (one `tokio::spawn` or `JoinSet` task each): `pid = handle.foreground_pid()`; `proc = proc::process_name(pid)`; `cwd = daemon.gate().pid_cwd(pid)`. A gate `Out`, an error or `None` leaves `cwd` out. No `pid` leaves both out. So all the reads end within about one `READ_LIMIT` (1 s), not one per term.
4. Rows are sorted by the board's index in `Boards` order, then by `term_id`.
5. Reply `Terms {terms}`. An empty list is a valid reply.

**CLI — shared** (`tarmac-cli/src/events.rs` for `events`, `wait.rs` for `wait`, `terms.rs` for `terms`; dispatched from `main.rs`).

- **The subscribe exchange.** `connect_until(deadline)`, send `Subscribe`, then read frames until `Ack` or `Err`. Frames before `Ack` are the snapshot. Each read gets `time_out_at(min(5 s from the send, the --timeout deadline))`.
  - `Err {msg}` → `tarmac: <msg>`, exit 1.
  - The 5 s run out first → `tarmac: no answer from the daemon in 5 s (an older daemon)`, exit 1.
  - The `--timeout` deadline runs out first → `tarmac: wait: timed out before the daemon answered` on stderr, exit 124 [D14].
- **After `Ack`**, `events` clears the read timeout (`connect()` set 5 s, `main.rs:275`). `wait` sets it to what is left of `--timeout`, or none.
- **The stream ends** [D13]:
  - EOF or a read error: `tarmac: daemon connection lost: <error>`, exit 1. A daemon restart kills every terminal, and the ids are not reused across it, so there is no reconnect.
  - `Err {msg: "lagged"}`: `tarmac: the daemon dropped this stream: it fell behind (lagged)`, exit 1.
  - Any other `Err {msg}`: `tarmac: <msg>`, exit 1.
- **Frames the CLI does not want** (another kind, another term, an unknown type) are skipped. The CLI checks `term_id` too; it does not trust the daemon's filter alone.

**CLI — `tarmac events`**.

```
tarmac events [--term ID] [--kind exit,bell,changed,report]
```

- **Usage (exit 2).** An unknown kind; an empty `--kind`; a flag given twice; a stray argument; `--term` with an explicit `changed` in `--kind` [D8]. The usage check comes first; nothing connects.
- `--kind` is sent as `kinds` in the given order; no `--kind` sends no `kinds` key. `--term` is sent as `term_id`.
- **One JSON line per admitted frame** [D9], written with `writeln!` and flushed:

  | Frame | Line |
  | --- | --- |
  | `Exit {code: Some(n)}` | `{"event":"exit","term":"t1","code":3,"received_ms":…}` |
  | `Exit {code: None}` | `{"event":"exit","term":"t1","signal":true,"received_ms":…}` |
  | `Bell` | `{"event":"bell","term":"t1","received_ms":…}` |
  | `FileEvent` | `{"event":"changed","path":"/abs/a.md","mtime_ms":…,"received_ms":…}` |
  | `TermReport` with a `kind` | `{"event":"report","term":"t1","kind":"blocked","text":"May I?","proc":"claude","at_ms":…,"read":false,"received_ms":…}` |
  | `TermReport` with no `kind` | `{"event":"report","term":"t1","received_ms":…}` (no report) |

  - `received_ms` is the CLI's wall clock when it read the frame, in ms since the Unix epoch.
  - In a report line, `text` and `proc` are left out when the frame has none; `at_ms` and `read` are always there.
  - A snapshot line (read before `Ack`) has `"snapshot": true` after `event`. A live line has no `snapshot` key.
  - Keys are in the order shown.
- **A closed stdout** [D16]: the first failed write ends `events` with exit 0 and nothing on stderr. (`println!` would panic; Rust ignores SIGPIPE, so the write gives `EPIPE`.) The close is seen only at that next write: `events | head -1` runs until the next admitted frame.
- Otherwise `events` runs until it is killed, or until the stream ends (exit 1, above).

**CLI — `tarmac wait` (daemon side)**.

```
tarmac wait --exit ID [--timeout MS]
tarmac wait --bell ID [--timeout MS]
tarmac wait --report blocked|done --term ID [--timeout MS]
```

- **Usage (exit 2).** Not exactly one of `--exit`, `--bell`, `--report`, `--changed`; a missing value; `--report` with a kind other than `blocked` or `done`; `--report` with no `--term`; `--term` with another mode; `--settle` with a daemon mode; a `--timeout` or `--settle` that is not a whole number of at least 1; a stray argument. Nothing connects.
- `--timeout` [D14]: the deadline is the start of the command plus MS. With no `--timeout` there is none. A sum that would overflow `Instant` counts as none.
- **`--exit ID`.** Subscribes `{kinds: ["exit"], term_id: ID}`. At the first `Exit` for ID (snapshot or live) it prints `{"code":N}` or `{"signal":true}` and exits 0.
- **`--bell ID`** [D10, D11]. Subscribes `{kinds: ["bell", "exit"], term_id: ID}`. At the first `Bell` for ID it prints nothing and exits 0. An `Exit` for ID first: `tarmac: terminal <ID> exited`, exit 1.
- **`--report KIND --term ID`** [D10, D11, D12]. Subscribes `{kinds: ["report", "exit"], term_id: ID}`.
  - A `TermReport` for ID whose `kind` is KIND ends it, whether it is from the snapshot or live, read or unread. It prints `{"kind":"blocked","text":…,"proc":…,"at_ms":…,"read":…}` (`text` and `proc` left out when absent) and exits 0.
  - A `TermReport` with another kind, or no kind, is skipped.
  - An `Exit` for ID: `tarmac: terminal <ID> exited`, exit 1.
- **Timeout:** exit 124, nothing on stdout. After `Ack`, nothing on stderr either; before `Ack`, the one line of D14.

**CLI — `tarmac wait --changed PATH [--settle MS] [--timeout MS]`** [D17]. It never connects.

- `PATH` is made absolute with `std::path::absolute` against the CLI's cwd.
- **A sample** is `Present {dev, ino, mtime_ns, size}` or `Missing`, from `std::fs::metadata` (it follows a symlink). `NotFound` and `NotADirectory` give `Missing`. Any other error, at any sample, exits 1 with `tarmac: cannot stat <PATH>: <error>`.
- **The base** is the first sample, taken at start. A change is any sample that differs from the one before it. A change in `ino` (or `dev`) catches an atomic replace (a rename over the file).
- **The schedule** is one pure function, `poll_interval(elapsed)`: 100 ms while less than 2 s have passed since the start, then 250 ms.
- **Ending.**
  - No `--settle`: the first change ends the wait.
  - `--settle MS`: after the first change, each further change starts the MS again. The wait ends when MS pass with no change. The settle is checked at each poll, so it ends up to one interval late.
  - It prints `{"deleted":true}` when the last sample is `Missing`, else `{"deleted":false}`, and exits 0.
  - The deadline, if any, runs out first (also while it settles): exit 124, nothing on stdout.

**CLI — `tarmac terms`** [D15].

- No arguments; any argument is a usage error (exit 2).
- `connect()`, send `TermsList`, read until `Terms` or `Err`, with the 5 s wait. `Err {msg}` → exit 1. No answer → the *older daemon* line, exit 1.
- One JSON line per row, in the daemon's order: `{"term":"t1","board":"board-0","cwd":"/w","proc":"zsh"}`. `cwd` and `proc` are left out when absent. An empty list prints nothing; exit 0.

### Data Flow

1. A Makefile runs `tarmac terms` and reads `{"term":"t7","board":"board-1","cwd":"/w/api","proc":"cargo"}`.
2. It runs `tarmac wait --exit t7 --timeout 600000`.
3. The CLI sends `hello`, then `Subscribe {kinds: ["exit"], term_id: "t7"}`.
4. The daemon subscribes `rx`, finds t7 live, sends no snapshot frame, and sends `Ack`.
5. `cargo test` ends; the shell in t7 runs `exit 3`. `term_ended` records `("t7", Some(3))` in the ring, then removes t7. The pump pushes `Exit {t7, Some(3)}`. `push` publishes it, then sends it to the app.
6. `serve` gets it from `rx`, the filter admits it, and it is written.
7. The CLI prints `{"code":3}` and exits 0. The daemon reads EOF and drops `rx`.

### Interface Contract

Additive only. Both codecs ignore unknown keys and unknown types.

```
subscribe   { t:"subscribe", kinds?: [str], term_id?: str }           cli → daemon
            reply: err (then close) | snapshot frames…, ack, then live frames
terms_list  { t:"terms_list" }                                         cli → daemon; reply terms | err
terms       { t:"terms", terms: [ { term_id: str, board_id: str,
                                    cwd?: str, proc?: str } ] }        daemon → cli
```

- **`subscribe`.**
  - `kinds` values: `exit`, `bell`, `changed`, `report`. Missing: all four. Unknown values are ignored. None known: `err` `no known event kind`.
  - `term_id` not live and not among the last 64 exits: `err` `unknown terminal: <id>`.
  - The snapshot comes only with a `term_id`: that term's `term_report` (with `report` in the kinds), then its `exit` from the ring (with `exit`, when it is not live). Then `ack`.
  - Live frames are the existing `exit`, `bell`, `file_event` and `term_report` frames, byte for byte as the app gets them, filtered. A `term_id` filter passes no `file_event`.
  - A report that ends with its terminal's exit gets no `term_report` (spec 2611.0009 D4: the daemon forgets it, `state.rs:511`, and the `exit` frame ends it). A receiver that tracks reports must take `exit` too.
  - A frame may come twice: once in the snapshot and once live, or a `file_event` with the same `mtime_ms`. Receivers must accept that.
  - A subscriber more than 1024 frames behind gets `err` `lagged`, and the daemon closes the connection.
  - After `subscribe`, the daemon reads nothing from the client but its close.
- **`terms`.** Rows sorted by board order, then `term_id`. `cwd` and `proc` are omitted when the daemon could not read them.
- **Not persisted.** The exit ring is in memory only. A daemon restart empties it.
- **New conformance vectors** [D18]: the next free numbers at merge; the current proposal is V28–V32 (hex = `rmp_serde::to_vec_named` bytes, in its key order; each vector gives the whole frame):
  - **V28:** `{t:"subscribe", kinds:["exit","report"], term_id:"t1"}`
  - **V29:** `{t:"subscribe"}` (no `kinds`, no `term_id`)
  - **V30:** `{t:"terms_list"}`
  - **V31:** `{t:"terms", terms:[{term_id:"t1", board_id:"board-0", cwd:"/w", proc:"zsh"}]}`
  - **V32:** `{t:"terms", terms:[{term_id:"t1", board_id:"board-0"}]}` (no `cwd`, no `proc`)
  - Both codecs decode each one and round-trip it. The Swift encoder's bytes equal Rust's (`RustEncoderParityTests`). V1–V24 (and V25–V27 if merged) do not change.

## Alternatives Considered

- **A new handshake role, `events`** [D1]. An older daemon would refuse it at once (`conn.rs:76`), so a new CLI would fail fast instead of waiting 5 s. It loses because it adds a role to both codecs' docs and to `handshake`, while `report` already set the pattern of a `cli` message with a 5 s *older daemon* line. `TermsList` would still need the 5 s wait.
- **`Ack` first, then the snapshot.** Simpler to describe, but the CLI then cannot tell a snapshot line from a live one, and `events` loses the `snapshot` marker. `Ack` after the snapshot costs nothing more.
- **Filter at the sender** (one channel per subscriber). It saves the clone of frames a subscriber does not want, but it needs a registry of subscribers in the daemon and a lock in `push`. R5 chose one broadcast channel.
- **A new event schema** (`{event, term, …}` on the wire). Rejected by the `/simplify` note: the existing frames already carry the facts, and the CLI shapes the JSON.
- **`wait --changed` through the daemon's watcher, or a second daemon watcher.** Rejected by the design (*Alternatives*): it restarts the shared FSEvents stream, uses its path budget, and widens the crash surface.
- **Keep the last report and bell history for `events` replay.** Not needed: reports are already current state in the daemon, and a bell is a moment (design §2).
- **Read the cwd for `terms` from `term_records.last_cwd`.** No file-system call, but it lags by one command (it is read only when the foreground pid changes). A fresh read through the gate is bounded and more current.

## Migration & Rollback

- **Migration.** None. Nothing is persisted.
- **A new CLI with an older daemon.** The daemon ignores `subscribe` and `terms_list` (`conn.rs:101-102`). `terms`, `events` and `wait` wait 5 s and exit 1 with `no answer from the daemon in 5 s (an older daemon)`. A `wait --timeout` shorter than 5 s exits 124 instead, with the line `tarmac: wait: timed out before the daemon answered` [D14]. `wait --changed` does not talk to the daemon, so it works with any daemon.
- **A new daemon with an older CLI.** Nothing changes.
- **A new daemon with any app.** The app gets the same frames as today. The tap does not change `push`'s return or the order of the app's frames.
- **Rollback.** Revert the change. No state to clean.

## Security Considerations

- **Who can subscribe.** Any process that can open the socket. The socket is the user's own. A subscriber sees the paths of open docs, report texts and the exits and bells of every terminal. This is the same trust as `open`, `push` and `report`; `tarmac terms` also shows each terminal's cwd.
- **A subscriber cannot slow the daemon.** `broadcast::send` never waits. A slow subscriber only lags and is closed (R5). A stuck one blocks only its own task.
- **No cap on the number of subscribers.** Each costs one task and one receiver, as each `cli` session does today. See *Trade-offs*.
- **`wait --changed` reads only metadata**, never the file's bytes, and only of the path the caller names, with the caller's own rights.

  - (c) A missing path, then created → exit 0, `{"deleted":false}`.
  - (d) Delete it → exit 0, `{"deleted":true}`.
  - (e) `touch` only (mtime changes, size does not) → exit 0.
- **S14 (`terms`; CLI):** A double that answers `Terms` with V31's row and V32's row gives two lines, `{"term":"t1","board":"board-0","cwd":"/w","proc":"zsh"}` and `{"term":"t1","board":"board-0"}`, and exit 0. An empty list gives no output and exit 0.
- **S15 (wire):** V28–V32 decode to the stated structures in both codecs and round-trip. The Swift encoder's bytes equal Rust's. A `subscribe` with no keys has no `kinds` or `term_id` key; a row with no `cwd` has no `cwd` key. V1–V24 still pass unchanged.

### Edge Cases

- **S16 (the filter; unit, `events.rs`):**
  - `Filter::new(None, None)` admits `Exit`, `Bell`, `FileEvent` and `TermReport`, and not `Output`, `TermProc`, `DocOpened`, `BoardList`, `DocEvent` or `Err`.
  - `kinds: ["exit"]` admits `Exit` only.
  - `kinds: ["exit", "later"]` is `Ok` and admits `Exit` only. `kinds: ["later"]` and `kinds: []` are `Err("no known event kind")`.
  - `term_id: T` admits `Bell {T}`, not `Bell {U}`, and no `FileEvent`.
  - `is_event` is false for `Output`.
- **S17 (the exit ring; unit):**
  - After 65 `record`s of distinct ids, `lookup` of the first gives `None` and of the 65th gives its code.
  - Two records of the same id give the later code.
- **S18 (the ring is written before the term goes; state-level):**
  - Given a daemon with a live term T (a detached handle put in `terms`),
  - when `term_ended(T, Some(3))` runs,
  - then right after it, `exits.lookup(T)` is `Some(Some(3))` and `terms` has no T.
  - The order inside `term_ended` (the ring before `terms.remove`) has no deterministic test: the window is a few instructions wide. Review checks it, under exception 2 of `docs/coding-style.md` (thin wiring over `ExitRing::record`, which S17 tests). The PR body states the check.
- **S19 (a live term wins over the ring; integration):**
  - Given T exited with code 3, then a new terminal spawned with the same id T,
  - when a subscriber sends `Subscribe {kinds: ["exit"], term_id: T}`,
  - then the snapshot is empty, and the new T's exit comes live.
- **S20 (the subscriber goes; unit, `serve` on a duplex):**
  - Given `serve` on a duplex with a filter for all kinds,
  - when the client end is closed,
  - then `serve` returns within 1 s, and the fan-out's `receiver_count()` is 0 after it.
  - Bytes the client writes after `Subscribe` are dropped: when the client writes half a frame (2 bytes) and then a published frame arrives, `serve` keeps running and writes that frame whole. This fails if the read arm is a framed read that the receiver arm cancels.
- **S21 (lagged; unit, `serve` with `Fanout::new(2)`):**
  - Given a subscriber whose `serve` the test has not polled, and 3 published frames,
  - when `serve` runs,
  - then the client end reads `Err {msg: "lagged"}` as the first frame, then EOF.
- **S22 (the tap does not change `push`; state-level):**
  - Given a daemon with a subscriber, no app, and an open doc D on the active board,
  - when `docs::push_file_event` runs for D,
  - then the subscriber gets the `FileEvent`, and D is held: the next `take_untold` of its registry gives it. (`push` returned `false`; `push_file_event` holds on that.)
  - Given an app and no subscriber, `push` of `Output` returns `true` and the app gets it.
- **S23 (no watch for any of this; state-level):**
  - Given a daemon with a counting `WakeSource` and one open doc (one `watch` call),
  - when the test subscribes with every filter shape, sends `TermsList`, and drops the subscribers,
  - then the source counted no further `watch` or `unwatch` call.
- **S24 (`terms` with a cwd that does not answer; state-level, `StuckFs` holding `pid_cwd`):**
  - Given a daemon on `StuckFs` (`fixtures.rs`) with four live terms, each spawned by the state tests' `spawn` helper (as `state/tests/spawn_cwd.rs` does) with `["/bin/sh", "-c", "read _"]`, so each has a real foreground pid, and every `pid_cwd` held,
  - when the terms list is built,
  - then it is done in less than 2 × `LIMIT` (one after another would take 4 × `LIMIT`), it has four rows, no row has `cwd`, and each row has `proc`.
  - Then the test releases the held calls.
- **S25 (the app slot is not touched; integration):**
  - Given an app connection A and a subscriber,
  - then `probe_app_slot` reports A as before; A still gets `Bell` and `Exit` frames for its terminals.
  - When A closes and the subscriber stays, `probe_app_slot` reports `app_connected: false`.
  - When a new app B connects while the subscriber stays, the subscriber still gets frames.
- **S26 (`--term` drops doc changes; integration):** Given a subscriber with `{term_id: T}` (all kinds) and an open doc D, when the test edits D and then T rings, the subscriber gets `Bell {T}` and no `FileEvent`.
- **S27 (wait --changed timing and settle; CLI and unit):**
  - Unit: `poll_interval` gives 100 ms at 0 and 1 999 ms, 250 ms at 2 000 ms and later.
  - Unit: the sample compare finds a change in each of `dev`, `ino`, `mtime_ns`, `size`, and between `Present` and `Missing`, and none for equal samples.
  - Unit: the settle decision ends only after MS with no change, and restarts at each change.
  - CLI: an atomic replace 2.2 s after the start makes the CLI exit within 250 ms + 200 ms of the rename (the design's ≤ 250 ms target, plus process slack).
  - CLI: `--settle 500` with changes at 0.3 s and 0.6 s after the start exits no earlier than 1.1 s after the start.
- **S28 (a change before the start does not count; CLI):** Write the file, then start `wait --changed` with `--timeout 600` → exit 124, empty stdout.

### Error Scenarios

- **S29 (unknown terminal; integration and CLI):**
  - Integration: `Subscribe {term_id: "nope"}` gets `Err {msg: "unknown terminal: nope"}`, then EOF.
  - Integration: `Subscribe {kinds: ["later"]}` gets `Err {msg: "no known event kind"}`.
  - CLI: a double that answers `Err {msg: "unknown terminal: t9"}` → stderr `tarmac: unknown terminal: t9`, exit 1.
- **S30 (a wait that cannot happen; CLI):** For `--bell t9` and `--report done --term t9`, a double that writes `Ack` then `Exit {t9, Some(0)}` → stderr `tarmac: terminal t9 exited`, exit 1, empty stdout.
- **S31 (timeouts; CLI):**
  - A double that writes `Ack` and holds: `wait --exit t9 --timeout 300` exits 124 after at least 300 ms and within 300 + 500 ms, with empty stdout and stderr.
  - A double that never answers: `wait --exit t9 --timeout 300` exits 124 in the same window, with empty stdout and exactly one stderr line, `tarmac: wait: timed out before the daemon answered`.
  - A double that never answers: `wait --exit t9` with no timeout exits 1 after about 5 s with the *older daemon* line. `terms` and `events` do the same.
- **S32 (the daemon goes away; CLI):** A double that writes `Ack` then closes → `wait --exit t9` exits 1 with `tarmac: daemon connection lost: …`. A double that writes `Err {msg: "lagged"}` → exit 1 with the *lagged* line.
- **S33 (usage, exit 2; CLI):** Each of these exits 2 with a usage line on stderr and makes no connection: `wait`; `wait --exit`; `wait --exit t1 --bell t1`; `wait --report later --term t1`; `wait --report done`; `wait --exit t1 --term t1`; `wait --exit t1 --settle 5`; `wait --exit t1 --timeout 0`; `wait --exit t1 --timeout abc`; `wait --changed`; `events --kind later`; `events --kind ""`; `events --term t1 --kind changed`; `events extra`; `terms extra`.
- **S34 (stat errors; CLI):** `wait --changed` on a path inside a directory with mode 000 (not `NotFound`) exits 1 with `tarmac: cannot stat …`. The test restores the mode in its cleanup.
- **S35 (events and a closed stdout; CLI):** Given a double that writes `Ack` and then a `Bell` every 50 ms, when stdout is a pipe that the test closes after it reads the first line, then the CLI exits 0 within 1 s with empty stderr.

- **S43 (the report replay is not published; integration) [D5]:**
  - Given T with a report from `cli_report`, a subscriber with `{kinds: ["report"]}` that has read its `Ack`, and the app connection closed,
  - when a new app connects (its restore replays T's report to the app), and then the app sends `BoardSwitch` to the active board's own id,
  - then the app gets T's `TermReport` in each restore, and the subscriber gets no frame within 1 s of each.
- **S44 (a timeout while it settles; CLI) [D17]:** `wait --changed F --settle 1000 --timeout 800`, with one change of F 200 ms after the start, exits 124 at about 800 ms, with empty stdout.

### QA (dev channel, not automated)

Use `make run` with its own `DEV_DIR`. Call the dev CLI (`core/target/debug/tarmac`) from a dev terminal, and from a plain Terminal.app shell with `TARMAC_SOCKET` set to the dev socket's absolute path.

- **S36 (terms):** With three dev terminals on two boards, one `cd`-ed to `/tmp` and running `vim`, `tarmac terms` lists all three, in board order, with `/tmp` (as its real path) and `vim`.
- **S37 (wait for an exit):** In terminal A run `tarmac wait --exit <B's id>`. In B run `exit 3`. A prints `{"code":3}`. Run the same wait again: it prints at once.
- **S38 (events):** Run `tarmac events` outside the app. In a dev terminal: `printf '\a'`, `tarmac report blocked "QA"`, edit an open doc, `exit 2`. Each shows one line. Switch to a board with a doc edited in the background: its `changed` line shows at the switch.
- **S39 (wait for a report):** `tarmac wait --report blocked --term <id> --timeout 60000` outside; then `tarmac report blocked "QA"` in that terminal; the wait prints the report and exits 0.

## Trade-offs and Limitations

- **`changed` means "told to the app"**, not "the file changed" [D5]. A `doc_refresh`, a repeated `data_file` and a re-told held change repeat an `mtime_ms`. Compare `mtime_ms` to skip them.
- **`changed` covers the active board only, at the looks** (design §3). A background board's change comes when the board is shown. With no app there are no data-file events.
- **Repeated frames.** A frame can come in the snapshot and again live. Every one is a state or has its own `mtime_ms`.
- **No `report` event at an exit.** A report that ends because its terminal exited sends no `TermReport` (slice 2, D4). `events --kind report` alone never shows that end; take `exit` with it. `GUIDE.md` says so.
- **A subscriber holds a daemon file descriptor, possibly for hours.** `tarmacd` does not raise `RLIMIT_NOFILE`, and the accept loop retries a failed `accept` with no pause (`main.rs:124-134`). Many forgotten `events` or `wait`s could use up the descriptors and make that loop spin. `GUIDE.md` tells unattended scripts to pass `--timeout`. A follow-up issue tracks a cap on subscribers or a raised limit (was OQ5).
- **Only 64 exits are kept.** A `wait --exit` for a terminal that ended 65 exits ago gets `unknown terminal` (exit 1). A daemon restart empties the ring.
- **A reused id.** A live term with an id in the ring hides the old exit [D3].
- **An older daemon costs 5 s.** A new verb waits 5 s for its answer [D1]. With `--timeout` under 5 s, the result is 124, not 1 [D14].
- **`wait --report` takes a current report** [D12]. A script that wants only a new report must make sure the old one is gone first. With slice 3's hooks, `UserPromptSubmit` clears it at each prompt.
- **`wait --changed` touches the file system.** On a hung volume, a `stat` can block and Ctrl-C may not end it (#267). `open` and `push` avoid this; `wait --changed` cannot, because a stat is its job. `--timeout` does not help while a stat is blocked.
- **Two notions of "changed"** (design *Trade-offs*): the CLI's stat poll and the daemon's `FileEvent` can disagree on a burst.
- **A change and its undo between two polls are not seen** (for example a write and a restore of the same size and mtime within 100 ms).
- **A stuck subscriber keeps its task** until it reads again or exits. Its memory is bounded by the shared ring.
- **The broadcast ring is allocated at start** (1024 slots), with or without a subscriber. That is a fixed cost, not a cost per frame.
