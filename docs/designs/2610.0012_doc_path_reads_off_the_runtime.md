# 2610.0012 Read a doc's path off the runtime, with a time limit

> **Doc status: HISTORICAL** — a design record for work that has already
> shipped (#274, #275, #276, #277). It describes the system *as of the change it
> accompanied*, not as it is today. For current behaviour see
> [`../architecture.md`](../architecture.md); for the contract it was built
> against, see the
> [spec](../../.blueprint/specs/2610.0012_doc_path_reads_off_the_runtime.md).

**Date:** 2026-10-29
**Status:** implemented
**Author:** EP Lin
**Doc type:** Mini RFC
**Issue:** [#267](https://github.com/pingeplin/tarmac/issues/267)

## Decision

Every call that touches a doc's path on the file system leaves the tokio
workers and the main thread, and the caller waits a fixed time for it:

- `canonicalize`, `metadata` and the `.git` walk go through one **gate**. The
  gate runs each call on a blocking thread. A path whose call is still out is
  not tried again until that call returns.
- notify's `watch` / `unwatch` go to one **watcher thread**. It owns the notify
  source and runs its calls one at a time. The callers keep only the counts,
  under a lock that no file-system call is made under.
- The `tarmac` cli makes no file-system call on the path. It makes the path
  absolute without touching the disk and leaves every read to the daemon.

This generalises what `reader::FileReader` already does for a look (#265) to
startup, open and close. A daemon with a doc on a dead volume then:

- starts and answers;
- fails that doc's open in seconds;
- closes that doc at once.

Every other doc and connection is unaffected, with two exceptions named in
*Trade-offs*.

## Problem

The measurements are in the
[#267 comment](https://github.com/pingeplin/tarmac/issues/267#issuecomment-6490720115).
They used a WebDAV mount whose server stops answering. `stat`, `realpath` and
`exists` under it then block in an uninterruptible state for 4–6 minutes, and
SIGKILL does not reap the thread.

- **Startup:** a restored doc on the mount. `hydrate` runs on the main thread, so
  the socket accepts but no hello is answered until the volume answers.
- **Open in the cli:** `tarmac open` calls `canonicalize` and `metadata` on the
  path itself (tarmac-cli main.rs:190,192), before it connects. On a hung
  volume the cli process is stuck there for 4–6 minutes, prints nothing, and
  Ctrl-C does not end it. It never reaches the daemon.
- **Open in the daemon (cli or app):** `handle_open`'s `canonicalize` / `metadata` runs on a
  tokio core worker. It freezes **every** connection. 6 of 6 trials froze: app
  hellos, `BoardCreate`, other opens, new handshakes. The worker that holds the
  I/O driver is the one in `stat`, so nothing polls kqueue, and timers stop too.
- **Close of a doc on the mount:** `release_watch` calls notify `unwatch`, which
  canonicalizes the path. It does this **while holding the watcher
  `std::sync::Mutex`**. The same global freeze follows.
- **A look** is bounded since #265: 1.0 s the first time, 1.4 ms once the path is
  out.

A user can hit this with a doc on an SMB/NFS/WebDAV share whose server drops, or
on an external disk that stops answering. Then the cockpit stops answering for
minutes. If no terminal is printing, nothing wakes the runtime: a PTY chunk or an
FSEvents callback does, and in the measurements either one ended the freeze.

## Constraints

- **A stuck call cannot be stopped.** The thread is in `U` state. A time limit
  can only stop *waiting*. The thread stays busy until the file system gives up,
  about 4–6 minutes for webdavfs. So the design has to bound how many threads a
  dead path can hold, not only how long a caller waits.
- **A timer only fires if the runtime is alive.** `tokio::time::timeout` around a
  call that runs on the worker does nothing. The call has to leave the worker.
- **notify's FSEvents watcher reads the path itself.** It calls `exists()` and
  `canonicalize()` in `append_path` / `remove_path` (notify 8.2.0
  `fsevent.rs:376,389,392`), under our watcher lock. We cannot make notify skip
  that.
- **The look's ordering rules stand.**
  - A watch-set change is followed by a look (#253).
  - `delete_board` has no look of its own: its caller sends the active board
    next, and that send looks (#268).
  - `looking` is taken before `boards`.
  - The watcher lock is never held across `.await`.
- **No protocol change in this step.** The wire is additive-only. A new
  "unreachable" state on a card is possible later (see Out of scope).

## Proposal

### One gate: `reader.rs` grows from "stamps for a look" to "any read of a doc path"

`FileReader` becomes `PathGate`. It keeps its two halves:

- the `limit`;
- the `out` set: paths whose call has not returned.

Its API:

```rust
/// The file-system calls the gate makes. `RealFs` in the daemon; a test
/// double holds a call, as `StuckReads` holds a `ReadFile` today.
pub trait PathFs: Send + Sync {
    fn resolve(&self, raw: &Path) -> io::Result<(PathBuf, FileStamp)>;
    fn stamp(&self, path: &Path) -> Option<FileStamp>;
    fn repo_of(&self, path: &Path) -> Option<RepoInfo>;
}

impl PathGate {
    /// `returned` runs when an out call returns: the daemon notifies `wake`
    /// and sends the watcher thread `Retry`.
    pub fn new(fs: Arc<dyn PathFs>, limit: Duration,
        returned: Arc<dyn Fn() + Send + Sync>) -> Self;
    /// `op` on a blocking thread, keyed by `key`. `Err(Out)` when it did not
    /// return within the limit, or when an earlier call on `key` is still out.
    pub async fn run<T: Send + 'static>(&self, key: &Path,
        op: impl FnOnce(&dyn PathFs) -> T + Send + 'static) -> Result<T, Out>;
    /// The look's batch read, as `FileReader::stamps` today.
    pub async fn stamps(&self, paths: impl IntoIterator<Item = PathBuf>)
        -> HashMap<PathBuf, Option<FileStamp>>;
    /// True while a call on a path in `dir` is out.
    pub fn is_out_dir(&self, dir: &Path) -> bool;
}
```

The `out` set is shared by both methods. It is keyed by the doc's path for
stamps and opens, and by the directory for a startup `.git` walk. So a dead doc costs **one** blocking
thread, however many looks and opens ask for it.

An open is keyed by the path it was given and a look by the canonical one. A
doc opened through a symlink can therefore hold two threads. That is accepted.

A directory is **out** when an out key is the directory itself or a direct child
of it (`gate.is_out_dir(dir)`). A dead mount deeper down does not make `~` out.
This is how a close and the watcher thread learn that a directory is dead
without a call of their own.

When an out call returns, the path leaves the set and `returned` runs: `wake`
is notified, so a look runs at once, and the watcher thread is sent `Retry`
(below). See
*Retry*.

`PathFs` keeps the seam that `FileReader::new(read, limit)` gives the #265
tests today (`stuck_reader`, `StuckReads`). The same double holds an open, a
`.git` walk or a startup read.

### The watcher thread: notify off the callers

notify's `watch` / `unwatch` read the path themselves and cannot be put behind
our gate. Today they run under the watcher `std::sync::Mutex`, on the caller's
worker. So `WatcherState` splits in two.

**`doc_counts`** (docs per directory, as today) stays in `Daemon`, under a
`std::sync::Mutex` that is held only for map updates, never for a file-system
call. It is the only state the callers keep.

**The watcher thread** is one `std::thread`. It owns the existing
`Box<dyn WakeSource>` unchanged, so `NotifySource` and the test doubles
(`Silent`, `RefusesDir`) still plug in through `Daemon::with_source`, and a
double that blocks gives the test of the *Riskiest assumption*. It also owns
two sets of its own: `watched`, the directories in the stream, and `retry`, the
directories it skipped.

It takes one request, `Reconcile(dir)`. The request is level-triggered: the
thread compares "`doc_counts[dir]` > 0" with "`dir` in `watched`".

1. **Equal:** nothing to do. A re-open that came before an unwatch's
   `Reconcile` ran, or a close before a watch's, ends here with no extra rule.
2. **`gate.is_out_dir(dir)`:** no notify call. `dir` goes into `retry`. A
   caller that waits gets `Out`.
3. **Otherwise:** `watch` or `unwatch`, update `watched` (an `unwatch` even when it fails: notify has already dropped the path), then
   notify `wake` whether it succeeded or not: a failed call restarts the stream
   too (#253: every stream restart is followed by a look). A waiting caller gets
   the error.

When an out call returns, the gate sends the thread `Retry`, and it reconciles
each directory in `retry` again. No polling.

`acquire_watch` and `release_watch` update `doc_counts` and send `Reconcile`:

- **A first doc in a directory:** wait for the answer, with the limit.
- **Any other open:** do not wait. A directory that is counted but not
  watched, because its watch failed at startup, is watched then (*Decisions*,
  8).
- **The last doc out of a directory:** return at once, with no wait.

`open_doc` keeps its own `report_changes` after the upsert, as today: only
that look is sure to run after the doc is registered, so a write between the
open's stamp and the watch is not missed. The thread's `wake` may add one more
look, which finds nothing new.

`close_doc` stops looking after an unwatch. The thread's `wake` gives that
look, after the stream has really restarted, which a caller's look can no
longer promise: the unwatch now runs after the close has answered. For the same
reason a board delete gets the thread's look as well as its caller's board
send (#268). That is one look more than today, and it is the one #253 needs.
`watch_loop`'s one-permit `Notify` folds the wakes of a delete that unwatches
many directories into one look, or two when a wake comes during the look.

If notify blocks anyway (the race under *Riskiest assumption*), only this one
thread blocks:

- **Opens that need a new watch** fail at their limit.
- **Every other open, close and look** goes on: they never wait for the thread.

### Each call site, through the gate

| Today (no limit) | Through the gate |
|---|---|
| `tarmac open` in the cli: `canonicalize` + `metadata` (tarmac-cli main.rs:190,192) | Removed, not gated. The cli makes the path absolute with `std::path::absolute`, which joins it to the cwd and does not touch the disk, and sends it. The daemon already canonicalizes and refuses a path that is not a regular file, with the same messages. A cli-side time limit is not used: a process with a thread stuck in the kernel may not be able to exit, and that is not measured. The `opened …` line names the path as sent, not the canonical one. |
| `handle_open`: `canonicalize` + `metadata` (docs.rs:54,56) | One `gate.run(raw_path, canonicalize_and_stat)`. `Out` replies `Err("cannot open … : did not answer in N s")` to the cli or the app. |
| `open_doc`: `reader::stamp` (state.rs:207) | Folded into the open's call above: it is the same `metadata`. |
| `upsert_doc` → `derive_repo` for a new doc (docs.rs:100) | Only for a doc not yet registered, as today: the open looks the canonical path up in the registry, then runs `repo_of` on the gate before the `boards` lock. Two opens of the same new doc at once may both walk; the second result is dropped. `Out` registers the doc with no repo, as for a doc outside a repo, in a directory that is already watched. In a new directory the stuck walk makes the directory out, so the open fails at its watch (*Decisions*, 9). The next startup fills it in. A re-open does not: `upsert_doc` keeps the stored repo of a doc that is already registered. |
| `open_doc` → `acquire_watch` → notify `watch` (first doc of a dir) | A `Reconcile(dir)` to the watcher thread, waited for with the limit (above). `Out`, or no answer in time, makes the open fail, as a failed watch does today. The open has already read the doc's own path through the gate, so a dead directory is usually known to be out before the thread is asked. |
| `close_doc` / `delete_board` → `release_watch` → notify `unwatch` | The count drops and a `Reconcile(dir)` is sent. The close answers at once. While the directory is out, it waits in the thread's `retry`. A dead directory left in the FSEvents stream costs only spurious wakes, and a look ignores those. |
| Startup `hydrate`: `derive_repo` + `stamp` per doc (persist.rs:106,116); the startup `acquire_watch` loop | `Daemon::new` becomes `async`, so the gate's timer can fire. Every doc's stamp (the batch read, ≤ 2 × limit) and one `.git` walk per distinct directory (all at once; docs in one directory share a repo) start together, so startup waits at most 2 × limit in all. The startup watches are sent to the watcher thread and not waited for. A doc whose stamp is out is restored as **unread** (below), not as gone. |
| The first reading of an **unread** doc | `DocInfo` gets an `unread` flag. In `take_changes`, the first reading of an unread doc is taken as `seen` with no `FileEvent`, as a restart does today (architecture.md, *a daemon restart*). After that the doc is like any other. `seen: None` cannot carry this: it already means "the file is gone", and a gone file does give a `FileEvent` when it comes back. |

### Retry

**Yes, and it happens on its own.**

- **While the call is out:** the path is never tried again. An open or a look
  that asks for it gets `Out` at once (an open in under 1 ms, as the look does
  today). It does not add another stuck thread.
- **When the call returns:** the gate takes the path out of `out` and notifies
  `wake`. The volume may answer again, or the file system may time out and
  return an error after about 4–6 minutes. Either way the next look:
  - reads the doc;
  - pushes a `FileEvent` if it changed (an unread doc is taken silently);
  - meanwhile the gate's `Retry` lets the watcher thread run the watch or
    unwatch it skipped for that directory, and its `wake` gives one more look.
- **An open is not finished late on its own.** The `tarmac open` call has already
  had its error. A doc that appears later, with no one having asked, would be a
  surprise. The user, or the agent, runs the open again, and it works once the
  path has returned.

### Giving up on purpose

Today the user **cannot** give up: closing the card is what hangs. After this
change, every step the user can take answers within the limit, whatever the
volume does:

- **Close the card:** it answers at once. The unwatch waits in the watcher
  thread's `retry` (above).
- **Delete its board:** the same.
- **An open that hangs:** it answers by itself, with an error, after the limit.
  Ctrl-C on `tarmac open` ends the cli at once, because the cli makes no
  file-system call on the path and only waits on the socket. The daemon does
  not see the
  drop: `cli_session` waits for `handle_open` inline, so its wait still ends at
  the limit and the reply goes to a closed connection. The stuck thread is left
  behind as for a timeout.

The kernel call itself cannot be stopped by anyone, so "giving up" means the
daemon stops waiting and forgets the doc. A forgotten path's stuck thread still
runs to its end and then clears the path from `out`; nothing else is affected.

Opt-in controls are *not* proposed in this step: a "stop trying this doc"
action, or a card that shows "unreachable". Both need a new message in both
codecs. The two cases above already give the user a way out.

## Alternatives

**A. `tokio::task::block_in_place` around each call.** This is a few lines per
call site. The worker hands its core, and with it the I/O driver, to a new
thread, so the rest of the daemon keeps answering. That fixes the global freeze,
the worst symptom.

It does not bound anything:
- the asking connection still waits 4–6 minutes;
- the close still holds the watcher lock for that long, so every open and close
  behind it waits too;
- startup is unchanged.

It is a fair stopgap if the gate slips, not the fix.

**B. Accept connections before reading the restored docs.** Hello would be
answered at once. But the app's first `Restore` needs the boards, so it would
wait for `hydrate` anyway, or show cards with no repo colour and no stamp. That
moves the wait without bounding it. The gate makes startup bounded, so this is
not needed.

**C. One dedicated file-system thread for every doc call.** It is simple and it
serializes calls. But one dead path stalls every other doc's open and look behind
it: the very failure we are removing. A pool of such threads, with a per-path out
set, is the gate.

**D. Drop notify's own path checks by talking to FSEvents directly.** That
removes the `canonicalize` inside watch and unwatch at the root. But it means
owning an FSEvents binding in place of a maintained crate. The watcher thread
gets the same bound. Its one cost is that new watches stall while notify is
stuck (below).

**E. Run notify inside the gate, under the watcher lock.** Each watch and
unwatch would be a gate call. But the lock would then be held on a blocking
thread for as long as notify hangs. Every other open and close that wants the
lock would park a worker (the freeze again) or take one more blocking thread
each. The gate's one-thread-per-dead-path bound would be lost. The watcher
thread keeps the lock free of file-system calls.

## Trade-offs we accept

- **A slow but live volume can fail an open.** For example, the first stat of a
  sleeping NAS can take 2–3 s. That open now fails where it would have succeeded
  late. We value "the cockpit always answers" over "a slow open always succeeds".
  The user can retry, and the path is not marked bad after its call returns.
- **A stuck call still holds a blocking thread for minutes.** It is one thread
  per dead path, not one per request. Tokio's blocking pool allows 512.
- **A deferred unwatch leaves a directory in the FSEvents stream for a while.**
  The only effect is spurious wakes; the look ignores unchanged files.
- **One watcher thread serializes every watch change.** If notify itself hangs,
  opens that need a new directory watched fail until it returns. Opens in
  watched directories, closes and looks are not affected.
- **An app open of a hung doc stalls the app's session for up to `limit`.**
  `app_session` runs each message inline (`dispatch_app_msg`), so terminal
  input, closes and switches from the app wait behind that open. A cli open
  has its own connection and does not do this.
- **`DocInfo` grows an `unread` flag**, one more state for `take_changes` to
  keep right, so that a restart onto a hung volume tells the app nothing new.
- **`Daemon::new` becomes `async`**, and startup can take up to 2 × `limit`
  before it accepts when a restored doc is on a dead volume. With no dead
  volume, startup is unchanged.

## Riskiest assumption

**That a directory the gate does not know to be out rarely makes notify
hang.** The watcher thread asks notify only about a directory that is not out.
But "not out" only means no read under it is stuck *now*. A volume can die
between the last read and notify's call. At startup the watches are sent only
after the stamps and the walks have answered or are out, which is the safer
order: a directory that is out then is never asked of notify.

When that happens, the watcher thread hangs in notify for minutes.

- **Its cost is bounded:** new watches fail, and nothing else waits.
- **It is unbounded in time:** it lasts until the file system gives up.

If it shows up in practice, the fallback is Alternative D. A test can force it:
send a `Reconcile` for a directory on the WebDAV mount with the hold on, before
any read, or plug in a `WakeSource` double that blocks. So the bounded part is testable.

## How we will know it worked

These are measured with the WebDAV harness from #267, driven through
`TestDaemon`, on a runtime kept idle so that the freeze would show.

| Case | Today | Target |
|---|---|---|
| Startup with a restored doc on a hung volume: hello answered | not within 5 s (4–6 min) | ≤ 2 × `limit` + 100 ms |
| `tarmac open` of a doc on a hung volume: the cli process | stuck 4–6 min, no output | exits 1 with `tarmac: cannot open …` on stderr within `limit` + 100 ms; Ctrl-C ends it at once |
| Open of a doc on a hung volume: that connection | no answer within 5 s | `Err` within `limit` + 100 ms |
| Another connection during that open (not the app session that sent it) | no answer within 5 s | answered within 100 ms |
| A second open of the same hung path | another stuck worker | `Err` within 10 ms; still one stuck thread |
| Close of an open doc on a hung volume | no answer within 5 s (global freeze) | answered within 100 ms |
| The watcher thread stuck in notify (forced, see *Riskiest assumption*): an open in a watched directory, a close, a look | the global freeze | each answered within 100 ms; an open that needs a new watch fails within `limit` + 100 ms |
| The volume answers again | — | the next look reads the doc; a re-open succeeds; the skipped watch or unwatch runs |
| Restart with a restored doc on a hung volume, then the volume answers, file unchanged | — | no `FileEvent` for that doc |

`limit` is `READ_LIMIT`, 1 s, for opens and looks (*Decisions*, 1).

## Out of scope

- A card state or message for "unreachable", and a user action to stop
  retrying. These are a protocol change and come later, if wanted.
- The terminal's cwd check in portable-pty (`Path::is_dir` during `SpawnTerm`).
  It has the same shape but is not a doc path; it gets its own issue.
- Making the look faster or changing `READ_LIMIT`.
- A cwd that is itself on a hung volume: `std::path::absolute` reads the cwd
  for a relative path. An absolute path does not need it.

## Decisions

Decided by the user on 2026-10-29:

1. **One limit of 1 s** for opens and for the look. No longer limit for opens.
2. **A timed-out open is not finished late.** The caller runs `tarmac open`
   again when the path answers.
3. **The deferred unwatch is accepted:** a dead directory stays in the
   FSEvents stream until it answers.
4. **The watcher-thread stall is accepted** as a stated risk (Riskiest
   assumption). Our own FSEvents binding (Alternative D) is not written now.
5. **`FileReader` becomes the general `PathGate`.** No second type beside it.
6. **A re-open does not fill in a missing repo.** The next startup does.
7. **The cli makes no file-system call on the path.** It sends the path made
   absolute and the daemon does every read, through the gate.

Decided on 2026-10-29 after the spec review
([spec 2610.0012](../../.blueprint/specs/2610.0012_doc_path_reads_off_the_runtime.md)):

8. **A failed watch is retried by the next open.** Every open sends
   `Reconcile`, and only a first doc waits for its answer.
9. **A new directory whose `.git` walk is out fails the open** at its watch.
10. **Three readings:** a directory is out only through its own key or a direct
    child's; an `unread` doc whose first reading finds no file is gone, as
    today; a `doc_refresh` of an `unread` doc works as today and ends `unread`.
