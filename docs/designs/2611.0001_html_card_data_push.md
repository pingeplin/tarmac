# 2611.0001 Push data into a loaded HTML card

> **Doc status: PROPOSED** — a design that is built in part: phases 1 and 2
> are built (#313, #326), phase 3 is not. For current behaviour see
> [`../architecture.md`](../architecture.md).

**Date:** 2026-11-10, changed 2026-11-11 (decisions 13–22)
**Status:** draft
**Author:** EP Lin
**Doc type:** Feature Doc
**Issue:** [#306](https://github.com/pingeplin/tarmac/issues/306)

## Decision

An HTML card gets new data **without a reload**, in two ways:

- **State.** The card's document names one JSON file. When that file changes,
  the app reads it and hands the whole content to the loaded document. Only the
  latest content matters.
- **Events.** A new cli verb, `tarmac push <html-path> <json>`, hands one JSON
  value to every loaded card of that file, through the daemon. Nothing is kept:
  a card that is not loaded at that moment never sees the event.

Both arrive in the document as DOM events that the card shim dispatches. The
document is not loaded again, so nothing flashes and its JavaScript state
stays.

A data file is in the directory of the HTML file or, from phase 3, under it. A card reads
no file anywhere else, and there is no setting that lets it (decision 14).
The read needs no consent (decision 15).

**A card is not a network boundary.** A card's script can send packets out
today (measured on loopback, see Evidence), as the script of a page in a
browser can. The owner decided on 2026-11-11 not to close this (decision 13):
the fix that was phase 0 of this design was built and taken back out. So a
card that reads a file may also send it away. That is why a card reads only
in its own directory tree: the settings that let it read elsewhere
(decisions 8, 9 and 11) are dropped.

The trade in one sentence: we take **two delivery paths and no replay of
events** in order to get a live feed with no file to manage, and a state path
that needs no cooperation from the writer beyond "write a JSON file".

## Problem

An HTML card was meant to carry a dashboard. Today it cannot do that well.

The card's CSP is `default-src 'none'` with no `connect-src`
(`CardProtocol.csp`), so the document cannot fetch anything. The only way new
data reaches it is a rewrite of the HTML file. The daemon reports the change
(`file_event`), and `HTMLCardView.refresh` gives the frame a new source:

1. the document loads again and all of its JavaScript state is lost;
2. the web view is hidden until the new document says it is on screen (the
   `shown` wait of #255), so the card shows its backdrop;
3. the web view is shown again.

Each update is therefore one flash of the whole card. Observed by the user on
2026-10-29 with a dashboard that was rewritten many times a minute. The zoom
half of that report was fixed in #271. This half was parked.

The user also wants Tarmac as a monitoring surface: a process emits one record
at a time, and a card shows each as it arrives. A rewrite of the HTML file per
record is the same flash, many times a second.

## Constraints

- **The sandbox does not move.** The CSP is byte-exact by spec 2607.0004 and
  the frame is `sandbox="allow-scripts"`. The design adds no network access
  and changes no CSP byte.
- **Tarmac is not an agent harness.** Every mark Tarmac draws is backed by an
  OS fact, and Tarmac never parses agent output. Both paths keep this. The
  facts are a file that changed and a socket call, the same two kinds that
  `tarmac open` and `file_event` already are. Tarmac checks that the payload is
  JSON and carries it. It reads no meaning from it and draws no chrome from it:
  what appears is drawn by the card's own script.
- **The CSP is not the only wall.** Under the card's exact CSP, a `srcdoc`
  frame sent a CSP report to a URL the page chose (one control run outside the
  card). In the card nothing left, and the reason is most likely
  `CardNavigation.htmlCard`, which refuses every subframe that is not the card
  scheme. A change to that rule is a change to the sandbox.
- **The wire grows by addition only**, in both codecs, with new conformance
  vectors after V13.
- **The cli has no dependency but `tarmac-protocol`** (`tarmac-cli/Cargo.toml`:
  "std-only on purpose"). It has no JSON parser and gets none.
- **No file-system call on the main thread or a tokio worker** (2610.0012). A
  data file can be on a volume that does not answer.
- **The watcher gives no detail.** A wake says "look"; looks are at least
  `watch::BURST` (100 ms) apart; the daemon compares stamps
  (`docs::report_changes`). So a notification count is not an event count. This
  is why events cannot ride on the state path.
- **A `file_event` is sent for the active board only**, and each `watch` or
  `unwatch` restarts the FSEvents stream (#253).
- **Host → card messages ask no question.** `CardHostMessage`: "each is a
  state the shim applies as given; none asks a question". State data fits
  that. An event does not: it is the one host message that is not a state. It
  is never sent again after a `ready`, and twice is a bug.
- **Who the path rule is against.** An HTML file from a source the user does
  not trust: a cloned repo, a download. A local process that can write the
  HTML can already read the same files. No rule here stops it.

## Proposal

### What the document sees

```html
<meta name="tarmac-data" content="stats.json">
<script>
  addEventListener("tarmac:data",  e => render(e.detail));   // the whole file
  addEventListener("tarmac:event", e => append(e.detail));   // one pushed value
</script>
```

- `tarmac-data` names one file. A relative name is taken from the directory of
  the HTML file. One file for each card.
- `tarmac:data` fires with the parsed content after each load of the document
  and after each change of the file. The shim also keeps the last content at
  `window.tarmac.data`, so a script that starts late can read it.
- `tarmac:event` fires once for each pushed value, in the order pushed.
- Both are dispatched by `card_shim.js`, which already accepts messages from
  the host page only. A document that listens to raw `message` events would
  have to make that check itself.

MCP Apps (SEP-1865) rejected a host-injected object because not every host can
inject one. Tarmac injects its shim into every card already
(`CardProtocol.respond`), so the cost is paid.

### State: one file, latest wins

```
page ──ready{data:"stats.json"}──▶ app ──doc_data{board,path,data}▶ daemon
                                    ▲                              │ stamps the file,
                                    │                              │ looks at it with the docs
        read off the main thread ◀──┴──────file_event{data path}───┘
        StrictJSON check
        callAsyncJavaScript ──▶ shim ──▶ "tarmac:data"
```

1. The shim's `ready` word gains the `tarmac-data` content. It is a message
   inside the app, not a wire message. **Only the first `ready` of a load
   names the file.** Today `ready` has no load number, and a card's own script
   can post one: the host page passes on any small object and keeps only
   `shown` for itself (`card-host.js`). So the host page, which the card
   cannot speak for, stamps the load on `ready` as it does on `shown` and
   passes on one for each load. Without this, one loaded document could name
   file after file, each a stat, a read and perhaps a new watch. This is
   decision 22; the other way was to read the name from the HTML as it is
   served, in the scheme handler. The host page drops a message over
   1,000 characters whole; the spec must size `ready` for a long path.
2. The app makes the name absolute with no file-system call, and applies the
   path rule (below). A refusal ends here, with a line in the card's console.
3. The app sends one new wire message,
   **`doc_data {board_id, path, data}`** (app → daemon): "the doc `path` on
   this board reads `data`". It names the board, as a layout snapshot does: a
   card of a board in the background can say `ready` too (a web process that
   was restarted, a reconnect), and the same HTML can be open on two boards.
   The board key is decision 22. No `data` key clears it. The daemon keeps this with the doc entry, in memory
   only, includes the file in its looks, and answers with a `file_event` for
   the data path at once when the file exists, as `doc_refresh` does. After
   that it sends a `file_event` for each change. `file_event` is the existing
   message; the app tells a data path from a doc path by what it registered.
4. On a `file_event` for a data path the app reads the file **off the main
   thread**. One read at a time for each card: an event that arrives during a
   read marks the card "read again", and no more than that. With the
   reader's 64 MiB cap (below), this is all that bounds the cost of a large
   file (see Trade-offs).
5. The content must pass `StrictJSON` (the kit's check, serde_json's grammar).
   Content that does not pass is not delivered and the document keeps what it
   has. A writer caught in the middle of a write is the usual cause, and the
   daemon reports the file again while the writes go on (#266).
6. The app hands the text to the shim as an **argument** of
   `callAsyncJavaScript`, never spliced into a script (`CardWebView`). The shim
   parses it, stores it and dispatches `tarmac:data`. The text form is a
   requirement, not a taste: a 10 MB string argument held the main thread
   under 3 ms for the call; the same data as a dictionary argument held it
   165–186 ms (Evidence). The measurement parsed the text in the host page and
   posted the object on. Here the text is posted and the shim parses it, so
   the spec measures this path again.

The app reads the file, not the daemon, so the content never crosses the
socket and the 16 MiB frame limit does not apply to it. The app reads the HTML
file itself today too, with `FileBytes.read`: regular files only, 64 MiB at
most, because the file is held whole in memory. A data file is read the same
way and so has the same cap. The cap is kept and no other limit is added
(decision 20).

**Late join is one rule.** After every `ready` — a first load, a reload after
the HTML file changed, a web process that was restarted — the app sends
`doc_data` again, and the daemon's immediate `file_event` brings the current
content. After a reconnect the app sends `doc_data` again for each card that
has one. A data file is looked at with its board's docs: while the board is
active, and once at the switch back, when the daemon compares and reports. A
data file that is deleted sends nothing, and the document keeps what it has.

**A culled card is not fed state.** The app keeps "content is newer than what
the document has" and delivers once when the card is back in view. For its
state, a dashboard off screen costs a stat in each look and nothing more.
Events still reach it (see the table under *Events*).

Because every read follows a `file_event`, there is no window in which a
change between the app's read and the daemon's first stamp is lost.

### Events: `tarmac push`

```
tarmac push <html-path> '<json>'      one value, then exit
<producer> | tarmac push <html-path> -   one value per line of stdin, one connection
```

Two new wire messages:

```
{t:"push",      path, data:<str>}     cli → daemon, answered with ack | err
{t:"doc_event", path, data:<str>}     daemon → app
```

- `data` is the JSON text, a msgpack `str`. The cli sends each argument or
  line as it is; it does not parse. One value is one frame, so it is under the
  16 MiB frame limit. That is the wire's limit, kept as the limit of an event
  (decision 20), and an event is meant to be small.
- **The daemon checks the JSON** (`serde_json`, already a dependency) and
  answers `err` for text that is not one JSON value. This is where "JSON only"
  is enforced for events, and how the caller learns of a refusal.
- The daemon answers `err` when the path is not an open doc of any board, and
  when no app is connected. Otherwise it pushes `doc_event` and answers `ack`.
- **`ack` means "queued for the app", not "drawn".** The daemon does not know
  which cards the app has loaded, and an app that goes away after the `ack`
  loses the event.
- In stream mode the cli waits for each answer before it sends the next
  line.
- The path is made absolute by the cli with no file-system call, as `open`
  does. The daemon looks it up as given; on a miss it resolves it once through
  the path gate and remembers the answer for that connection. A stream
  therefore costs one resolve, not one for each line.
- Exit codes follow `open`: 0, 1 for a refusal or no daemon, 2 for usage. In
  stream mode a refused line is named on stderr with its line number, the
  stream goes on, and the exit code is 1 if any line was refused.
- One call of the verb is a process start and a round trip: a median of 4–5 ms
  for `tarmac open` on a dev channel, about 3 ms of it the process start
  (Evidence, with its caveat). That serves a few values a second. The stream
  is for more.

In the app, a `doc_event` goes to each card of that path whose document has
said `ready` for its current load, on every board the app holds
(`handleFileEvent` already walks all boards). Events that arrive in one turn
of the main loop go to the shim in one call, in order; the shim dispatches one
`tarmac:event` for each. They go in as an argument, as state does:
`HTMLCardView.post` splices its message into a script, which is right only for
the app's own text. There is no buffer: an event for a card that is not ready
is dropped.

What "loaded" means. No code tracks "ready for the current load" today; the
load stamp on `ready` (state, step 1) gives it.

| Card | Gets the event |
| --- | --- |
| On the active board, in view | yes |
| Culled | yes — the document stays loaded; the shim pauses only its timers and frames. Measured: a culled card answered 480 posts of 480, at two a second, and one post after 1, 5 and 16 minutes with no call from the host, each within 11 ms. With the app not active: 10 posts of 10 answered before the return, each within 18.1 ms (Evidence). |
| On a board visited in this run of the app | yes — the app keeps the board and its cards when it is switched away from, and every card of a board out of the window is culled. Measured: 840 of 840 with the view out of the window, and one post after 1, 5 and 16 quiet minutes, each within 11 ms. With the app not active (hidden, miniaturised, or with its window wholly covered): 10 posts of 10 answered before the return, each within 11.6 ms. Not measured: the window partly in view behind another app, another Space, the display asleep, the screen locked. |
| On a board not visited in this run | no — its cards are built on the first visit |
| Reloading (HTML file changed) | no, until its `ready` |

A document that needs the whole picture after a reload takes it from the
state file and uses events for what is new. That pairing is the answer to "no
replay".

### Paths

Only the state path reads a file, so only it has a rule, and the rule has no
setting (decision 14):

- **In the HTML file's directory, or in a directory under it:** allowed, with
  no consent (decisions 15 and 16). A directory under it is refused until
  phase 3 (Phases).
- **Anywhere else:** refused. Nothing in Settings, in the HTML file or on the
  card changes that.

The rule is a pure function in `TarmacKit`. It is judged twice: on the name
made absolute (no disk), so that a plain `../` is refused at once; and on the
resolved paths of both files, taken off the main thread at each read, so
that a symlink that leaves the tree is "anywhere else". A resolve that fails
is a refusal. The resolve and the read have no time limit of their own
(phase 1's spec, choice 21): they are off the main thread and one at a time
for each card, so a volume that does not answer holds that card's data and
nothing else.

A card that is refused says so in its console, with the path. No registration
is made and no read.

**A data file in a subdirectory costs a watch.** The daemon's watch of a
directory is not recursive, so it watches the subdirectory and counts it with
that directory's docs. The stream restart of #253 applies to it. A data file
beside the HTML file costs none: that directory is watched already.

### Phases

Each lands alone, with its own issue, spec and PR.

0. *Dropped (decision 13).* It was "close the card's way out". It was built
   as #307 and reverted by #310 before any release. Its measurements stay in
   Evidence: both channels the probe hit can be closed with two ways
   together, each at a cost.
1. **State, beside the HTML file.** Shim, `ready`, the kit decisions (the
   path rule among them), `doc_data`, the daemon's side, delivery. A data
   file in a subdirectory is refused until phase 3.
2. **Events.** `push`, `doc_event`, the cli verb, routing, delivery. Takes
   two things from phase 1: the shim's dispatcher, and the load stamp on
   `ready` that tells a card ready for its current load.
3. **Subdirectories.** The watch of a directory under the HTML file's, and
   the rule opened to it. (The order of 2 and 3 is not fixed.)

Each phase also owes what it changes in `docs/protocol.md`,
`docs/architecture.md` and the agent's guide `tarmac-cli/src/GUIDE.md` (how
to write a card that takes data). Phase 2 also owes the sentence in
`CLAUDE.md` that says `open` and `--version` are the two verbs that talk to
the daemon.

## Alternatives

**Events from a file that only grows (JSON Lines).** The writer appends one
line for each event; the app remembers how far it has read. This was the
first recommendation. It uses one mechanism for both modes and the file is the
history, so a reloaded card can be given the past. Against it: an event waits
for the watcher (100 ms at least between looks), the writer must manage a file
that grows, and truncation and half-written lines need rules. The user chose
the verb: a pipe from the producer, no file, no wait for a look. The price is
replay.

**The document pulls, the host answers** (MCP Apps: `tools/call` through the
host). It fits a host with a server behind it. Tarmac has files behind it, so
a pull is "read this file for me": the same path rule, plus a message that
asks a question, which no host message does today, plus polling, because a
pull has no signal that tells it when.

**`connect-src tarmac-card:` and let the document poll.** The least code. It
changes the CSP that spec 2607.0004 pins, gives every card a read of every
local file the scheme serves, and polls.

**The app watches the data file itself.** No wire change, and phase 1 would
ship sooner. But observation is the daemon's job, and the app would learn
again what the daemon learned in #253, #258, #265 and #267: lost events on a
stream restart, writes that go on, volumes that do not answer.

**The daemon reads the file and sends the content.** One reader, one gate.
But each update of a file would cross the socket that terminal output uses,
whole, at every change. Events cross that socket too; the difference is that
an event is one small value that a producer chose to send.

**Load the new HTML in a second frame and swap** (double buffer). It removes
the flash of an HTML rewrite with no work from the author. It does not keep
JavaScript state and it reloads the whole document for each record. It is a
separate improvement and is not part of this design.

**A buffer of the last N events in the daemon; channel names in place of
paths.** Both were put to the user and refused: the first is state the daemon
would own with a bound to choose, the second a new concept beside the path
that every doc is already known by.

## Trade-offs we accept

- **No replay.** A card that reloads, an app that restarts, a board that was
  not visited: the events in between are gone. A producer cannot tell, because
  `ack` says only that the event was queued for the app.
- **Two paths to build, test and explain**, where a growing file would have
  been one.
- **No limit on a state file but the reader's 64 MiB** (decision 20). The
  other guard is "one read at a time, latest wins". A very large file that changes often costs a read, a JSON
  check and a hand-over to the page for each look that finds it changed.
  Measured: the hand-over of 10 MB as a string held the main thread under
  3 ms, and the document had it about 0.1 s later (on a path that parsed in
  the host page; the path proposed here is to be measured again). The read
  and the check are off the main thread by design and were not measured, and
  nothing was measured above 10 MB or for memory. So the hand-over asks for
  no limit; the reader has one (64 MiB), and the cost that stays is in the
  card's own page, which parses the whole file at each change.
- **Events share the app's connection with terminal output.** A producer that
  floods can delay a terminal's bytes. Nothing in this design limits the rate.
  The app's connection holds 256 messages and the daemon waits when it is
  full (`conn.rs`), so a flood slows terminal output and loses none of it. How
  much is not measured: there is no event path to measure yet. Phase 2's spec
  owes the number.
- **No order between state and events.** State waits for a look and a read;
  an event comes at once. A document can get an event before the state that
  already holds it, or a state older than events it has applied. A culled
  card gets events now and state later, and after a reload events can come
  before the first `tarmac:data`. A producer that uses both must make its
  events safe to apply twice, or number them. That is the producer's work,
  and the guide must say so. Decision 21 chose this over a defined order.
- **An event runs a culled card's code.** Spec 2609.0002 paused culled cards
  so that they use no CPU. A handler for `tarmac:event` runs all the same.
  What the handler does at once, and in a microtask or a promise, runs at
  once. A `setTimeout` that it starts waits until the card is no longer
  culled (the shim holds it); a `requestAnimationFrame` waits until the card
  is on screen (WebKit holds it). Measured once for each (Evidence). The
  guide must say so: a handler that draws in a frame callback draws nothing
  until the card is back in view.
- **A card can read every JSON file in its own tree, with no question
  asked**, and may send it away (decisions 13 and 15). An HTML file in
  `~/Downloads` or at the root of a cloned repo reads what is beside it and
  under it. The user's act of consent is `tarmac open` on that file.
- **State is never faster than the watcher**: a change is seen at the next
  look, 100 ms or more after the one before.
- **A refused card is easy to miss**: the console line is all the user gets.

## The assumption this design gave up

**A card that has read a file has no way to send it anywhere.** The first
draft's path settings rested on this: a card that reads `~/x.json` shows it
on the board and can do no more with it.

**It is false, and it stays false (decision 13).** The live probe of 2026-11-10 (Evidence) found:

- **WebRTC.** In 4 card runs of 4, STUN and TURN packets from the card's
  script reached listeners on 127.0.0.1. When the TURN listener answered 401,
  the retry carried a 23-byte username that the page chose, in plain bytes
  (one run of the first probe; every one of the 12 control runs of the
  second). The card's CSP did not stop it: the same probe under that exact
  CSP outside the card sent the same packets. The second probe added
  `webrtc 'block'`, then `connect-src 'none'`, to the card's policy: neither
  stopped a packet. (The text reached the policy; that WebKit enforces
  `webrtc` is not shown.)
- **`<link rel=preconnect>`** opened a TCP connection (no bytes within 3 s).

What the probe does not show: a destination that is not loopback, a host name
(a DNS query, a TLS name), how much one run can carry, and which process sent
the packets. The fetch, image, script, style, font, media, frame, worker and
form channels gave no hit in the card and did hit with no CSP (that control was
a top-level page, not a sandboxed frame). The third probe gave `window.open`
and a blob download a control that hits: the card sent nothing. A link or a
form to `_blank`, dns-prefetch and prefetch gave no hit, but their controls
were silent too, so they are not shown to be closed.

The second and third probes show that both channels can be closed (Evidence,
the rows from "Closing WebRTC"), with two ways together and each at a cost. They also gave 18 ways out a
control that speaks: the card sent nothing on any of them. Still not
run: a DNS query, a destination off the machine, and anything that needs a
real click in the card (a form or a link that opens a new window).

The first draft of this design made the consequence a phase 0 that closes
the way out before any phase ships. The owner's decision of 2026-11-11 goes
the other way: a card's script is trusted no more than a page's in a browser,
and Tarmac does not try to be the wall. What follows for this design:

- A card reads no file outside its own directory tree, and no setting lets
  it (decision 14). The settings of the first draft would have meant "this
  card can read any JSON file I can read **and may send it away**".
- Inside that tree the read needs no consent (decision 15): an HTML file in
  `~/Downloads` reads any JSON beside it or under it, and may send it. This
  is accepted (Trade-offs).
- Phase 2 gives a card whatever a producer pushes, and the card may send it
  on.

This is true of the sandbox as shipped, without this feature: a card can
signal out today. What this feature adds is something worth sending.

The probe also showed that a card's script can send its own frame to
`tarmac-card://doc/<any path>`, and the app opens that path. The document that
asked is gone by then, so it reads nothing back. No phase of this design
changes that.

Two things would widen it later and must look at this design when they are
built: #69 (card console output piped to agents) and any connection from a
card to a service outside.

## The assumptions this design rests on

With the old assumption given up, these two carry the most weight. Neither
is fully measured.

- **Phase 1: every write of a data file is seen.** The daemon knows a change
  by the file's mtime, length and inode, at a look that follows a wake of the
  directory's watch. This is read from the code and is how docs are reported
  today; it is not measured for a data file that is rewritten many times a
  second. If a write is missed, the card keeps old state and nothing says so.
  Phase 1's live checks count the changes that arrive.
- **Phase 2: a hidden web view runs its message handler.** Measured for a
  culled card, a card of a board out of the window, and an app that is not
  active (Evidence). Not measured: the screen locked, the display asleep, the
  lid closed, another Space, battery power, a frame from the daemon as the
  trigger, and a bundled build. "No buffer" (decision 4) rests on it. Phase
  2's spec owes these runs before it is accepted.

## How we will know it worked

- **No reload.** 100 changes of a state file: the card's load count does not
  move, a counter in the document's own JavaScript reaches 100 less the
  changes that fell in one look, and the last `tarmac:data` holds the last
  content written.
- **No flash.** The 60 fps capture used for #271 shows 0 frames of backdrop
  over 20 updates. Today: every update.
- **No loss, in order.** 1,000 values through `tarmac push <card> -` reach a
  loaded card as 1,000 `tarmac:event`s in the order sent.
- **Terminals stay live.** Phase 2's spec sets the number and the method: the
  delay of a terminal's echo while a card takes 100 events a second through
  one stream, against the same delay with no events. Not measured here.
- **A refusal is whole.** A data file outside the HTML file's directory
  tree: no `doc_data` is sent, no read is made, the console names the path.
  With a symlink in the tree that points out of it: the same.
- **A subdirectory waits for phase 3.** In phase 1 a data file in a directory
  under the HTML file's is refused like any other place, with its own console
  line. In phase 3 the same file is delivered, and a change of it reaches
  the card.
- **The wire holds.** The new vectors pass in both codecs and the Swift
  encoder matches Rust's bytes.

## Evidence

Measured on 2026-11-10 on a debug build of `ccf67c2`, on a fresh dev channel,
with loopback listeners only. An independent check recomputed every figure
from the raw records. The records are kept outside the repo history
(`.dev/push-investigation-2611/`; read `VERIFICATION.md` first, it corrects
`INDEX.txt`). The probe pages and listeners are there too and are not tracked;
with phase 0 dropped, no phase owes a tracked copy.

## Out of scope

- Any chrome for data: no fresh mark, no unread dot, no count on the card.
- More than one data file for a card, and formats other than JSON.
- Replay, buffers, and channel names.
- A way from the card back to the producer.
- Markdown cards. `tarmac push` to a path that is not an HTML card is handed
  to the app and dropped there.
- The double-buffer swap for HTML rewrites.
- OpenUI as a card kind, and a connection to MCP servers. Both were raised on
  2026-11-10 and set aside; the second would reverse the rule in `CLAUDE.md`
  that Tarmac is not MCP.

## Decisions

Made by the user: 1–12 on 2026-11-10, 13–22 on 2026-11-11. They are not open
in this review.

| 1 | Push over the existing host → card path; the document stays loaded. Not pull, not a wider CSP. |
| 2 | Two modes: whole file / latest wins, and one event at a time. |
| 3 | Events come from a new cli verb through the socket, not from a file that grows. |
| 4 | The daemon keeps no events. An event goes to the cards loaded at that moment. |
| 5 | The target of a push is the HTML file's path, as with `tarmac open`. |

| 9 | ~~A per-file grant is for the card and any directory, and is given in the UI, never in the HTML.~~ Void by 14. |

| 14 | An HTML card reads no file outside its own directory tree. No setting, no grant. |
| 15 | A read inside that tree needs no consent. |
| 16 | A directory under the HTML file's directory is inside the tree. |
| 17 | The document's interface: `tarmac:data` and `tarmac:event` from the shim, and the last state at `window.tarmac.data`. |

## For the specs

Questions the review of this doc found, by phase. None changes the design.

**Phase 1.** A `ready` of an old load. `StrictJSON` is internal to the kit and
refuses more than 127 levels, which a browser's `JSON.parse` takes. A data
file that is also an open doc; two cards that name one data file. A data
`file_event` that arrives while the card reloads. A `doc_data` sent again with
the same name must not watch again. After a switch back, `restore` carries no
data stamp: the data `file_event` must follow it. A page's own global named
`tarmac`. A document that sends its own frame to another card URL gets no new
load number (`documentStarted` in `card-host.js`), so its `ready` is a second
one: the first-`ready` rule must say what it gets. What the daemon answers to
a `doc_data` for a board in the background, where no `file_event` is sent.

**Phase 2.** Line framing on stdin: a value over several lines, empty lines,
CRLF, input that ends inside a line. A batch of events as one array argument
was not measured, and the dictionary cost may apply to it.

**Phase 3.** A symlink that is pointed elsewhere after the check: resolve
again at each read, or check the path of the open descriptor (this
question is phase 1's too, for a symlink beside the HTML file). How many
subdirectory watches one card and one board may cost, given #253.
