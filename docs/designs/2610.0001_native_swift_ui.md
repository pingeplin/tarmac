> for what the build was measured against, see the

**Date:** 2026-10-02
**Status:** implemented
**Author:** EP Lin
**Doc type:** Mini RFC

## Decision

Rebuild the cockpit glass as a native Swift/AppKit application. The Rust daemon,
the CLI and the wire protocol do not change. Terminal cards are built on
[libghostty-vt](https://github.com/ghostty-org/ghostty) for terminal emulation
only; drawing and input handling are Tarmac's own code.

## Why

Three months on Tauri + xterm.js settled the product and exposed where a web
view fights it:

- **Crispness under zoom.** The board is one transform over every card. In a
  web view that is a bitmap scale, so each card type grew its own workaround
  (terminal canvas oversampling, frozen-K downscale for prose, device-pixel
  snapping for 1× displays). A native view rasterises text at the scale it is
  shown.
- **Key routing.** Every ⌘ chord, IME commit and dead key crosses three owners
  — AppKit's menu, WebKit, xterm.js — and each fix was a rule about who stands
  aside. Natively there is one responder chain.
- **Terminal fidelity.** xterm.js is a browser terminal. libghostty-vt is the
  emulator core of a native macOS terminal, with the kitty keyboard protocol,
  synchronized output, grapheme handling and selection semantics already in it.

## What stays and what moves

| Piece | Before | After |
| --- | --- | --- |
| `tarmacd`, `tarmac` CLI, `tarmac-protocol` | Rust | unchanged |
| Wire client | Rust (`bridge.rs`, path-deps the protocol crate) | Swift codec in TarmacKit, gated by the same conformance vectors |
| Pure decisions (`kit/*.ts`, Vitest) | TypeScript | Swift in TarmacKit, XCTest, ported test-for-test |
| Board, cards, overlays | React + CSS | AppKit views |
| Terminal card | xterm.js (WebGL) in the app's web view | `TerminalView`: libghostty-vt + CoreText |
| Markdown / HTML doc cards | DOM / sandboxed iframe | WKWebView, same `tarmac-card://` scheme and CSP |

The Swift package lives in `app/` with three layers:

- **TarmacKit** — Foundation only. The msgpack codec and daemon client, and
  every decision that can be a pure function. This is where the tests are.
- **TarmacTerm** — the terminal card, usable without the rest of the app.
- **TarmacApp** — the AppKit shell: wiring, views, event routing.

## The terminal card

libghostty-vt is a C library that parses the PTY byte stream and owns the
screen, scrollback and modes. It draws nothing and reads no events. Tarmac
links it as a prebuilt XCFramework pinned to one Ghostty commit with a recorded
SHA-256 (`scripts/fetch-ghostty-vt.sh`); the C API is declared unstable, so the
pin moves deliberately.

`TarmacTerm` is four pieces with one job each:

- **`TerminalEngine`** wraps the emulator: feed bytes, resize, read modes, and
  encode host events (keys, mouse, paste, focus) from the terminal's live
  state. It also answers what libghostty-vt leaves to the embedder — device
  attribute and cursor-position reports, title, working directory, bell — since
  shells block on some of those replies.
- **`FrameReader`** copies the render state into a value `TerminalFrame`,
  re-reading only the rows the library marks dirty.
- **`TerminalRenderer`** draws a frame with CoreText. Layout is in points and
  every fill is snapped to the context's device pixels, so the grid is seamless
  at any zoom and glyphs are rasterised at the real scale.
- **`TerminalView`** is the `NSView`: it runs the input context for IME and
  dead keys, encodes keys through the engine, routes the mouse to the program
  or to selection, and holds the shown frame during synchronized output.

The view lays out in its own bounds. The board scales a card by giving it a
frame larger than its bounds and raising the layer's `contentsScale`, so zoom
never changes cols×rows — only a real resize reaches the PTY.

Policy stays out of the view. Which card a wheel event reaches, whether a
program may write the clipboard, and app-level key bindings are the host's
decisions, passed in as closures.

## Alternatives considered

- **Stay on Tauri and keep fixing.** Each fix worked; the count of them is the
  argument. The workarounds are structural to hosting a terminal and a zoomable
  canvas inside one web view.
- **The full libghostty surface (GhosttyKit).** It brings Ghostty's Metal
  renderer and its input handling, which is the part Tarmac wants to own: the
  board needs to scale, clip and composite terminal cards like any other view,
  and to decide key routing itself.
- **SwiftTerm**, as the pre-Tauri app used. Its `keyDown` is sealed and its IME
  support needed an unreleased commit; it does not build on the current Xcode.

## Costs and risks

- **A second codec.** The Swift msgpack codec is a second implementation of the
  wire contract. The conformance vectors are mandatory tests on both sides, and
  the Swift encoder is checked byte-for-byte against `rmp_serde::to_vec_named`.
- **An unstable upstream API.** A libghostty-vt bump can break the build. The
  pin, the hash, and a test suite that exercises every call the engine makes
  are the mitigation.
- **Text rendering is ours now.** Font fallback, wide characters, ligature
  policy and underline styles are code Tarmac maintains. CoreText does the
  shaping; the renderer tests sample real bitmaps.
- **The app layer has no unit tests**, as before. The QA driver (`tarmac dev`)
  was reimplemented on the native app, and `make qa` was the parity gate.

## How it lands

The native app was built beside `desktop/` and replaced it in one final change
that moved the Makefile, bundling, release and docs over and deleted the Tauri
app. Parity was measured against the Tauri behaviour of the time, not against
the pre-Tauri Swift app the shell started from.
