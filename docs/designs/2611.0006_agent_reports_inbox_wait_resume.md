- **R6 (revised by Q3).** `wait` keeps the CLI's 0/1/2 and adds 124 for a timeout. `--exit` prints the terminal's code on stdout and exits 0.

## Decision

Tarmac gets four things. Each is a new doorbell or a new use of a fact that
the daemon already observes. Details are in *Approach*.

1. **`tarmac report`** (§1). A process in a terminal says "blocked" or "done",
   with a short text. The UI quotes it and places it in time, never as
   Tarmac's own state.
2. **The inbox** (§2). It is a transient panel, plus report and exit kinds on
   the existing offscreen pills.
3. **`tarmac terms`, `events` and `wait`** (§3). They give out the facts that
   the daemon already has. `wait --changed` watches any path in the CLI
   itself.
4. **Resume after a restart** (§4). A cold spawn opens the shell in its last
   folder, and the card offers a recorded resume command that runs only on
   Enter.

Agent integration comes from **`tarmac hooks install`** (§5). It writes one
fixed entry, `tarmac hooks run <agent>`, into the agent's hook config. The
mapping lives in the binary, so `brew upgrade` updates it. This is the shim
pattern of `tarmac skill install`.

**The trade-off in one sentence:** we accept agent-specific adapters in the
CLI (only there) and a second, cruder file watcher in the CLI, so that the
daemon and the app stay agent-agnostic and the doc watcher is never put at
risk by a user's `wait`.

## Problem

Three gaps, each seen in daily use. The first cannot be closed today without
breaking principle 1 (*No-harness honesty*). The other two need facts that the
daemon has but does not give out (exits, bells, changes) or does not keep (the
cwd of a terminal).

**"The agent is waiting for me" has no signal of its own.** Today the only
hint is a bell (`Bell {term_id}`). A bell has no text. It cannot tell
"needs permission" from "finished", and it does not say *which* question.
With four or more agent terminals on two boards, the user has to look at
every card to find the one that waits.

**Scripts cannot wait on Tarmac's facts.** The daemon observes exits, bells
and file changes, but sends them to the app only. A Makefile, a git hook or a
second agent cannot say "continue when the test terminal exits" or "continue
when `plan.md` changes". They poll, or they ask the user.

**A daemon restart throws away the working context.** A version-mismatch
restart (every `brew upgrade`) kills every terminal (*What survives what*,
architecture §6). A cold spawn restores the card's frame but not its
directory: a tile persists `x, y, w, h, z, term_id` only (*Layout
persistence*). The shell opens in the default directory, and the agent
session that ran there is gone from view, though its id is still on disk
(`claude --resume <id>`, `codex resume <id>`).

## Constraints

- **Principle 1.** Every mark maps to one observable fact. A `report` call
  *is* a fact (a process in terminal T called the socket at time t), but
  the content is a claim. The UI must quote it and attribute it, never adopt
  it.
- **Principle 2.** Nothing an agent does may move the view or take
  keystrokes. The inbox only *marks*. A jump happens only when the user
  clicks or presses Enter.
- **Principle 6.** Facts that must survive an app relaunch live in the
  daemon: the current report of each terminal, its read flag, and the cwd and
  resume record of each tile.
- **Additive protocol only**, in two codecs, gated by the conformance vectors.
- **Not MCP, not a harness.** Agents reach Tarmac only through the CLI over
  the existing socket.
- **The doc watcher is shared and has limits.** There is one FSEvents stream
  for each daemon, run by one watcher thread. Each `watch`/`unwatch` that
  changes the path set restarts the stream. notify 9 starts the new stream at
  the last event that the old one delivered, so the event loss of #253 is
  closed, but a change made in the gap is seen only at the next look
  (architecture §3, *Docs & file watching*). A watch fails over the FSEvents
  path budget (a twelfth of `RLIMIT_NOFILE`), and the daemon then unwatches
  that directory at once. Each watch is on a doc's parent directory and is
  non-recursive (`core/crates/tarmacd/src/watch.rs`). The OS stream under it
  still covers the subtree, and notify filters it in its callback. On
  2026-11-12, a file name that is not UTF-8, in a *subdirectory* of a watched
  directory, made notify 8.2's callback panic and abort the installed daemon.
  So a wide watch, such as `~`, widens the crash surface even when it wakes
  nothing.
- **Backlog §3 says "no rail is built, by design".** The inbox is a
  *transient* panel, not a docked rail. The owner accepted this on
  2026-11-14.
- **Term ids are not stable.** A cold spawn mints a new id
  (*Restore and reconnect*). Anything that must survive a restart is keyed by
  the tile slot, not by the id. Today there is no such key (next item). §4
  says how a record follows a terminal to its new id (decision R1).
- **The app owns the tile list.** Each `Layout` replaces a board's tiles
  wholesale (`Registry::apply_layout` → `set_tiles` in
  `core/crates/tarmacd/src/boards.rs`). The app builds the tiles from its own
  cards (`LayoutTiles.build` in `app/Sources/TarmacKit/LayoutTiles.swift`),
  and it leaves dead cards out. A tile has no slot id: a terminal tile is
  known by its `term_id` only.

### Hook facts this design rests on

The facts come from the vendor docs, read 2026-11-14 (code.claude.com
`/hooks`, `/cli-reference`; the Codex config and hooks pages).

- **Claude Code hooks.**
  - `Notification` has the matcher values `permission_prompt` and
    `idle_prompt`, and it carries `message`.
  - `Stop` carries `last_assistant_message`.
  - Every hook carries `session_id` and `cwd`.
  - A hook runs with no controlling terminal, but it inherits claude's

  - Claude treats a hook's **exit 2 as blocking**.
- **Claude Code resume.**
  - `claude --resume <id>` searches the current project first, then every

  - `--continue` searches the current directory only.
- **Codex.**
  - Codex has hooks (`SessionStart`, `Stop`, … with `session_id`) and also
    `notify` (`agent-turn-complete`, which carries `thread-id`).
  - `codex resume <id>` resumes a session by id.
  - Codex hooks are configured in `hooks.json` or in inline `[hooks]` tables
    in `config.toml`. **[ASSUMPTION: an adapter writes `hooks.json`; to be
    verified before the Codex slice.]**

## Approach

### 1 · `tarmac report`

```
tarmac report blocked "<text>"     # the caller is waiting for the user
tarmac report done "<text>"        # the caller finished a unit of work
tarmac report clear                # drop this terminal's report
```

The resume command is a separate verb, `tarmac resume` (§4 B). It is a
declared command with its own lifetime, not a status claim, so it never
enters the report model, the inbox, `wait --report` or `events`.

- **A terminal is required.** With no `TARMAC_TERM_ID`, the command exits 1. A
  report always belongs to one terminal.
- **The text is capped** at 280 characters. The CLI cuts it at a character
  boundary and adds `…`. [ASSUMPTION: 280 is enough for a permission message
  and the first lines of a `Stop` summary.]
- **The daemon observes the caller (Q2).** `TARMAC_TERM_ID` still names the
  terminal. The daemon finds the *agent process* this way:
  - Right after `accept()`, before any `await`, it reads the CLI's peer pid
    with tokio `peer_cred()`. On macOS this is `LOCAL_PEEREPID`.
  - It walks the ppid chain with sysctl `KERN_PROC_PID` (`proc_pidinfo`
    fails on a zombie and on pid 1). It stops at the PTY's child pid, the
    shell. The agent pid is the chain's member just below the shell. If
    the PTY's child *is* the agent (`SpawnTerm.cmd`), the agent pid is the
    child itself.
  - **Fallback.** If the walk does not reach the PTY's child, the caller is
    *unattributed*. This happens when the peer read fails, when a
    double-forked helper is re-parented to launchd, or when a parent exits
    mid-walk. The daemon then makes a fresh read of the foreground
    process-group leader instead, the read that the 750 ms `TermProc` poll
    makes.
  - It stores `{kind, text, at_ms, pid, proc_name}` as the terminal's current
    report. `pid` is the agent pid, or the leader in the fallback.
    `proc_name` is that process's name.
- **No needless traffic.** `clear` with no current report does nothing and
  sends nothing to the app. A report with the same kind and text as the
  current one refreshes `at_ms` only. Claude runs `UserPromptSubmit` on every
  prompt, so most `clear`s land here.

**Lifetime.** Each rule below is driven by an observed fact.

| Event | Effect on `blocked` / `done` |
| --- | --- |
| A new report from the same terminal | Replaces the current report |
| `report clear` | Removes it |
| The recorded pid has exited; in the fallback case, it is no longer the foreground leader (a pid check in the existing 750 ms poll; a name compare would miss two `claude`s in a row) | Removes it |
| The terminal exits | Removes it |
| The user types or pastes into the terminal | Sets `read: true`. The report stays and dims. |

**How the daemon knows user input (decision R2).** An `Input` frame is not
always the user. The terminal view sends two other kinds of bytes through the
same `onInput`, and so as `Input` (`AppController+Terminals.swift:35`):
- the engine's own replies to the program (`onWritePty`,
  `app/Sources/TarmacTerm/TerminalView.swift:197`);
- focus reports (`TerminalView.swift:389`, through `send` at `:450`).

So `Input` gets a new optional key, `typed: true`. The app sets it only on the
key and paste paths. Only an `Input` with `typed: true` marks a report read.
A missing key decodes as false, so an older app never marks a report read.
`Input` is the keystroke hot path, so the check costs one flag on the
terminal handle (an unread report exists). Only the first typed key after a
report takes the slow path.

Today's bell dot clears on *any* bytes that leave for the PTY, the engine's
replies included (architecture §4, *Terminal cards*). **Q4 (accepted):** the
bell dot also clears on `typed` input only, so the bell, the report and the
resume chip (R4) share one meaning of "the user touched this terminal". This
changes a shipped rule, so it ships as its own issue, [#343](https://github.com/pingeplin/tarmac/issues/343), before slice 2. "Typed" means user-originated: a key, a paste or a mouse report.

**Display.**
- **The copy only places the report in time (decision R3).** The daemon
  records the *foreground* process, not the process that called. So the copy
  says when the report came, never who sent it, as principle 1 requires
  ("during claude").
  - The title is `report · during claude`, the same form as the bell's.
  - The card-header chip is short: `report · 2m`. The colour shows the kind:
    amber for blocked, green for done. A read report is dimmed.
- The quote is shown in the inbox and on hover, and is always set in quote
  marks.
- `claude` is the `proc_name` that the daemon observed, not a name that the
  caller supplied.
- The age always shows, so an old claim looks old.

### 2 · The inbox

The inbox follows mockup "A + offscreen pills".

- **Panel.**
  - A title-bar button carries the unread count. A key opens and closes the
    panel: `⌘I`. It is a new rung of the key ladder (`KeyLadder`), as `⌘K`
    is. No clash today: `MainMenu.swift` has no `⌘I`, and `KeyLadder.swift`
    takes only `⌘K`, `⌘W` and `⌘T`. [ASSUMPTION: a terminal program does not
    need `⌘I`.]
  - The panel overlays the right side of the board and lists items from
    **all boards**.
  - Each item shows the kind tag, a title, the quote, a line in the form
    `board › terminal · cwd`, and its age. Titles: `report · during claude`,
    `bell · during claude`, and for an exit the existing toast wording
    (`TermExitToast`: `shell exited · N`, `killed by signal`).
  - There are filter chips (all / reports / bell / exit), a
    **"clear all read"** button, and the keys ↑↓ ↵ ⌫.
- **Jump.** ↵ or a click switches the board if needed. Then it flies the
  viewport to the card (`ViewportFlight`) and makes it prime. It is always a
  user action.
- **Offscreen pills.** These exist today: one pill for each signalling
  terminal whose centre is off screen, and plain Return flies to such a card
  (key ladder rung 5). Today only terminals signal, `bell` or `live`, so a
  dead card has no pill. This design adds the report and exit kinds.
  - A pill points only to an off-screen card on the **current** board, and a
    click pans to that card.
  - A report pill carries the start of the quote. A bell or exit pill
    carries the kind only.
  - A report on another board makes no pill. It is counted in the inbox
    badge, and in the board switcher's per-board count, which today counts
    bells (`AppController+Boards.swift`).
  - Pill rank (`OffscreenHintLayout.priority`, today `bell` 1000 and `live`
    0): blocked report > bell > exit > done report > live.
    [ASSUMPTION: a blocked agent outranks a bell.]
  - While the panel is open, the right-edge pills move to the panel's left
    edge.
- **Who owns what.**
  - The daemon owns reports and their read flags (principle 6). The app
    receives each change as `TermReport`.
  - Bell and exit items are the app's own list, built from the `Bell`
    and `Exit` messages it already gets. An app relaunch loses them.
    [ASSUMPTION: acceptable. A bell or an exit is a moment.] Note: a dead card
    does not survive an app relaunch either, because the layout leaves dead
    cards out (architecture §4, *Layout persistence*). So after a relaunch an
    exit leaves no trace at all.

### 3 · `tarmac events` and `tarmac wait`

```
tarmac terms                                  # id, board, cwd, foreground process
tarmac events [--term ID] [--kind exit,bell,changed,report]   # JSON lines until killed
tarmac wait --exit ID [--timeout MS]          # exit status = the terminal's exit code
tarmac wait --bell ID [--timeout MS]
tarmac wait --report blocked|done --term ID [--timeout MS]
tarmac wait --changed PATH [--settle MS] [--timeout MS]
```

`--timeout` takes milliseconds, as `tarmac dev snapshot --timeout` already
does.

- **`terms`.** Ids are not stable, and a caller outside a terminal cannot see
  them, so `terms` is how a caller names a terminal. It is built from what
  the daemon has: `term_boards` (board), `TermProc` (process) and
  `pid_cwd` (cwd). It has no title, because titles are the app's
  (`TermLabel`).
- **`events` and the daemon-side `wait`.** One new connection mode,
  `Subscribe {kinds?, term_id?}`, turns the connection into a one-way stream.
  - **No new event schema.** The stream carries the frames that the app
    already gets (`Exit`, `Bell`, `FileEvent`) and the new `TermReport`,
    filtered by type and `term_id`. They are tapped at the one place they
    all pass, `Daemon::push`. The CLI stamps each line with the time it
    received it.
  - **A short snapshot first.** The daemon first sends the current state for
    the filter only: one exit lookup for `--exit`, the current report of the
    named terminals for `--report`, and nothing for `bell` and `changed`.
    Then it sends live frames. So a `wait --exit` for a terminal that has
    already exited returns at once.
  - **Recent exits.** The daemon keeps a ring of the last 64 exits
    (`term_id`, code). It is bounded by count, with no timer.
  - **No cost with no subscriber.** The tap builds nothing when no receiver
    exists.
  - The `changed` events cover open docs and their data files only: the
    paths that are already watched. They come from the daemon's looks, so
    they have the looks' limits: a look reads the **active** board only, and
    there is no timer. A change of a doc on a background board gives no event
    until that board is shown. Data-file registrations are dropped when the
    app goes, so with no app there are no data-file events.
  - **Fan-out (decision R5).** Today the daemon pushes to one app slot,
    through one bounded channel (architecture §3, *Process & connection
    model*).
    - Subscribers use a separate path: one tokio `broadcast` channel with a
      bound, and one receiver for each `Subscribe` connection.
    - A subscriber that falls behind gets one last `Err {msg: "lagged"}`, the
      existing error frame, and then its connection is closed.
    - The daemon never waits for a subscriber, and the app's channel is not
      touched.
- **`wait --changed` runs in the CLI.** It never talks to the daemon.
  - It stats `PATH` and compares `(dev, ino, mtime, size)` with the first
    sample. A change in `ino` catches an atomic replace. It stats every
    100 ms for the first 2 s, then every 250 ms, so a wait that lasts hours
    does not wake the CPU ten times a second.
  - A missing file is a state: its creation is a change, and its deletion is
    a change with its own exit code.
  - Only changes after the start count. By default the first change ends the
    wait. `--settle` waits until that many ms pass with no further change.
- **Exit codes (decision R6, revised by Q3).** `wait` keeps the CLI's
  convention: every other verb uses 0 = ok, 1 = failure, 2 = usage
  (`main.rs`, `skill.rs`, `push.rs`). `--exit` does not pass the terminal's
  code through. It prints it on stdout, so no terminal code can collide with
  Tarmac's own.

  | Code | Meaning |
  | --- | --- |
  | 0 | the event happened. `--exit` prints `{"code": N}`, or `{"signal": true}` for a signal death (`Exit` sends a nil code). `--changed` prints `{"deleted": true}` when the file went away. |
  | 1 | Tarmac failure: no daemon, or an unknown terminal |
  | 2 | usage error |
  | 124 | timeout (the same code as GNU `timeout`) |

- **Excluded on purpose:** any match on terminal output (herdr's
  `output_matched`). That would be parsing the agent's output.

### 4 · Resume after a restart

**Slice A — the folder.** This slice needs no agent cooperation.

- **Recording.**
  - The daemon records `last_cwd` for each live terminal. It comes from
    `PathFs::pid_cwd` of the foreground leader, through the gate.
  - **It reads the cwd only when the foreground pid changes**, not on every
    750 ms tick. `pid_cwd` is a gated `proc_pidinfo` on a blocking thread,
    heavier than the poll's `proc_pidpath`. A `cd` at an idle prompt does not
    change the pid, but the next command does. So the record lags by at most
    one command.
  - **One more read at shutdown.** The SIGTERM/SIGHUP/SIGINT handler
    (`tarmacd/src/main.rs`) reads every live terminal's cwd and saves once
    before it exits. A version-mismatch restart sends exactly that SIGTERM,
    while the ptys are still alive. Only a crash or a SIGKILL loses the last
    idle `cd`.
  - **A cwd change does not mark the state dirty.** The record is saved with
    the next save that something else causes, and at shutdown. So a busy
    shell does not rewrite and fsync `state.json` once per command.
  - The foreground process name is not recorded. Nothing in the restore uses
    it.
  - **Where the record lives (decision R1).** The app's `Layout` replaces
    the tiles wholesale (*Constraints*), so the record is **not** a tile
    field in the daemon. Each board instead keeps its own table, with one
    entry for each terminal:

    ```
    term_records: { term_id → { last_cwd?, resume? } }
    ```

    `last_cwd` is observed by the daemon. `resume` is declared by the agent
    (§4 B). They share the entry, so they share the move and delete rules
    below, but each has its own clear rule.

    - **Saving.** The table is saved in `state.json` beside `tiles`. A
      `Layout` never touches it.
    - **Restore.** `Restore` carries the board's table as one new optional
      map, `term_records`. The app reads it beside the tiles. No `Tile` key
      is added, so `Layout` has nothing to ignore.
    - **Moving to a new id.** A cold spawn carries the record over:
      `SpawnTerm` gets a new optional key, `succeeds: <old term_id>`. The
      daemon moves the entry to the new id when the spawn succeeds.
    - **Deleting.** The daemon deletes an entry when the user closes the
      card (`TermClose`) or the terminal exits cleanly. An entry that no
      tile names stays until a `succeeds` moves it or a `TermClose` deletes
      it. This is how a dead card keeps its "reopen here" record across an
      app relaunch, though the card itself is not in the layout.
    - **Size.** This slice is "small to medium", not "smallest": it adds one
      table, one `Restore` key and one `SpawnTerm` key, in both codecs.
      `succeeds` stays in this slice, though the new shell's first pid
      change re-records its cwd: without it, the old id's entry is left
      with no owner and is never deleted.
- **Restore.**
  - A first-visit cold spawn sends
    `SpawnTerm { cwd: term_records[tile.term_id].last_cwd, succeeds: tile.term_id }`. The spawn
    already checks the cwd through the gate: a cwd that is not a directory,
    or a check that does not answer in time, starts the shell in `$HOME`
    with no error (architecture §3, *Terminal sessions*).
  - The new term id is persisted as today, and its record moves with it.

**Slice B — the session.**

```
tarmac resume set "<command>"     # how to resume the caller after a restart
tarmac resume clear
```

- **Recording.**
  - `tarmac resume set` stores `resume: {cmd, pid}` in the terminal's
    `term_records` entry. The pid is the foreground leader at that time.
    It needs `TARMAC_TERM_ID`, as `report` does.
  - **Clear rule:** if the daemon sees that pid exit while the daemon is
    alive, the user ended the agent, so the record is dropped.
  - If the daemon dies first, the record stays, and the next restore offers
    it. So "offered" means exactly "the agent was still running when Tarmac
    went down".
- **Restore.**
  - The cold-spawned card shows a chip:
    `↻ last here: claude --resume 3f2a…  ⏎ run · esc skip`.
    The chip shows the whole command on hover.
  - **Keys (decision R4).**
    - Only the **prime** card's chip takes keys.
    - The shell counts as up at the PTY's **first `Output`** after the
      spawn (its prompt). Before that, the chip takes no key.
    - The first key that the shell would get decides the result. ⏎ writes
      the command and a newline once. Any other key drops the chip and the
      record, and then goes to the shell as usual.
    - When the §1.2 restore card is up, it takes the first key. Only after
      it closes do the chips take keys.
- **A running app** that sees `daemon restarted — terminals lost` marks the
  cards dead, as today. A dead card that has a `last_cwd` offers *"reopen
  here"*. It also offers the resume command if one is recorded. Nothing
  respawns without a press.
- **The restore card in backlog §1.2** gets new content. Its v3 text names
  tmux, which is deferred (§2). The new lines are
  `✓ 5 terminals back in their folders` and
  `↻ 2 with an agent session to resume`.

### 5 · `tarmac hooks install`

```
tarmac hooks install [--target claude-code|codex|all] [--scope user|project] [--dry-run]
tarmac hooks status
tarmac hooks uninstall [--target …]
tarmac hooks run <agent>   # the entry the agent runs; reads the hook JSON on stdin
```

- **The flags are `skill install`'s.** `--target`, `--scope`, `--dry-run`, the
  `Target`/`Scope` enums, the `Env` that reads `$CLAUDE_CONFIG_DIR`, and the
  rule that one failed target does not stop the others all come from
  `tarmac-cli/src/skill.rs`. Only the config path differs: Claude's
  `settings.json` is under the same user root, and Codex's is not (see *Hook
  facts*).
- **`install` merges** the agent's config file and backs it up first. It
  writes only entries whose command is `tarmac hooks run <agent>`, with a
  bare `tarmac`, never an absolute path.
  - Its own entries are recognised by that command string, so a re-run
    changes nothing.
  - `uninstall` removes only those entries.
  - `status` reports, for each agent, whether the entries are there, whether
    they use the current entry form, and whether `tarmac` is on the hook's
    `PATH`.
- **The Claude mapping** lives in `tarmac hooks run claude` and is updated with
  the binary.

  | Hook | Report sent |
  | --- | --- |
  | `Notification` with `permission_prompt` | `blocked`, with the hook's `message` |
  | `Stop` | `done`, with the start of `last_assistant_message` |
  | `UserPromptSubmit` | `clear` |
  | `SessionStart` | `resume set "claude --resume <session_id>"` |

- **`tarmac hooks run` always exits 0, in 200 ms or less with no daemon.**
  - With no `TARMAC_TERM_ID` (the agent runs outside Tarmac), it does
    nothing and does not connect.
  - With no daemon, it gives up at the first failed connect and does not
    retry.
  - It never prints to stdout, because Claude reads a hook's stdout as
    control JSON.
- **Only the CLI knows any agent.** The daemon and the app receive plain
  `Report` messages.
  - Reading a payload that the agent gives on purpose, through a documented
    hook, is not parsing its output.

### Protocol additions (additive, both codecs, new vectors)

| Message | Dir | Purpose |
| --- | --- | --- |
| `Report {term_id, kind, text?}` | cli→D | `kind` ∈ `blocked`, `done`, `clear`; reply `Ack` / `Err` |
| `TermReport {term_id, kind?, text?, at_ms?, proc?, read?}` | D→app, and on a `Subscribe` stream | the current report of a terminal; no `kind` = none; a missing `read` = unread (unlike `DocEntry.read`, whose default is true) |
| `Resume {term_id, cmd?}` | cli→D | set (with `cmd`) or clear the terminal's resume record; reply `Ack` / `Err` |

| `Subscribe {kinds?, term_id?}` | cli→D | turn the connection into a stream of the existing `Exit`, `Bell`, `FileEvent` frames and `TermReport`; `Err {msg: "lagged"}` ends it |
| `Restore.term_records?` | D→app | the board's `{term_id → {last_cwd?, resume?}}` (R1) |
| `SpawnTerm.succeeds?` | app→D | move the old id's record to the new terminal (R1) |
| `Input.typed?` | app→D | the bytes came from a key or a paste; only these mark a report read (R2) |

## Alternatives considered

**Infer the state from the screen** (herdr's `output_matched`, or a
recogniser for Claude's permission box). This needs no hooks and would work
on day one with any agent version. It is rejected because it is the one
thing principle 1 forbids. It also breaks on every prompt-format change, and
then Tarmac would *claim* a state it guessed.

**Bell only: build the inbox on bells, and ship no `report` verb.** This is
cheap and needs no agent integration: Claude already has
`preferredNotifChannel: terminal_bell`. It is rejected as the *whole*
answer, because a bell has no text and no kind. The user still has to open
every card to learn why it rang. The inbox does include bells, so this
option is kept as the floor for agents with no hooks.

**An MCP server that agents call to report.** It is rejected by the project
rule (*not MCP*). It would also couple the signal to agents that speak MCP,
where a plain CLI call works for any caller, including shell scripts.

**`wait --changed` through the daemon's watcher.** This is one mechanism, and
the changes would show in `events` for free. It is rejected for the limits in
*Constraints* (the doc watcher): each short wait restarts the shared stream,
uses the shared path budget, and widens the crash surface of every doc card.

**A second watcher in the daemon, only for waits.** This is isolated from the
doc stream and could feed `events`. It is not rejected outright: it is the
upgrade path if someone needs to *stream* arbitrary paths. It loses now
because it adds lifetime management to the daemon for a need that a
100-line CLI loop meets.

**Install full hook commands** (`jq` pipelines in `settings.json`). This needs
no adapter code in the CLI. It is rejected because the installed text goes
stale with each release, it needs `jq`, and it puts logic where Tarmac
cannot update it.

**Ship hooks as a Claude Code plugin.** This uses Claude's own update path. It
is rejected because it means a release channel for each agent, Codex has no
equivalent, and whether a plugin can carry hooks is unverified.

**Daemon-restart PTY re-parenting** (backlog §2). True survival would make
the resume chip unneeded for daemon restarts. It stays deferred: it is the
largest change in the list, and it still does not cover a reboot. Slice A
and B help in both cases.

**Auto-run the resume command on restore.** This saves one keypress. It is
rejected because a restart would then run a command that the user did not
ask for. It may also be stale: the session may have been resumed elsewhere
since.

## Trade-offs accepted

- **Agent-specific code in the CLI.** `tarmac hooks run claude` knows Claude's
  hook names and fields, and a vendor change can break it. We accept this to
  keep the daemon and the app agent-agnostic and the user's config
  stale-proof. A break degrades to "no reports", never to a wrong mark,
  because the hook always exits 0.
- **The lifetime is exact only when the walk succeeds.** Normally a report
  lives until the agent pid that the daemon found exits, which is an
  observed fact. An unattributed caller falls back to "the foreground leader
  changed", which only stands in for "the claim is no longer current".
  Inside tmux or a wrapper script that leader is the wrapper, so the report
  can outlive its agent. The age on every chip is the guard.
- **Two notions of "changed".** The CLI's stat poll (100 ms, any path) and the
  daemon's `FileEvent` (open docs, FSEvents) can disagree on bursts. We
  accept this rather than tie `wait` to the doc watcher.
- **Bell and exit history is lost on an app relaunch.** Only reports persist.
- **A rail-like surface returns.** It is transient, but it still reverses
  part of backlog §3.

## Open questions (from the `/simplify` review, 2026-11-14)

Each one, if answered "yes", reopens or changes an R-decision. Each blocks only
the slice named. All four are answered (2026-11-14).

- **Q1 (R1, slice 1): answered no, R1 stays.** Could a cold spawn reuse the
  persisted term id? No source gives a reason for the "never reused" rule.
  It is a leftover of "each spawn mints a UUID" (1b7f018), written down later
  in 194bf60 (`BoardRestore.swift`). But reuse needs two guards:
  - A late `Exit` or `TermProc` of the old pty, pushed after the id leaves
    `live_terms`, would hit the new shell's card. This was read in
    `term.rs`, not reproduced.
  - A process that survived the restart still holds the old
    `TARMAC_TERM_ID`. Its `open`, `report` or `resume set` would land on the
    new shell.

  Reuse also merges "tile slot" with "shell instance", and reports must
  belong to the shell instance. So `term_records` + `succeeds` (R1) stays.
- **Q2 (riskiest assumption, slice 2): answered yes, adopted in §1.** A probe
  on Darwin 25.6 checked this (scratchpad `peerpid-probe/`).
  - `LOCAL_PEERPID` and `LOCAL_PEEREPID` work on Unix stream sockets, and a
    ppid walk through nested shells reaches the right ancestors.
  - tokio's `peer_cred()` gives the pid on macOS (`ucred.rs`, `impl_macos`,
    tokio 1.52.3).
  - Limits:
    - The pid is readable only while the client's end is open: ENOTCONN
      after it closes. The CLI waits for `Ack`, so a read straight after
      `accept()` is safe.
    - A double-forked caller is re-parented to pid 1.
  - R3's copy is kept: the text is still a claim, and the fallback still
    guesses.
- **Q3 and Q4** were accepted on 2026-11-14 and are written into R6 (§3)
  and R2 (§1).

## Riskiest assumption

**The hook runs as a descendant of the agent, so that the ppid walk finds
the agent.** The `blocked`/`done` lifetime and the slice B clear rule both
rest on this. Claude Code runs a hook "in its own session without a
controlling terminal". That changes the session, not the parent, but whether
Claude forks the hook directly or through a helper that detaches is not
verified.

- **If it is wrong**, the walk ends at pid 1, and every report falls back to
  the foreground leader: the weaker rule, which a wrapper such as tmux
  defeats.
- **The check:** before the `report` slice, run Claude and Codex in a dev
  terminal. From a hook, record the chain the daemon sees (a debug log of
  the walk), and check that it reaches the shell.
- **If it fails:** have `tarmac hooks run` send its own parent chain, read
  before it connects, as an optional key on `Report`.

## Success criteria

All of these are checked on a dev channel. The automated ones are integration
tests.

| What | Target | How |
| --- | --- | --- |
| Folder after a daemon restart | 100% of terminals whose last cwd still exists reopen there | `restore_integration` test: kill the daemon, restore, compare `pid_cwd` |
| Report → chip | ≤ 1 s from the CLI's exit to `TermReport` at the app | integration test on the socket |
| Stale report removed | ≤ 1 poll period (750 ms) after the leader changes | integration test with a fake leader |
| `tarmac hooks run` with no daemon | exits 0 in ≤ 200 ms, prints nothing on stdout | CLI test |
| `wait --changed` on an atomic replace | detected ≤ 250 ms | CLI test (rename over the file) |
| Doc watcher | zero `watch`/`unwatch` calls caused by any `wait` | by construction; assert in a daemon test that `Subscribe` never calls the watcher |
| Re-running `hooks install` | the config file is unchanged byte-for-byte | CLI test on a temp config |
| Inbox jump | ↵ on an item on another board ends with that card prime and in view, in one board switch and one flight | `TarmacKit` test of the jump decision + `make qa` scenario |
| Resume chip | ⏎ writes the recorded command exactly once; any other first key writes nothing and drops the record | `TarmacKit` test of the chip decision + `make qa` scenario |

## Out of scope

- Any match on terminal output, any summary that Tarmac writes, and any
  inference of state.
- `tarmac focus` and the idle auto-switch (backlog §1.1). A report marks; it
  never moves the view.
- Streaming arbitrary paths in `events` (the daemon-side second watcher).
- Running a resume command without a keypress.
- tmux and bare-terminal attach (backlog §2), and PTY re-parenting.
- Persisting bell and exit history across an app relaunch.
