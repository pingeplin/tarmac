**Status:** implemented
**Author:** EP Lin
**Doc type:** Mini RFC
**Issue:** [#171](https://github.com/pingeplin/tarmac/issues/171)

## Decision

Tarmac adopts Chromium's confirm-to-quit on macOS. Keyboard ⌘Q no longer quits
on a tap.

- **Tap.** A tap shows a centered "Hold ⌘Q to Quit" notice. After Q is
  released it lingers 1 s, then fades over 0.2 s.
- **Hold.** Holding Q for 500 ms hides the window; the notice stays up. The app
  quits when Q is released.
- **Second tap.** A second ⌘Q within 1 s of the first *press* hides the window
  and quits when Q is released.
- **Menu toggle.** An app-menu check item, *Warn Before Quitting (⌘Q)*, turns
  the guard off. It is **on by default**.
- **Mouse paths.** A mouse click on *Quit*, Dock → Quit, and logout still quit
  immediately, as in Chromium.
- **Hidden window.** ⌘Q stays guarded after the red button hides the window;
  the notice shows on the main screen. This departs from Chromium, which quits
  at once with no window open (`app_controller_mac.mm:1010-1014`): a hidden
  Tarmac still owns live terminals.

The red close button **hides** the window instead of quitting. The app keeps
running, and the window comes back whenever Tarmac is activated: ⌘Tab, a Dock
click, Spotlight.

We guard every keyboard ⌘Q (window open, minimized or hidden), not only when a
terminal is busy. A hold costs almost nothing when the user means
to quit, so we prefer a guard that is always there and needs no daemon or
protocol change. The alternative was a precise
"busy" signal that needs both.

The earlier draft of this doc (a modal alert gated by a daemon-computed busy
count) is superseded. See Alternative A.

## Problem

⌘W (close card) is used constantly, and Q sits next to it. One slip quits the
cockpit mid agent-run. Quitting does not kill terminals: the daemon is
`setsid`-detached (`desktop/src-tauri/src/bridge.rs:614-619`), and a relaunch
re-binds them. But the user loses their place. The next launch after a
`brew upgrade` also SIGTERMs the daemon and every shell with it (#172,
`docs/architecture.md` §6). The red button quits too, through the last-window
exit path.

## Constraints the source imposes

Two investigators and two verifiers checked these claims. Sources:

- crates at tauri 2.11.3, tao 0.35.3, muda 0.19.3, wry 0.55.1,
  objc2-app-kit 0.3.2, objc2-core-graphics 0.3.2;
- Chromium @ `1a56c69`;
- WebKit @ `be683cb`;
- Apple's *Monitoring Events* guide and WWDC 2010 session 145;
- Apple Developer Forums thread 729242, which motivated the stale-event check;
- three throwaway spikes in a dev build (see *Spike results*).

Each claim below comes from reading source unless it names a spike. A spike
claim marked *hand-observed* has no surviving log.

1. **⌘Q cannot be stopped at the Tauri layer.** Two facts combine here:
   - The default Quit item uses the `terminate:` selector (muda
     `macos/mod.rs:994`).
   - No crate implements `applicationShouldTerminate:`.
   The path is `applicationWillTerminate` → `RunEvent::Exit`
   (tauri-runtime-wry `lib.rs:4185-4187`), and that event cannot be prevented.
2. **A custom Quit `MenuItem` does not help.** Its action reaches
   `on_menu_event` a run-loop turn later, through the event-loop proxy (muda
   `mod.rs:1130`, tauri `app.rs:2350`, tao `event_loop.rs:343-353`). By then the
   handler cannot tell a key from a click, and cannot see key repeats.
3. **Retargeting the native Quit item runs inside the key event.**
   - muda creates Quit with action `terminate:` and no target
     (`mod.rs:994`; only About gets a target, `:866-873`). It never resets an
     item's target or action.
   - Tauri installs the default menu in `Builder::build()`, before `.setup()`
     runs (`app.rs:2245-2249, 2383-2396, 1423-1425`).
   - Setting that item's target and action to a Tarmac object makes AppKit call
     it from its own key-equivalent matching. For a menu click,
     `[NSApp currentEvent]` is a mouse event (spike v3 logged a mouse-down;
     Firefox's `nsMenuBarX.mm:1272-1276` expects a mouseUp). For a keypress
     it is the keyDown (spike v3, hand-observed: a tap did not quit, which v3
     does only for a keyDown).
   - **AppKit decides what the Quit shortcut is**, so Tarmac compares no
     characters and no key codes. Spike v3 behaved identically under ABC,
     Zhuyin, Japanese Romaji and Japanese Kana (hand-observed).
4. **Q's keyUp cannot be relied on while ⌘ is held.** tao's `sendEvent:`
   override sends ⌘-keyUps straight to the key window without calling super
   (tao `macos/app.rs:28-52`), so a local monitor never saw one (spike v2), and
   a hidden window cannot be the key window. Chromium also found keyUp lost on
   ⌘Tab mid-hold, and moved to polling (Chromium ffd9d0f172, bug 40945664).
   Release is therefore detected by polling
   `CGEventSourceKeyState(CombinedSessionState, keyCode)` on the
   **triggering event's keyCode** (never a hard-coded Q; Chromium aaabc160f1).
   The binding is `objc2_core_graphics::CGEventSource::key_state`
   (`CGEventSource.rs:112-120`).
5. **No nested event loop.** tao holds a `Mutex` and a `RefCell` borrow while
   it runs callbacks. `wakeup` and `cleared` return early while nested, and
   `reopen` and `open_urls` re-lock without a guard (tao
   `app_state.rs:69-78, 203-218, 324, 389`). Polling runs off the main thread
   and hops back with `run_on_main_thread`.
6. **Auto-repeat reaches the Quit item again.** Every repeat keyDown invokes
   the retargeted action with `isARepeat`. While a gesture is active, repeats
   must do nothing. Inferred: spike v2 logged repeats reaching a monitor, and
   v3's log of calls to the item was lost.
7. **WebKit sees ⌘Q first.** With the WKWebView first responder, WebKit offers
   the keyDown to the page. Only if the page leaves it unhandled does it
   re-send the event through `[NSApp _setCurrentEvent:] + sendEvent:` to the
   menu (`WebViewImpl.mm:5893-5899`; the re-sent event is the original object,
   checked by pointer at `:6823`). This has three consequences:
   - The handler runs one web-process round trip after the press. A very quick
     tap can already read as released on the first poll, which is still a tap
     (inferred; spike v2's `first sample held=true` was taken before WebKit,
     and v3's first samples were in the lost log).
   - The re-sent event is the original `NSEvent`, so its `timestamp` is the
     press time and its age includes the round trip.
   - A page that calls `preventDefault` on ⌘Q suppresses it. With terminal
     focus the page leaves it unhandled today: v1's unmatched ⌘Q quit through
     the menu (hand-observed). `App.tsx` must keep letting ⌘Q through. The
     board switcher's gate does so by matching `e.key` against a literal `"q"`
     (`App.tsx:1395-1399`).
8. **Chromium's numbers** (`confirm_quit_panel_controller.mm`):
   - Hold threshold is about 0.5 s: `kShowDuration` 1.5 s minus a 1.0 s fuzz,
     at `:290-311`.
   - The second-tap window is 1.0 s from the start of the previous attempt
     (`:244-276`).
   - After an early release the notice lingers 1.0 s, then fades over 0.2 s
     (`:352-383`).
   - Past the threshold, windows fade over 0.2 s, and the app terminates only
     after Q is released (`:251-258, 312-322`). Quitting while Q is still down
     sends the repeating ⌘Q to the next app.
   - Pref `browser.confirm_to_quit` defaults to true (`confirm_quit.cc:18`).
9. **Hide on close is supported.**
   - `CloseRequested` + `api.prevent_close()` works (tauri `app.rs:97-118`).
   - `RunEvent::Reopen { has_visible_windows }` fires on a Dock click (tauri
     `app.rs:279, 2632`; tao `app_delegate.rs:79, 206-215`). A plugin's
     `on_event` also receives it (`app.rs:2643-2648`).
   - A **minimized window counts as visible** (Apple,
     `applicationShouldHandleReopen:hasVisibleWindows:`), and AppKit restores
     it by itself. Only a window hidden by the red button needs `show()` +
     `set_focus()`.

## Proposed approach

**Intercept.**

- **Retarget.** In `.setup()`, walk `NSApp.mainMenu` for the item whose action
  is `terminate:`. Set its target to a Tarmac `define_class!` object, kept alive
  for the app's lifetime (a menu item does not retain its target), and its
  action to that object's method.
- **The handler reads `[NSApp currentEvent]`** and asks `QuitGuard::route`.
  First it decides whether the event is a **keyboard Quit**, i.e. all of:
  - its type is keyDown;
  - its ⇧⌃⌥⌘ modifier bits equal those of the item's live
    `keyEquivalentModifierMask`, with ⇧ added when the item's `keyEquivalent`
    carries Shift in its character (e.g. `"Q"`). Chromium notes a remap can
    store Shift that way (`nsmenuitem_additions.mm:154-156, 286-291`). Caps
    Lock, Fn and NumericPad never break a match; a remap onto an arrow or
    keypad key sets NumericPad;
  - its age, handler uptime − `timestamp`, lies in `0 ..= bound`. A timestamp of
    0 or one in the future fails the check. Both are seen in the field: events
    posted by third-party apps (Firefox `nsCocoaUtils.mm:1170-1175`) and bogus
    timestamps (Chromium `base_event_utils.cc:67-81`). A failed check means an
    unguarded immediate quit, never a stuck one.
  `currentEvent` is not the Quit key when no key triggered the item. After
  keyboard menu navigation (⌃F2 … Return) it is a fresh Return keyDown, which
  the modifier check rejects. After a VoiceOver press or automation it can be
  an older event, which the freshness check rejects. Treating any keyDown as a
  keyboard Quit would start a gesture on the wrong key, and that quit would
  never happen. The check reads the item's live mask, so a user
  remap still counts, and it compares no characters. The freshness bound is a
  `QuitGuard` constant that must outlast a busy web-process round trip
  (constraint 7); the spec sets it and check 12 measures it. Chromium likewise
  refuses to trust the event type. It re-matches the event, comparing
  characters as well as the mask, and has no freshness check
  (`app_controller_mac.mm:1009-1047`,
  `global_keyboard_shortcuts_mac.mm:206-223`). Neither the modifier check nor
  the freshness check was spiked: v3 treated every keyDown as a keyboard Quit.
  - **not a keyboard Quit** (menu click, stale event) → `terminate:` now;
  - **a keyboard Quit, guard off, no gesture in progress** → `terminate:` now;
  - **otherwise** → `on_quit_key(timestamp, keyCode, isARepeat)`. A gesture already
    in progress stays guarded (never calls `terminate:`) even if the toggle
    flips mid-gesture.
- **Retarget the final menu.** The toggle (below) builds its menu from
  `Menu::default`, which creates a fresh `terminate:` item. It is installed
  through `Builder::menu`, which sets it in `build()` before `.setup()` runs
  (tauri `app.rs:2383-2396`), so the retarget sees it. Any later menu set must
  re-run the retarget (muda `init_for_nsapp`; tauri `set_menu`,
  `app.rs:961-990`).
- **Window state does not matter:** open, minimized and hidden are all guarded.
- **Not intercepted:** Dock → Quit, the ⌘Tab-switcher Q and logout send
  `terminate:` straight to `NSApp` and bypass the item.

**Decide: a pure state machine.** `QuitGuard` lives in a new
`desktop/src-tauri/src/quit_guard.rs`. It has no AppKit types; time, key state,
raw modifier bits and the item's key equivalent are passed in, so the
keyboard-Quit test and the notice's shortcut text are pure and unit-tested too.

```
enum Phase { Idle { last_start_ms: Option<u64> }, Showing { started_ms, key_code }, Confirming { since_ms, key_code } }
enum Route { TerminateNow, Guard }
struct QuitEvent { is_key_down: bool, modifiers: u64, item_mask: u64, item_key_equivalent: String, age_ms: i64 }
fn route(&self, ev: QuitEvent, enabled: bool) -> Route   // Guard iff keyboard Quit && (!Idle || enabled)
fn on_quit_key(&mut self, press_ms, key_code, is_repeat) -> Vec<Effect>   // press_ms = the keyDown's timestamp
fn on_poll(&mut self, sampled_ms, key_down: bool) -> Vec<Effect>
fn shortcut_label(key_equivalent: &str, mask: u64) -> String
enum Effect { ShowHud, LingerThenFadeHud, HideWindows, StartPolling(key_code), StopPolling, Exit }
```

"Recent" means `press_ms − last_start_ms < 1000`, strict, as in Chromium
(`confirm_quit_panel_controller.mm:249-250`). In the table, "chord" means a
keyDown delivered to the retargeted Quit item. `key_code` is the chord that
issued `StartPolling`; a re-press keeps it.

All `_ms` values are on one monotonic clock: `NSEvent.timestamp` and the
poller's sample times are both system uptime. `press_ms` is the keyDown's own
timestamp, which WebKit's re-send preserves (constraint 7). The 500 ms hold and
the 1 s second-tap window therefore count from the physical press, not from
the handler after a web-process round trip. The event's age for the freshness
check is handler uptime − `press_ms`.

| From | Input | To | Effects |
|---|---|---|---|
| Idle, no recent start | chord, not repeat | Showing { started_ms: press } | ShowHud, StartPolling |
| Idle, recent start | chord, not repeat | Confirming { since_ms: press } | HideWindows, StartPolling |
| Idle | chord, repeat | Idle | none (ignored) |
| Idle | poll | Idle | none (stale) |
| Showing | poll, held, < 500 ms since `started_ms` | Showing | none |
| Showing | poll, held, ≥ 500 ms since `started_ms` | Confirming { since_ms: sampled } | HideWindows |
| Showing | poll, released (any elapsed time) | Idle { last_start_ms: started_ms } | LingerThenFadeHud, StopPolling |
| Showing | chord, not repeat (re-pressed before a poll saw the release) | Confirming { since_ms: press } | HideWindows |
| Showing / Confirming | chord, repeat | same | none (ignored) |
| Showing / Confirming | poll with `sampled_ms` before the phase was entered | same | none (stale) |
| Confirming | chord, not repeat (re-pressed before a poll saw the release) | same | none |
| Confirming | poll, held | Confirming | none |
| Confirming | poll, released | Idle | StopPolling, Exit |

- If the first poll already reads Q as up, it counts as a tap. Two causes: a
  tap released within the WebKit round trip (constraint 7), or key state that
  is filtered or unavailable. In the second case the auto-repeats that follow
  land in `Idle` and are ignored, so a hold cannot quit; a second tap still
  does.
- A poll is stale when its sample predates the entry into the current phase;
  the stale check runs before the other poll rows. A sample queued before
  `StopPolling` can reach the main thread after the next chord. Without this
  rule a stale "released" could exit while Q is down.
- A ⌘Tab mid-hold that reads as "released" behaves as in Chromium: before the
  threshold it lingers; past it, the app exits.

**Effects: thin wiring in `lib.rs`.**

- `Exit` → set a `quitting` flag, then `app.exit(0)`. The close handler lets
  `CloseRequested` through while `quitting` is set, so hide-on-close cannot
  swallow the quit. `ExitRequested{code: Some(0)}` is let through.
- `HideWindows` → hide the main window. It does not set `hidden_by_close`.
- `ShowHud` → show the notice at full opacity, cancelling any pending linger or
  fade from an earlier tap. A new tap can land while the last notice lingers
  (release at 0.3 s, linger to 1.3 s, new tap at 1.1 s). Chromium's
  `showWindow` resets the animations but does not cancel the delayed fade
  (`confirm_quit_panel_controller.mm:340-356`).
- `LingerThenFadeHud` → after 1 s, fade over 0.2 s and order the panel out.
  It is the only effect that removes the notice. On the hold path the notice
  stays up over the hidden window until exit, as in Chromium, whose fade covers
  only browser windows (`confirm_quit_panel_controller.mm:147-162`).
- The poller is a thread that samples `key_state` every 50 ms and hops back to
  the main thread with the sample time as `sampled_ms`.

**Notice (the HUD).**

- **Window.** A native, borderless, **non-activating `NSPanel`**, created
  lazily, that ignores mouse events. It must not take key focus from the
  terminal. It joins all Spaces and works over full-screen apps.
- **Position.** Centered on the main window's screen; with the window hidden,
  on the main screen (`NSScreen.mainScreen`). Which screen a minimized window
  reports is left to the spec.
- **Look.** Chromium's: 350×70; fill white 0.2 at alpha 0.75; corner radius 20
  on macOS 26; bold 24 pt white text.
- **Accessibility.** It posts
  `NSAccessibilityAnnouncementRequestedNotification`, because borderless
  windows are not announced (Chromium `confirm_quit_panel_controller.mm:440-450`).
- **Text.** "Hold ⌘Q to Quit". The shortcut shown is built from the item's live
  `keyEquivalent` and mask, so a remap shows correctly (Chromium
  `confirm_quit_panel_controller.mm:389-395`).

**Toggle.**

- The app submenu gets a check item, *Warn Before Quitting (⌘Q)*. The app
  starts from `Menu::default(handle)` and inserts the item before Quit. The
  predefined Quit and Edit items are kept, so a menu click still quits and
  ⌘C/⌘V still reach the webview.
- The item is checked by default. Its state is saved across launches.

**Red button.**

- `on_window_event(CloseRequested)`, unless `quitting` → `api.prevent_close()`,
  hide the window, set `hidden_by_close`. The guard's own `HideWindows` does
  not set the flag.
- **Restore** (`show()` + `set_focus()`, clear the flag) while `hidden_by_close`,
  on either trigger:
  - **App activation** (⌘Tab, Spotlight, a Dock click on an inactive app):
    tao's delegate registers no `applicationDidBecomeActive:` (tao
    `app_delegate.rs:47-89`), so observe `NSApplicationDidBecomeActiveNotification`
    through `NSNotificationCenter`. This leaves tao's delegate class alone. The
    spec verifies the binding and that the notification does not fire for the
    notice panel.
  - **`RunEvent::Reopen`** (a Dock click while Tarmac is already active, which
    raises no activation). This needs `.build(ctx)?.run(|app, ev| …)` in place
    of `.run(ctx)` at `lib.rs:85`, or a plugin `on_event`.
  - Keying off the flag rather than `has_visible_windows` means a notice still
    lingering on screen cannot block the restore.
- Right after the red button Tarmac stays the active app with no window, so the
  window returns only on the next activation or Dock click.

**Dependencies.** Add direct dependencies, with features declared explicitly:

- `objc2`;
- `objc2-app-kit`: the retarget (`NSApplication`, `NSResponder`, `NSMenu`,
  `NSMenuItem`, `NSEvent`), plus the notice (`NSPanel`, `NSScreen`, the
  accessibility announcement);
- `objc2-foundation`: `NSProcessInfo`, `NSNotificationCenter`, `NSUserDefaults`;
- `objc2-core-graphics`: `CGEventSource`;
- `block2`, if the activation observer takes a block.

Today those symbols exist only because tao, muda and wry happen to enable them.
All five crates are already in `Cargo.lock` at the versions used. Spike v3 added
`objc2`, `block2`, `objc2-app-kit` and `objc2-core-graphics` (retarget and
key-state features only) with no new crate versions. The foundation and notice
features are not yet built.

## Alternatives

**A. Modal alert when a terminal is busy** (this doc's first draft). A native
alert, gated by a daemon-published `BoardMeta.busy` count. Rejected by the
reviewer:

- a modal on every guarded quit is more friction than a hold;
- "busy" needs a daemon change and a protocol key;
- process-group heuristics miss backgrounded or suspended jobs.

**B. A custom muda Quit `MenuItem`.** Its event reaches Rust a run-loop turn
later (constraint 2). By then it cannot tell a key from a click, cannot see
repeats, and cannot read the keyCode to poll.

**G. An `NSEvent` local keyDown monitor that matches the chord** (spikes v1 and
v2).
- It runs before WebKit and the menu, and returning `nil` stops Quit. So it
  needs no freshness check and adds no round trip, a page's `preventDefault`
  cannot block it, and replacing the menu does not undo it.
- But Tarmac would have to decide what ⌘Q is by comparing characters:
  - `charactersIgnoringModifiers` read `"ㄆ"` under Zhuyin, so v1 never matched.
  - The Command-applied characters read `"q"` there, but that is still a
    literal that second-guesses AppKit for other input sources and layouts, and
    for a Quit shortcut the user remapped.
- Rejected in favour of letting the menu match (constraint 3). We value
  AppKit's own shortcut matching over a round-trip-free intercept, and pay with
  the freshness check, the round trip and menu-replacement fragility (see
  *Trade-offs accepted*).

**C. JS `keydown` in the webview.** Keys typed inside an HTML card's
cross-origin iframe never reach the parent document. Repeats are absent when
Key Repeat is off. A busy JS thread stalls detection.

**D. Chromium's nested tracking loop.** Not safe inside tao (constraint 5).

**E. A React overlay for the notice.** It is invisible while the window is
hidden or minimized, and lags when the webview is busy.

**F. Inject `applicationShouldTerminate:` into tao's delegate.** It would also
catch Dock → Quit and logout, but patches a dependency's private class.
Chromium itself leaves those paths unguarded. Deferred.

## Trade-offs accepted

- **Unguarded paths.** A mouse click on Quit, Dock → Quit, the ⌘Tab-switcher Q
  and logout are unguarded by design.
- **Stale-event heuristic.** The freshness window trades a stale keyDown
  against a slow web process. Too short, and a busy page turns a real ⌘Q into
  an immediate quit; too long, and a stale ⌘-keyDown could start a gesture that
  never quits. The spec picks the value and check 12 measures it.
- **The retarget is fragile to menu replacement.** Anything that later replaces
  the app menu drops it. Tauri's JS menu API is allowed by `core:default` but
  unused. No check here catches a later replacement.
- **WebKit sees ⌘Q first.** With a webview focused, the guard acts one
  web-process round trip after the press. A web page that calls
  `preventDefault` on ⌘Q blocks the shortcut; a menu click still quits.
- **Unsafe AppKit code without unit tests.** The retarget, panel and poller are
  covered by manual QA. Every decision sits in `quit_guard.rs`, which is
  unit-tested.
- **Accessibility.** A hold is hard for some users. The alternatives are the
  menu click, the toggle, and the second tap. The notice is announced to
  VoiceOver.
- **Lifecycle change.** With the window hidden, the webview and terminals keep
  running and rendering. `ExitRequested{code: None}` from closing the last
  window no longer happens.
- **Second tap within 1 s quits.** Brave users report accidental quits from two
  quick ⌘Q presses while switching apps. Accepted to match Chromium.

## Key assumptions

- **AppKit calls the retargeted action inside its key-equivalent dispatch, with
  the keyDown as `currentEvent`.** Backed by source reading and a
  hand-observation whose log was lost (constraint 3). If it fails, the handler
  cannot tell a key from a click and the intercept needs a new design.
- **`CGEventSourceKeyState` returns real key state with no permission prompt
  in a bundled build.** Under `make run` only: the state was logged (spike v2)
  and the absent prompt was seen by hand. Check 8 covers the bundle. If it
  prompts or reads nothing, release detection needs another source.

## Spike results (2026-09-17)

Three throwaway patches ran in a `make run` dev build, with a human pressing
keys while a terminal card had focus. Synthetic input does not reach Tarmac, so
a human was required. The patches are `.dev/spike-171-hold-quit{,-v2,-v3}.patch`.
v1 and v2 used a local keyDown monitor (Alternative G); v3 retargets the native
Quit item (the proposed approach).

- **v1 never matched.** It matched on `charactersIgnoringModifiers == "q"`. It
  logged `monitor installed=true` but no ⌘Q keydown line, and ⌘Q quit through
  the menu.
- **v2 logged every ⌘ keydown before matching.**
  - Under ABC: `keyCode=12 chars="q" cim="q" cbam="q" devind=0x100000`.
  - Under Zhuyin: `keyCode=12 chars="q" cim="ㄆ" cbam="q"`. That is why v1
    missed (Alternative G).
- **v2, intercept by the monitor: confirmed with terminal focus.**
  - Four ⌘Q taps, released after 106–161 ms, were stopped by the monitor. The
    app stayed open.
  - The other focus contexts (HTML card iframe, markdown card, board) are
    measured for neither mechanism. They move into implementation QA
    (check 1).
- **v2, key state: confirmed under `make run`.**
  - `first sample held=true` on all five presses. The monitor sampled before
    WebKit saw the event; under the retarget the first sample is unmeasured
    (constraint 7).
  - A ~1 s hold under Zhuyin: the monitor stopped 6 auto-repeat keydowns, then
    logged `released after 1027ms`, and only then `exit(0)`.
  - There was no permission prompt. `make run` attributes TCC to the launching
    terminal (inferred), so a `make bundle` build still has to show the same
    before release (check 8).
- **Constraint 4 observed (v2).** No keyUp for Q reached the monitor while ⌘
  was held; the only keyUps logged were Space under ⌃⌥, from the input-source
  switch.
- **v3, retargeted Quit item.**
  - Startup logged `quit item found=true keyEquivalent="q" mask=0x100000
    target_before=nil`.
  - A menu-bar Quit click logged `action event_type=1` (mouse-down), then
    `non-key quit`, and quit at once.
  - **Observed by hand; this log was overwritten by a relaunch:** under ABC,
    Zhuyin, Japanese Romaji and Japanese Kana, a ⌘Q tap kept the app open, and a
    hold quit only after release.
- **Not exercised by any spike:** the modifier and freshness checks (v3 treated
  every keyDown as a keyboard Quit), the round trip's effect on the first
  sample, focus outside a terminal, a hidden or minimized window, keyboard menu
  navigation, a remapped shortcut, and a `make bundle` build.

## Open questions for the spec

- **Activation hook.** Confirm `NSApplicationDidBecomeActiveNotification` is
  reachable with the locked objc2 crates (objc2-foundation features), and that
  observing it coexists with tao's own delegate.
- **Where the toggle is saved.** Tarmac has no app-side preference store
  today. The candidate is `NSUserDefaults` under the bundle id. It is unverified
  which domain an unbundled `make run` binary writes to (its bundle id is NULL,
  per spec 2609.0009), and whether that is kept apart from the installed app.

## How we'll know it worked

**Manual (dev build unless noted):**

1. Under ABC, Zhuyin, Japanese Romaji and Japanese Kana, with focus in a
   terminal, an HTML card, a markdown card, or the board:
   - a ⌘Q tap shows the notice and the app stays; the notice fades about 1 s
     after release, and typing still reaches the focused card;
   - holding ~1 s hides the window with the notice still up; the app keeps
     running until Q is released, then quits, and the app behind Tarmac does
     not receive ⌘Q;
   - no `q` is typed on a tap or during a hold (every press and repeat passes
     through WebKit before the menu);
   - two taps within 1 s quit.
2. With the window minimized, a ⌘Q tap shows the notice and the app stays.
3. With the toggle off, a ⌘Q tap quits immediately. The toggle's state
   survives a relaunch.
4. A menu click on Quit, and Dock → Quit, each quit immediately.
5. The red button hides the window and the app stays running. ⌘Tab away and
   back, or a Dock click, brings it back with its terminals still live, also
   while the notice from an earlier ⌘Q tap is still on screen. With the window
   hidden, a ⌘Q tap shows the notice on the main screen and a hold quits.
6. ⌘C/⌘V still work in a terminal.
7. VoiceOver announces "Hold ⌘Q to Quit".
8. On a `make bundle` build, a hold quits with no permission prompt (spike v2
   saw none under `make run`).
9. A Quit shortcut remapped in System Settings → Keyboard → App Shortcuts is
   the one that gets guarded (e.g. ⌥⌘Q guards, plain ⌘Q does nothing), the
   notice reads "Hold ⌥⌘Q to Quit", and both hold with the board switcher open.
10. Keyboard menu navigation (⌃F2, arrow to Quit, Return) and a VoiceOver
    press on Quit each quit immediately, including right after a guarded ⌘Q
    tap.
11. Layouts beyond the spike: AZERTY, Dvorak, "Dvorak – QWERTY ⌘", Cangjie,
    Korean 2-Set, Hebrew, Greek or Russian, Caps Lock on, ⌘Q while Zhuyin
    or Japanese composition is in progress, and Zhuyin with the board switcher
    open. Record the result for each.
12. Freshness bound (by hand; `tarmac dev key` dispatches a DOM event that never
    reaches AppKit): log the event's age at the handler for ⌘Q taps with an
    idle page and with a page busy in a blocking loop (length set by the spec).
    The bound exceeds the largest busy age measured, and a tap on the busy page
    still shows the notice.

**Automated:** `quit_guard.rs` unit tests cover every table row, `route` and
`shortcut_label`:

- tap: a released poll before 500 ms lingers; a released poll after 500 ms
  with no earlier held poll (stalled poller) is still a tap;
- hold: held polls under 500 ms change nothing; at 500 ms, `HideWindows`;
  held polls in `Confirming` change nothing; `Exit` only on the released poll;
- second tap measured from the first press, not its release: press 0,
  release 400, press 950 → `Confirming`; press 1000 or 1050 → `Showing`;
- re-press in `Showing` → `Confirming`; re-press in `Confirming` → no effect;
- repeats ignored with no state change in every phase, including `Idle`
  after a first poll up;
- stale polls: any poll in `Idle`, and a poll sampled before the phase was
  entered (a "released" sample must not exit a second-tap `Confirming`);
- `route`: a non-key event, a keyDown whose modifiers don't match the item,
  an event just past the freshness bound, a zero timestamp and a future
  timestamp (negative age) each terminate now; a `"Q"` key equivalent matches a
  ⇧⌘ keyDown; Caps Lock, Fn or
  NumericPad set still matches; a keyboard Quit with the guard off terminates only in
  `Idle`; any gesture in progress guards;
- `shortcut_label`: `q` with ⌘ gives "⌘Q"; `q` with ⌥⌘ gives "⌥⌘Q".

## Out of scope

- Making the #172 restart visible (spec 2609.0017).
- Keeping PTYs alive across a version-mismatch restart (backlog).
- Guarding Dock → Quit and logout (F).
- Windows or Linux (Tarmac is macOS-only).
