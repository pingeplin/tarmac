## TL;DR

Magnify freezes the sandboxed iframe's root `zoom` at a **constant** `MAGNIFY_K = 3` instead of tracking board zoom. The document lays out once per load and never again; a permanent `scale(zoom/K)` on the outer box carries every subsequent board zoom. This makes wrap points genuinely immovable — the property 2607.0006 promised, measured to be false, and had to weaken to an ICB claim. Removing the settle relayout also removes the mid-gesture blur it existed to resolve.

## Problem

Spec 2607.0006 shipped magnify as "the shim sets `document.documentElement.style.zoom = z` at settle", where `z` is the current board zoom. Its S6 asserted that text wrap points never change. Rendering the real shim in WebKit 26.5 across the full board-zoom range falsified that (commit `700862f`, `ffddbfa` before this branch was rebased onto `main`). One paragraph:

| board zoom | 0.5 | 1 | 2 | 3 |
|---|---|---|---|---|
| magnify, WebKit 26.5 (ICB constant at 460px) | 9 | **7** | **7** | 6 |
| reveal-more, WebKit 26.5 | 16 | 7 | 4 | 2 |
| magnify, Chromium 149 | 7 | 7 | 7 | 7 |

The ICB held at exactly 460px in all four magnify cells, so the mechanism did what it claimed at the layout-viewport level. Wrap points still moved, via two engine-specific effects the same measurement named:

- **Above z=2, non-linear text metrics.** The same sentence measures 496 → 461 → 455 layout units at z = 1 → 2 → 3 in WebKit — roughly 7–8% narrower per layout unit as zoom rises. Chromium measures 486 at every level. No preference controls this.
- **Below z≈0.6, a used-font-size floor.** WebKit clamps the used font size under zoom < 1; a declared 15px resolves to 18px in layout units at z = 0.5, widening text ~20%. This is `minimumLogicalFontSize` semantics. Measured under Playwright WebKit's defaults; whether Tarmac's real WKWebView applies the same floor was never verified.

S6 was accordingly rewritten to judge on ICB constancy and on magnify being conspicuously more stable than reveal-more, rather than on an exact line count.

## Root cause

The variable is not `zoom`. It is the **changing zoom value**.

Settle-time magnify re-runs layout at a *new* root zoom on every settle, and WebKit does not scale glyph advances linearly across those values. Any design that varies the root zoom inherits that non-linearity; no amount of care at the ICB level removes it, because the ICB is not where the drift lives.

## Design

Freeze the root zoom. `MAGNIFY_K` (`desktop/src/kit/cardZoom.ts`) is a constant, and in magnify mode:

- the shim is posted `K` **once**, from the `ready` handler, and never again;
- the iframe is sized `frame × K` — a function of the card's world frame only, so it changes on card resize and on nothing else;
- a **permanent** `scale(zoom/K)` on the outer box carries all board zoom.

Layout therefore runs once per document load. A wrap point cannot move because nothing that determines one ever changes. The settle path is **removed**, not bypassed: `desktop/src/cards/HtmlCard.tsx` returns early from the zoom watcher in magnify mode, and the settle-keyed relayout effect is gone.

Two consequences fall out of that removal:

- **No mid-gesture blur.** The settle machinery existed because a transform stretches a cached raster (WebKit bug 27684), so a gesture was momentarily soft until the relayout landed. With `K ≥ MAX_ZOOM`, `scale(zoom/K) ≤ 1` across the whole range — always a down-scale, never an upsample — so the card is crisp at rest *and* in motion. Magnify's "no crispness advantage mid-gesture" limitation in 2607.0006 no longer applies.
- **Reveal-more is untouched.** It keeps real-px sizing and the settle resize. `cardIframePx` and `cardGestureScale` are unchanged; magnify simply passes `K` where reveal passes `settledZoom`.

### Relationship to doc cards' Panel H

This is the same idea `docZoom.ts` already uses for markdown prose: lay out once at a frozen K× reference, then down-scale by `zoom/K`. Both end in an identical `scale(zoom/K)`.

The one real difference is *how* the freeze is expressed. We author `.doc-prose`, so `docZoom.ts` freezes it by hand-multiplying every metric by `--oversample-k`. A foreign document cannot be asked to do that — we do not control its CSS — so root `zoom` performs the freeze instead, scaling the used lengths of the whole subtree in one property.

`MAGNIFY_K` and `DOC_OVERSAMPLE_K` are both 3 and both carry the same invariant (`K ≥ MAX_ZOOM`, `BoardEngine.MAX_ZOOM = 3.0`), but they are deliberately separate constants: they freeze different subtrees by different means, and nothing forces them to move together.

## Costs

Stated plainly; both are inherent to a frozen reference, not incidental.

- **Raster is K² in area at every zoom**, including 1× and below. A magnify card pays 9× the raster of an equivalently-sized reveal card even when zoomed out. This is the same cost `DOC_OVERSAMPLE_K` imposes on every doc card, and it is the cost issue [#76](https://github.com/pingeplin/tarmac/issues/76) exists to reclaim for markdown — that issue's premise is unchanged by this design, and it remains deferred pending its own triggers.
- **`K ≥ MAX_ZOOM` is an invariant, not a preference.** Board zoom past K would upsample and blur. `docZoom.test.ts` S13 enforces this for prose; `cardZoom.test.ts` now enforces the same for `MAGNIFY_K`.

That invariant is a *floor*, though, and K² is what you pay for clearing it — so the choice of 3 over 2 costs 2.25× the raster. 3 is `BoardEngine.MAX_ZOOM` exactly, which is the cheapest value that satisfies the invariant: K=2 would break crispness above board zoom 2, well inside the range the board already allows. If `MAX_ZOOM` ever drops, K should follow it down rather than stay at 3.

## Capability: resolved by the OS floor, not by a probe

2607.0006 built a runtime capability probe because WebKit 17.4 (macOS 14 field) no-ops CSS `zoom` entirely, and `CSS.supports('zoom','2')` returns `true` on that build — so capability had to be measured, never queried.

Commit `8f7b2ef` (`1cbef34` pre-rebase) raises the minimum macOS to 26 (`packaging/Casks/tarmac.rb`, `depends_on macos: :tahoe`). Standardized `zoom` ships around Safari 26.4, and the range between 17.4 and 26.5 was never measured, so 26 is the only floor the mechanism is verified against.

**With that floor there is no zoom-incapable target left, and `desktop/src/kit/zoomMode.ts`'s probe is dead weight.** It still runs, still costs two forced layouts per HTML card load, and still gates magnify behind a verdict that can now only come back `true`. Removing it — along with the shim's probe, the `ready` payload's `probe` field, and the `capable` half of the console line — is named as follow-up work below. It is not retained for safety; it is retained only because this change did not touch it.

Note the failure mode this floor avoids is not graceful. With the host at `zoom: K` and the outer box dividing by K, a no-op `zoom` renders the card at 1/K size with broken scroll height — not a fallback, a visibly broken card.

## Verification

Verified by a self-reporting probe rather than by eye.

`desktop/qa/wrap-probe.html` walks its ruler paragraph's text node with `Range.getClientRects()`, records the **character offset** at which each line begins, and re-measures every 400ms, reporting only when the signature differs from its baseline. Character offsets rather than a line count: a count can hold while breaks move.

- **Magnify:** the signature held its baseline across a 25% → 300% board-zoom sweep.
- **Control:** `desktop/qa/wrap-probe-reveal.html` — byte-identical content declaring `tarmac-zoom: reveal` — reflowed over the same sweep. This is what makes the positive result non-vacuous; a probe that reports "no change" for both would be broken, not passing.

Environment: macOS 26.6.1, on both the built-in Retina panel (3024×1964 @ 14.2", ~254 ppi) and an external BenQ EW2770QZ (2560×1440 @ 27", ~109 ppi, true 1× with no macOS scaling).

**Limits of this evidence.** One engine, one OS version, human-observed, two displays, one document. It is not a test-suite guarantee and nothing in `make test` will catch a regression of this property. The 2607.0006 measurements it corrects were themselves taken under Playwright WebKit 26.5, a different build from field WKWebView.

Both probes were written in gitignored `.dev/` and would have been lost with it; commit `1468721` promoted them to `desktop/qa/` alongside `magnify-probe.html` and `sandbox-probe.html`, where this repo keeps permanent QA artifacts. The instrument that decides S6 is therefore in the tree, not ephemeral.

## What this supersedes

- **2607.0004's zoom semantics** (real-px sizing, resize on settle) survive as reveal-more — but no longer as the default. Magnify is what a document gets by saying nothing; reveal is reached only by declaring `content="reveal"`. An agent writing a report does not know to ask for a stable layout, and re-wrapping under zoom is the wrong default for what most HTML cards are. Opting out is the case with a reason behind it (honest viewport dimensions for a self-contained D3/Canvas dashboard, 2607.0004 S6), so it is the half worth spelling.
- **2607.0006's settle-time shape** is replaced. Its capability machinery, message contract, and `<meta name="tarmac-zoom">` declaration mechanism are retained; the value posted and its timing change (`K` once, instead of the board zoom per settle), and the declaration's default inverts — see above.
- **2607.0006's S6** was already weakened from "wrap points never change" to an ICB claim (`700862f`). Under frozen-K the original wording is true again, and S6 could be restored to it.
- The shield/borrow interaction model (2607.0004) is unchanged by this design.

Issues #75 and #76 were both written against the pre-rebase picture:

- **#75's acceptance criteria are obsolete.** They require a measurement-based runtime capability probe and a zoom-incapable fallback path. The macOS 26 floor removes the target those exist for. The issue's *outcome* — magnify without re-wrap — is delivered, by a different mechanism than it specifies.
- **#76's premise is unchanged and it remains deferred.** Its case rests on doc-card raster memory and the `MAX_ZOOM ≤ K` ceiling, neither of which this change affects. Note that it lists #75's capability probe as the infrastructure it would reuse; that dependency is now void.
