# 2610.0002 Native wheel for HTML cards

> **Doc status: HISTORICAL** — a design record for work that has already
> shipped. It describes the system *as of the change it accompanied*, not as it
> is today. For current behaviour see [`../architecture.md`](../architecture.md);
> for what the build settled on, see
> [spec 2610.0002](../../.blueprint/specs/2610.0002_native_html_card_wheel.md).

**Date:** 2026-10-03
**Status:** implemented
**Author:** EP Lin
**Doc type:** Mini RFC
**Issue:** [#144](https://github.com/pingeplin/tarmac/issues/144)
**Companion:** [2610.0003 Card scroll indicator](2610.0003_card_scroll_indicator.md) — the other half of "unified card scroll"

## Decision

An HTML card's document takes the wheel event itself, as a terminal's and a
markdown card's content already do. The per-event `scrollBy` relay is deleted.

The card's web view converts every wheel it is handed — the delta becomes the
document's own units — and passes it to WebKit. The shield hands it the wheel
and nothing else, so a shielded card still sees no press. A borrowed card's
wheel reaches the same web view directly, so both states scroll alike.

We rewrite the wheel event's delta rather than change how a magnified document
is laid out, because we value leaving the frozen-K raster path
([2608.0001](2608.0001_frozen_k_magnify_for_html_cards.md)) untouched more than
we value having no event rewriting.

## Problem

Three card kinds, four wheel paths. Only the shielded HTML one is not the
content's own; the borrowed one is, at the wrong speed:

| Card | Wheel path today |
| --- | --- |
| Terminal | `TerminalView.scrollWheel` → `scrollViewport(.rows)` |
| Markdown | WebKit, natively, in `.doc-scroll` |
| HTML, shielded | shield → `CardZoom.ScrollRelay` → `postMessage` → shim `window.scrollBy` |
| HTML, borrowed | WebKit, natively, unconverted |

Measured on `main` @ `9174ca7`, macOS 26, magnify mode (K = 3). One gesture of
10 precise events × 10 pt; the figure is travel **on screen**, in points, for
100 pt of finger. A blank cell was not run. The events were built in the app
and handed to the shield; the runs that posted real gestures at the HID tap
are named as such below. The middle column is the same path with the conversion
off — what a borrowed card's web view is handed today — not a borrowed card.

| Board zoom | Relay (shipped, shielded) | Forwarded as-is (borrowed, today) | Forwarded, converted |
| --- | --- | --- | --- |
| 0.1 | | | 100.0 |
| 0.25 | | | 100.0 |
| 0.5 | 33.3 | 16.7 | 100.0 |
| 1 | | | 100.0 |
| 1.728 | 33.4 | 57.6 | 100.2 |
| 2 | 33.3 | 66.7 | 100.0 |
| 3 | | | 100.0 |

1. **A shielded HTML card moves at one third of the finger.** A magnified
   document's `scrollY`, `scrollHeight` and `innerHeight` are in iframe pixels:
   one unit is `zoom/3` of a screen point. `CardZoom.scrollDelta` divides by
   `zoom` where it has to multiply by `3/zoom`. A markdown card and a board pan
   both move 1:1.
2. **A borrowed card moves at `zoom/3` of the finger** — a different wrong
   speed, and one that changes with the board zoom. Borrowing a card changes how
   fast it scrolls.
3. **A notched wheel moves a shielded card 3.3 pt a line**, at zoom 1 and 2
   alike. WebKit's own line step is 40 units (measured on the unconverted HTML
   path); a markdown card's scroller is not scaled, so there a line is 40 pt.
4. **The relay can only scroll the window.** With the pointer over a nested
   scroller (`overflow: auto` inside the document), 100 pt of wheel scrolled the
   window through the relay, and scrolled the nested element — window unmoved —
   when the event was forwarded.

What this design does **not** claim: that the relay is slow. #144 calls the
card "heavy" and blames per-event `scrollBy` on the main thread; no frame time
was measured, and none is a criterion here. The measured defects are travel and
reach. #142's white band is likewise not a live bug — spec
[2609.0013](../../.blueprint/specs/2609.0013_whole_px_relayed_scroll_deltas.md)
fixed it in the relay.

## Constraints

- **Look, don't touch**
  ([2607.0004](2607.0004_html_js_doc_cards_sandboxed_webview.md)): a shielded
  card's document sees no press and no key. #144's PoC let the wheel in by
  making the shield `pointer-events: none`, which let clicks in too, and stopped
  there. In AppKit the shield is a view and can pass on one event type.
- **Frozen-K magnify stays.** The document is laid out once at root zoom 3 and
  shown scaled by `zoom/3`; a board zoom never re-wraps it.
- **The `TarmacApp` shell has no unit tests.** The arithmetic below is
  `TarmacKit`; the view only writes its result into an event.
- No wire, daemon or persisted-state change, and no CLI code change: the agent
  guide the CLI embeds gains a sentence (plan, step 5).

## Proposed change

```swift
// TarmacKit
extension CardZoom {
    /// Document units per screen point of wheel travel: `magnifyK / zoom`
    /// under magnify, 1 in reveal and for a zoom that is not finite and positive.
    public static func wheelScale(zoom: CGFloat, magnify: Bool) -> CGFloat
}

/// One HTML card's wheel conversion: what to write into the event, or nil to
/// pass it unchanged. A precise delta is written to an integer event field, so
/// each axis's residue is kept for the next event.
public struct CardWheel: Sendable {
    public enum Delta: Equatable, Sendable {
        case points(dx: Int, dy: Int)        // a precise device: whole document units
        case lines(dx: Double, dy: Double)   // a notched wheel: lines of the document
    }

    public init()
    /// `dx`, `dy` are the event's own delta fields — points when `precise`,
    /// lines otherwise. nil when `scale` is 1.
    public mutating func convert(dx: Double, dy: Double, precise: Bool, scale: CGFloat) -> Delta?
}
```

```swift
// TarmacApp — the HTML card's web view
final class HTMLCardWebView: WKWebView {
    var wheelScale: () -> CGFloat          // CardZoom.wheelScale(zoom: host.zoom, magnify: …)
    func resetWheel()                      // a new document starts with no residue
    override func scrollWheel(with event: NSEvent)   // super.scrollWheel(with: converted(event))
}
```

- **Where it sits.** In the web view, because that is the one place a shielded
  wheel and a borrowed wheel both pass. `CardShieldView.scrollWheel` hands the
  raw event to the web view; a borrowed card's wheel is dispatched to it by
  AppKit. `CardWebView.make` takes the web view's class so only an HTML card
  gets this one.
- **What is rewritten.** A copy of the event's `CGEvent`: for a precise device
  the two point deltas (`scrollWheelEventPointDeltaAxis1/2`) take the
  `.points` `CardWheel.convert` makes of their own values; for a notched wheel
  the two fixed-point line deltas (`scrollWheelEventFixedPtDeltaAxis1/2`) take
  the `.lines` it makes of theirs — the fields are read and written back, as
  the spike did. Phase, momentum phase, location and window are untouched.
  Momentum events are converted like any other.
- **The zoom is the live one** (`ScreenSpaceHost.zoom`), as `relayWheel` uses
  today: while a zoom is settling the card's stretch carries the difference, so
  a unit is `zoom/3` of a point throughout.
- **When the scale is 1** — reveal mode, or magnify at zoom 3 — the event
  passes unchanged. So does an event with no `CGEvent` behind it. Which of the
  three it is — points, lines or unchanged — is `CardWheel.convert`'s answer;
  the view reads two fields, asks, and writes two fields.
- **A notched line is not carried.** At a fractional scale WebKit lands it on
  a whole unit: 1.736 lines at zoom 1.728 came to 69 units, 39.7 pt.
- **A zero step is still passed on.** Its phase is content: WebKit's gesture
  state needs the began and ended events. The relay dropped them.

Deleted with the relay: `CardHostMessage.scroll`, the shim's
`tarmac === "scroll"` branch, `HTMLCardView.relayWheel`, `CardZoom.scrollDelta`,
`CardZoom.wheelDelta`, `CardZoom.ScrollRelay` and `CardZoom.ScrollStep`.
`CardZoom.quantizeScrollDelta` — whole step plus carry — stays, as what
`CardWheel.convert` is built on. `HTMLCardView` is the only caller of any of
them. Their tests follow: the `scrollDelta` and `wheelDelta` cases of
`CardZoomTests` go; its `ScrollRelay` cases move to `CardWheelTests` with a
zero `.points` where they expected nil — nil now means *pass unchanged*, and
the residue kept across zero steps is still the carry's test — less
`testS12StillPostsWhenOnlyOneAxisQuantizesToZero`, which only asserts that
something is posted; `testScrollCarriesWholePixelsPerAxis` goes;
`testAScrollFromTheHostReachesScrollByWithItsOwnDeltas` is inverted — a
`scroll` message no longer reaches `scrollBy` — which is criterion 10's check
of the shim.
`qa/scroll-band-probe.html` listens for the deleted message and goes inert; its
sheet is a closed record.

Routing is unchanged: `BoardWheel.route` still gives a card the wheel only over
the body of the selected one. At the document's limit the board stays: the QA
run measured that WebKit keeps a wheel it does not use, and
`BoardView.scrollWheel`, where one would arrive, does nothing.

## Why this and not the alternatives

**Keep the relay and fix the factor.** One line in `CardZoom.scrollDelta`
(`3/zoom`), and a shielded card moves 1:1. It is the cheapest fix of problem 1
and the fallback if the rewrite ever breaks. It loses on three counts. The
borrowed card stays at `zoom/3`: bringing it to 1:1 means either the event
rewrite — after which the relay is the second of two mechanisms doing one job —
or relaying a borrowed card's wheel too, which takes away the native wheel a
borrowed card has today. Nested scrollers stay dead to the wheel. And the ask
is one mechanism for every card: this keeps two inside one card kind.

**Lift the shield while the card is selected** (#144's PoC). Native scrolling,
no rewrite — and every click, drag and text selection reaches an untrusted
document the moment its card is selected. It also leaves the travel at
`zoom/3`.

**Forward the event unconverted.** The middle column of the table: right only
at zoom 3.

**Convert in the shield, not the web view.** What the first spike did. The
shielded card is fixed and the borrowed one is not.

**Magnify with `WKWebView.magnification` instead of a CSS transform.** WebKit
would own the scale and map the wheel itself. It replaces the raster path
2608.0001 settled, which the constraint above rules out.

## Trade-offs accepted

- **A shielded document now sees a DOM `wheel` event for every wheel over its
  selected card** — cancelable, with pointer coordinates. It is how WebKit
  scrolls; there is no native scroll without it. A map or chart that zooms on
  wheel will do so on a card that is selected and not borrowed, and a document
  that calls `preventDefault` will not scroll. Look-don't-touch narrows to *no
  press, no key*; 2607.0004's "DOM events never enter the iframe" stops being
  true for this one event. Measured: the probe counted one `wheel` per event
  and no `mousedown`.
- **HTML cards scroll faster, and everyone will feel it.** Trackpad, shielded:
  three times today's. Notched wheel, shielded: twelve times (3.3 → 40 pt a
  line), which is also four times the 10 pt a line the board pans by
  (`BoardWheel.lineTravel`). Borrowed: `3/zoom` times. Those are magnify; a
  shielded reveal card's trackpad travel is already 1:1 and stays, and its
  notched line goes from 10 pt to 40 (by the code, not measured).
- **The wheel path rests on rebuilding an `NSEvent` from a modified `CGEvent`
  copy.** Public API, measured, but a seam the relay did not have.
- **The relay's whole-unit guarantee becomes WebKit's.** The relay only ever
  sent whole units, which is what closed #142. A forwarded notched wheel carries
  a fractional line delta (1.736 lines at zoom 1.728). Measured, it does not
  band — see below — but the guarantee is no longer ours.

## Riskiest assumption

**That an event rebuilt with `NSEvent(cgEvent:)` from a copy of a real wheel
event reaches WebKit as the original would, with only its delta changed.**
Measured with real gestures posted at the HID tap, zoom 2: the rebuilt event
kept `window` and `locationInWindow`; a shielded card and a borrowed card each
moved 90 units for 6 events × 10 pt (60 pt on screen); the nested scroller under
the pointer scrolled. If an OS update breaks it, the fallback is the first
alternative, and what is lost is the borrowed card's speed and nested
scrollers, not scrolling.

Also measured, each a claim the proposal rests on:

- **The carry.** Zoom 2, factor 1.5, 30 events × 1 pt: whole step with carry
  30 pt on screen; truncating 20; rounding each event 40.
- **Momentum.** Zoom 2, a 10 × 20 pt gesture with 6 coasting events: 327 units
  converted against 218 unconverted — the coast scales by the same 1.5.
- **The field set.** Replacing only the point deltas (precise) or only the
  fixed-point line deltas (notched) moves the document exactly as scaling all
  six delta fields does.
- **A notched wheel.** 40 units a line unconverted; converted, 40 pt a line on
  screen at zoom 1 and 2, and 39.7 at zoom 1.728.
- **Reveal.** Scale 1, nothing converted: 10 × 10 pt moved the document 100 pt
  on screen at zoom 0.5, 1 and 2.
- **No band.** Zoom 1.728, region captures of the card body mid-scroll. A
  control that calls a fractional `scrollBy` itself: 30 of 30 frames banded; a
  whole-unit control: 0 of 30. Forwarded precise: 0 of 80. Forwarded notched,
  fractional lines: 0 of 80. Relay: 0 of 80. 37–39 of every 40 frames caught
  the content moving.
- **Both axes.** Zoom 2, 10 events of (−10, −10) pt: converted, `scrollX` and
  `scrollY` each moved 150 units (100 pt); unconverted, 100 units each.
- **Real notched events.** Three one-line events posted at the HID tap, zoom 2,
  shielded: 180 units, 40 pt a line, the same as the synthesized ones.

The harness and its logs are in `.dev/spike-wheel/`, which is not tracked. The
plan moves the probe, the gesture poster and the fractional-scroll control page
into the tree, so the travel and band checks can be run again; the frame
counter the spike used (`band.py`, PIL and numpy) stays out, and the band check
is recorded in the QA sheet by eye or by capture, as 2609.0013's was.

Not measurable by a harness:

  arithmetic; a real coast and its feel need a hand, and are a check in the QA

- [ASSUMPTION] A hardware notched mouse behaves as the posted line events did.
  Its line deltas are accelerated and fractional; every notched run here was
  whole lines, and no such mouse was on the machine. Criterion 4 takes one

## Success criteria

Each is checked by the instrument named. *Probe* is `qa/wheel-travel-probe.html`,
which paints its own `scrollX`, `scrollY`, `innerHeight`, `scrollHeight`,
scroll target and `wheel` / `mousedown` counts;
*poster* is `scripts/qa/wheel-gesture.swift`, which posts a real gesture at a
screen point. Both are added by this change.

1. **Travel, shielded.** 100 pt of precise wheel moves a magnified document
   100 ± 1 pt on screen at board zoom 0.25, 0.5, 1, 1.728, 2 and 3 (today:
   33). Zoom 0.1, where the spike's in-app events also measured 100, is left
   out: the card is 39 pt wide there, too small a target to post at.
   *Probe + poster.*
2. **Travel, borrowed.** The same, with the card borrowed (today: `zoom/3` ×
   100). *Probe + poster.*
3. **Carry.** 30 events of 1 pt at zoom 2 move it 30 ± 1 pt. *`CardWheelTests`
   for the arithmetic; probe + poster for the wiring.*
4. **Notched.** One line moves it 40 ± 1 pt on screen at zoom 1, 1.728 and 2
   (today: 3.3). *Probe + poster, posting line events; a real mouse too where
   one is to hand.*
5. **Reveal.** 100 pt moves a reveal document 100 ± 1 pt at zoom 0.5 and 2
   (today, through the relay: the same by the code — a no-regression check).
   *Probe + poster.*
6. **Across.** 100 pt of horizontal wheel moves a document wider than its
   card 100 ± 1 pt at zoom 2 (today: 33, by the code). *Probe + poster.*
7. **Nested scroller.** With the pointer over an `overflow: auto` element the
   wheel scrolls that element and the window's `scrollY` does not change
   (today: the window scrolls). *Probe + poster.*
8. **Shield.** The probe's `mousedown` count is 0 after every check above on a
   shielded card. *Probe.*
9. **No band.** At zoom 1.728, scrolling for 30 s with reversals, precise and
   notched, shows no white band at either edge, while
   `qa/scroll-band-control.html` — a document that calls a fractional
   `scrollBy` itself — bands beside it in the same run. *The QA sheet's record;
   the spike's count was 0 of 80 frames against 30 of 30.*
10. **Relay gone.** `CardHostMessage` has no `scroll` case; the shim ignores a
    `scroll` message. *The diff, for the case — no test can name a case that is
    gone; `CardShimTests`, for the shim.*
11. `make test` passes; `make qa` passes with no scenario changed.

## Out of scope

- **Terminal wheel travel.** [ASSUMPTION — read from the code, not measured]
  `TerminalView.scrollWheel` counts rows against the cell height in world units
  while the delta is in screen points, so a terminal's travel is `zoom ×` the
  finger. This design unifies the mechanism; that is a separate change.
- A `tarmac dev wheel` verb. It would make criteria 1–8 part of `make qa`, and
  needs the dev protocol's two codecs; the poster covers them meanwhile.
- Which card takes the wheel (`BoardWheel.route`).
- The scroll indicator: 2610.0003.

One PR, branch `perf/144-…`, closing #144:

1. Kit: `CardZoom.wheelScale`, `CardWheel`, with `CardWheelTests` written
   first.

   the `CardZoom`, `HTMLCardView` and `CardShieldView` comments, the shim's,

   through the shield"), which gains that a selected card's document receives
   `wheel` events. That file is embedded text; no Rust code changes.

   WebKit's 40 pt a line on a notched wheel, twelve times today's.
2. **A shielded document sees `wheel` events.** Look-don't-touch becomes *no
   press, no key*.
3. **The conversion sits in the web view**, so a borrowed card is fixed too.
