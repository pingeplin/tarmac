終端卡片「下緣被吃掉」：根因與解法

實測基礎 — WebKit（Tauri 在 macOS 用的引擎家族）＋專案實際的 CSS 與 xterm.js 版本，9 份原始量測資料、15,000+ 組樣本

一句話結論：xterm 的 FitAddon 是拿「含 padding 的 .term-host 盒子」去除以格高（cellH）算出行數，但真正畫字的 .xterm 只拿到「不含 padding 的內容盒」。於是只要餘數落在門檻內（約半數的卡片高度都會），fit 就會多算一行，那一行就從卡片下緣溢出去被裁掉。

所以加 padding 沒用：padding 在被量測的盒子裡面。實測 padding-bottom 設 0 / 16 / 40 px，裁切情形逐格一模一樣（§5）—— 不是治標，是零效果。

為什麼縮放後才發作：rasterScale 改變字級後，格高變成 21 → 31 → 43 → 53 → 63 —— 並不是原字高的等比例放大，行數因此重算而改變，卡片就在「會裁 / 不會裁」之間跳。

10 × zoom裁切量上界（螢幕 px），最多吃掉半行字

0 / 1,630套用修法 1–4 後的裁切數；推薦組合 3＋D′ 為 0 / 815

1量測方法

結論不是讀 code 推論出來的，是量出來的。作法：用專案未經簡化的 theme/*.css、實際版本的 @xterm/xterm 與 @xterm/addon-fit，在 headless 瀏覽器裡重建 Board → CardShell → TerminalCard 的完整 DOM 鏈（wrapper → .card → .card-header → .card-body → termInnerBox → .term-raster-clip → .term-raster-wrapper → .term-host），然後掃過縮放階 × 卡片高度 × 掛載／縮放兩條路徑，逐一量測。（縮放階不是獨立的第三軸 —— rasterScale 是 zoom 的函數，見 §2 的定義。）

  • 引擎：playwright webkit-2336（WKWebView 家族，Tauri 在 macOS 實際使用），dpr 2 與 dpr 1 各跑一輪，另跑 Chrome 對照（資料檔名為 chromium-dpr2.json）。裁切成因、判準公式與行數算法三者完全一致，這不是單一引擎的怪癖；只有欄數會隨 renderer 與 dpr 而異（見 §3）。
  • 字型：專案內建的 JetBrainsMono NFM；字級 termFontSize = 16。
  • Renderer：DOM 與 WebGL 都跑過。應用實際用的是 WebGL，兩者的行算法相同（webgl-tall.json；覆核者另以自己重建的 WebGL harness 重跑，210/210 一致），欄算法不同（見 §3）。
  • 量測欄位：getComputedStyle(host).height、clientHeight、.xterm 版面高、term.rows/cols、cell 尺寸，以及最關鍵的 畫面溢出量＝.xterm-screen 底緣減去 .card-body 底緣（螢幕 px，正值＝被吃掉）。

2根因 A：量錯盒子（主因）

FitAddon.proposeDimensions() 的實作是：

parentH = parseInt(getComputedStyle(term.element.parentElement).height)  // ← .term-host
padding = getComputedStyle(term.element).padding…                        // ← .xterm，目前是 0
rows    = floor((parentH - padding) / cell.height)

兩個關鍵事實（實測）：

  1. getComputedStyle(el).height 回報的是「以該元素自己的 box-sizing 為準」的高度。專案全域是 * { box-sizing: border-box }，所以它含 padding。獨立探針（兩次獨立實作、WebKit 與 Chrome 都一致）：height:300px; padding:8px 10px 16px 的 border-box div 回報 "300px"（內容盒應為 276px）；inset:0 撐滿 400px 父層時回報 "400px"，而它 height:100% 的子元素只拿到 376px —— 這就是 .term-host / .xterm 那一對的最小重現。
  2. padding 掛在 .term-host，但 FitAddon 只會扣掉 .xterm 自己的 padding —— 而 .xterm 沒有 padding（xterm.css 未定義）。

附帶一提：parseInt 會直接截掉小數，rs=1.5 且卡片高度為奇數時 host 是 406.5px、FitAddon 只看到 406 —— 這是另一個次像素誤差來源，但不是本 bug 的主因。

結果：行數是用「含 padding 的盒子」算的，字卻只畫在「不含 padding 的內容盒」裡。多算出來的那一行，先被上緣 padding 往下推 8·rs px，再從下緣溢出。

精確判準

先定義三個貫穿全文的量：zoom 是看板的連續縮放值；rs（rasterScale）是它吸附後的階梯值 —— zoom ≤ 1 時為 1，否則往上吸附到 0.5 的倍數、上限 3（所以 zoom 1.03 與 1.5 都對應 rs 1.5）；card_h 是看板座標下的卡片高度（螢幕高度＝card_h × zoom）。

判準寫在版面座標（.term-host 內部的座標系，與 zoom 無關）。令 H = rs × (card_h − 30) 為 .term-host 的版面高度（30 ＝ header 高度）、cellH 為該 rs 下的格高（一行文字的高度）：

下緣被吃掉  ⟺  (H mod cellH) < (8 + 2) × rs

門檻的兩項是 8·rs（上緣 padding，見下）與 2·rs（根因 C 的邊框溢出 —— 它在螢幕上是 2·zoom px，換算回版面座標要除以 zoom/rs，正好是 2·rs）。這條規則在 fixes2.json 的 294 組實測樣本上全數命中，包含 zoom 1.03、1.6 這類 zoom ≠ rs 的情形（覆核者另以自己的彙總涵蓋 882 個取樣點重驗，同樣全中）。它同時解釋了三件事：

  • 約 48% 的卡片高度會命中裁切條件（10·rs / cellH ≈ 0.48，下稱「中獎」），所以「有時候好、有時候壞」。
  • 拉一下卡片大小就好了：改變 card_h 就是改變餘數。
  • 再縮放又壞掉：改變 rs 就是同時改變 H 和 cellH，餘數重骰。

3觸發器（兼獨立缺陷 B）：rasterScale 讓格子尺寸非線性

xterm 會把 cell 尺寸對齊到整數裝置像素，所以放大字級後的格子不是原本的等比例放大。高度用 ceil(charHeight * dpr)（讀自 xterm.js 與 addon-webgl 的 _updateDimensions，並經實測吻合），兩種 renderer 算法相同，dpr 1 與 dpr 2 實測也相同：

差距雖小，但 floor(H / cellH) 只要跨過一個整數就會多一行或少一行。實測 815 次縮放事件（寬 720px 的卡片、163 種高度，含 11–14 行的小卡與 27–45 行的高卡；163 × 5 階 = 815）：rows 在 41% 的情況下改變（例如 12 → 13 行）。這就是「一縮放就發作」的觸發器 —— 它同時改變 H 與 cellH，把 §2 的餘數重骰一次。

欄數的漂移更大，而且跟 renderer 有關

寬度則兩種 renderer 不同：DOM renderer 用 charWidth * dpr（不取整），WebGL renderer 用 floor(charWidth * dpr)。應用實際載入的是 WebGL（TerminalCard.tsx 探測後掛 WebglAddon，只有失敗才退回 DOM），所以要看的是 WebGL 那一組。再加上 proposeDimensions 為捲軸保留的 14px 是固定值、不隨 rs 縮放，一張 720px 寬的卡片沿著縮放階梯走一趟會變成：

renderer / dprrs 11.522.53最大偏移
WebGL, dpr 2 實際情況7476757475+2
WebGL, dpr 1 外接螢幕7876757476−4
DOM renderer（僅供對照）7374747474+1

意思是：光是縮放看板，就會對 PTY 送出 term_resize／SIGWINCH，讓 vim、htop 這類程式無謂重排 —— 在 1× 螢幕上從 100% 放到 173%（rs 2）欄數會少掉 3 欄，整條階梯最壞是 −4 欄。spec 2609.0007 當初已經明文接受「±1 欄 ±1 行的既有 FitAddon 漂移」—— 那個 ±1 與 DOM renderer 的實測恰好吻合，推測是拿 DOM 的數字估的；實際 renderer 下的漂移超出這個容忍值。TerminalCard.tsx 檔頭那句「fit() 會算出相同的 cols×rows」則與實測不符，應一併更正。

注意：欄數漂移與「下緣被吃掉」是兩個獨立缺陷 —— 本節前半（格高非線性）是後者的觸發器，後半（欄數）則是另一個 bug。行數的算法與 renderer 無關，所以 §2 的診斷、判準公式與 §5 的 padding 結論在 WebGL 下完全成立；只有欄數需要看 WebGL 的數字。

4根因 C：inner box 比 card body 高 2 × zoom px

termInnerBox() 的高度是 calc(var(--card-h) − 30px)，只扣了 header；但 .card 有 border-width: calc(1px * var(--zoom))，.card-body 實際只有 (card_h − 30 − 2) × zoom。實測 zoom 落在 0.5 的倍數上時，溢出量正好是 2 × zoom（1/1.5/2/2.5/3 → 2/3/4/5/6 px）；zoom 落在其他值（1.03、1.6）時邊框會被吸附到裝置像素，量到的是 ~2.00 而非 2.06 —— 上界仍是 2 × zoom。這段溢出被 .card-body 的 overflow:hidden 裁掉。

單獨看它不嚴重（吃掉的是下緣留白），但它是判準公式裡的那個 +2：把它修掉，門檻會從 10·rs 降成 8·rs，命中率由公式推算會從 ~48% 降到 ~38%。（反過來把上緣 padding 設 0、只留那 2px，公式預測 ~10%，實測 13/126 ≈ 10% 吻合 —— 公式在兩端都成立。）只修它不會解決問題。

5為什麼「加 padding」註定無效

現況 .term-host 的 padding-bottom: 16px，是 issue #36 為了「最後一行不要貼著邊框」加的，依據是 spec 2606.0015 §Motivation 的一段推論（原文為英文，以下為中譯）：

「…proposeDimensions() 讀的是父元素（.term-host）的內容高度…
  因為 padding 掛在 .term-host 上，它已經反映在內容高度裡，FitAddon 已經算進去了。
  在那裡增加下緣 padding 只會讓算出來的 rows 變少，不可能裁到內容。
  這一點已對照 addon 的 sizing 邏輯驗證過。」

這段話的每一個技術主張都與實測相反：getComputedStyle 給的不是內容高度、padding 沒有被算進去、rows 不會變少 —— 「加 padding 不可能裁到內容」這個結論建立在假前提上，得到的正是與事實相反的答案。（至於最後那句「已對照 addon 的 sizing 邏輯驗證過」，顯然沒有真的對照。）這是 16px 會 ship 的原因，也是為什麼它從來沒有解決問題。（後來的 spec 2609.0007 換了說法：「padding 對 cols×rows 沒有影響 —— 它只買到視覺留白」。這句話是對的，但它描述的正是 bug 本身：既然沒有影響，行數就是照著含 padding 的盒子算的。）

直接實測：只改 .term-host 的 padding-bottom，其餘不動（每格 126 個樣本＝ 3 個 zoom × 42 種高度，資料檔 padding.json；這一輪只跑到 zoom 2，所以上界是 20px 而不是 §6 的 30px）。

16 px 現況61 / 12620.0 px12

前三列（0 / 16 / 40 px）逐格相同。原因是：下緣 padding 既不影響 rows（它在量測盒內），也不影響字的起始位置（那是上緣 padding）。它唯一的作用是在「沒中獎」時提供下緣留白（gutter） —— 中獎時它完全幫不上忙。真正把字往下推出去的是上緣 padding，這也是為什麼把上緣設成 0 時中獎率會掉到一成。

6解法（皆已實測）

前四個修法是同一件事的不同寫法：讓 FitAddon 量到的盒子，等於 .xterm 真正能畫的盒子。實測都把裁切歸零。最後兩列（D 與它的夾限版 D′）處理的是另一半問題 —— 縮放時的 PTY 抖動；其中只有 D′ 是可以直接上的版本。

各方案細節與風險

1 — padding 移到 .xterm。最貼近 FitAddon 的契約（它本來就扣 term.element 的 padding）。但 xterm 自己的 .xterm-viewport 與 .xterm-helpers 都是相對 .xterm 的 padding 盒定位：捲軸從「內縮 10px」變成貼齊圓角邊框（實測 viewport.right − host.right：−10 → 0），輸入法候選字窗的錨點也位移 (10·rs, 8·rs)。要動它就得補一輪 CJK 輸入 QA。

2 — .term-host { box-sizing: content-box }。因為它是 inset:0 的絕對定位元素，改成 content-box 後 getComputedStyle().height 回報的正好是 .xterm 拿到的內容盒 —— 這就是修法奏效的地方。版面幾何完全不動：實測 clientHeight/offsetHeight 與現況在 fixes2.json 的 588 組中完全相同，改變的只有 getComputedStyle().height 這一個回報值。缺點有兩個：它替全域 * { box-sizing: border-box } 開了一個例外（tokens.css 的註解宣稱那條規則是普遍的），而且它依賴的正是造成這個 bug 的同一個引擎語意 —— 沒有註解的話，下一個人會順手刪掉。

3 — 不要 padding，改用 inset。.term-host 本來就是 position:absolute; inset:0；把 padding 換成 inset: calc(8px * var(--rs)) calc(10px * var(--rs)) calc(16px * var(--rs))，host 的盒子就是內容區，FitAddon 讀到的自然是對的。不需要 box-sizing 例外、不需要改 addon、捲軸與 IME 錨點都不動，留白處露出的是 .card 的 --term-bg（與終端背景同色，肉眼看不出差異）。實測各項數字與方案 2 完全相同。

4 — 自己算格子。把規則抽成 kit/ 的純函式（輸入：內容盒寬高、padding、捲軸保留寬、cell 寬高；輸出：cols×rows），在 mount / ResizeObserver / rasterScale 三處呼叫 term.resize()。換來的是這條規則終於能被 Vitest 單測（符合本專案「純邏輯進 kit 才測得到」的慣例）。實作時要保留 FitAddon 原本的細節：讀公開的 term.dimensions、cell 尺寸為 0 時早退、尊重 options.scrollbar、保留 max(2, cols)／max(1, rows) 夾限，以及既有的 ResizeObserver 0×0 防護。

D — 縮放時鎖住格子，但一定要夾限。rasterScale 變動時不重新 fit，直接沿用原本的 cols0 × rows0。單純鎖住會出事：cellH 在 rs=2 每行比等比例值多 1px，所以超過約 31 行的高卡片會再度裁切（實測值，非推算：final.json 中 25/815 組、最多 15px，全部落在 31 行以上且 rs 2 的組合）。正確寫法是夾限（clamp，只取 min）：

rows = min(rows0, floor(contentH / cellH(rs)))
cols = min(cols0, floor((contentW − scrollbar) / cellW(rs)))

// contentH / contentW = 修好之後 .term-host 的內容盒尺寸
// scrollbar = FitAddon 保留的 14px；rows0 / cols0 = rs 變動前的格子

夾限後實測（DOM renderer）：裁切 0、欄數不再變動、行數只有在真的放不下時才少一行（20%）。文件與 release note 上的承諾要誠實寫成「縮放不會放大 PTY，只會在放不下時縮一行」，而不是「縮放永不改變 PTY」。

＊但欄數的承諾要看螢幕：把 D′ 放到實際的 WebGL renderer 上再量一次（64 組，兩種寬度 × 四種高度 × 四個 rs × 兩種 dpr）：dpr 2（Retina）欄數 0/32 完全不動；dpr 1（外接 1× 螢幕）則 32/32 仍會縮，最多 −5 欄。原因是 WebGL 在 dpr 1 的格寬隨 rs 跳得更兇（每單位 9.0 → 9.5），原本的欄數是真的放不下，夾限只好縮。兩種 dpr 下裁切都是 0、也永遠不會放大格子。所以承諾應該寫成：「縮放不會放大 PTY；在 Retina 上完全不動，在 1× 螢幕上只會在放不下時縮。」

另一條路我也量了、但沒有用：把捲軸保留寬 14px 跟著 rs 縮放（term.options.scrollbar = { width: 14 * rs }）。實測欄數階梯 dpr 2 從 +2 變 +1、dpr 1 從 −4 變 −5 —— 因為欄數漂移的主因是 WebGL 的 floor(charWidth * dpr)，不是捲軸。別花時間在這裡。

建議

  1. 修法 3 ＋ D′（夾限版鎖格子） —— 裁切歸零；Retina 上縮放完全不動格子，1× 外接螢幕上欄數仍會縮（但不會裁切、也不會放大）。若希望這條規則能進 Vitest，改用修法 4 ＋ D′（3 與 4 也可以疊：4 的純函式正好就是 D′ 夾限用的那個式子）。
  2. 順手修根因 C：termInnerBox() 的高度改成 calc(var(--card-h) - 32px)（header 30 + 上下邊框 2）。注意這會動到 termZoom.test.ts（它斷言「card-h 減 header」），是測試看得見的改動，建議獨立一個 commit。
  3. 更正 spec 2606.0015 那段錯誤前提，否則下次還會有人依它推論。docs-check 只驗路徑存在，不驗內容真偽。
  4. 不要再加 padding（§5 已證明零效果）；不用查 useLayoutEffect 的時序 —— 實測 fixes2.json 全部 1,176 組「先改 fontSize 再 fit」「ResizeObserver 事後再 fit」「一開始就用 rs 掛載」三者結果完全相同，現有時序設計是對的。

取捨：留白會浮動

修好之後，原本被拿去畫「半行字」的餘料會變成下緣留白：在 100% 縮放下是 14–35 螢幕 px（實測；zoom 3 的極端值到 102，理論上界 16·rs − 2·rs + cellH(rs) ≈ 105）。留白下限是 14 而不是 16，正是因為根因 C 那 2px 還在吃它 —— 這也是為什麼建議順手一起修。若要讓留白恆定，額外的作法是在 resize 結束時把卡片高度吸附到整數行（以 rs=1 為基準：card_h = 32 + 24 + n × cellH(1)，32 ＝ header 30 + 上下邊框 2，24 ＝ 上下 padding 8+16）；這是獨立的體驗改善，不是修 bug 的必要條件。

7落地檢查點

  • 單測：proposeGrid() 的純函式測試 —— 邊界要蓋到 H mod cellH == 0（裁切量最大的那格）、H mod cellH == 10·rs（第一格不該裁的），以及夾限生效的高卡片。CSS 行為本身無法單測，建議把這次的 harness 存成一份不進 CI 的驗證腳本，日後動到 .term-host 時再手動跑一次。
  • 既有測試的影響面：termZoom.test.ts 會變紅（若修根因 C）。kit-build.test.ts 斷言 kit 樣式表不含 .term-host —— 這一項不會變紅，列出來是因為容易誤判：規則要加的位置 app-only.css 不在 kit 的 import closure 內，所以在那裡動 .term-host 的樣式是安全的；前提是修法 1 的選擇器要寫成 .term-host .xterm，不要用裸的 .xterm。
  • 手動 QA：固定一張卡片，從 100% 依序縮放到 300% 再回來，每一級都確認最後一行完整、下緣留白存在；再拉一次卡片大小重複一輪。走修法 1 的話另加一輪 CJK 輸入法候選字窗位置檢查。
  • 回歸風險：修好後卡片的 rows 會少 1–2 行（實測 86% 少 1 行、14% 少 2 行 —— 那些本來就是畫不下的行），既有 board 的 PTY 會收到一次 resize —— 這是正確行為，但值得在 release note 提一句。
